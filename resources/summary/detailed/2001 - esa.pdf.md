# Detailed Summary: APAF Software Requirements Specification

## Background and Scope
The ASPERA-3 Processing and Archiving Facility (APAF) is a ground data system for the Mars Express mission, responsible for processing telemetry from the ASPERA-3 instrument package. Its primary goals are to acquire telemetry via NISN, process data into Instrument Data File Set (IDFS) format, distribute data to the science team, provide web-based displays, maintain a local archive, and submit validated data to the Planetary Data System (PDS) within six months of receipt. Non-goals include operating in multiple states/modes, imposing safety hazards, or having specific training requirements for developers.

## Stakeholders Matrix and Use Cases
*   **IRF Principal Investigator (Prof. Rickard Lundin):** Oversees the scientific objectives and validation of the ASPERA-3 experiment data.
*   **IRF Project Manager (Herman Andersson):** Manages the overall ASPERA-3 project deliverables and coordination with ESA.
*   **SwRI Principal Investigator (Dr. J. David Winningham):** Provides scientific leadership and ensures the APAF system meets NASA program-level requirements.
*   **SwRI Software Project Manager (Sandee Jeffers):** Leads the APAF software development, ensuring requirements are met and the system is delivered on schedule.
*   **SwRI Software Team Member (Carrie Gonzalez):** Implements and tests the APAF software components and data processing algorithms.
*   **ASPERA-3 Co-Investigators (Co-I's):** Receive processed IDFS data for scientific analysis and contribute to instrument-specific requirements.
*   **European Space Agency (ESA) / ESOC:** Provides the raw ASPERA-3 and Mars Express Orbit/Attitude (OA) telemetry data via the Data Disposition System.
*   **NASA Planetary Data System (PDS):** Receives the final, calibrated, and validated ASPERA-3 IDFS data sets for long-term public archival.

**Main Scenarios:** 1) Daily acquisition of telemetry from ESOC. 2) Processing of raw telemetry into IDFS data sets for all instrument components. 3) Generation of cleaned-up telemetry files if not provided by ESOC. 4) Archiving of raw telemetry and IDFS data locally. 5) Distribution of data products to Co-I's within 24 hours. 6) Provision of password-protected and public web-based data displays. 7) Submission of PDS-compliant data within six months of acquisition. 8) Provision of data access and analysis software to the Co-I team.
**Exception Scenarios:** Handling transmission or processing errors that delay the 24-hour distribution SLA.

## Business Process
**Main Process: Data Ingest, Processing, and Distribution**
1.  **Trigger:** Receipt of new ASPERA-3 and MEX OA telemetry files from ESOC via NISN.
2.  **Input:** Raw telemetry data packets.
3.  **Step 1:** Acquire and validate incoming telemetry data.
4.  **Step 2:** Generate cleaned-up telemetry intermediate files (if not provided by ESOC).
5.  **Step 3:** Process cleaned telemetry through instrument-specific algorithms to create IDFS data sets.
6.  **Step 4:** Archive raw telemetry, intermediate files, and IDFS data sets to the local SwRI archive.
7.  **Step 5:** Update web-based displays with the most current processed data.
8.  **Step 6:** Distribute IDFS data sets and intermediate files to ASPERA-3 Co-I's.
9.  **Step 7:** Periodically validate and calibrate data for PDS submission.
10. **Step 8:** Submit final, PDS-compliant IDFS data sets to NASA PDS.
11. **Output:** Distributed IDFS data, archived data sets, PDS submissions, and web displays.

**Key Branch A: Web Display Generation**
*   Trigger: New IDFS data set is available.
*   1. Generate plots and summaries as defined in Plot Interface Definition Files (PIDF).
*   2. Update public website with non-sensitive data.
*   3. Update password-protected science analysis website with full data access.
*   4. Log update activities.

**Key Branch B: Error Handling & Re-processing**
*   Trigger: Processing error or data corruption detected.
*   1. Log error and halt affected processing stream.
*   2. Notify operators via system logs.
*   3. Allow operator to initiate re-processing from archive.
*   4. Resume normal processing once resolved.

## Interfaces and Integrations
*   **ESOC Data Disposition System (DDS):** Inbound. Interaction: Telemetry acquisition. Input: System parameters from DDID. Output: Raw telemetry files. SLA: Daily data delivery.
*   **NASA Integrated Services Network (NISN):** Bi-directional. Interaction: Data transport network. Input/Output: Telemetry and distributed data files. SLA: Reliable network connection.
*   **Local SwRI Archive System:** Outbound. Interaction: Data storage. Input: Telemetry and IDFS files. Output: Archive confirmation. SLA: High availability for re-processing.
*   **ASPERA-3 Co-I Distribution System:** Outbound. Interaction: Data distribution. Input: IDFS data sets. Output: Distributed files to team members. SLA: Within 24 hours of error-free acquisition.
*   **NASA Planetary Data System (PDS):** Outbound. Interaction: Data submission. Input: Validated IDFS data sets. Output: Submission receipt. SLA: Submission within 6 months of data acquisition.
*   **www.ASPERA-3.org Web Server:** Bi-directional. Interaction: Information exchange and display. Input: IDFS data, display configs (PIDF). Output: Web pages and plots. SLA: Password protection for sensitive data.
*   **APAF Operations Console:** Inbound. Interaction: Operator control and monitoring. Input: Commands, configuration. Output: System logs, status. SLA: Documented in Operations Procedures.

## Acceptance Criteria
*   **Given** new ASPERA-3 telemetry is available from ESOC, **when** the APAF system executes its daily processing, **then** IDFS data sets for all virtual instruments are created and archived within 24 hours.
*   **Given** a validated IDFS data set is ready for distribution, **when** the distribution process runs, **then** all designated ASPERA-3 Co-I's receive the data electronically.
*   **Given** a processing error occurs, **when** the system encounters the error, **then** it logs the error, halts the affected process, and notifies the operator without corrupting archived data.
*   **Given** a full mission data set has been calibrated, **when** the PDS submission milestone is reached, **then** the data is delivered to PDS in a compliant format no later than six months after acquisition.

## Non-functional Metrics
*   **Performance:** Process daily telemetry volume to generate IDFS data sets within 24-hour window. Support concurrent web access for multiple science team members.
*   **Reliability:** System uptime to support daily automated processing. Built-in error handling to ensure data integrity.
*   **Security/Privacy:** Password protection for pre-public science data on web server. Secure data transmission to Co-I's.
*   **Compliance:** Output data formats must comply with PDS standards. Development follows NASA Program-Level Requirements.
*   **Observability:** Comprehensive system logging for all processing steps and operator actions. Logs accessible for troubleshooting.

## Risk List and Mitigation Strategies
1.  **Risk:** Delays in ESOC providing telemetry or interface documents (DDID). **Mitigation:** Maintain flexible ingest module; use preliminary packet definitions for development.
2.  **Risk:** Changes to telemetry packet formats after launch. **Mitigation:** Design processing algorithms to be configurable via external definition files.
3.  **Risk:** Higher-than-anticipated data volumes affecting the 24-hour processing SLA. **Mitigation:** Profile and optimize processing code; ensure archive and hardware can scale.
4.  **Risk:** Network issues (NISN) disrupting data acquisition or distribution. **Mitigation:** Implement robust retry logic and offline notification for operators.
5.  **Risk:** Delays in science team calibration validation affecting 6-month PDS submission deadline. **Mitigation:** Work closely with IRF to define and automate validation steps early.
6.  **Risk:** Insufficient archive storage capacity for mission-long data. **Mitigation:** Define data retention policies in PDMP; plan for storage expansion.
7.  **Risk:** Evolving PDS compliance requirements. **Mitigation:** Engage with PDS early and use standard IDFS formats designed for compatibility.
8.  **Risk:** Key personnel turnover during the long project lifecycle (1999-2007). **Mitigation:** Comprehensive documentation (SDDs, OPD) and knowledge sharing within the team.
