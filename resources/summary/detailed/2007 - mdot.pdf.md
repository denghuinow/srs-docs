# Detailed Summary: VII Data Use Analysis and Processing (DUAP) System

## Background and Scope
The DUAP system is a research prototype for the Michigan Department of Transportation (MDOT) to evaluate the utility of Vehicle Infrastructure Integration (VII) data, integrated with other sources, for enhancing safety, mobility, and asset management. Its scope includes collecting, consolidating, converting, and communicating VII and related transportation data to support operational decisions and demonstrations. Non-goals include being a fully operational, production-ready system and handling all potential future data sources or algorithms not identified for the prototype phase.

## Stakeholders Matrix and Use Cases
*   **Transportation Agency (TA) Operators (Local/Regional/State):** Monitor incidents and traffic flow to minimize impact and determine response actions.
*   **TA Maintainers:** Maintain roadways and bridges, responding to incidents and daily condition changes.
*   **TA Asset Managers:** Analyze collected data to determine cost-effective annual programs and projects.
*   **System Administrators:** Administer systems to ensure collected data is available for use by other stakeholders.
*   **TA Management:** Supervise agency staff working with raw and analyzed data.
*   **TA Contractors:** Perform specific contracted jobs in collaboration with agency staff.
*   **Travelers:** Use trip information from various sources to plan commutes or trips, considering delays and alternative routes.
*   **Emergency Services:** Use roadway data to respond to incidents, evaluate traffic impact, and determine resource needs.
*   **Researchers/University Personnel:** Analyze collected data based on agency requirements, requiring accurate and complete datasets.
*   **Michigan Transportation Research Board (MTRB):** Advises on transportation research needs, prioritization, and information exchange.
*   **Automobile Manufacturers (OEMs):** Provide vehicle equipment and communication systems that enable VII data transmission.
*   **VII Network Operating Entity:** Operates, monitors, and maintains the flow of VII data and the supporting infrastructure.

**Main Scenarios:** 1) Collect probe, traffic, and weather data from multiple sources. 2) Process raw data to derive traffic metrics (speed, queue length), incidents, and road conditions. 3) Publish processed data and alerts in standard formats (e.g., SAE J2354) for external systems. 4) Present processed information via web-based browsers for human operators. 5) Archive data for long-term analysis.
**Exception Scenarios:** 1) Handling data with latency or quality issues from vehicle sensors. 2) Managing privacy concerns related to potentially identifiable probe data. 3) Restricting system access based on user authorization. 4) Logging all system transactions for audit and debugging.

## Business Process
**Main Process: Data Ingestion to Publication**
1.  **Trigger:** Subscription request for probe data is sent to the VII Proof of Concept Probe Data Service.
2.  **Input:** Raw probe, traffic, and weather data streams are received from various subscribed sources (e.g., VII POC, MITS Center, Clarus).
3.  **Process:** Incoming data is cached in Dynamic Data services for fast access.
4.  **Process:** Computational services apply algorithms to cached data to derive new information (e.g., speed, incidents, potholes).
5.  **Process:** Derived and raw data are archived to Persistent Data services for long-term storage.
6.  **Process:** Output services format processed data into standard structures (e.g., SAE J2354 XML) for external consumption.
7.  **Output:** Formatted data is published to external systems (e.g., TMS, SEMSIM) and presentation layers.
8.  **Output:** Presentation services render data via web browsers for human users to query and view.

**Key Branch A: System Administration**
1.  **Trigger:** Authorized administrator logs in.
2.  **Process:** Administrator adds, modifies, or deletes system services (Input, Computational, Output, Presentation).
3.  **Process:** Administrator configures user access rights and views system logs.
4.  **Output:** System configuration is updated, and access is controlled.

**Key Branch B: Alert Generation**
1.  **Trigger:** A computational service detects a threshold has been exceeded (e.g., congestion, ice).
2.  **Process:** An alert is generated and formatted by an Output service.
3.  **Process:** The alert is published to subscribed external systems.
4.  **Output:** Alert is displayed via presentation services and/or sent to external interfaces.

## Interfaces and Integrations
*   **VII Proof of Concept Probe Data Service:** Inbound; X-031 interface; Input: subscription request; Output: continuous stream of SAE J2735 probe data; SLA: Near real-time data delivery.
*   **MITS Center ATMS:** Inbound; MITS traffic data interface; Input: connection request; Output: speed, volume, occupancy data; SLA: To be determined in prototype design.
*   **Clarus System:** Inbound; Standard interface; Input: connection request; Output: weather data elements (Appendix D); SLA: To be determined.
*   **TMS (Transportation Management System):** Outbound; TMS interface format; Input: processed traffic/incident data; Output: formatted data for operational use; SLA: To be determined in prototype design.
*   **SAE J2354 Consumer Systems:** Outbound; SAE J2354 XML format; Input: processed traveler, event, or link traffic data; Output: standardized XML messages; SLA: Compliance with SAE standard.
*   **Web Browser Clients:** Outbound; HTTP/HTML/JavaScript/XML; Input: user queries; Output: interactive map and tabular displays; SLA: Support for specified browser technologies (IE 6+, Firefox 2+).
*   **Oracle Database:** Internal; JDBC/SQL; Input: SQL commands; Output: query results; SLA: Conformance to MDIT IT standards.
*   **Administrative Client:** Internal; System-specific interface; Input: configuration commands; Output: configuration status and logs; SLA: Restricted to authorized users.

## Acceptance Criteria
**Capability: Incident Detection from Probe Data**
*   Given probe vehicle data indicating sudden deceleration and stopped vehicles on a freeway segment, when the incident detection computational service processes the data, then an incident record with type and location shall be generated and cached.
*   Given no anomalous patterns in the probe vehicle data stream, when the incident detection service processes the data, then no new incident records shall be generated.

**Capability: Data Presentation via Web Browser**
*   Given a system operator with valid credentials, when they access the traffic information browser and selects a geographic area, then a map displaying traffic icons for that area shall be rendered.
*   Given a published weather alert for a specific roadway, when a user queries incident information for that area, then the alert shall be visible in the incident information browser display.

## Non-functional Metrics
*   **Performance:** System shall cache data for 1 week; data shall be accessible as soon as it is cached.
*   **Reliability:** All service transactions (Input, Administrative, Dynamic Data, etc.) shall be logged.
*   **Security:** System shall restrict access to authorized users and keep records of user access.
*   **Compliance:** System shall conform to IT standards established by the Michigan Department of Information Technology (MDIT).
*   **Observability:** System shall log data transactions for all core services (Input, Dynamic Data, Computational, etc.).

## Milestones and Release Strategy

## Risk List and Mitigation Strategies
1.  **Privacy/Data Ownership:** Probe data, while anonymized, could be correlated to identify vehicles. *Mitigation:* Establish operational policies for data use and comply with USDOT VII program policies.
2.  **Third-party Data Limitations:** Use or redistribution of data from commercial sources may be restricted. *Mitigation:* Consider limitations in service agreements and design DUAP to function with available data.
3.  **Data Latency:** VII data is "near real-time," causing delays from collection to use. *Mitigation:* Design consuming applications to evaluate data suitability based on source and timestamps.
4.  **Data Quality:** Vehicle sensor calibration and degradation may affect data. *Mitigation:* Implement data quality checking computational services and enable applications to use quality flags.
5.  **Variable Data Volume:** Data inflow depends on VII vehicle penetration and RSE deployment. *Mitigation:* Control factors during evaluation; for production, plan scalability based on RSE rollout.
6.  **Evolving Computational Needs:** New algorithms will be discovered during the research project. *Mitigation:* Design a flexible, service-oriented architecture capable of adding new Computational Services.
7.  **Integration Complexity:** Numerous external systems with undetermined interface formats. *Mitigation:* Define specific interface formats during prototype design for each required integration.
8.  **Compliance with MDIT Standards:** Ensuring all software and database components meet state IT standards. *Mitigation:* Consult with MDIT throughout the project and document any exceptions for approval.
