# Detailed Summary: Project ZNIX Framework

## Background and Scope
Project ZNIX is a research and development effort to create an object-based, application-independent information management framework. It aims to refine traditional systems by shifting focus from managing applications to managing meaningful information, allowing users to access and organize data in logical, user-defined ways. The scope covers the high-level design of the ZNIX Framework, including its core services, public API, and proxy mechanism for third-party application integration. Non-goals include multi-user support, networking capabilities, and compatibility with operating systems beyond Windows 2000/XP at this stage.

## Stakeholders Matrix and Use Cases
*   **End User (Home User/Manager/Researcher):** Interacts with the framework via a GUI browser to manage personal information hierarchically, with minimal training required.
*   **ZNIX-Aware Application Developer:** Utilizes the public API to build applications that create, modify, query, and manage Entities and their relationships within the framework.
*   **ZNIX Framework System Architect:** Designs the core framework services, data store, and proxy mechanism to ensure integration with the OS and target applications.
*   **Open Source Community Contributor:** Reviews, uses, and potentially contributes to the project's source code hosted on distribution platforms.

**Use Cases:**
1.  **Main: User browses information hierarchy.** User opens the ZNIX browser (or integrated Windows Explorer view) to navigate their stored Entities and Associates in a folder-like structure.
2.  **Main: User archives information to removable media.** User selects a set of related information (e.g., all data for a "Person" Entity) to archive to a CD-ROM or USB drive, leaving a placeholder in the central store.
3.  **Main: User creates relationships between documents and Entities.** After editing a document, the user invokes a special ZNIX GUI to visually link the document to relevant Entities (e.g., people, projects), defining its semantic context.
4.  **Main: Framework captures outbound email.** The framework intercepts an email before it is sent, creates an Associate for the message body, and links it to recipient Entities (creating them if necessary).
5.  **Main: Framework captures inbound email.** The framework fetches an email from a POP3 server, creates an Associate for it, and links it to a sender Entity.
6.  **Main: Developer queries for Entities via API.** A ZNIX-aware application uses the public API to execute a search for Entities based on user-defined criteria.
7.  **Exception: User attempts to access archived data.** When a user searches for an archived Entity, the framework informs them of its archived status and may prompt for the corresponding storage media.
8.  **Exception: Malicious script attempts data access.** The framework security layer prevents scripts from remote websites from accessing or corrupting the managed information store.

## Business Process
**Main Process: Information Ingestion and Relationship Mapping**
1.  **Trigger:** User action within a supported third-party application (e.g., sending email, saving a document) or a direct framework command.
2.  **Input:** Raw data from the application (email content, document, URL) and user context (recipient names, project tags).
3.  The framework identifies the data type and determines if it corresponds to a new or existing Entity or Associate.
4.  For data linked to people (e.g., email), the framework creates or retrieves corresponding "Person" Entities.
5.  An Associate record is created for the data item (e.g., email body, document reference).
6.  The framework establishes defined relationships (links) between the new Associate and the relevant Entities.
7.  All data (Entities, Associates, relationships) is persisted to the centralized data store.
8.  **Output:** The information is integrated into the user's hierarchical view and is accessible via the browser or API.

**Key Branch A: Manual Relationship Definition via GUI**
1.  **Trigger:** User invokes the relationship GUI from within an application or the ZNIX browser.
2.  **Input:** The target data item (e.g., an open document) and the current set of Entities.
3.  User visually draws links from the data item to one or more Entity symbols.
4.  The framework saves the document and records the user-defined relationships.

**Key Branch B: Archiving to Removable Media**
1.  **Trigger:** User selects a set of information (e.g., an Entity and its related Associates) and chooses an archive command.
2.  **Input:** The selected data subset and target removable drive.
3.  The framework copies the data to the media.
4.  It replaces the original data in the central store with a lightweight placeholder indicating the archive location.

## Domain Model
Core entities representing the information managed by the ZNIX Framework.
*   **Entity:** A first-class citizen with a unique, independent identity. (Fields: ID [required, unique], Name, Type/Category [required], CreationDate)
*   **Associate:** A data unit whose identity depends on its relationship to one or more Entities. (Fields: ID [required, unique], Content/Reference [required], DataType, CreationDate)
*   **Relationship:** A link defining the association between an Associate and an Entity. (Fields: ID [required, unique], SourceEntityID [required, reference to Entity], TargetAssociateID [required, reference to Associate], RelationshipType)
*   **Category:** A user-definable classification for Entities (e.g., People, Email, Project). (Fields: Name [required, unique])
*   **Archive Record:** A placeholder for data that has been moved to removable media. (Fields: OriginalEntityID [reference to Entity], ArchiveMediaID, ArchivePath, ArchiveDate [required])
*   **User Session:** Represents an active interaction with the framework (single-user mode). (Fields: SessionID [required, unique])
*   **Data Store:** The centralized repository. (Conceptual entity; implied by the system).

## Interfaces and Integrations
*   **ZNIX Public API (System: ZNIX Framework, Direction: Outbound, Theme: Programmatic Entity & Relationship Management):** Input: API calls for CRUD operations on Entities/Associates, queries. Output: Entity/Associate data, query results. SLA: Must expose functionality similar to .NET System.IO APIs for listings.
*   **ZNIX Proxy Mechanism (System: ZNIX Framework, Direction: Inbound, Theme: Integration with ZNIX-Unaware Applications):** Input: Data streams and events from applications like Outlook Express, Internet Explorer, Word 2003. Output: Intercepted/captured data fed into the framework's ingestion process. SLA: Must support versions specified in Table 3.10.3-A for email, web, and document capture.
*   **ZNIX Browser GUI (System: ZNIX Framework, Direction: Outbound, Theme: User Information Browsing & Management):** Input: User navigation and command actions. Output: Hierarchical display of Entities/Associates, relationship editing interface. SLA: UI must be intuitive for Windows users, resembling Windows Explorer.
*   **Windows OS Integration (System: Windows OS, Direction: Inbound, Theme: Shell Integration):** Input: OS events, file system metaphors. Output: Framework services and potentially an Explorer-integrated view. SLA: Must comply with Windows 2000 Logo Requirements.

## Acceptance Criteria
**Capability: Centralized Information Capture from Email**
*   Given the user sends an email via a supported client (e.g., Outlook Express),
    When the framework intercepts the message,
    Then an Associate is created for the email body and linked to "Person" Entities for each recipient.
*   Given an email is received via POP3,
    When the framework fetches it,
    Then an Associate is created and linked to a "Person" Entity for the sender.

**Capability: Hierarchical Information Browsing**
*   Given the central store contains Entities and Associates,
    When the user opens the ZNIX browser,
    Then they can navigate a hierarchical, folder-like view reflecting the defined relationships.
*   Given a user has archived an Entity to removable media,
    When they search for that Entity in the browser,
    Then they are notified of its archived status.

**Capability: Relationship Management via API**
*   Given a developer is building a ZNIX-aware application,
    When they use the public API to create a relationship between an Entity and an Associate,
    Then the relationship is persisted and affects the hierarchical view.

## Non-functional Metrics
*   **Performance:** Framework shell memory utilization shall not exceed 40 MB RAM. System must run on a Pentium III 1-GHz with 256 MB RAM.
*   **Reliability:** Mean Time Between Failures (MTBF) shall exceed 3 months.
*   **Security:** Must guard against data access by remote malicious scripts and unintended corruption by the user.
*   **Compliance:** Must conform to Windows 2000 Logo Requirements and ISO 10646 (Unicode UTF-8/16) character encoding.
*   **Observability:** The project distribution website shall include user feedback and feature wish-list mechanisms.

## Milestones and Release Strategy
1.  Finalize core framework architecture and data store design.
2.  Implement basic Entity/Associate/Relationship model and public API skeleton.
3.  Develop proxy mechanism integrations for key applications (Email, Web).
4.  Build ZNIX browser GUI with hierarchical navigation.
5.  Implement archiving functionality and relationship-defining GUI.
6.  Alpha release to open source community for feedback, followed by beta and v1.0 under LGPL/GPL licenses.

## Risk List and Mitigation Strategies
1.  **Risk:** Performance degradation with large information stores. **Mitigation:** Implement efficient data indexing and querying from the start; profile regularly.
2.  **Risk:** Third-party application updates break proxy integrations. **Mitigation:** Design proxy interfaces for robustness; assume compatibility with listed versions per assumptions.
3.  **Risk:** Low adoption by developers for the ZNIX-aware API. **Mitigation:** Provide comprehensive Developer's Guide; promote the proxy mechanism for easier legacy app integration.
4.  **Risk:** User confusion in defining complex relationship hierarchies. **Mitigation:** Ensure GUI is highly intuitive, mimicking known Windows paradigms; provide contextual help.
5.  **Risk:** Data corruption during archiving/retrieval process. **Mitigation:** Implement robust transaction and verification steps for archive operations.
6.  **Risk:** Insufficient resources in target hardware (256MB RAM). **Mitigation:** Strict adherence to the 40 MB memory budget; aggressive optimization and profiling.
7.  **Risk:** Security vulnerabilities in dependent third-party software. **Mitigation:** Acknowledge dependency on their security; framework must add an additional security layer.
8.  **Risk:** Project scope creep due to open-source feature requests. **Mitigation:** Maintain clear v1.0 scope; manage community input through a structured wish-list and roadmap.
