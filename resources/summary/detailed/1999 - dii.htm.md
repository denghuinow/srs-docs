**Detailed Summary**

**Background and Scope**
This document defines the software requirements for the XML Services (XS) functional area within the Defense Information Infrastructure (DII) Common Operating Environment (COE). The XS provides infrastructure services for mission and support applications using XML technology, focusing on the registration of terms and structures, design of XML schemas, and generation/consumption of XML documents. Its primary goal is to isolate vendor-unique implementations and provide data management functions for accessing distributed databases to achieve interoperability. Non-goals include defining specific personnel or training requirements, which are left to the embedding system developers.

**Stakeholders Matrix and Use Cases**
*   **DII COE AOG Data Access Services Technical Working Group (DATATWG) / SSD-MD Sub-panel**: Responsible for preparing and specifying the requirements for the XML Services.
*   **Defense Information System Agency (DISA)**: The sponsoring agency for whom the specification is prepared and the ultimate recipient of the COE components.
*   **COE Chief Engineer**: Approves Points of Contact (POCs) for Communities of Interest (COIs) and mediates unresolved disputes regarding XML tags and semantics.
*   **COE Data Engineering Team**: Analyzes submitted tags and semantics to identify opportunities for consolidation and standardization.
*   **Community of Interest (COI) Point of Contact (POC)**: Manages the lifecycle (submission, review, approval, status transition) of information resources (e.g., tags, DTDs) within their specific domain.
*   **Application Developers (Producers/Consumers)**: Use the registry to discover, reuse, or submit XML tags and schemas for their applications to ensure interoperability.
*   **System/Data/Database Managers**: Utilize XS services for administrative tasks such as managing user permissions, tuning services for workload, and overseeing data models within the registry.
*   **DISA Configuration Manager (CM)**: Responsible for the distribution of the finalized XS product to system developers.

**Main Use Case Scenarios:**
1.  **Submit New XML Tag for Registration**: A developer (Producer) downloads the submission package, fills out forms with metadata and artifacts (DTD, sample document), and submits them via email/FTP or an online process for review and population into the registry.
2.  **Discover and Reuse an Existing XML Tag**: A developer (Consumer) searches the registry via various criteria (name, author, substring), views tag relationships (hierarchy, data type, versions), and downloads the selected information resource for use in their application.
3.  **Review and Approve a Submission**: A COI POC or Manager reviews a submitted tag package, checks for conflicts with standards and existing tags, and approves or rejects the submission, potentially notifying the submitter.
4.  **Manage Registry Content**: A Manager creates user accounts, defines naming conventions and metadata standards, and monitors changes to data models within the registry.
5.  **Design an XML Schema**: A developer uses design services to structure a document, check it against standards, and create or reference existing tags and semantic structures extracted from the registry.
6.  **Generate an XML Document**: The service generates a document that includes a schema, checks it for conformance (well-formed, valid), and can render or transmit it with sufficient metadata for alternate views.
7.  **Consume an XML Document**: A parser (DOM, SAX) is used to check an incoming document for conformance, validate it against a schema, and extract semantically valid views or disassemble it into a relational representation.
8.  **Operate in a Degraded Environment**: The system allows administrators to dynamically adjust session time-out values based on network performance to maintain service availability during communications degradation.

**Business Process**
*   **Main Process: Register and Manage XML Information Resource**
    1.  **Trigger/Input**: Developer identifies need for a new or modified XML tag/schema.
    2.  Developer reviews existing registry content.
    3.  Developer prepares Information Resource Submittal Package (metadata, DTD, sample document).
    4.  Developer submits package (online or batch) to the registry.
    5.  System parses submission and populates staging area.
    6.  Assigned COI POC/Manager reviews submission against standards and existing content.
    7.  POC/Manager approves or rejects the submission.
    8.  **Output**: Approved metadata is populated into the live registry; submitter is notified. Approved artifacts (DTDs) become available for discovery and download.

*   **Key Branch A: Submission Rejection**
    1.  **Trigger**: Submission fails review (e.g., conflict, insufficient info).
    2.  POC/Manager annotates the submission with rejection reason.
    3.  Submitter is notified of the rejection and reason.
    4.  Submission status is set to "Rejected" in the registry log.

*   **Key Branch B: Dynamic Operational Adjustment**
    1.  **Trigger**: Detection of degraded communications environment.
    2.  Network/System manager identifies affected services.
    3.  Manager redefines session time-out parameters for relevant data management services.
    4.  New parameters are applied for subsequent user sessions.

**Domain Model (Core Entities)**
*   **Information_Resource**: Core entity representing any registrable item (required fields: ID, Name, Type, Status, Definition, Submitter_ID).
*   **XML_Element**: A type of Information_Resource representing a tag (required fields: Parent_Element_ID [reference], Data_Type).
*   **XML_Spec**: A type of Information_Resource representing a schema/DTD (required fields: Specification_Text, Version).
*   **Metadata**: Attributes describing an Information_Resource (required fields: Resource_ID [reference], Name, Value).
*   **Association**: Defines relationships between Information_Resources (required fields: From_Resource_ID [reference], To_Resource_ID [reference], Association_Type [e.g., uses, version_of]).
*   **Submission**: A request to add/modify registry content (required fields: Package, Submitter_ID, Date, Status).
*   **Community_of_Interest (COI)**: A domain group (required fields: Name, POC_ID).
*   **User**: Interacts with the registry (required fields: User_ID, Role, COI_Affiliation [reference]).

**Interfaces and Integrations**
*   **External Developer Submission**: Direction: Inbound. Interaction: Email/FTP or Web Form. Input: Zipped Information Resource Submittal Package. Output: Submission receipt/acknowledgment. SLA: Submission package format and content as defined in Appendix A.
*   **Registry Query API**: Direction: Inbound. Interaction: Standard API (Appendix B). Input: Search criteria (tag name, author, substring). Output: List of matching Information Resources with metadata. SLA: Response time for search queries.
*   **COE Management Services**: Direction: Outbound. Interaction: API for administration. Input: User management, configuration changes. Output: Status/confirmation. SLA: Compliance with COE management interfaces.
*   **COE Distributed System Services**: Direction: Outbound. Interaction: API for communications and distribution. Input: Data for network transmission. Output: Delivery status. SLA: Reliable messaging for notification services.
*   **COTS RDBMS (Oracle, Sybase, Informix)**: Direction: Outbound. Interaction: Internal, transparent interface. Input: SQL/data operations. Output: Query results/transaction status. SLA: Support for ANSI standard SQL (FIPS PUB 127-2).
*   **Legacy Data Systems (DBIF, DAC)**: Direction: Outbound. Interaction: Internal, transparent interface. Input: Data access requests. Output: Data. SLA: Location transparency for applications.

**Acceptance Criteria**
*   **Capability: Tag Discovery**
    *   Given a Consumer wants to find tags related to "country codes", When they perform a substring search on the tag name and definition, Then the system returns a list of relevant XML_Element resources (e.g., CTRY_CD) with their definitions and associated DTDs.
*   **Capability: Schema Validation**
    *   Given an application has generated an XML document, When the "Generate" service checks it for conformance, Then the document is validated as well-formed and against its referenced schema, and any errors are reported.
*   **Capability: Submission Workflow**
    *   Given a Producer submits a new tag package via the online form, When the COI POC reviews and approves it, Then the tag's status changes to "Approved" in the registry and becomes discoverable to all Consumers.

**Non-functional Metrics**
*   **Performance**: Session time-out values shall be user-definable and dynamically adjustable. Query response times for registry searches shall meet operational needs.
*   **Reliability**: The registry software shall be portable and execute on all COE-compliant platforms. Services must operate in both fixed (static) and deployed (dynamic) environments.
*   **Security**: Access control for registry submissions and management shall be enforced. Naming conventions shall not conflict with DoD data standards.
*   **Compliance**: XS components shall adhere to COE compliance level requirements described in the I&RTS. Must support qualification methods (Test, Demonstration, Analysis, Inspection).
*   **Observability**: The system shall provide capabilities for managers to monitor changes to data models recorded in the Registry.

**Risk List and Mitigation Strategies**
1.  **Risk**: Proliferation of inconsistent and redundant XML tags across systems. **Mitigation**: Establish a centralized registry with review/approval workflow and encourage reuse through discovery tools.
2.  **Risk**: Detailed internal/external interface specifications (Appendices B & C) are not yet defined. **Mitigation**: Specify these interfaces during the subsequent design phase of the COE XS architecture.
3.  **Risk**: Operating in degraded communications environments. **Mitigation**: Design services to allow dynamic adjustment of session parameters (e.g., time-outs) based on network performance.
4.  **Risk**: Ensuring semantic understanding and interoperability of registered terms. **Mitigation**: Require detailed definitions and synonyms in submissions, and establish rules for maximum semantic clarity.
5.  **Risk**: Integration with multiple COTS RDBMS products (Oracle, Sybase, Informix). **Mitigation**: Define transparent internal interfaces that isolate vendor-unique implementations.
6.  **Risk**: Managing the lifecycle and versioning of information resources. **Mitigation**: Define clear status levels (developmental, candidate, approved, retired) and versioning relationships in the registry model.
7.  **Risk**: Disputes within Communities of Interest over tag approval. **Mitigation**: Define an escalation path to the COE Chief Engineer for ultimate mediation authority.
8.  **Risk**: Performance under varying workloads in static vs. deployed environments. **Mitigation**: Design services to be tunable by on-site personnel in fixed environments and more predetermined in dynamic ones.
