# Detailed Summary: GOG Software Requirements Specification

## Background and Scope
The Gaia Object Generator (GOG) is a software simulator designed to produce catalog data, auxiliary data, and intermediate main database data (including statistically equivalent final mission data) for all Gaia instruments. It uses error models to provide rapid simulations of large amounts of data, bypassing the need for GASS telemetry, GIBIS, or the main ESAC database. The realism of simulations depends on the availability and accuracy of error models. GOG is modular and configurable, supporting source generation from either the Universe Model in the GaiaSimu library or a user-provided input object catalog. Non-goals include producing raw data (focus is on pre-processed data) and simulating detailed instrumental noise with crowding effects (which is the domain of GIBIS).

## Stakeholders Matrix and Use Cases
*   **CU2 (Coordination Unit 2) / Development Team (Y. Isasi, P. Sartoretti, C. Babusiaux, X. Luri, E. Masana):** Responsible for the design, development, and maintenance of the GOG software.
*   **CU2 CCB (Change Control Board):** Responsible for reviewing and approving the requirements specification and subsequent changes.
*   **DPAC (Data Processing and Analysis Consortium) / Other CUs:** Consumers of GOG's simulated data for algorithm development, testing, and validation.
*   **End Users (Scientists, Developers):** Configure and execute GOG simulations to generate specific datasets for their needs.

**Main Scenarios:**
1.  User configures GOG via an XML file to generate data for a specified sky region using the Universe Model.
2.  User configures GOG to generate data for a pre-defined list of objects from an input catalog.
3.  GOG processes sources individually (source-by-source) to generate epoch observation data.
4.  GOG processes sources to generate combined (astrometric solution) data from multiple transits.
5.  User selects which instrumental and reduction noise effects to apply during simulation.
6.  GOG outputs data in formats compliant with the Universe Model ICD and the Main Database ICD.

**Exception Scenarios:**
1.  The required error model for a specific noise type is not yet available.
2.  The input configuration file contains invalid or missing parameters.

## Business Process
**Main Process: GOG Simulation Execution**
1.  **Trigger:** User executes GOG from the command line with a configuration file.
2.  **Initialization Module** reads the XML configuration file, loading parameters for universe/instrument/reduction models and output specification.
3.  **Source Generation:** Based on configuration, sources are retrieved either from the GaiaSimu Universe Model for a sky region or from a user-provided input catalog.
4.  **For each source:** Determine if epoch data, combined data, or both are requested.
5.  **If epoch data requested:** Epoch Parameters Module calculates astrometric, photometric, radial velocity, and physical parameters for each transit, applying selected errors.
6.  **If combined data requested:** Combined Parameters Module calculates astrometric solutions, mean photometry, radial velocity, and physical parameters by combining data from all transits, applying selected errors.
7.  **Spectrum Simulation Module** generates RP/BP and RVS spectra for the source, applying relevant noise models for both epoch and combined data as required.
8.  **Output Module** writes the final results for the source to files in the specified formats (Universe Model catalog and/or Main Database format).

**Key Branch A: Spectrum Simulation Flow**
1.  Input source data and configuration.
2.  Apply flux noise (Poisson, total detection noise).
3.  Apply CCD combination noise (for RVS).
4.  Apply wavelength calibration and multi-transit combination noise (for combined data).

**Key Branch B: Astrometric Data Generation (Epoch vs. Combined)**
*   **Epoch Flow:** Calculate field angles and times per CCD/transit, considering gate activation and window cutoff.
*   **Combined Flow:** Compute parallax, proper motions, and covariance matrix by combining all transit data.

## Domain Model
*   **Source:** The core astronomical object being simulated. (Fields: sourceId [required, unique], position, photometry, radial velocity, physical parameters).
*   **Configuration:** Runtime parameters for the simulation. (Fields: inputSourceType [required], skyRegion, outputMode [required], noiseModelsSelected, reductionStage).
*   **Transit:** A single observation epoch of a source by Gaia. (Fields: transitId [required], sourceId [reference], timestamp [required], fieldAngles, photometry).
*   **EpochData:** The calculated data for a single transit, including errors. (Fields: transitId [reference], astrometry, photometry, radialVelocity, flags, physicalParameters).
*   **CombinedData:** The calculated data from combining all transits for a source. (Fields: sourceId [reference, unique], astrometricSolution [required], meanPhotometry, meanRadialVelocity, meanPhysicalParameters, finalFlags).
*   **Spectrum:** Simulated spectral data. (Fields: sourceId [reference], type [RP/BP/RVS, required], epochData [reference], combinedData [reference], fluxArray, wavelengthArray).
*   **NoiseModel:** Definition of an error to be applied. (Fields: modelId [required, unique], type [Instrumental/Reduction], parameters).
*   **OutputFile:** A generated data file. (Fields: filename [required], format [UM/MDB, required], content).

## Interfaces and Integrations
*   **GaiaSimu Library (Internal):** Direction: Inbound. Interaction: Source generation and universe/instrument models. Input: Sky region or source list request. Output: Source objects with properties. SLA: Library must be available and compatible.
*   **Universe Model ICD (External):** Direction: Outbound. Interaction: Output data format specification. Input: Simulated source data. Output: Catalog files compliant with ICD GAIA-C2-SP-LAOB-CR-001. SLA: Format adherence is mandatory.
*   **Main Database (MDB) ICD (External):** Direction: Outbound. Interaction: Output data format specification. Input: Simulated epoch and combined data. Output: Data files structured per ICD GAIA-C1-SP-ESAC-JH-001 (prep). SLA: Format adherence is mandatory for data exchange with DPCs.
*   **User Configuration (External):** Direction: Inbound. Interaction: Runtime parameters via XML file. Input: XML configuration file. Output: Loaded configuration properties. SLA: File must be well-formed and validate against a schema.
*   **Command Line / Shell (External):** Direction: Inbound. Interaction: Software invocation. Input: Command with path to config file. Output: Process initiation and status logs. SLA: Must be callable from scripts for batch processing.

## Acceptance Criteria
**Capability: Generate Data from Universe Model**
*   Given a valid configuration file specifying a sky region and the Universe Model source,
    When GOG is executed,
    Then it produces output files containing simulated data for sources within that region.
*   Given identical configuration files on two different runs,
    When GOG is executed,
    Then the output data must be statistically identical.

**Capability: Apply User-Selectable Noise**
*   Given a configuration file where instrumental noise models are disabled,
    When GOG generates epoch photometry data,
    Then the output contains no added instrumental noise for the photometric measurements.
*   Given a configuration file specifying the application of a specific reduction noise model,
    When GOG generates combined astrometric data,
    Then the output parameters include errors consistent with that model's specification.

## Non-Functional Metrics
*   **Performance:** Must process one complete source (including all transits) within 2 CPU seconds. Must be capable of simulating data for up to 20% of the expected final Gaia catalog.
*   **Reliability:** Must produce identical results for identical input configurations across runs. Must handle malformed configuration files gracefully with informative error messages.
*   **Security:** (Implicit) As a scientific simulation tool run in controlled environments, primary security concerns relate to data integrity and access controls on input/output files as per DPAC policies.
*   **Compliance:** Output data formats must comply with the Universe Model ICD and the Main Database ICD. Development must follow the DPAC Software Product Assurance Plan (GAIA-C1-PL-CNES-TL-001).
*   **Observability:** Must support logging of execution progress, errors, and warnings. Should be invokable from command line/scripts to enable integration into workflow managers.

## Milestones and Release Strategy
1.  Initial version supporting basic source generation and output in Universe Model format.
2.  Integration of core epoch parameter simulation (astrometry, photometry).
3.  Integration of combined parameter simulation and basic error models.
4.  Integration of spectrum simulation module (RP/BP and RVS).
5.  Full compliance with Main Database (MDB) output format.
6.  Performance optimization and validation for large-scale simulations (up to catalog-scale subsets).

## Risk List and Mitigation Strategies
1.  **Risk:** Main Database (MDB) specifications are not finalized, causing interface instability.
    **Mitigation:** Base initial versions on current specifications, design GOG with modular, adaptable I/O layers, and plan for updates.
2.  **Risk:** Error models (instrumental and reduction) are unavailable or immature, limiting simulation realism.
    **Mitigation:** Implement a pluggable architecture for noise models; provide default or simplistic models initially; collaborate with other CUs for model development.
3.  **Risk:** Inability to meet the performance target (2 CPU seconds per source) for complex simulations.
    **Mitigation:** Implement profiling early; optimize critical algorithms; leverage efficient libraries; consider parallelization where possible.
4.  **Risk:** The software cannot effectively run in grid/cluster environments for large-scale production.
    **Mitigation:** Design for stateless, batch-oriented processing from the start; avoid platform dependencies; test in target environments early.
5.  **Risk:** Overlap and crowding effects are not simulated, reducing fidelity for dense fields.
    **Mitigation:** Clearly document this as a known limitation; scope a potential future version to work on sky regions for overlap modeling.
6.  **Risk:** Changes in the dependent GaiaSimu library break GOG functionality.
    **Mitigation:** Establish clear version dependencies; implement integration tests; coordinate closely with the GaiaSimu development team.
7.  **Risk:** Insufficient validation leads to scientifically inaccurate simulated data.
    **Mitigation:** Develop a comprehensive test suite comparing GOG output against other simulators (e.g., GIBIS) where possible; engage science validation teams.
8.  **Risk:** Complex configuration leads to user errors.
    **Mitigation:** Provide detailed documentation, example configuration files, and implement robust configuration validation with clear error messages.
