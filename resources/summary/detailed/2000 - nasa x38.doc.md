# Detailed Summary: X-38 Fault Tolerant System Services (FTSS)

## Background and Scope
The X-38 Fault Tolerant System Services (FTSS) is a software component for NASA's X-38 Crew Return Vehicle's quad-redundant Flight Critical Computer (FCC). It provides an Application Programming Interface (API) between NASA's application code and the underlying hardware (Motorola Power PCs) and the VxWorks operating system. The FTSS delivers fault-tolerant services including scheduling, communication, time management, memory management, fault detection, redundancy management, and system support. The system must operate in a high-reliability, real-time aerospace environment. Non-goals include handling non-hardware-related security, extensive user training, and logistics beyond software delivery.

## Stakeholders Matrix and Use Cases
- **NASA (Johnson Space Center)**: Primary customer; defines mission requirements and provides application software.
- **Charles Stark Draper Laboratory**: Developer and maintainer of the FTSS software.
- **Flight Software Application Developers**: Use the FTSS API to build the X-38 vehicle control software.
- **System Integrators**: Integrate FTSS with FCC hardware and other avionics components.
- **Test and Verification Engineers**: Validate FTSS against requirements and perform certification testing.
- **Maintenance Personnel**: Support operational use and troubleshooting.

**Main Scenarios**:
1. System powers up and initializes within 1.5 minutes, synchronizing FCPs and configuring ICPs.
2. Scheduler executes 50 Hz, 10 Hz, and 1 Hz rate group tasks with minimal jitter.
3. Communication services pass messages synchronously and immediately between FCPs and ICPs.
4. Continuous BIT detects and diagnoses processor or NE faults within 1 second.
5. Redundancy Management reconfigures the system upon fault detection, degrading from quad to triplex.
6. Memory alignment reintegrates a recovered FCP channel, aligning congruent memory.
7. Telemetry data is transferred to the MPCC/CTC every 10 Hz frame.
8. Exception handling logs errors and restarts affected tasks.

**Exception Scenarios**:
1. An FCP fails during operation; system degrades to triplex and attempts recovery.
2. An ICP fails to send heartbeat; it is masked after two consecutive missed cycles.
3. A babbling NE or ICP is detected and masked within 40 milliseconds.
4. A task overruns its rate group boundary; scheduler reports and restarts it.

## Business Process
**Main Process: Normal Operation Cycle (50 Hz Minor Frame)**
1. **Trigger**: 50 Hz timer interrupt.
2. Scheduler updates minor frame count, MET, SEP, and writes to ICP shared memory.
3. Scheduler issues VME interrupt to ICPs to start their 50 Hz cycle.
4. Scheduler executes enabled tasks in 50 Hz rate group in priority order.
5. Communication services exchange synchronous messages at frame boundaries.
6. Continuous BIT performs presence test and resets watchdog timer.
7. Redundancy Management checks for faults and reconfigures if needed.
8. Scheduler sets timer for next interrupt and yields to lower priority tasks.

**Key Branch A: Fault Detection and Recovery**
1. **Trigger**: Continuous BIT or NE syndrome detects a fault (e.g., FCP failure).
2. Fault is diagnosed within 1 second; health status reported to application.
3. Redundancy Management masks failed component within 3 minor frames.
4. If alignment permitted, voted reset is sent and recovery attempts begin.

**Key Branch B: System Initialization**
1. **Trigger**: Power-on reset or CPU reset.
2. IBIT executes on FCPs, ICPs, and MPCCs; failures logged.
3. FCPs synchronize; unsynchronized processors are excluded.
4. Application initialization creates tasks, sockets, and sets vehicle mode.
5. 50 Hz timer is started, enabling normal operation.

## Domain Model
- **Virtual Group (VG)**: Entity representing a computational set (e.g., FCP quad, ICP simplex). Fields: VG_ID (required, unique), redundancy_level, member_processors (reference).
- **Task**: Entity for application functions. Fields: task_ID (required, unique), priority, rate_group (reference), vehicle_mode (reference).
- **Rate Group**: Entity for scheduling tasks at specific rates. Fields: rate (required; 50,10,1 Hz), task_list (reference).
- **Vehicle Mode**: Entity for mission phases. Fields: mode_ID (required, unique), rate_groups (reference).
- **Socket**: Entity for communication endpoints. Fields: socket_ID (required, unique), type (message_queue/pipe), VG_sender (reference), VG_receiver (reference).
- **Fault Log**: Entity for recording faults. Fields: fault_ID (required, unique), component (FCP/ICP/NE), error_type, timestamp.
- **Memory Region**: Entity for memory management. Fields: region_ID, type (congruent_aligned, congruent_initialized, non-congruent), start_address, size.
- **Time**: Entity for mission timing. Fields: MET (required), SEP, utility_timer.

## Interfaces and Integrations
1. **API/FTSS**
   - Direction: FTSS provides API to application.
   - Interaction: Function calls for scheduling, communication, time, etc.
   - Input: Application parameters (e.g., task function, rate group).
   - Output: Status codes, data (e.g., MET, fault logs).
   - SLA: API defined in Draper document 297752.

2. **Network Element (NE)/FTSS**
   - Direction: Bidirectional; FTSS sends/receives packets via NE.
   - Interaction: Packet exchanges for data, configuration, voted resets.
   - Input: Descriptor and data blocks from NE.
   - Output: Descriptor and data blocks to NE.
   - SLA: Packet exchange ≤200 µs (ICP to FCP), ≤150 µs (broadcast).

3. **VxWorks/FTSS**
   - Direction: FTSS uses VxWorks services.
   - Interaction: OS calls for tasking, memory, exceptions.
   - Input: FTSS system calls.
   - Output: OS responses.
   - SLA: Use of allowed VxWorks subset per API manual.

4. **Radstone/FTSS**
   - Direction: Radstone firmware provides BIT results to FTSS.
   - Interaction: FTSS configures and reads Radstone IBIT logs.
   - Input: IBIT fault logs from Radstone boards.
   - Output: Configuration commands for IBIT.
   - SLA: IBIT execution during startup.

5. **MPCC/FTSS**
   - Direction: FTSS sends telemetry/receives commands via MPCC.
   - Interaction: Serial communication configured for SDLC mode.
   - Input: Command data from CTC.
   - Output: Telemetry data to CTC.
   - SLA: Telemetry transfer ≤5.2 ms per 10 Hz frame.

6. **FCP-ICP/FTSS**
   - Direction: FCP writes to shared memory; interrupts ICP.
   - Interaction: Shared memory block with frame number, MET, SEP; VME interrupt.
   - Input: ICP reads shared memory.
   - Output: FCP writes shared memory and asserts interrupt.
   - SLA: Interrupt skew ≤330 µs across ICPs.

7. **IRIG-B/FTSS** (deleted section; assumed not required).
8. **Internal FTSS Interfaces**: None specified.

## Acceptance Criteria
**Capability: Fault Detection and Recovery**
- Given an operational quad-redundant FCP set, when an FCP processor fails, then the system shall degrade to triplex within 60 milliseconds and report the fault via telemetry.
- Given a masked faulty NE, when alignment is permitted, then the system shall attempt recovery via voted reset and TNR within 1.5 minutes.

**Capability: Scheduling**
- Given a 50 Hz timer interrupt, when the scheduler executes, then it shall complete overhead tasks within 1 millisecond and start the first 50 Hz task.
- Given a task overrun in a rate group, when detected, then the scheduler shall report the overrun and restart the task at its beginning.

**Capability: Communication**
- Given a message queue socket between FCP and ICP, when a message is sent, then it shall be delivered congruently at the next frame boundary.
- Given a broadcast pipe created on an FCP, when a message is sent, then all receiving VGs shall be able to read it.

**Capability: Time Services**
- Given system startup, when the first 50 Hz frame occurs, then MET shall be initialized to zero and increment with ≤50 PPM drift.
- Given vehicle separation signal, when received, then SEP shall start counting within one minor frame.

## Non-Functional Metrics
- **Performance**: Scheduler and Time Services overhead ≤1 ms per minor frame; telemetry transfer ≤5.2 ms per 10 Hz frame.
- **Reliability**: Two-fault tolerant for non-simultaneous hardware faults; recovery of failed channel within 1.5 minutes.
- **Security**: No specific requirements (addressed by hardware isolation).
- **Compliance**: Adheres to MIL-STD-498 documentation standards; uses VxWorks 5.4 and C language.
- **Observability**: All faults and recovery actions reported to application for telemetry; IBIT results logged.

## Risk List and Mitigation Strategies
1. **Risk**: NE or ICP babbling overwhelms network.
   - **Mitigation**: Detect within 20 ms, mask within 40 ms.
2. **Risk**: Memory alignment takes too long, affecting real-time performance.
   - **Mitigation**: Limit alignment to 4 MB of DRAM; complete within 1 sec/MB.
3. **Risk**: Fault recovery fails due to permanent hardware damage.
   - **Mitigation**: Discriminate permanent vs. transient faults; request power cycle from application.
4. **Risk**: Software exceptions cause task desynchronization.
   - **Mitigation**: Restart offending task at initialization; log context data.
5. **Risk**: Telemetry bandwidth exceeded by FTSS data.
   - **Mitigation**: Limit FTSS telemetry to 5000 bps; allocate 600 bits for startup data.
6. **Risk**: Asymmetric I/O calls cause FCP skew.
   - **Mitigation**: Restrict I/O calls to maintain synchronization.
7. **Risk**: MPCC/CTC link failures disrupt command/telemetry.
   - **Mitigation**: Switch to redundant MPCC; retry faulty link.
8. **Risk**: Radiation-induced SEUs corrupt memory.
   - **Mitigation**: RAM scrub at 10 MB/8 min; report errors congruently.

## Undecided Issues and Responsible Parties
1. **Issue**: Specific implementation of memory protection policy (restart task on violation).
   - **Responsible**: Draper/NASA joint decision.
2. **Issue**: Handling of simultaneous faults beyond two non-simultaneous faults.
   - **Responsible**: NASA to define mission-critical scenarios.
3. **Issue**: Optimization of RAM scrub algorithm to meet 1% CPU duty cycle.
   - **Responsible**: Draper implementation.
4. **Issue**: Final telemetry data format and integration with NASA application.
   - **Responsible**: Draper/NASA coordination.
5. **Issue**: Validation of fault recovery time bounds (e.g., 1.5 minutes) in all scenarios.
   - **Responsible**: Draper testing, NASA review.
6. **Issue**: Configuration of NE debug commands for flight vs. test modes.
   - **Responsible**: Draper to document.
7. **Issue**: Utility timer usage with non-congruent memory; application guidelines.
   - **Responsible**: Draper API documentation.
8. **Issue**: Power-down sequencing coordination with application.
   - **Responsible**: Draper/NASA interface definition.
