# Detailed Summary: HATS Graphical User Interface (HATS-GUI) Software Requirements Specification

## Background and Scope
The HATS-GUI is a platform-independent graphical user interface for the High Assurance Transformation System (HATS), developed to facilitate transformation-based software development. The system enables users to apply provably correct transformations to target programs, generating syntax derivation trees (SDTs) and pretty-printed text outputs. The GUI manages applications, orchestrates parsing and execution of transformation programs, and provides visualization tools for examining outputs. Non-goals include handling transformation logic itself (handled by HATS-SML), supporting multiple concurrent users, or providing extensive user guidance.

## Stakeholders Matrix and Use Cases
**Stakeholders:**
- **User:** Domain expert who interacts with HATS-GUI to prepare and execute program transformations.
- **HATS-SML:** Service programs providing parsing, transforming, and pretty-printing functions.
- **Host OS:** Operating system providing file services and process management.

**Main Scenarios (≤8):**
1. Parse transformation language programs or target files to generate SDTs.
2. Execute transformation language programs to apply transformations to targets.
3. Select an application from the file system.
4. Select individual files within an application.
5. Prepare applications (create, close, save, edit files).
6. Configure application settings (editors, display colors, file associations).
7. Display and manipulate SDT transformation outputs with navigation and search.
8. Display and manipulate pretty-printed text outputs with search capabilities.

## Business Process
**Main Process: Apply Transformation (≤8 steps)**
1. **Trigger:** User selects "Execute Transformation" from Run menu.
2. Verify transformation language program exists in current application.
3. Check parser file currency; regenerate if older than grammar/lexical files.
4. Check parsed program file currency; regenerate if older than source files.
5. Identify target files using FindTarget program.
6. Verify/regenerate parsed target files for each target.
7. Execute ApplyTransformations program with parsed program and library.
8. **Output:** Generated SDTs and captured standard output/error streams.

**Key Branch A: Parse File (≤4 steps)**
1. User selects parse option for target or program file.
2. Check parser file currency; regenerate if needed.
3. Execute ParseTarget or ParseTLP program.
4. Save generated SDT file in application.

**Key Branch B: Generate Pretty-Printed Output (≤4 steps)**
1. User selects SDT and pretty-print style file.
2. Generate output filename.
3. Execute PrettyPrint program.
4. Save formatted text file.

## Domain Model
**Entities (≤8):**
1. **Application** (required): name, directory path, configuration reference.
2. **Configuration** (required): editor associations, node display settings, file associations, parser filename.
3. **File** (required): filename, extension, path, timestamp, type reference.
4. **FileType** (required): extension, description.
5. **SDT** (required): filename, root node reference.
6. **DisplayedNode** (required): label, color, shape, type, SDT node reference.
7. **Editor** (required): name, startup command, file type associations.
8. **TransformationOutput** (required): filename, type (SDT/text), source references.

## Interfaces and Integrations
1. **HATS-SML** (outbound): Invokes ML programs via command line; passes input/output filenames; captures stdout/stderr.
2. **Host OS File System** (bidirectional): File operations (create/read/write/delete); directory listing; timestamp comparison.
3. **Host OS Process Management** (outbound): Launches external editors and HATS-SML programs with command arguments.
4. **User Interface** (inbound): Menu-driven interface with file/application/configure/run/view menus; mouse/keyboard interactions.
5. **Display System** (outbound): Renders SDTs as graphs with configurable colors/shapes; displays text with formatting.
6. **Clipboard Integration** (outbound): Copies selected text to system buffer for pasting into other applications.

## Acceptance Criteria
**Capability: Execute Transformation**
- Given a selected application with valid grammar, lexical spec, and transformation program, when the user executes the transformation, then SDT outputs are generated and available for viewing.
- Given an outdated parser file, when executing a transformation, then the parser is regenerated before proceeding.

**Capability: Display and Navigate SDT**
- Given a displayed SDT graph, when the user clicks an expandable node, then descendant nodes are displayed according to configured expansion levels.
- Given both SDT and pretty-printed text displays from the same transformation, when nodes are selected in the SDT, then corresponding text is highlighted in the text window.

**Capability: Configure Application**
- Given an open application, when the user configures node display colors and saves the configuration, then those colors are used in subsequent SDT displays.
- Given a file type without associated editor, when the user edits that file type, then they are prompted to select and associate an editor.

## Non-Functional Metrics
**Performance:** Display 10,000-node SDT within 5 seconds; scrolling response under 3 seconds for 10,000 nodes.
**Reliability:** Continue operation despite HATS-SML errors; preserve data during file operations with overwrite protection.
**Security:** No authentication required; relies on host OS file permissions.
**Compliance:** Platform independence across Windows 2000, Solaris 8, and Linux.
**Observability:** Collect and display all HATS-SML error/output streams; maintain navigation state during user interactions.

## Milestones and Release Strategy
1. Complete core application management (create/open/save applications).
2. Implement HATS-SML integration for parsing and transformation execution.
3. Develop basic SDT display with expansion/collapse functionality.
4. Add SDT navigation features (scrolling, search, navigation window).
5. Implement pretty-printed text display and synchronization with SDT views.
6. Final testing on all target platforms and delivery.

## Risk List and Mitigation Strategies
1. **HATS-SML interface changes:** Maintain protocol abstraction layer; coordinate with HATS development team.
2. **Large SDT performance issues:** Implement incremental rendering algorithms; avoid virtual window approach.
3. **Platform-specific file system differences:** Use Java file APIs; conduct early testing on all target OSs.
4. **Memory constraints with huge SDTs:** Implement lazy loading and partial tree rendering.
5. **User interface complexity:** Follow established menu conventions; provide consistent navigation patterns.
6. **Error handling in asynchronous operations:** Maintain process tracking; provide clear error messages.
7. **File association management complexity:** Use configuration persistence with validation.
8. **Search algorithm performance:** Implement efficient tree traversal with complexity bounds.
