# Detailed Summary: I-15 Reversible Lane Control System (I-15 RLCS) Application Software Requirements

## Background and Scope
This document defines the software requirements for the I-15 Reversible Lane Control System (RLCS) application, which will replace an aging, non-expandable system. The primary purpose is to safely open and close reversible lanes for peak traffic hours and special events by monitoring and controlling field devices (e.g., gates, pop-ups, changeable message signs). The scope includes developing a new application that interfaces with new controller hardware and field device interface cards via driver software. Non-goals include interfacing with applications beyond system-level interfaces (e.g., network, OS, database) and supporting regulatory policies not specifically covering the RLCS.

## Stakeholders Matrix and Use Cases
*   **Operator:** Controls the system during normal mode; only one operator can have command control at a time.
*   **Management:** Views reports and checks system status only.
*   **Field Maintenance Staff:** Controls the system during maintenance mode from FCU workstations or remote dial-in terminals.
*   **Electrical Systems (Hardware):** Views reports and checks system status only.
*   **Software Systems (Software):** Views reports and checks system status only.
*   **System Administrator:** A District 11 technical staff member who creates/modifies system configuration data (staff, devices, schedules) and security settings.

**Main Scenarios:**
1.  Operator logs in, views facility status, and initiates a scheduled opening sequence.
2.  System automatically polls device status and updates the GUI display every 2 seconds.
3.  A critical alarm (e.g., device status unknown) halts an opening sequence, prompting operator intervention.
4.  System Administrator configures a new user account and assigns security permissions.
5.  Scheduled closing sequence executes after operator confirmation.
6.  External systems (e.g., ATMS) retrieve lane status data from an external server.
7.  Field maintenance staff logs in remotely during maintenance mode to test a specific device.
8.  System generates and exports log reports (e.g., Alarm Log, Daily Diary) for review.

## Business Process
**Main Process: Execute Scheduled Lane Opening/Closing**
*   **Trigger:** Scheduled time reached or operator manual command.
*   **Input:** System mode, schedule, current device status.
*   **Output:** Changed device states, updated system status, log entries.
1.  System checks schedule and current mode.
2.  Presents command sequence to operator for confirmation.
3.  Executes sequence steps (e.g., close gates, open pop-ups, update CMS) in defined order.
4.  Monitors device status after each command.
5.  Proceeds to next step if status is confirmed within timeout.
6.  Updates GUI and database with new status.
7.  Logs all commands and status changes.
8.  Finalizes sequence and updates external data store.

**Key Branch A: Sequence Halted Due to Alarm**
1.  Device fails to report status within timeout or an opposite-direction device opens.
2.  System enters 'hold' state, sounds audible alarm, and notifies operator.
3.  Operator diagnoses issue (may override device status if authorized).
4.  Operator issues resume command or aborts the sequence.

**Key Branch B: System Startup and Initialization**
1.  Control unit (workstation/controller) comes online.
2.  System identifies unit and its associated device sensors.
3.  Initializes control unit and device sensors.
4.  Performs control system integrity check (e.g., MD5 hash verification).

## Domain Model (Key Entities ≤8)
*   **Device:** ID, Name, Status_ID (required), Location_ID (required), Category_ID, Last_Maintenance_Date.
*   **Device Status:** ID, Name (e.g., OK, Alarm) (required).
*   **Location:** ID, Highway #, Segment, Direction, Name (required).
*   **Personnel:** ID, Name, Password (encrypted, required), Security_Level_ID (required).
*   **System Operational Command (Super Macro):** ID, Name, Description, Timeout, Command_Level_ID (required).
*   **System Operation Command Schedule:** ID, Mode_ID, Start_DateTime, End_DateTime, Command_ID (required).
*   **Alarm Type:** ID, Description (e.g., Critical, Warning) (required).
*   **Device Command Log:** ID, Command_ID, DateTime, Operator_ID (required), Status_ID.

## Interfaces and Integrations
*   **External Systems (ATMS, ValuePricing, ATIS):** Direction: Outbound. Theme: One-way data provision. Input: N/A. Output: RLCS status, customers, access, sign messages to external server. SLA: Data updated every 30 seconds.
*   **Field Device I/O Drivers:** Direction: Bidirectional. Theme: Hardware control via controller. Input: Device sensor status. Output: Device control commands. SLA: Device response to command within 12 seconds of operator confirmation.
*   **Remote Dial-in Interface:** Direction: Bidirectional. Theme: Secure remote access. Input: User credentials, commands. Output: System access, status. SLA: Secure connection through firewall.
*   **COTS Reporting Tool:** Direction: Outbound. Theme: Data export for reporting. Input: RLCS log and entity data. Output: Formatted report parameters. SLA: Report processing must not impact core system performance.
*   **COTS Database Management System:** Direction: Bidirectional. Theme: All application data persistence. Input: All entity data. Output: Queried data for operations. SLA: Update/retrieval must support <2 sec GUI response times.
*   **TMC/FCU/DCU Network:** Direction: Bidirectional. Theme: Private network communication. Input: Status, commands. Output: Status, commands. SLA: Status polling transmission rate supports 2-second update goal; uses checksums for integrity.

## Acceptance Criteria (Examples)
*   **Capability: Monitor Device Status**
    *   Given the system is operational, when a field device sensor changes state, then the GUI display updates within 2 seconds and the database is updated.
    *   Given a device fails to report status, when the system retries a configurable number of times, then a device failure alarm is generated.
*   **Capability: Execute Safety-Screened Command**
    *   Given the northbound gate is open, when an operator attempts to open a southbound gate, then the system blocks the command and notifies the operator of the safety violation.
    *   Given a scheduled opening sequence is pending, when the scheduled time is reached, then the system prompts the operator for confirmation before execution.
*   **Capability: User Security and Access**
    *   Given a user with 'Status Only' command level, when they attempt to issue a device control command, then the system denies the command.
    *   Given a System Administrator, when they modify a device rule in the database, then the system analyzes the change for conflicts before saving.

## Non-functional Metrics
*   **Performance:** GUI status updates within 2 seconds; system must support at least 4 daily normal mode scheduled operations plus emergency/maintenance events.
*   **Reliability:** Must function continuously for 30 days without reset due to RLCS error; availability target 99.99% (≈50 min downtime/year).
*   **Security:** User passwords stored using MD5 hash; command rules and login data in controllers stored in encrypted, non-volatile memory.
*   **Compliance:** Must adhere to safety screening rules to prevent catastrophic wrong-way openings (detailed in Appendix F).
*   **Observability:** All application activity logged; alarm conditions detected within 2 seconds; system generates configurable audible/visual alarms.

## Risk List and Mitigation Strategies
1.  **Catrophic Wrong-Way Opening:** Mitigation: Multi-layered safety screening of all commands at every control unit; strict operational sequences; non-volatile storage of safety rules.
2.  **Device or Communication Failure During Operation:** Mitigation: Sequence halting logic; operator override capability (with authorization); degraded mode operation with configurable polling.
3.  **Unauthorized System Access:** Mitigation: Multi-factor security (command level, device, mode, workstation, function); encrypted passwords; remote access via secure firewall.
4.  **Software/Data Corruption in Field Controllers:** Mitigation: Use of MD5 hash for integrity verification of non-volatile memory; daily automatic integrity checks; alarms on verification failure.
5.  **System Downtime Affecting Lane Operations:** Mitigation: Redundant control capabilities (TMC -> FCU -> DCU -> Manual); max 10-minute recovery time objective.
6.  **Future Roadway Changes Requiring Software Modifications:** Mitigation: Open, modular architecture; device rules and configuration stored in updatable database tables to avoid reprogramming.
7.  **Integration Issues with New Controller Hardware:** Mitigation: Requirement to interface via standard I/O driver software, abstracting hardware specifics.
8.  **Inadequate Network Performance:** Mitigation: Performance calculations based on sensor count; design to support estimated 164 kbits/s peak load for 2-second updates.
