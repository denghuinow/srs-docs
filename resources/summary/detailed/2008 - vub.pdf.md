# Detailed Summary: Publications Management System (PMS)

## Background and Scope
The Publications Management System (PMS) is a web-based platform designed to manage a database of academic publications with associated bibliographical information and full-text documents (PDF/PostScript). It supports automated extraction of metadata from uploaded documents, manual correction, and sophisticated search capabilities with access control based on user roles and network location. The system must be accessible via web browser (W3C XHTML compliant) and command line, developed in Ruby without frameworks, and run on a Linux server (Wilma). Non-goals include support for non-academic media formats (e.g., audio/video) in the core release, automatic author/institute disambiguation, and compatibility with non-free software tools.

## Stakeholders Matrix and Use Cases
*   **Guest**: Anonymous user outside VUB-network; can only register or log in.
*   **VUB-Network User**: User connected to VUB-network via IP; can search, view, and download publications without logging in.
*   **Member**: Logged-in user; can manage personal account, search, view, and download publications.
*   **Publisher**: Logged-in user; can upload publications (bulk/single) and edit their own.
*   **Moderator**: Logged-in user; can manage user levels and edit publications within their department/group.
*   **Administrator**: Logged-in user; has full system control, including user/group management and global publication editing.
*   **Customer/Supplier**: Academic institution (VUB) requiring the system; defines requirements and receives deliverables.
*   **Developer/Tester**: SE1 team; responsible for design, implementation, and verification against this SRS.

**Main Scenarios**: User registration/validation; Publication search and result browsing; Publication upload with auto-extraction; Download publications/references; User/group management (Admin). **Exception Scenarios**: Login from outside VUB-network (requires account); Password retrieval; Handling uploads with incorrect auto-extracted data; Empty search results.

## Business Process
**Main Process: Publication Search and Access**
1.  **Trigger**: User accesses system via web or CLI.
2.  **Input**: User credentials or network IP detection.
3.  System authenticates user or grants VUB-network access.
4.  User submits search query (keywords, authors, date range).
5.  System queries database and returns result list.
6.  User views publication details or selects items.
7.  User downloads full-text or exports references (BIB/RIS).
8.  **Output**: Requested publication files or reference data.

**Key Branch A: Publication Upload**
1.  **Trigger**: Publisher/Moderator/Admin initiates upload.
2.  **Input**: Document file (PDF/PS) and optional metadata.
3.  System extracts bibliographical data automatically.
4.  User reviews and manually corrects extracted data.
5.  System saves publication and metadata to database.
6.  **Output**: New publication record available for search.

**Key Branch B: User Management (Admin)**
1.  **Trigger**: Administrator accesses control panel.
2.  **Input**: User details or search criteria.
3.  Admin creates/deletes user or modifies user level/group.
4.  System validates changes (e.g., unique username).
5.  System updates database and notifies if required.
6.  **Output**: Updated user account with new permissions.

## Domain Model
*   **User** (required: username/unique, password, email; reference: Group): Represents system users with roles.
*   **Publication** (required: title, publication date; reference: Author, Institute): Core publication entity with metadata.
*   **Author** (required: name; unique: canonical ID): Author of publications; may have aliases.
*   **Institute** (required: name; unique: canonical ID): Affiliated institution; may have variations.
*   **Reference** (required: citation text; reference: Publication): Bibliographic reference cited by a publication.
*   **Group** (required: groupname/unique; reference: User): Departmental or functional user grouping.
*   **DownloadLog** (required: timestamp, user ID, publication ID): Audit trail for access control.
*   **SystemConfig** (required: setting key/unique, value): Administrator-managed configuration parameters.

## Interfaces and Integrations
*   **Web Browser (User)**: Inbound; HTTP/TCP port 80; XHTML forms for all user interactions; Input: search queries, upload files, login credentials; Output: result pages, publication files, error messages; SLA: W3C XHTML 1.0 Transitional compliance, informative error messages.
*   **Command Line (Admin)**: Inbound; Direct server shell access; Administrative commands; Input: CLI commands for user/pub management; Output: System logs, confirmation messages; SLA: Full system control, local VUB-network access only.
*   **MySQL Database**: Outbound; Database driver; Persistent data storage; Input: SQL queries for CRUD operations; Output: Result sets, persistence confirmation; SLA: ACID compliance, concurrent request handling, backup capability.
*   **Email Server (External)**: Outbound; SMTP; Account validation and notifications; Input: User email, validation link; Output: Sent emails; SLA: Delivery for registration/password recovery.

## Acceptance Criteria
*   **Publication Search**: Given a VUB-network user, when they search by author and keyword, then a list of matching publications is displayed with title and main author.
*   **User Registration**: Given a guest, when they submit a valid registration form, then a confirmation email is sent and account is pending validation.
*   **Publication Upload**: Given a Publisher, when they upload a PDF, then the system extracts metadata and allows manual correction before saving.
*   **Access Control**: Given a Member, when they attempt to edit another user's publication, then the system denies the edit and shows an authorization error.

## Non-Functional Metrics
*   **Performance**: Search results returned within 3 seconds under typical load; Concurrent user support (specific number TBD).
*   **Reliability**: Mean time between failures (MTBF) target per spiral iteration; Automated backup and restore capability.
*   **Security**: Passwords stored encrypted; Role-based access control enforced; Secure HTTP for credential transmission.
*   **Compliance**: W3C XHTML 1.0 Transitional standard; Adherence to SE1 coding conventions.
*   **Observability**: All errors logged for administrator review; System availability status page.

## Milestones and Release Strategy
1.  First Iteration (Critical Requirements): Core login, publication search/view/download for VUB-network users and Members.
2.  Second Iteration (Sufficient Requirements): Publication upload, user management, advanced search, and moderator/admin functions.
3.  Optional Features Implementation: If time permits, add format expansions (MS Word) and enhanced reference linking.
4.  Alpha Release: Internal testing on Wilma server.
5.  Beta Release: Limited user acceptance testing with academic personnel.
6.  Final Release: Deployment with documentation and handover.

## Risk List and Mitigation Strategies
1.  **Inaccurate Auto-Extraction**: Manual correction interface is mandatory; provide bulk edit tools.
2.  **Scalability of Database**: Design for concurrent access; implement query optimization and indexing.
3.  **Security Breaches**: Encrypt passwords; validate all inputs; restrict CLI access to local network.
4.  **Wilma Server Downtime**: Clearly communicate dependency to customer; implement informative downtime messages.
5.  **Complex User Role Management**: Use hierarchical role model; thorough testing of permission boundaries.
6.  **File Storage Limits**: Define maximum file size for uploads (TBD); implement storage monitoring.
7.  **Browser Compatibility**: Adhere strictly to XHTML standard; test with text-based browsers (e.g., Links2).
8.  **Project Scope Creep**: Prioritize requirements as Critical/Sufficient/Optional; adhere to iteration plan.
