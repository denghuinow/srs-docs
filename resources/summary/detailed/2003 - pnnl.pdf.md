# Detailed Summary: Automated Diagnostics Software Requirements Specification

## Background and Scope
This document specifies requirements for an automated diagnostic tool to detect faults in HVAC subsystems (chillers, cooling towers, boilers) using sensed and fixed data. The tool replaces manual visual analysis with automated algorithms derived from expert practices. It targets building operators, service technicians, energy service providers, and supervisors, providing fault identification, causes, and corrective actions. The initial version focuses on chillers and cooling towers, with design extensibility for additional subsystems. Non-goals include implementing field-level details, providing user-defined analysis beyond diagnostics, and supporting non-Windows platforms.

## Stakeholders Matrix and Use Cases
- **General User**: Views current/historical diagnostic results; limited to browsing capabilities.
- **Administrator User**: Configures system settings, modifies fixed data, starts/stops diagnostics, and defines sensed data units.
- **Building Operator**: Monitors HVAC units from a central control room for faults.
- **Service Technician**: Uses tool on-site during repairs or off-site for continuous monitoring.
- **Energy Service Provider**: Remotely monitors multiple units across buildings for inefficiencies.
- **Building Operator Supervisor**: Guides operator assignments and prioritizes work based on diagnostic results.

**Main Scenarios**:
1. Start/stop diagnostic processing (administrator).
2. Browse current diagnostic results (all users).
3. Browse historical diagnostic results (all users).
4. Configure diagnostic parameters (administrator).
5. Authenticate user privileges (included in start/stop and configure).

**Exception Scenarios**:
1. Missing data preventing algorithm execution.
2. Authentication failures (three attempts limit).
3. Invalid sensed data outside expected ranges.
4. Unauthorized access attempts to administrative functions.

## Business Process
**Main Process (Diagnostic Execution)**:
1. **Trigger**: User launches tool and starts diagnostics.
2. **Input**: Sensed data (real-time or batch file) and fixed data (specifications, setpoints).
3. **Preprocessing**: Validate, convert units, filter, and average data.
4. **Diagnostic Processing**: Apply algorithms to detect faults in chillers/cooling towers.
5. **Output Processing**: Display results with fault descriptions, causes, fixes.
6. **Storage**: Save diagnostic results and sensed data to permanent storage.
7. **User Interaction**: Browse current/historical results via hierarchical windows.
8. **Termination**: User stops diagnostics or exits tool.

**Key Branch A (Batch Mode Processing)**:
1. Input sensed data from ASCII file with tab/comma delimiters.
2. Validate file format and header requirements.
3. Process data sequentially with associated timestamps.
4. Store results as in real-time mode.

**Key Branch B (Configuration Changes)**:
1. Administrator modifies fixed data or sensitivity settings.
2. Save changes to disk/database.
3. Relay changes to active diagnostic processing if confirmed.
4. Log changes with original/new values.

## Domain Model
- **Building**: Identifier (required, unique), name.
- **Subsystem**: Type (chiller/cooling tower/boiler, required), specifications (reference).
- **Diagnostic Condition**: Category (e.g., compressor cycling, required), fault description, sensitivity settings.
- **Sensed Data**: Parameter (e.g., temperature, required), value, timestamp (required), unit, validation status.
- **Fixed Data**: Setpoints, schedules, specifications (required), equipment identifiers.
- **User**: Role (general/administrator, required), authentication credentials.
- **Diagnostic Result**: Fault identification, timestamp (required), building/subsystem reference, causes, fixes.
- **Configuration**: Sensitivity levels, data ranges, unit conversion factors.

## Interfaces and Integrations
- **Data Acquisition Devices**: Direction: Input; Interaction: Real-time sensed data; Input: Current/power/temperature values; Output: Validated data stream; SLA: Continuous availability, <3 successive failures per sensor type.
- **Batch Data File**: Direction: Input; Interaction: ASCII file ingestion; Input: Tab/comma-delimited columns with headers; Output: Parsed sensed data; SLA: File format compliance, sequential processing.
- **Permanent Storage**: Direction: Bidirectional; Interaction: Data logging/retrieval; Input: Diagnostic results, sensed data; Output: Historical queries; SLA: Data integrity, three-significant-figure precision.
- **User Interface Windows**: Direction: Output; Interaction: Hierarchical navigation; Input: User selections; Output: Diagnostic displays, color maps; SLA: Responsive navigation, modal window management.
- **Authentication System**: Direction: Input; Interaction: Credential validation; Input: Username/password; Output: Privilege level; SLA: Three-attempt limit, 15-minute auto-logout.
- **Printing Service**: Direction: Output; Interaction: Window image printing; Input: User selection; Output: Printed diagnostics; SLA: On-demand generation.

## Acceptance Criteria
**Capability: Fault Detection**
- Given sensed data indicating chilled water supply temperature above setpoint, when diagnostic processes, then tool identifies "Too High" fault with causes/fixes.
- Given compressor cycling off more frequently than minimum on time, when diagnostic evaluates, then tool reports "Compressor On Cycle Not OK" with recommended actions.

**Capability: Historical Browsing**
- Given stored diagnostic results over past week, when user selects history view, then tool displays color-coded map with hourly resolution.
- Given historical interval specification, when user inputs start/end times, then tool shows results within selected period.

**Capability: Configuration Management**
- Given administrator privileges, when user modifies sensitivity settings, then changes are saved and relayed to active diagnostics.
- Given invalid fixed data edits, when user attempts save, then tool requests confirmation and logs change attempts.

## Non-Functional Metrics
- **Performance**: Process real-time data with <1-second delay for fault detection; support up to 10 simultaneous building displays.
- **Reliability**: Operate continuously for indefinite periods; log all errors with module/function details.
- **Security**: Authenticate users via credentials; auto-revert to general user after 15 minutes inactivity.
- **Compliance**: Adhere to IEEE Std 610.12-1990 definitions; store data with three-significant-figure precision.
- **Observability**: Log all sensor validation failures; provide animated indicators for diagnostic activity status.

## Milestones and Release Strategy
1. **Phase A Prototype**: Core chiller/cooling tower diagnostics with basic UI.
2. **Data Integration**: Real-time and batch data input capabilities.
3. **User Management**: Authentication and privilege system.
4. **Historical Features**: Browsing and printing functionalities.
5. **Boiler Diagnostics**: Expand to boiler subsystems (future version).
6. **Final Release**: Full HVAC diagnostic suite with extensible architecture.

## Risk List and Mitigation Strategies
1. **Missing Sensor Data**: Notify user and halt affected diagnostics; use default thresholds for continuation.
2. **Algorithm Inaccuracy**: Allow sensitivity adjustment by administrator; incorporate expert validation.
3. **User Interface Complexity**: Implement hierarchical windows with clear navigation; provide tooltips.
4. **Data Volume Overload**: Use averaging/filtering in preprocessing; limit historical displays to two-year max.
5. **Platform Dependence**: Restrict to Windows initially; design modularly for future portability.
6. **Security Breaches**: Enforce authentication; log all configuration changes.
7. **Integration Failures**: Validate data formats; provide error logging for acquisition devices.
8. **Maintenance Challenges**: Document all algorithms; design for subsystem addition/replacement.
