# DigitalHome Software Requirements Specification – Detailed Summary

## Background and Scope
The DigitalHome (DH) project is a prototype "Smart House" system developed by HomeOwner Inc.'s DigitalHomeOwner Division. It aims to integrate security, environmental control (temperature, humidity, lighting), and appliance management into a unified home automation platform accessible via web interfaces. The scope is limited to managing simulated devices for temperature, humidity, security, and appliance power within a controlled, simulated environment. Non-goals include deployment in physical homes, support for entertainment systems, and comprehensive commercial feature sets.

## Stakeholders Matrix and Use Cases
*   **General User:** A home resident who monitors and controls home environment devices via a web interface; familiar with basic web operations.
*   **Master User:** A designated user (often a resident) with configuration privileges, such as adding accounts or changing default parameters; shares rights with the DH Technician.
*   **DH Technician:** A trained professional responsible for system setup, maintenance, configuration changes, and starting/stopping system operations.
*   **DigitalHomeOwner Division (Development Team):** Responsible for designing, building, and testing the prototype system.
*   **HomeOwner Inc. Management:** Uses the prototype to make business decisions about future commercial product development.

**Main Scenarios:** User logs in to view current temperature/humidity; User sets a weekly schedule for thermostat; User remotely turns on a light/appliance; User receives and reviews a monthly environmental report.
**Exception Scenarios:** Security breach triggers alarm; User manually overrides a scheduled setting; System failure and recovery from backup; Attempted unauthorized login.

## Business Process
**Main Process: User Adjusts Home Environment**
1.  **Trigger:** User logs into the DH web portal via a browser or mobile device.
2.  User navigates to the control panel for a specific device type (e.g., Thermostat).
3.  System displays current sensor readings and scheduled settings for that device.
4.  User submits a new setting (e.g., desired temperature) or schedule.
5.  System validates the request against user permissions and physical constraints.
6.  System sends the command via the home gateway to the target simulated device.
7.  System confirms the command and updates the display.
8.  System logs the action and updates planning/reporting data.

**Key Branch A: Security Breach Detected**
1.  **Trigger:** A simulated door/window contact sensor changes to "OPEN" while armed.
2.  System immediately activates the sound and light alarm subsystems.
3.  System logs the breach event with a timestamp.
4.  System may notify the user via the web interface (implied).

**Key Branch B: Monthly Report Generation**
1.  **Trigger:** User requests a report for a past month.
2.  System retrieves stored sensor data and event logs for the specified period.
3.  System calculates daily averages, min/max values, and compiles security breach times.
4.  System presents the formatted report to the user.

## Domain Model
*   **User Account** (username: unique, required; password: required; role: required)
*   **Device** (deviceID: unique, required; type: required; location: required; status)
*   **Thermostat** (inherits from Device; currentTemp: required; setPoint: required; schedule: reference to Schedule)
*   **Humidistat** (inherits from Device; currentHumidity: required; setPoint: required; schedule: reference to Schedule)
*   **SecuritySensor** (inherits from Device; contactState: required (OPEN/CLOSED))
*   **PowerSwitch** (inherits from Device; applianceState: required (ON/OFF); schedule: reference to Schedule)
*   **Schedule** (scheduleID: unique, required; deviceID: reference, required; timePeriod: required; settingValue: required)
*   **MonthlyReport** (reportID: unique, required; monthYear: required; data: required)

## Interfaces and Integrations
*   **DH Web Portal (User Interface)**
    *   **Direction:** User → System
    *   **Interaction:** Browser-based GUI for monitoring/control.
    *   **Input:** Login credentials, control commands, schedule data.
    *   **Output:** Real-time sensor data, confirmation messages, reports.
    *   **SLA:** Display updates ≤2 seconds.
*   **Simulated Device Network**
    *   **Direction:** System ↔ Simulators
    *   **Interaction:** Wireless communication simulation via Gateway.
    *   **Input:** Control commands (set points, ON/OFF).
    *   **Output:** Sensor readings (temp, humidity, contact state).
    *   **SLA:** Sensor data acquisition rate ≥10 Hz; range 1000 ft.
*   **Backup System**
    *   **Direction:** System → Storage
    *   **Interaction:** Daily automated backup of configuration and data.
    *   **Input:** System data (config, plans, logs).
    *   **Output:** Backup archive.
    *   **SLA:** Daily backup at technician-set time.

## Acceptance Criteria
*   **Capability: Remote Temperature Control**
    *   Given a logged-in user, when they set a thermostat to 72°F, then the system confirms the setting and the thermostat's set point is updated.
    *   Given an invalid temperature setting (e.g., 85°F), when the user submits it, then the system rejects the input with a descriptive error message.
*   **Capability: Security Monitoring**
    *   Given the security system is armed, when a contact sensor is opened, then the sound and light alarms are activated immediately.
*   **Capability: Reporting**
    *   Given a month of operational data exists, when a user requests the monthly report, then a report is generated showing daily average temperature and recorded security breaches.

## Non-Functional Metrics
*   **Performance:** Environmental condition displays update at least every 2 seconds. Sensor data acquisition rate minimum of 10 Hz.
*   **Reliability:** Mean Time Between Failures (MTBF) target of 10,000 hours. Daily backup and recovery mechanisms in place.
*   **Security:** User authentication via username/password. Data transmission encrypted using a recognized standard (e.g., Transport Layer Security).
*   **Compliance:** Adherence to ASHRAE standards for HVAC. Use of IEEE and internal HomeOwner standards for development and documentation.
*   **Observability:** All operations include exception handling with clear user messages. System logs actions and events for reporting.

## Risk List and Mitigation Strategies
1.  **Risk:** Prototype scope creep into commercial features.
    *   **Mitigation:** Strict adherence to SRS; change requests require Director approval.
2.  **Risk:** Simulation environment lacks fidelity to real-world conditions.
    *   **Mitigation:** Ensure simulated environment adheres to real physical properties and constraints.
3.  **Risk:** Team size (5 engineers) may be insufficient for the 12-month timeline.
    *   **Mitigation:** Adhere to prioritized requirements; use efficient development processes and tools.
4.  **Risk:** Integration challenges between web server, gateway, and simulated devices.
    *   **Mitigation:** Early prototyping of communication layers; use accepted standards.
5.  **Risk:** Failure to meet reliability target (1/10,000 hrs).
    *   **Mitigation:** Rigorous unit and integration testing; robust error handling.
6.  **Risk:** Cost overruns on development tools or simulated components.
    *   **Mitigation:** Prioritize use of widely available, low-cost technologies; conduct price comparisons.
