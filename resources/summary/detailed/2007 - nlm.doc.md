# Detailed Summary: NLM Digital Repository Requirements Specification

## Background and Scope
The National Library of Medicine (NLM) requires a robust digital repository to fulfill its mission of acquiring, organizing, preserving, and providing access to biomedical literature in all formats. This document outlines high-level functional requirements based on the OAIS (Open Archival Information System) reference model, covering ingest, archival storage, data management, administration, preservation planning, and access for NLM's collection materials under Library Operations. The scope includes existing digital collections like PubMed Central but excludes non-collection resources such as UMLS or Visible Human. A key non-goal is web harvesting functionality, which will use separate software.

## Stakeholders Matrix and Use Cases
*   **General Public (including international users):** End-users who search, view, and access repository materials, subject to potential restrictions based on licensing, copyright, or location.
*   **NIH Staff (including NLM staff):** End-users who require access for research and reference, potentially with different access rights than the public.
*   **NLM Staff (Metadata Access):** Staff who create, review, or edit descriptive and administrative metadata for objects without altering the objects themselves.
*   **NLM Staff (Object Maintenance Access):** Staff who perform quality assurance, file manipulation, format conversion, and technical investigations on the digital objects.
*   **NLM System Administrators/Programmers:** Staff responsible for system management, development, security, and assigning user access rights.
*   **Content Producers/Donors:** External entities (e.g., publishers) who submit digital materials to the repository under negotiated agreements.

**Main Scenarios:**
1.  A content producer submits a journal issue via FTP; the system performs virus checking, validates format, and ingests it after quality assurance.
2.  A public user searches metadata and full text, retrieves a PDF article, and views it online.
3.  An NLM cataloger updates descriptive metadata for a digitized monograph.
4.  Preservation staff monitor technology trends and develop a migration plan for TIFF images.

**Exception Scenarios:**
1.  A submitted SIP fails format validation; the system rejects it and notifies the producer with reasons.
2.  A user attempts to access an embargoed article; the system denies access based on user role and date.
3.  A system error corrupts a stored AIP; error-checking routines detect it and trigger recovery from backup.
4.  A donor submits material in an obsolete format; staff decide to accept it for potential future migration.

## Business Process
**Main Process: Ingest and Store Digital Object**
1.  **Trigger:** Receipt of a Submission Information Package (SIP) from a producer.
2.  **Input:** SIP (digital files and metadata) via electronic transfer or physical media.
3.  **Step 1 - Receive & Validate:** Perform virus checking, verify transfer integrity (checksums), and validate format against approved list.
4.  **Step 2 - Quality Assurance:** Automated and manual review for content, quality, and completeness. Accept or reject (partially or fully).
5.  **Step 3 - Generate AIP:** Transform SIP into Archival Information Package, converting data to archival formats as needed.
6.  **Step 4 - Generate Metadata:** Extract and enhance descriptive, administrative, and structural metadata.
7.  **Step 5 - Coordinate Updates:** Transfer AIP to Archival Storage and metadata to Data Management, confirming successful storage.
8.  **Output:** Stored AIP with linked metadata, ready for access and preservation.

**Key Branch A: Rejection Handling**
1.  **Trigger:** SIP fails QA or validation.
2.  Record rejection reason and metadata.
3.  Notify producer; for certain errors, request resubmission.
4.  Optionally retain metadata for rejected submissions to prevent duplicate review.

**Key Branch B: Access Request**
1.  **Trigger:** User submits a query or order via the Access interface.
2.  Verify user authorization against object's access rights.
3.  Retrieve AIP from storage and associated metadata.
4.  Generate and deliver a Dissemination Information Package (DIP) to the user.

## Domain Model (Key Entities)
*   **Digital Object:** Core entity representing the preserved content. (Fields: Unique Identifier [required, unique], Permanence Level [required], Original File Format, File Size)
*   **Archival Information Package (AIP):** The stored package containing the Digital Object and preservation metadata. (Fields: AIP ID [required, unique], Storage Location, Creation Date, linked to Digital Object [required])
*   **Submission Information Package (SIP):** The package as submitted by a producer. (Fields: SIP ID, Submission Date, Producer ID [reference], Status [e.g., received, validated, rejected])
*   **Metadata Record:** Descriptive, administrative, and technical metadata. (Fields: Record ID [required, unique], Metadata Standard [e.g., MODS, PREMIS], linked to Digital Object [required])
*   **Producer/Donor:** Entity submitting content. (Fields: Producer ID [required, unique], Name, Contact Information, Submission Agreement ID [reference])
*   **Submission Agreement:** Formal contract governing terms of submission. (Fields: Agreement ID [required, unique], Terms, Effective Date, linked to Producer [required])
*   **Access Control Rule:** Defines permissions for users/groups on objects. (Fields: Rule ID, User/Role [required], Object/Collection [required], Permission [required: read, write, etc.])
*   **Audit Log:** Record of system actions and user activities. (Fields: Log ID, Timestamp [required], User/Actor, Action [required], Target Object)

## Interfaces and Integrations
*   **Integrated Library System (ILS):** Direction: Inbound. Interaction: Bibliographic data supply. Input: MARC records. Output: Metadata for repository objects. SLA: Must support standard bibliographic exchange protocols.
*   **NIH Consolidated Collocation Site (NCCS):** Direction: Bi-directional. Interaction: Disaster recovery backup. Input: AIPs for off-site storage. Output: Recovery requests. SLA: Must conform to NIH security and backup policies.
*   **Public Access Interface (Web):** Direction: Outbound. Interaction: User search and retrieval. Input: User queries (supports SRU, OpenSearch). Output: DIPs (HTML, PDF, etc.). SLA: Section 508 compliant, supports multiple languages/scripts.
*   **Metadata Harvesting Interface (OAI-PMH):** Direction: Outbound. Interaction: Expose metadata for harvesting. Input: Harvest requests. Output: Metadata in standard formats (DC, MODS). SLA: Compliant with OAI-PMH protocol.
*   **Internal Staff Client:** Direction: Bi-directional. Interaction: Ingest management, metadata editing, system admin. Input: Staff actions, metadata updates. Output: Workflow status, editing interfaces. SLA: Role-based access control, audit trail.

## Acceptance Criteria
**Capability: Ingest and Validate Submission**
*   Given a producer submits a valid SIP via FTP, when the Ingest function receives it, then the system performs virus checking and checksum validation and places it in a staging area for QA.
*   Given a SIP contains files in a non-preferred format, when the Ingest function processes it, then the system flags it for review and can convert it to an archival format if a policy-based rule exists.

**Capability: Enforce Access Rights**
*   Given a public user searches for an article under embargo, when the Access function processes the request, then the search results omit the article or indicate restricted access.
*   Given an NLM staff member with "Object Maintenance" rights, when they request a TIFF master file, then the system retrieves and delivers the AIP component.

**Capability: Preservation Monitoring**
*   Given a scheduled technology review, when Preservation Planning executes, then the system can generate a report on at-risk formats based on stored technical metadata.

## Non-functional Metrics
*   **Performance:** Supports bulk ingest of large collections; search response time under 3 seconds for typical queries.
*   **Reliability:** 99.9% system availability; statistically valid error checking on all internal data transfers.
*   **Security:** Complies with HHS/NIH security standards; implements granular, role-based access control.
*   **Compliance:** Follows OAIS reference model concepts; adheres to relevant metadata standards (METS, PREMIS, etc.).
*   **Observability:** Maintains a complete audit trail for all system and user actions; generates operational and preservation statistics.

## Milestones and Release Strategy
1.  Finalize and approve requirements specification.
2.  Evaluate commercial and open-source repository software options.
3.  Select and procure/configure repository software solution.
4.  Develop and test core ingest and access workflows with pilot collections.
5.  Implement production repository with phased rollout for different material types (e.g., e-journals, then images).
6.  Establish ongoing preservation planning and policy development cycle.

## Risk List and Mitigation Strategies
1.  **Risk:** Evolving digital formats and standards may outpace preservation strategies. **Mitigation:** Establish active preservation planning function to monitor technology and community trends.
2.  **Risk:** Complex copyright and licensing terms complicate access management. **Mitigation:** Develop a flexible rights metadata schema and machine-actionable access control system.
3.  **Risk:** Lack of dedicated NLM systems staff for implementation and maintenance. **Mitigation:** Secure funding for necessary staff or contractor support during evaluation and implementation phases.
4.  **Risk:** Ingest of non-standard or obsolete formats from special collections. **Mitigation:** Define acceptance policies for exceptions and allocate resources for format migration research.
5.  **Risk:** Integration challenges with existing NLM systems (ILS, PMC). **Mitigation:** Prioritize standards-based interfaces and conduct early integration testing.
6.  **Risk:** Ensuring long-term data integrity and recovery from disasters. **Mitigation:** Implement robust error-checking, checksums, and a tested disaster recovery plan with NCCS.
7.  **Risk:** Insufficient metadata quality from external producers hinders discovery and preservation. **Mitigation:** Define minimum metadata requirements, implement validation, and plan for metadata enhancement workflows.
8.  **Risk:** Budget constraints limit software options or scope. **Mitigation:** Conduct thorough cost-benefit analysis during software evaluation; consider phased implementation based on priority collections.
