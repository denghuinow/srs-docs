# Detailed Summary: ISIN Issuance for Money Market Instruments

## Background and Scope
This project establishes an automated system for the JSE, acting as the National Numbering Agent (NNA), to issue, cancel, and deregister International Securities Identification Numbers (ISINs) for Money Market Instruments (MMIs). The system enables the dematerialization, trading, and same-day electronic settlement of MMIs by providing ISINs electronically via SWIFT messages to STRATE, the Central Securities Depository. The scope includes developing a program to process SWIFT MT598 messages, manage ISIN lifecycle events, and provide a front-end monitoring interface. Non-goals include handling top-ups/reductions of issuance amounts and managing ISINs for equities or bonds.

## Stakeholders Matrix and Use Cases
*   **Money Market Forum (MMF):** Represents money market participants and defines the business requirements for electronic ISIN issuance.
*   **STRATE (CSD/IOR):** Acts as the central securities depository, initiating ISIN requests and confirmations via SWIFT and paying for the service.
*   **JSE (NNA):** The authorized National Numbering Agent responsible for developing, operating, and maintaining the automated ISIN issuance system.
*   **JSE Application and Service Division (ASD):** Responsible for the design, development, testing, and implementation of the ISIN issuance program.
*   **JSE Clearing & Settlement (C&S):** Uses the front-end system for monitoring, manual overrides (BCP), and handling rejections.
*   **MMF Participants/Issuers:** Entities that issue money market instruments, whose requests are routed through STRATE to the JSE.

**Main Scenarios:**
1.  STRATE sends a valid new ISIN request; JSE validates and issues a new ISIN with prefix ZAM.
2.  STRATE sends a request to cancel/de-issue an existing ISIN; JSE validates and confirms cancellation.
3.  STRATE sends a request to deregister an ISIN upon instrument maturity; JSE validates and confirms deregistration.
4.  JSE receives an invalid format SWIFT message and sends a format rejection (MT598-901).
5.  JSE receives a message with invalid content (e.g., duplicate request) and sends a content rejection (MT598-902).
6.  STRATE receives an invalid confirmation from JSE and sends a rejection back.
7.  JSE C&S staff manually issues an ISIN via the front-end during a Business Continuity Plan (BCP) event.
8.  JSE C&S staff views and prints reports of issued, cancelled, or deregistered ISINs via the front-end.

## Business Process
**Main Process: ISIN Issuance**
1.  **Trigger:** STRATE sends a validated ISIN Issue Request (MT598-150-NEWM) to JSE.
2.  **Input:** SWIFT MT598-150 message with MMI details (Issuer Code, Instrument Type, Generic Category, Dates, etc.).
3.  JSE system validates message format and content.
4.  JSE system checks for duplicates and validates against ISIN issuance rules.
5.  JSE system generates a new ISIN with prefix ZAM and records it.
6.  **Output:** JSE sends an ISIN Confirmation (MT598-151) back to STRATE, including the new ISIN.
7.  STRATE validates the confirmation message.
8.  Process completes; ISIN is active for use in settlement.

**Key Branch A: Request Rejection**
1.  **Trigger:** JSE validation fails (format or content error).
2.  JSE system generates a rejection message (MT598-901 for format, MT598-902 for content).
3.  JSE sends rejection to STRATE and triggers an email alert to JSE C&S.
4.  Process ends; original request is not processed.

**Key Branch B: Confirmation Rejection**
1.  **Trigger:** STRATE validation of JSE's confirmation message fails.
2.  STRATE generates a rejection message (MT598-901 or MT598-902).
3.  STRATE sends rejection back to JSE.
4.  JSE system logs the rejection and triggers an email alert to JSE C&S.

## Domain Model
Core entities and their key fields:
1.  **ISIN Record:** ISIN Code (unique, required), Status (Active/Cancelled/Deregistered, required), Issue Date (required), Issuer Participant Code (required, reference), Quantity Issued (required).
2.  **Financial Instrument:** Generic Category (1-4, required), MMI Type (e.g., EBA, NCD, required), Short Description.
3.  **Issuance Details:** Coupon Rate (conditional), Coupon Payment Frequency (conditional), Coupon Payment Day (conditional), Maturity Date (conditional), Issue Date (required).
4.  **Issuer:** Participant Code (unique, required).
5.  **SWIFT Message Log:** Transaction Reference (unique, required), Message Type (e.g., 150, 151, 901), Direction, Related Reference, Preparation Date/Time, Status.
6.  **Rejection Record:** Error Code (required), Error Details, Related Message Reference (required, reference).
7.  **Front-End User (JSE C&S):** User ID.
8.  **Manual Override Record (BCP):** ISIN, Override Date/Time, User ID (reference), Reason.

## Interfaces and Integrations
1.  **SWIFT Network (JSE to/from STRATE)**
    *   **Direction:** Bidirectional.
    *   **Interaction:** Exchange of MT598 proprietary messages for all ISIN lifecycle events.
    *   **Input Key Points:** MT598-150 (Request), MT598-151 (Confirmation).
    *   **Output Key Points:** MT598-901/902 (Rejection), MT598-151 (Confirmation).
    *   **SLA Key Points:** Message format per ISO15022/ANNA rules, agreed error codes, BIC addressing (JSE: XJSEZAJJXISN).
2.  **Front-End User Interface (for JSE C&S)**
    *   **Direction:** Internal.
    *   **Interaction:** Screens for manual ISIN entry (BCP), view rejections, view/print ISIN reports, update issuer codes.
    *   **Input Key Points:** Manual ISIN data, search parameters (ISIN, issuer, date ranges).
    *   **Output Key Points:** On-screen data grids, printable reports, email alerts for rejections.
    *   **SLA Key Points:** Real-time email alerts for rejections, parameter-driven reporting.

## Acceptance Criteria
**Capability: Automated ISIN Issuance**
*   Given a valid MT598-150-NEWM message is received from STRATE, when the JSE system processes it, then a new ZAM-prefixed ISIN is generated and returned in an MT598-151 confirmation.
*   Given a duplicate ISIN request is received, when the JSE system validates it, then an MT598-902 content rejection is sent to STRATE.

**Capability: ISIN Cancellation**
*   Given a valid MT598-150-DISS message for an active ISIN is received, when processed, then the ISIN status is updated to 'Cancelled' and an MT598-151 confirmation is sent.
*   Given an MT598-150-MATU message is received on an instrument's maturity date, when processed, then the ISIN status is updated to 'Deregistered' and confirmed.

**Capability: Front-End Monitoring**
*   Given a JSE C&S user searches for an ISIN, when the query is executed, then all instrument details and status are displayed.
*   Given a SWIFT message is rejected by the JSE system, when the rejection occurs, then an email with rejection details is sent to the designated JSE C&S team.

## Non-Functional Metrics
*   **Performance:** System must support an estimated 200-500 ISIN issuances per day. SWIFT message processing and response should occur within minutes to support T+0 settlement.
*   **Reliability:** Availability as per the Service Level Agreement (SLA) with STRATE, including a defined Business Continuity Plan (BCP).
*   **Security:** SWIFT communication requires Bilateral Key Exchange (BKE). Front-end access restricted to authorized JSE C&S personnel.
*   **Compliance:** ISIN issuance must adhere to ANNA Guidelines (ISO 6166) and JSE's ISIN Issuance Rules.
*   **Observability:** Comprehensive logging of all SWIFT messages and system actions. Front-end provides daily rejection logs and audit trails.

## Risk List and Mitigation Strategies
1.  **Risk:** Delays in final approval of SWIFT message standards by NMPG.
    *   **Mitigation:** Proceed with development based on draft specifications, pending formal approval.
2.  **Risk:** High volume of ISIN requests impacting system performance.
    *   **Mitigation:** Design system to handle peak loads and establish monitoring alerts.
3.  **Risk:** SWIFT network or interface failure disrupting ISIN issuance.
    *   **Mitigation:** Implement BCP with manual front-end issuance capability and defined procedures.
4.  **Risk:** Invalid data in SWIFT messages causing processing errors.
    *   **Mitigation:** Implement robust validation and clear rejection messaging with error codes.
5.  **Risk:** Disagreement on cost recovery between JSE and STRATE.
    *   **Mitigation:** Define clear monthly running costs and billing methodology in the SLA.
6.  **Risk:** Non-compliance with ANNA/ISO rules in automated issuance.
    *   **Mitigation:** Incorporate rule checks into system logic and conduct compliance reviews.
7.  **Risk:** Inadequate front-end functionality for operational monitoring.
    *   **Mitigation:** Engage JSE C&S users in UAT to ensure reporting and alerting needs are met.
8.  **Risk:** Errors in manual ISIN entry during BCP.
    *   **Mitigation:** Provide controlled front-end screens with data validation for manual overrides.
