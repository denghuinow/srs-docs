# Detailed Summary: PHIN Outbreak Management Functional Requirements

## Background and Scope
This document defines the functional requirements for systems supporting the Public Health Information Network (PHIN) Outbreak Management (OM) area. The primary goal is to support the investigation, monitoring, management, analysis, and reporting of health events or acts of bioterrorism. The system must be configurable to handle different event types, capturing data related to cases, contacts, exposures, specimens, laboratory results, and travel history. A core function is creating traceable links between entities to understand transmission mechanisms. The scope includes integration with early event detection, countermeasure administration, laboratory, and surveillance systems. Non-goals include defining specific transport protocols or implementation details, which are covered in separate cross-functional documents.

## Stakeholders Matrix and Use Cases
*   **Public Health Investigator**: Conducts case and exposure investigations, collects data, and traces contacts.
*   **Laboratory Personnel**: Processes specimen test requests, returns results, and maintains chain of custody.
*   **Public Health Response Coordinator**: Manages the overall health event response, coordinates across jurisdictions, and oversees reporting.
*   **System Administrator**: Configures the system for new health events, manages user roles, and ensures system availability.
*   **Data Analyst**: Performs analysis on aggregated data, generates visualizations (e.g., epi-curves, maps), and creates reports.
*   **Partner Organization (e.g., other health departments)**: Exchanges case, contact, and laboratory data across jurisdictional boundaries.

**Main Scenarios**: 1) Initiating a new health event investigation and defining its parameters. 2) Investigating a new case, linking it to the event, and completing an electronic questionnaire. 3) Identifying and tracing exposure contacts from a confirmed case. 4) Requesting laboratory tests for a collected specimen and receiving/processing the results.
**Exception Scenarios**: 1) Handling investigation data when the system is in disconnected/offline mode. 2) Updating case status and records when the official case definition changes mid-investigation. 3) Managing data exchange and activity logs for cases that cross jurisdictional boundaries.

## Business Process
**Main Process: Manage Health Event Investigation**
1.  **Trigger**: Identification of a potential health event.
2.  Create a new health event record with a unique Event ID and capture initial details (suspected agent, geographic area, case definition).
3.  Identify and register entities (persons, animals, locations) involved in the event.
4.  For each case entity, initiate a case investigation, assign a unique Case ID, and complete an electronic questionnaire to collect demographic and epidemiological data.
5.  Identify and trace exposure contacts from the case, creating links between entities.
6.  Collect specimens from relevant entities, assign Specimen IDs, and create laboratory test requests.
7.  Receive, parse, and link laboratory results to the corresponding specimens and entities.
8.  Generate analysis, visualizations, and reports (e.g., line lists, aggregate counts, maps) to support containment efforts.

**Key Branch A: Manage Disconnected Operations**
1.  **Trigger**: Investigator needs to work offline (e.g., in the field).
2.  Investigator collects data locally on a disconnected device.
3.  Upon reconnection, data is synchronized with the central server.
4.  Conflicts are resolved according to defined policies, ensuring all instances share consistent data.

**Key Branch B: Update Case Definition**
1.  **Trigger**: Official case definition for the health event changes.
2.  System configuration is updated with the new case definition criteria.
3.  Existing case records are manually or automatically re-evaluated against the new definition.
4.  Case statuses are updated, and the change history is tracked.

## Domain Model
Core entities and their key fields/constraints:
*   **Health Event**: Event ID (unique, required), Category, Start Date, Status, Case Definition.
*   **Entity**: Subject ID (unique, required), Type (Person/Animal/Location/etc.), Name, Demographic Details (varies by type).
*   **Case**: Case ID (unique, required), linked to Entity and Health Event (required), Diagnosis, Status (confirmed/probable/suspect), Symptom Onset Date.
*   **Exposure Contact**: Contact ID, linked to Source Entity and Exposed Entity (required), Exposure Type, Dates, Proximity.
*   **Specimen**: Specimen ID (unique, required), linked to Subject Entity (required), Collection Date/Time, Type, Suspected Agent.
*   **Laboratory Test Request**: Linked to Specimen(s) (required), Request Date, Test Type.
*   **Laboratory Result**: Linked to Test Request and Specimen (required), Result Date/Time, Result Value, Interpretation.
*   **Activity Log**: Activity ID, Timestamp (required), User, Activity Type, Description.

## Acceptance Criteria
**Capability: Case Investigation & Linking**
*   Given a new health event exists, when an investigator creates a new case for a person entity, then the system assigns a unique Case ID and links it to the Event ID and the person's Subject ID.
*   Given a case is under investigation, when laboratory results are received, then the system successfully links the results to the correct specimen and the associated case record.

**Capability: Contact Exposure Tracing**
*   Given a confirmed case record, when an investigator identifies an exposure contact, then the system allows the creation of a new contact record with a unique Contact ID and establishes a link defining the exposure relationship between the two entities.
*   Given multiple contacts exist for a case, when an investigator requests a work list, then the system can generate a list sortable by priority or geographic area.

**Capability: Disconnected Operations**
*   Given an investigator is working offline, when they collect case investigation data, then the data is stored locally. When the device reconnects, then the data is synchronized with the central server without loss.

## Non-Functional Metrics
*   **Performance**: System must support configurable electronic questionnaires and dynamic data capture. Must enable analytical searches based on multiple criteria.
*   **Reliability/Availability**: Must have a continuity plan for operations when systems are unavailable. Must support multiple deployment options (client-server, disconnected, web).
*   **Security**: Must protect data from corruption and unauthorized access. Must support digital signatures for questionnaires.
*   **Compliance**: Must use established vocabulary standards (e.g., LOINC, SNOMED) for data exchange. Must adhere to privacy requirements protecting patient and personnel information.
*   **Observability**: Must capture activity logging data (timestamp, user, activity type) for management and audit purposes.

2.  Define detailed message implementation guides for key exchanges (Lab, Case, Contact).
3.  Develop and test core configuration engine for dynamic fields/entities.
4.  Pilot integrated data exchange with laboratory and surveillance partner systems.
5.  Develop and deliver training for public health investigators and system administrators.
6.  Full deployment of OM system capabilities to support health event investigations.

## Risk List and Mitigation Strategies
1.  **Risk**: Inability to handle diverse and evolving health events with fixed data models.
    *   **Mitigation**: Mandate a highly configurable system architecture allowing addition of fields, entities, and relationship types.
2.  **Risk**: Data inconsistency and loss during synchronization from disconnected operations.
    *   **Mitigation**: Establish clear data synchronization policies and conflict resolution protocols.
3.  **Risk**: Failure to accurately link data (e.g., lab results to cases) across complex investigations.
    *   **Mitigation**: Enforce strict requirements for unique identifiers (Subject ID, Specimen ID, Case ID) and unambiguous linking logic.
4.  **Risk**: Ineffective cross-jurisdictional collaboration due to incompatible data formats.
    *   **Mitigation**: Require use of standard vocabularies and PHIN message guides for all data exchanges, including mapping interfaces for custom data.
5.  **Risk**: System unavailability during a critical health event response.
    *   **Mitigation**: Develop and test a comprehensive continuity of operations plan (COOP).
6.  **Risk**: Privacy breaches of sensitive investigation data.
    *   **Mitigation**: Implement robust security controls and adhere to overarching PHIN privacy requirements.
7.  **Risk**: Poor user adoption due to complex workflows for field investigators.
    *   **Mitigation**: Design reusable questionnaire libraries and support intuitive field data collection, including printing for offline use.
8.  **Risk**: Inability to scale analysis and reporting for large-scale events.
    *   **Mitigation**: Ensure ability to aggregate data into a central warehouse and export to common analytical tools.
