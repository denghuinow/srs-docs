# Detailed Summary: NDE System Requirements Specification

## Background and Scope
The NPOESS Data Exploitation (NDE) system is designed to receive, process, package, archive, and distribute data from the NPOESS Preparatory Project (NPP) and NPOESS satellites to NOAA's operational and climate communities and other civilian customers. Its primary mission includes disseminating NPOESS Data Records, generating tailored and NOAA-unique products, delivering products to the CLASS archive, and providing customer support services. The system will be partitioned into Operational (OPS), System Test (TEST), and Development (DEV) environments. Non-goals include not being the primary satellite data acquisition system (that is IDPS) and not developing core scientific algorithms internally (they are NOAA-supplied).

**Main/Exception Scenarios (≤8):**
1.  **Nominal Product Generation & Distribution:** System ingests xDRs from IDPS, processes them into NOAA-unique/tailored products, and distributes to subscribed users within latency targets.
2.  **Customer Subscription & Order Fulfillment:** User registers, requests product subscription, gets approved, and receives products via push or pull mechanisms.
3.  **Data Delivery to CLASS:** System automatically packages and delivers NOAA-unique products and system elements to the CLASS archive.
4.  **System Monitoring & Health Reporting:** Operators monitor system health, performance metrics, and product quality; system generates alerts and reports.
5.  **Degraded Operations Mode:** Upon notification from NPOESS, system enters degraded mode, generates subset of priority products, and notifies affected customers.
6.  **Restricted Access Mode:** System restricts data access based on defined criteria (e.g., Data Denial Plan) and notifies authorized users receiving restricted data.
7.  **Failure Recovery & Failover:** System detects failure, executes automated recovery procedures, and fails over to backup (e.g., TEST environment) to maintain service.
8.  **Reprocessing Archived Data:** Operator initiates ingestion and processing of historical data from CLASS for product regeneration or testing.

## Business Process
**Main Process: Operational Product Generation & Distribution (≤8 steps)**
1.  **Trigger:** Receipt of xDR data delivery notification from IDPS.
2.  **Ingest & Validate:** Request and receive xDRs from IDPS; validate data integrity and metadata.
3.  **Acquire Ancillary Data:** Retrieve necessary ancillary data (e.g., from NCEP) for processing.
4.  **Execute Product Generation:** Schedule and execute scientific algorithms to generate NOAA-unique and tailored products.
5.  **Apply Tailoring:** Reformats, compresses, re-projects, or aggregates products per customer subscriptions.
6.  **Distribute to Customers:** Make products available for pull delivery or push to customer endpoints.
7.  **Archive to CLASS:** Package and deliver NOAA-unique products and relevant metadata to CLASS.
8.  **Update Logs & Notify:** Update order status logs and send notifications to customers.

**Key Branch A: System Failure & Recovery (≤4 steps)**
*   **Trigger:** Detection of hardware/software failure or performance degradation.
*   **Isolate & Notify:** Isolate affected component, log event, and notify operators.
*   **Execute Failover:** Automatically initiate failover procedures to redundant system or TEST environment.
*   **Restore Service:** Resume product processing and distribution from the point of failure or last checkpoint.

**Key Branch B: Customer Subscription Management (≤4 steps)**
*   **Trigger:** New user registration or subscription request via online portal.
*   **Review & Approve:** Government authority reviews and approves/denies request.
*   **Configure System:** System updates user access controls and product subscription profiles.
*   **Confirm & Notify:** Send confirmation and access instructions to the user.

## Domain Model (Entities ≤8)
*   **Data Product:** ID (unique), Type (xDR/Tailored/NOAA-unique), Format, Generation Timestamp, Shelf Life, Quality Flags, Metadata (required).
*   **User/Customer:** UserID (unique), Name, Organization, Contact Info, Authorization Level, Subscription List (reference).
*   **Product Subscription:** SubscriptionID (unique), UserID (reference, required), Product Type, Delivery Format, Delivery Method, Latency Requirement.
*   **Algorithm/System Element:** ElementID (unique), Name, Version, Type (Algorithm/Utility), Status, Storage Location (reference to CLASS).
*   **Processing Job:** JobID (unique), Trigger (Schedule/Event), Input Data References, Algorithm ID (reference), Priority, Status, Start/End Time.
*   **System Log/Performance Record:** RecordID (unique), Timestamp, Component, Event Type, Severity, Details, Metrics (e.g., latency, volume).
*   **Ancillary Data:** DatasetID (unique), Source, Type, Validity Period, Data Reference.
*   **Archive Manifest (for CLASS):** ManifestID (unique), Timestamp, Product/Element List, Delivery Status, CLASS Receipt Acknowledgement.

## Interfaces and Integrations (≤8 total)
1.  **System: IDPS | Direction: Inbound | Theme:** Primary data acquisition.
    *   **Input Key Points:** xDRs (HDF5), SARSAT/A-DCS telemetry, Data Delivery Reports (DDRs).
    *   **Output Key Points:** Subscription requests, ad-hoc retransmission requests.
    *   **SLA Key Points:** Real-time receipt; access latency <10 sec from notification.
2.  **System: CLASS | Direction: Bi-directional | Theme:** Long-term archiving and data retrieval.
    *   **Input Key Points:** Archived xDRs and products for reprocessing.
    *   **Output Key Points:** NOAA-unique products, system elements, metadata, manifests.
    *   **SLA Key Points:** Delivery and receipt acknowledgements; conform to CLASS interface specs.
3.  **System: NPOESS MMC (via ESPC) | Direction: Bi-directional | Theme:** Mission coordination.
    *   **Interaction Points:** Service requests, status inquiries, degraded/restricted mode notifications.
    *   **SLA Key Points:** 100% of messages delivered within ICD-specified time.
4.  **System: External Ancillary Data Sources (e.g., NCEP) | Direction: Inbound | Theme:** Acquisition of processing inputs.
    *   **Input Key Points:** Meteorological/oceanographic model data.
    *   **Output Key Points:** (None specified).
5.  **System: Customer Delivery Endpoints | Direction: Outbound | Theme:** Product distribution.
    *   **Output Key Points:** Tailored/NOAA-unique products in various formats (BUFR, GRIB, netCDF, etc.).
    *   **Input Key Points:** (Potentially pull requests).
    *   **SLA Key Points:** Meet customer-specified latency (<5 min target).
6.  **System: ESPC Trouble Ticket System | Direction: Outbound | Theme:** Operational support.
    *   **Output Key Points:** System issue reports, change requests.
7.  **System: NPOESS Trouble Ticket System | Direction: Outbound | Theme:** IDPS/data source issue reporting.
    *   **Output Key Points:** Data quality or delivery issue reports.
8.  **System: USMCC & US Global Processing Center | Direction: Outbound | Theme:** Specialized data relay.
    *   **Output Key Points:** SARSAT and A-DCS telemetry/data.
    *   **SLA Key Points:** Delivery within 1 minute of receipt from IDPS.

## Acceptance Criteria (2–4 Given-When-Then per capability)
*   **Capability: Generate NOAA-Unique Product**
    *   Given all required xDRs and ancillary data are ingested,
    When the scheduled product generation job executes,
    Then a NOAA-unique product in HDF5 format with compliant metadata is created and placed in the distribution queue.
    *   Given a product generation job fails due to corrupt input,
    When the failure is detected,
    Then the job is logged as failed, an alert is sent to operators, and recovery procedures are initiated.
*   **Capability: Distribute Product to Customer**
    *   Given a subscribed customer and a new product is available,
    When the distribution scheduler runs,
    Then the product is formatted per the subscription (e.g., GRIB2, GZIP) and delivered to the customer's endpoint.
    *   Given a customer subscription with a latency requirement of 5 minutes,
    When the final input xDR is received,
    Then the finished product is made available for distribution within 5 minutes.
*   **Capability: Archive to CLASS**
    *   Given a NOAA-unique product is generated,
    When the archiving process runs,
    Then the product and its FGDC-compliant metadata are packaged and sent to CLASS, and a delivery manifest is recorded.
    *   Given a system element (e.g., algorithm version) is approved for baselining,
    When an operator initiates archiving,
    Then the element's source code and documentation are delivered to CLASS for permanent archive.

## Non-Functional Metrics
*   **Performance:** Product generation latency <5 minutes from final input receipt for 98% of products; IDPS data access latency <10 seconds.
*   **Reliability/Availability:** Operational environment availability >98% over 12 months; individual capabilities (Ingest, Generation, Distribution) not interrupted >2hrs/24hrs or >4hrs/30days.
*   **Security:** Compliance with NOAA IT Security Manual; data integrity protected from human error, transmission error, software bugs, hardware failure, and natural disasters.
*   **Compliance:** Conformance to Federal Enterprise Architecture (FEA); metadata compliant with FGDC CSDGM standards and remote sensing extensions.
*   **Observability:** Retention of performance logs for ≥90 days; capability to generate custom reports on system performance and product processing.

## Risk List and Mitigation Strategies (≤8 items)
1.  **Risk:** Inability to meet stringent latency requirements due to data volume or processing complexity.
    *   **Mitigation:** Design for scalable, parallel processing; prototype critical algorithms; establish performance testing early.
2.  **Risk:** Delays or instability in external interfaces (IDPS, CLASS).
    *   **Mitigation:** Develop robust interface handlers with retry logic; participate in joint interface testing; establish clear ICDs and SLAs.
3.  **Risk:** Failure to achieve required system availability targets.
    *   **Mitigation:** Implement high-availability architecture with automatic failover; comprehensive disaster recovery (COOP) planning.
4.  **Risk:** Challenges in integrating NOAA-supplied scientific algorithms.
    *   **Mitigation:** Define clear algorithm packaging (DAP) and integration standards early; provide robust development/test (SADIE) environment.
5.  **Risk:** Scalability issues transitioning from NPP to NPOESS C1/C2 data volumes.
    *   **Mitigation:** Design modular, scalable infrastructure from outset; conduct volume stress testing during NPP era.
6.  **Risk:** Evolving security threats and compliance requirements.
    *   **Mitigation:** Adhere to NOAA security policies; design with security in mind; plan for regular security assessments and updates.
7.  **Risk:** Insufficient developer resources or expertise for sustainable system evolution.
    *   **Mitigation:** Use COTS/open-source where possible; design for reusability and modularity; implement comprehensive documentation and knowledge transfer.
8.  **Risk:** Dependency on legacy hardware/software reuse may limit performance or increase maintenance.
    *   **Mitigation:** Conduct trade-off analysis for reuse vs. new procurement; ensure government approval for reuse items; plan for phased modernization.
