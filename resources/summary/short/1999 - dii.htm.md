# Short Summary

## Background and objectives
This SRS defines requirements for XML Services (XS) within the DII Common Operating Environment (COE) to provide infrastructure services for mission applications using XML technology. The objective is to isolate vendor-specific implementations and provide data management functions for accessing distributed databases to achieve interoperability.

## In scope
*   Registration of XML terms, tags, and structures (DTDs, DCDs) via producer, consumer, and manager services.
*   Design of XML schemas, including structure and content services for creating and validating tags.
*   Generation of XML and schema documents, including conformance checking and rendering.
*   Consumption of XML documents via parsers and validation services.
*   Operation within specified environmental modes (e.g., real-time, fixed, dynamic, degraded communications).

## Out of scope
*   Detailed design of internal programming interfaces and data structures (to be specified later).
*   Detailed specifications for external interfaces to commercial products (e.g., Sybase, Oracle).
*   Personnel and training requirements (determined by system developers).
*   Expansion on specific data management administrative processes.
*   Detailed packaging procedures (follows DII COE guidelines).

## Stakeholders and core use cases
*   **Defense Information Systems Agency (DISA)**: Oversees the COE baseline and configuration management.
*   **DII COE AOG Data Access Services TWG**: Prepares and maintains the XS specification.
*   **COE Chief Engineer**: Approves Points of Contact for Communities of Interest and mediates disputes.
*   **COE Data Engineering Team**: Analyzes tags and semantics for consolidation opportunities.
*   **Community of Interest (COI) Point of Contact**: Manages the status and lifecycle of information resources within their COI.
*   **System Developers/Application Developers**: Implement and integrate XS components into COE-compliant systems.

**User Stories:**
1.  As a **producer**, I want to submit metadata and XML artifacts to the registry so that terms are available for reuse and semantic understanding.
2.  As a **consumer**, I want to discover, view, and download registered XML tags and structures so that I can reuse them in my applications.
3.  As a **data/database manager**, I want to review, approve, and monitor submissions to the registry so that data standards and naming conventions are maintained.
4.  As an **application developer**, I want to design XML schemas using existing registered tags so that I ensure interoperability and compliance.
5.  As an **end-user (e.g., in a deployed unit)**, I want the XS to adapt to degraded communications so that session time-outs can be managed dynamically.
6.  As a **maintainer**, I want to modify application data segments and user permissions so that the system can be updated and restructured.

## Success metrics
*   Successful qualification of COE software through formal validation tests (Test, Demonstration, Analysis, Inspection) against SRS requirements.
*   Establishment of a functional XML Registry enabling the discovery, submission, and management of approved XML tags and structures.
*   Demonstrated ability of XS components to operate on COE-compliant platforms in the required environmental modes.

## Major constraints
*   XS must be segmented and comply with COE compliance level requirements as described in the I&RTS.
*   Must adhere to DOD data standards conventions and established naming structures within the COE architecture.
*   Must internally interface transparently with existing DBIF, DAC, and COTS RDBMS data elements.
*   Registry software must be portable and execute on COE-compliant platforms.
*   Development must follow applicable government standards (e.g., MIL-STD-498, FIPS PUB 127-2).

## Undecided issues
*   Specific precedence and criticality codes (Essential, Desirable, Optional) for individual requirements are To Be Determined (TBD).
*   Detailed external and internal programming interface specifications are unavailable and will be defined during the design phase.
*   The specific addressee (email/FTP) for submitting the Information Resource Submittal Package is not specified.
*   The complete set of metadata for submission (referenced in Appendix A) requires finalization.
*   The explicit rules of engagement for federated registries are not fully defined.
