# Short Summary: VII Data Use Analysis and Processing (DUAP) System Requirements

## Background and Objectives
The DUAP system is a research prototype for the Michigan Department of Transportation (MDOT) to evaluate Vehicle Infrastructure Integration (VII) data's utility in enhancing safety, mobility, and asset management. Its objective is to collect, consolidate, convert, and communicate VII and other transportation data to support operational decisions and application demonstrations.

## In Scope
*   Collecting probe vehicle, traffic, weather, and road condition data from multiple sources, including the VII Proof of Concept network.
*   Processing data via computational services to derive traffic metrics, detect incidents, and assess road conditions.
*   Storing data dynamically (cached for one week) and persistently (archived) with geo-references and timestamps.
*   Publishing processed data and alerts in standard formats (e.g., SAE J2354) for external systems and internal presentation services.
*   Providing web-based user interfaces for browsing traffic, incident, weather, and asset condition information.

## Out of Scope
*   Operational deployment as a production system; it is a functional prototype for demonstration and assessment.
*   Collection of probe data from several transit agencies (e.g., The Rapid, Ann Arbor Transit, DDOT) and car rental fleets, which are deferred.
*   Publishing data to specific traffic analysis tools (VISSIM, Synchro, Paramics, SimTraffic), which are deferred.
*   Real-time data with zero latency; the system handles "near real-time" data with inherent delays.
*   Resolving data privacy, ownership, and policy issues, which are external institutional requirements.

## Stakeholders and Core Use Cases
**Stakeholders:**
*   **MDOT & Partner Transportation Agencies (Operators, Maintainers, Asset Managers):** Use data to minimize incident impact, maintain roadways, and manage assets cost-effectively.
*   **System Administrators:** Administer the DUAP system to ensure data availability.
*   **Transportation Agency Management & Contractors:** Supervise staff and perform contracted work using DUAP data.
*   **Travelers:** Obtain trip information for route planning and delay avoidance.
*   **Emergency Services:** Use data for incident response and impact assessment.
*   **Researchers/University Personnel (e.g., UMTRI):** Analyze data for transportation research.
*   **Michigan Transportation Research Board (MTRB):** Advises on research needs and direction.
*   **Automobile Manufacturers (OEMs) & VII Network Operators:** Provide vehicle data and operate the communication infrastructure.

**Core User Stories:**
1.  As a **Transportation Operator**, I want to view detected incidents and traffic conditions so that I can quickly assess and respond to events.
2.  As a **System Administrator**, I want to add or modify data input services so that I can integrate new data sources into the system.
3.  As a **Maintainer**, I want to receive alerts on pothole locations so that I can prioritize roadway repair tasks.
4.  As a **Traveler**, I want to access a public web interface showing travel times and incidents so that I can plan my route accordingly.
5.  As a **Researcher**, I want to access archived, geo-referenced probe data so that I can analyze traffic patterns and algorithm effectiveness.
6.  As an **Asset Manager**, I want to browse derived road condition reports so that I can inform annual program and project planning.

## Success Metrics
*   Successful integration and processing of VII probe data alongside traffic and weather data from specified sources.
*   Demonstrated utility of derived information (e.g., incident detection, travel time) for at least one operational application per key area (safety, mobility, asset management).
*   System meets specified performance and quality characteristics, including extensibility for adding new data sources and algorithms.

## Major Constraints
*   Must conform to Michigan Department of Information Technology (MDIT) IT standards, including using a Java foundation and Oracle database.
*   Must use Michigan Geographic Framework for all geo-references.
*   Data is "near real-time" with inherent latency; consuming systems must evaluate data suitability based on timestamps.
*   Data quality may vary due to vehicle sensor calibration states; applications must handle data quality flags.
*   Data volume and availability depend on external factors like the number of VII-equipped vehicles and roadside units.

## Undecided Issues
*   Specific interface formats for many external data sources and output consumers are to be determined during prototype design.
*   The ability to link probe data directly to specific vehicles for research poses unresolved privacy and anonymity policy issues.
*   Ownership and use limitations for commingled data from third-party sources may impact DUAP's usefulness.
*   The system's capability to collect Origin/Destination (O/D) data is noted, but the specific type of O/D data needs to be established.
*   Implementation details for certain presentation features (e.g., unit selection, data layer management) are deferred or marked as low priority.
