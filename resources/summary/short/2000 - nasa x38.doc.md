# Short Summary: X-38 Fault Tolerant System Services (FTSS) Requirements

## Background and Objectives
The FTSS software provides fault-tolerant system services for NASA's X-38 Crew Return Vehicle's quad-redundant Flight Critical Computer (FCC). It serves as an interface between application software and underlying hardware/operating system to ensure reliable operation in aerospace environments.

## In Scope
- System initialization and synchronization services
- Scheduling services with 50Hz/10Hz/1Hz rate groups
- Fault detection, isolation, and redundancy management
- Communication services (synchronous and immediate message passing)
- Time services (Mission Elapsed Time and Separation Elapsed Time)

## Out of Scope
- Non-Radstone VME slave board initialization
- Application-specific fault response mechanisms
- Hardware-level network element diagnostics
- Year 2000 compliance (not used in time services)
- Training and logistics requirements

## Stakeholders and Core Use Cases
**Stakeholders:**
- NASA Johnson Space Center: System owner and requirements authority
- Charles Stark Draper Laboratory: FTSS developer and maintainer
- X-38 Application Developers: Users of FTSS API services
- Flight Operations: End users of the operational system

**User Stories:**
1. As a flight application developer, I want to create rate-based tasks so that my code executes at precise intervals.
2. As a system operator, I want automatic fault detection and recovery so that the system maintains operation despite hardware failures.
3. As an ICP application developer, I want immediate message passing services so that I can communicate sensor data to FCPs with minimal latency.
4. As a mission manager, I want vehicle mode changes so that I can adapt system behavior to different flight phases.
5. As a telemetry system, I want fault status reporting so that ground control can monitor system health.
6. As a recovery system, I want memory alignment services so that failed channels can be reintegrated without data corruption.

## Success Metrics
- System initialization within 1.5 minutes from power-on
- Fault isolation within 60 milliseconds of detection
- Two-fault tolerance throughout all mission phases

## Major Constraints
- Must operate on Radstone PowerPC 604R hardware
- Must use VxWorks 5.4 operating system
- Maximum 3MB ROM and 9MB DRAM usage
- All FCP software modules must be identical
- Must support operation with any 3 of 5 FCRs active

## Undecided Issues
- Specific memory protection implementation methodology
- Complete set of allowable VxWorks API calls for applications
- Final telemetry data format and structure
- Detailed power sequencing requirements
- Validation approach for Byzantine fault resilience
