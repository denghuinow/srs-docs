# Balanced Summary: I-15 Reversible Lane Control System (I-15 RLCS) Application Software Requirements

## Goals and Scope
The I-15 RLCS Application Software aims to replace an aging system to safely open and close reversible lanes for peak traffic and special events. It will interface with new field hardware components and support monitoring, control, sequencing, data processing, and reporting functions to enhance traffic management in Southern California.

## Stakeholders and User Stories
*   **Operator:** Controls the system during normal mode and can change the system mode.
*   **Management:** Accesses reporting and status checking capabilities only.
*   **Field Maintenance Staff:** Controls the system during maintenance mode from authorized workstations.
*   **Electrical Systems (Hardware) Staff:** Performs reporting and status checking.
*   **Software Systems Staff:** Performs reporting and status checking.
*   **System Administrator:** A District 11 technical staff member who configures system data, including staff, devices, and schedules, and can change the system mode.

**User Stories:**
1.  As an **Operator**, I want to issue commands to open or close the reversible lanes so that I can manage peak traffic flows.
2.  As **Management**, I want to generate historical operation reports so that I can analyze system performance and traffic patterns.
3.  As **Field Maintenance Staff**, I want to execute maintenance control sequences from remote dial-in terminals so that I can repair devices without traveling to the TMC.
4.  As a **System Administrator**, I want to create and modify user security levels and device configurations so that I can manage system access and adapt to changes.
5.  As an **Operator**, I want the system to alert me with audible and visual alarms for critical device failures so that I can respond to safety issues promptly.
6.  As an **external system (e.g., ATMS)**, I want to retrieve RLCS lane status from an external server so that I can provide integrated traveler information.

## Key Processes
1.  **System Startup & Initialization:** Triggered by power-on; each control unit identifies itself, verifies hardware, and initializes device monitoring.
2.  **Continuous Device Monitoring:** Triggered continuously; the system polls all field device sensors and updates status displays every 2 seconds.
3.  **Alarm Detection & Notification:** Triggered by a status change; the system checks sensor data against criteria and generates critical or warning alarms within 2 seconds.
4.  **Command Processing & Safety Screening:** Triggered by an operator or scheduled command; each command is validated against safety rules at multiple control levels before execution.
5.  **Scheduled Sequence Execution:** Triggered by a system schedule check (every 60 seconds); the system presents scheduled opening/closing operations to the operator for confirmation.
6.  **Sequence Halt & Recovery:** Triggered by a device failure or illegal status change during a sequence; the operation halts, and the operator is prompted with recovery options.
7.  **Data Logging & External Export:** Triggered by commands and status changes; the system logs all activity and updates an external data store for other systems every 30 seconds.

## Domain Data Elements
*   **Device** (Primary Key: Device ID): Name, Device Status ID, Location ID, Device Category ID, Last Maintenance Date.
*   **Personnel** (Primary Key: Personnel ID): Name, Login Initials, Password, Password Date, Personnel Classification ID.
*   **System Operational Command** (Primary Key: Command ID): Name, Description, Timeout, Command Level.
*   **Device Command Log** (Primary Key: Log ID): Device Command ID, Date, Time, Device Status ID, Operator ID.
*   **Alarm Type** (Primary Key: Alarm Type ID): Description (e.g., Critical, Warning).
*   **System Mode** (Primary Key: Mode ID): Name (e.g., Normal, Degraded, Emergency, Maintenance).

## Non-Functional Requirements
1.  **Availability:** The system must be operational 24/7 with a recovery time of ≤10 minutes and uptime of ≥99.99%.
2.  **Performance:** GUI status updates and alarm notifications must occur within 2 seconds of an event.
3.  **Reliability:** The system must function continuously without needing a reset due to RLCS error for at least 30 consecutive days.
4.  **Security:** User passwords and device rules must be stored and processed in encrypted format using the MD5 algorithm.
5.  **Maintainability:** The system must support remote administration and allow for future roadway changes (e.g., adding devices) without programming effort.
6.  **Integrity:** A one-way hash function must verify the integrity of software and data in field controllers daily.

## Milestones and External Dependencies
1.  Deployment and parallel operation with the existing system during field testing.
2.  Successful completion of a full system test while the facility is closed to traffic.
3.  Deployment of the Fiber Optic Network along the I-15 corridor to support RLCS communications.
4.  Selection and provisioning of new intelligent field controllers (e.g., 2070 ATC).
5.  Finalization of the software architecture design by the contractor before the high-level design phase.

## Risks and Mitigation Strategies
1.  **Risk:** Catrophic wrong-way traffic if entrances in opposite directions are open simultaneously.
    *   **Mitigation:** Implement multi-layered safety screening of all commands against rules stored in non-volatile memory.
2.  **Risk:** System failure due to hardware or communication link outage.
    *   **Mitigation:** Design redundant, degraded modes of operation with alternate control points (e.g., FCU, DCU, manual override).
3.  **Risk:** Unauthorized access or malicious control of field devices.
    *   **Mitigation:** Employ secure logins, encrypted passwords, command-level security, and one-way data export to external systems.
4.  **Risk:** Software corruption in field controllers.
    *   **Mitigation:** Use hash-based integrity verification (MD5) of non-volatile memory contents daily and on command.
5.  **Risk:** Device sensor failure halting critical opening/closing sequences.
    *   **Mitigation:** Allow authorized operators to override device status temporarily to complete sequences after manual verification.
