# Balanced Summary: NLM Digital Repository Requirements

## Goals and Scope
The NLM Digital Repository aims to acquire, organize, preserve, and provide long-term access to NLM's digital biomedical collections, including both digitized and born-digital materials. Its scope encompasses collection materials under Library Operations' responsibility, utilizing the OAIS reference model as a framework, while excluding non-collection resources like research databases.

## Stakeholders and User Stories
*   **General Public:** End-users requiring access to repository materials, subject to licensing and copyright restrictions.
*   **NIH Staff:** Internal users, including NLM staff, needing repository access for research and reference purposes.
*   **NLM Staff (Metadata):** Personnel responsible for creating, reviewing, and editing descriptive metadata for objects in the repository.
*   **NLM Staff (Object Maintenance):** Personnel authorized to perform technical actions on digital objects, such as quality checks and format migrations.
*   **NLM System Administrators:** Personnel with ultimate system rights for management, development, and user access assignment.
*   **Content Producers/Donors:** External entities who submit digital materials to the repository under negotiated agreements.

**User Stories:**
1.  As a **General Public user**, I want to search and view repository materials online so that I can access biomedical information.
2.  As an **NIH Staff user**, I want to access licensed or embargoed materials so that I can conduct research.
3.  As **NLM Staff (Metadata)**, I want to add and edit descriptive metadata so that objects are discoverable and well-documented.
4.  As **NLM Staff (Object Maintenance)**, I want to perform quality assurance on submitted files so that only valid content enters the archive.
5.  As a **Content Producer**, I want to submit digital materials via FTP or physical media so that my content is preserved by NLM.
6.  As a **System Administrator**, I want to manage user access permissions so that security and policy restrictions are enforced.

## Key Processes
1.  **Ingest (Trigger: Submission from Producer):** Receives Submission Information Packages (SIPs), performs quality assurance, and generates Archival Information Packages (AIPs).
2.  **Archival Storage (Trigger: AIP from Ingest):** Stores AIPs, manages storage hierarchy, performs media refreshment and error checking.
3.  **Data Management (Trigger: Query or Update Request):** Administers the database containing descriptive and administrative metadata, performs queries, and generates reports.
4.  **Access (Trigger: User Request):** Coordinates user activities, generates Dissemination Information Packages (DIPs), and delivers content to users based on access rights.
5.  **Administration (Trigger: Operational Need):** Negotiates submission agreements, manages system configuration, and establishes repository policies and standards.
6.  **Preservation Planning (Trigger: Environmental Change):** Monitors technology and the designated user community to develop preservation strategies and migration plans.
7.  **Archival Information Update (Trigger: Change Request):** Updates or removes AIPs from the repository as governed by policy.

## Domain Data Elements
*   **Archival Information Package (AIP)** - *Primary Key:* NLM Unique ID; *Key Fields:* Content Data, Preservation Description Info (PDI), Packaging Info, Descriptive Info.
*   **Submission Information Package (SIP)** - *Primary Key:* Source Identifier; *Key Fields:* Content Data, Submission Agreement ID, Producer Info, Preliminary Metadata.
*   **Dissemination Information Package (DIP)** - *Primary Key:* Derived from AIP ID; *Key Fields:* Content Data (derivative), Relevant Metadata, User Access Info.
*   **Descriptive Metadata Record** - *Primary Key:* Linked to AIP ID; *Key Fields:* Title, Author, Subject (MeSH/Keyword), Date, Resource Type.
*   **Submission Agreement** - *Primary Key:* Agreement ID; *Key Fields:* Producer/Donor ID, Content Specifications, Format Standards, Transfer Schedule.
*   **User Account** - *Primary Key:* User ID; *Key Fields:* Affiliation (Public/NIH/NLM), Access Level, Authentication Credentials.

## Non-functional Requirements
1.  The system must conform to HHS/NIH security standards and policies.
2.  The repository must not be a "dark archive"; objects must be accessible, albeit with potential restrictions.
3.  The system must support multiple languages and non-Roman scripts for metadata and objects.
4.  Audit trails must be kept for all significant actions within the system.
5.  Automation should be maximized for metadata extraction and quality assurance processes.
6.  The system architecture must minimize duplicate data entry of metadata.

## Milestones and External Dependencies
1.  Evaluation and testing of commercial and open-source repository software options.
2.  Development of policies for migration strategies, ingest criteria, and format support.
3.  Integration with NLM's Integrated Library System (ILS) for bibliographic data.
4.  Compatibility with the NIH off-site backup facility (NCCS) for disaster recovery.
5.  Review and potential expansion of NLM's metadata schemes and DTDs (e.g., adoption of TEI).

## Risks and Mitigation Strategies
1.  **Risk:** Obsolescence of digital formats and technologies. **Mitigation:** Implement active preservation planning and monitoring to develop timely migration strategies.
2.  **Risk:** Insufficient staff resources for system implementation and management. **Mitigation:** Secure dedicated funding and staffing as part of the project plan.
3.  **Risk:** Complex copyright and licensing terms restricting access. **Mitigation:** Develop a robust, granular rights management system and negotiate clear submission agreements.
4.  **Risk:** Ingest of materials in non-standard or obsolete formats. **Mitigation:** Define acceptance policies for exceptions and develop procedures for handling special cases.
5.  **Risk:** System failure or data corruption. **Mitigation:** Implement comprehensive error checking, disaster recovery procedures, and off-site backups.

## Undecided Issues
1.  Final selection of repository software (commercial vs. open-source).
2.  Specific technical metadata requirements for all supported file formats.
3.  Detailed workflows for ingest preparation and quality assurance across different material types.
4.  The definitive set of metadata schemas to be used and their mapping rules.
5.  Policies governing the removal of objects with a "Permanent" rating.
6.  The extent and implementation method for federated searching across multiple NLM repositories.
