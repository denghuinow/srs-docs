# Balanced Summary: VII Data Use Analysis and Processing (DUAP) System

## Goals and Scope
The DUAP system is a research prototype designed to evaluate the utility of Vehicle Infrastructure Integration (VII) data for enhancing transportation safety, mobility, and asset management in Michigan. It will collect, consolidate, process, and disseminate VII probe vehicle data integrated with other traffic, weather, and roadway information sources. The scope focuses on demonstrating data transformation and management capabilities to support operational decisions by transportation agencies.

## Stakeholders and User Stories
*   **Transportation Agency (TA) Operators:** Local, regional, and state personnel who minimize incident impacts on traffic flow.
*   **TA Maintainers:** Employees who maintain roadways and bridges and respond to incidents.
*   **TA Asset Managers:** Personnel who analyze data to determine cost-effective annual programs and projects.
*   **System Administrators:** Staff responsible for administering systems to make collected data available.
*   **Travelers:** Roadway users who obtain trip information for route planning.
*   **Emergency Services:** Trained personnel who respond to roadway incidents.
*   **Researchers/University Personnel:** Analysts who study collected data for transportation agencies.
*   **Automobile Manufacturers (OEMs):** Providers of vehicle equipment and communication systems for VII data.
*   **VII Network Operating Entity:** Entity responsible for operating and maintaining the VII data infrastructure.

**User Stories:**
1.  As a **TA Operator**, I want to receive real-time incident alerts so that I can quickly assess and respond to traffic disruptions.
2.  As a **TA Maintainer**, I want to receive pothole location and severity data so that I can prioritize roadway repair tasks.
3.  As a **Traveler**, I want to access current travel time and congestion information via a web browser so that I can plan my route effectively.
4.  As a **System Administrator**, I want to add and configure new data input services so that the system can integrate additional data sources.
5.  As a **Researcher**, I want to access archived, geo-referenced probe data so that I can analyze long-term traffic patterns.
6.  As an **Emergency Service**, I want to receive accurate incident location data so that I can navigate to the scene efficiently.

## Key Processes
1.  **Data Collection (Trigger:** Continuous data streams): Input Services collect probe, traffic, weather, and road condition data from various external sources and interfaces.
2.  **Short-Term Caching:** Dynamic Data Services cache incoming raw and derived data with source, location, and timestamp for one week to support immediate processing.
3.  **Data Processing:** Computational Services apply algorithms to cached data to derive new information (e.g., speed, incidents, queue length, pothole location).
4.  **Long-Term Storage:** Persistent Data Services archive cached data and store system configuration and geographic reference data.
5.  **Information Packaging:** Output Services subscribe to processed data and format it for external systems (e.g., in SAE J2354 XML) or for internal presentation.
6.  **Information Presentation (Trigger:** User request): Presentation Services provide web-based browser interfaces for users to view and query traffic, incident, weather, and asset condition information.
7.  **System Administration:** Administrative Services allow configuration of other services, management of user access, and logging of system operations.

## Domain Data Elements
*   **Probe Vehicle Data (Primary Key:** Probe Segment Number + Timestamp): Time, Latitude/Longitude, Speed, Heading, Vehicle Sensor Statuses (e.g., wiper, brake, light).
*   **Traffic Condition Data (Primary Key:** Unique ID): Location, Update Time, Average Speed, Travel Time, Link Status, Level of Service.
*   **Weather Data (Primary Key:** Unique ID): Location, Update Time, Air Temperature, Precipitation, Visibility, Pavement Surface Temperature.
*   **Incident/Event Data (Primary Key:** Unique ID): Location, Start Time, Event Type, Severity, Status, Lanes Affected.
*   **Road Condition Data (Primary Key:** Data Source + Location + Timestamp): Surface Status, Ice Thickness, Pothole Location, Pavement Condition.
*   **System Configuration Data (Primary Key:** Configuration ID): Service Parameters, User Access Rights, Data Source Endpoints.

## Non-Functional Requirements
1.  The system shall conform to IT standards established by the Michigan Department of Information Technology (MDIT).
2.  The system shall be capable of adding new data sources, computational algorithms, and output formats.
3.  The system shall restrict access to authorized users and keep records of user access.
4.  The system shall log data transactions for all major services (Input, Administrative, Dynamic Data, etc.).
5.  Data presented must be "near real-time," with applications evaluating suitability based on source and timestamps.
6.  Presentation services shall support standard web browsers (e.g., IE 6.0+, Firefox 2.0+) capable of HTML 4.01, JavaScript, and XML.

## Milestones and External Dependencies
1.  Availability of VII Proof of Concept (POC) Probe Data Service and its X-031 interface.
2.  Establishment of data sharing agreements with third-party data providers (e.g., Traffic.com, transit agencies).
3.  Completion and availability of the MDOT Road Weather Information System (RWIS).
4.  Development and finalization of specific interface formats for various data sources (e.g., Chrysler telematics, SEMSIM).
5.  Resolution of data privacy and ownership policies for commingled VII and third-party data.

## Risks and Mitigation Strategies
1.  **Risk:** Data latency and quality issues from vehicle sensors and network transmission may affect application usefulness.
    *   **Mitigation:** Design applications to evaluate data based on source and quality flags, recognizing VII data as "near real-time."
2.  **Risk:** Data volume and utility are highly dependent on the penetration rate of VII-equipped vehicles and roadside equipment.
    *   **Mitigation:** Control factors during the evaluation phase; for operational rollout, focus on strategic RSE deployment.
3.  **Risk:** Privacy concerns may arise from potential identifiability of vehicles when VII penetration is low.
    *   **Mitigation:** Establish and adhere to operational data anonymization policies, especially during the transition period.
4.  **Risk:** Limitations on use or redistribution of third-party data could hamper DUAP's functionality.
    *   **Mitigation:** Consider data use restrictions in service agreements with third-party providers.
5.  **Risk:** The research-oriented nature of the project may lead to the discovery of new, unanticipated computational needs.
    *   **Mitigation:** Design a flexible, service-oriented architecture that allows for the addition of new Computational Services.

## Undecided Issues
1.  Specific interface formats for many data sources (e.g., Chrysler telematics, SEMSIM, various transit agencies, traffic management centers).
2.  The type and format of Origin/Destination (O/D) data to be collected.
3.  Implementation details for user authentication (e.g., username/password mechanism).
4.  Final set of computational algorithms beyond the initially identified list (e.g., for asset management).
5.  Specific output formats for asset condition data and alerts.
6.  Prioritization and timeline for integrating data from deferred sources (e.g., The Rapid Transit, DDOT, WMTMS).
