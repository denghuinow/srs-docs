# Balanced Summary: X-38 Fault Tolerant System Services (FTSS)

## Goals and Scope
The FTSS software provides fault-tolerant system services for the X-38 Crew Return Vehicle's quad-redundant Flight Critical Computer (FCC). It acts as an intermediary between NASA's application code and the underlying hardware/operating system, ensuring reliable, synchronized operation across redundant processors. The system must support real-time scheduling, communication, fault detection, and recovery to maintain mission-critical functions.

## Stakeholders and User Stories
*   **NASA (Johnson Space Center):** The customer and end-user, responsible for mission success and defining system requirements.
*   **Charles Stark Draper Laboratory:** The developer and integrator of the FTSS software and FTPP hardware architecture.
*   **Flight Software Application Developers:** Engineers who write the mission-specific application code that runs on top of FTSS.
*   **System Test and Integration Engineers:** Personnel who verify the combined FTSS, hardware, and application software.
*   **Flight Operations:** Personnel who monitor and command the vehicle during mission execution.

**User Stories:**
1.  As a **Flight Software Developer**, I want a reliable API for task scheduling and inter-process communication so that my application can execute predictably and exchange data safely in a fault-tolerant environment.
2.  As a **System Integrator**, I want the FTSS to perform comprehensive built-in tests at startup and continuously during operation so that hardware faults are detected and isolated promptly.
3.  As a **Flight Operations Controller**, I want the system to autonomously manage redundancy and recover from processor or network element failures so that mission capability is maintained without manual intervention.
4.  As an **Application Developer**, I want the system to provide congruent Mission and Separation Elapsed Time across all processors so that my application has a consistent time reference for control logic.
5.  As a **Test Engineer**, I want detailed fault and status information to be available via telemetry so that I can monitor system health and diagnose issues during testing and flight.
6.  As a **System Architect**, I want the FTSS to enforce memory segregation (congruent vs. non-congruent) so that channel recovery and memory realignment can be performed correctly.

## Key Processes
1.  **System Initialization (Trigger: Power-on or CPU reset):** Executes hardware self-tests (IBIT), synchronizes the FCP virtual group, and initializes the application.
2.  **Scheduling Execution (Trigger: 50 Hz timer interrupt):** Invokes the scheduler to execute cyclic application tasks within defined rate groups (50 Hz, 10 Hz, 1 Hz) and vehicle modes.
3.  **Synchronous Message Passing (Trigger: Rate group frame boundaries):** Queues and transmits application messages between virtual groups using the Network Element, ensuring congruent data delivery.
4.  **Continuous Fault Detection (Trigger: 50 Hz rate group):** Performs presence tests to verify processor synchronization and monitors system health (CBIT).
5.  **Fault Recovery (Trigger: Fault detection by FDI):** Reconfigures the system by masking failed components (FCP, NE, ICP) and attempts reintegration if alignment is permitted.
6.  **Memory Scrubbing (Trigger: Cyclic, background task):** Periodically reads all used RAM to trigger Error Detection and Correction (EDAC) and reports errors.
7.  **Telemetry/Command Handling (Trigger: 10 Hz rate group):** Transfers application telemetry data to the MPCC/CTC and reads ground commands for delivery to the application.

## Domain Data Elements
*   **Virtual Group (VG):** (Primary Key: VG_ID) Fields: Redundancy Level, Member Processors (list), NE Port Mapping, Status.
*   **Task:** (Primary Key: Task_ID) Fields: Function Pointer, Priority, Rate Group Association, State (blocked/ready).
*   **Message Queue Socket:** (Primary Key: Socket_ID) Fields: Sender VG_ID, Receiver VG_ID, Max Message Size, Queue Buffer, Message Count.
*   **Pipe Socket:** (Primary Key: Socket_ID) Fields: Sender VG_ID, Receiver VG_ID(s), Broadcast Flag, Buffer.
*   **Fault Log:** (Primary Key: Fault_ID/Timestamp) Fields: Fault Type (FCP, NE, ICP, Link), Channel Identifier, Diagnosis, Recovery Action Taken.
*   **System Time:** (Primary Key: N/A - singleton) Fields: Mission Elapsed Time (MET), Separation Elapsed Time (SEP), Minor Frame Count, Vehicle Mode.

## Non-Functional Requirements
1.  **Performance:** System initialization must complete within 1.5 minutes from power-on. The scheduler and time services overhead must take ≤1 ms per 50 Hz minor frame.
2.  **Fault Tolerance:** The system must be two-fault tolerant for any two non-simultaneous hardware faults and must mask a failed component within 60 ms of fault manifestation.
3.  **Determinism:** The behavior of synchronous tasks executed by the scheduler must be deterministic. All FCPs must remain synchronized barring a hardware fault.
4.  **Resource Constraints:** FTSS and VxWorks together shall use ≤3 MB of ROM and ≤9 MB of DRAM. Only 4 MB of DRAM is subject to realignment.
5.  **Accuracy:** Mission Elapsed Time (MET) and Separation Elapsed Time (SEP) must have a drift rate ≤50 PPM.
6.  **Interoperability:** FTSS must provide a defined Application Programming Interface (API) for the application software.

## Milestones and External Dependencies
1.  Delivery of FTSS software engineering releases for integration with NASA application software.
2.  Availability of qualified Radstone PowerPC 604R hardware and VME boards.
3.  Completion of Network Element (NE) hardware development and certification.
4.  Finalization of the NASA application software requirements and design.
5.  Successful completion of system-level certification testing in the integrated FCC.

## Risks and Mitigation Strategies
1.  **Risk:** Undetected common-mode software errors in FTSS could cause simultaneous failure across redundant channels.
    *   **Mitigation:** Rigorous independent testing and verification of FTSS; use of defensive programming and memory protection schemes.
2.  **Risk:** Recovery and realignment of a failed channel may not complete within the required 1.5-minute timeframe under high system load.
    *   **Mitigation:** Performance testing of realignment algorithms with worst-case data loads; optimization of memory copy routines.
3.  **Risk:** A "babbling" Network Element or ICP could disrupt fault-tolerant communications.
    *   **Mitigation:** FTSS must detect a babbling component within 20 ms and mask it within 40 ms, as per requirements.
4.  **Risk:** Asymmetric I/O operations from the application could cause FCPs to desynchronize.
    *   **Mitigation:** FTSS API restricts unsafe I/O calls; application guidelines and code reviews enforce symmetric operations.
5.  **Risk:** Single Event Upsets (SEUs) in space could corrupt memory or processor state.
    *   **Mitigation:** Use of EDAC RAM, periodic RAM scrubbing, and watchdog timers to detect and correct errors.
