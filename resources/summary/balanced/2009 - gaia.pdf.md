# Balanced Summary: GOG Software Requirements Specification

## Goals and Scope
GOG (Gaia Object Generator) is a software simulator designed to produce catalog data, auxiliary data, and intermediate main database data (including statistically equivalent final mission data) for all Gaia instruments without relying on GASS telemetry, GIBIS, or the main ESAC database. It uses error models to rapidly simulate large datasets, with realism dependent on the available models, and is modular and configurable via an input file. The scope of this document is to provide all CU members with an understanding of the software requirements, restrictions, and assumptions for designing and building GOG.

## Stakeholders and User Stories
*   **CU2 (Coordination Unit 2):** Responsible for the design and development of GOG.
*   **DPAC (Data Processing and Analysis Consortium) Members:** Require simulated data for algorithm development and testing.
*   **GOG Developers:** Design, implement, and maintain the GOG software.
*   **GOG Users (Scientists/Engineers):** Configure and execute simulations to generate required data products.
*   **Quality Assurance (QA):** Verify that GOG meets its specified requirements and standards.

**User Stories:**
1.  As a **DPAC member**, I want to generate simulated catalog and main database data so that I can develop and test data processing algorithms without needing full system telemetry.
2.  As a **GOG user**, I want to specify a sky region or provide an input object catalog so that GOG can generate data for the sources I am interested in.
3.  As a **GOG user**, I want to select which noise effects (instrumental and reduction) to include in the simulation so that I can control the realism and characteristics of the output data.
4.  As a **GOG developer**, I want the software to be modular and configurable via an input file so that it can evolve with the availability of new error models and satisfy diverse user needs.
5.  As a **QA engineer**, I want GOG to produce identical results for identical input configurations so that the simulation is deterministic and verifiable.
6.  As a **system operator**, I want GOG to run from a command line and be deployable on cluster/grid environments so that I can execute large-scale simulations efficiently.

## Key Processes
1.  **Initialization (Trigger: Execution start):** Load configuration from an XML file, including source generation mode (Universe Model or user catalog), instrument models, noise models, and output specifications.
2.  **Source Input:** Read source information either from the GaiaSimu Universe Model library or from a user-provided input object catalog.
3.  **Epoch Data Calculation (Trigger: Request for epoch data):** For each source transit, compute epoch parameters including astrometry (field angles, times), photometry (magnitudes), radial velocity, physical parameters, and flags, applying selected noise models.
4.  **Combined Data Calculation (Trigger: Request for combined data):** For each source, compute combined parameters by statistically combining data from all transits, including astrometric solutions (parallax, proper motion), mean photometry, mean radial velocity, final flags, and mean physical parameters.
5.  **Spectrum Simulation (Trigger: Request for spectrum data):** Simulate RP/BP and RVS spectra, applying relevant noise models such as flux noise, CCD combination noise, and wavelength calibration errors.
6.  **Output Generation:** Format and write the simulation results according to the defined output specifications, adhering to the Universe Model ICD for catalog data and the Main Database (MDB) data model for other outputs.
7.  **Execution Completion:** Finalize all file writes and terminate the process.

## Domain Data Elements
*   **Source:** `source_id` (Primary Key), celestial coordinates, intrinsic astrophysical parameters, input spectrum.
*   **Transit (Epoch Data):** `transit_id`, `source_id`, observation time, field angles, photometric measurements, radial velocity measurement, epoch flags.
*   **Combined Solution:** `source_id`, mean epoch, astrometric parameters (parallax, proper motions), covariance matrix, mean photometry, mean radial velocity, final physical parameters, combined flags.
*   **Spectrum (Epoch/Combined):** `spectrum_id`, `source_id`, wavelength array, flux array, flux error array, instrument band (RP/BP/RVS).
*   **Configuration:** `config_id`, source generation mode, selected noise models, output parameters, processing options.
*   **Noise Model:** `model_id`, noise type (instrumental/reduction), applicable parameters, error distributions.

## Non-Functional Requirements
1.  **Performance:** Must process one complete source (including all transits) within 2 CPU seconds.
2.  **Portability:** Must run on Linux, UNIX, and Mac computers; results must be platform-independent.
3.  **Deployability:** Must be a standalone Java application invokable from a command line and deployable as a JAR file.
4.  **Scalability:** Must be able to run in single-threaded mode and be suitable for cluster or grid environments to handle large datasets (up to a significant fraction of the final catalog).
5.  **Determinism:** Must produce identical results for identical input configuration parameters.
6.  **Interoperability:** Output formats must comply with the Universe Model ICD and the Main Database (MDB) data model.

## Milestones and External Dependencies
1.  **Availability of the Main Database Interface Control Document (ICD):** GOG output format is dependent on this specification.
2.  **Availability of detailed error models:** Realism of simulations depends on models for instrumental and calibration errors, which will be developed gradually based on GIBIS studies and CU inputs.
3.  **Integration with Gaia Simulator project:** GOG must use the GaiaSimu and Gaia Tools libraries.
4.  **Evolution of the Universe Model:** Source generation from the Universe Model depends on its continued development and ICD.
5.  **Validation against other simulators (e.g., GIBIS):** Required to ensure consistency and accuracy of GOG's rapid simulation approach.

## Risks and Mitigation Strategies
1.  **Risk:** The Main Database contents and ICD are not fully defined, leading to potential rework.
    *   **Mitigation:** Base initial versions on current specifications and design for modularity to accommodate changes.
2.  **Risk:** Error models are incomplete or unavailable, limiting simulation realism.
    *   **Mitigation:** Implement a gradual integration plan, make noise addition user-selectable, and use placeholder models initially.
3.  **Risk:** GOG's source-by-source processing may not accurately model overlapping effects (crowding).
    *   **Mitigation:** Consider a future version that works per sky region to model overlapping effects, while clearly stating the current limitation.
4.  **Risk:** Performance targets (2 seconds per source) may not be met for complex simulations.
    *   **Mitigation:** Optimize critical algorithms, leverage efficient libraries, and profile code regularly.
5.  **Risk:** Inability to handle the required volume of data for large-scale simulations.
    *   **Mitigation:** Design for cluster/grid execution and optimize I/O and memory management.

## Undecided Issues
1.  The precise implementation timeline for integrating all required error models.
2.  The feasibility and schedule for developing a version of GOG that models overlapping effects per sky region (TBC).
3.  Final details on how calibration errors will be selectively added by users to simulate specific processing steps.
4.  Specifics of the "reduction noise" models and their dependencies on calibration algorithm development.
5.  Handling of edge cases in transit calculation and combined parameter derivation for sources from user catalogs without full positional history.
6.  The exact mechanism for user specification of noise values when noise effects are enabled.
