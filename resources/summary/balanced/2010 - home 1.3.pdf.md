# Balanced Summary: DigitalHome Software Requirements Specification

## Goals and Scope
The DigitalHome (DH) system is a prototype smart home management system designed to allow residents to monitor and control environmental, security, and appliance functions via a web interface. Its scope is limited to managing temperature, humidity, security, and appliance power in a simulated home environment to support future business decisions for HomeOwner Inc.

## Stakeholders and User Stories
*   **General User:** A home resident who uses the DH system to monitor and control their home environment via a web interface.
*   **Master User:** A designated user (often a resident) with additional privileges to change system configuration and user accounts.
*   **DH Technician:** A trained professional responsible for installing, configuring, and maintaining the DH system.
*   **HomeOwner Inc. Management:** Decision-makers who will evaluate the prototype for potential commercial development.
*   **Development Team:** The engineers building the prototype under specified constraints and timelines.

**User Stories:**
1.  As a **General User**, I want to view the current temperature and humidity in my home rooms so that I can assess the environment.
2.  As a **General User**, I want to schedule my thermostat settings for different times of the week so that I can optimize comfort and energy use.
3.  As a **General User**, I want to remotely turn lights or appliances on/off so that I can manage my home while away.
4.  As a **Master User**, I want to add new user accounts to the system so that I can grant access to other household members.
5.  As a **DH Technician**, I want to configure the initial system parameters and backup schedule so that the system is set up correctly for the homeowner.
6.  As a **General User**, I want to receive a monthly report of temperature extremes and security breaches so that I can review home activity.

## Key Processes
1.  **User Authentication:** Triggered by user access attempt; verifies account credentials via the web server.
2.  **Environmental Monitoring:** Triggered periodically (every 2 sec); reads sensor data (temp, humidity) via wireless gateway and updates displays.
3.  **Device Control:** Triggered by user command; sends set-point or on/off instructions to controllers (thermostats, power switches).
4.  **Security Breach Detection:** Triggered by a contact sensor opening; activates light and sound alarms.
5.  **Plan Execution:** Triggered by scheduled time; applies preset environmental and appliance settings from the user's monthly plan.
6.  **Data Backup:** Triggered daily at a configured time; backs up system configuration, plans, and usage data.
7.  **Report Generation:** Triggered by user request; compiles and displays a monthly summary report of historical data.

## Domain Data Elements
*   **User Account:** (PK: UserID) Username, Password, Role (General/Master/Technician), Contact Info, Creation Date.
*   **Device:** (PK: DeviceID) Type (Thermostat/Humidistat/Sensor/Switch), Location, Current State/Value, Configuration Parameters.
*   **Environmental Plan:** (PK: PlanID) UserID, Month/Year, Daily Time Periods, Temperature Settings, Humidity Settings, Appliance Schedules.
*   **Sensor Reading:** (PK: ReadingID) DeviceID, Timestamp, Value (Temperature/Humidity/State).
*   **Security Event:** (PK: EventID) ContactSensorID, Timestamp, Event Type (Breach/Reset), Alarm Status.
*   **System Backup:** (PK: BackupID) Timestamp, Backup Type (Full/Incremental), Data Scope, Storage Location.

## Non-Functional Requirements
1.  **Performance:** Sensor displays must update at least every 2 seconds.
2.  **Reliability:** System must have no more than 1 failure per 10,000 hours of operation.
3.  **Security:** User authentication via account name/password and data encryption (e.g., Transport Layer Security) is required.
4.  **Maintainability:** Design must use abstraction and modularity to allow incorporation into a future commercial product.
5.  **Operational Range:** Wireless communication must be effective within a 1000-foot indoor range.
6.  **Recoverability:** System must restore from the most recent daily backup after a failure.

## Milestones and External Dependencies

2.  Architecture design completion by November 15, 2010.

## Risks and Mitigation Strategies
1.  **Risk:** Prototype completion may exceed the 12-month constraint.
    *   **Mitigation:** Adhere strictly to the phased schedule with defined cycle completions.
2.  **Risk:** Simulated environment may not accurately reflect real-world hardware interactions.
    *   **Mitigation:** Ensure the simulation adheres to realistic physical properties and constraints.
3.  **Risk:** System reliability target (1 failure/10k hours) may not be met in the prototype.
    *   **Mitigation:** Implement robust exception handling and daily backup/recovery mechanisms.
4.  **Risk:** Development costs may exceed minimization goals due to technology choices.
    *   **Mitigation:** Conduct price comparisons for all system elements as part of the final report.
5.  **Risk:** Security of user data and system access could be compromised.
    *   **Mitigation:** Employ recognized encryption and authentication technologies from the start.

## Undecided Issues
1.  Specific hardware brands/models for sensors, controllers, and gateway devices.
2.  Detailed user interface design and layout for the web portal.
3.  Exact algorithms for calculating daily averages and extremes in monthly reports.
4.  The specific "recognized reliable and effective security technology" to be implemented.
5.  Procedures for handling concurrent manual overrides and scheduled plan conflicts.
6.  Detailed format and storage mechanism for the daily system backups.
