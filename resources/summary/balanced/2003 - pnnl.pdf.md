# Balanced Summary: Automated Diagnostics Software Requirements Specification

## Goals and Scope
The software automates fault detection and diagnostics for HVAC subsystems (chillers, cooling towers, boilers) using pattern-recognition algorithms derived from expert practices. It replaces manual visual analysis with automated processing of sensed and fixed data, providing building operators, service technicians, and energy service providers with fault identification, causes, and corrective actions. The initial version focuses on chillers and cooling towers, with design allowing expansion to additional subsystems.

## Stakeholders and User Stories
*   **Building Operator:** Monitors HVAC units from a central control room to ensure proper operation and identify faults.
*   **Service Technician:** Uses the tool on-site during repairs or off-site between visits to diagnose issues and verify fixes.
*   **Energy Service Provider:** Remotely monitors multiple units across different buildings to detect inefficiencies and dispatch personnel.
*   **Building Operator Supervisor:** Guides work assignments and prioritization based on diagnostic results.
*   **Administrator User:** Configures the system, modifies fixed data, and controls diagnostic processing.
*   **General User:** Views current and historical diagnostic results but cannot modify system settings.

**User Stories:**
1.  As a **Building Operator**, I want to **view a simple, graphical summary of current faults** so that **I can quickly assess the status of all equipment under my responsibility**.
2.  As a **Service Technician**, I want to **input sensed data from a file collected by a data logger** so that **I can diagnose a unit without a live connection**.
3.  As an **Energy Service Provider**, I want to **review historical diagnostic results over a configurable time period** so that **I can identify recurring or long-term performance issues**.
4.  As a **Building Operator Supervisor**, I want to **see which buildings or subsystems have confirmed faults** so that **I can prioritize maintenance tasks for my team**.
5.  As an **Administrator**, I want to **adjust the sensitivity thresholds for fault detection algorithms** so that **I can reduce false alarms or increase detection probability for specific conditions**.
6.  As a **General User**, I want to **print a detailed report of a specific fault, including its description and recommended fix** so that **I can provide it to a technician or keep a record**.

## Key Processes
1.  **Data Acquisition & Preprocessing:** (Trigger: Real-time data stream or batch file input) Acquires sensed data (temperatures, currents) and fixed data (specifications, setpoints), validates ranges, converts units, and flags missing or erroneous data.
2.  **Equipment Status Determination:** (Trigger: New preprocessed data) Calculates "On"/"Off" status for components (e.g., compressor, pumps, fans) by comparing measured current/power against configurable thresholds.
3.  **Diagnostic Algorithm Execution:** (Trigger: Updated equipment status and data) Runs specific algorithms (e.g., for chiller schedule, chilled water temperature control, cooling tower approach) to detect predefined fault conditions.
4.  **Fault Logging & Storage:** (Trigger: Fault detection) Saves diagnostic results with timestamp, unit identity, and fault details to permanent storage for historical review.
5.  **User Interface Navigation:** (Trigger: User interaction) Presents a hierarchical window interface (Building -> Subsystem -> Condition -> Detail) allowing users to browse current and historical diagnostics.
6.  **System Configuration:** (Trigger: Administrator action) Allows privileged users to define monitored buildings/subsystems, modify fixed data, set sensitivity parameters, and manage user authentication.
7.  **Diagnostic Control:** (Trigger: Administrator command) Starts or stops the continuous diagnostic processing engine.

## Domain Data Elements
*   **Building:** (Primary Key: Building_ID) Fields: Name, Location, Contact_Info.
*   **HVAC Subsystem (e.g., Chiller):** (Primary Key: Subsystem_ID) Fields: Building_ID (FK), Type, Model, Specifications, Schedule.
*   **Sensed Data Point:** (Primary Key: Timestamp, Sensor_ID) Fields: Value, Unit, Validation_Status, Equipment_Status (On/Off).
*   **Fixed Data Parameter:** (Primary Key: Parameter_ID, Subsystem_ID) Fields: Name (e.g., HWST_Setpoint), Value, Unit, Date_Entered.
*   **Diagnostic Result:** (Primary Key: Result_ID) Fields: Timestamp, Subsystem_ID (FK), Fault_Category, Severity (OK/Caution/Not OK), Description.
*   **User:** (Primary Key: User_ID) Fields: Name, Role (General/Admin), Authentication_Credentials.

## Non-Functional Requirements
1.  **Usability:** The interface must be navigable by users with varying computer expertise but a good understanding of HVAC systems.
2.  **Supportability:** Significant software errors must be logged with timestamp, module/function name, and description to aid maintenance.
3.  **Extensibility:** The software architecture must support the addition of new diagnostic algorithms for other HVAC subsystems.
4.  **Data Integrity:** Sensed data must be stored with precision (three significant figures) and missing data clearly indicated.
5.  **Platform Constraint:** The software must be compatible with Microsoft Windows operating systems.
6.  **Security:** User privileges must be enforced, requiring authentication for administrative functions like configuration and starting/stopping diagnostics.

## Milestones and External Dependencies
1.  Delivery of initial software version with chiller and cooling tower diagnostics.
2.  Completion of boiler diagnostics algorithms (future expansion).
3.  Dependency on data acquisition hardware/software (e.g., AEC Micrologger) to provide sensed data in the specified format.
4.  Availability of accurate fixed data (equipment specifications, setpoints) from users for system configuration.
5.  Validation of diagnostic algorithms against expert manual analysis.

## Risks and Mitigation Strategies
1.  **Risk:** Inaccurate or missing fixed/setup data leads to false diagnostics.
    *   **Mitigation:** Implement data validation during configuration and allow administrator review/editing.
2.  **Risk:** Sensor failure or communication loss results in missing input data, halting diagnostics.
    *   **Mitigation:** Define rules for flagging missing data, notify users, and allow algorithms to skip processing only when critical inputs are absent.
3.  **Risk:** Diagnostic algorithms are too sensitive or not sensitive enough for all installations.
    *   **Mitigation:** Provide administrator-configurable sensitivity levels for key parameters.
4.  **Risk:** Users lack the required computer skills to operate the software effectively.
    *   **Mitigation:** Design a simple, guided user interface with clear navigation and minimal required input.
5.  **Risk:** Software cannot interface with the variety of data acquisition systems in use.
    *   **Mitigation:** Support a standard ASCII file input format for batch processing in addition to real-time interfaces.

## Undecided Issues
1.  Specific procedures for deriving certain benchmark values (e.g., Cooling Tower Approach Benchmark) automatically from performance data.
2.  Detailed diagnostic algorithms for chiller performance assessment (marked as a placeholder for future development).
3.  Full diagnostics for boiler hot-water pump operation when the pump is off but the boiler is on (a safety-related condition).
4.  Diagnostic procedures for ambient-temperature-based or other temperature-based boiler shutoff schedules.
5.  Optimal default values for configurable parameters (e.g., `CHWST Alarm Evaluation Interval`).
6.  The method for handling and diagnosing individual fan stages within a multi-fan cooling tower.
