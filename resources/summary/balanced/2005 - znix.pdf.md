# Balanced Summary: Project ZNIX

## Goals and Scope
Project ZNIX aims to refine traditional information management by providing an object-based, application-independent framework for retrieving and manipulating user information. The scope covers the high-level design of the ZNIX Framework, which centralizes and hierarchically organizes data from various sources, emphasizing information semantics over application mastery.

## Stakeholders and User Stories
*   **End User:** A home user, manager, executive, or researcher with basic IT skills who interacts with the system to manage personal information.
*   **Developer:** A third-party application developer who uses the public API to create ZNIX-aware applications.
*   **System Administrator:** Responsible for deploying and maintaining the framework on compatible hardware.

**User Stories:**
1.  As an **End User**, I want to view all my information (emails, contacts, documents) in a single, customizable hierarchy so that I can find and manage it logically.
2.  As an **End User**, I want the system to automatically capture and link information (e.g., link emails to contact entries) so that my data relationships are built with minimal effort.
3.  As an **End User**, I want to archive information to removable media without losing its reference in the system so that I can manage storage while preserving context.
4.  As a **Developer**, I want a simple, filesystem-like public API to create, query, and modify entities and relationships so that I can build applications that leverage the framework.
5.  As an **End User**, I want to use familiar applications (e.g., Outlook, Word) while their data is integrated into the framework via a proxy mechanism so that I don't have to change my workflow.
6.  As a **System Administrator**, I want the framework to run on modest hardware (e.g., 256MB RAM) so that it has broad compatibility and low resource overhead.

## Key Processes
1.  **Information Capture (Trigger:** User action or system event in a supported application): The framework intercepts or captures data from third-party applications like email clients and web browsers.
2.  **Entity/Associate Creation:** Captured data is classified and stored as either an independent Entity or a dependent Associate linked to an Entity.
3.  **Relationship Establishment:** Users can manually define or the system can automatically infer relationships (e.g., linking an email to a person) between data objects.
4.  **Hierarchical Browsing (Trigger:** User opens the ZNIX browser): Users navigate and manage their information through an Explorer-like interface that reflects the defined relationships.
5.  **Archiving (Trigger:** User request): Users can archive data subsets to removable media, leaving a placeholder in the central store to indicate the data's archived status.
6.  **API Access (Trigger:** Call from client application): Third-party applications use the public API to programmatically interact with the framework's data store.
7.  **Proxy Mediation:** The framework's proxy mechanism allows ZNIX-unaware applications to interact with managed information transparently.

## Domain Data Elements
*   **Entity**
    *   **Primary Key:** Unique Entity ID
    *   **Key Fields:** Name, Type/Category, Creation Date, Metadata
*   **Associate**
    *   **Primary Key:** Associate ID (dependent on related Entity IDs)
    *   **Key Fields:** Content/Data, Source Application, Link to Entity, Creation Date
*   **Relationship**
    *   **Primary Key:** Relationship ID
    *   **Key Fields:** Source Entity ID, Target Entity/Associate ID, Relationship Type, Strength/Weight
*   **Category**
    *   **Primary Key:** Category Name
    *   **Key Fields:** Description, Default Entity Types, Parent Category
*   **Archive Record**
    *   **Primary Key:** Archive ID
    *   **Key Fields:** Archived Entity/Associate ID, Storage Media ID, Archive Date, Location Pointer

## Non-Functional Requirements
1.  **Performance:** The framework shell must not use more than 40MB of RAM.
2.  **Reliability:** Mean Time Between Failures (MTBF) must exceed 3 months.
3.  **Usability:** GUIs must be intuitive for users familiar with Windows 2000/XP, requiring minimal training.
4.  **Supportability:** The project will be released as open-source (LGPL/GPL) and hosted on a community site for feedback.
5.  **Compatibility:** Must run on Intel Pentium III (or compatible) 1GHz PCs with 256MB RAM, targeting Windows 2000 Professional and Windows XP.
6.  **Security:** Must guard against malicious remote scripts and unintended user corruption of information.

## Milestones and External Dependencies
1.  Finalization of coding conventions documentation before implementation begins.
2.  Development of the proxy mechanism for key third-party applications (Outlook, IE, Word).
3.  Creation of the public API specification and accompanying Developer's Guide.
4.  Dependency on continued compatibility with specified versions of third-party software (Table 3.10.3-A).
5.  Launch of the project on an open-source distribution website.

## Risks and Mitigation Strategies
1.  **Risk:** Low adoption by third-party developers if the framework is not seen as a standard.
    *   **Mitigation:** Provide a robust proxy mechanism to ensure immediate utility with popular existing applications.
2.  **Risk:** Performance degradation with very large information stores on constrained hardware.
    *   **Mitigation:** Implement efficient data indexing and querying algorithms; emphasize the archiving feature.
3.  **Risk:** Security vulnerabilities introduced through integration with multiple external applications.
    *   **Mitigation:** Isolate the framework's core data store and implement strict input validation for the proxy layer.
4.  **Risk:** New releases of dependent third-party software (e.g., Windows, Office) break compatibility.
    *   **Mitigation:** Design modular interfaces to facilitate updates; assume compatibility only with specified versions per the SRS.
5.  **Risk:** User resistance due to complexity in defining information relationships.
    *   **Mitigation:** Focus on automated relationship creation (e.g., from emails) and provide an intuitive, graphical relationship manager.

## Undecided Issues
1.  Whether the hierarchy browser will be a standalone application or integrated directly into Windows Explorer.
2.  The specific set of default categories that must always be present (beyond "People" and "Email").
3.  The detailed design of the graphical user interface for creating relationships between documents and entities.
4.  The exact mechanism and format for storing archived data on removable media.
5.  The specific "wish-list" and feedback features for the open-source project website.
6.  Whether to mandate UTF-16 (ISO 10646-1) support in addition to UTF-8.
