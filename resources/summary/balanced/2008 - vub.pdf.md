# Balanced Summary: Publications Management System (PMS)

## Goals and Scope
The PMS is a web- and command-line-accessible system for managing a database of academic publications, including full texts in PDF/PostScript. It supports automatic extraction of bibliographic data from uploaded documents, manual correction, and user-defined author/institute aliases. The system enforces a hierarchical access control model based on user roles and network location.

## Stakeholders and User Stories
*   **Guest**: An anonymous user not connected to the VUB network, limited to login and registration functions.
*   **VUB-Network User**: A user recognized by IP address within the university network, allowed to search and download publications without logging in.
*   **Member**: A logged-in user with basic search and download privileges.
*   **Publisher**: A logged-in user who can upload, edit their own publications, and perform bulk imports.
*   **Moderator**: A privileged user who can manage publications and user levels within their assigned department/group.
*   **Administrator**: The super-user responsible for full system configuration, user/group management, and all publications.

**User Stories:**
1.  As a **Guest**, I want to register for an account so that I can gain access to the system's features.
2.  As a **VUB-Network User**, I want to search for publications by author or keyword so that I can find relevant research without needing an account.
3.  As a **Member**, I want to download the full text of a publication so that I can read it offline.
4.  As a **Publisher**, I want to upload a publication in BibTeX format so that the system can automatically populate its bibliographic details.
5.  As a **Moderator**, I want to edit the details of publications within my department so that I can ensure data accuracy and consistency.
6.  As an **Administrator**, I want to create and delete user groups so that I can manage departmental access and permissions.

## Key Processes
1.  **User Registration & Login** (Trigger: User accesses the web interface).
2.  **Publication Search** (Trigger: User submits a query via a search form).
3.  **Result Browsing & Detail Viewing** (Trigger: User selects a publication from search results).
4.  **Publication Download** (Trigger: User clicks a download button for a selected publication).
5.  **Publication Upload & Metadata Extraction** (Trigger: Publisher submits a document file).
6.  **User & Group Management** (Trigger: Administrator accesses the control panel).
7.  **System Configuration** (Trigger: Administrator edits settings via the configuration panel).

## Domain Data Elements
*   **User**: (PK: UserID) Username, Password (encrypted), Email, Role, Department.
*   **Publication**: (PK: PublicationID) Title, Abstract, Publication Date, Full Text File Path, Uploader ID.
*   **Author**: (PK: AuthorID) First Name, Last Name, Institute, Alias (for name normalization).
*   **Reference**: (PK: ReferenceID) Citation Text, Source Publication ID, Target Publication ID.
*   **User Group**: (PK: GroupID) Group Name, Description, Moderator ID.
*   **Institute**: (PK: InstituteID) Institute Name, Alias (for name normalization).

## Non-Functional Requirements
1.  **Reliability**: Developed using a spiral model with two iterations to minimize software faults.
2.  **Availability**: System must be accessible at all times, contingent on the Wilma server's uptime.
3.  **Security**: User passwords must be encrypted in transit and in storage; access control must strictly enforce user role privileges.
4.  **Maintainability**: Code must be modular, object-oriented, and documented using RDoc for ease of updates.
5.  **Portability**: Primary target is the Linux-based Wilma server, though design should allow for potential relocation.
6.  **Compliance**: Web interface must conform to W3C XHTML 1.0 Transitional standards.

## Milestones and External Dependencies
1.  Completion of the first iteration prototype with critical functions.
2.  Delivery of the second iteration with enhanced and sufficient functions.
3.  Dependency on the Wilma server's continuous availability and network connectivity.
4.  Dependency on users having a W3C XHTML-compliant web browser.
5.  Dependency on Ruby 1.8+ being installed on the server.

## Risks and Mitigation Strategies
1.  **Risk**: Incorrect automatic extraction of bibliographic data from uploaded files.
    *   **Mitigation**: Provide a straightforward manual correction interface for users.
2.  **Risk**: Database corruption or server hardware failure.
    *   **Mitigation**: Implement a regular database backup and restoration procedure.
3.  **Risk**: Security breach exposing user passwords or unauthorized data access.
    *   **Mitigation**: Enforce password encryption and strict, role-based access control checks.
4.  **Risk**: Insufficient performance under high user load.
    *   **Mitigation**: Design database to handle concurrent SQL requests efficiently (performance specifics TBD).
5.  **Risk**: Scope creep or timeline overrun during development.
    *   **Mitigation**: Adhere to the apportioned requirements (Critical, Sufficient, Optional) for the two planned iterations.
