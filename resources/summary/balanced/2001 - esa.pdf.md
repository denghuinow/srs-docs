# Balanced Summary: APAF Software Requirements Specification

## Goals and Scope
The APAF ground data system will process ASPERA-3 instrument telemetry and Mars Express orbit/attitude data into IDFS datasets for scientific analysis. It will acquire data from ESOC, provide web-based displays, archive data locally, and deliver validated datasets to the NASA Planetary Data System within six months of receipt. The system supports the ASPERA-3 science team during the Mars Express mission operations and data analysis phase.

## Stakeholders and User Stories
*   **IRF Principal Investigator (Prof. Rickard Lundin):** Oversees the scientific integrity and objectives of the ASPERA-3 experiment.
*   **IRF Project Manager (Herman Andersson):** Manages project execution and coordination for the Swedish Institute of Space Physics.
*   **SwRI Principal Investigator (Dr. J. David Winningham):** Provides scientific leadership and ensures requirements are met from Southwest Research Institute.
*   **SwRI Software Project Manager (Sandee Jeffers):** Manages the software development lifecycle and delivery of the APAF system.
*   **SwRI Software Team Member (Carrie Gonzalez):** Contributes to the development, review, and implementation of the APAF software.
*   **ASPERA-3 Co-Investigators (Co-I's):** Analyze the processed IDFS data to meet mission science goals.

**User Stories:**
1.  As a **System Operator**, I want to **automatically acquire telemetry data from ESOC daily** so that **processing can begin promptly**.
2.  As a **Scientist (Co-I)**, I want to **receive IDFS data sets within 24 hours of error-free telemetry acquisition** so that **I can perform timely scientific analysis**.
3.  As a **Data Archivist**, I want to **submit calibrated and validated ASPERA-3 data to the PDS within six months** so that **it is preserved for the broader scientific community**.
4.  As a **Public Outreach Officer**, I want to **provide web-based displays of the most current data** so that **the public can monitor the mission**.
5.  As a **Science Team Member**, I want to **access password-protected web displays for detailed data analysis** so that **I can collaborate on proprietary data before public release**.
6.  As a **System Maintainer**, I want the **system to have built-in error handling and local archives** so that **data integrity is maintained and re-processing is possible**.

## Key Processes
1.  **Trigger:** Daily receipt of new telemetry. Acquire ASPERA-3 and MEX OA telemetry data from ESOC via NISN.
2.  Process the raw telemetry into cleaned-up intermediate files if not provided by ESOC.
3.  Process all science, engineering, and ancillary data into standardized IDFS data sets.
4.  Store all source telemetry and generated IDFS data sets on the local SwRI archive.
5.  Generate and update web-based displays for public viewing and (password-protected) science analysis.
6.  Distribute IDFS data and intermediate files to all ASPERA-3 Co-Investigators.
7.  Prepare and submit validated, PDS-compliant IDFS data sets to the NASA Planetary Data System.

## Domain Data Elements
*   **Telemetry Data**
    *   Primary Key: Packet Identifier / Time
    *   Fields: Source (DPU, ELS, IMA, etc.), Raw Data, Receipt Timestamp, Data Quality Flag
*   **IDFS Data Set**
    *   Primary Key: Virtual Instrument ID / Processing Time Range
    *   Fields: Instrument Parameters, Science Measurements, Calibration Coefficients, Metadata, PDS Compliance Flag
*   **Virtual Instrument Description**
    *   Primary Key: Virtual Instrument ID
    *   Fields: Physical Component Source, Logical Grouping, Data Product Definitions, IDFS Schema
*   **Orbit/Attitude (OA) Data**
    *   Primary Key: Spacecraft Time
    *   Fields: Position (X, Y, Z), Attitude (Quaternion/Vectors), Velocity, Reference Frame
*   **System Log**
    *   Primary Key: Log Entry Timestamp
    *   Fields: Process Name, Event Type (Error/Info), Message, Severity, Operator ID
*   **Web Display Configuration**
    *   Primary Key: Display ID
    *   Fields: Data Source, Plot Type (Time Series, Spectra), Access Level (Public/Protected), Refresh Rate

## Non-Functional Requirements
1.  The system shall run on designated UNIX-based production and development computers.
2.  Web server components shall be password-protected to restrict access to authorized ASPERA-3 team members only.
3.  The system shall maintain a network connection between SwRI and NISN for reliable data transfer.
4.  SwRI shall provide ongoing system maintenance and software support for the APAF.
5.  The system design shall consider factors like reliability, maintainability, and usability.
6.  Data shall be electronically distributed to Co-I's within 24 hours of error-free acquisition and processing.

## Milestones and External Dependencies
1.  Mars Express launch scheduled for June 2003.
2.  Delivery of Software Design Documents (SDDs) for each instrument component (DPU, ELS, etc.) through 2002.
3.  Finalization of data distribution mechanisms detailed in the APAF Operations Procedures Document six months prior to launch.
4.  Dependence on ESOC for telemetry data delivery and interface definitions (DDID, SGICD).
5.  Project end date: September 30, 2007.

## Risks and Mitigation Strategies
1.  **Risk:** Delays in receiving cleaned-up telemetry from ESOC.
    *   **Mitigation:** APAF will generate necessary intermediate cleaned-up files internally.
2.  **Risk:** Inability to meet the 6-month PDS delivery deadline for validated data.
    *   **Mitigation:** Implement robust, automated processing and validation pipelines early in development.
3.  **Risk:** Evolving needs of the science team for data distribution and web displays.
    *   **Mitigation:** Define final distribution mechanisms and display requirements in procedures six months before launch.
4.  **Risk:** Network failures disrupting data acquisition from NISN.
    *   **Mitigation:** Design system with retry logic and local buffering; ensure reliable network infrastructure.
5.  **Risk:** Insufficient computational or archival resources for the volume of mission data.
    *   **Mitigation:** Specify and procure adequate UNIX-based production hardware with scalable storage.

## Undecided Issues
1.  The final mechanism and specifics for distributing data to each Co-Investigator (e.g., media, subsets).
2.  Complete definition of all internal software interfaces, deferred to detailed Software Design Documents.
3.  Detailed internal data structures and formats for virtual instruments, deferred to SDDs.
4.  Any installation-dependent adaptation requirements for the APAF system.
5.  The specific content and configuration of password-protected web displays for science analysis.
6.  Final validation procedures and criteria for data prior to PDS submission.
