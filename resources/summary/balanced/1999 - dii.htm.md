# Balanced Summary: DII COE XML Services (XS) SRS

## Goals and Scope
The XML Services (XS) functional area provides infrastructure services for mission and support applications using XML technology within the Defense Information Infrastructure (DII) Common Operating Environment (COE). Its primary goals are to isolate vendor-unique data access implementations, avoid application dependencies on physical access models, and provide data management functions for distributed database interoperability. The scope encompasses the registration of XML terms and structures, the design of XML schemas, and the generation and consumption of XML documents.

## Stakeholders and User Stories
*   **DISA (Defense Information Systems Agency):** The sponsoring agency responsible for the overall COE baseline and system integration.
*   **DII COE AOG Data Access Services Technical Working Group (DATATWG):** The technical body that prepared the specification, defining the functional and performance requirements.
*   **COE Chief Engineer:** Holds ultimate authority to mediate disputes within Communities of Interest (COIs) and approves Points of Contact.
*   **COE Data Engineering Team:** Analyzes tags and semantics to identify consolidation opportunities and guide standardization.
*   **Community of Interest (COI) Point of Contact (POC):** Manages the lifecycle (submission, review, status) of XML information resources within their specific domain.
*   **Application Developers:** Create mission and support applications that consume XS services to generate and process XML data.
*   **System Administrators/Data Managers:** Configure, tune, and maintain the XS services and registries in various operational environments.

**User Stories:**
1.  As a **Producer**, I want to submit metadata and XML artifacts to the registry so that my terms can be shared and understood across the community.
2.  As a **Consumer**, I want to search, view, and download registered XML tags and DTDs so that I can reuse approved structures in my applications.
3.  As a **Manager**, I want to review, approve, and manage submissions and user access so that registry integrity and naming conventions are maintained.
4.  As an **Application Developer**, I want to use XS services to generate and validate XML documents so that my application remains independent of specific database vendors.
5.  As a **System Administrator**, I want to tune session time-outs and connection descriptors so that services remain responsive in degraded communications environments.
6.  As a **COI POC**, I want to transition information resources between statuses (e.g., developmental to approved) so that my community's XML standards evolve in a controlled manner.

## Key Processes
1.  **Registry Submission (Trigger: Developer needs to register a new term):** A producer downloads a submittal package, completes forms with metadata and XML artifacts, and submits them via batch or interactive process.
2.  **Registry Management (Trigger: New submission received):** A manager reviews the submission, parses the forms, populates the registry database, and approves or rejects the entry.
3.  **Registry Discovery (Trigger: Developer needs an XML component):** A consumer searches the registry by tag, author, or relationship, views detailed information and relationships, and downloads selected resources.
4.  **Schema Design (Trigger: Need to define structure for a new XML document):** A designer uses services to create or reference existing tags, records semantic structures, and validates against standards.
5.  **Document Generation (Trigger: Application needs to output data as XML):** Services generate an XML document with an embedded or referenced schema, check it for conformance (well-formed, valid), and render it.
6.  **Document Consumption (Trigger: Application receives an XML document):** A parser processes the document, checks conformance, and may extract semantically-valid views or transform the hierarchical data.
7.  **Notification (Trigger: Change to a registered information resource):** The registry notifies subscribed consumers or authorized producers about the change to ensure awareness.

## Domain Data Elements
*   **Information_Resource**
    *   **Primary Key:** Resource_ID
    *   **Key Fields:** Resource_Type (e.g., XML_Element, XML_Spec), Name, Definition, Status (e.g., developmental, approved), Submitter/Author
*   **XML_Element (Tag)**
    *   **Primary Key:** Element_ID
    *   **Key Fields:** Element_Name, Data_Type, Definition, Parent_Element_ID (for hierarchy), Namespace_ID
*   **XML_Spec (e.g., DTD, DCD)**
    *   **Primary Key:** Spec_ID
    *   **Key Fields:** Spec_Name, Version, Formal_Public_Identifier, Defining_Text, Status
*   **Registry_Submission**
    *   **Primary Key:** Submission_ID
    *   **Key Fields:** Submitter_ID, Submission_Date, Package_Content (e.g., forms, artifacts), Review_Status, Reviewer_ID
*   **Association**
    *   **Primary Key:** Association_ID
    *   **Key Fields:** Source_Resource_ID, Target_Resource_ID, Association_Type (e.g., uses/used_by, is_newer_version_of), Effective_Date
*   **Namespace**
    *   **Primary Key:** Namespace_ID
    *   **Key Fields:** Namespace_Name, Formal_Public_Identifier, Owner_COI, Description

## Non-functional Requirements
1.  **Portability:** The registry software must be portable and execute on all COE-compliant platforms.
2.  **Operational Modes:** Services must support fixed/static, dynamic/deployed, and degraded communications environments with tunable parameters (e.g., session time-outs).
3.  **COE Compliance:** XML Services components must be segmented and adhere to COE compliance level requirements as described in the I&RTS.
4.  **Performance:** In fixed environments, services must be tunable by on-site personnel to adjust for varying workloads and database sizes.
5.  **Interoperability:** Services must provide location transparency and isolate applications from vendor-unique data access implementations.
6.  **Maintainability:** The XS developer is responsible for software maintenance, support, and updates, with DISA CM responsible for distribution.

## Milestones and External Dependencies
1.  Finalization and approval of this SRS (Version 2.0 is a draft as of 11 June 1999).
2.  Detailed design of external and internal programming interfaces (APIs), which are currently unspecified and deferred to the design phase.
3.  Development and integration of XS components with other COE services (Management, Distributed System, Application Support).
4.  Qualification through formal validation tests (Test, Demonstration, Analysis, Inspection) of the SRS-level requirements.
5.  Establishment of operational Communities of Interest (COIs) and their appointed Points of Contact.

## Risks and Mitigation Strategies
1.  **Risk:** Proliferation of inconsistent, redundant XML tags across systems hindering interoperability.
    *   **Mitigation:** Implement a centralized registry with review/approval processes and strong encouragement for reuse of approved tags.
2.  **Risk:** Unclear or deferred interface specifications (APIs) could lead to integration challenges.
    *   **Mitigation:** Prioritize detailed design of external and internal APIs in the next phase, adhering to COE and JTA standards.
3.  **Risk:** Operational challenges in dynamic/deployed or degraded communications environments.
    *   **Mitigation:** Design services with configurable parameters (time-outs, descriptors) that can be adjusted for environmental conditions.
4.  **Risk:** Disputes within Communities of Interest over tag semantics or approval.
    *   **Mitigation:** Define a clear escalation path to the COE Chief Engineer for final arbitration of unresolved disputes.
5.  **Risk:** Ensuring semantic understanding and valid use of registered terms.
    *   **Mitigation:** Require detailed definitions, synonyms, and amplifying information in submissions, and provide relationship views (ancestor, versioning) in the registry.
