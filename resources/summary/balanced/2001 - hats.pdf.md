# Balanced Summary: HATS Graphical User Interface (GUI) Software Requirements Specification

## Goals and Scope
The HATS-GUI is a platform-independent graphical user interface designed to simplify user interaction with the High Assurance Transformation System (HATS). Its primary goal is to facilitate the creation, management, and execution of program transformations, enabling users to apply formal, provably correct transformations to target programs. The system aims to increase HATS adoption by providing an intuitive interface for preparing applications, parsing and executing transformation programs, and examining outputs in both Syntax Derivation Tree (SDT) and pretty-printed text formats.

## Stakeholders and User Stories
*   **Dr. Victor Winter (Customer):** Provides requirements and final approval for the system.
*   **Guidance Team (Dr. Ann Gates, Dr. Steve Roach, Mr. Francisco Javier Leyva):** Oversees development, reviews documentation, and provides technical guidance.
*   **Software Development Teams (Creative, Omega, Porcelain, Resilient, Suzaku):** Responsible for the design, implementation, and testing of the HATS-GUI.
*   **End User (Transformation Expert):** A computer-savvy expert in a specific problem domain who uses the GUI to construct and apply software transformations.

**User Stories:**
1.  As a **User**, I want to **select and open an existing application** so that I can work on a specific transformation problem.
2.  As a **User**, I want to **parse a transformation language program (.tlp file)** so that HATS-SML can execute it.
3.  As a **User**, I want to **execute a parsed transformation program on a target file** so that I can generate transformed output.
4.  As a **User**, I want to **display and navigate a graphical representation of an output SDT** so that I can inspect the structure of the transformation result.
5.  As a **User**, I want to **configure color schemes and shapes for different node types in the SDT display** so that I can customize the visual presentation for clarity.
6.  As a **User**, I want to **search for specific patterns within an SDT or pretty-printed text** so that I can quickly locate relevant parts of large outputs.

## Key Processes
1.  **Select Application:** (Trigger: User menu selection) The system lists directories, allows navigation, and loads a chosen application's configuration and file associations.
2.  **Prepare Application:** (Trigger: User action to create/edit) The user creates or modifies an application's core files (lexical spec, grammar, user library) and configuration.
3.  **Generate Parser:** (Trigger: Need to parse new/changed grammar) The system invokes HATS-SML to create a parser from the lexical and grammar specifications.
4.  **Parse File:** (Trigger: User selects a .tlp or .tgt file to parse) The system checks parser currency, invokes HATS-SML, and saves the resulting SDT (.parsed file).
5.  **Execute Transformation:** (Trigger: User selects a parsed .tlp program to run) The system verifies file dependencies, invokes HATS-SML's transformation engine, and captures output/error streams.
6.  **Display Output:** (Trigger: User selects an output file for viewing) The system renders the SDT as a navigable graph or displays pretty-printed text in a dedicated window.
7.  **Configure Settings:** (Trigger: User accesses configuration menu) The user defines editors, file associations, and display properties (colors, shapes, expansion levels) for the application.

## Domain Data Elements
*   **Application:** (Primary Key: Directory Name) Contains configuration, core files, transformation programs, target files, and outputs.
*   **Core Domain:** (Implicitly keyed by Application) Comprises `lexical.spec`, `grammar.grm`, `library.sml` files defining the transformation language.
*   **Transformation Program (.tlp):** (Primary Key: Filename) A text file containing transformation rules and control logic.
*   **Target File (.tgt):** (Primary Key: Filename) The input program to be transformed.
*   **Syntax Derivation Tree (SDT):** (Primary Key: Filename, e.g., `.parsed`, `.sdt`) A tree structure representing the parsed form of a program or transformation output.
*   **Pretty-Printed Output (.txt):** (Primary Key: Filename) Formatted text generated by applying a style to an SDT.

## Non-Functional Requirements
1.  **Performance:** Must display a 10,000-node SDT within 5 seconds.
2.  **Portability:** Must run on Windows 2000, Sun Solaris 8, and Linux without code modification.
3.  **Implementation:** The system shall be developed using Java 1.3.
4.  **Responsiveness:** The GUI must remain responsive, allowing user interaction while HATS-SML executes long-running transformations.
5.  **Scalability:** Display and navigation algorithms must handle large SDTs (up to 1,000,000 nodes) efficiently.
6.  **Usability:** The interface shall be menu-driven, assuming a sophisticated user with minimal need for extensive help systems.

## Milestones and External Dependencies
1.  Completion of HATS-SML version 2.0 by October 2001.
2.  Availability of Java Virtual Machine (JVM) and ML interpreter on the host system.
3.  Final approval of this SRS by the customer and guidance team.
4.  System testing on all target platforms (Solaris, Windows, Linux).
5.  Project completion by December 2001.

## Risks and Mitigation Strategies
1.  **Risk:** HATS-SML version 2.0 interface changes. **Mitigation:** Maintain close communication with the customer (Dr. Winter) and update the protocol in Appendix D as needed.
2.  **Risk:** Inadequate performance for very large SDTs. **Mitigation:** Employ efficient, incremental graph drawing and search algorithms, avoiding the prohibited "virtual window" approach.
3.  **Risk:** Complexity of mapping between SDT nodes and pretty-printed text. **Mitigation:** Implement the mapping requirement conservatively, acknowledging that perfect correspondence may not always be possible due to pretty-print transformations.
4.  **Risk:** Cross-platform file system and process invocation differences. **Mitigation:** Use Java's abstracted APIs for file and process operations and conduct early testing on all target OSs.
5.  **Risk:** Unclear search semantics for complex grammars. **Mitigation:** Implement the search criteria defined in Appendices E & F and validate with example grammars provided by the customer.

## Undecided Issues
1.  Specific details of the communication protocol between HATS-GUI and HATS-SML may evolve with version 2.0.
2.  The exact mechanism for "mirroring" navigation between SDT and pretty-printed text windows when correspondence is ambiguous.
3.  Default settings for the application configuration (e.g., default colors, expansion levels).
4.  Handling of error recovery when HATS-SML processes fail mid-execution.
5.  The detailed user interface layout and widget specifics (buttons, dialogs).
6.  Management of system resources when multiple large SDTs are displayed simultaneously.
