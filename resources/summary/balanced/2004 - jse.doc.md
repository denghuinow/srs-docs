# Balanced Summary: ISIN Issuance for Money Market Instruments

## Goals and Scope
This project aims to establish an automated system for the JSE, as the National Numbering Agent (NNA), to electronically issue, cancel, and de-register ISIN codes for Money Market Instruments (MMIs) to support the dematerialization and same-day settlement environment. The scope is limited to providing this service to STRATE via SWIFT messages, enabling the electronic clearing and settlement of MMIs as required by the Money Market Forum (MMF).

## Stakeholders and User Stories
*   **JSE (NNA):** The authorized entity responsible for issuing ISINs in South Africa, developing and operating the automated issuance system.
*   **STRATE (CSD/IOR):** The central securities depository and instrument ownership register that requests ISINs from the JSE on behalf of market participants.
*   **Money Market Forum (MMF):** The body representing money market participants, defining the business requirements for electronic trading and settlement.
*   **JSE Application and Service Division (ASD):** The department responsible for developing and maintaining the ISIN issuance system.
*   **JSE Clearing & Settlement (C&S):** The division that will administer and monitor the ISIN issuance service.
*   **National Market Practice Group (NMPG):** The group responsible for approving the SWIFT message standards used in the process.

**User Stories:**
1.  As **STRATE**, I want to **electronically request a new ISIN for an MMI** so that the instrument can be immediately dematerialized and settled.
2.  As **STRATE**, I want to **request the cancellation/de-issue of an existing ISIN** so that instrument changes can be reflected in the settlement system.
3.  As **STRATE**, I want to **request the deregistration of an ISIN upon an instrument's maturity** so that the instrument register is kept accurate.
4.  As the **JSE (NNA)**, I want to **automatically validate and process ISIN requests** so that ISINs are issued rapidly and accurately to support T+0 settlement.
5.  As **JSE Clearing & Settlement**, I want to **manually input or update ISIN data via a front-end system** so that business continuity is maintained during system outages.
6.  As **JSE Clearing & Settlement**, I want to **view and monitor all ISIN issuance, rejection, and cancellation activity** so that I can oversee the service and troubleshoot issues.

## Key Processes
1.  **ISIN Issuance Request:** Triggered by STRATE sending a validated MT598-150 (NEWM) SWIFT message to the JSE.
2.  **Request Validation:** The JSE system validates the message format and content upon receipt.
3.  **Rejection Notification:** If validation fails, the JSE sends a rejection message (MT598-901/902) back to STRATE.
4.  **ISIN Generation & Confirmation:** If valid, the system generates a new ISIN (with prefix ZAM) and sends a confirmation message (MT598-151) to STRATE.
5.  **Cancellation/De-issue Request:** Triggered by STRATE sending an MT598-150 (DISS) message to cancel an active ISIN.
6.  **Maturity Deregistration Request:** Triggered automatically by STRATE's system on an instrument's maturity date, sending an MT598-150 (MATU) message.
7.  **Confirmation Rejection:** STRATE validates and may reject the JSE's confirmation messages (MT598-151) if discrepancies are found.

## Domain Data Elements
*   **Money Market Instrument (MMI)**
    *   **Primary Key:** ISIN (e.g., ZAM...)
    *   Key Fields: MMI Type, Generic Category, Issue Date, Maturity Date, Issuer Participant Code
*   **ISIN Request**
    *   **Primary Key:** Transaction Reference (Tag 20)
    *   Key Fields: Sub-Message Type, Function (NEWM), Instruction Type (ISSU/DISS/MATU), Preparation Date/Time
*   **Issuer**
    *   **Primary Key:** Participant Code
    *   Key Fields: BIC Code, Name
*   **Financial Instrument Attributes**
    *   **Primary Key:** Part of MMI record
    *   Key Fields: Coupon Rate, Coupon Payment Frequency, Coupon Payment Day, Quantity Issued
*   **Rejection Message**
    *   **Primary Key:** Transaction Reference
    *   Key Fields: Related Reference (to original message), Error Code(s), Error Details
*   **Confirmation Message**
    *   **Primary Key:** Transaction Reference
    *   Key Fields: Related Reference, Confirmation Type, ISIN

## Non-Functional Requirements
1.  **Performance:** System must handle an estimated 200-500 ISIN issuance requests per day.
2.  **Availability:** A Business Continuity Plan (BCP) must be in place, including manual override capabilities.
3.  **Interoperability:** Must communicate via SWIFT MT598 messages using ISO15022 standards.
4.  **Usability:** A front-end system is required for JSE staff to monitor, manually update, and report on ISIN activity.
5.  **Data Integrity:** ISIN issuance must comply with ANNA and ISO 6166 rules and guidelines.
6.  **Maintainability:** The system must allow for updates to issuer codes and other reference data.

## Milestones and External Dependencies
1.  Approval of SWIFT MT598 message formats and content by the NMPG.
2.  STRATE's review and approval of the JSE's cost assessment for development and monthly running costs.
3.  JSE's acquisition of a new SWIFT BIC branch code (XJSEZAJJXISN) for message routing.
4.  Finalization and signing of a Service Level Agreement (SLA) between JSE and STRATE.
5.  Target implementation in the 2nd quarter of 2004.

## Risks and Mitigation Strategies
1.  **Risk:** High volume of requests could overwhelm the system.
    *   **Mitigation:** Design system to handle the estimated peak load of 500 requests/day.
2.  **Risk:** SWIFT message format or content changes after development.
    *   **Mitigation:** Secure final NMPG approval before final development and build flexibility into message parsing logic.
3.  **Risk:** System failure disrupting critical ISIN issuance.
    *   **Mitigation:** Implement a BCP with manual ISIN entry functionality in the front-end system.
4.  **Risk:** Cost recovery disputes with STRATE.
    *   **Mitigation:** Define clear monthly running costs and billing methodology within the SLA.
5.  **Risk:** Invalid or duplicate ISIN requests from STRATE.
    *   **Mitigation:** Implement robust validation logic and clear rejection messaging with specific error codes.

## Undecided Issues
1.  Final approval of the SWIFT MT598 message content by the NMPG.
2.  Definition of specific error codes for rejection messages (MT598-901/902).
3.  Finalization of the billing methodology and monthly running costs in the SLA.
4.  Resolution of how to handle issuer participant code updates (referenced in email correspondence).
5.  The process and responsibility for handling "top-up" or "reduction" requests for issued amounts (mentioned as removed from flows).
6.  Final sign-off and approval from all parties (MMF, STRATE, JSE, NMPG) pending on the document.
