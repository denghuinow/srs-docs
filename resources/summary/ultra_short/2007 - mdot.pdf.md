**Purpose & Scope**
The system is a prototype research platform called the Data Use Analysis and Processing (DUAP) system. Its purpose is to investigate and evaluate the utility of Vehicle Infrastructure Integration (VII) data, integrated with other sources, to enhance transportation safety, mobility, and asset management for the Michigan Department of Transportation (MDOT). It is a functional prototype for demonstration and assessment, not necessarily intended for sustained operational use.

**Product Background / Positioning**
DUAP is part of MDOT's broader VII research program. It will ingest data from the nascent VII network (e.g., probe data from vehicles), existing MDOT and partner systems (e.g., traffic management, weather stations), and other telematics sources. Its processed outputs are intended for use by existing transportation agency systems and personnel.

**Core Functional Overview**
1.  Collect probe vehicle, traffic, weather, and road condition data from multiple external sources.
2.  Cache incoming data for short-term, fast access (e.g., for one week).
3.  Apply computational algorithms to raw data to derive traffic metrics, detect incidents, and assess road conditions.
4.  Archive both raw and processed data for long-term storage and analysis.
5.  Format and publish processed data and alerts for use by external systems and internal presentation services.
6.  Provide web-based user interfaces for human operators to browse traffic, incident, weather, and asset condition information.
7.  Provide administrative services to configure, sequence, and secure all other system services.

**Key Users & Usage Scenarios**
Primary users are MDOT and partner transportation agency personnel, including traffic operators, maintenance staff, asset managers, and system administrators. They use the system to monitor real-time conditions, detect incidents, plan maintenance, and make operational decisions. All users require system login, with access controlled by an administrator.

**Major External Interfaces**
The system interfaces with numerous external data providers and consumers. Key interfaces include the VII Proof of Concept network for probe data, various Traffic Management Systems (TMS), Road Weather Information Systems (RWIS), and the Clarus weather system. It outputs data in standard formats like SAE J2354 XML and to specific systems like MDOT's presentation services.

**Key Non-functional Requirements**
*   **Performance:** Data must be cached and made available for access immediately upon receipt. The system handles continuously streaming data.
*   **Security:** System access is restricted to authorized users. The system logs user access and data transactions. An administrator manages user rights.
*   **Reliability/Maintainability:** The architecture must be flexible, scalable, and maintainable, allowing new data sources, algorithms, and outputs to be added.
*   **Compliance:** The system shall conform to IT standards established by the Michigan Department of Information Technology (MDIT).
*   **Data Constraints:** Cached data records must include source, geo-reference, and timestamp. Dynamic data is cached for one week.

**Constraints, Assumptions & Dependencies**
*   **Constraints:** The system must use Michigan Geographic Framework geo-references and handle database requests via standard SQL. It is a prototype.
*   **Assumptions:** VII and integrated data are "near real-time"; applications must handle data latency and quality variations. Data utility depends on the penetration of VII-equipped vehicles and roadside equipment.
*   **Dependencies:** Success depends on data availability from the VII network and other third-party sources, which may have use limitations. MDOT is responsible for establishing user authorization policies.

**Priorities & Acceptance Approach**
Requirements are explicitly prioritized as High (H), Medium (M), Low (L), or Deferred (D). High-priority requirements are essential to the DUAP system's core mission of data collection, processing, and dissemination for research evaluation. Acceptance will be based on verifying that the implemented system fulfills these specified, testable requirements.
