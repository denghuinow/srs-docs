**Purpose & Scope**  
The system defines a standard C/C++ modeling interface (SCE-MI) to enable high-performance communication between untimed software models on a host workstation and structural hardware models (e.g., RTL netlists) on verification platforms like emulators. It provides message-based channels to bridge these abstraction levels, focusing on transaction-oriented co-emulation. It does not handle software-to-software communication, event-based simulation, or debug/control features (which are out of scope for this specification).

**Product Background / Positioning**  
SCE-MI is proposed as an industry standard to replace proprietary emulator APIs, addressing the need for a common, high-performance interface for System-on-Chip (SoC) verification. It is part of the broader SCE-API standard effort by a consortium of EDA vendors and customers. The interface is optimized for use with SystemC and emulation platforms, aiming to avoid communication bottlenecks that limit emulator performance.

**Core Functional Overview**  
1. Establish message channels between software models and hardware transactors.  
2. Serialize/deserialize messages between untimed software data and bit vectors for hardware transport.  
3. Provide controlled clock generation and reset for the hardware DUT.  
4. Allow transactors to freeze controlled time during message composition/decomposition.  
5. Support multi-threaded and single-threaded software environments via a service loop.  
6. Enable binding of software proxies to hardware message ports by name.  
7. Offer error and informational message handling for the interface.  
8. Provide C++ and C APIs for software-side interaction.

**Key Users & Usage Scenarios**  
*End Users*: SoC design engineers who integrate pre-built transactor models to connect untimed testbenches to RTL DUTs without needing detailed API knowledge.  
*Transactor Implementors*: IP developers who create plug-and-play transactor and proxy models using SCE-MI macros and APIs.  
*SCE-MI Infrastructure Implementors*: EDA tool vendors who provide compliant implementations of the interface for specific verification platforms.  
Typical scenario: An end user employs transactor models to bridge a SystemC testbench to an emulator-running RTL design, using the SCE-MI infrastructure for message passing and clock control.

**Major External Interfaces**  
*Hardware-side*: Defined by Verilog/VHDL macros (message ports, clock control, clock port) instantiated in transactors and the DUT netlist.  
*Software-side*: C++ class API (and C function API) for proxy binding, message sending/receiving, and service loop management.  
*Parameter interface*: File-based configuration generated by the infrastructure linker, detailing system dimensions (clocks, ports, transactors).

**Key Non-functional Requirements**  
*Performance*: The interface must avoid inherent communication bottlenecks that could throttle emulator performance. Message channels are transaction-oriented to minimize host-workstation interaction.  
*Compatibility*: Must function in both multi-threaded (e.g., SystemC) and single-threaded C/C++ environments.  
*Reliability*: Fatal errors are reported via a registered error handler or returned status; the interface does not support recovery from fatal errors.  
*Maintainability*: The specification defines a clear separation between user roles (end user, transactor implementor, infrastructure implementor).

**Constraints, Assumptions & Dependencies**  
*Constraints*: The hardware-side interface is specified as empty HDL macros with defined ports and parameters; the implementation must expand these. The software-side API must be provided in both C++ and C forms.  
*Assumptions*: The primary use case bridges untimed software models to cycle-accurate (RTL) hardware models; bridging cycle-accurate software models is possible but not ideal.  
*Dependencies*: Relies on a compliant infrastructure linker to analyze the user's hardware netlist, extract parameters, and generate the parameter file. Assumes the existence of a verification platform (emulator) and a host workstation with a C/C++ environment.

**Priorities & Acceptance Approach**  
The highest priority is providing a standard, high-performance message-passing interface that avoids proprietary lock-in and enables plug-and-play transactor models. Acceptance is based on compliance with the functional specification of the API and macros, successful co-modeling sessions using the interface, and meeting performance goals without introducing bottlenecks. The interface must be validated by the consortium members for interoperability across different vendor platforms.
