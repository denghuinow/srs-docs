**Purpose & Scope**
The NDE system receives, processes, packages, archives, and distributes environmental satellite data from the NPP and NPOESS programs to NOAA's operational and climate communities. It generates tailored and NOAA-unique data products, provides customer services, and ensures long-term archiving. The system does not include the primary satellite data processing (IDPS) or the long-term archive (CLASS) itself; it interfaces with them.

**Product Background / Positioning**
NDE is a downstream processing and distribution system within NOAA's Environmental Satellite Processing Center (ESPC). It sits between the NPOESS Interface Data Processing Segment (IDPS), which provides raw data, and end-user communities. It also interfaces with the CLASS archive for long-term data stewardship and the NPOESS Mission Management Center (MMC).

**Core Functional Overview**
1.  Receive and ingest all data records (xDRs), telemetry, and ancillary data from the IDPS and other external sources.
2.  Generate NOAA-unique environmental data products by applying scientific algorithms to the ingested data.
3.  Tailor data products by reformatting (e.g., to BUFR, GRIB2, netCDF), re-projecting, compressing, and aggregating them based on customer specifications.
4.  Distribute products to authorized users and deliver NOAA-unique products to the CLASS long-term archive.
5.  Provide customer services including user registration, subscription management, order status notification, and a help desk.
6.  Operate in distinct Open, Degraded, and Restricted Access modes based on system and data availability.
7.  Monitor system health, performance, data integrity, and product quality.

**Key Users & Usage Scenarios**
Primary users are NOAA operational and climate communities (e.g., NWS, NCEP) and other authorized civilian customers. Users register and subscribe to specific data products. Operators monitor and control the system, manage quality, and handle trouble tickets. Typical scenarios include automated product generation and distribution based on satellite data receipt, customer ad-hoc data requests, and system monitoring by operators.

**Major External Interfaces**
Key interfaces are with: the IDPS for data ingestion; the CLASS archive for product storage and retrieval; the NPOESS Mission Management Center (MMC) for status and coordination; external ancillary data sources (e.g., NCEP); and end-user systems for product delivery.

**Key Non-functional Requirements**
*   **Availability:** Core capabilities (Ingest, Product Generation, Distribution, Operations Monitoring) must not be interrupted for more than 2 hours in any 24-hour period or 4 hours in any 30-day period.
*   **Performance/Latency:** Products must be available for distribution within 5 minutes of receiving all required input data. Specific telemetry data (SARSAT, A-DCS) must be delivered to processing centers within 1 minute of receipt.
*   **Capacity:** Must support input/output data volumes of 4/8 TB per day during NPP, scaling to 8/16 TB per day for NPOESS missions.
*   **Reliability:** 99% of scheduled and event-driven tasks must execute successfully in any consecutive 30-day period.
*   **Security:** Must comply with NOAA IT security procedures and protect data integrity from errors, malfunctions, and disasters. Access is controlled and requires government authorization.
*   **Maintainability:** The system must be scalable and capable of accepting technology updates without downtime.

**Constraints, Assumptions & Dependencies**
*   Must reuse existing government-furnished hardware and software where possible and practical.
*   Must comply with the Federal Enterprise Architecture (FEA) and Federal Geographic Data Committee (FGDC) metadata standards.
*   Dependent on external systems: IDPS for primary data, CLASS for archiving, ESPC for ancillary data and security infrastructure, and the NPOESS ground system for mission status.
*   Assumes the provision of NOAA-supplied scientific algorithms for product generation.

**Priorities & Acceptance Approach**
Priority is on continuous operational availability and meeting strict latency requirements for data delivery. Acceptance will be based on demonstrated compliance with the quantified performance, availability, capacity, and security standards outlined in the requirements. System capabilities must be verifiable through logs, performance reports, and successful integration tests with external interfaces.
