**Purpose & Scope**
The system is an automated diagnostic tool for detecting and identifying operational faults in HVAC subsystems (chillers, cooling towers, and boilers) using sensed and fixed data. It replaces manual, expert visual analysis with automated algorithms. The tool is for monitoring and fault detection only; it does not perform control actions, design new systems, or provide user-defined analytical capabilities beyond its configured diagnostics.

**Product Background / Positioning**
The tool automates existing manual diagnostic processes performed by human experts on HVAC systems. It is intended to be used within the existing ecosystem of building management, interfacing with data acquisition devices and existing HVAC units. It is a standalone software product that processes data from these systems to provide diagnostic results.

**Core Functional Overview**
1.  Acquire and validate sensed data (e.g., temperatures, currents) from HVAC units in real-time or from batch files.
2.  Detect and identify specific performance and operational faults in chiller subsystems (e.g., schedule errors, temperature control issues, abnormal compressor cycling, improper equipment interlocks).
3.  Detect and identify specific faults in cooling tower subsystems (e.g., sump temperature control, fan cycling, approach problems, fan staging issues, range problems).
4.  Detect and identify specific faults in boiler subsystems (e.g., shutoff schedule compliance, hot water temperature control, excessive cycling).
5.  Determine the operational status (On/Off/Steady/Transient) of key HVAC components (compressors, pumps, fans) from sensed current/power data.
6.  Display current and historical diagnostic results to the user through a structured interface.
7.  Allow an administrator to configure system parameters, diagnostic sensitivities, and fixed data.
8.  Log all diagnostic results and significant errors to permanent storage.

**Key Users & Usage Scenarios**
*   **Building Operators & Facilities Managers:** Primary users. Monitor HVAC units from a central location, checking diagnostic status periodically (e.g., daily) to prioritize maintenance.
*   **HVAC Service Technicians:** Use on-site during repairs or off-site for remote monitoring. Sessions may last up to an hour, several times a day.
*   **Energy Service Providers:** Monitor multiple customer units remotely for inefficiencies, deciding when to dispatch personnel.
*   **Building Operator Supervisors:** Use to guide work assignments and prioritization.
*   **Permission Differences:** A **General User** can only browse diagnostic results. An **Administrator** can also start/stop diagnostics and configure all system parameters.

**Major External Interfaces**
*   **Data Acquisition Interface:** Inputs real-time sensed data from HVAC units and data acquisition devices.
*   **Data File Interface:** Inputs historical sensed data from formatted ASCII text files (batch mode).
*   **User Interface:** A graphical Windows application with six main windows (Main, Configuration, Subsystems, Condition, Diagnostic Information, Diagnostic History) following a strict hierarchical navigation model.

**Key Non-functional Requirements**
*   **Platform:** Must run on Microsoft Windows-compatible operating systems.
*   **Data Precision:** Sensed data stored with a precision of three significant figures.
*   **Data Validation:** Sensed data must be validated against expected ranges (with user-modifiable defaults).
*   **Engineering Units:** Sensed data must be in specified units (e.g., °F, Amps) or be convertible to them.
*   **Reliability:** Diagnostic algorithms must not process if any required input data is missing; the user must be notified.
*   **Security:** User authentication (ID/password) required to distinguish General Users from Administrators for privileged functions.
*   **Supportability:** Significant software errors must be logged to permanent storage with time, module, function, and description.
*   **Usability:** The interface must support users with varying computer expertise but a good understanding of HVAC systems.

**Constraints, Assumptions & Dependencies**
*   The initial version focuses on diagnostics for chillers and cooling towers; boiler diagnostics are also specified but noted for future inclusion.
*   The software architecture must support the addition of diagnostic algorithms for other HVAC subsystems.
*   The tool's diagnostic algorithms are derived from existing expert practices; its success depends on the accuracy and completeness of these underlying rules.
*   It is assumed users have a fundamental understanding of HVAC systems.
*   The tool depends on receiving valid sensed and fixed data; data acquisition or communication failures will limit its functionality.

**Priorities & Acceptance Approach**
*   **Highest Priority:** Core diagnostic detection for chillers and cooling towers, data acquisition and validation, and result display/storage.
*   **High Priority:** User authentication, administrator configuration capabilities, and boiler diagnostics.
*   **Medium Priority:** Advanced features like diagnostic sensitivity adjustment and detailed historical data browsing with zoom/scroll.
*   Acceptance will be based on the software's ability to correctly identify the enumerated faults under test conditions using provided data sets, per the specified algorithms and interface behaviors.
