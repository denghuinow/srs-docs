**Purpose & Scope**
The system provides fault-tolerant system services for the X-38 Crew Return Vehicle's quad-redundant Flight Critical Computer (FCC). It acts as an interface between NASA's application code and the underlying hardware/OS, delivering scheduling, communication, fault management, and redundancy services. It does not include the application code itself or the hardware-level design of the Network Elements (NEs) and processors.

**Product Background / Positioning**
This is the core system software for the X-38's Fault Tolerant Parallel Processor (FTPP) architecture. It resides on the four Flight Critical Processors (FCPs) and a reduced set runs on five Instrument Control Processors (ICPs). It provides a consistent Application Programming Interface (API) to isolate the flight application from the redundant hardware and Commercial Off-The-Shelf (COTS) operating system (VxWorks).

**Core Functional Overview**
1.  **System Initialization & Synchronization**: Configures hardware into fault-tolerant virtual groups after power-up, synchronizing processors within a 2.5-second skew.
2.  **Deterministic Task Scheduling**: Executes application tasks in predefined 50 Hz, 10 Hz, and 1 Hz rate groups across configurable vehicle modes.
3.  **Fault-Tolerant Communication Services**: Provides synchronous (message queue) and immediate (pipe) message-passing between tasks, both within and between virtual groups, guaranteeing congruent data exchange.
4.  **Fault Detection, Isolation, and Recovery (FDIR)**: Performs continuous built-in tests, detects hardware faults, and manages reconfiguration (e.g., degrading from quad to triplex) and recovery of processors and Network Elements.
5.  **Redundancy Management**: Maintains the mapping of physical hardware to virtual groups and executes recovery strategies for processor, link, and NE failures.
6.  **Time Services**: Provides synchronized Mission Elapsed Time (MET) and Separation Elapsed Time (SEP) to all FCPs with specified drift and resolution.
7.  **Memory Management**: Performs RAM scrubbing for error detection/correction and manages memory alignment during processor reintegration.

**Key Users & Usage Scenarios**
*   **Primary User**: The NASA flight application software, which calls the provided API.
*   **Usage Scenario**: During a mission, the application runs cyclic control tasks. The FTSS ensures these tasks execute synchronously across redundant processors, handles communication with I/O processors, monitors system health, and automatically reconfigures around failed components without application intervention.

**Major External Interfaces**
*   **Application Programming Interface (API)**: Defined interface for all FTSS services.
*   **Network Element (NE) Hardware Interface**: For Byzantine-resilient, fault-tolerant inter-processor communication.
*   **VxWorks Operating System**: Uses VxWorks 5.4 as the underlying OS.
*   **Instrument Control Processor (ICP) Interface**: Via shared memory and VME interrupts for synchronization and data exchange.
*   **Command & Telemetry Computer (CTC) Interface**: Via Multi-Protocol Communications Controller (MPCC) boards for telemetry output and command input.

**Key Non-functional Requirements**
*   **Performance**: System initialization from power-up to operational state must complete within 1.5 minutes. Scheduler and Time Services overhead must be ≤1 ms per 50 Hz frame. A failed FCP must be masked within 3 minor frames (60 ms) of detection.
*   **Reliability/Availability**: The system must be two-fault tolerant for any two non-simultaneous hardware faults and must operate with any combination of 3 of the 5 Fault Containment Regions (FCRs) active.
*   **Safety/Criticality**: Provides fault masking and recovery to maintain operation despite hardware failures.
*   **Resource Constraints**: FTSS with VxWorks shall use ≤3 MB of ROM and ≤9 MB of DRAM. Only 4 MB of DRAM is subject to realignment during recovery.
*   **Accuracy**: Mission Elapsed Time drift shall be ≤50 parts per million (PPM).

**Constraints, Assumptions & Dependencies**
*   **Hardware Constraint**: Must execute on the Radstone Power PC 604R processor.
*   **Software Constraint**: Must be written in C and use VxWorks 5.4.
*   **Key Dependency**: Correct operation of the underlying Network Element hardware and its firmware for fault-tolerant communications.
*   **Assumption**: The application software uses the FTSS API correctly and manages memory types (congruent vs. non-congruent) as defined.

**Priorities & Acceptance Approach**
The highest priority requirements are those ensuring basic fault-tolerant operation, deterministic scheduling, and critical fault recovery within specified time bounds. Acceptance will be based on demonstration and test against the qualification methods (Demonstration, Test, Analysis, Inspection) specified for each requirement, with traceability to the parent FTPP system requirements document.
