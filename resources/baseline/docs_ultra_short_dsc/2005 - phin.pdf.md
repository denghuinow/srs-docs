## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the Outbreak Management System (OMS), a critical component of the Public Health Information Network (PHIN). The intended audience includes project stakeholders, system architects, developers, testers, and public health end-users.

### 1.2 Scope
The OMS is a software application designed to support the investigation, monitoring, management, analysis, and reporting of public health outbreaks and bioterrorism events. The system will collect, link, and manage data related to cases, contacts, exposures, specimens, laboratory results, and treatments to facilitate the containment of public health events.

**In-Scope:**
*   Core outbreak management workflows (case investigation, contact tracing, lab management, monitoring).
*   Dynamic configuration of data elements and relationships.
*   Data analysis, visualization, and reporting.
*   Standards-based data exchange with external PHIN partner systems.
*   Support for connected and disconnected (field) operational modes.

**Out-of-Scope:**
*   Definition of specific data transport mechanisms (e.g., specific web service protocols, VPN details).
*   Detailed operational policies for all external partner organizations.
*   Underlying PHIN infrastructure components (e.g., master patient indexes, shared authentication services) unless directly interfaced.

## 2. Overall Description

### 2.1 Product Perspective
The OMS is a functional subsystem within the larger PHIN ecosystem. It must integrate seamlessly with other PHIN components to provide a comprehensive public health response capability.

**System Interfaces:**
*   **PHIN Surveillance Systems:** For early event detection and initial case data.
*   **Laboratory Information Systems (LIS):** For electronic lab orders and results (ELR).
*   **Countermeasure Administration Systems:** For tracking vaccine or medication distribution.
*   **Other Jurisdictional OMS Instances:** For multi-jurisdictional outbreak coordination.

### 2.2 Product Functions (High-Level)
1.  Configure event-specific investigation protocols.
2.  Conduct electronic case investigations.
3.  Establish and visualize relationships between entities (people, places, cases, contacts).
4.  Perform contact identification, exposure tracing, and monitoring.
5.  Manage the lifecycle of specimens and associated lab data.
6.  Monitor isolation/quarantine status and follow-up activities.
7.  Generate analytical outputs (reports, maps, graphs).
8.  Exchange data with external partner systems in standard formats.
9.  Operate in connected and disconnected modes with secure synchronization.

### 2.3 User Characteristics
| User Role | Primary Responsibilities | Skill Level / Assumptions |
| :--- | :--- | :--- |
| **Public Health Investigator** | Conducts case interviews, enters investigation data, identifies contacts. | Proficient in epidemiological concepts and investigative interviews. Moderate computer literacy. |
| **Contact Tracer** | Performs contact notification, exposure assessment, and follow-up monitoring. | Trained in interview techniques and data entry. May work extensively in field/disconnected mode. |
| **Lab Coordinator** | Manages specimen data, initiates lab test requests, reviews and interprets lab results. | Knowledge of laboratory procedures and terminology. |
| **Epidemiologist / Analyst** | Analyzes aggregated data, creates visualizations and reports, monitors outbreak trends. | Strong analytical skills. Proficient in data interpretation. |
| **System Administrator** | Configures system for new events, manages user accounts and roles, oversees system operations. | High technical proficiency. Understands public health workflows. |

### 2.4 Constraints
*   The system **must** comply with all applicable PHIN Messaging Implementation Guides and vocabulary standards (e.g., LOINC, SNOMED CT) for external data exchanges.
*   Development and deployment are dependent on successful integration with other PHIN systems (Surveillance, LIS, Countermeasure).
*   The system design assumes the existence of clearly defined personnel roles and configuration management protocols within the deploying organization.

### 2.5 Assumptions and Dependencies
*   Partner systems are capable of sending and receiving PHIN-compliant messages.
*   Adequate training will be provided to end-users.
*   A stable network infrastructure will be available for connected operations and synchronization.
*   Legal and policy frameworks for data sharing between jurisdictions are established externally to the system.

## 3. Specific Requirements

### 3.1 Functional Requirements

#### 3.1.1 Event and Configuration Management (ECM)
*   **ECM-001:** The system shall allow an authorized administrator to define a new outbreak event type (e.g., "Novel Influenza," "Foodborne Salmonella").
*   **ECM-002:** For each event type, the system shall allow an administrator to dynamically create and configure electronic case investigation forms, including the ability to add, modify, and reorder data fields.
*   **ECM-003:** The system shall allow an administrator to define new entity types (e.g., "Restaurant," "Event Venue," "Livestock Herd") and relationship types (e.g., "worked at," "attended," "owned by") relevant to an outbreak.

#### 3.1.2 Case Investigation and Management (CIM)
*   **CIM-001:** The system shall provide an interface for investigators to create a new case record for a person or animal.
*   **CIM-002:** The system shall present the event-specific, configured electronic questionnaire for data entry during a case investigation.
*   **CIM-003:** The system shall allow an investigator to link a case record to other entities (e.g., a specific location of exposure, a known contact, a household).

#### 3.1.3 Contact Tracing and Exposure Management (CTM)
*   **CTM-001:** The system shall provide functionality to generate a contact record from within a case investigation.
*   **CTM-002:** The system shall support many-to-many relationships, allowing a single contact to be linked to multiple source cases and a single case to be linked to multiple contacts.
*   **CTM-003:** The system shall provide a workflow to track the status of each contact (e.g., notified, monitored, lost to follow-up, cleared).
*   **CTM-004:** The system shall support the management of isolation/quarantine orders, including start/end dates and monitoring check-ins.

#### 3.1.4 Specimen and Laboratory Management (SLM)
*   **SLM-001:** The system shall record specimen collection details (collection date/time, site, collector, etc.).
*   **SLM-002:** The system shall maintain a chain of custody log for each specimen.
*   **SLM-003:** The system shall generate electronic lab test requests (orders) conforming to PHIN standards.
*   **SLM-004:** The system shall receive, parse, and store electronic lab results (ELR) messages, linking them to the correct specimen and case/contact record.

#### 3.1.5 Analysis, Visualization, and Reporting (AVR)
*   **AVR-001:** The system shall generate standard epidemiological curves (epi-curves) based on case onset dates.
*   **AVR-002:** The system shall generate geographical maps plotting case and contact locations.
*   **AVR-003:** The system shall produce line listings and aggregate summary reports for cases, contacts, and lab results.
*   **AVR-004:** The system shall allow users to export report data in standard formats (CSV, PDF, XLS).

#### 3.1.6 Data Exchange and Interoperability (DEI)
*   **DEI-001:** The system shall send and receive PHIN-compliant laboratory test orders and results (ELR) with external Laboratory Information Systems.
*   **DEI-002:** The system shall send and receive PHIN-compliant case reports and contact investigation messages with other public health jurisdictions.
*   **DEI-003:** The system shall import and export data files in standard formats (e.g., HL7, CSV, XML) for bulk data operations.

#### 3.1.7 Offline and Synchronization Operations (OSO)
*   **OSO-001:** The system shall provide a functional user interface for all core investigation and data entry tasks when the client device is disconnected from the central network.
*   **OSO-002:** Upon reconnection, the system shall automatically and securely synchronize all data created or modified offline with the central server, resolving conflicts based on configurable business rules.

### 3.2 Non-Functional Requirements

#### 3.2.1 Usability
*   **US-001:** A user proficient in public health workflows shall be able to complete a basic case investigation with minimal training (< 2 hours).
*   **US-002:** The system shall provide context-sensitive help and guidance for all configured data fields.

#### 3.2.2 Reliability & Availability
*   **RA-001:** The core system shall be available for use 99.5% of the time during standard business hours.
*   **RA-002:** A documented continuity of operations plan (COOP) must exist to guide manual processes when the system is unavailable.
*   **RA-003:** The system must prevent data corruption during normal use and synchronization.

#### 3.2.3 Performance
*   **PE-001:** The system shall support concurrent use by at least 200 users within a jurisdiction without significant degradation of response times (< 3 seconds for standard data entry actions).
*   **PE-002:** Data synchronization following a period of offline work shall complete within 5 minutes for a typical field investigator's daily data load.

#### 3.2.4 Supportability & Configurability
*   **SC-001:** The system must be configurable to add new data fields, entity types, and relationship types without requiring changes to the underlying application source code.
*   **SC-002:** The system must support multiple deployment models: centralized web-based, client-server, and disconnected field client.

#### 3.2.5 Security & Privacy
*   **SE-001:** The system shall employ role-based access control (RBAC) to restrict data and functionality based on user roles.
*   **SE-002:** All data transmissions, including synchronization, shall be encrypted using industry-standard protocols (e.g., TLS 1.2+).
*   **SE-003:** The system shall maintain an audit log of all user actions, including data creation, modification, viewing, and deletion.
*   **SE-004:** Data at rest in the central database and on field devices shall be encrypted.

### 3.3 Interface Requirements

#### 3.3.1 User Interfaces
*   The primary user interface shall be a web-based application compatible with current versions of major browsers (Chrome, Firefox, Edge).
*   The field/disconnected interface shall be a dedicated client application for Windows/macOS or a progressive web application (PWA).

#### 3.3.2 Hardware Interfaces
*   The system must be compatible with standard barcode scanners for specimen label processing in field and lab settings.

#### 3.3.3 Software/Communication Interfaces
*   **PHIN Lab Interface:** Bidirectional HL7 v2.5.1 (or later) messaging for lab orders/results.
*   **PHIN Case Reporting Interface:** PHIN-compliant XML-based messaging for case notification.
*   **Data Import/Export:** Support for CSV, XML, and JSON file formats.

## 4. Acceptance Criteria & Priorities

### 4.1 Priority
Requirements are prioritized as follows:
*   **P1 (Critical):** ECM-001, ECM-002, CIM-001, CIM-002, CTM-001, CTM-002, DEI-001, DEI-002, SC-001, SE-001, SE-002. These form the minimum viable product (MVP).
*   **P2 (High):** CIM-003, CTM-003, SLM-001, SLM-003, SLM-004, AVR-001, AVR-003, OSO-001, OSO-002.
*   **P3 (Medium):** ECM-003, CTM-004, SLM-002, AVR-002, AVR-004, SC-002.

### 4.2 Acceptance Approach
Formal acceptance of the system will be based on:
1.  Successful demonstration of all P1 functional requirements.
2.  Successful execution of end-to-end test scenarios for PHIN Key Performance Measures, specifically:
    *   The submission of a valid electronic lab test order from OMS to a simulated LIS.
    *   The receipt and processing of a valid electronic lab result from a simulated LIS into the correct OMS record.
    *   The generation and export of a PHIN-compliant case report message.
3.  Verification that the system meets the stated non-functional requirements for security, performance, and configurability.
