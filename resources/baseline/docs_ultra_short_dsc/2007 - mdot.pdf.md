## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the Data Use Analysis and Processing (DUAP) system. The DUAP system is a prototype research platform designed to investigate and evaluate the utility of Vehicle Infrastructure Integration (VII) data, integrated with other sources, to enhance transportation safety, mobility, and asset management for MDOT. This SRS serves as the authoritative specification for developers, testers, project managers, and stakeholders, and will be the basis for system design, implementation, and acceptance testing.

### 1.2 Scope
The DUAP system is a functional prototype for demonstration and assessment, not necessarily intended for sustained operational use. Its scope encompasses:
*   Ingesting data from multiple external sources (VII probe data, traffic management systems, weather stations, other telematics).
*   Processing raw data through computational algorithms to derive traffic metrics, detect incidents, and assess road conditions.
*   Managing data lifecycle through short-term caching and long-term archiving.
*   Disseminating processed data and alerts to external consumer systems and internal presentation services.
*   Providing web-based user interfaces for agency personnel to monitor conditions and access information.
*   Providing administrative services for system configuration and security.

Out of Scope:
*   Development of the external source systems (e.g., VII network, TMS, RWIS).
*   Long-term, 24/7 operational support and maintenance beyond the prototype phase.
*   Direct control of field devices (e.g., traffic signals, dynamic message signs).

## 2. Overall Description

### 2.1 Product Perspective
DUAP is a middleware processing and analysis platform within MDOT's broader VII research ecosystem. It acts as a central hub, sitting between external data providers (VII network, TMS, RWIS, Clarus) and data consumers (MDOT presentation services, other agency systems). It is a self-contained system but depends on the availability and format of external data feeds.

### 2.2 Product Functions
The core functions of the DUAP system are:
1.  **Data Collection:** Ingest streaming and batch data from heterogeneous external sources.
2.  **Data Caching:** Temporarily store incoming data in a high-performance cache for immediate access.
3.  **Data Processing:** Apply configurable algorithms to raw data to generate derived metrics, events (incidents), and condition assessments.
4.  **Data Archiving:** Persist both raw and processed data to long-term storage for historical analysis.
5.  **Data Publication:** Format and output processed data, alerts, and metrics to external systems and internal UIs.
6.  **User Interface:** Provide role-based web interfaces for monitoring, browsing, and querying system information.
7.  **System Administration:** Provide tools for configuring system parameters, managing users/security, and monitoring system health.

### 2.3 User Characteristics
| User Role | Description | Key Tasks | Skill Level |
| :--- | :--- | :--- | :--- |
| **Traffic Operator** | MDOT staff monitoring real-time traffic. | View real-time traffic metrics, incident alerts, and camera feeds (if integrated). | Proficient with traffic management software. |
| **Maintenance Staff** | Personnel responsible for road maintenance. | View road condition assessments, weather data, and asset status to plan activities. | Familiar with maintenance management concepts. |
| **Asset Manager** | Personnel managing transportation assets. | Access historical and current condition data for infrastructure. | Analytical, uses data for decision-making. |
| **System Administrator** | IT staff managing the DUAP system. | Configure data sources/algorithms, manage user accounts, monitor logs, ensure system uptime. | Advanced IT and system administration skills. |
| **Data Analyst/Researcher** | Personnel evaluating VII data utility. | Query archived raw and processed data for analysis and report generation. | Advanced data analysis skills. |

*All users require authenticated system access.*

### 2.4 Constraints
1.  **Geospatial:** The system must use the **Michigan Geographic Framework (MGF)** for all geo-referencing.
2.  **Database:** Database requests must be handleable via **standard SQL**.
3.  **Prototype Nature:** The system is a research prototype; design trade-offs may favor flexibility and speed of development over industrial-grade robustness.
4.  **Regulatory:** The system shall conform to all applicable IT standards established by the **Michigan Department of Information Technology (MDIT)**.

### 2.5 Assumptions and Dependencies
#### Assumptions
1.  Incoming VII and integrated data are "near real-time"; the DUAP applications must be designed to handle inherent data latency and quality variations.
2.  The utility of derived data is dependent on the penetration rate of VII-equipped vehicles and roadside equipment, which is outside DUAP's control.
3.  Authorized users will have standard modern web browsers.

#### Dependencies
1.  The successful operation of DUAP is dependent on the **availability and continuity of data feeds** from the VII Proof of Concept network and other third-party sources (TMS, RWIS, Clarus). These sources may have their own use limitations or availability schedules.
2.  **MDOT** is responsible for establishing and providing the user authorization policies and roles that the DUAP system will enforce.

## 3. Specific Requirements

### 3.1 External Interface Requirements
#### 3.1.1 User Interfaces
*   **UI.1 (H):** The system shall provide a **web-based user interface** accessible via standard browsers (Chrome, Firefox, Edge).
*   **UI.2 (H):** The interface shall provide distinct **views/dashboards** tailored for Traffic Operators, Maintenance Staff, and Asset Managers.
*   **UI.3 (M):** The interface shall include map-based visualization of traffic flow, incident locations, weather conditions, and asset status.

#### 3.1.2 Hardware Interfaces
*   **HW.1 (M):** The system shall be deployable on standard MDOT-approved server hardware.

#### 3.1.3 Software Interfaces
*   **SI.1 (H):** The system shall interface with the **VII Proof of Concept network** to receive probe vehicle data (format TBD by VII).
*   **SI.2 (H):** The system shall interface with one or more **Traffic Management Systems (TMS)** to receive sensor and incident data.
*   **SI.3 (H):** The system shall interface with **Road Weather Information Systems (RWIS)** and the **Clarus** national weather system.
*   **SI.4 (H):** The system shall output processed data and alerts to **MDOT's presentation services**.
*   **SI.5 (M):** The system shall be capable of outputting data in the **SAE J2354 XML** format for consumption by other standardized systems.

#### 3.1.4 Communications Interfaces
*   **CI.1 (H):** The system shall support standard internet protocols (TCP/IP, HTTP/S, FTP/S) for data exchange with external interfaces.

### 3.2 Functional Requirements
#### 3.2.1 Data Collection & Ingestion
*   **FUN-1 (H):** The system shall collect probe vehicle data (position, speed, heading, timestamp) from the VII interface.
*   **FUN-2 (H):** The system shall collect traffic data (volume, speed, occupancy) from TMS interfaces.
*   **FUN-3 (H):** The system shall collect weather and road condition data (precipitation, temperature, friction) from RWIS/Clarus interfaces.
*   **FUN-4 (M):** The system shall be configurable to accept new data source definitions (format, protocol, frequency) via administrative services.

#### 3.2.2 Data Caching
*   **FUN-5 (H):** The system shall cache all incoming dynamic data records upon receipt.
*   **FUN-6 (H):** Each cached data record **must include** source identifier, geo-reference (MGF), and timestamp.
*   **FUN-7 (H):** Cached data shall be made available for access **immediately** after being stored.
*   **FUN-8 (H):** The system shall retain dynamic data in the cache for a **minimum of one week** before purge/archive.
*   **FUN-9 (M):** The cache retention period shall be configurable by a system administrator.

#### 3.2.3 Data Processing
*   **FUN-10 (H):** The system shall apply algorithms to raw probe and traffic data to derive **traffic metrics** (e.g., segment speed, travel time).
*   **FUN-11 (H):** The system shall apply algorithms to detect potential **incidents** (e.g., sudden speed drops, stopped vehicles).
*   **FUN-12 (H):** The system shall apply algorithms to integrate weather and probe data to assess **road surface conditions** (e.g., wet, icy).
*   **FUN-13 (M):** The system shall allow an administrator to enable, disable, and configure parameters for processing algorithms.

#### 3.2.4 Data Archiving
*   **FUN-14 (H):** The system shall archive all **raw data** received from external sources to long-term storage.
*   **FUN-15 (H):** The system shall archive all **processed data** (metrics, incidents, conditions) to long-term storage.
*   **FUN-16 (M):** Archived data shall be queryable using **standard SQL**.

#### 3.2.5 Data Publication & Output
*   **FUN-17 (H):** The system shall format and publish processed data (metrics, incidents, conditions) to the MDOT presentation service interface.
*   **FUN-18 (M):** The system shall generate and publish alerts (e.g., for new incidents) to configured external systems.
*   **FUN-19 (L):** The system shall be capable of generating data extracts in standard formats (e.g., CSV, SAE J2354 XML) on demand.

#### 3.2.6 User Interface Functions
*   **FUN-20 (H):** The system shall require user authentication (login) for all access to UI functions.
*   **FUN-21 (H):** The system shall present traffic operators with a real-time view of current traffic metrics and active incidents.
*   **FUN-22 (H):** The system shall present maintenance staff with current weather and road condition assessments.
*   **FUN-23 (M):** The system shall allow asset managers to query historical condition data for specific road segments.
*   **FUN-24 (M):** The system shall provide basic data filtering and search capabilities within all views.

#### 3.2.7 Administrative Services
*   **FUN-25 (H):** The system shall provide an administrative interface for a System Administrator to **create, modify, and delete user accounts**.
*   **FUN-26 (H):** The system shall allow an administrator to **assign access rights and roles** to users.
*   **FUN-27 (H):** The system shall **log all user access** (successful and failed) and major data transactions.
*   **FUN-28 (M):** The system shall provide tools to **configure and sequence** data ingestion, processing, and publication services.
*   **FUN-29 (M):** The system shall provide a view of system health and status (e.g., data feed connectivity, service status).

### 3.3 Non-Functional Requirements
#### 3.3.1 Performance Requirements
*   **PER-1 (H):** The system shall handle **continuously streaming data** from all configured sources without sustained backlog.
*   **PER-2 (H):** Data written to the cache shall be available for read access **within 5 seconds** of receipt.
*   **PER-3 (M):** The web interface shall load initial dashboard views for an authenticated user within **10 seconds**.

#### 3.3.2 Security Requirements
*   **SEC-1 (H):** System access shall be **restricted to authorized users** only.
*   **SEC-2 (H):** User passwords shall be stored using industry-standard hashing/encryption.
*   **SEC-3 (H):** An administrator shall manage all user rights and roles.
*   **SEC-4 (M):** The system shall implement role-based access control (RBAC) to limit UI functions and data visibility based on user role.
*   **SEC-5 (M):** All external data exchanges shall support secure protocols (e.g., HTTPS, FTPS) where provided by the external system.

#### 3.3.3 Reliability, Maintainability, and Supportability
*   **RMS-1 (H):** The system architecture shall be **flexible and modular** to allow new data sources, processing algorithms, and output formats to be added with minimal impact to existing components.
*   **RMS-2 (M):** The system shall be designed to be **scalable** to handle increased data volumes from a growing VII network.
*   **RMS-3 (M):** System configuration shall be stored externally (e.g., in files or a database) to allow changes without code modification.

#### 3.3.4 Data Management Requirements
*   **DATA-1 (H):** All geo-spatial data shall be referenced using the **Michigan Geographic Framework (MGF)**.
*   **DATA-2 (H):** The system shall maintain data provenance (source, receipt time) for all records.

### 3.4 Priority & Acceptance
Each requirement above is tagged with a priority:
*   **High (H):** Essential to the DUAP system's core mission of data collection, processing, and dissemination for research evaluation. Must be implemented for acceptance.
*   **Medium (M):** Important for usability, administration, and demonstrating full prototype capability. Should be implemented if possible.
*   **Low (L):** Useful enhancements that provide additional value but are not critical to core prototype function.

**Acceptance Approach:** The implemented DUAP system will be verified against this SRS. Acceptance will be granted upon successful demonstration and/or testing that proves the system fulfills the specified High-priority (H) requirements. Verification of Medium and Low-priority requirements will be documented but may not be mandatory for prototype acceptance.
