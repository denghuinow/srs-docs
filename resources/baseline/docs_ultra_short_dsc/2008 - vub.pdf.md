## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the Publications Management System (PMS). The intended audience includes project stakeholders, developers, testers, and project managers. This document will serve as the foundation for system design, implementation, and verification.

### 1.2 Scope
The PMS is a web-based application for managing a centralized database of academic bibliographic information and associated full-text publications (PDF/PS). The system will provide authorized users with capabilities to search, view, download, and upload publications, enforced through a granular access control model. The system is explicitly scoped to handle document files (PDF, PS) and will **not** support audio or video media.

### 1.3 Product Background and Positioning
The PMS is a standalone system developed for academic use within the Free University of Brussels (VUB). It is designed to be deployed on the existing university Linux server named 'Wilma'. The system must integrate seamlessly with a MySQL database for persistent data storage and operate under a standard web server environment.

## 2. Overall Description

### 2.1 Product Perspective
The PMS is a new, self-contained system. It will interface with the following external components:
*   **Web Server:** (e.g., Apache, Nginx) on the Wilma server to deliver the application.
*   **Database Server:** MySQL server for all structured data storage.
*   **Server OS:** Linux-based Wilma server.
*   **Client Browser:** User web browser supporting XHTML.

### 2.2 Product Functions
The core functions of the PMS are:
1.  **Publication Search:** Allow users to find publications using various criteria.
2.  **Publication Retrieval:** Enable viewing of bibliographic details and downloading of full-text files.
3.  **Publication Submission:** Allow authorized users to upload new publications, with system-assisted metadata extraction.
4.  **User & Permission Management:** Provide a hierarchy of user roles with distinct privileges.
5.  **System Administration:** Allow full configuration, user/group management, and data curation.

### 2.3 User Characteristics and Personas
| User Role | Description | Key Characteristics |
| :--- | :--- | :--- |
| **Guest** | A visitor to the system. | Can only access the registration and login pages. |
| **VUB-Network User** | A user connected from a VUB IP address. | Identified by network IP; can search and download publications without authentication. |
| **Member** | A registered, logged-in user. | Has explicit search and download rights for all publications. |
| **Publisher** | A member who contributes content. | Can upload new publications and edit the metadata of publications they own. |
| **Moderator** | A user with departmental oversight. | Can edit publication metadata within their assigned department or user group. |
| **Administrator** | A system super-user. | Has full control over all system functions, data, and user/group management. |

**Typical Scenario:** A researcher (acting as a Member/Publisher) searches the database for relevant papers, downloads several, and later uploads their own new publication, editing its details as needed.

### 2.4 Operating Environment
*   **Server:** Application must run on the designated 'Wilma' Linux server.
*   **Software Stack:** Must be developed in Ruby (without frameworks such as Rails), interfacing with MySQL and a web server (e.g., Apache via CGI or similar).
*   **Network:** Accessible via HTTP on TCP/IP port 80.

### 2.5 Design and Implementation Constraints
1.  **Technology:** The application core must be written in Ruby without utilizing full-stack frameworks (e.g., Ruby on Rails). Standard libraries are permitted.
2.  **Deployment:** Must be deployable and operable on the existing VUB 'Wilma' Linux server environment.
3.  **Interface Compliance:** The generated web interface must comply with the W3C XHTML 1.0 Transitional standard.
4.  **Database:** Must use MySQL as the primary data store.

### 2.6 Assumptions and Dependencies
*   **Assumption:** End-users have access to a modern web browser that supports XHTML rendering.
*   **Assumption:** The Wilma server, its MySQL database, and web server software will be available and maintained by VUB IT.
*   **Dependency:** The system is fully dependent on the continuous operation and connectivity of the Wilma server and its MySQL database service.

## 3. Specific Requirements

### 3.1 External Interface Requirements

#### 3.1.1 User Interfaces
*   **Primary Interface:** A web-based interface accessible via standard browsers (Chrome, Firefox, Safari, Edge).
*   **Standard Compliance:** All rendered pages must validate against the W3C XHTML 1.0 Transitional standard.
*   **Key Pages:** Shall include Login, Registration, Search, Publication Detail, Upload, User Management (Admin), and System Configuration (Admin) pages.

#### 3.1.2 Hardware Interfaces
None. The system runs entirely on the Wilma server hardware.

#### 3.1.3 Software Interfaces
*   **SI-01: Database Interface:** The system shall interface with a MySQL database using the standard Ruby `mysql` library or equivalent.
*   **SI-02: Web Server Interface:** The Ruby application shall execute as a CGI script or equivalent module within the host web server (e.g., Apache).

#### 3.1.4 Communication Interfaces
*   **CI-01:** The system shall communicate with client browsers using HTTP/1.1 over TCP/IP, primarily on port 80.

### 3.2 Functional Requirements

#### 3.2.1 Authentication & Authorization Module
*   **FR-AA-01 (Critical):** The system shall allow a Guest to register a new account by providing a unique username, email, and password.
*   **FR-AA-02 (Critical):** The system shall allow registered users to log in using their username and password.
*   **FR-AA-03 (Critical):** The system shall automatically identify and grant VUB-Network User privileges to any request originating from a predefined set of VUB IP addresses, without requiring login.
*   **FR-AA-04 (Sufficient):** The system shall enforce the role-based privilege hierarchy (Guest < VUB-Network User < Member < Publisher < Moderator < Administrator) for all actions.

#### 3.2.2 Publication Search & Retrieval Module
*   **FR-SR-01 (Critical):** The system shall provide a search interface allowing users to query publications by keyword(s) matching title, author, abstract, and other bibliographic fields.
*   **FR-SR-02 (Critical):** The system shall allow filtering of search results by author, publication date range, and department/group.
*   **FR-SR-03 (Critical):** The system shall display a list of search results showing core details (title, authors, year).
*   **FR-SR-04 (Critical):** The system shall provide a detailed view for a single publication, displaying all stored bibliographic metadata.
*   **FR-SR-05 (Critical):** The system shall allow users with download rights (VUB-Network User, Member, Publisher, Moderator, Admin) to download the full-text file associated with a publication.

#### 3.2.3 Publication Upload & Management Module
*   **FR-PM-01 (Sufficient):** The system shall allow Publisher, Moderator, and Administrator users to upload new publication files (PDF/PS).
*   **FR-PM-02 (Sufficient):** During upload, the system shall attempt to automatically extract bibliographic metadata (e.g., title, author, abstract) from the header of the uploaded PDF/PS file.
*   **FR-PM-03 (Sufficient):** The user uploading the publication shall be presented with a form pre-populated with extracted data for verification and completion before final submission.
*   **FR-PM-04 (Sufficient):** A Publisher user shall be able to edit the bibliographic metadata of publications they have uploaded.
*   **FR-PM-05 (Sufficient):** A Moderator user shall be able to edit the bibliographic metadata of any publication assigned to their department/group.
*   **FR-PM-06 (Sufficient):** An Administrator user shall be able to edit or delete any publication.

#### 3.2.4 Administration Module
*   **FR-ADM-01 (Sufficient):** The system shall provide an interface for Administrators to create, view, modify, and disable user accounts.
*   **FR-ADM-02 (Sufficient):** The system shall provide an interface for Administrators to create, modify, and delete user groups/departments and assign users (including Moderators) to them.
*   **FR-ADM-03 (Sufficient):** The system shall provide an interface for Administrators to modify core system configuration settings.
*   **FR-ADM-04 (Optional):** The system shall provide a Command Line Interface (CLI) for Administrators with local server access to perform key administrative functions (e.g., bulk user import, database integrity check).

### 3.3 Non-Functional Requirements

#### 3.3.1 Security Requirements
*   **NFR-SEC-01 (Critical):** All user passwords shall be hashed using a strong, salted cryptographic hash function (e.g., bcrypt) before storage in the database. Plain-text passwords must never be stored.
*   **NFR-SEC-02 (Critical):** Authentication sessions shall be managed securely (e.g., using session tokens). Passwords transmitted during login shall be encrypted in transit (via HTTPS is implied as best practice, though port 80/HTTP is specified as a constraint).
*   **NFR-SEC-03 (Critical):** The system shall strictly enforce access control rules, preventing users from performing actions outside their privilege level (e.g., a Member cannot access upload pages, a Publisher cannot edit others' publications).

#### 3.3.2 Availability Requirements
*   **NFR-AVL-01 (Critical):** The application shall be available for use whenever the host Wilma server and its essential services (web server, MySQL) are available. Target uptime is congruent with Wilma server uptime.

#### 3.3.3 Maintainability Requirements
*   **NFR-MNT-01 (Sufficient):** The system shall be designed in a modular fashion, separating concerns (e.g., database logic, business logic, presentation logic) to facilitate future maintenance and updates.
*   **NFR-MNT-02 (Sufficient):** Procedures shall be established for regular backup of the MySQL database to prevent data loss.

#### 3.3.4 Compliance Requirements
*   **NFR-COM-01 (Sufficient):** All dynamically generated web pages shall comply with the W3C XHTML 1.0 Transitional standard.

### 3.4 Priority and Acceptance
Requirements are categorized by priority to guide development phases:

*   **Critical:** Must be implemented and functional in the first working prototype. These form the minimum viable product (MVP).
*   **Sufficient:** Must be implemented and functional for the final product delivery. These complete the core scope.
*   **Optional:** May be implemented if time and resources permit. Desirable but not mandatory for acceptance.

**Acceptance Approach:** Formal acceptance of the system will be based on verification against the externally testable requirements outlined in this SRS, particularly the Functional and key Non-Functional requirements. Test cases will be derived directly from these requirements.
