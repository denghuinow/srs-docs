# Software Requirements Specification (SRS)
## HVAC Automated Diagnostic Tool (HADT)
**Version:** 1.0
**Date:** October 26, 2023
**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the HVAC Automated Diagnostic Tool (HADT). It is intended for use by the project stakeholders, including developers, testers, project managers, and end-users, to ensure a common understanding of the system to be developed.

#### 1.2 Scope
The HADT is a standalone software application that automates the detection and identification of operational faults in Heating, Ventilation, and Air Conditioning (HVAC) subsystems—specifically chillers, cooling towers, and boilers. The system processes sensed data (real-time or historical) and fixed configuration data to execute diagnostic algorithms derived from expert manual practices.

**In-Scope:**
*   Automated fault detection for specified HVAC subsystems.
*   Data acquisition from real-time sources and batch files.
*   Data validation and storage.
*   Display of diagnostic results via a structured graphical user interface (GUI).
*   User authentication and role-based access control.
*   Administrative configuration of system parameters and diagnostic rules.
*   Logging of diagnostics and system errors.

**Out-of-Scope:**
*   Direct control of HVAC equipment.
*   Design or simulation of new HVAC systems.
*   User-defined custom analytical algorithms.
*   Repair recommendations or maintenance scheduling automation.
*   Data acquisition hardware (interfaces only).

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **HVAC:** Heating, Ventilation, and Air Conditioning.
*   **HADT:** HVAC Automated Diagnostic Tool.
*   **GUI:** Graphical User Interface.
*   **Sensed Data:** Time-series measurements from HVAC units (e.g., temperature, current, power).
*   **Fixed Data:** Static configuration parameters of the HVAC system and diagnostic thresholds (e.g., setpoints, schedules, equipment ratings).
*   **Admin:** Administrator user role with full system privileges.
*   **General User:** Standard user role with read-only access to diagnostics.

### 2. Overall Description

#### 2.1 Product Perspective
The HADT is a standalone, monitor-only software product that fits into an existing building management ecosystem. It interfaces with external data acquisition systems and acts upon existing HVAC units but does not replace a Building Management System (BMS). Its position is as an analytical layer on top of data sources.

#### 2.2 Product Functions (Summary)
1.  Acquire and validate HVAC sensed data from streams or files.
2.  Execute diagnostic algorithms for chiller, cooling tower, and boiler subsystems.
3.  Determine operational states (On/Off/Steady/Transient) of key components.
4.  Present current and historical diagnostic results through a hierarchical GUI.
5.  Provide administrative functions for system configuration.
6.  Securely authenticate users and enforce role-based permissions.
7.  Log all diagnostic outcomes and system events persistently.

#### 2.3 User Characteristics
| User Class | Expertise | Primary Goal |
| :--- | :--- | :--- |
| **Building Operator / Facilities Manager** | Moderate computer skill; Strong HVAC knowledge. | Daily monitoring to identify maintenance priorities. |
| **HVAC Service Technician** | Varying computer skill; Expert HVAC knowledge. | Diagnose specific faults during repair or remote support sessions. |
| **Energy Service Provider** | Moderate computer skill; Strong HVAC & energy knowledge. | Monitor multiple sites for inefficiencies to optimize service dispatch. |
| **Building Operator Supervisor** | Moderate computer skill; Strong HVAC knowledge. | Review diagnostics to assign and prioritize team workloads. |
| **System Administrator** | Strong computer skill; Basic HVAC knowledge. | Configure system, manage users, and set diagnostic parameters. |

#### 2.4 Constraints
*   **Platform:** Must be developed for and run on Microsoft Windows-compatible operating systems.
*   **Architecture:** Must be designed to allow for the future addition of diagnostic modules for other HVAC subsystems.
*   **Phase 1 Focus:** The initial release must fully support chiller and cooling tower diagnostics. Boiler diagnostics are a high-priority follow-on.
*   **Algorithm Dependency:** Diagnostic accuracy is inherently dependent on the correctness of the underlying expert rules being automated.

#### 2.5 Assumptions and Dependencies
*   Users possess a fundamental understanding of HVAC principles and terminology.
*   The system will receive valid, correctly formatted sensed and fixed data from its interfaces. Garbage data or communication failures will impede functionality.
*   The system's external data sources (acquisition devices, file formats) are stable and well-defined.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Data Acquisition & Validation (DA)
*   **DA-1:** The system shall acquire sensed data in real-time from a configured data acquisition interface.
*   **DA-2:** The system shall acquire sensed data from formatted ASCII text files for batch processing.
*   **DA-3:** The system shall validate all incoming sensed data against configurable expected minimum and maximum ranges.
*   **DA-4:** The system shall store all validated sensed data with a precision of three significant figures.
*   **DA-5:** The system shall convert all sensed data to specified engineering units (°F, Amps, etc.) if not already provided in them.

##### 3.1.2 Diagnostic Processing (DP)
*   **DP-1:** The system shall determine the operational status (On, Off, Steady, Transient) for key components (compressors, pumps, fans) from current/power data.
*   **DP-2:** **Chiller Diagnostics:** The system shall detect and identify the following chiller faults:
    *   Schedule compliance errors.
    *   Supply water temperature control issues.
    *   Abnormal compressor cycling.
    *   Improper equipment interlocks.
*   **DP-3:** **Cooling Tower Diagnostics:** The system shall detect and identify the following cooling tower faults:
    *   Sump temperature control issues.
    *   Abnormal fan cycling.
    *   Approach temperature problems.
    *   Fan staging issues.
    *   Range problems.
*   **DP-4:** **Boiler Diagnostics:** The system shall detect and identify the following boiler faults:
    *   Shutoff schedule non-compliance.
    *   Hot water temperature control issues.
    *   Excessive boiler cycling.
*   **DP-5:** The diagnostic algorithms shall not execute if any required input data point is missing or invalid. The user shall be notified of the deficiency.
*   **DP-6:** All diagnostic results (fault detected/not detected, fault type, timestamp, relevant data values) shall be written to permanent storage.

##### 3.1.3 User Interface & Presentation (UI)
*   **UI-1:** The system shall provide a graphical Windows application with the following six main windows:
    1.  **Main Window:** Application entry point with navigation.
    2.  **Configuration Window:** For Admin users to set parameters (see CFG requirements).
    3.  **Subsystems Window:** Overview of monitored HVAC subsystems (Chillers, Towers, Boilers).
    4.  **Condition Window:** Detailed view of a selected subsystem's current state and active diagnostics.
    5.  **Diagnostic Information Window:** Detailed explanation of a selected identified fault.
    6.  **Diagnostic History Window:** Browsable history of past diagnostic results for a selected subsystem.
*   **UI-2:** Navigation between windows shall follow a strict hierarchy: Main -> Subsystems -> (Condition | Diagnostic History) -> Diagnostic Information.
*   **UI-3:** The interface shall be usable by individuals with varying computer expertise but a good understanding of HVAC systems.

##### 3.1.4 Configuration & Administration (CFG)
*   **CFG-1:** An Administrator shall be able to start and stop the real-time diagnostic monitoring process.
*   **CFG-2:** An Administrator shall be able to configure all fixed data parameters (e.g., equipment schedules, setpoints, interlock logic).
*   **CFG-3:** An Administrator shall be able to modify default validation ranges for sensed data.
*   **CFG-4:** An Administrator shall be able to adjust the sensitivity thresholds for specific diagnostic algorithms.

##### 3.1.5 Security & User Management (SEC)
*   **SEC-1:** The system shall require user authentication via a unique User ID and password.
*   **SEC-2:** The system shall distinguish between at least two user roles: "General User" and "Administrator".
*   **SEC-3:** A General User shall only have permission to browse diagnostic results (read-only access).
*   **SEC-4:** An Administrator shall have all General User permissions plus the ability to start/stop diagnostics and access the Configuration Window.

##### 3.1.6 Logging & Support (LOG)
*   **LOG-1:** All diagnostic results (per DP-6) shall be logged.
*   **LOG-2:** All significant system errors (e.g., module failures, interface errors) shall be logged to permanent storage with the following details: timestamp, module name, function name, and error description.

#### 3.2 Non-Functional Requirements

##### 3.2.1 Usability
*   The user interface shall be designed for clarity and efficiency for the primary user classes (Building Operators, Technicians). HVAC terminology shall be used correctly and consistently.

##### 3.2.2 Reliability
*   The system shall have an uptime of 99.5% during scheduled building operational hours when running in monitoring mode.
*   As stated in **DP-5**, the system shall fail-safe by not producing diagnostics with incomplete data.

##### 3.2.3 Performance
*   The system shall process incoming real-time data points and update current diagnostic status with a latency of less than 10 seconds from data receipt.
*   Loading and displaying one year of historical diagnostic results for a single subsystem shall take less than 15 seconds.

##### 3.2.4 Supportability
*   The software architecture shall be modular to allow for the addition of new diagnostic algorithms for other HVAC subsystems with minimal impact on existing code.
*   Log files shall be in a plain text, human-readable format to facilitate debugging.

##### 3.2.5 Implementation Constraints
*   The application must be compatible with current and immediately previous versions of Microsoft Windows (e.g., Windows 10/11).

#### 3.3 Interface Requirements

##### 3.3.1 Hardware Interfaces
*   **HI-1:** The system shall interface with industry-standard data acquisition devices (e.g., via Modbus TCP/IP, BACnet IP) to read sensed data. Specific drivers/protocols will be defined during design.

##### 3.3.2 Software Interfaces
*   **SI-1:** **Data File Interface:** The system shall read historical sensed data from ASCII text files with the following format:
    ```
    TIMESTAMP, SENSOR_ID, VALUE, UNITS
    2023-10-26 14:30:00, CH1_TEMP, 45.2, F
    ```
*   **SI-2:** **Database:** The system shall store configuration, historical data, and logs in a relational database (e.g., SQLite, Microsoft SQL Server Express).

##### 3.3.3 Communications Interfaces
*   **CI-1:** The system shall communicate with data acquisition hardware over standard Ethernet networks using specified protocols (see HI-1).

### 4. Priority and Acceptance

#### 4.1 Requirement Priority
| Priority Level | Requirements / Features |
| :--- | :--- |
| **Highest** | DA-1 to DA-5, DP-1, DP-2, DP-3, DP-5, DP-6, UI-1, UI-2, LOG-1 |
| **High** | SEC-1 to SEC-4, CFG-1 to CFG-4, DP-4 (Boiler Diagnostics) |
| **Medium** | CFG-4 (Sensitivity adjustment), UI-3 (Advanced history browsing features) |

#### 4.2 Acceptance Criteria
The software will be considered acceptable when it successfully passes validation tests demonstrating:
1.  Correct acquisition and validation of data from both real-time and file interfaces.
2.  Accurate identification of all specified chiller and cooling tower faults using provided test data sets that simulate fault conditions.
3.  Correct enforcement of user roles and permissions.
4.  Proper functioning of all administrative configuration tasks.
5.  Correct logging of all diagnostic results and system errors.
6.  Adherence to all specified non-functional requirements, particularly platform compatibility and interface behavior.
