### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the 3D Biological Data Visualization Tool. It is intended to serve as a comprehensive guide for developers, testers, project managers, and stakeholders to ensure a common understanding of the system's capabilities, constraints, and objectives. The primary audience for this SRS is the development team.

#### 1.2 Scope
The system is a specialized 3D visualization tool designed to plot biological data points from a pre-formatted input file. Its core purpose is to enable interactive investigation and comparison of data attributes within a manipulable three-dimensional space. The system is responsible for accurate visual rendering, user interaction with data points, and view manipulation. It explicitly **does not** include functionality for generating, cleaning, or statistically pre-processing raw biological data. Data preparation is the responsibility of the user, using external tools (e.g., Matlab).

#### 1.3 Product Background & Positioning
Existing visualization solutions are deemed insufficient for the specific research needs of the NIMR parasitology department. This product is developed to fill that gap, with its primary merit being research utility. It is envisioned as a complementary tool to be used in conjunction with data generation and analysis software, deployed via a standard web server (e.g., Apache Tomcat) to ensure accessibility within the research environment.

#### 1.4 Definitions, Acronyms, and Abbreviations
*   **NIMR:** National Institute for Medical Research
*   **3D Grid:** The three-dimensional Cartesian coordinate system within which data points are plotted.
*   **Data Point:** A single entity from the input file, representing a biological sample (e.g., a protein), defined by its coordinates and attributes.
*   **Cluster Attribute:** A specific data field used to categorize points, determining their visual color.
*   **Re-orient:** To pan or translate the view of the 3D grid without rotation.

### 2. Overall Description

#### 2.1 Product Perspective
This is a new, self-contained software component. It operates as a server-side application accessed via a client's web browser equipped with Java support. The system interacts with two key external entities:
1.  **Users:** Via a Java applet or application interface in the browser.
2.  **Data Files:** Formatted text files provided by the user.

#### 2.2 Product Functions (High-Level Summary)
1.  Parse and validate user-supplied, tab-delimited data files.
2.  Render up to 2000 discrete data points within an interactive 3D coordinate system.
3.  Apply color mapping to points based on a specified cluster attribute.
4.  Provide interactive controls for rotating, zooming, and panning the 3D view.
5.  Display point information (name or full details) in response to user mouse actions.
6.  Enable selection of multiple points for simultaneous label display.
7.  Accurately label the axes of the 3D grid based on input file headers.

#### 2.3 User Characteristics and Personas
| Persona / Role | Primary Goal | Skill Level |
| :--- | :--- | :--- |
| **Identifier** | To supply a dataset and quickly locate points of interest within the 3D space. | High domain knowledge, moderate computing skills. |
| **Investigator** | To retrieve and examine the complete set of attributes for specific data points. | High domain knowledge, basic computing skills. |
| **Demonstrator** | To manipulate the view to effectively present and explain data patterns to an audience. | Variable domain knowledge, basic computing skills. |
*All users are assumed to have basic competency with their operating system, a Java-enabled web browser, mouse/keyboard operation, file management, and command-line input.*

#### 2.4 Operating Environment
*   **Software Environment:**
    *   **Server:** Application must run on Apache Tomcat or equivalent Java servlet container.
    *   **Client:** Must be accessible from a standard web browser with Java Runtime Environment (JRE) support.
*   **Hardware Environment:**
    *   Must be operational on a mid-range personal computer (contemporary to 2005 specifications).
    *   **Supported OS (Server & Client):** Microsoft Windows (98, 2000, NT, XP) and Linux/Solaris.

#### 2.5 Design and Implementation Constraints
1.  **Architecture:** Execution is constrained to server-side processing; the client is a "thin" Java viewer.
2.  **Language:** Must be implemented using technologies compatible with a Java-based web deployment stack.
3.  **Deadline:** The system must be developed and ready for inclusion in a scientific paper by **March 2005**.
4.  **Input Dependency:** The system depends entirely on users providing correctly formatted tab-delimited text files.

#### 2.6 Assumptions and Dependencies
*   Users possess the ability to create correctly formatted input files as specified.
*   The hosting web server (e.g., Tomcat) is properly configured and maintained by the IT department.
*   Client machines have a compatible, up-to-date Java Runtime Environment installed.

### 3. Specific Requirements

#### 3.1 External Interface Requirements

##### 3.1.1 User Interfaces
*   **Primary UI:** A Java-rendered window within a web browser, containing:
    *   A main viewport displaying the 3D grid and data points.
    *   Axis labels (X, Y, Z) derived from the input file.
    *   A minimal interface for potential future controls (e.g., reset view).
*   **Colour Scheme:** Black graphical elements (axes, points, text) on a white background to ensure clarity for printed screenshots.
*   **Interaction Model:** The interface shall be fully operable using only a standard mouse and keyboard.

##### 3.1.2 Hardware Interfaces
None specified beyond the requirement to run on a mid-range PC.

##### 3.1.3 Software Interfaces
*   **Input File Interface:** The system shall accept a single, plain-text input file with the following characteristics:
    *   Format: Tab-delimited values.
    *   First row: Header row containing column names.
    *   Required columns: At least three columns containing numerical data for X, Y, and Z coordinates.
    *   Required column: One column containing a "cluster" identifier for color mapping.
    *   Required column: One column containing a unique "name" for each data point.
*   **Web Server Interface:** The application shall be deployable as a Java web application (WAR file) on Apache Tomcat version [Specify version, e.g., 5.x] or equivalent.

##### 3.1.4 Communications Interfaces
HTTP/HTTPS for serving the Java application to the client browser.

#### 3.2 Functional Requirements

##### **FR-1: Data File Input and Parsing**
*   **FR-1.1:** The system shall allow the user to specify the location of a tab-delimited data file for input.
*   **FR-1.2:** The system shall parse the input file, validating its format and identifying the coordinate (X,Y,Z), cluster, and name columns.
*   **FR-1.3:** The system shall handle up to 2000 data records (rows) from the input file.

##### **FR-2: 3D Visualization Rendering**
*   **FR-2.1:** The system shall plot each valid data point as a distinct graphical marker within a 3D Cartesian grid.
*   **FR-2.2:** The system shall automatically scale the grid axes to encompass all plotted data points.
*   **FR-2.3:** The system shall label the X, Y, and Z axes with the corresponding column names from the input file header.

##### **FR-3: Data Point Coloring**
*   **FR-3.1:** The system shall color each data point based on the value of its designated "cluster" attribute.
*   **FR-3.2:** The system shall use a distinct, easily differentiable color for each unique cluster value.

##### **FR-4: View Manipulation**
*   **FR-4.1:** The user shall be able to rotate the 3D grid freely along all axes by clicking and dragging with the mouse.
*   **FR-4.2:** The user shall be able to zoom the view in and out using the mouse scroll wheel or a keyboard shortcut (e.g., Ctrl + Drag).
*   **FR-4.3:** The user shall be able to pan (re-orient) the grid by dragging with a modifier key pressed (e.g., Shift + Drag).

##### **FR-5: Data Point Interaction**
*   **FR-5.1:** A **single mouse click** on a data point shall cause its "name" attribute to be displayed prominently near the point (e.g., as a tooltip or anchored label).
*   **FR-5.2:** A **double mouse click** on a data point shall open a separate panel or dialog displaying all attributes (all column values) for that specific data point.
*   **FR-5.3:** The user shall be able to select **multiple data points** (e.g., via Ctrl+Click or a lasso selection tool). The names of all selected points shall be displayed simultaneously.

#### 3.3 Performance Requirements
*   **PER-1: Startup Time:** The application shall load, parse a data file, and render the initial 3D view within **30 seconds**. This time is dependent on the number of data points, with 2000 points representing the maximum load case.
*   **PER-2: Interaction Responsiveness:** Any user interaction with a data point (click, double-click) shall trigger the corresponding display action with a delay of **no more than 2 seconds**.
*   **PER-3: View Manipulation Fluidity:** Rotation, zoom, and pan operations shall provide visual feedback at a rate perceived as smooth and continuous by the user (target: >10 frames per second during manipulation).

#### 3.4 Non-Functional Requirements

##### **3.4.1 Usability**
*   **US-1:** The interface shall be intuitive for scientists with basic computer literacy, requiring minimal formal training.
*   **US-2:** All visualization and interaction functions shall be achievable using only a mouse and keyboard.
*   **US-3:** The default color scheme for the application interface shall be black text and graphics on a white background.

##### **3.4.2 Reliability**
*   **REL-1:** The system shall not crash due to malformed data files. It shall reject the file and provide a clear error message to the user.
*   **REL-2:** The system shall maintain state and be stable during continuous user interaction for a period of at least 8 hours.

##### **3.4.3 Portability**
*   **PORT-1:** The application must be fully functional on both the Windows (98/2000/NT/XP) and Linux/Solaris operating systems, as specified in Section 2.4.

#### 3.5 Priority and Acceptance
*   **Critical (P0):** FR-2 (3D Plotting), FR-4 (View Manipulation), FR-5.1/5.2 (Point Interaction), PORT-1 (Cross-Platform). These are mandatory for the March 2005 deadline.
*   **High (P1):** FR-1 (Data Parsing), FR-3 (Coloring), FR-5.3 (Multi-select), PER-1 & PER-2 (Performance).
*   **Medium (P2):** PER-3 (Fluidity), US-3 (Print-friendly scheme).

**Acceptance Approach:** Formal acceptance will require successful execution of test cases demonstrating:
1.  Correct visual rendering of multiple approved test data files.
2.  Adherence to all performance timing requirements (PER-1, PER-2) under maximum load.
3.  Full operational capability on designated Windows and Linux/Solaris test platforms.
4.  Satisfaction of all "Critical" and "High" priority functional requirements.
