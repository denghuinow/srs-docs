## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the ASPERA-3 Ground Data System, also known as the ASPERA-3 Processing and Archiving Facility (APAF). The purpose of this system is to reliably acquire, process, archive, and distribute scientific telemetry data from the ASPERA-3 instrument package aboard the ESA Mars Express spacecraft. The primary outputs are standardized IDFS data sets for the science team and PDS-compliant data packages for long-term archival with the NASA Planetary Data System.

### 1.2 Document Conventions
*   **Requirements:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a recommendation. "Will" indicates a statement of fact.
*   **Acronyms:**
    *   **APAF:** ASPERA-3 Processing and Archiving Facility
    *   **ASPERA-3:** Analyzer of Space Plasmas and Energetic Atoms
    *   **ESA:** European Space Agency
    *   **ESOC:** European Space Operations Centre
    *   **FMI:** Finnish Meteorological Institute
    *   **IDFS:** Instrument Data File Set (standardized science data product)
    *   **NISN:** NASA Integrated Services Network
    *   **PDS:** Planetary Data System (NASA)
    *   **SDD:** Software Design Document
    *   **SwRI:** Southwest Research Institute
    *   **UMU:** Umeå University

### 1.3 Project Scope
The APAF system encompasses the end-to-end pipeline from the receipt of raw telemetry to the delivery of validated scientific data products. This includes:
*   Automated acquisition and management of raw telemetry streams.
*   Processing of raw data into cleaned telemetry and higher-level IDFS data sets.
*   Long-term archival of all data at SwRI.
*   Web-based data visualization and access for the science team and public.
*   Distribution of data products to Co-Investigators.
*   Preparation and submission of data to the NASA PDS.

**Out of Scope:** The specific scientific algorithms used to convert raw instrument counts to physical units (e.g., density, temperature) are defined in external SDDs and are considered inputs to this system. The APAF provides the framework to execute these defined algorithms.

## 2. Overall Description

### 2.1 Product Perspective
The APAF is a component of the Mars Express ground segment. It is positioned as an intermediary data processing facility between the mission operations center (ESOC) and the final data consumers.

**System Interfaces:**
*   **Upstream:** ESOC delivers raw ASPERA-3 science telemetry and Mars Express spacecraft orbit/attitude telemetry via the NISN network.
*   **Downstream:**
    *   ASPERA-3 Co-Investigators receive distributed IDFS data sets.
    *   NASA PDS receives validated, formatted data packages.
    *   Science Team and Public access data via the `www.aspera-3.org` web server.

### 2.2 Product Functions
The core high-level functions of the APAF are:
1.  **Data Acquisition:** Automatically ingest telemetry streams from ESOC.
2.  **Telemetry Processing:** Convert raw telemetry into cleaned, time-ordered files.
3.  **Science Processing:** Generate IDFS data sets using sensor-specific algorithms.
4.  **Archival:** Store raw, intermediate, and processed data on the local SwRI archive.
5.  **Web Serving:** Host public and private websites for data display.
6.  **Data Distribution:** Package and deliver IDFS data sets to Co-Investigators.
7.  **PDS Submission:** Prepare, validate, and deliver PDS-compliant data bundles.

### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **ASPERA-3 Co-Investigator** | Scientist, expert in space physics. Located internationally. | Timely access to all processed data for scientific analysis. Ability to visualize data quickly via web. Secure access to pre-public data. |
| **APAF Operator** | SwRI technical staff. Trained in system operations. | Reliable, automated daily pipeline. Clear status monitoring and error alerts. Tools for manual intervention and reprocessing. |
| **General Public** | Students, educators, space enthusiasts. | Easy-to-understand visualizations of recent Mars plasma environment data. Non-technical explanations. |
| **NASA PDS** | Archival system. Automated ingestion protocols. | Data delivered in strict PDS format with complete, validated metadata. |

### 2.4 Operating Environment
*   **Hardware:** Designated UNIX-based servers (e.g., Sun Solaris, Linux) at SwRI for production and development.
*   **Software:** Operating System (e.g., Solaris 10, RHEL). Required services: FTP/SFTP server, Web server (Apache), Database (e.g., PostgreSQL), and standard development tools (C, IDL, Perl/Python).
*   **Networks:** Continuous connection to the NISN for ESOC data transfer. Internet connection for web serving and data distribution.

### 2.5 Design and Implementation Constraints
1.  `CON-001:` The system shall be developed and deployed on the designated UNIX hardware at SwRI.
2.  `CON-002:` The system development schedule must support mission operations, with core functionality ready prior to the Mars Express launch (June 2003).
3.  `CON-003:` All data processing algorithms shall adhere to the interfaces and definitions specified in the external Sensor SDDs.

### 2.6 Assumptions and Dependencies
*   **A-001:** ESOC will deliver telemetry data continuously via NISN according to agreed-upon schedules and formats.
*   **A-002:** The definitions for IDFS data sets and processing algorithms will be stable and provided by the instrument teams prior to integration.
*   **D-001:** The system is dependent on the external ESOC and FMI/UMU documents defining the telemetry format.
*   **D-002:** The system is dependent on the NASA PDS maintaining its data standards and submission interfaces.

## 3. External Interface Requirements

### 3.1 User Interfaces
*   `FR-010:` The system shall provide a public website at `www.aspera-3.org` with pre-defined displays of the most recent processed data (e.g., summary plots, mission status).
*   `FR-011:` The system shall provide a password-protected section of the website for Co-Investigators, offering advanced data search, display, and subsetting capabilities for all processed data.
*   `FR-012:` The system shall provide a web-based operator console for APAF Operators to monitor pipeline status, view logs, and initiate manual processes.

### 3.2 Hardware Interfaces
*   `FR-020:` The system shall interface with the SwRI-local archive storage system (e.g., RAID array/tape library) for permanent data storage.
*   `FR-021:` The system shall utilize the SwRI connection to the NISN network for telemetry acquisition.

### 3.3 Software Interfaces
*   `FR-030:` The system shall accept telemetry input files in the format specified by the ESOC/FMI/UMU Interface Control Document (ICD).
*   `FR-031:` The system shall produce IDFS data sets in the format and structure defined in the external IDFS Data Set Definition documents.
*   `FR-032:` The system shall produce PDS submission packages that comply with the NASA PDS Data Preparation Workbook and standards.
*   `FR-033:` The system shall distribute data to Co-Investigators via a standard protocol (e.g., SFTP, secure HTTP).

### 3.4 Communications Interfaces
*   `FR-040:` The system shall use FTP over NISN for automated telemetry acquisition from ESOC.
*   `FR-041:` The system shall use standard TCP/IP protocols (HTTP/HTTPS) for web server communication.

## 4. System Features

### 4.1 Feature 1: Telemetry Acquisition and Management
**Description:** Automatically acquire, verify, and catalog incoming raw telemetry files.

**Requirements:**
*   `FR-101:` The system shall automatically connect to the designated ESOC server via NISN at scheduled intervals to check for and retrieve new ASPERA-3 and S/C orbit/attitude telemetry files.
*   `FR-102:` The system shall perform a checksum/validation on retrieved files to confirm data integrity.
*   `FR-103:` The system shall generate and archive an intermediate "cleaned" telemetry file (time-sorted, duplicate-removed) if this product is not provided directly by ESOC.
*   `FR-104:` The system shall ingest cleaned telemetry files (from ESOC or internal generation) for input to the science processing pipeline.
*   `FR-105:` The system shall maintain a database cataloging all acquired raw and intermediate telemetry files with metadata (filename, acquisition time, time range, size, checksum).

### 4.2 Feature 2: Science Data Processing Pipeline
**Description:** Process cleaned telemetry through sensor-specific algorithms to produce standardized IDFS data sets.

**Requirements:**
*   `FR-201:` The system shall execute the processing algorithms defined in the external SDDs for each ASPERA-3 sensor (IMA, NPI, ELS, etc.) to convert cleaned telemetry into Level 1-2 IDFS data sets.
*   `FR-202:` The system shall merge spacecraft orbit and attitude data with science telemetry during processing to provide geophysical coordinates (e.g., latitude, longitude, altitude, MSO coordinates).
*   `FR-203:` The system shall log all processing steps, including algorithm versions, input files, and any warnings or errors encountered.
*   `FR-204:` The system shall store the final IDFS data sets in the designated archive directory structure.

### 4.3 Feature 3: Data Archival and Cataloging
**Description:** Provide long-term, managed storage for all system data products.

**Requirements:**
*   `FR-301:` The system shall archive all raw telemetry files received from ESOC.
*   `FR-302:` The system shall archive all intermediate cleaned telemetry files.
*   `FR-303:` The system shall archive all final IDFS data sets.
*   `FR-304:` The system shall maintain a searchable master catalog (database) of all archived products, linking raw data to processed derivatives.

### 4.4 Feature 4: Web-Based Data Access and Display
**Description:** Serve data visualizations and access to users via the internet.

**Requirements:**
*   `FR-401:` The public website shall display pre-generated summary plots and data from the most recent [e.g., 30 days] of operations without requiring authentication.
*   `FR-402:` The science team website shall require username/password authentication for access.
*   `FR-403:` Authenticated users shall be able to search for data by time range, sensor, and data product type.
*   `FR-404:` Authenticated users shall be able to generate custom plots and data listings from available IDFS data sets via the web interface.
*   `FR-405:` The web system shall restrict access to data marked as "proprietary" (pre-PDS release) to authenticated Co-Investigators only.

### 4.5 Feature 5: Data Distribution
**Description:** Package and deliver processed data to the science team.

**Requirements:**
*   `FR-501:` The system shall automatically package newly processed IDFS data sets (e.g., on a daily basis) for distribution.
*   `FR-502:` The system shall distribute the data packages to all registered Co-Investigators via a secure, automated method (e.g., SFTP push, or notification for pull).
*   `NFR-501:` **Performance:** The distribution to Co-Investigators shall occur within 24 hours of successful acquisition of the corresponding error-free telemetry.

### 4.6 Feature 6: PDS Preparation and Submission
**Description:** Prepare, validate, and submit data to the NASA Planetary Data System.

**Requirements:**
*   `FR-601:` The system shall provide tools to bundle a complete set of IDFS data sets (e.g., for a defined mission phase) with all required PDS metadata (labels, catalog files, documentation).
*   `FR-602:` The system shall include a validation step to check the PDS bundle for compliance with current PDS standards before submission.
*   `FR-603:` The system shall transmit the validated PDS bundle to the designated NASA PDS node.
*   `NFR-601:` **Compliance/Archival:** All data from a given time period shall be submitted to the PDS in a compliant form within 6 months of acquisition.

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   `NFR-001:` The daily processing pipeline (from telemetry receipt to IDFS generation) shall complete within 6 hours under nominal data loads to meet the 24-hour distribution target.
*   `NFR-002:` The web server shall deliver plot images and data listings to users with a latency of less than 10 seconds for standard queries.

### 5.2 Safety Requirements
*   Not applicable (ground-based data system).

### 5.3 Security Requirements
*   `NFR-010:` User authentication for the science team website shall be performed over an encrypted connection (HTTPS).
*   `NFR-011:` Passwords shall be stored using a strong, salted hashing algorithm.
*   `NFR-012:` Access to raw and processed data on the archive filesystem shall be restricted via UNIX file permissions to authorized system and operator accounts.

### 5.4 Software Quality Attributes
*   **Reliability:** `NFR-020:` The automated pipeline shall have a success rate of >99% for processing nominal telemetry. Errors shall be trapped, logged, and trigger operator alerts without causing a full system halt.
*   **Availability:** `NFR-021:` The web server and data distribution functions shall have 99% uptime during scheduled mission operations. The NISN connection is recognized as a single point of failure for acquisition.
*   **Maintainability:** `NFR-022:` The system shall be modular, with clear separation between data acquisition, processing, and delivery components to facilitate updates and bug fixes.
*   **Portability:** `NFR-023:` The core processing software shall be written to be portable across common UNIX-like environments (Solaris, Linux).

## 6. Other Requirements

### 6.1 Priorities
*   **Highest Priority:** Features 1, 2, and 5 (Daily Acquisition, Processing, and Distribution). The 24-hour delivery to the science team is critical for mission science.
*   **Mandatory:** Feature 6 (PDS Submission). Delivery to NASA PDS within 6 months is a contractually binding requirement.
*   **High Priority:** Features 3 and 4 (Archival and Web Access). Essential for team analysis and long-term data preservation.

### 6.2 Acceptance Criteria
Acceptance of the APAF system will be determined by successful demonstration of the following:
1.  End-to-end processing of simulated telemetry data sets, producing IDFS outputs that are verified against expected results provided by the instrument teams.
2.  Demonstration of the automated daily pipeline meeting the 24-hour delivery target in a test environment.
3.  Validation of a sample PDS data bundle by the NASA PDS node using their standard validation tools.
4.  Verification of all security and access control measures for the web interface.
