## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the Gaia Object Generator (GOG), a software simulator for the Gaia space mission. It is intended for use by the Gaia Data Processing and Analysis Consortium (DPAC) project managers, developers, testers, and scientific end-users to guide the development, verification, and validation of the system.

### 1.2 Scope
GOG is a software application that generates simulated catalog, main database, and final mission data products for the Gaia mission. It produces statistically equivalent, pre-processed data by applying user-selectable error models to simulated observations. The system does **not**:
*   Use actual Gaia mission telemetry.
*   Rely on detailed, low-level simulators (e.g., GASS, GIBIS).
*   Generate raw detector data.
*   Model source overlapping effects (e.g., crowding, blending).

The simulator operates on a source-by-source basis, generating data from either an internal Universe Model or an external input catalog, and outputs data in formats strictly defined by external Interface Control Documents (ICDs).

## 2. Overall Description

### 2.1 Product Perspective
GOG is a component of the broader Gaia Simulator project within the DPAC software ecosystem. It is a mid-level simulator positioned between fast, simplistic models and highly detailed, computationally expensive simulators. GOG relies on the shared **GaiaSimu** and **Gaia Tools** libraries for core astronomical and instrument models. Its primary external interfaces are with the file system (for configuration and data) and the aforementioned libraries.

### 2.2 Product Functions (Summary)
1.  Generate a list of astronomical sources from a built-in statistical Universe Model or ingest a user-provided catalog.
2.  For each source, simulate all Gaia transits over the mission lifetime.
3.  For each transit (epoch), generate simulated astrometric, photometric, and radial velocity observations.
4.  Apply configurable instrumental and data processing error/noise models to the ideal observations.
5.  Process all epoch data for a source to generate combined, mission-averaged data products (e.g., mean astrometry, parallax, proper motions).
6.  Simulate low-resolution (BP/RP) and high-resolution (RVS) spectra with applicable noise.
7.  Output all generated data in formats compliant with the official Gaia ICDs for the Universe Model and Main Database.

### 2.3 User Characteristics
The primary users are **scientists and software developers** within the various DPAC Coordination Units (CUs). They are highly knowledgeable in astronomy, astrophysics, and data processing. They require a flexible, reliable, and performant tool to generate large volumes of test data for:
*   Developing and validating data processing algorithms.
*   Testing downstream science analysis pipelines.
*   Performing statistical studies and feasibility analyses.
Users are expected to be proficient with command-line tools and editing XML configuration files.

### 2.4 Constraints
*   **Data Format Compliance:** All output data structures and file formats are dictated by external, evolving ICDs.
*   **Model Dependency:** The realism and completeness of error simulations depend on the timely delivery of accurate instrumental and calibration models from other DPAC units.
*   **Physical Model Limitation:** The simulator does not model interactions between sources (e.g., crowding, blending).
*   **Architectural Dependency:** GOG's design and implementation are tightly coupled to the GaiaSimu library API.

### 2.5 Assumptions and Dependencies
*   The GaiaSimu library provides accurate models for spacecraft attitude, scanning law, instrument characteristics, and basic Universe generation.
*   Users will provide correctly formatted XML configuration and input catalog files.
*   The target execution environment will have a compliant Java Runtime Environment (JRE) installed.
*   The system will process sources sequentially and independently.

## 3. Specific Requirements

### 3.1 External Interface Requirements

#### 3.1.1 User Interfaces
*   **UI-001:** The system shall be operated via a command-line interface (CLI).
*   **UI-002:** The CLI shall accept a single mandatory argument: the path to an XML configuration file.
    ```bash
    java -jar gog.jar /path/to/config.xml
    ```

#### 3.1.2 Hardware Interfaces
*   **HI-001:** The system shall have no direct hardware interfaces.

#### 3.1.3 Software Interfaces
*   **SI-001:** The system shall interface with the **GaiaSimu** library (Java API) to obtain universe models, instrument parameters, and fundamental simulation functions.
*   **SI-002:** The system shall interface with the **Gaia Tools** library for common utilities and data structures.

#### 3.1.4 Communications Interfaces
*   **CI-001:** The system shall have no network communication interfaces. It is a standalone batch-processing application.

### 3.2 Functional Requirements

#### 3.2.1 Configuration Management
*   **FR-001:** The system shall read all runtime parameters from a single, well-defined XML configuration file.
*   **FR-002:** The configuration file shall specify the source generation mode: "Universe Model" or "Input Catalog".
*   **FR-003:** The configuration file shall allow selection and parameterization of error/noise models (e.g., astrometric noise, photometric noise, spectroscopic noise).

#### 3.2.2 Source Generation
*   **FR-010:** In "Universe Model" mode, the system shall generate a list of synthetic astronomical sources based on a built-in statistical model of the Milky Way.
*   **FR-011:** In "Input Catalog" mode, the system shall read source parameters (e.g., position, magnitude, spectral type) from a user-provided ASCII or FITS catalog file.
*   **FR-012:** The system shall assign a unique, persistent source identifier to each generated source.

#### 3.2.3 Epoch Observation Simulation
*   **FR-020:** For each source, the system shall calculate all Gaia observation epochs (transits) over the nominal mission lifetime.
*   **FR-021:** For each epoch, the system shall generate ideal (noiseless) astrometric measurements (e.g., focal plane coordinates).
*   **FR-022:** For each epoch, the system shall generate ideal photometric measurements for the relevant Gaia bands (G, BP, RP).
*   **FR-023:** For each epoch where the source is observed by RVS, the system shall generate an ideal radial velocity measurement.
*   **FR-024:** The system shall apply user-selected error models to corrupt the ideal epoch measurements, producing realistic observed data.

#### 3.2.4 Combined Data Simulation
*   **FR-030:** The system shall process the complete set of epoch observations for a single source.
*   **FR-031:** The system shall compute mission-averaged astrometric parameters, including but not limited to: mean position, parallax, proper motions, and their associated covariance matrices.
*   **FR-032:** The system shall compute mean photometric values (e.g., mean G magnitude) from the epoch photometry.

#### 3.2.5 Spectra Simulation
*   **FR-040:** For each source, the system shall generate a simulated, noiseless BP/RP low-resolution spectrum.
*   **FR-041:** For sources within the RVS magnitude range, the system shall generate a simulated, noiseless RVS high-resolution spectrum.
*   **FR-042:** The system shall apply applicable noise models to the generated spectra.

#### 3.2.6 Data Output
*   **FR-050:** The system shall write all generated data to output files.
*   **FR-051:** The format and structure of all output files shall be 100% compliant with the latest versions of the **Universe Model ICD** and the **Main Database ICD**.
*   **FR-052:** Output shall be logically separated (e.g., into different files or tables) for epoch data, combined data, and spectral data as defined by the ICDs.

### 3.3 Non-Functional Requirements

#### 3.3.1 Performance Requirements
*   **NFR-PERF-001:** The system shall process one complete source (including generation of all epoch data, combined data, and spectra) in **≤ 2 CPU seconds** on a standard DPAC reference hardware platform.
*   **NFR-PERF-002:** The system shall maintain linear scaling characteristics when processing large numbers of sources in batch mode.

#### 3.3.2 Capacity & Scalability Requirements
*   **NFR-CAP-001:** The system shall be capable of generating data for a volume of sources equivalent to **at least 20% of the final Gaia catalog** (approximately 2 billion sources) without inherent software limitations, assuming sufficient hardware resources and storage.

#### 3.3.3 Portability Requirements
*   **NFR-PORT-001:** The system shall be executable on **Linux**, **UNIX**, and **Mac OS** operating systems.
*   **NFR-PORT-002:** The system shall produce **bitwise identical** output results for identical input and configuration across all supported platforms.

#### 3.3.4 Reliability & Operational Requirements
*   **NFR-REL-001:** The system shall be **deterministic**. Given identical configuration and input, it must produce identical output in every run.
*   **NFR-REL-002:** The system shall be capable of running in a **single-threaded** environment.
*   **NFR-REL-003:** The system shall be deployable to run in **clustered or grid computing** environments (e.g., via job arrays where each job processes a distinct subset of sources).

#### 3.3.5 Deployment Requirements
*   **NFR-DEP-001:** The system shall be distributed as a standalone **Java Archive (JAR) file**.
*   **NFR-DEP-002:** The system shall require only a standard Java Runtime Environment (JRE) for execution, with no other external runtime dependencies besides the GaiaSimu and Gaia Tools libraries bundled within or accessible to the JAR.

### 3.4 System Attributes

#### 3.4.1 Maintainability
*   The code shall be modular, with clear separation between the core engine, error model plugins, and I/O modules to facilitate updates as ICDs and error models evolve.

#### 3.4.2 Verification & Acceptance
*   Acceptance of the system will be based on:
    1.  **Format Verification:** Successful validation of output files against the official ICD schemas.
    2.  **Performance Benchmarking:** Demonstration that the 2-second-per-source performance target is met for representative source types.
    3.  **Functional Validation:** Successful execution of test suites covering all source generation modes and data product types.
    4.  **Error Model Validation:** Comparison of simulated error distributions against specifications from providing CUs, as models become available.
