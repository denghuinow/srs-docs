## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the National Library of Medicine's (NLM) Digital Preservation Repository. The purpose of this system is to acquire, organize, preserve, and provide long-term access to NLM's digitized and born-digital biomedical collection materials. This document is intended for use by NLM stakeholders, project managers, system architects, developers, testers, and quality assurance personnel.

### 1.2 Scope
The system is a comprehensive digital repository designed to fulfill NLM's core mission of preserving and providing access to its digital collections. The scope includes:

*   **In-Scope:**
    *   Digitized and born-digital collection materials under the responsibility of NLM's Library Operations.
    *   Implementation of the core functional entities defined by the Open Archival Information System (OAIS) reference model (Ingest, Archival Storage, Data Management, Administration, Preservation Planning, Access).
    *   Management of descriptive, administrative, and structural metadata.
    *   Secure, long-term storage with disaster recovery.
    *   Controlled access for multiple user classes via web interfaces.
    *   Interfaces with existing NLM systems (e.g., Integrated Library System - ILS).
    *   Storage of data harvested by external web harvesting tools.

*   **Out-of-Scope:**
    *   Non-collection resources such as the Unified Medical Language System (UMLS) or the Visible Human Project.
    *   The functionality to perform web harvesting itself.
    *   Provision of special client software for accessing complex materials (e.g., proprietary audiovisual players).
    *   Management of physical collection items.

### 1.3 Definitions, Acronyms, and Abbreviations
| Term | Definition |
| :--- | :--- |
| **AIP** | Archival Information Package. A coherent set of content information and preservation description information, packaged for storage and management within the archive. |
| **DIP** | Dissemination Information Package. A package derived from one or more AIPs, sent to a Consumer in response to an access request. |
| **OAIS** | Open Archival Information System. An ISO standard reference model (ISO 14721) for a system dedicated to preserving and providing access to digital information over the long term. |

| **OAI-PMH** | Open Archives Initiative Protocol for Metadata Harvesting. A protocol for sharing metadata between repositories. |

| **HHS/NIH** | Department of Health and Human Services / National Institutes of Health. |
| **SIP** | Submission Information Package. The package of data and metadata submitted by a Producer to the repository for ingest. |

## 2. Overall Description

### 2.1 Product Perspective
The Digital Preservation Repository is a new, mission-critical system within the NLM technology ecosystem. It is positioned as a central, OAIS-compliant archive for general digital collections, complementing existing specialized repositories like PubMed Central (PMC). It must interoperate with the current ILS for bibliographic data and support standard protocols for data exchange and metadata harvesting.

### 2.2 Product Functions (High-Level Summary)
The system shall:
1.  **Ingest** digital materials from multiple submission streams.
2.  **Preserve** content via secure archival storage and active preservation planning.
3.  **Manage** comprehensive metadata for discovery, administration, and preservation.
4.  **Provide Access** to preserved materials for authorized users.
5.  **Support Administration** of the repository, including configuration, policy management, and auditing.

### 2.3 User Characteristics
| User Class | Skill Level | Key Responsibilities / Needs |
| :--- | :--- | :--- |
| **General Public / Researcher** | Novice to Expert in subject matter, novice in system use. | Search, discover, view, and retrieve digital objects. Access may be restricted. |
| **NIH Staff (Internal User)** | Novice to Expert. | Similar to General Public, but may have broader access rights to certain materials. |
| **NLM Staff (Metadata Specialist)** | Expert in metadata standards. | Create, review, update, and manage descriptive, technical, and administrative metadata for objects. Cannot modify preserved bitstreams. |
| **NLM Staff (Digital Curator / Conservator)** | Expert in digital preservation practices. | Perform quality assurance, initiate format migrations, manage preservation events, and manipulate file structures as part of preservation actions. |
| **NLM System Administrator** | Expert in system administration and security. | Manage system configuration, user roles and permissions, storage systems, backups, system monitoring, and software updates. |
| **External Data Producer** | Varies. | Prepare and submit SIPs via agreed-upon methods (e.g., FTP, API). |

### 2.4 Operating Environment
*   **Hardware:** To be deployed on NLM/NIH-approved infrastructure, compatible with the NCCS backup facility.
*   **Software:** Must operate within the standard NLM enterprise software environment. Specific OS, application server, and database requirements will be defined during architecture design.
*   **Security:** Must reside within the NLM security boundary and comply fully with HHS/NIH security policies, including access control, auditing, and data encryption standards.

### 2.5 Design and Implementation Constraints
1.  The system **must** comply with all applicable HHS and NIH security policies and standards.
2.  The system **must** interface with NLM's existing Integrated Library System (ILS).
3.  The system **must** be capable of ingesting and preserving materials in non-standard or obsolete formats as exceptions to normal policy.
4.  The system architecture **must** adhere to the conceptual framework and terminology of the OAIS reference model.

### 2.6 Assumptions and Dependencies
*   **Assumptions:**
    *   A distributed custodial model will be employed; the repository may manage metadata for objects stored in external, trusted locations.
    *   End-users will have access to necessary software (e.g., PDF readers, video codecs) to use disseminated content; the repository will not provide this software.
    *   Necessary policies for ingest, format migration, and metadata standards will be developed in parallel with the system.
*   **Dependencies:**
    *   Successful operation depends on the development and ratification of new digital preservation policies by NLM.
    *   Interfaces with the ILS require stable ILS APIs or export mechanisms.

## 3. System Features (Functional Requirements)

Requirements are grouped by the primary OAIS functional entities.

### 3.1 Ingest (SIP to AIP)

**FR-INGEST-01: Receive Submission**
> The system shall accept Submission Information Packages (SIPs) via multiple methods, including electronic transfer (e.g., SFTP, HTTPS-based API) and from designated physical media loaders.

**FR-INGEST-02: Validate Submission**
> The system shall validate the structure, completeness, and conformity of incoming SIPs against predefined submission agreements and technical profiles.

**FR-INGEST-03: Generate AIP**
> The system shall transform a validated SIP into a complete Archival Information Package (AIP), assigning a persistent unique identifier and adding preservation metadata.

**FR-INGEST-04: Quality Assurance**
> The system shall provide tools for authorized staff to perform quality checks on ingested content before final commitment to archival storage.

**FR-INGEST-05: Notification**
> The system shall notify submitters and/or administrators of the success or failure of an ingest process, providing detailed error reports for failures.

### 3.2 Archival Storage

**FR-STOR-01: Reliable Storage**
> The system shall store AIPs on primary storage with integrity checking via checksums.

**FR-STOR-02: Bitstream Preservation**
> The system shall ensure the bit-level integrity of all stored files through regular fixity checks.

**FR-STOR-03: Disaster Recovery**
> The system shall replicate AIPs to a geographically separate disaster recovery site (NCCS-compatible).

**FR-STOR-04: Media Refreshment**
> The system shall support procedures for the planned migration of data across storage media to prevent obsolescence.

**FR-STOR-05: Retrieve AIP**
> The system shall retrieve any stored AIP for internal processing (e.g., for migration or dissemination) upon authorized request.

### 3.3 Data Management

**FR-DM-01: Metadata Management**
> The system shall store, index, and manage descriptive, administrative, structural, and technical metadata for all AIPs.

**FR-DM-02: Metadata Editing**
> The system shall provide a secure interface for authorized staff (Metadata Specialists) to create, view, update, and delete object metadata without altering preserved bitstreams.

**FR-DM-03: Database Integrity**
> The system shall maintain referential integrity between metadata records and the stored AIPs they describe.

**FR-DM-04: Search Index**
> The system shall maintain a search index for all public and appropriate administrative metadata to support discovery.

**FR-DM-05: ILS Synchronization**
> The system shall be capable of importing and synchronizing bibliographic metadata from the NLM ILS.

### 3.4 Administration

**FR-ADMIN-01: User & Role Management**
> The system shall allow administrators to define user roles, assign permissions, and manage user accounts.

**FR-ADMIN-02: System Configuration**
> The system shall allow administrators to configure system parameters, including ingest workflows, virus scanning settings, and default metadata templates.

**FR-ADMIN-03: Audit Trail**
> The system shall maintain an immutable log of all significant actions performed on objects (e.g., ingest, modification, access, deletion) and within the system (e.g., user login, configuration change).

**FR-ADMIN-04: Reporting**
> The system shall generate reports on repository holdings, ingest statistics, access statistics, and storage utilization.

**FR-ADMIN-05: Policy Management**
> The system shall support the association of preservation and access policies with collections or individual objects.

### 3.5 Preservation Planning

**FR-PRES-01: Format Registry**
> The system shall maintain or interface with a format registry to track the sustainability of file formats in the repository.

**FR-PRES-02: Risk Monitoring**
> The system shall provide tools to help staff monitor technological obsolescence risks for stored formats.

**FR-PRES-03: Migration Planning**
> The system shall support the definition and documentation of format migration plans and strategies.

**FR-PRES-04: Execute Migration**
> The system shall provide tools for authorized staff (Digital Curators) to initiate and manage preservation actions, such as format migrations, resulting in the creation of new AIP versions.

### 3.6 Access

**FR-ACCESS-01: Search & Discovery**
> The system shall provide a public web interface for users to search and browse repository contents using metadata fields.

**FR-ACCESS-02: Access Control**
> The system shall enforce access restrictions based on user identity, role, IP address, object embargo dates, and other policy rules.

**FR-ACCESS-03: Generate DIP**
> The system shall generate Dissemination Information Packages (DIPs) on demand, which may consist of derivatives (e.g., access copies) of the preserved archival files.

**FR-ACCESS-04: Delivery**
> The system shall deliver DIPs to users via the web interface (view in browser) or as downloadable files.

**FR-ACCESS-05: OAI-PMH Provider**
> The system shall act as an OAI-PMH data provider, exposing public metadata for harvesting by external services.

**FR-ACCESS-06: Object Manipulation (Staff)**
> The system shall provide a secure staff interface for authorized users (Digital Curators) to perform file-level operations (e.g., rearrangement, quality check, derivative creation) on objects within the repository.

## 4. Non-Functional Requirements

### 4.1 Security Requirements
**NFR-SEC-01: Compliance**
> The system shall conform to all HHS and NIH mandatory security standards, policies, and procedures.

**NFR-SEC-02: Access Control**
> The system shall implement role-based access control (RBAC) with granular permissions for all functions and data.

**NFR-SEC-03: Authentication**
> The system shall integrate with NLM's enterprise authentication system (e.g., NIH Login).

**NFR-SEC-04: Data-in-Transit**
> All external data transfers (ingest, access) shall use encrypted protocols (e.g., TLS 1.2+).

### 4.2 Reliability, Availability, and Maintainability
**NFR-REL-01: Availability**
> The system shall be designed for high availability to support its role as a non-"dark" archive. Target availability metrics to be defined during architecture.

**NFR-REL-02: Disaster Recovery**
> The system shall support full recovery at the disaster recovery site with a Recovery Point Objective (RPO) and Recovery Time Objective (RTO) to be defined.

**NFR-MAIN-01: Auditability**
> The system shall maintain a complete, tamper-evident audit trail as specified in FR-ADMIN-03.

**NFR-MAIN-02: Support Bulk Operations**
> The system shall perform efficiently during the bulk ingest of large collections and bulk metadata operations.

### 4.3 Performance Requirements
**NFR-PERF-01: Ingest Performance**
> The system shall be capable of ingesting a defined volume of data (TBD) per day without becoming a bottleneck for collection workflows.

**NFR-PERF-02: Search Performance**
> The system shall return search results from the public interface for typical queries in under 3 seconds.

**NFR-PERF-03: Retrieval Performance**
> The system shall deliver a standard DIP (e.g., a PDF) for viewing or download within 5 seconds of request.

### 4.4 Compatibility & Usability
**NFR-COMP-01: Language & Script Support**
> The system shall support the ingest, storage, management, and display of metadata and content in multiple languages and non-Roman scripts (e.g., Cyrillic, Arabic, CJK).

**NFR-USAB-01: User Interface**
> The public and staff interfaces shall be designed for clarity and efficiency, following NLM/USWDS design guidelines where applicable.

## 5. Acceptance Criteria

Acceptance of the system will be based on its demonstrated ability to:
1.  Fulfill all core OAIS functional requirements (Section 3) as implemented.
2.  Meet the Security Requirements (NFR-SEC-01 through NFR-SEC-04).
3.  Maintain a complete and reliable audit trail (FR-ADMIN-03, NFR-MAIN-01).
4.  Successfully enforce granular access controls for all user classes.
5.  Preserve the intellectual content of materials as the highest priority, with the preservation of original "look and feel" as a secondary, best-effort goal where possible.
6.  Perform within the defined performance parameters for ingest, search, and retrieval.
