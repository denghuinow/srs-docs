### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Tactical Control System (TCS). The intended audience includes project managers, system architects, software developers, test engineers, and end-user representatives. This document serves as the definitive source of requirements for system development and verification.

#### 1.2 Scope
The TCS is a unified ground control station software system designed to command, control, receive data from, process, and disseminate information for tactical Unmanned Aerial Vehicles (UAVs). Its scope encompasses:
*   Interoperability with present and future tactical UAVs (e.g., Outrider, Predator) and their payloads.
*   Interface with UAV data links and network communication systems.
*   Integration into the Joint C4I infrastructure for battlefield management.
*   **Exclusions:** The design, manufacture, or physical characteristics of the UAVs, their payloads, or the ground station hardware are outside the scope of this software specification.

### 2. Overall Description

#### 2.1 Product Perspective
The TCS is a core component within a larger battlefield ecosystem. It acts as the central software node between tactical UAVs and the broader Joint C4I infrastructure. It replaces legacy, platform-specific ground control stations with a common software architecture.

**System Interfaces:**
*   **Upstream:** UAVs via data links (radio, satellite).
*   **Downstream:** Over 20 specified C4I systems (e.g., AFATDS, JSTARS, ASAS), external data storage, printers, and geospatial data sources.
*   **Platform:** Commercial and DoD-standard computing hardware within shelter or shipboard environments.

#### 2.2 Product Functions
The core high-level functions of the TCS are:
1.  **Mission Planning:** Create, manage, and distribute comprehensive UAV mission plans.
2.  **Mission Control & Monitoring:** Real-time command, navigation, and health/status monitoring of UAVs and payloads.
3.  **Payload Product Management:** Full lifecycle handling of sensor imagery and data.
4.  **Targeting:** Derive accurate geolocation data from imagery.
5.  **C4I Interoperability:** Seamless data exchange with external battlefield systems.
6.  **System Support:** Maintenance, diagnostics, and software updates for the TCS itself.

#### 2.3 User Characteristics
| User Class | Expertise | Key Tasks |
| :--- | :--- | :--- |
| **UAV Operator** | Highly trained in flight operations, sensor management, and tactical procedures. | Plan missions, control UAV flight and payloads, monitor systems, disseminate intelligence products. |
| **System Maintainer** | Trained in computer system maintenance and diagnostics. | Perform system diagnostics, install software/hardware updates, rectify faults. |

#### 2.4 Operational Modes
1.  **Normal Operations:** Full functionality for live mission execution.
2.  **Training Operations:** All normal functions using simulated UAV and C4I data to train operators without live assets.
3.  **Maintenance Operations:** Restricted functionality allowing maintainers to run diagnostics, view system logs, and perform updates.

#### 2.5 Constraints
*   **Regulatory:** Must comply with DII/COE, JTA, NITF, VMF, and other mandated standards.
*   **Technical:** Must use COTS/DoD-standard hardware and non-proprietary software with unlimited data rights where possible.
*   **External Dependencies:** Interfaces are dependent on external C4I system specifications and UAV data link formats.
*   **Year 2000:** All components must be Year 2000 compliant.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Mission Planning (MP)
*   **MP-1:** The system shall provide a graphical user interface (GUI) for creating and editing UAV flight routes using waypoints, orbits, and loiter patterns.
*   **MP-2:** The system shall allow the operator to assign payload tasks (e.g., sensor pointing, imaging schedules) to specific segments of the flight plan.
*   **MP-3:** The system shall import and export mission plans in formats compatible with specified external C4I systems (e.g., [Format A], [Format B]).
*   **MP-4:** The system shall perform automated route feasibility checks (e.g., terrain clearance, fuel constraints).

##### 3.1.2 Mission Control & Monitoring (MC)
*   **MC-1:** The system shall transmit flight control commands (altitude, heading, airspeed) to a minimum of two Medium Altitude Endurance UAVs simultaneously from a single operator station.
*   **MC-2:** The system shall display real-time telemetry for each controlled UAV (position, attitude, fuel, system health) on a moving map and instrument panel.
*   **MC-3:** The system shall provide direct control of EO/IR and SAR payloads, including slewing, zoom, focus, and mode selection.
*   **MC-4:** The system shall monitor and display the status of the data link(s) (e.g., signal strength, latency, dropped packets).

##### 3.1.3 Payload Product Management (PM)
*   **PM-1:** The system shall receive, decode, and display real-time video streams (EO/IR) and SAR imagery from UAV payloads.
*   **PM-2:** The system shall provide tools for image annotation (text, symbols, measurement), basic enhancement (contrast, sharpening), and georeferencing.
*   **PM-3:** The system shall store all received imagery and associated metadata in a searchable database, compliant with NITF 2.0.
*   **PM-4:** The system shall disseminate imagery products to pre-configured external systems (C4I, databases, printers) in specified digital and analog formats.

##### 3.1.4 Targeting (TG)
*   **TG-1:** The system shall allow an operator to place a marker on displayed imagery and calculate the corresponding geographic coordinates (latitude, longitude, elevation).
*   **TG-2:** The system shall compute and display an estimated Circular Error Probable (CEP) or Figure of Merit (FOM) for the derived target coordinates.
*   **TG-3:** The system shall format and transmit targeting messages (e.g., VMF) to designated fire control and battlefield management systems.

##### 3.1.5 C4I System Interface (CI)
*   **CI-1:** The system shall send and receive tactical messages (e.g., situation reports, spot reports) with all systems listed in the ORD interface annex.
*   **CI-2:** The system shall exchange mission plans with external planning systems.
*   **CI-3:** The system shall ingest geospatial data and intelligence updates from external sources.

##### 3.1.6 System Maintenance & Diagnostics (SD)
*   **SD-1:** The system shall perform continuous self-diagnostics on its major hardware and software components, logging all faults.
*   **SD-2:** The system shall provide a maintenance GUI for viewing fault logs, system status, and performing diagnostic tests.
*   **SD-3:** The system shall support remote and local installation of authorized software updates without requiring a full system re-build.

#### 3.2 External Interface Requirements

##### 3.2.1 Hardware Interfaces
*   **HI-1:** The software shall interface with standard tactical radio and satellite communication modems.
*   **HI-2:** The software shall support printing to designated military-grade printers.
*   **HI-3:** The software shall interface with external mass storage devices for data archiving.

##### 3.2.2 Software/Communication Interfaces
*   **SI-1:** The software shall communicate via [Protocol A] over [Network Type B] with the Predator UAV data link.
*   **SI-2:** The software shall implement a [Standard API, e.g., CORBA] for integration with the DII/COE framework.
*   **SI-3:** The software shall connect to a minimum of 20 distinct C4I systems using their specified protocols and message formats (detailed in Interface Control Documents).

##### 3.2.3 User Interfaces
*   **UI-1:** The primary operator interface shall consist of multiple high-resolution displays presenting a tactical map, video feeds, telemetry, and control panels.
*   **UI-2:** The interface shall be navigable primarily via keyboard and trackball, with critical functions accessible through dedicated hardware controls.
*   **UI-3:** All displays and controls shall be usable while wearing Nuclear, Biological, Chemical (NBC) gloves.

#### 3.3 Non-Functional Requirements

##### 3.3.1 Performance
*   **PER-1:** The system shall achieve operational readiness (complete startup) from a powered-off state within 60 seconds.
*   **PER-2:** The system shall achieve operational readiness from a standby state within 45 seconds.
*   **PER-3:** The system shall provide an acknowledgment to any operator command input within 1 second.
*   **PER-4:** End-to-end data latency (command to vehicle action, sensor to display) shall not exceed the latency benchmarks of the existing Predator or Outrider ground control stations.

##### 3.3.2 Safety
*   **SAF-1:** No single point of hardware or software failure shall cause the transmission of an unsafe command (e.g., engine kill in flight, collision course) that is accepted by the UAV.

##### 3.3.3 Security
*   **SEC-1:** The system shall be accredited under the DoD Risk Management Framework (RMF) for processing up to [specified classification level] data.
*   **SEC-2:** The system shall enforce user identification, authentication, and role-based access control (RBAC).
*   **SEC-3:** All data at rest and in transit shall be encrypted using NSA-approved algorithms.

##### 3.3.4 Reliability, Availability, and Maintainability
*   **RAM-1:** The system MTBF shall be ≥ [Value] hours as specified in the Predator and Outrider ORDs.
*   **RAM-2:** The system Operational Availability (Ao) shall be ≥ [Value] as specified in the Predator and Outrider ORDs.
*   **RAM-3:** The system shall be capable of continuous operation for a minimum of 72 hours without degradation.

##### 3.3.5 Resource Utilization
*   **RES-1:** The software shall be designed such that the CPU utilization of the primary mission processor does not exceed 50% of its total capability over any rolling 10-second window during normal operations.
*   **RES-2:** The software shall require that 50% of the total available mission storage memory (RAM and disk) remains free for operational use.

##### 3.3.6 Environmental
*   **ENV-1:** The software shall operate correctly on hardware deployed in worldwide climatic conditions, including temperature extremes, humidity, vibration, and shock as defined in [Military Standard, e.g., MIL-STD-810] for land-based shelters and shipboard environments.

### 4. Verification and Acceptance

#### 4.1 Requirement Priorities
All requirements stated in this SRS are considered mandatory and of equal priority, unless otherwise noted in a formal Requirements Traceability Matrix (RTM). In the event of a conflict between requirements, precedence shall be given in this order:
1.  The TCS Operational Requirements Document (ORD).
2.  This SRS document.
3.  Other subordinate requirement documents.

#### 4.2 Acceptance Approach
Verification of requirements shall be conducted through an integrated test program as defined in a separate Master Test Plan. Methods will include:
*   **Inspection:** Review of design and code artifacts.
*   **Analysis:** Performance modeling and trade studies.
*   **Demonstration:** Showcasing of operational workflows.
*   **Test:** Formal, procedurally-driven testing in lab, integration, and field environments.
