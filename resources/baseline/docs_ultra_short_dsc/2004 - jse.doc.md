### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the JSE ISIN Management System. The purpose of this system is to provide the Johannesburg Stock Exchange (JSE), in its capacity as the National Numbering Agent (NNA) for South Africa, with an automated, electronic method for the issuance, cancellation, and de-registration of International Securities Identification Numbers (ISINs) for dematerialized Money Market Instruments (MMIs). This document is intended for use by the project stakeholders, development team, testers, and project managers.

#### 1.2 Scope
The system will automate the core NNA functions for MMIs, enabling same-day trading and settlement within the South African market. The system's scope is strictly limited to:
*   Processing ISIN lifecycle events (Issuance, Cancellation, Maturity De-registration) for MMIs.
*   Validating and processing SWIFT-based messages from STRATE.
*   Maintaining a definitive record of all ISINs and their statuses.
*   Providing a monitoring and manual override interface for JSE staff.

**Out of Scope:**
*   Management of ISINs for equities or bonds.
*   The underlying trading or settlement processes (handled by STRATE's SAFIRES).
*   Direct interfaces with issuers, custodians, or other market participants beyond STRATE.
*   Financial calculation or instrument valuation.

### 2. Overall Description

#### 2.1 Product Perspective
The JSE ISIN Management System is a new, standalone system that acts as a core component within the South African electronic money market infrastructure. It positions the JSE as the automated NNA service provider. The system has one critical external interface: a SWIFT messaging link with STRATE. It is independent of but supports STRATE's SAFIRES settlement system.

#### 2.2 Product Functions
The system shall perform the following core functions:
1.  **Automated ISIN Issuance:** Generate and assign a new, valid ISIN upon receipt and validation of a creation request from STRATE.
2.  **Automated ISIN Cancellation:** Cancel (de-issue) an existing ISIN upon receipt and validation of a cancellation request from STRATE.
3.  **Automated ISIN De-registration:** Update the status of an ISIN to "Matured" upon receipt and validation of a maturity de-registration request from STRATE.
4.  **SWIFT Message Validation:** Validate the format, structure, and business content of all incoming SWIFT MT598 messages.
5.  **Confirmation/Rejection Generation:** Automatically generate and transmit the appropriate SWIFT confirmation or rejection message back to STRATE for every request processed.
6.  **ISIN Database Management:** Maintain a secure, auditable master database of all ISINs, including their full details, status (Issued, Cancelled, Matured), and timestamps of all lifecycle events.
7.  **Administrative Interface:** Provide a secure web-based interface for authorized JSE staff to monitor system activity, query the ISIN database, and perform manual ISIN management during BCP events.

#### 2.3 User Characteristics
| User Class | Description | Key Responsibilities & Skill Level |
| :--- | :--- | :--- |
| **STRATE MMI Engine** | External system. The primary automated user. | Automatically generates and sends SWIFT requests for ISIN lifecycle events. Expects automated, machine-readable responses. No human intervention. |
| **JSE Clearing & Settlement Staff** | Internal users (e.g., operators, supervisors). | Monitor automated message flows, investigate and resolve rejected transactions, perform manual database entries via the front-end during BCP scenarios, and generate reports. Requires training on ISIN rules and system procedures. |

#### 2.4 Constraints
*   The ISIN prefix for all South African Money Market Instruments is fixed as **"ZAM"**.
*   The system **must** adhere to all ANNA guidelines and the ISO 6166 standard for ISIN generation and management.
*   Communication with STRATE **must** use the SWIFT protocol and the specifically allocated BIC branch code **`XJSEZAJJXISN`**.
*   Final message formats and data validation rules are dependent on approval from the MMF and the NMPG.
*   All system development and operational costs are to be recovered from STRATE as per a commercial agreement.
*   The system is scheduled for implementation in **Q2 2004**.

#### 2.5 Assumptions and Dependencies
*   STRATE's MMI Engine will be developed and available to interface as specified.
*   The final SWIFT MT598 message specifications will be provided by the MMF/NMPG before development completion.
*   A stable SWIFT connectivity and infrastructure will be provided and maintained.
*   A formal SLA covering support and maintenance will be established between JSE and STRATE.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 SWIFT Message Processing (FUN-SWIFT)
*   **FUN-SWIFT-01:** The system shall receive incoming SWIFT MT598 messages via the dedicated BIC `XJSEZAJJXISN`.
*   **FUN-SWIFT-02:** The system shall validate the syntax and mandatory fields of every incoming MT598 message against the MMF/NMPG approved format specification.
*   **FUN-SWIFT-03:** The system shall parse the business content (e.g., instrument details, ISIN for cancellation) from validated messages.

##### 3.1.2 ISIN Issuance (FUN-ISSUE)
*   **FUN-ISSUE-01:** Upon receipt of a valid **ISIN Creation Request**, the system shall generate a new ISIN compliant with ISO 6166, using the prefix "ZAM", a valid NSIN, and a calculated check digit.
*   **FUN-ISSUE-02:** The system shall record the new ISIN, all associated instrument details from the request, the issue timestamp, and status "ISSUED" in the master database.
*   **FUN-ISSUE-03:** The system shall immediately generate and send an **ISIN Creation Confirmation** MT598 message back to STRATE, containing the newly assigned ISIN.
*   **FUN-ISSUE-04:** If the creation request is invalid (format error, duplicate request, missing data), the system shall generate and send an **ISIN Creation Rejection** MT598 message with an appropriate error code and description.

##### 3.1.3 ISIN Cancellation (FUN-CANCEL)
*   **FUN-CANCEL-01:** Upon receipt of a valid **ISIN Cancellation Request** for an existing, issued ISIN, the system shall update the status of that ISIN to "CANCELLED" in the database, retaining all original data and adding a cancellation timestamp.
*   **FUN-CANCEL-02:** The system shall generate and send an **ISIN Cancellation Confirmation** MT598 message to STRATE.
*   **FUN-CANCEL-03:** If the cancellation request is invalid (e.g., ISIN not found, already cancelled/matured), the system shall generate and send an **ISIN Cancellation Rejection** MT598 message.

##### 3.1.4 ISIN Maturity De-registration (FUN-MATURE)
*   **FUN-MATURE-01:** Upon receipt of a valid **Maturity De-registration Request** for an existing, issued ISIN, the system shall update the status of that ISIN to "MATURED" in the database, adding a maturity timestamp.
*   **FUN-MATURE-02:** The system shall generate and send a **Maturity De-registration Confirmation** MT598 message to STRATE.
*   **FUN-MATURE-03:** If the maturity request is invalid, the system shall generate and send a **Maturity De-registration Rejection** MT598 message.

##### 3.1.5 ISIN Database & Administration (FUN-ADMIN)
*   **FUN-ADMIN-01:** The system shall maintain a secure, persistent database storing a complete history for every ISIN, including all request/confirmation data and status changes.
*   **FUN-ADMIN-02:** The system shall provide a secure web-based login for JSE staff using JSE domain credentials.
*   **FUN-ADMIN-03:** The front-end shall allow authorized users to search and view ISIN details by ISIN code, instrument description, status, or date range.
*   **FUN-ADMIN-04:** The front-end shall provide a real-time dashboard showing system status, recent message activity, and any pending errors.
*   **FUN-ADMIN-05 (BCP Mode):** In a declared BCP scenario, the front-end shall allow authorized supervisors to **manually enter** ISIN issuance, cancellation, or maturity data directly into the database, simulating an automated transaction. All manual entries must be logged with user ID and reason.

#### 3.2 External Interface Requirements

##### 3.2.1 SWIFT Interface (EXT-SWIFT)
*   **EXT-SWIFT-01:** The interface shall use the SWIFT Alliance Access (or equivalent) software for message transmission and reception.
*   **EXT-SWIFT-02:** All application-to-application messages shall use the **MT598 (Free Format)** message type with structured, proprietary content as defined in the MMF/NMPG specification.
*   **EXT-SWIFT-03:** The system's dedicated BIC for this service is `XJSEZAJJXISN`. STRATE will use its designated BIC.
*   **EXT-SWIFT-04:** The system must support the nine core message flows:
    1.  ISIN Creation Request (STRATE → JSE)
    2.  ISIN Creation Confirmation (JSE → STRATE)
    3.  ISIN Creation Rejection (JSE → STRATE)
    4.  ISIN Cancellation Request (STRATE → JSE)
    5.  ISIN Cancellation Confirmation (JSE → STRATE)
    6.  ISIN Cancellation Rejection (JSE → STRATE)
    7.  ISIN Maturity De-registration Request (STRATE → JSE)
    8.  ISIN Maturity De-registration Confirmation (JSE → STRATE)
    9.  ISIN Maturity De-registration Rejection (JSE → STRATE)

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements (NFR-PERF)
*   **NFR-PERF-01:** The system must be capable of processing a peak load of **500 ISIN issuance transactions per day** within a standard business window (e.g., 7:00 - 17:00 SAST).
*   **NFR-PERF-02:** The 95th percentile of response time (from receipt of a valid request to dispatch of the corresponding confirmation) must be **under 30 seconds**.

#### 4.2 Availability & Reliability (NFR-AVAIL)
*   **NFR-AVAIL-01:** The system shall achieve **99.5% operational availability** during mandated market hours.
*   **NFR-AVAIL-02:** A formal **Business Continuity Plan (BCP)** must be documented and implemented. The system must support manual override capabilities (see FUN-ADMIN-05) to ensure service continuity during SWIFT or system outages.
*   **NFR-AVAIL-03:** All data must be backed up daily with transaction logs, allowing point-in-time recovery.

#### 4.3 Security Requirements (NFR-SEC)
*   **NFR-SEC-01:** The system must enforce **compliance with ANNA guidelines and ISO 6166** in all ISIN generation logic.
*   **NFR-SEC-02:** Access to the administrative front-end shall be restricted via JSE network authentication and role-based access controls (RBAC).
*   **NFR-SEC-03:** All SWIFT communication must comply with SWIFT's security standards and protocols.
*   **NFR-SEC-04:** All changes to the ISIN database (automated or manual) must be recorded in an immutable audit trail.

#### 4.4 Maintainability & Support (NFR-MAIN)
*   **NFR-MAIN-01:** A detailed **Service Level Agreement (SLA)** governing administration, maintenance, support procedures, and response times must be established between JSE and STRATE prior to go-live.
*   **NFR-MAIN-02:** The system shall provide comprehensive logging for all system and business events to facilitate troubleshooting.

### 5. Other Requirements

#### 5.1 Priorities
*   **Highest Priority (Critical):** The reliable, automated issuance of a new ISIN in response to a valid SWIFT request (FUN-ISSUE-01, FUN-ISSUE-03). This is the foundational capability that enables same-day trading.
*   **High Priority:** Automated cancellation and maturity de-registration, along with comprehensive validation and rejection messaging for all flows.
*   **Medium Priority:** Development of the full-featured JSE administrative front-end for monitoring and BCP functions.

#### 5.2 Acceptance Approach
Final system acceptance will be contingent upon the successful execution of **end-to-end integration tests** demonstrating all nine SWIFT message flows between STRATE's test environment and the JSE ISIN Management System. A formal test plan, co-signed by JSE and STRATE, will detail the test cases covering normal operation and error conditions.
