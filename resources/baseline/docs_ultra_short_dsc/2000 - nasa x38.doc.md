### 1. Introduction

#### 1.1 Purpose
This document defines the software requirements for the Fault-Tolerant System Services (FTSS) of the X-38 Crew Return Vehicle's Flight Critical Computer (FCC). The FTSS provides the core system software layer that isolates NASA's flight application from the underlying quad-redundant hardware and Commercial Off-The-Shelf (COTS) operating system. It ensures deterministic, fault-tolerant execution of critical flight software.

#### 1.2 Document Conventions
*   **Requirements IDs:** Follow the format `FTSS-REQ-XXX`, where `XXX` is a unique numeric identifier.
*   **Priority:** `(P1)` = High, `(P2)` = Medium, `(P3)` = Low.
*   **Qualification Method:** `[D]` = Demonstration, `[T]` = Test, `[A]` = Analysis, `[I]` = Inspection.

#### 1.3 Scope
The FTSS software provides scheduling, communication, fault management, redundancy, time, and memory management services for the Fault Tolerant Parallel Processor (FTPP) architecture. It executes on four Flight Critical Processors (FCPs) and a reduced subset on five Instrument Control Processors (ICPs).

**In-Scope:**
*   FTSS software modules and API.
*   Integration with VxWorks 5.4.
*   Management of the FTPP virtual group architecture.
*   Fault Detection, Isolation, and Recovery (FDIR) logic.

**Out-of-Scope:**
*   NASA flight application software.
*   Hardware design of Network Elements (NEs) or processors.
*   VxWorks operating system kernel modifications.
*   Instrument Control Processor (ICP) application software.

#### 1.4 References
*   FTPP System Requirements Document (SRD)
*   X-38 Crew Return Vehicle System Architecture Description
*   VxWorks 5.4 Programmer's Guide

### 2. Overall Description

#### 2.1 Product Perspective
The FTSS is a middleware layer within the FCC software stack.
```
+---------------------------------------+
|     NASA Flight Application Code      |
+---------------------------------------+
|  FTSS API | Deterministic Scheduler   |
|  Fault Mgmt | Comm Services | Time    |
+---------------------------------------+
|      VxWorks 5.4 Operating System     |
+---------------------------------------+
| Radstone PPC604R | NE Comm Hardware   |
+---------------------------------------+
```
**System Interfaces:**
*   **Upward:** FTSS API for the flight application.
*   **Downward:** VxWorks OS and Board Support Package (BSP).
*   **Lateral:** Network Element hardware/firmware for inter-processor communication.
*   **External:** ICPs (via shared memory/VME), CTC (via MPCC boards).

#### 2.2 Product Functions
1.  **Initialization & Synchronization:** Configure hardware into synchronized virtual groups post power-up.
2.  **Deterministic Scheduling:** Execute application tasks in predefined, rate-based frames across mission modes.
3.  **Fault-Tolerant Communication:** Provide guaranteed message-passing services between tasks across redundant processors.
4.  **Fault Management:** Detect, isolate, and recover from hardware faults in processors and network elements.
5.  **Redundancy Management:** Map physical resources to logical groups and execute reconfiguration strategies.
6.  **Time Services:** Distribute synchronized, high-accuracy mission time.
7.  **Memory Management:** Perform error scrubbing and manage memory congruence during recovery.

#### 2.3 User Characteristics
*   **Primary "User":** The NASA flight application software. It is a sophisticated, real-time system with developers who are experts in aerospace software but are not required to understand the underlying FTPP hardware redundancy.
*   **Secondary Users:** Ground support personnel and system integrators who configure FTSS parameters and monitor system health via telemetry.

#### 2.4 Constraints
*   **Hardware:** Must execute on the Radstone Power PC 604R processor.
*   **Operating System:** Must be compatible with and run on top of VxWorks 5.4.
*   **Implementation Language:** Core FTSS services shall be implemented in C.
*   **Legacy Interfaces:** Must support existing MPCC and VME bus interfaces for ICP/CTC communication.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** The flight application uses the FTSS API correctly and adheres to memory usage guidelines (congruent vs. non-congruent).
*   **Assumption:** The underlying Network Element hardware and its firmware function correctly to provide Byzantine-resilient communication.
*   **Dependency:** Availability of a validated VxWorks 5.4 BSP for the Radstone PPC604R platform.

### 3. System Features and Requirements

#### 3.1 System Initialization & Synchronization
**3.1.1** `FTSS-REQ-001` `(P1)` The system shall perform a cold start initialization, loading software and configuring all FCPs and ICPs, within 90 seconds of power application. `[D, T]`

**3.1.2** `FTSS-REQ-002` `(P1)` The system shall establish fault-tolerant virtual groups comprising the four FCPs and necessary ICPs as part of the initialization sequence. `[T]`

**3.1.3** `FTSS-REQ-003` `(P1)` The system shall synchronize the Mission Elapsed Time (MET) and internal scheduling clocks across all FCPs in a virtual group to within a skew of 2.5 seconds during initialization. `[T]`

#### 3.2 Deterministic Task Scheduling
**3.2.1** `FTSS-REQ-010` `(P1)` The system shall provide a deterministic scheduler that executes application tasks in predefined 50 Hz (20 ms), 10 Hz (100 ms), and 1 Hz (1000 ms) rate groups. `[T]`

**3.2.2** `FTSS-REQ-011` `(P1)` The scheduler shall support multiple, configurable vehicle modes (e.g., pre-launch, ascent, entry) with defined task sets for each mode. `[T]`

**3.2.3** `FTSS-REQ-012` `(P1)` The combined overhead of the scheduler and time services shall not exceed 1 millisecond per 20 ms (50 Hz) minor frame. `[T, A]`

#### 3.3 Fault-Tolerant Communication Services
**3.3.1** `FTSS-REQ-020` `(P1)` The system shall provide a synchronous message queue service for guaranteed, rate-based communication between tasks. `[T]`

**3.3.2** `FTSS-REQ-021` `(P1)` The system shall provide an immediate pipe service for low-latency, event-driven communication between tasks. `[T]`

**3.3.3** `FTSS-REQ-022` `(P1)` Communication services shall guarantee congruent data exchange across all non-faulty processors within a virtual group, ensuring all correct processors have identical data values. `[T, A]`

**3.3.4** `FTSS-REQ-023` `(P1)` The system shall support message-passing between tasks located on different virtual groups (e.g., FCP to ICP). `[T]`

#### 3.4 Fault Detection, Isolation, and Recovery (FDIR)
**3.4.1** `FTSS-REQ-030` `(P1)` The system shall perform continuous Built-In Tests (BIT) on FCPs, ICPs, and Network Elements. `[T]`

**3.4.2** `FTSS-REQ-031` `(P1)` Upon detection of a faulty Flight Critical Processor, the system shall mask (logically remove) that FCP from the active virtual group within 3 minor frames (60 ms). `[T]`

**3.4.3** `FTSS-REQ-032` `(P1)` The system shall manage reconfiguration of the virtual group, including degradation from quad to triplex redundancy, without intervention from the application software. `[D, T]`

**3.4.4** `FTSS-REQ-033` `(P2)` The system shall support the recovery and reintegration of a previously failed processor once it is deemed healthy. `[T]`

#### 3.5 Redundancy Management
**3.5.1** `FTSS-REQ-040` `(P1)` The system shall maintain the dynamic mapping between physical hardware components (processors, links) and logical fault-tolerant virtual groups. `[T]`

**3.5.2** `FTSS-REQ-041` `(P1)` The system shall execute predefined recovery strategies for link failures and Network Element failures. `[T]`

#### 3.6 Time Services
**3.6.1** `FTSS-REQ-050` `(P1)` The system shall provide synchronized Mission Elapsed Time (MET) to all FCPs with a drift rate not exceeding 50 parts per million (PPM). `[T, A]`

**3.6.2** `FTSS-REQ-051` `(P2)` The system shall provide a Separation Elapsed Time (SEP) from a defined mission event. `[T]`

**3.6.3** `FTSS-REQ-052` `(P2)` Time services shall have a resolution of 1 millisecond or better. `[T]`

#### 3.7 Memory Management
**3.7.1** `FTSS-REQ-060` `(P2)` The system shall perform periodic RAM scrubbing to detect and correct single-bit errors and detect multi-bit errors. `[T]`

**3.7.2** `FTSS-REQ-061` `(P2)` During processor reintegration, the system shall manage the alignment of a defined 4 MB region of DRAM to ensure congruence with the active virtual group. `[T]`

### 4. External Interface Requirements

#### 4.1 Application Programming Interface (API)
**4.1.1** `FTSS-REQ-100` `(P1)` A well-defined C-language API shall be provided for all FTSS services (scheduling, communication, time, status). `[I]`

#### 4.2 Hardware Interfaces
**4.2.1** `FTSS-REQ-110` `(P1)` The software shall interface with the Network Element hardware drivers to send and receive Byzantine-resilient messages. `[T]`

**4.2.2** `FTSS-REQ-111` `(P1)` The software shall interface with ICPs via the defined shared memory map and VME interrupt mechanism. `[T]`

**4.2.3** `FTSS-REQ-112` `(P2)` The software shall interface with the Multi-Protocol Communications Controller (MPCC) boards to send telemetry to and receive commands from the Command & Telemetry Computer (CTC). `[T]`

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
**5.1.1** `FTSS-REQ-200` `(P1)` System initialization time shall be ≤ 1.5 minutes. (See 3.1.1)
**5.1.2** `FTSS-REQ-201` `(P1)` Fault masking latency shall be ≤ 60 ms. (See 3.4.2)
**5.1.3** `FTSS-REQ-202` `(P1)` Inter-processor message latency (within a group) shall be bounded and deterministic. `[T]`

#### 5.2 Reliability & Availability
**5.2.1** `FTSS-REQ-210` `(P1)` The FTSS shall enable the FCC to be two-fault tolerant for any two non-simultaneous hardware faults. `[A, T]`
**5.2.2** `FTSS-REQ-211` `(P1)` The system shall maintain operational capability with any combination of 3 out of the 5 total Fault Containment Regions (FCRs) active. `[A]`

#### 5.3 Safety & Criticality
**5.3.1** `FTSS-REQ-220` `(P1)` The FTSS shall provide fault masking to prevent a single hardware failure from causing a system failure. `[A, T]`
**5.3.2** `FTSS-REQ-221` `(P1)` The FTSS shall not contain a single point of failure whose malfunction would cause loss of critical vehicle functions. `[A]`

#### 5.4 Resource Constraints
**5.4.1** `FTSS-REQ-230` `(P1)` The FTSS software, integrated with VxWorks 5.4, shall occupy no more than 3 Megabytes of ROM. `[T]`
**5.4.2** `FTSS-REQ-231` `(P1)` The FTSS software, integrated with VxWorks 5.4, shall require no more than 9 Megabytes of DRAM during operation. `[T]`

#### 5.5 Accuracy
**5.5.1** `FTSS-REQ-240` `(P1)` Mission Elapsed Time accuracy shall be ≤ 50 PPM. (See 3.6.1)

### 6. Other Requirements

#### 6.1 Design Constraints
*   The software shall be modular to allow for testing of individual services.
*   The design shall minimize dependencies between the FTSS core and the VxWorks OS to facilitate portability.

#### 6.2 Software Quality Attributes
*   **Maintainability:** Code shall adhere to NASA C coding standards with detailed comments.
*   **Verifiability:** All requirements shall be traceable to test cases.
*   **Robustness:** The system shall handle out-of-range inputs and hardware exceptions gracefully without crashing.

### 7. Acceptance and Verification
Each requirement in this document includes a designated qualification method `[D, T, A, I]`. Acceptance of the FTSS software will be contingent upon successful completion of a formal Qualification Test Procedure (QTP) that demonstrates, tests, analyzes, and inspects the system against these requirements. Traceability to the parent FTPP System Requirements Document will be maintained throughout the verification process.

**Priority Verification Focus:** Initial acceptance will prioritize verification of all `(P1)` requirements related to fault tolerance, deterministic scheduling, and critical fault recovery timelines.
