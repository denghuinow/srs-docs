# Software Requirements Specification (SRS)
## Standardized Communication Solution for Remote Monitoring and Control (SCADA) of Wind Turbines and Wind Farms

**Document Version:** 1.0
**Date:** [Date of Generation]
**Status:** Draft for Procurement & Tendering

### 1. Introduction

#### 1.1 Purpose
This document defines the Software Requirements Specification (SRS) for a standardized communication solution enabling remote monitoring and control (SCADA) of wind turbines and wind farms. The primary purpose is to specify the data exchange protocol, services, and data model between wind turbine controllers and remote supervisory computers. This specification serves as a procurement guide to ensure vendor-independent, interoperable solutions.

#### 1.2 Scope
This specification covers:
*   The definition of data objects representing wind turbine components and signals.
*   The services for reading, writing, reporting, and controlling these data objects.
*   The communication protocol stack and messaging structure.
*   Functional requirements for supervision, control, alarm management, logging, and system management.
*   Non-functional requirements for performance, security, reliability, and data quality.

This specification explicitly **excludes**:
*   The design, characteristics, or implementation of the remote SCADA system or Human-Machine Interface (HMI).
*   Turbine control algorithms or safety functions.
*   Physical transmission media specifications (e.g., fiber, radio, cellular).
*   Local temporary connections (e.g., service laptops).
*   Voice or video communication.
*   Actor-specific business functions (e.g., energy accounting, billing).

#### 1.3 Intended Audience
*   **Wind Turbine & Component Manufacturers:** To develop compliant turbine controllers and gateways.
*   **SCADA System Vendors & Integrators:** To develop client applications and systems.
*   **Wind Farm Owners & Operators:** To use this document as a baseline for procurement and tendering.
*   **Standardization Bodies (e.g., IEC TC88):** As a foundational technical document.

#### 1.4 Definitions, Acronyms, and Abbreviations
| Term | Definition |
| :--- | :--- |
| **SCADA** | Supervisory Control and Data Acquisition. |
| **WFMC** | Wind Farm Main Controller. An optional intermediate supervisory system for a wind farm. |
| **UTC** | Coordinated Universal Time. The primary time standard. |

### 2. Overall Description

#### 2.1 Product Perspective
The system is a middleware communication layer positioned between the wind turbine's internal control system and the external, remote SCADA systems. It is an **open standard** designed to overcome the industry's reliance on proprietary, incompatible solutions.

**System Context Diagram:**
```
[Remote SCADA Clients] <---Standard Protocol---> [Wind Turbine Servers]
         ^                                                  ^
         |                                                  |
    (May connect via WFMC)                          (May connect via Gateway)
         |                                                  |
[Wind Farm Controller]                            [Proprietary Turbine Control System]
```

#### 2.2 Product Functions (High-Level)
1.  **Remote Supervision:** Monitor real-time status, measurements, and state changes of wind turbines.
2.  **Remote Control:** Issue commands to turbine equipment (e.g., start, stop, set points).
3.  **Alarm Management:** Receive, display, and acknowledge alarms generated by abnormal turbine states.
4.  **Event Logging:** Record and retrieve time-sequenced logs of operational and fault events.
5.  **Parameter Management:** Read and modify operational parameters and set points.
6.  **Data Retrieval:** Access configuration data, settings, and historical data records (e.g., fault history, statistical reports).
7.  **System Management:** Perform network management, time synchronization, and software/configuration management tasks.

#### 2.3 User Characteristics
| User Role | Primary Goal | Technical Expertise |
| :--- | :--- | :--- |
| **Wind Turbine Operator** | Daily monitoring, fault response, performance optimization. | High. Expert in turbine operation and maintenance procedures. |
| **Wind Farm Owner / Manager** | Overview of fleet performance, energy yield reporting, asset management. | Medium. Understands operational metrics and business outcomes. |
| **Electrical Network Operator** | Grid stability, power curtailment commands, compliance monitoring. | High. Expert in grid codes and power system management. |
| **System Administrator** | Configuration, user management, system maintenance, and troubleshooting. | Very High. Expert in network and system administration. |

#### 2.4 Constraints
*   **Safety:** The communication system is **not safety-critical**. All personnel, plant, and network safety functions must be self-contained within the turbine's local control system.
*   **Open Standards:** The solution must be based on open, widely accepted communication standards (e.g., TCP/IP, web services).
*   **Backward Compatibility:** Must allow integration with existing, proprietary wind power plants through gateway solutions.
*   **Data Model:** The specification assumes and requires a hierarchical, object-oriented data model to represent the turbine.

#### 2.5 Assumptions and Dependencies
*   It is assumed the wind turbine operates autonomously; this system is for supervision and coordination.
*   A reliable underlying network connection (latency, bandwidth) is provided but not defined by this spec.
*   Implementation depends on the existence of a gateway to translate between this standard and legacy turbine protocols.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Data Model Services
*   **FR-DM-01:** The system shall define a hierarchical logical device model for wind turbines (e.g., Wind Turbine -> Rotor -> Generator -> Converter).
*   **FR-DM-02:** Each logical node shall contain standardized data objects (e.g., measurements, status info, controls, settings).
*   **FR-DM-03:** The system shall support the retrieval of the device's data model (self-description).

##### 3.1.2 Information Monitoring & Supervision
*   **FR-SUP-01:** The system shall allow SCADA clients to read the current value of any data object.
*   **FR-SUP-02:** The system shall support reporting by exception, where the turbine server automatically sends updates upon a significant change of a data object's value or quality.
*   **FR-SUP-03:** The system shall support periodic reporting of data object values at configurable intervals.

##### 3.1.3 Control Services
*   **FR-CTRL-01:** The system shall allow authorized clients to send direct control commands (e.g., "Start", "Stop", "Open Breaker") to controllable data objects.
*   **FR-CTRL-02:** The system shall support "Select-Before-Operate" (SBO) control sequences for critical commands, requiring a select and execute phase.
*   **FR-CTRL-03:** The system shall allow authorized clients to write new set points (e.g., active power limit, voltage reference) to relevant data objects.

##### 3.1.4 Alarm & Event Management
*   **FR-ALM-01:** The turbine server shall generate and transmit an alarm message to subscribed clients when a predefined abnormal condition occurs.
*   **FR-ALM-02:** Alarm messages shall include: alarm identifier, severity, condition, timestamp, and associated data object.
*   **FR-ALM-03:** The system shall allow an authorized client to acknowledge an active alarm.

##### 3.1.5 Logging Services
*   **FR-LOG-01:** The turbine server shall maintain a chronological log of significant events (state changes, commands issued, alarms).
*   **FR-LOG-02:** The system shall allow clients to retrieve log entries based on time range and event type.

##### 3.1.6 Historical Data Retrieval
*   **FR-HIST-01:** The system shall allow clients to retrieve time-series historical data (e.g., 10-minute averages, fault records) stored in the turbine.
*   **FR-HIST-02:** Historical data shall be retrievable for configurable periods and resolutions.

##### 3.1.7 System Management
*   **FR-MGMT-01:** The system shall support time synchronization, allowing the turbine clock to be synchronized with a UTC time source from the SCADA client.
*   **FR-MGMT-02:** The system shall support the retrieval of device identification and version information.
*   **FR-MGMT-03:** The system shall support secure file transfer for configuration updates and software management.

#### 3.2 External Interface Requirements

##### 3.2.1 Hardware Interfaces
*   Not specified. The protocol is media-agnostic (Ethernet, serial, etc.).

##### 3.2.2 Software Interfaces
*   **EI-PROT-01:** The application-layer protocol shall be defined using a platform-independent, openly documented messaging scheme (e.g., based on XML/JSON and MMS/web services concepts).
*   **EI-GW-01:** For turbines with proprietary controllers, a Gateway component shall implement the standard server interface on one side and the proprietary protocol on the other.

##### 3.2.3 Communication Interfaces
*   The specification defines a client-server architecture. The wind turbine (or gateway) acts as the server. SCADA systems act as clients.
*   The protocol shall operate over a reliable transport layer (e.g., TCP).

#### 3.3 Non-Functional Requirements

##### 3.3.1 Performance Requirements
*   **NFR-PER-01:** The overall transfer time (command issuance to confirmation receipt) for **time-critical functions** (e.g., power set point change, emergency stop) shall not exceed **0.5 seconds** under normal network conditions.
*   **NFR-PER-02:** The response delay for **system management functions** (e.g., model query, log retrieval) shall not exceed **2 seconds**.
*   **NFR-PER-03:** The system shall support concurrent connections from multiple SCADA clients.

##### 3.3.2 Security Requirements
*   **NFR-SEC-01:** The system shall require mutual authentication of client and server before establishing a session.
*   **NFR-SEC-02:** The system shall ensure data integrity, with a residual undetected error rate in line with industrial communication standards (e.g., < 10^-15).
*   **NFR-SEC-03:** The system shall support encryption (e.g., TLS/SSL) for data confidentiality.
*   **NFR-SEC-04:** The system shall implement an access control mechanism based on user roles and permissions for data objects and services.

##### 3.3.3 Reliability, Availability, and Maintainability
*   **NFR-REL-01:** The communication system's failure shall not impede the turbine's autonomous safety functions.
*   **NFR-REL-02:** The system design shall support redundant communication channels and server components to enhance availability.
*   **NFR-REL-03:** The mean time between failures (MTBF) for the communication server software shall exceed 10,000 hours.

##### 3.3.4 Data Quality Requirements
*   **NFR-DQ-01:** All time-critical data (events, alarms, measurements) shall be timestampable by the source (turbine) with **UTC time**.
*   **NFR-DQ-02:** The timestamp accuracy and resolution shall be at least **10 milliseconds**.
*   **NFR-DQ-03:** Data objects shall have an associated "quality" indicator (e.g., good, invalid, old-data, substituted).

##### 3.3.5 Environmental Requirements
*   **NFR-ENV-01:** Hardware components implementing this specification (e.g., gateways, communication modules) shall be designed to operate in the environmental conditions of a wind turbine (wide temperature range, high humidity, salinity, vibration).

### 4. Acceptance Criteria
Acceptance of an implementation of this specification shall be based on:
1.  **Functional Compliance:** Successful demonstration of all core functional requirements (Section 3.1).
2.  **Performance Validation:** Measured transfer times meeting NFR-PER-01 and NFR-PER-02.
3.  **Security Audit:** Verification of authentication, integrity, and optional confidentiality mechanisms.
4.  **Interoperability Testing:** Successful communication between the system under test and at least two independent SCADA client implementations from different vendors.
5.  **Data Quality Verification:** Demonstration of correct UTC timestamping with required resolution.

### 5. Appendix

#### 5.1 Priority Guide
*   **P0 (Critical):** Time-critical control & set points (FR-CTRL-xx), Alarm reporting (FR-ALM-01), Core data model (FR-DM-01).
*   **P1 (High):** Supervision services (FR-SUP-xx), Logging (FR-LOG-01), Security (NFR-SEC-01/02).
*   **P2 (Medium):** Historical data (FR-HIST-xx), System management (FR-MGMT-xx), Redundancy support (NFR-REL-02).
