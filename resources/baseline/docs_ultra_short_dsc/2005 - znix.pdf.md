# Software Requirements Specification (SRS)
## ZNIX Information Management Framework
**Version:** 1.0
**Date:** 2023-10-27
**Status:** Draft for Review

---

### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the ZNIX Information Management Framework. It is intended for use by the project's stakeholders, including developers, testers, project managers, and researchers, to establish a common understanding of the system's capabilities, constraints, and external interfaces.

#### 1.2 Document Conventions
*   **Shall / Must:** Indicates a mandatory requirement.
*   **Should:** Indicates a desirable, but not mandatory, requirement.
*   **May / Could:** Indicates an optional feature or capability.
*   **Bold Text:** Used for key terms and system components.
*   `Monospace Text:` Used for API calls, code snippets, and file names.

#### 1.3 Project Scope
The ZNIX Framework is an object-based, application-independent system designed to centralize user information from disparate sources into a single, user-defined hierarchical model. Its core purpose is to refine traditional information management by providing a deeply OS-integrated, semantic layer over personal data. The system operates in a single-user, non-networked environment on resource-constrained hardware. Out of scope for this version are multi-user collaboration, networked/cloud operation, and built-in advanced analytics.

### 2. Overall Description

#### 2.1 Product Perspective
ZNIX is a standalone desktop application framework that positions itself as a research-driven alternative to monolithic information management systems and semantic frameworks like Project Haystack. It is designed for deep integration with the Microsoft Windows operating system (2000/XP) and aims for significantly lower resource consumption than contemporary systems (e.g., Windows Longhorn). It interacts with third-party applications to capture data and provides services to both ZNIX-aware and non-aware client applications.

#### 2.2 Product Functions
1.  **Centralized Information Store:** Aggregate and store user information from integrated email, document, contact, and web applications.
2.  **Hierarchical Model Management:** Enable users to create, modify, and browse a customizable tree-like structure representing relationships between information entities.
3.  **Automated Data Capture:** Monitor and extract relevant information from specified third-party applications without continuous user intervention.
4.  **Archival Management:** Allow users to archive information entities to removable media while preserving their reference and metadata within the live hierarchy.
5.  **Service API:** Expose core functionality for entity/relationship management and querying to external ZNIX-aware applications.
6.  **Application Proxy:** Provide a mechanism for non-aware applications to interact indirectly with the framework's data and services.

#### 2.3 User Classes and Characteristics
*   **Home User:** Manages personal emails, downloaded documents, and web bookmarks. Has basic IT proficiency.
*   **Manager/Executive:** Organizes project documents, client communications, and contact details. Values quick retrieval and relationship mapping.
*   **Researcher:** Collects and links a large volume of reference material (papers, notes, web pages). Requires flexible categorization.

All user classes are assumed to be single, local users of the system.

#### 2.4 Operating Environment
*   **Hardware Minimum:** Pentium III 1.0 GHz processor, 256 MB RAM, 2 GB available disk space.
*   **Operating Systems:** Microsoft Windows 2000 Professional (SP4), Windows XP Professional/Home (SP2).
*   **Software Dependencies:** Specific versions of Microsoft Outlook, Microsoft Word, and Internet Explorer (to be detailed in the External Interface Requirements).

#### 2.5 Design and Implementation Constraints
1.  The framework core must be licensed under the GNU Lesser General Public License (LGPL).
2.  Supporting tools and utilities must be licensed under the GNU General Public License (GPL).
3.  The system must comply with Microsoft Windows Logo requirements for the target OS.
4.  All text data must internally use Unicode (UTF-16) encoding.
5.  The system shall be designed for single-user operation only.

#### 2.6 Assumptions and Dependencies
*   The security model of third-party applications (Outlook, IE, Word) from which data is captured is assumed to be adequate and uncompromised.
*   The framework assumes compatibility with the listed versions of third-party applications and their immediate subsequent minor releases.
*   The user is responsible for maintaining the integrity and availability of archived data on removable media.

### 3. System Features

#### 3.1 Centralized Information Store (CIS)
**3.1.1 Description**
The system shall provide a unified, persistent repository for all user information entities captured from integrated sources.

**3.1.2 Requirements**
*   **CIS.1:** The system shall store entities with mandatory metadata including, but not limited to: Source Application, Capture Timestamp, Global Unique ID (GUID), and Owner/User ID.
*   **CIS.2:** The system shall maintain the native format and binary content of original data items (e.g., `.doc`, `.eml` files) within the store.
*   **CIS.3:** The store shall be implemented as a single, managed database file (`ZNIXStore.db`) by default, with a defined schema for entities and relationships.

#### 3.2 User-Defined Hierarchical Model
**3.2.1 Description**
Users shall be able to create, modify, and visualize a tree hierarchy where nodes represent categories, projects, or concepts, and leaf nodes link to actual information entities.

**3.2.2 Requirements**
*   **HM.1:** The user shall be able to create, rename, move, and delete nodes in the hierarchy via the main user interface.
*   **HM.2:** The user shall be able to link any information entity in the CIS to one or more nodes in the hierarchy.
*   **HM.3:** The hierarchy shall be persisted independently of the physical location of archived entity content.

#### 3.3 Automated Data Capture
**3.3.1 Description**
The system shall monitor integrated applications and automatically import relevant information objects into the CIS.

**3.3.2 Requirements**
*   **ADC.1:** For Microsoft Outlook, the system shall capture incoming/outgoing email messages (Sender, Recipients, Subject, Body, Attachments) upon send/receive events.
*   **ADC.2:** For Internet Explorer, the system shall capture the URL, page title, and a local snapshot of visited web pages upon user command (e.g., a "Capture to ZNIX" browser extension).
*   **ADC.3:** For Microsoft Word, the system shall capture document metadata (Title, Author, Keywords) and the file path upon save or close events.
*   **ADC.4:** The user shall be able to configure capture rules and enable/disable monitoring per application.

#### 3.4 Archival to Removable Media
**3.4.1 Description**
Users shall be able to move the physical content of less-frequently accessed entities to removable media (CD-R, USB drive) to free local disk space.

**3.4.2 Requirements**
*   **ARM.1:** The user shall be able to select one or more entities or hierarchy nodes for archival.
*   **ARM.2:** Upon archival, the system shall move the primary content file(s) to the specified removable media root directory, maintaining a relative path structure.
*   **ARM.3:** The CIS shall retain the entity's metadata and hierarchy links, updating its internal record to point to the new removable media location (e.g., `F:\Archive\2023\ProjectX\document.doc`).
*   **ARM.4:** When an archived entity is requested, if its media is not available, the system shall display a clear message indicating the required media volume label.

#### 3.5 Public API for Client Applications
**3.5.1 Description**
A documented Application Programming Interface (API) shall expose core framework functionality to allow development of custom ZNIX-aware clients.

**3.5.2 Requirements**
*   **API.1:** The API shall provide functions for querying the CIS (e.g., `FindEntitiesByKeyword(keyword)`, `GetEntitiesInNode(nodeId)`).
*   **API.2:** The API shall provide functions for managing entities and relationships (e.g., `CreateEntity(metadata)`, `LinkEntityToNode(entityId, nodeId)`).
*   **API.3:** The API shall be exposed as a set of COM interfaces for Windows environment integration.

#### 3.6 Proxy Mechanism for Non-Aware Applications
**3.6.1 Description**
The system shall provide a method for applications not designed for the ZNIX API to still interact with the framework's data.

**3.6.2 Requirements**
*   **PRO.1:** The system shall implement a virtual filesystem driver or shell namespace extension that presents the user's ZNIX hierarchy as a browseable folder structure within Windows Explorer.
*   **PRO.2:** Accessing a "file" in this virtual structure shall trigger the framework to retrieve the actual entity from the CIS or prompt for archived media.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Main Application UI:** A two-pane interface similar to Windows Explorer. The left pane displays the user's hierarchical model tree. The right pane displays the contents (entities) of the selected node. It shall include a menu bar and toolbar for core actions (New Node, Capture, Archive, Search).
*   **Configuration Dialog:** A tabbed dialog for managing integrated applications, capture rules, and storage settings.

#### 4.2 Hardware Interfaces
*   The system must be able to read from and write to standard removable media interfaces as presented by Windows OS (e.g., USB Mass Storage, CD/DVD-ROM).

#### 4.3 Software Interfaces
*   **Microsoft Outlook:** Integration via Outlook COM Object Model (e.g., `Application`, `Explorer`, `MailItem` interfaces).
*   **Microsoft Internet Explorer:** Integration via Browser Helper Object (BHO) or toolbar extension using the IE COM API.
*   **Microsoft Word:** Integration via Word COM Object Model (e.g., `Application`, `Document` interfaces) for event handling.
*   **Windows Shell:** Integration via Shell Namespace Extension API to provide the virtual folder view.

#### 4.4 Communications Interfaces
Not applicable for this single-user, non-networked release.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   **PER.1:** The framework shell process (`ZNIXShell.exe`) shall not exceed **40 MB** of working set memory during typical operation.
*   **PER.2:** The time to populate the main hierarchy tree view upon application startup shall be less than 5 seconds for a store containing 10,000 entities.
*   **PER.3:** A simple keyword search across 10,000 entity metadata records shall return results in less than 2 seconds.

#### 5.2 Safety Requirements
*   **SAF.1:** The system shall include safeguards to prevent accidental corruption of the central store database due to application or system crashes (e.g., via transactional commits).

#### 5.3 Security Requirements
*   **SEC.1:** The system shall validate and sanitize all input from third-party application interfaces to guard against injection of malicious remote scripts via email or web content.
*   **SEC.2:** The user shall be prompted for confirmation before performing destructive operations (e.g., deleting a hierarchy node with linked entities, formatting the store).
*   **SEC.3:** Access to the framework's configuration and data store shall be limited to the currently logged-in Windows user.

#### 5.4 Software Quality Attributes
*   **REL.1:** The Mean Time Between Failures (MTBF) for the core framework shall exceed **3 months** of continuous operation. A "failure" is defined as an unhandled exception requiring application restart.
*   **MAI.1:** The database schema shall be versioned, and the system shall include a utility to migrate a store from a previous schema version to the current one.
*   **POR.1:** The system shall be portable across the two specified Windows operating system versions without code modification.

### 6. Acceptance Criteria
The product will be considered acceptable when the following conditions are met:

1.  All requirements marked "shall" in Sections 3 (System Features) for the core centralized store (CIS) and hierarchical management (HM) are fully implemented and verified.
2.  Successful demonstration of data capture from at least two of the specified third-party applications (e.g., Outlook and Internet Explorer).
3.  The system passes all test cases verifying the non-functional requirements for memory usage (40 MB limit) and performance benchmarks.
4.  The source code for the framework is released under the LGPL license, and all tools are released under the GPL license.
5.  The installation package passes the Windows Logo compatibility tests for Windows XP.
