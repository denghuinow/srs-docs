## 1. Introduction

### 1.1 Purpose
This document specifies the requirements for the Reversible Lane Control System (RLCS) replacement software for Interstate 15 peak-hour traffic management. It serves as a comprehensive description of all system functionalities, interfaces, and performance criteria for developers, testers, and project stakeholders.

### 1.2 Scope
The system replaces aging reversible lane control software to manage lane configurations for morning/evening commutes and special events.

#### 1.2.1 In-Scope
- Graphical user interface for system monitoring and control
- Automated sequencing of lane opening/closing operations
- Real-time device status monitoring and command validation
- Secure data processing and integrity verification
- System reporting and logging capabilities
- Integration with external systems via data store

#### 1.2.2 Out-of-Scope
- Traffic flow algorithms and optimization logic
- Public traveler information systems
- Physical infrastructure changes or hardware modifications
- Direct field hardware interfaces (beyond driver software)

### 1.3 Definitions & Acronyms

| Term | Definition |
|------|------------|
| RLCS | Reversible Lane Control System |
| ATMS-2 | Advanced Traffic Management System |
| ATIS | Advanced Traveler Information System |
| TMC | Traffic Management Center |
| FCU | Field Control Unit |
| MD5 | Message Digest Algorithm 5 |

## 2. Overall Description

### 2.1 Product Perspective
The system replaces the legacy RLCS application within Caltrans District 11's traffic operations center. It operates as a standalone application that integrates with existing enterprise systems through an external server data store.

### 2.2 Product Functions

#### 2.2.1 Core Functional Areas
1. **Graphical User Interface (GUI)**
   - Real-time system status monitoring
   - Device control and configuration management
   - User access control and security management

2. **Process Monitoring & Control**
   - Real-time device status tracking
   - Command validation and execution
   - System health monitoring

3. **Sequencing Operations**
   - Automated lane opening/closing sequences
   - Scheduled operations for peak hours and events
   - Manual override capabilities

4. **Data Processing & Security**
   - Encrypted database operations
   - Data integrity verification
   - Secure communication protocols

5. **Reporting System**
   - Operational logs and audit trails
   - Performance summaries
   - Safety compliance reporting

### 2.3 User Characteristics

| User Role | Access Level | Primary Responsibilities |
|-----------|-------------|--------------------------|
| Operator | Read/Write Control | Daily lane configuration, real-time monitoring, command execution |
| Management | Read-Only | System status review, report generation, operational oversight |
| Field Maintenance | Limited Control | Maintenance mode operations, manual device overrides, field testing |
| System Administrator | Full Access | System configuration, security setup, user management, rule configuration |

### 2.4 Constraints
- **Communication Infrastructure**: Must use fiber optic primary and ISDN secondary communications
- **Wireless Prohibition**: No wireless communication systems permitted
- **Deployment Strategy**: No parallel operation with legacy system; full field testing required before legacy system decommissioning
- **External Interface**: External server data store updates limited to once per minute

### 2.5 Assumptions & Dependencies
- Existing field hardware remains operational and compatible
- External systems (ATMS-2, ValuePricing/FasTrak) maintain current interface specifications
- Sufficient network bandwidth available for real-time operations
- Trained personnel available for system operation and maintenance

## 3. System Features

### 3.1 Graphical User Interface (GUI)

#### 3.1.1 Real-time Monitoring Interface
**Requirement ID:** GUI-001  
**Description:** The system shall provide a graphical representation of the reversible lane system status.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Display current lane configuration (open/closed/transition)
- Show real-time device status with color-coded indicators
- Update status displays within 2 seconds of state change

#### 3.1.2 Control Interface
**Requirement ID:** GUI-002  
**Description:** The system shall provide control mechanisms for lane configuration changes.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Single-click initiation of standard sequences
- Confirmation dialogs for critical operations
- Role-based access to control functions

### 3.2 Process Monitoring & Control

#### 3.2.1 Device Status Monitoring
**Requirement ID:** PMC-001  
**Description:** The system shall monitor and display real-time status of all field devices.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Status updates received within 2 seconds of device state change
- Alert generation for device failures or communication loss
- Historical status tracking for troubleshooting

#### 3.2.2 Command Validation
**Requirement ID:** PMC-002  
**Description:** The system shall validate all commands before execution.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Pre-execution safety checks completed
- Command sequence validation against current system state
- Rollback capability for failed operations

### 3.3 Sequencing System

#### 3.3.1 Automated Sequence Execution
**Requirement ID:** SEQ-001  
**Description:** The system shall execute predefined lane opening and closing sequences.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Complete sequence execution within specified timeframes
- Progressive status updates during sequence execution
- Automatic pause/resume on system fault detection

#### 3.3.2 Manual Override
**Requirement ID:** SEQ-002  
**Description:** The system shall allow authorized manual intervention in automated sequences.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Role-based override permissions
- Audit logging of all manual interventions
- Safe transition between automated and manual modes

### 3.4 Data Processing & Security

#### 3.4.1 Data Integrity
**Requirement ID:** SEC-001  
**Description:** The system shall implement MD5 hashing for data integrity verification.  
**Priority:** Must Have  
**Acceptance Criteria:**
- 128-bit MD5 hash generation for critical data transactions
- Daily integrity verification checks
- Alert generation on integrity check failures

#### 3.4.2 Secure Storage
**Requirement ID:** SEC-002  
**Description:** The system shall store sensitive data in encrypted format.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Password encryption using industry-standard algorithms
- Non-volatile memory storage for critical configuration data
- Secure erase capabilities for decommissioned devices

### 3.5 Reporting System

#### 3.5.1 Operational Reporting
**Requirement ID:** REP-001  
**Description:** The system shall generate operational summary reports.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Daily operational summaries including lane configuration changes
- System performance metrics
- Exception and error reporting

#### 3.5.2 Compliance Reporting
**Requirement ID:** REP-002  
**Description:** The system shall generate safety compliance reports.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Audit trails of all system operations
- Safety procedure compliance verification
- Regulatory requirement documentation

## 4. External Interface Requirements

### 4.1 External Server Data Store

#### 4.1.1 Data Export Interface
**Requirement ID:** EXT-001  
**Description:** The system shall provide one-way status updates to external systems via data store.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Lane status (open/closed) updates
- Customer eligibility information for ValuePricing/FasTrak
- Maximum update frequency: once per minute
- Data format compatibility with ATMS-2 specifications

### 4.2 Remote Access Interface

#### 4.2.1 Secure Remote Administration
**Requirement ID:** EXT-002  
**Description:** The system shall support secure remote dial-in access for administrators.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Two-way communication through enterprise firewall
- Multi-factor authentication for remote access
- Encrypted communication channels
- Session logging and monitoring

## 5. Non-Functional Requirements

### 5.1 Availability Requirements

**Requirement ID:** NFR-AVAIL-001  
**Description:** The system shall maintain 24/7/365 operation.  
**Priority:** Must Have  
**Acceptance Criteria:**
- 99.99% uptime requirement
- Maximum annual downtime: 50 minutes
- Automated failover to degraded mode
- No single point of failure

### 5.2 Performance Requirements

#### 5.2.1 Response Time
**Requirement ID:** NFR-PERF-001  
**Description:** The system shall meet specified response time requirements.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Device status updates: ≤ 2 seconds
- Command execution: ≤ 12 seconds
- GUI refresh rate: ≤ 1 second
- Report generation: ≤ 30 seconds

#### 5.2.2 Reliability
**Requirement ID:** NFR-REL-001  
**Description:** The system shall operate continuously without requiring reboots.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Continuous operation ≥ 30 days without reboot
- Automatic recovery from communication failures
- Degraded-mode operation during partial system failures

### 5.3 Security Requirements

#### 5.3.1 Data Security
**Requirement ID:** NFR-SEC-001  
**Description:** The system shall implement comprehensive data security measures.  
**Priority:** Must Have  
**Acceptance Criteria:**
- MD5 hashing (128-bit) for all critical data
- Encrypted password storage
- Secure communication protocols
- Regular security audit compliance

#### 5.3.2 Access Control
**Requirement ID:** NFR-SEC-002  
**Description:** The system shall enforce role-based access control.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Four distinct user roles with appropriate permissions
- Session timeout for inactive users
- Failed login attempt limitations
- Comprehensive audit logging

### 5.4 Safety Requirements

**Requirement ID:** NFR-SAFE-001  
**Description:** The system shall incorporate fail-safe operational principles.  
**Priority:** Must Have  
**Acceptance Criteria:**
- Default to safe state on system failure
- Manual override capabilities for emergency operations
- Redundant critical components
- Regular safety system self-tests

## 6. Acceptance Criteria

### 6.1 Performance Validation
1. **Uptime Verification**
   - Demonstrate 99.99% availability over 30-day test period
   - Document all downtime incidents with root cause analysis

2. **Response Time Validation**
   - Measure and verify device status updates ≤ 2 seconds
   - Validate command execution within 12-second threshold
   - Conduct performance testing under peak load conditions

### 6.2 Reliability Testing
1. **Continuous Operation**
   - 30-day continuous operation test without system reboot
   - Monitoring of system stability and resource utilization

2. **Failover Testing**
   - Simulated TMC failure with transition to FCU control
   - Verification of degraded-mode functionality
   - Recovery testing after simulated failures

### 6.3 Security Verification
1. **Integrity Checks**
   - Daily MD5 hash verification validation
   - Data corruption detection and recovery testing
   - Encryption algorithm implementation verification

2. **Access Control**
   - Role-based permission testing for all user types
   - Authentication and authorization validation
   - Audit log completeness and accuracy
