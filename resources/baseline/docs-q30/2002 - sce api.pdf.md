## 1. Introduction

### 1.1 Purpose
This document specifies the requirements for the Standard Co-Emulation Modeling Interface (SCE-MI), which provides a standardized C/C++ interface for connecting untimed software models executing on host workstations to structural hardware netlists representing Devices Under Test (DUT) on emulation or verification platforms.

### 1.2 Scope
The SCE-MI standard defines a common interface that replaces proprietary emulator APIs, enabling high-performance verification of System-on-Chip (SoC) designs through co-emulation. The interface specifically facilitates communication between software testbenches and hardware DUTs but does not support:
- Event-based simulation
- Direct software model-to-software model bridging
- Real-time simulation interfaces

## 2. Overall Description

### 2.1 Product Perspective
SCE-MI serves as a bridge between software simulation environments and hardware emulation platforms, addressing critical industry challenges with proprietary emulator APIs that restrict software portability and reduce verification productivity.

### 2.2 Product Functions
- Message-based communication channels between software models and hardware DUTs
- Bidirectional message flow management
- Clock control mechanisms for time synchronization
- Multi-clock domain support with configurable parameters
- Software-to-hardware binding infrastructure

### 2.3 User Characteristics

#### 2.3.1 End Users
- Verification engineers connecting untimed testbenches to RTL DUTs
- Require minimal effort interface with transactor models hiding complexity

#### 2.3.2 Transactor Implementors
- Develop plug-and-play models for specific hardware interfaces
- Create abstraction layers between software models and hardware protocols

#### 2.3.3 Infrastructure Implementors
- Provide SCE-MI implementations on verification platforms
- Enable seamless co-emulation between software and hardware components

### 2.4 Constraints
- Dependent on correct instantiation of hardware side macros within bridge netlists
- Assumes SystemC usage for untimed models
- Requires compatible emulation platforms with SCE-MI infrastructure support
- Infrastructure linkage must generate parameter files for software-hardware binding

### 2.5 Assumptions and Dependencies
- Users employ SystemC for untimed modeling
- Emulation platforms provide necessary infrastructure support
- Hardware netlists properly instantiate SCE-MI macros
- Parameter files are correctly generated by infrastructure linkage

## 3. Specific Requirements

### 3.1 Functional Requirements

#### 3.1.1 Message-Based Communication

**REQ-COM-001:** The system shall provide message-based communication channels between software models and hardware DUTs.

**REQ-COM-002:** The interface shall support bidirectional message flow with separate input and output channels.

**REQ-COM-003:** Message ports shall support parameterized widths to accommodate varying data sizes.

**REQ-COM-004:** Message ports shall implement configurable priority levels for message handling.

#### 3.1.2 Clock Control

**REQ-CLK-001:** The system shall enable clock control for freezing emulation time during message processing.

**REQ-CLK-002:** The interface shall support multiple clock domains with configurable frequency ratios.

**REQ-CLK-003:** Clock domains shall support configurable phase relationships.

**REQ-CLK-004:** All controlled clocks shall maintain precise edge alignment across domains.

#### 3.1.3 Software-Hardware Binding

**REQ-BND-001:** The infrastructure shall provide mechanisms for binding software models to hardware components.

**REQ-BND-002:** Binding shall be configurable through parameter files generated by infrastructure linkage.

**REQ-BND-003:** The system shall support dynamic binding and unbinding of software models.

### 3.2 External Interface Requirements

#### 3.2.1 Hardware Side Interfaces

```verilog
// Message Port Macros
SceMiMessageInPort(parameters)
SceMiMessageOutPort(parameters)

// Clock Control Macros
SceMiClockControl(parameters)
SceMiClockPort(parameters)
```

**REQ-HW-001:** Hardware interfaces shall provide message port macros for data transmission.

**REQ-HW-002:** Clock control macros shall manage timing synchronization between software and hardware.

#### 3.2.2 Software Side Interfaces

**REQ-SW-001:** The system shall provide C++ API interfaces for software side access.

**REQ-SW-002:** The system shall provide C API interfaces for software side access.

**REQ-SW-003:** Software interfaces shall include message port proxy classes for abstraction.

**REQ-SW-004:** Binding methods shall be available through software APIs.

#### 3.2.3 Infrastructure Linkage

**REQ-INF-001:** Infrastructure linkage shall analyze bridge netlists to extract connection parameters.

**REQ-INF-002:** The system shall generate parameter files required for software-hardware binding.

### 3.3 Performance Requirements

**REQ-PER-001:** The interface shall prevent communication bottlenecks with emulators.

**REQ-PER-002:** Performance shall match native emulator capabilities without degradation.

**REQ-PER-003:** Message delivery between software and hardware shall maintain reliability with zero data loss.

**REQ-PER-004:** Multi-clock synchronization shall maintain precise alignment within specified tolerances.

### 3.4 Design Constraints

**REQ-DC-001:** The interface design shall be compatible with major emulation platforms.

**REQ-DC-002:** Implementation shall not require modifications to existing proprietary emulator APIs.

**REQ-DC-003:** The design shall support incremental adoption alongside existing verification methodologies.

### 3.5 Software System Attributes

#### 3.5.1 Reliability

**REQ-REL-001:** The system shall ensure reliable message delivery with error detection mechanisms.

**REQ-REL-002:** Clock synchronization shall maintain integrity throughout extended verification sessions.

#### 3.5.2 Availability

**REQ-AVL-001:** The interface shall be available for integration with all supported verification platforms.

**REQ-AVL-002:** API availability shall support continuous verification workflows.

#### 3.5.3 Security

**REQ-SEC-001:** The interface shall maintain data integrity during transmission between software and hardware.

## 4. Verification and Acceptance

### 4.1 Acceptance Criteria

**ACC-001:** Successful connection of untimed testbench to RTL DUT demonstrating functional message delivery.

**ACC-002:** Verification of clock control functionality with proper time freezing during message processing.

**ACC-003:** Demonstration of multi-clock support with correct synchronization across domains.

**ACC-004:** Performance validation showing no degradation compared to proprietary interfaces.

### 4.2 Priority Classification

#### 4.2.1 High Priority
- Untimed-to-RTL bridging functionality
- No performance degradation compared to proprietary interfaces
- Basic message delivery and clock control

#### 4.2.2 Medium Priority
- Multi-clock support with synchronization
- Parameterized message port configurations
- C and C++ API completeness

#### 4.2.3 Low Priority
- Advanced clock control features
- Extended error handling scenarios
- Optimization for specific use cases
