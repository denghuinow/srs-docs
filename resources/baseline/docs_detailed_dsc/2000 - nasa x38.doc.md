**Status:** Baseline

### 1. Introduction

#### 1.1 Purpose
This document defines the requirements for the X-38 Fault Tolerant System Services (FTSS) software. The FTSS provides a fault-tolerant, real-time operating environment for the Flight Critical Computer (FCC) of the X-38 Crew Return Vehicle. It serves as the middleware between NASA's flight application software and the underlying Motorola PowerPC hardware and VxWorks operating system.

#### 1.2 Scope
The FTSS encompasses the following core services:
*   **Scheduling:** Deterministic execution of application tasks at 50 Hz, 10 Hz, and 1 Hz rates.
*   **Communication:** Reliable, synchronous message passing between processors.
*   **Time Management:** Maintenance of Mission Elapsed Time (MET) and Separation Time (SEP).
*   **Memory Management:** Management of congruent and non-congruent memory regions.
*   **Fault Detection:** Continuous Built-In Test (BIT) for hardware components.
*   **Redundancy Management:** Reconfiguration of the system in response to faults.
*   **System Support:** Initialization, telemetry, and exception handling.

**Out of Scope:**
*   Non-hardware-related security features.
*   End-user training programs.
*   Logistics and physical deployment support beyond software delivery.

### 2. Overall Description

#### 2.1 Product Perspective
The FTSS is a middleware component within the X-38 FCC architecture. It abstracts the complexities of the quad-redundant hardware and real-time OS, providing a simplified, fault-tolerant API to the flight application software.

**System Interfaces:**
1.  **Flight Application Software:** Consumes the FTSS API.
2.  **VxWorks 5.4 Operating System:** Provides low-level tasking, memory, and I/O services.
3.  **FCC Hardware (Motorola PowerPC, Radstone Boards):** The physical execution platform.
4.  **Network Elements (NEs):** Provide inter-processor communication.
5.  **MPCC/CTC:** For command and telemetry exchange.

#### 2.2 Product Functions
The primary functions of the FTSS are:
1.  **System Initialization & Configuration:** Execute IBIT, synchronize processors, and establish operational state within 1.5 minutes of power-up.
2.  **Deterministic Scheduling:** Execute application tasks within defined 50 Hz, 10 Hz, and 1 Hz rate groups with minimal jitter.
3.  **Fault-Tolerant Communication:** Facilitate synchronous (frame-boundary) and immediate message passing between Virtual Groups (VGs).
4.  **Time Services:** Maintain and distribute MET and SEP with high accuracy (≤50 PPM drift).
5.  **Health Monitoring & Fault Detection:** Perform continuous BIT to detect processor, memory, and NE faults within 1 second.
6.  **Redundancy Management:** Reconfigure the system upon fault detection (e.g., degrade from quad to triplex) within 60 ms for an FCP failure.
7.  **Memory Management:** Manage congruent memory alignment and support recovery of failed channels.
8.  **Telemetry & Command Handling:** Transfer FTSS health and status data to the MPCC every 10 Hz frame (≤5.2 ms transfer time).

#### 2.3 User Characteristics
*   **Flight Software Application Developers:** Engineers familiar with real-time C programming who will use the FTSS API. They require detailed API documentation but not training on FTSS internals.
*   **System Integrators:** Personnel integrating the FTSS with FCC hardware and NASA application. They require interface control documents.
*   **Test & Verification Engineers:** Personnel responsible for validating FTSS against these requirements. They require testable requirements and interface hooks.
*   **Maintenance Personnel:** Support staff who may analyze fault logs and telemetry for troubleshooting.

#### 2.4 Constraints
*   **Real-Time Performance:** Must operate within strict 20 ms minor frames (50 Hz).
*   **High Reliability:** Must be two-fault tolerant for non-simultaneous hardware faults.
*   **Platform:** Must run on the specified Motorola PowerPC hardware with VxWorks 5.4.
*   **Language:** Implemented in the C programming language.
*   **Standards:** Documentation must adhere to MIL-STD-498.

#### 2.5 Assumptions and Dependencies
*   The underlying VxWorks OS and hardware function correctly within their specified parameters.
*   NASA application software uses the FTSS API as defined and does not directly call prohibited OS or hardware functions.
*   Fault recovery times for permanent hardware damage may require application-initiated power cycling.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Scheduling Services
*   **FR-SCH-001:** The FTSS scheduler shall execute tasks assigned to the 50 Hz, 10 Hz, and 1 Hz rate groups at their specified frequencies.
*   **FR-SCH-002:** Upon a 50 Hz timer interrupt, the scheduler shall complete its overhead operations (updating time, interrupting ICPs) within 1 millisecond before starting the first 50 Hz application task.
*   **FR-SCH-003:** The scheduler shall execute tasks within a rate group in strict priority order.
*   **FR-SCH-004:** If a task exceeds its allocated time within a rate group boundary (overrun), the scheduler shall report the overrun, terminate the task, and restart it at its next scheduled invocation.

##### 3.1.2 Communication Services
*   **FR-COM-001:** The FTSS shall provide message queue sockets for point-to-point communication between Virtual Groups (VGs).
*   **FR-COM-002:** Messages sent via synchronous message queues shall be delivered congruently to the receiving VG at the next minor frame boundary.
*   **FR-COM-003:** The FTSS shall provide broadcast pipes for one-to-many communication.
*   **FR-COM-004:** A message sent to a broadcast pipe shall be readable by all VGs configured to receive from that pipe.

##### 3.1.3 Time Services
*   **FR-TIME-001:** The FTSS shall initialize Mission Elapsed Time (MET) to zero upon the first 50 Hz frame of system operation.
*   **FR-TIME-002:** MET shall increment once per minor frame (20 ms) and maintain an accuracy with a drift of ≤50 parts per million (PPM).
*   **FR-TIME-003:** Upon receipt of a vehicle separation signal, the FTSS shall begin incrementing Separation Time (SEP) within one minor frame (20 ms).

##### 3.1.4 Fault Detection (BIT)
*   **FR-FD-001:** The FTSS shall perform continuous Built-In Test (BIT) on FCPs, ICPs, and Network Elements.
*   **FR-FD-002:** A processor (FCP/ICP) or NE fault shall be detected and diagnosed within 1 second of occurrence.
*   **FR-FD-003:** The FTSS shall detect a "babbling" NE or ICP (errant continuous transmission) and shall initiate masking within 40 milliseconds of detection.

##### 3.1.5 Redundancy Management
*   **FR-RM-001:** Upon detection of a faulty FCP, the system shall degrade from quad-redundant to triplex operation. The faulty FCP shall be masked from the voting set within 60 milliseconds.
*   **FR-RM-002:** If an ICP fails to send its expected heartbeat for two consecutive cycles, the FTSS shall mask that ICP.
*   **FR-RM-003:** For a masked faulty NE where alignment is permitted by the application, the FTSS shall initiate a voted reset and recovery sequence.

##### 3.1.6 Memory Management
*   **FR-MM-001:** The FTSS shall manage designated regions of DRAM as "congruent aligned" memory, maintaining bit-for-bit consistency across all healthy FCPs.
*   **FR-MM-002:** The FTSS shall support the reintegration of a recovered FCP channel by aligning its congruent memory with the active set. Alignment shall complete at a rate of at least 1 MB per second.

##### 3.1.7 System Initialization & Support
*   **FR-SYS-001:** Upon power-on or CPU reset, the FTSS shall execute Initiation BIT (IBIT) on all FCPs, ICPs, and MPCCs. Failures shall be logged.
*   **FR-SYS-002:** The FTSS shall synchronize the FCPs during startup. Any FCP failing to synchronize shall be excluded from the operational set.
*   **FR-SYS-003:** The FTSS shall transfer telemetry data containing system health, fault logs, and status to the MPCC/CTC during every 10 Hz major frame. This transfer shall complete within 5.2 milliseconds.
*   **FR-SYS-004:** The FTSS shall log all detected faults and software exceptions for access by the application and telemetry.

#### 3.2 External Interface Requirements

##### 3.2.1 Application Programming Interface (API)
*   **IR-API-001:** The FTSS shall provide a C-language API as defined in Draper Document 297752 for all services (scheduling, communication, time, etc.).
*   **IR-API-002:** The API shall return defined status codes for all function calls.

##### 3.2.2 Network Element (NE) Interface
*   **IR-NE-001:** The FTSS shall exchange descriptor and data blocks with NEs for inter-processor communication.
*   **IR-NE-002:** The latency for a packet exchange from an ICP to an FCP shall be ≤200 µs.
*   **IR-NE-003:** The latency for a broadcast packet shall be ≤150 µs.

##### 3.2.3 FCP-ICP Interface
*   **IR-FI-001:** The FTSS on the FCP shall write a shared memory block (containing frame number, MET, SEP) and assert a VME interrupt to signal the start of a 50 Hz cycle to all ICPs.
*   **IR-FI-002:** The skew of the VME interrupt across all ICPs shall be ≤330 µs.

##### 3.2.4 MPCC/CTC Interface
*   **IR-MPCC-001:** The FTSS shall communicate with the MPCC via a serial link configured in SDLC mode for command and telemetry.

#### 3.3 Performance Requirements
*   **PR-PERF-001:** The combined overhead of the scheduler and time services per 50 Hz minor frame shall not exceed 1 millisecond.
*   **PR-PERF-002:** Telemetry data transfer to the MPCC shall not exceed 5.2 ms per 10 Hz frame.
*   **PR-PERF-003:** Memory alignment for recovery shall complete at a rate of ≥1 MB/second.
*   **PR-PERF-004:** The system shall initialize from power-up to a state ready for normal 50 Hz operation within 1.5 minutes.

#### 3.4 Design Constraints
*   **DC-001:** The software shall be implemented in C.
*   **DC-002:** The software shall run on the VxWorks 5.4 real-time operating system.
*   **DC-003:** The software shall use only the subset of VxWorks services explicitly permitted by the FTSS API manual.
*   **DC-004:** FTSS telemetry data shall be limited to a bandwidth of 5000 bps.

#### 3.5 Software System Attributes

##### 3.5.1 Reliability
*   **SA-REL-001:** The system shall be tolerant of any two non-simultaneous hardware faults.
*   **SA-REL-002:** The system shall attempt recovery of a failed FCP channel within 1.5 minutes of fault detection, provided the fault is not permanent.

##### 3.5.2 Safety
*   **SA-SAF-001:** The FTSS shall include a watchdog timer that must be reset every minor frame. Failure to reset shall trigger a processor reset.
*   **SA-SAF-002:** The FTSS shall implement a RAM scrub algorithm to detect and correct SEUs, operating at a rate of 10 MB per 8 minutes, with a CPU duty cycle not exceeding 1%.

##### 3.5.3 Maintainability
*   **SA-MAIN-001:** All fault events and significant state changes shall be logged with a timestamp and made available to the application for inclusion in telemetry.

#### 3.6 Acceptance Criteria
The criteria below map to the functional requirements and serve as the basis for formal acceptance testing.

*   **AC-Fault-1:** Given an operational quad-redundant FCP set, when an FCP processor is artificially failed, then the system shall degrade to triplex operation within 60 milliseconds and report the fault via telemetry.
*   **AC-Sched-1:** Given a 50 Hz timer interrupt, when the scheduler executes, then it shall complete its overhead tasks within 1 millisecond and start the first 50 Hz application task.
*   **AC-Com-1:** Given a message queue socket between an FCP and an ICP, when a message is sent synchronously, then it shall be delivered and readable by the receiver at the next minor frame boundary.
*   **AC-Time-1:** Given system startup, when the first 50 Hz frame occurs, then MET shall be initialized to zero and shall increment each subsequent frame with an accuracy of ≤50 PPM.

### 4. Supporting Information

#### 4.1 Domain Model
Key conceptual entities managed by the FTSS:
*   **Virtual Group (VG):** A logical grouping of processors (e.g., the quad FCP set, a simplex ICP).
*   **Task:** An application function scheduled by the FTSS.
*   **Rate Group:** A collection of tasks scheduled at a specific frequency (50 Hz, 10 Hz, 1 Hz).
*   **Socket:** A communication endpoint (Message Queue or Pipe).
*   **Fault Log:** A record of a detected anomaly.
*   **Memory Region:** A defined area of memory with specific consistency properties.

#### 4.2 Risk Management
| Risk | Mitigation Strategy |
| :--- | :--- |
| NE/ICP babbling overwhelms network. | Detect within 20 ms, mask within 40 ms. |
| Memory alignment impacts real-time performance. | Limit alignment to 4 MB of critical DRAM. |
| Asymmetric I/O calls cause FCP skew. | Restrict I/O calls to maintain synchronization. |
| Radiation-induced SEUs corrupt memory. | Implement background RAM scrub; report errors. |

#### 4.3 Open Issues
1.  **Issue:** Final implementation of memory protection violation policy (e.g., task restart).
    *   **Responsible:** Draper/NASA joint decision.
2.  **Issue:** Handling scenarios with more than two simultaneous faults.
    *   **Responsible:** NASA to define mission-critical requirements.
3.  **Issue:** Final telemetry data format and integration details.
    *   **Responsible:** Draper/NASA coordination.
4.  **Issue:** Validation of all fault recovery time bounds (e.g., 1.5-minute recovery).
    *   **Responsible:** Draper testing with NASA review.
