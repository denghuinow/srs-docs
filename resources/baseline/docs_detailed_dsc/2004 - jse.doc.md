### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Automated ISIN Issuance System. The system will enable the Johannesburg Stock Exchange (JSE), in its capacity as the National Numbering Agent (NNA), to electronically issue, cancel, and deregister International Securities Identification Numbers (ISINs) for Money Market Instruments (MMIs) via SWIFT messaging. The intended audience includes stakeholders from the JSE (ASD, C&S), STRATE, the Money Market Forum (MMF), and the development team.

#### 1.2 Scope
The system's scope encompasses:
*   Development of a backend service to send, receive, validate, and process proprietary SWIFT MT598 messages for ISIN lifecycle management.
*   Implementation of business logic for generating ZAM-prefixed ISINs compliant with ANNA/ISO 6166 guidelines.
*   Provision of a secure internal web-based front-end application for JSE Clearing & Settlement (C&S) staff to monitor activity, perform manual overrides under Business Continuity Plan (BCP) conditions, and generate reports.
*   Management of the full ISIN lifecycle: Issuance (NEWM), Cancellation (DISS), and Deregistration at Maturity (MATU).

**Out of Scope:**
*   Handling top-ups or reductions in issuance amounts for existing ISINs.
*   Management of ISINs for instrument types other than Money Market Instruments (e.g., equities, bonds).
*   Direct interaction with MMF Participants/Issuers; all communication is via STRATE.

### 2. Overall Description

#### 2.1 Product Perspective
The system is a new, standalone application that integrates with the JSE's operational technology landscape. It acts as an intermediary between STRATE's systems (via SWIFT) and the JSE's internal operational databases and users.

**System Interfaces:**
1.  **SWIFT Alliance Gateway:** The primary external interface for bidirectional exchange of MT598 messages with STRATE.
2.  **Front-End Web Interface:** An internal interface for JSE C&S operational monitoring and control.
3.  **Email Server:** For sending automated alerts to the JSE C&S team.
4.  **Database:** For persistent storage of ISIN records, message logs, and audit data.

#### 2.2 Stakeholders and User Classes
| Stakeholder / User Class | Description | Key Interests |
| :--- | :--- | :--- |
| **Money Market Forum (MMF)** | Represents issuers and investors. Defines business needs. | Automated, efficient ISIN issuance process that supports market dematerialization. |
| **STRATE (CSD/IOR)** | Central Securities Depository. Initiates requests and pays for service. | Reliable, fast, and accurate automated ISIN issuance via SWIFT. Clear error handling and confirmations. |
| **JSE (NNA)** | System owner and National Numbering Agent. | Compliant, reliable, and maintainable system that fulfills its NNA mandate. |
| **JSE Application & Service Division (ASD)** | Internal development team. | Clear, testable requirements and stable interfaces for development and maintenance. |
| **JSE Clearing & Settlement (C&S)** | Primary internal users/operators. | Effective monitoring tools, clear alerts, and a robust BCP manual process. |
| **MMF Participants/Issuers** | Entities issuing MMIs. | Timely receipt of ISINs for their instruments. |

#### 2.3 Operating Environment
*   **Software:** The backend service will run on a JSE-standard application server (OS to be determined). It will connect to a relational database (e.g., Oracle, SQL Server) and the JSE's SWIFT Alliance Gateway.
*   **Hardware:** Standard JSE server infrastructure meeting performance and availability SLAs.
*   **Network:** Secure connection to the SWIFT network, adhering to SWIFT security protocols including Bilateral Key Exchange (BKE).

#### 2.4 Design and Implementation Constraints
1.  **Compliance:** ISIN generation logic must strictly adhere to ISO 6166 and ANNA guidelines.
2.  **Messaging Standard:** Must use the SWIFT MT598 message format as finalized and approved by the NMPG/MMF.
3.  **Security:** All SWIFT communication must comply with SWIFT's security policy. Internal system access must be role-based.
4.  **Legacy Consideration:** The system must maintain a consistent and accurate record of all ISINs issued, including those manually entered during BCP.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** STRATE will have validated issuer and instrument data before sending an MT598-150 request.
*   **Assumption:** The final MT598 message specifications and error codes will be agreed upon with STRATE/NMPG prior to final development.
*   **Dependency:** Successful BKE setup with STRATE for secure SWIFT communication.
*   **Dependency:** Formal sign-off and cost approval from STRATE for the project.

### 3. Specific Requirements

#### 3.1 Functional Requirements

**3.1.1 SWIFT Message Processing (Backend Service)**
*   **FR1.1:** The system shall receive and parse incoming SWIFT MT598 messages from STRATE.
*   **FR1.2:** The system shall validate the format of all incoming MT598 messages against the agreed SWIFT standard (ISO 15022/ANNA). *[See Undecided Issue #1]*
*   **FR1.3:** If format validation (FR1.2) fails, the system shall generate and send an MT598-901 (Format Rejection) message to STRATE.
*   **FR1.4:** The system shall validate the business content of incoming MT598-150 messages (e.g., valid issuer code, dates in correct sequence, mandatory fields present).
*   **FR1.5:** The system shall check for duplicate requests based on a unique transaction reference or key instrument details.
*   **FR1.6:** If content validation (FR1.4, FR1.5) fails, the system shall generate and send an MT598-902 (Content Rejection) message to STRATE, including a specific error code. *[See Undecided Issue #2]*
*   **FR1.7:** Upon receiving a valid MT598-150-NEWM (New Issue) request, the system shall generate a new, unique ISIN with the prefix "ZAM".
*   **FR1.8:** The system shall persist all details of the newly issued ISIN, including its status as 'Active'.
*   **FR1.9:** The system shall generate and send an MT598-151 (Confirmation) message back to STRATE for every successfully processed MT598-150 request, containing the relevant ISIN and details.
*   **FR1.10:** Upon receiving a valid MT598-150-DISS (Cancel) request for an active ISIN, the system shall update the ISIN's status to 'Cancelled' and send an MT598-151 confirmation.
*   **FR1.11:** Upon receiving a valid MT598-150-MATU (Maturity) request on the instrument's maturity date, the system shall update the ISIN's status to 'Deregistered' and send an MT598-151 confirmation.
*   **FR1.12:** The system shall log every incoming and outgoing SWIFT message (full details) to a database for audit and troubleshooting.
*   **FR1.13:** The system shall process incoming MT598-901/902 rejection messages from STRATE (e.g., for a faulty confirmation), log them, and trigger an alert.

**3.1.2 Front-End User Interface (Monitoring & BCP)**
*   **FR2.1:** The system shall provide a secure login for authorized JSE C&S personnel.
*   **FR2.2:** The system shall provide a screen for the manual creation (override) of an ISIN record, to be used only during a declared BCP event. This screen shall enforce data validation rules consistent with backend logic.
*   **FR2.3:** The system shall create a permanent audit record for every manually entered ISIN, capturing the user ID, timestamp, and reason.
*   **FR2.4:** The system shall provide search screens to query the ISIN database by: ISIN code, Issuer Participant Code, date range (issue, maturity), and status (Active/Cancelled/Deregistered).
*   **FR2.5:** The system shall display search results in a data grid, showing all relevant instrument and issuance details.
*   **FR2.6:** The system shall allow users to generate and print reports of issued, cancelled, and deregistered ISINs for a specified period.
*   **FR2.7:** The system shall provide a dedicated screen to view all recent system-generated rejections (MT598-901/902 sent or received) with error details.
*   **FR2.8:** The system shall provide a mechanism (e.g., admin screen) for JSE C&S to maintain a list of valid Issuer Participant Codes. *[See Undecided Issue #4]*

**3.1.3 Alerting and Reporting**
*   **FR3.1:** The system shall immediately send an email alert to a configured distribution list of JSE C&S staff whenever the system generates a rejection message (MT598-901/902) to STRATE.
*   **FR3.2:** The system shall immediately send an email alert when a rejection message (MT598-901/902) is received from STRATE.
*   **FR3.3:** Email alerts shall contain key details: Transaction Reference, Error Code, Error Description, and timestamp.

#### 3.2 Non-Functional Requirements

**3.2.1 Performance**
*   **NFR1:** The system shall be capable of processing a peak load of **500 ISIN issuance requests per day**.
*   **NFR2:** The end-to-end processing time for a valid ISIN request (from receipt of MT598-150 to sending MT598-151) shall be **under 5 minutes** under normal load to support T+0 settlement.

**3.2.2 Reliability & Availability**
*   **NFR3:** System availability shall meet or exceed the targets defined in the **Service Level Agreement (SLA) with STRATE**. *[See Undecided Issue #3]*
*   **NFR4:** The system shall implement a **Business Continuity Plan (BCP)** allowing for manual ISIN entry via the front-end during a prolonged SWIFT or system outage.

**3.2.3 Security**
*   **NFR5:** All SWIFT message exchanges shall be secured using **Bilateral Key Exchange (BKE)** as per SWIFT policy.
*   **NFR6:** Access to the front-end monitoring system shall be restricted via **role-based authentication** (e.g., JSE Active Directory). Only authorized JSE C&S personnel shall have access.
*   **NFR7:** All sensitive data (e.g., ISIN records, logs) shall be stored securely in the database with access controlled by the application.

**3.2.4 Compliance**
*   **NFR8:** The ISIN generation algorithm and data management shall be fully compliant with **ISO 6166** and **ANNA Guidelines**.
*   **NFR9:** SWIFT message structures shall comply with the **ISO 15022** standard and the agreed NMPG market practice.

**3.2.5 Observability & Maintainability**
*   **NFR10:** The system shall maintain a complete, immutable log of all SWIFT transactions, system actions, and user (front-end) actions for a minimum of **7 years** for audit purposes.
*   **NFR11:** System health and performance metrics (e.g., queue length, processing time, error rates) shall be exposed for monitoring by JSE's standard operational tools.

### 4. System Models

#### 4.1 Use Case Model (Summary)
*   **UC-01:** Process New ISIN Request (MT598-150-NEWM)
*   **UC-02:** Process ISIN Cancellation Request (MT598-150-DISS)
*   **UC-03:** Process ISIN Deregistration Request (MT598-150-MATU)
*   **UC-04:** Handle Message Format Rejection (MT598-901)
*   **UC-05:** Handle Message Content Rejection (MT598-902)
*   **UC-06:** Manually Issue ISIN (BCP Override)
*   **UC-07:** Search and View ISIN Records
*   **UC-08:** Generate ISIN Reports

#### 4.2 Data Model (Core Entities)
```sql
-- Simplified Entity-Relationship Representation
ENTITY ISIN_Record {
    PK ISIN_Code (String, Format: ZAMXXXXXXXXX)
    Status (Enum: Active, Cancelled, Deregistered)
    Issue_Date (Date)
    FK Issuer_Participant_Code (String)
    Quantity_Issued (Decimal)
    FK Financial_Instrument_ID (Integer)
    FK Issuance_Details_ID (Integer)
}

ENTITY Financial_Instrument {
    PK Instrument_ID (Integer)
    Generic_Category (Integer, 1-4)
    MMI_Type (String, e.g., 'EBA', 'NCD')
    Short_Description (String)
}

ENTITY Issuer {
    PK Participant_Code (String)
    -- Other issuer details as required
}

ENTITY SWIFT_Message_Log {
    PK Transaction_Reference (String)
    Message_Type (String, e.g., '150-NEWM', '151', '901')
    Direction (Enum: Incoming, Outgoing)
    Related_Reference (String)
    Preparation_Datetime (DateTime)
    Message_Content (Text/XML)
    Status (Enum: Received, Processed, Rejected)
}

ENTITY Rejection_Record {
    PK Rejection_ID (Integer)
    Error_Code (String) -- e.g., "DUP_REQ", "INV_ISS"
    Error_Details (Text)
    FK Related_Message_Ref (String)
}
```

### 5. Appendices

#### 5.1 Acceptance Criteria (Detailed)
*   **AC-01 (New Issuance):** Given a correctly formatted and valid MT598-150-NEWM message from STRATE, when processed, then a new, unique ZAM-prefixed ISIN is saved with status 'Active', and an MT598-151 confirmation is sent to STRATE containing that ISIN.
*   **AC-02 (Duplicate Rejection):** Given an MT598-150-NEWM message with a Transaction Reference that has already been processed, when validated, then no new ISIN is created, and an MT598-902 rejection with error code "DUPLICATE_REQUEST" is sent to STRATE.
*   **AC-03 (Manual BCP Entry):** Given a JSE C&S user is on the manual entry screen during a declared BCP event, when they enter valid instrument data and submit, then a new ISIN record is created with an audit trail, and the status is set to 'Active'.
*   **AC-04 (Rejection Alert):** Given the system generates an MT598-902 rejection for an invalid issuer code, when the rejection is sent, then an email is immediately dispatched to the JSE C&S team containing the error code and the related Transaction Reference.
