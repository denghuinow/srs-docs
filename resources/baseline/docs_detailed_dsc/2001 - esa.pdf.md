### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the ASPERA-3 Processing and Archiving Facility (APAF). The APAF is the ground data system responsible for the acquisition, processing, archiving, distribution, and public submission of scientific data from the ASPERA-3 instrument aboard the Mars Express (MEX) spacecraft. This document serves as the authoritative source of requirements for developers, testers, project managers, and stakeholders.

#### 1.2 Scope
The APAF system will:
*   Acquire raw ASPERA-3 and MEX Orbit/Attitude (OA) telemetry from the European Space Operations Centre (ESOC) via the NASA Integrated Services Network (NISN).
*   Process raw telemetry into calibrated scientific data products in the standard Instrument Data File Set (IDFS) format.
*   Maintain a secure, local archive of all raw, intermediate, and processed data.
*   Distribute processed data to the ASPERA-3 Co-Investigator (Co-I) team within a 24-hour Service Level Agreement (SLA).
*   Provide password-protected and public web-based displays of processed data.
*   Submit validated, PDS-compliant data sets to the NASA Planetary Data System (PDS) within six months of data acquisition.

**Out of Scope:**
*   Operating in multiple, complex states or modes.
*   Posing any safety hazards to personnel or equipment.
*   Imposing specific, formal training requirements for software developers.
*   Direct control of the ASPERA-3 instrument on Mars Express.

### 2. Overall Description

#### 2.1 Product Perspective
APAF is a standalone ground data processing system. It interfaces with external entities for data input (ESOC), data output (Co-Is, PDS), and operator interaction. The system is not part of the spacecraft command chain.

**System Interfaces:**
*   **ESOC DDS (Inbound):** Source of raw telemetry.
*   **NISN (Bi-directional):** Transport layer for all external data transfer.
*   **Local SwRI Archive (Outbound):** Primary storage for all data products.
*   **Co-I Distribution (Outbound):** Mechanism for delivering IDFS to the science team.
*   **NASA PDS (Outbound):** Final destination for validated, public data.
*   **Web Server (Bi-directional):** Host for data displays and configuration uploads.
*   **Operations Console (Inbound):** Interface for system monitoring and control.

#### 2.3 Operating Environment
*   **Hardware:** Standard server-class hardware located at SwRI, with sufficient processing power and storage for mission-long data volumes.
*   **Software:** Operating System and supporting software to be determined during design phase. Core APAF software will be custom-developed.
*   **Network:** Connected to the NASA Integrated Services Network (NISN) for all external communications.

#### 2.4 Design and Implementation Constraints
1.  **Data Format Compliance:** All PDS-submitted data must adhere to NASA PDS standards.
2.  **IDFS Format:** Internal processed data must use the IDFS standard.
3.  **Configuration-Driven:** Telemetry parsing and plot generation must be configurable via external files (DDID, VIDF, PIDF).
4.  **NASA Program Requirements:** Development must follow applicable NASA software engineering requirements.

#### 2.5 Assumptions and Dependencies
*   ESOC will deliver telemetry data daily via the agreed-upon NISN interface.
*   The Data Disposition Interface Document (DDID) will be provided by ESOC in a timely manner.
*   The NASA NISN will provide a reliable network connection.
*   The local SwRI archive system will be highly available and scalable.

### 3. System Features and Requirements

#### 3.1 Feature: Telemetry Acquisition and Validation
**Description:** The system shall automatically acquire and validate raw telemetry files from ESOC.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F1.1** | The system shall connect to the ESOC Data Disposition System (DDS) via NISN to check for and retrieve new ASPERA-3 and MEX OA telemetry files on a daily schedule. | High |
| **F1.2** | The system shall validate the integrity (e.g., checksum, file size) of incoming telemetry files. | High |
| **F1.3** | The system shall log the acquisition of each telemetry file, including source, timestamp, and validation status. | Medium |

#### 3.2 Feature: Telemetry Processing to IDFS
**Description:** The system shall process raw or cleaned telemetry into calibrated IDFS data sets for each ASPERA-3 virtual instrument.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F2.1** | The system shall generate cleaned-up telemetry intermediate files if they are not provided directly by ESOC. | High |
| **F2.2** | The system shall apply instrument-specific calibration algorithms (as defined in VIDFs) to cleaned telemetry to produce IDFS data sets. | High |
| **F2.3** | Each IDFS data set shall be tagged with a Virtual Instrument ID, creation date, data version, and calibration level. | High |
| **F2.4** | The system shall process a full day's worth of telemetry to produce IDFS data sets for all virtual instruments within 24 hours of telemetry receipt. | High |

#### 3.3 Feature: Data Archiving
**Description:** The system shall persistently store all data products in a local archive.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F3.1** | The system shall archive the original raw telemetry files received from ESOC. | High |
| **F3.2** | The system shall archive all intermediate cleaned telemetry files. | High |
| **F3.3** | The system shall archive all final IDFS data sets. | High |
| **F3.4** | The system shall create and maintain an index (Archive Record) for each archived file, containing data type, file path, ingest date, and size. | Medium |

#### 3.4 Feature: Data Distribution to Co-Investigators
**Description:** The system shall distribute processed data products to the ASPERA-3 science team.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F4.1** | The system shall distribute the latest IDFS data sets and relevant intermediate files to all designated ASPERA-3 Co-Is. | High |
| **F4.2** | Distribution shall occur automatically upon successful processing and archiving of a data set. | High |
| **F4.3** | The system shall complete distribution to all Co-Is within 24 hours of error-free telemetry acquisition. | High |
| **F4.4** | The system shall log each distribution event (recipient, data set, time, status). | Medium |

#### 3.5 Feature: Web-Based Data Display
**Description:** The system shall generate and update web-based displays for both public and science team access.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F5.1** | The system shall generate plots, summaries, and listings based on IDFS data and Plot Interface Definition Files (PIDF). | High |
| **F5.2** | The system shall update a public website (`www.ASPERA-3.org`) with non-sensitive data and plots. | High |
| **F5.3** | The system shall update a password-protected science analysis website with access to the full suite of processed data and displays. | High |
| **F5.4** | Access to the science website shall require individual user authentication. | High |

#### 3.6 Feature: PDS Data Submission
**Description:** The system shall support the preparation and submission of data to the NASA Planetary Data System.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F6.1** | The system shall provide tools for operators to validate and calibrate data sets for PDS readiness. | High |
| **F6.2** | The system shall format validated IDFS data sets into PDS-compliant bundles. | High |
| **F6.3** | The system shall submit the final data bundles to NASA PDS. | High |
| **F6.4** | Submission to PDS shall occur no later than six (6) months after the acquisition of the corresponding telemetry. | High |

#### 3.7 Feature: System Operations and Error Handling
**Description:** The system shall provide monitoring, control, and robust error handling.

| **Req ID** | **Requirement Description** | **Priority** |
| :--- | :--- | :--- |
| **F7.1** | The system shall provide an operations console for monitoring system status and logs. | Medium |
| **F7.2** | Upon detecting a processing error or data corruption, the system shall log the error in detail, halt the affected processing stream, and alert the operator via system logs. | High |
| **F7.3** | The system shall allow an operator to initiate re-processing of any data set from archived sources. | High |
| **F7.4** | The system shall not delete or corrupt source data in the archive during a processing failure. | High |

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **APAF Operations Console:** A command-line or simple graphical interface for system status, log viewing, and manual process control (e.g., trigger re-processing).
*   **Web Interfaces:** Public and password-protected websites for data browsing and plotting.

#### 4.2 Hardware Interfaces
*   **NISN Connection:** Standard network interface card and connection to the NASA Integrated Services Network.
*   **Archive Storage:** Connection to Network-Attached Storage (NAS) or Storage Area Network (SAN) for the local SwRI archive.

#### 4.3 Software Interfaces
*   **ESOC DDS Interface:** Protocol and format defined by the Data Disposition Interface Document (DDID). APAF will act as a client pulling data.
*   **Local Archive API:** Interface (e.g., filesystem, database) for storing and retrieving archive records and files.
*   **PDS Submission Interface:** Submission protocol as defined by the NASA PDS (e.g., FTP, API).

#### 4.4 Communications Interfaces
*   All external data transfers (ESOC, Co-I, PDS) shall occur over the secured NISN network using agreed-upon protocols (e.g., SFTP).

### 6. Acceptance Criteria
The following test scenarios define the minimum criteria for system acceptance:

1.  **Daily Processing SLA Test:** *Given* new ASPERA-3 telemetry is available from ESOC, *when* the APAF system executes its daily processing, *then* IDFS data sets for all virtual instruments are created and archived within 24 hours.
2.  **Co-I Distribution Test:** *Given* a validated IDFS data set is ready for distribution, *when* the distribution process runs, *then* all designated ASPERA-3 Co-I's receive the data electronically, as verified by distribution logs.
3.  **Error Handling Test:** *Given* a simulated processing error occurs (e.g., corrupt telemetry packet), *when* the system encounters the error, *then* it logs the error with sufficient detail, halts the affected process, and notifies the operator without corrupting any previously archived data.
4.  **PDS Compliance Test:** *Given* a calibrated mission data set, *when* the PDS submission process is executed, *then* the data is delivered to PDS in a format that passes PDS validation tools, and this occurs within the 6-month deadline.
