### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Tactical Control System (TCS) Block 0. It serves as the authoritative source for developers, testers, project managers, and other stakeholders to understand the system's capabilities, constraints, and interfaces. The intended audience includes the System Engineering IPT, Software Development IPT, Test & Evaluation IPT, and Program Management.

#### 1.2 Scope
The TCS is a joint-service command, control, data receipt, processing, export, and dissemination system. Its primary purpose is to provide a common human-computer interface (HCI) for the control of present and future tactical Unmanned Aerial Vehicles (UAVs), specifically the Predator (Medium Altitude Endurance - MAE) and Outrider (Tactical UAV - TUAV), and to simplify their integration into joint Command, Control, Communications, Computers, and Intelligence (C4I) infrastructure.

**In-Scope (Block 0):**
*   Mission planning, validation, upload, and execution for supported UAVs.
*   Real-time control and monitoring of UAV flight and payloads (EO/IR/SAR).
*   Processing, display, and limited exploitation of received imagery/data.
*   Dissemination of imagery products and tactical messages to external C4I systems.
*   Handling of Loss of Link (LOL) scenarios.
*   Mission handover between TCS instances.
*   Concurrent control of two MAE-class UAVs.
*   Dedicated Training and Maintenance modes of operation.
*   System startup, recovery, and fault detection.

**Out-of-Scope (Non-Goals):**
*   Conducting formal training concurrently with live mission operations.
*   Any requirement for nuclear safety considerations or hardening.
*   Support for UAVs or payloads not explicitly identified in the referenced Operational Requirements Documents (ORDs).

### 2. Overall Description

#### 2.1 Product Perspective
The TCS is a mission-critical, software-intensive system that operates as the central control node within a larger UAV ecosystem. It interfaces with UAVs (via data links), data terminals (LOS/SATCOM), multiple external C4I battlefield management systems, and internal components like data servers and intercoms. It is a standalone system but must be interoperable within a network of tactical systems.

#### 2.2 User Classes and Characteristics

| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **UAV Operator** | Trained in flight dynamics, payload operation, and TCS HCI. | Execute mission plans, manually control UAV/payload, monitor telemetry, handle contingencies (e.g., LOL). |
| **Mission Planner** | Trained in mission planning tools, terrain analysis, and threat assessment. | Create, modify, and validate detailed UAV mission plans (route, payload, comms). |
| **Maintenance Personnel** | Certified technicians with knowledge of TCS hardware/software. | Perform diagnostics, repair/replace LRUs, install software updates, conduct preventive maintenance. |
| **C4I System Operator** | User of external systems (e.g., AFATDS, ASAS). | Receive and act upon UAV-derived data (imagery, target messages) sent from TCS. |
| **Training Personnel** | Instructor qualified on TCS operations. | Use TCS in Training Mode to simulate missions and train operators without live assets. |
| **System Administrator** | Privileged user with deep system knowledge. | Install major software upgrades, modify system parameters, perform debugging. |

#### 2.3 Operating Environment
*   **Hardware:** Shelter-based or shipboard workstations, data terminals, servers, storage arrays (RAID), and networking equipment.
*   **Software:** Built upon the DII/COE foundation. Host Operating System per COTS specifications. Includes GOTS middleware (UCP/CMP) for C4I interfaces.
*   **Physical:** Must withstand tactical deployment environments (temperature, humidity, shock, vibration) as specified in system design documents.
*   **Security:** Must process and transmit classified information. Requires compliance with DoD 5200.28(D) and NSA-approved encryption for external links.

#### 2.4 Design and Implementation Constraints
1.  **Architecture:** Must follow an open, modular architecture to support multiple UAV types and future upgrades.
2.  **Compliance:** Software shall be DII/COE and JTA compliant. The entire system shall be Year 2000 compliant.
3.  **COTS/NDI:** Maximum use of Commercial Off-The-Shelf and Non-Developmental Item hardware and software is mandated.
4.  **Safety:** Design must incorporate safeguards to prevent single-point failures from generating unsafe UAV commands.

#### 2.5 Assumptions and Dependencies
*   Assumes UAVs comply with defined standard interface protocols for command and telemetry.
*   Assumes external C4I systems are available and configured per interface control documents.
*   Dependent on timely provision of threat data, terrain data, and UAV performance models.
*   Dependent on successful security accreditation by the Designated Approving Authority (DAA).

### 3. System Features and Requirements

#### 3.1 Mission Planning and Management (F-0100)
**3.1.1 Description:** The system shall provide tools for the creation, modification, validation, storage, and retrieval of comprehensive UAV mission plans.
**3.1.2 Requirements:**
*   **F-0101:** The system shall allow an operator to graphically create and edit a flight route plan consisting of a sequence of waypoints (latitude, longitude, altitude, airspeed).
*   **F-0102:** The system shall allow an operator to create and edit a payload plan, specifying sensor types (EO, IR, SAR), modes, and tasks associated with waypoints or areas.
*   **F-0103:** The system shall allow an operator to create and edit a communications plan, specifying data link schedules and parameters.
*   **F-0104:** The system shall provide a mission validation function that checks the mission plan against UAV performance constraints (e.g., max/min altitude, turn radius, fuel), threat zones, and terrain data.
*   **F-0105:** If validation detects a fault, the system shall present a clear notification to the operator describing the fault and shall prevent mission upload until the operator acknowledges and overrides the fault or modifies the plan.

#### 3.2 UAV Command, Control, and Monitoring (F-0200)
**3.2.1 Description:** The system shall enable the uploading of mission plans to the UAV and provide real-time command and monitoring capabilities.
**3.2.2 Requirements:**
*   **F-0201:** The system shall upload a validated mission plan to a selected UAV via the established data link.
*   **F-0202:** The system shall display real-time UAV telemetry including, but not limited to, position (latitude, longitude, altitude), attitude, airspeed, groundspeed, fuel state, and system health status.
*   **F-0203:** The system shall provide the operator with Level 1-5 control interfaces (as per UAV ORDs) for direct manual control of the UAV's flight path and payload pointing.
*   **F-0204:** The system shall initiate and monitor automatic launch and recovery sequences for UAVs supporting Level 5 interaction.
*   **F-0205:** The system shall support the dynamic retasking of a UAV during flight, allowing the operator to modify the active flight route or payload tasking.

#### 3.3 Loss of Link (LOL) Handling (F-0300)
**3.3.1 Description:** The system shall automatically detect and respond to a loss of downlink communication with a UAV.
**3.3.2 Requirements:**
*   **F-0301:** Upon detection of downlink loss, the system shall automatically start a configurable LOL timer and display the last known UAV state and status.
*   **F-0302:** The system shall continuously compute and display the estimated UAV position based on its last known state and the active flight plan.
*   **F-0303:** The system shall automatically attempt to re-establish the data link.
*   **F-0304:** The system shall provide a clear visual indication when the UAV is estimated to be executing its pre-programmed LOL procedures (e.g., return to base) upon timer expiry.

#### 3.4 Payload Data Processing and Exploitation (F-0400)
**3.4.1 Description:** The system shall receive, process, display, and allow limited exploitation of payload sensor data (imagery/video).
**3.4.2 Requirements:**
*   **F-0401:** The system shall display live video streams from EO/IR payloads and radar imagery from SAR payloads.
*   **F-0402:** When an operator selects a point on a live video display, the system shall calculate and display the geographic coordinates (latitude, longitude) of that point.
*   **F-0403:** The system shall allow an operator to annotate still imagery or video freeze-frames with text, symbols, and geometric shapes.
*   **F-0404:** The system shall store all received payload data and operator-generated products in a searchable archive.

#### 3.5 C4I Interoperability and Dissemination (F-0500)
**3.5.1 Description:** The system shall exchange digital messages and imagery with external joint C4I systems.
**3.5.2 Requirements:**
*   **F-0501:** The system shall format and transmit compliant tactical messages (e.g., USMTF, VMF) to designated C4I systems (e.g., AFATDS, ASAS).
*   **F-0502:** The system shall format and transmit digital imagery products in NITF 2.0 (or later) format to designated C4I systems.
*   **F-0503:** The system shall output an RS-170A analog video signal (with optional graphical overlay) for distribution to systems such as CCTV.
*   **F-0504:** The system shall log all incoming and outgoing interface communications for audit and reconstruction purposes.

#### 3.6 Multi-UAV and Handover Operations (F-0600)
**3.6.1 Description:** The system shall manage multiple UAVs and facilitate control handover between TCS units.
**3.6.2 Requirements:**
*   **F-0601:** The system shall allow a single operator to concurrently control and monitor two (2) MAE-class UAVs using sequential communications.
*   **F-0602:** The system shall support the seamless handover of control for a UAV from one TCS instance to another, transferring the active mission plan and context.

#### 3.7 System Modes and Administration (F-0700)
**3.7.1 Description:** The system shall operate in distinct modes for Operations, Training, and Maintenance.
**3.7.2 Requirements:**
*   **F-0701:** The system shall complete a normal startup (power-on to operational state) in ≤ 60 seconds.
*   **F-0702:** The system shall complete a recovery from a standby state to an operational state in ≤ 45 seconds.
*   **F-0703:** In Training Mode, the system shall simulate all UAV and interface behaviors without connecting to live assets, except for pre-defined training messages to external simulators.
*   **F-0704:** In Maintenance Mode, the system shall provide diagnostic tools for testing TCS hardware components (workstation, data terminal) and for installing software updates.

### 4. External Interface Requirements

#### 4.1 UAV Interface (IF-001)
*   **Type:** Bidirectional, Digital Data Link (LOS & SATCOM)
*   **Purpose:** Uplink of command/control messages; Downlink of telemetry and payload data.
*   **Requirements:** Shall support concurrent uplink/downlink. Shall use a generic architecture with AV-specific modules to support Predator (MAE) and Outrider (TUAV) initially.

#### 4.2 Data Terminal Control Interface (IF-002)
*   **Type:** Bidirectional, Serial/Network
*   **Purpose:** Control of antenna pointing (azimuth, elevation), mode selection, and transmitter/receiver parameters (frequency, power).
*   **Requirements:** Shall support simultaneous control of LOS and SATCOM terminals. Shall provide both automatic (tracking) and manual control modes.

#### 4.3 C4I Digital Interface (IF-003)
*   **Type:** Bidirectional, Network (TCP/IP)
*   **Purpose:** Exchange of USMTF/VMF messages and NITF imagery with battlefield systems (AFATDS, ASAS, JSTARS, etc.).
*   **Requirements:** Shall utilize DII/COE UCP/CMP GOTS software. Shall include error-checking and acknowledgment protocols.

#### 4.4 External Data Storage Interface (IF-004)
*   **Type:** Bidirectional, Peripheral
*   **Purpose:** Import of mission planning data (maps, threats); Export of mission data and imagery products for archiving.
*   **Requirements:** Shall support standard media including CD-ROM, magnetic tape, and RAID arrays.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   **PER-001:** The system shall maintain a throughput utilization of ≤ 50% of its maximum capability over any rolling 10-second period during normal operations.
*   **PER-002:** The response time from an operator command input to system acknowledgment shall be ≤ 1.0 second, 95% of the time.

#### 5.2 Reliability, Availability, and Maintainability (RAM)
*   **REL-001:** The system shall meet or exceed the Mean Time Between Failures (MTBF), Mean Time To Repair (MTTR), and Operational Availability (Ao) thresholds specified in the Predator and Outrider UAV ORDs.

#### 5.3 Security Requirements
*   **SEC-001:** The system shall be accredited per the requirements of DoD Directive 5200.28(D).
*   **SEC-002:** All external communications links (UAV, C4I) shall be secured using NSA-approved encryption commensurate with the classification level of the data transmitted.

#### 5.4 Observability and Logging
*   **OBS-001:** The system shall record (log) all operator inputs, system-generated warning and error messages, and all communications sent/received via external interfaces. Logs must be sufficient to support post-mission event reconstruction and performance analysis.

### 6. Other Requirements

#### 6.1 Acceptance Criteria
*   **AC-01 (Mission Validation):** Given a mission plan with waypoints violating UAV altitude constraints, when the operator requests validation, the system must notify the operator of the fault and prevent upload until the fault is acknowledged/overridden.
*   **AC-02 (Payload Exploitation):** Given a UAV streaming live EO video, when the operator selects a point on the display, the system must calculate/display its geographic coordinates and allow annotation.
*   **AC-03 (LOL Handling):** Given a UAV in autonomous flight loses downlink, when the LOL timer expires, the system must display the estimated UAV position and indicate LOL procedure execution.
*   **AC-04 (C4I Interoperability):** Given a target coordinate in TCS, when the operator sends it to AFATDS, the system must transmit a compliant VMF message and log the transaction.
