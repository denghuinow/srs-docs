# Software Requirements Specification (SRS)
## PHIN Outbreak Management System (OMS)
**Document Version:** 1.0
**Date:** 2023-10-27
**Status:** Baseline

### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Public Health Information Network (PHIN) Outbreak Management System (OMS). The primary purpose of this system is to provide a configurable platform for the investigation, monitoring, management, analysis, and reporting of public health events, including outbreaks and acts of bioterrorism. This document serves as a contract between stakeholders and the development team, ensuring a common understanding of the system's capabilities.

#### 1.2 Document Conventions
*   **Shall / Must**: Indicates a mandatory requirement.
*   **Should**: Indicates a desirable, but not mandatory, requirement.
*   **May / Could**: Indicates an optional feature or capability.
*   **Italics**: Used for emphasis and referencing external standards or entities.
*   `Code Blocks`: Used for technical examples or data structures.

#### 1.3 Scope
The scope of the OMS includes:
*   The creation and management of configurable health event investigations.
*   The capture and linkage of data related to cases, contacts, exposures, specimens, laboratory results, and travel history.
*   The creation of traceable links between entities to model disease transmission.
*   Integration with external systems for early event detection, countermeasure administration, laboratory processing, and surveillance.
*   Support for disconnected operations for field investigators.
*   Generation of analysis, visualizations, and reports.

**Out of Scope:**
*   Definition of specific network transport protocols or low-level implementation details.
*   The operational policies of public health agencies.
*   Hardware specifications for end-user devices.

#### 1.4 References
*   PHIN Messaging Guides
*   LOINC, SNOMED CT Vocabulary Standards
*   Relevant Public Health Information Privacy Regulations (e.g., HIPAA)

### 2. Overall Description

#### 2.1 Product Perspective
The OMS is a component within the larger PHIN ecosystem. It interacts with external systems as both a consumer and provider of data. It must be deployable in various architectures (client-server, web-based, with offline clients) to accommodate different public health jurisdictions' infrastructure.

#### 2.2 Product Functions (High-Level)
1.  **Health Event Management**: Create, configure, and manage health event records.
2.  **Entity & Case Management**: Register subjects (persons, animals, locations) and conduct case investigations.
3.  **Contact Tracing**: Identify, register, and manage exposure contacts, establishing relationships between entities.
4.  **Specimen & Lab Management**: Track specimen collection, generate test requests, and process laboratory results.
5.  **Questionnaire Administration**: Present dynamic, configurable electronic forms for data collection.
6.  **Data Exchange**: Securely send and receive data with partner systems using standardized messages.
7.  **Analysis & Reporting**: Generate line lists, aggregate counts, epi-curves, maps, and export datasets.
8.  **Disconnected Operations**: Allow data collection and storage offline with subsequent synchronization.
9.  **Audit Logging**: Record all significant user and system activities.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **Public Health Investigator** | Field-based; may have intermittent connectivity; requires intuitive, fast data entry. | Conduct case/contact interviews, collect data, complete questionnaires, trace exposure links. |
| **Laboratory Personnel** | Works within a Laboratory Information System (LIS); requires clear specimen and test data. | Process test requests, generate results, maintain chain of custody information. |
| **Public Health Response Coordinator** | Managerial role; needs dashboard views and summary reports. | Oversee event response, coordinate across teams/jurisdictions, authorize reports. |
| **System Administrator** | Technical role; requires deep system access for configuration. | Configure events, manage users/roles, monitor system health, deploy updates. |
| **Data Analyst** | Analytical role; requires robust data export and visualization tools. | Analyze aggregated data, create visualizations, generate statistical reports. |
| **Partner Organization User** | External user from another jurisdiction or agency. | Submit and receive case/contact/lab data, view shared investigation details. |

#### 2.4 Operating Environment
*   **Software**: Must be compatible with modern operating systems (Windows, macOS, mobile OS). Web components must support current versions of major browsers (Chrome, Firefox, Edge, Safari).
*   **Network**: Must operate in both connected and periodically disconnected environments.
*   **Integration**: Must support web service APIs (e.g., REST, SOAP) and standard health data exchange protocols (e.g., HL7).

#### 2.5 Design and Implementation Constraints
1.  The system **shall** use established vocabulary standards (LOINC, SNOMED CT) for all coded data elements in external exchanges.
2.  The data model **must** be highly configurable without requiring code changes to accommodate new event types.
3.  All external data exchanges **shall** adhere to published PHIN Messaging Guides.
4.  The system **must** comply with all applicable federal and state privacy and security regulations.

#### 2.6 Assumptions and Dependencies
*   **Assumption**: Partner organizations will implement compatible systems capable of sending/receiving PHIN-standard messages.
*   **Assumption**: Sufficient network bandwidth will be available for synchronization after extended offline periods.
*   **Dependency**: The availability and stability of external vocabulary code servers (e.g., for LOINC updates).
*   **Dependency**: The definition of detailed message implementation guides by the PHIN governing body.

### 3. System Features and Requirements

#### 3.1 Feature: Health Event Management
**Description:** The system shall allow authorized users to initiate and configure new public health event investigations.

**3.1.1 Functional Requirements:**
*   **FR-HE-01:** The system shall allow a user to create a new Health Event record.
*   **FR-HE-02:** The system shall automatically assign a unique, system-generated Event ID upon creation.
*   **FR-HE-03:** The system shall capture and store the following initial event details:
    *   Event Category (e.g., infectious disease, bioterrorism, environmental)
    *   Suspected Agent/Etiology
    *   Geographic Area of Concern
    *   Official Case Definition (configurable criteria)
    *   Start Date
    *   Event Status (e.g., pending, active, closed)
*   **FR-HE-04:** The system shall allow a System Administrator to configure event-specific data fields, entity types, and electronic questionnaires.

#### 3.2 Feature: Entity and Case Investigation
**Description:** The system shall support the registration of subjects and the detailed investigation of cases linked to a health event.

**3.2.1 Functional Requirements:**
*   **FR-CI-01:** The system shall allow a user to register a new Entity (e.g., Person, Animal, Location) and assign a unique Subject ID.
*   **FR-CI-02:** The system shall allow a user to initiate a Case investigation for a registered Entity within the context of an active Health Event.
*   **FR-CI-03:** The system shall automatically assign a unique, system-generated Case ID and link it to the Entity's Subject ID and the Health Event's Event ID.
*   **FR-CI-04:** The system shall present the user with a configurable electronic questionnaire to capture demographic, clinical, and epidemiological data for the case.
*   **FR-CI-05:** The system shall calculate and assign a Case Status (Suspect, Probable, Confirmed) based on the configured Case Definition and available data (e.g., lab results).
*   **FR-CI-06:** The system shall store key case information, including Diagnosis and Symptom Onset Date.

#### 3.3 Feature: Contact Exposure Tracing
**Description:** The system shall enable the identification, registration, and management of contacts exposed to a case.

**3.3.1 Functional Requirements:**
*   **FR-CT-01:** From a Case record, the system shall allow a user to create a new Exposure Contact record, linking a source Entity (the case) to an exposed Entity (the contact).
*   **FR-CT-02:** The system shall assign a unique Contact ID for the exposure relationship.
*   **FR-CT-03:** The system shall capture exposure details: Exposure Type, Start/End Dates, Proximity, and Setting.
*   **FR-CT-04:** The system shall allow a user to generate and export a work list of contacts, sortable by priority, geographic area, or exposure date.
*   **FR-CT-05:** The system shall visually represent relationships (links) between entities (cases and contacts) within an event.

#### 3.4 Feature: Specimen and Laboratory Workflow
**Description:** The system shall manage the lifecycle of a specimen from collection through laboratory testing and result reporting.

**3.4.1 Functional Requirements:**
*   **FR-LAB-01:** The system shall allow a user to record the collection of a Specimen from a Subject Entity, assigning a unique Specimen ID and capturing Collection Date/Time, Type, and Suspected Agent.
*   **FR-LAB-02:** The system shall allow a user to generate a Laboratory Test Request for one or more Specimens.
*   **FR-LAB-03:** The system shall transmit the Test Request to an external Laboratory System via a standardized message.
*   **FR-LAB-04:** Upon receipt of a Laboratory Result message, the system shall automatically parse the message, validate the Specimen ID, and link the result to the corresponding Specimen and its associated Case/Entity.
*   **FR-LAB-05:** The system shall update the affected Case Status based on laboratory result interpretation (e.g., result positive -> status changes to Confirmed).

#### 3.5 Feature: Disconnected Operations
**Description:** The system shall support full functionality for users operating on devices without a continuous network connection.

**3.5.1 Functional Requirements:**
*   **FR-DO-01:** The system shall allow a user to download relevant event, questionnaire, and entity data to a local device for offline access.
*   **FR-DO-02:** The system shall allow a user to perform all core investigative functions (create cases, enter data, trace contacts) while offline, storing data locally.
*   **FR-DO-03:** Upon re-establishing a network connection, the system shall automatically synchronize locally created and modified records with the central server.
*   **FR-DO-04:** The system shall detect and present synchronization conflicts (e.g., the same record modified by two users) for manual resolution according to configurable business rules.

#### 3.6 Feature: Data Exchange and Integration
**Description:** The system shall bi-directionally exchange data with external systems using standardized formats.

**3.6.1 Functional Requirements:**
*   **FR-INT-01:** The system shall send and receive Case and Exposure Contact messages with Surveillance/EED systems and Partner OM systems.
*   **FR-INT-02:** The system shall receive Administered Countermeasure messages from Countermeasure Administration systems and link them to the recipient Entity.
*   **FR-INT-03:** The system shall send Countermeasure Request messages.
*   **FR-INT-04:** The system shall provide a mapping interface to transform partner-specific or custom data fields to/from the internal OMS data model.
*   **FR-INT-05:** The system shall export aggregated or anonymized datasets in common formats (CSV, JSON) for external analytical tools (SAS, GIS, R).

#### 3.7 Feature: Reporting, Analysis, and Audit
**Description:** The system shall provide tools for generating reports, analyzing data, and maintaining a complete audit trail.

**3.7.1 Functional Requirements:**
*   **FR-REP-01:** The system shall generate standard reports, including line lists, aggregate case counts by demographics, and epi-curves.
*   **FR-REP-02:** The system shall provide visualization tools to generate maps based on case/contact location data.
*   **FR-REP-03:** The system shall log all user activities, including creates, reads, updates, and deletes, capturing: Activity ID, Timestamp, User ID, Activity Type, Target Record, and Description.
*   **FR-REP-04:** The system shall support re-evaluation of existing Case records against a modified Case Definition and provide a report of status changes.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The web-based interface shall follow responsive design principles for use on desktops, tablets, and smartphones.
*   The offline client interface shall be optimized for touch and stylus input where applicable.
*   All data entry forms shall provide clear validation messages and support skip patterns as defined in questionnaires.

#### 4.2 Hardware Interfaces
*   The system shall support printing case investigation forms and work lists from both online and offline clients.

#### 4.3 Software Interfaces
The system shall integrate with the following external systems as detailed in the provided matrix. All integrations shall be secured using industry-standard protocols (TLS, OAuth2 where applicable).

#### 4.4 Communications Interfaces
*   Synchronization between offline clients and the central server shall use a secure, efficient protocol capable of handling incremental updates.
*   All external system data exchanges shall occur over secure channels (e.g., HTTPS, SFTP).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   The system shall support concurrent users as defined by jurisdictional pandemic planning scenarios.
*   Analytical searches across cases and contacts using multiple criteria (date range, location, symptom) shall return results in under 5 seconds for 95% of queries.
*   The configuration engine shall allow administrators to add new fields to an active event's questionnaire without causing system downtime.

#### 5.2 Safety Requirements
*   N/A (No direct physical safety implications).

#### 5.3 Security Requirements
*   The system shall implement role-based access control (RBAC) to restrict data and functions according to user roles.
*   All Personally Identifiable Information (PII) and Protected Health Information (PHI) shall be encrypted at rest and in transit.
*   The system shall support the application of digital signatures to completed electronic questionnaires to ensure data integrity and non-repudiation.
*   All access shall be authenticated via a centralized identity management service.

#### 5.4 Software Quality Attributes
*   **Availability:** The core system shall maintain 99.5% uptime during business hours. A Continuity of Operations Plan (COOP) shall be in place for critical event response.
*   **Reliability:** Data loss during synchronization from disconnected operations shall be zero under normal conflict resolution scenarios.
*   **Maintainability:** The system shall be designed with modular components to allow for independent updates to configuration, data exchange, or reporting modules.
*   **Portability:** The offline client shall be capable of running on designated standard-issue field devices (specific OS TBD).
*   **Scalability:** The system architecture shall allow for the aggregation of data from multiple instances into a central data warehouse for large-scale event analysis.

### 6. Acceptance Criteria
The following high-level acceptance tests must pass for the feature set to be considered complete.

**AC-1: Case Investigation & Linking**
*   *Given* a health event "Event_Alpha" exists,
    *When* an investigator creates a new case for entity "Subject_123",
    *Then* the system creates a record with a unique "Case_XYZ" and links it to both "Event_Alpha" and "Subject_123".

**AC-2: Laboratory Result Integration**
*   *Given* case "Case_XYZ" has an associated specimen "Specimen_789",
    *When* a laboratory result message for "Specimen_789" is received,
    *Then* the system updates the laboratory result section of "Case_XYZ" with the new data.

**AC-3: Contact Tracing**
*   *Given* a confirmed case "Case_XYZ" is selected,
    *When* an investigator creates a contact record for entity "Subject_456",
    *Then* the system creates an exposure link where "Subject_123" is the source and "Subject_456" is the exposed entity.

**AC-4: Disconnected Mode**
*   *Given* an investigator's device is offline,
    *When* they complete a case questionnaire for a new entity,
    *Then* the data is saved locally. Upon reconnection and sync, the new case record appears in the central system.

### 7. Appendices

#### 7.1 Glossary
*   **Entity:** A subject of investigation (e.g., person, animal, location).
*   **Health Event:** A defined incident, such as an outbreak or bioterrorism act, under investigation.
*   **Case:** An instance of disease or condition in an entity, meeting a defined set of criteria, linked to a health event.
*   **Exposure Contact:** A documented interaction between a source entity and an exposed entity that may have led to disease transmission.
*   **PHIN:** Public Health Information Network.

#### 7.2 Data Model (Summary)
Core entities and their relationships are defined in the provided domain model. The implementable data model shall extend these with technical keys, versioning fields, and configuration metadata.
