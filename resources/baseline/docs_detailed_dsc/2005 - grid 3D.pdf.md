### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Grid 3D Application. It is intended to serve as a complete description of the system to be developed for stakeholders including Dr. Delmiro Fernandez-Reyes, Anthony Finkelstein, and the developer, Ben Tagger. This SRS will be the basis for design, implementation, testing, and project management.

#### 1.2 Scope
The Grid 3D Application is a visualization tool designed to display biological data in an interactive three-dimensional environment. Its primary purpose is to enable research scientists, particularly in parasitology and protein investigation, to visualize, investigate, and compare data attributes at a glance.

**In-Scope:**
*   Loading and parsing pre-formatted tab-delimited data files.
*   Rendering a 3D grid with data points plotted according to X, Y, Z coordinates.
*   Color-coding data points based on cluster membership.
*   Providing interactive manipulation of the 3D view (rotate, zoom, pan).
*   Enabling user interaction with individual data points to reveal names and detailed descriptions.
*   Basic selection and display of multiple points.
*   Running on Windows and Linux operating systems.

**Out-of-Scope (Non-Goals):**
*   Advanced statistical data analysis or data mining.
*   Integration with specific laboratory instruments or real-time data streaming.
*   Data editing or transformation within the application.
*   User management, authentication, or application-level security.
*   Replacing comprehensive data analysis suites (e.g., Matlab, R).

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **3D Grid:** The three-dimensional Cartesian coordinate system visualization space where data points are plotted.
*   **Data Point:** A single entity representing a biological sample or protein, defined by its coordinates and metadata.
*   **Cluster:** A group of data points considered similar based on pre-processed analysis; used for color-coding.
*   **MVP:** Minimum Viable Product.
*   **OS:** Operating System.
*   **SLA:** Service Level Agreement (used here for performance targets).

### 2. Overall Description

#### 2.1 Product Perspective
The Grid 3D Application is a new, standalone visualization tool. It operates independently but relies on correctly formatted input files, which are expected to be pre-processed by external tools (e.g., Matlab). It does not replace existing analysis tools but complements them by adding a dedicated 3D interactive visualization layer.

#### 2.3 Operating Environment
*   **Software:** Must be executable on Microsoft Windows (specified versions TBD) and common Linux distributions.
*   **Hardware:** Standard desktop or laptop computers with dedicated graphics hardware recommended for optimal performance with larger datasets (~2000 points).
*   **Dependencies:** Java Runtime Environment (JRE) version to be determined based on implementation.

#### 2.4 Design and Implementation Constraints
1.  **Technology:** The application shall be developed using platform-agnostic technologies (e.g., Java) to satisfy cross-platform requirements.
2.  **Deadline:** Version 1.0 must be ready for inclusion in a scientific paper by **March 2005**. This drives the need for a clear MVP scope.
3.  **Resources:** Development is primarily the responsibility of a single developer (Ben Tagger).

#### 2.5 Assumptions and Dependencies
*   Users will provide data files in the exact, pre-defined tab-delimited format.
*   Data pre-processing (normalization, clustering) is performed externally (e.g., using Matlab).
*   The operating environment is assumed to be secure; no sensitive data protection is required within the application itself.
*   A suitable Java 3D/OpenGL binding or graphics library is available for the chosen implementation language.

### 3. System Features and Requirements

#### 3.1 Functional Requirements

**3.1.1 Data File Handling**
*   **FR1.1:** The system shall provide a mechanism for the user to select and load a data file from the local filesystem.
*   **FR1.2:** The system shall validate the structure of the loaded file against the specified tab-delimited format.
*   **FR1.3:** If the file is malformed (FR1.2 fails), the system shall reject the file and display a clear error message to the user, indicating the nature of the format violation.
*   **FR1.4:** The system shall parse a valid data file, extracting axis labels from the header row and data points from subsequent rows.
*   **FR1.5:** The system shall handle files containing up to 2000 data points. Performance beyond this limit is not guaranteed and may result in a warning or failure to load.

**3.1.2 3D Visualization & Rendering**
*   **FR2.1:** The system shall render a 3D Cartesian grid upon successful loading of a valid data file.
*   **FR2.2:** The system shall plot each parsed `DataPoint` as a distinct graphical marker at coordinates corresponding to its `X_Value`, `Y_Value`, and `Z_Value`.
*   **FR2.3:** The color of each `DataPoint` marker shall be determined by its `Cluster_Number` field, using a distinct, visually separable color palette.
*   **FR2.4:** The axes of the 3D grid shall be labeled with the `X_Axis_Label`, `Y_Axis_Label`, and `Z_Axis_Label` text parsed from the data file header.

**3.1.3 User Interaction - View Manipulation**
*   **FR3.1:** The system shall allow the user to rotate the 3D grid view by clicking and dragging the mouse within the visualization window.
*   **FR3.2:** The system shall allow the user to zoom the 3D grid view in and out using the mouse scroll wheel.
*   **FR3.3:** The system shall allow the user to pan (move) the 3D grid view using a mouse drag action combined with a modifier key (e.g., Alt+drag or middle-button drag).
*   **FR3.4:** All view manipulations (rotate, zoom, pan) shall provide visual feedback with fluid, real-time updates to the rendered scene.

**3.1.4 User Interaction - Data Point Investigation**
*   **FR4.1:** When the user single-clicks on a rendered `DataPoint` marker, the system shall visually highlight the point (e.g., change size or border) and display its `Name` in a dedicated information panel or overlay.
*   **FR4.2:** When the user double-clicks on a rendered `DataPoint` marker, the system shall display the full `Description` field for that point in the information panel.
*   **FR4.3:** The system shall provide a method for selecting multiple `DataPoint` markers (e.g., Ctrl+click, or a simple rectangular selection box). The `Name` of all selected points shall be displayed.

**3.1.5 System Management**
*   **FR5.1:** The application shall launch from the OS and present its main interface within 30 seconds of user initiation.
*   **FR5.2:** The application shall produce visual output suitable for printing in black-and-white, ensuring clarity when color is not available.

#### 3.2 Non-Functional Requirements

**3.2.1 Performance**
*   **NFR1 - Startup Time:** The application shall present its main interface within 30 seconds of launch command execution on standard departmental hardware.
*   **NFR2 - Interaction Responsiveness:** User interface actions (point selection, view rotation initiation) shall provide visual feedback within 2 seconds. View manipulation (drag-rotate) shall be fluid with a perceived frame rate of >15 FPS.

**3.2.2 Reliability & Compatibility**
*   **NFR3 - Data Load Capacity:** The system shall successfully load and visualize data files containing up to 2000 `DataPoint` entries without crashing or hanging indefinitely.
*   **NFR4 - Cross-Platform Operation:** The core application functionality shall operate identically on both Microsoft Windows and Linux operating systems as specified in section 2.3.

**3.2.3 Usability**
*   **NFR5 - Learnability:** A research scientist with basic computer literacy shall be able to load a data file and perform basic view rotation without referring to a manual.
*   **NFR6 - Error Communication:** All error messages (e.g., file format errors) shall be displayed in plain language, clearly indicating the problem and suggesting a corrective action (e.g., "Error: Header row missing. Please ensure the first line contains X_LABEL, Y_LABEL, Z_LABEL.").

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Primary UI:** A single graphical window containing the 3D visualization canvas, a menu bar or button for file operations (`File -> Open`), and a persistent panel for displaying `DataPoint` information (name, description).
*   **Interaction:** Primary input via mouse (click, drag, scroll). Keyboard may be used for modifier keys (Ctrl, Alt).

#### 4.2 Hardware Interfaces
None specified.

#### 4.3 Software Interfaces
*   **File System:** The application shall read tab-delimited text files (.txt or .dat) from the user's local or network file system.
*   **Operating System:** The application shall execute as a standard process within the host OS (Windows/Linux), utilizing system APIs for file I/O and window management.
*   **Graphics Library:** The application shall interface with a 3D graphics API (e.g., OpenGL via JOGL, Java3D) for all rendering tasks.

#### 4.4 Communications Interfaces
None required for Version 1.0.

                         | - description (Str)|

#### 5.3 Data File Format Specification
The application expects a tab-delimited text file.
*   **Line 1 (Header):** `X_AXIS_LABEL<TAB>Y_AXIS_LABEL<TAB>Z_AXIS_LABEL`
*   **Subsequent Lines (Data):** `NAME<TAB>X_VALUE<TAB>Y_VALUE<TAB>Z_VALUE<TAB>CLUSTER_NUMBER<TAB>DESCRIPTION`
    *   `DESCRIPTION` field may contain tabs and should be parsed as the entire remaining content of the line.

**Example:**
```
Expression_Level    Motif_Density    Conservation
Gene_A    12.5    0.85    7.2    1    Encodes a surface protein.
Gene_B    8.2    0.45    5.1    2    Hypothetical protein.
```

### 6. Other Non-Functional Requirements

#### 6.1 Security
No application-level security features are required for Version 1.0. Security is assumed to be provided by the host operating environment.

#### 6.2 Maintainability
The source code shall be documented to allow a developer with knowledge of the chosen programming language and graphics library to understand and modify the core logic.

### 7. Acceptance Criteria
The application will be considered acceptable for Version 1.0 release when all scenarios below are satisfied during a demonstration to the stakeholders (Dr. Fernandez-Reyes and Anthony Finkelstein).

1.  **Data Load & Render Test:** The demonstrator loads a provided, valid test file with ~500 points. A 3D grid is displayed within 10 seconds. Points are plotted at correct relative positions and are color-coded by the `CLUSTER_NUMBER` column. Axes are labeled from the file header.
2.  **Point Interaction Test:** The demonstrator single-clicks a point. The point is visually highlighted and its `NAME` appears in the info panel. The demonstrator then double-clicks the same point, and its full `DESCRIPTION` is displayed.
3.  **View Manipulation Test:** The demonstrator clicks, drags, and releases the mouse on the grid. The view rotates smoothly in response to the drag direction. The demonstrator uses the scroll wheel to zoom the view in and out.
4.  **Error Handling Test:** The demonstrator attempts to load a deliberately malformed file (e.g., missing header). The application rejects the file and displays a clear, understandable error message.
5.  **Multi-Platform Check:** Evidence is provided (screenshot or live test) that the application runs successfully on both a Windows and a Linux machine, performing tests 1-3.
