## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the "Manage Indigent Defense Services" component of the Tarrant County Integrated Justice Information System (IJIS). The primary purpose is to provide a detailed description of the system to be developed, serving as a basis for agreement between stakeholders and as a guide for the development team.

### 1.2 Scope
The system will automate and streamline the end-to-end process for appointing, managing, and compensating court-appointed attorneys for indigent defendants in Tarrant County. This includes:
*   Managing requests for appointed counsel.
*   Determining and tracking indigency.
*   Maintaining and utilizing attorney rotation lists.
*   Appointing attorneys to cases.
*   Tracking attorney-defendant contact.
*   Processing attorney fee payments.
*   Generating compliance reports as mandated by the Texas Fair Defense Act and the Tarrant County Indigent Defense Plan.

**In-Scope:**
*   Core workflow from arrest/request through payment and reporting.
*   Integration with external justice and financial systems.
*   Management of attorney qualifications and lists.
*   Electronic record-keeping and signature capture.

**Out-of-Scope (Non-Goals):**
*   Full-fledged Case Management (handled by the external Court Case Management System - CCMS).
*   Management of retained (non-indigent) defense services.
*   Attorney timekeeping or practice management.
*   Defendant financial investigation beyond the submitted affidavit.

## 2. Overall Description

### 2.1 Product Perspective
The Manage Indigent Defense Services component is a module within the larger Tarrant County IJIS. It is a new system designed to replace and automate existing manual and paper-based processes. It must interoperate seamlessly with several external county systems.

### 2.2 User Classes and Characteristics (Stakeholders)
| User Class / Stakeholder | Primary Role / Interaction with System |
| :--- | :--- |
| **Defendant** | Subject of the process; provides financial information. Limited, read-only access to own appointment status. |
| **Magistrate** | Initiates the process; determines indigency; submits/waives request for counsel. |
| **Detention Facility Officer** | Inputs initial defendant data; schedules hearings. |
| **OAA Staff** | Core system operators; process requests, manage lists, coordinate notifications, generate reports. |
| **Defense Attorney** | Receives appointments; logs defendant contact; submits payment requests. |
| **District Attorney** | Notifies system of case filing decisions (accept/reject/modify charges). |
| **Judge (County/District)** | Reviews and approves attorney payment requests; approves attorney list applications; selects attorneys in capital cases. |
| **Court Coordinator** | Inputs court setting schedules and results. |
| **Auditor** | Receives approved payment orders for processing. |
| **Commissioners Court** | Approves claims for payment (system provides data/reports). |
| **Local Selection Committee** | Qualifies attorneys for capital cases (external to system, but their list is maintained). |
| **Presiding Administrative Judge** | Reviews appeals of disapproved payments. |
| **TFID** | External recipient of mandated compliance reports. |
| **System Administrator** | Manages user accounts, system configuration, and technical health. |

### 2.3 Operating Environment
*   **Hardware:** Hosted on Tarrant County secure servers or approved cloud infrastructure compliant with DIR standards.
*   **Software:** Web-based application accessible via standard browsers (Chrome, Edge, Firefox). Backend built on county-approved technology stack (.NET/Java).
*   **Networks:** Accessible over the county's secure intranet and via secure VPN for authorized external users (e.g., defense attorneys).

### 2.4 Design and Implementation Constraints
1.  **Legal Compliance:** The system must enforce business rules derived from Texas CCP and Government Code.
2.  **Integration:** Must support GJXDM-compliant data exchange with the CCMS.
3.  **Security:** Must comply with Texas DIR security standards and UETA for electronic records/signatures.
4.  **Accessibility:** Must meet WCAG 2.1 AA standards for public-facing components.

### 2.5 Assumptions and Dependencies
*   **Assumption:** External systems (CCMS, ECFS, SAP) will provide stable, documented APIs or interfaces for integration.
*   **Assumption:** Necessary legal authority for electronic signatures and records will be obtained.
*   **Dependency:** Project timeline is dependent on coordination with the CCMS vendor for integration.

## 3. Specific Requirements

### 3.1 Functional Requirements / Use Cases

#### 3.1.1 UC-1: Submit Request for Appointed Counsel
*   **Actor:** Magistrate
*   **Description:** Magistrate conducts indigency hearing, determines eligibility, and electronically submits a Request for Appointed Counsel (or a Waiver) to the OAA.
*   **Precondition:** Defendant is in custody and a hearing has been scheduled.
*   **Basic Flow:**
    1.  System presents defendant and case information (from CCMS/initial entry).
    2.  Magistrate reviews/enters financial affidavit details with defendant.
    3.  Magistrate makes indigency determination.
    4.  Magistrate applies electronic signature to the Request form.
    5.  System submits the signed Request and affidavit to the OAA workflow.
*   **Alternative Flow (Waiver):** Defendant waives right to counsel. Magistrate submits a signed Waiver form instead of a Request.
*   **Postcondition:** A Request or Waiver is recorded in the system and is pending OAA processing.

#### 3.1.2 UC-2: Process Request for Appointed Counsel
*   **Actor:** OAA Staff
*   **Description:** OAA receives a request, validates information, and appoints the next eligible attorney from the appropriate rotation list.
*   **Precondition:** A valid Request for Appointed Counsel has been submitted.
*   **Basic Flow:**
    1.  System alerts OAA of new request.
    2.  OAA confirms defendant is still in custody (via CCMS interface).
    3.  System checks for any existing attorney appointment for the defendant on related cases.
    4.  System identifies the correct attorney rotation list based on offense type/level.
    5.  System selects the next attorney on the list who is marked "Active."
    6.  System creates an Appointment record.
    7.  System automatically generates and sends notifications (email/fax) to the appointed attorney, detention facility, and defendant.
    8.  System logs the appointment in the integrated CCMS.
*   **Alternative Flow (Capital Case):** If the case is a capital felony with death penalty sought, the system routes the request to a designated District Court Judge for manual selection of two qualified attorneys from the Local Selection Committee list.
*   **Postcondition:** Attorney is officially appointed, and all relevant parties are notified.

#### 3.1.3 UC-3: Manage Defendant Contact
*   **Actor:** Defense Attorney
*   **Description:** Appointed attorney logs the date(s) of initial and subsequent contact with the defendant.
*   **Precondition:** Attorney has been appointed to a case.
*   **Basic Flow:**
    1.  Attorney accesses their dashboard of appointments.
    2.  Attorney selects a specific case.
    3.  Attorney enters the date and time of contact.
    4.  System records the contact and updates the case timeline.
*   **Postcondition:** Contact compliance is recorded for reporting and audit purposes.

#### 3.1.4 UC-4: Manage Defense Attorney Compensation
*   **Primary Actor:** Defense Attorney
*   **Secondary Actor:** Judge, Auditor
*   **Description:** Attorney submits a request for payment for services rendered, which is reviewed, approved, and sent for payment processing.
*   **Precondition:** Case activity or disposition has occurred warranting payment.
*   **Basic Flow:**
    1.  Attorney completes a detailed payment request form in the system, itemizing services and hours/fees.
    2.  Attorney submits the request electronically.
    3.  System routes the request to the presiding judge for the case.
    4.  Judge reviews and approves or denies the request electronically.
    5.  Upon approval, the system forwards a payment order to the County Auditor's external accounting system (e.g., SAP).
    6.  System updates the payment request status to "Approved-For Payment."
*   **Postcondition:** Approved payment request is queued for final approval by Commissioners Court and disbursement by the Auditor.

#### 3.1.5 UC-5: Manage Attorney Rotation List
*   **Actor:** OAA Staff, Judge
*   **Description:** Attorneys apply to be added to rotation lists; judges review qualifications; OAA manages list membership and order.
*   **Precondition:** Attorney submits an application.
*   **Basic Flow:**
    1.  Attorney submits an online application with qualifications and desired list(s).
    2.  System routes application to the appropriate presiding judge(s) for approval.
    3.  Judge reviews and approves/denies application electronically.
    4.  Upon approval, OAA staff adds the attorney to the bottom of the requested rotation list(s).
    5.  System manages list order (round-robin) automatically as appointments are made.
*   **Postcondition:** Attorney's status is updated to "Active" on the specified list(s).

#### 3.1.6 UC-6: Generate Compliance Reports
*   **Actor:** OAA Staff
*   **Description:** System compiles data and generates standardized reports required by the Texas Task Force on Indigent Defense (TFID).
*   **Precondition:** Reporting period has ended.
*   **Basic Flow:**
    1.  OAA staff selects report type (e.g., Quarterly Compliance Report) and date range.
    2.  System extracts relevant data (appointment timeliness, contact rates, payments by category, etc.).
    3.  System formats the data into the prescribed TFID template.
    4.  System allows for review, export (PDF, Excel), and electronic submission.
*   **Postcondition:** A compliant report is generated and ready for distribution.

### 3.2 Data Requirements / Domain Model
The system shall maintain the following core entities and their key attributes:

1.  **Defendant**
    *   DefendantID (PK, Required, Unique)
    *   PersonalDetails (LastName, FirstName, DOB, SSN)
    *   FinancialAffidavit (DocumentID, ScannedImage/Data)
    *   CustodyStatus
    *   AssociatedCaseIDs

2.  **Case/Incident**
    *   CaseID (PK, Required, Unique) - *Sourced from CCMS*
    *   Charges[]
    *   FilingAgency
    *   ArrestDateTime
    *   OffenseType/Level

3.  **RequestForAppointedCounsel**
    *   RequestID (PK, Required, Unique)
    *   DefendantID (FK)
    *   MagistrateID
    *   IndigencyDetermination (Indigent/Not Indigent/Waived)
    *   SubmissionDateTime
    *   FinancialAffidavitID (FK)

4.  **DefenseAttorney**
    *   AttorneyID (PK, Bar Number, Unique)
    *   ContactInfo
    *   Qualifications[]
    *   ListStatus (Active, Suspended, Removed)

5.  **Appointment**
    *   AppointmentID (PK, Required, Unique)
    *   DefendantID (FK)
    *   AttorneyID (FK)
    *   CaseID (FK)
    *   AppointmentDateTime
    *   AppointmentMethod (Rotation, Judge Selection)

6.  **AttorneyRotationList**
    *   ListID (PK, Required, Unique)
    *   ListName (e.g., "Felony 1st Degree")
    *   OffenseCriteria
    *   AttorneyQueue[] (Ordered list of AttorneyIDs)

7.  **PaymentRequest**
    *   PaymentRequestID (PK, Required, Unique)
    *   AttorneyID (FK)
    *   CaseID (FK)
    *   ServicesItemized[]
    *   TotalAmount
    *   Status (Pending, Approved, Denied, Paid)
    *   JudgeApprovalDateTime

8.  **CourtSetting**
    *   SettingID (PK, Required, Unique) - *Sourced from CCMS*
    *   CaseID (FK)
    *   DateTime
    *   Type (Arraignment, Pre-Trial, Trial)
    *   Result

### 3.4 Acceptance Criteria
**Capability: Submit and Process Request for Counsel**
*   **Given** a defendant is in custody and has an indigency hearing,
    **When** the magistrate submits a Request for Appointed Counsel,
    **Then** the OAA receives the request and can view the associated financial affidavit.
*   **Given** a valid request is received and the defendant is in custody,
    **When** the OAA processes the request,
    **Then** the next eligible attorney from the correct rotation list is selected, and notifications are sent to the defendant, attorney, and detention facility.

**Capability: Manage Attorney Payment**
*   **Given** a defense attorney has completed services,
    **When** they submit a detailed payment request through the system,
    **Then** the request is routed to the appropriate judge for review and approval.
*   **Given** a judge approves a payment request,
    **When** the OAA forwards the order to the Auditor,
    **Then** the payment is added to the queue for Commissioners Court approval and disbursement.

**Capability: Compliance Reporting**
*   **Given** the OAA needs to report to the TFID,
    **When** a user selects a report type and date range,
    **Then** the system generates a report containing the required metrics (e.g., average time to appointment, total payments by offense type).

## 4. Non-Functional Requirements

### 4.1 Performance Requirements
1.  The system shall process and route a new Request for Appointed Counsel to the OAA workflow within **15 minutes** of magistrate submission 95% of the time.
2.  Standard pre-defined compliance reports for a quarterly date range shall generate in **under 5 minutes** 99% of the time.
3.  System search functions for defendant/case/attorney shall return results in **under 3 seconds**.

### 4.2 Reliability & Availability
1.  The system shall maintain an uptime of **99.5%** during core court business hours (7:00 AM to 7:00 PM, Central Time, Monday-Friday, excluding county holidays).
2.  All electronic transactions and records shall be backed up daily with a point-in-time recovery capability. Backup retention cycle shall be a minimum of **30 days**.
3.  Scheduled maintenance shall be communicated at least 72 hours in advance and performed outside of standard business hours.

### 4.3 Security & Privacy
1.  Access shall be controlled via role-based authentication integrated with the county's active directory.
2.  Access to defendant financial affidavits and detailed attorney payment requests shall be restricted to authorized roles only (e.g., Magistrate, OAA, specific Judges). All access attempts shall be logged in an audit trail.
3.  All data in transit shall be encrypted using TLS 1.2 or higher.
4.  All electronic signatures and records must comply with Texas UETA and DIR record-keeping guidelines.
5.  The system shall undergo annual third-party security vulnerability assessments.

### 4.4 Compliance
1.  The system's business logic and data model shall directly support compliance with Texas CCP Articles 1.051, 26.04, 26.05, and Government Code Section 71.0351.
2.  The system shall enable reporting that fulfills all requirements outlined in the **Tarrant County Indigent Defense Plan**.
3.  Data exchange with the CCMS shall adhere to **GJXDM** standards as specified by the county.

### 4.5 Observability & Support
1.  All key state changes (e.g., request submitted, attorney appointed, payment approved/denied) shall be logged with a timestamp, user ID, and description of the change.
2.  The system shall provide real-time dashboard views for OAA administrators showing metrics like number of pending requests, average processing time, and appointment status.
3.  System health and performance metrics shall be available to the IJIS technical team.

### 5.2 Risk List and Mitigation Strategies
| Risk | Probability | Impact | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| Complex integration with legacy CCMS causes delays. | Medium | High | Early prototyping of integration points; involve CCMS technical team from inception. |
| Legal/compliance requirements lead to overly rigid software. | Medium | Medium | Maintain a requirements traceability matrix; design rule-based logic to be configurable by OAA admins where possible. |
| User resistance to change from paper-based processes. | High | Medium | Develop role-based training programs and quick-reference guides. Implement a phased rollout with "super-user" support in each department. |
| Poor historical data quality affects report accuracy. | High | Low-Medium | Implement strict data validation rules for new entries. Plan a separate data cleansing project for critical historical fields post-launch. |
| System unavailable during critical magistration hours. | Low | High | Design for high availability; establish and document clear manual fallback procedures to be used during outages. |
| Electronic signature method fails to meet legal standards. | Medium | High | Engage County Legal Counsel in the selection and validation of the e-signature technical approach (PKI, certificates) before development begins. |
