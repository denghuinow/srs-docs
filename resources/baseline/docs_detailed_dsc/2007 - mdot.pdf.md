### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the VII Data Use Analysis and Processing (DUAP) System, a research prototype. It is intended to serve as a comprehensive guide for the project's designers, developers, testers, and stakeholders, ensuring a common understanding of the system's capabilities, constraints, and scope.

#### 1.2 Document Conventions
*   **Shall / Must:** Indicates a mandatory requirement.
*   **Should:** Indicates a desirable, but not mandatory, requirement.
*   **May / Could:** Indicates an optional feature or capability.
*   **Italics:** Used for emphasis or to denote referenced external entities.
*   `Monospace`: Used for technical names, code, or interface specifications.

#### 1.3 Project Scope
The DUAP system is a research prototype designed to evaluate the utility of Vehicle Infrastructure Integration (VII) data, integrated with other transportation data sources (e.g., traffic sensors, weather), for enhancing safety, mobility, and asset management applications within MDOT.

**In-Scope:**
*   Collecting, consolidating, and converting raw VII probe, traffic, and weather data from multiple sources.
*   Processing raw data through computational algorithms to derive traffic metrics, incidents, and road conditions.
*   Publishing processed data and alerts in standard formats for consumption by external operational systems.
*   Presenting processed information via web-based interfaces for human operators.
*   Archiving raw and derived data for long-term analysis.
*   Providing system administration capabilities for service management and user access control.

**Out-of-Scope (Non-Goals):**
*   Being a fully operational, production-ready, 24/7 mission-critical system.
*   Handling all potential future data sources or computational algorithms not explicitly identified for the prototype phase.
*   Directly controlling field devices (e.g., signals, signs).
*   Providing public-facing traveler information applications.

### 2. Overall Description

#### 2.1 Product Perspective
The DUAP system is a middleware data processing hub. It sits between upstream data providers (VII network, traffic management centers, weather systems) and downstream data consumers (operational systems, web clients, analysts). It is a component within a larger research initiative to assess VII data value.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics & Key Needs |
| :--- | :--- |
| **TA Operators** | Need real-time and near-real-time visibility into incidents and traffic flow to make response decisions. |
| **TA Maintainers** | Require information on road conditions and incidents to schedule and dispatch maintenance resources. |
| **TA Asset Managers** | Need accurate, historical data for trend analysis and planning cost-effective programs. |
| **System Administrators** | Require tools to manage system services, user accounts, and monitor system health. |
| **Researchers** | Need access to complete, accurate, and well-documented datasets for analysis. |
| **Emergency Services** | Require reliable incident and traffic impact data to optimize response. |
| **External Systems (TMS, etc.)** | Act as automated consumers of processed data feeds in specific formats. |

#### 2.3 Operating Environment
*   **Software:** The system shall operate on servers conforming to MDIT standards. Core services will be developed in a language/framework suitable for a service-oriented architecture (SOA). The persistent data store shall be an Oracle database.
*   **Hardware:** Standard MDIT-approved server hardware.
*   **Networks:** Must operate within secure MDOT network zones, communicating with external entities via defined firewalls and interfaces.

#### 2.4 Design and Implementation Constraints
1.  The architecture **shall** be service-oriented to allow for flexible addition/modification of Computational Services.
2.  All software and database components **must** conform to Michigan Department of Information Technology (MDIT) standards.
3.  Data output for certain external systems **must** comply with the SAE J2354 XML standard.
4.  The web presentation layer **shall** support Internet Explorer 6+ and Firefox 2+.

#### 2.5 Assumptions and Dependencies
*   Assumes continuous (or regularly batched) data availability from upstream sources (VII POC, MITS, Clarus).
*   Dependent on finalized interface specifications from external system owners (TMS, SEMSIM, etc.).
*   Dependent on MDOT resolving data sharing agreements for commercial data sources.

### 3. System Features and Requirements

#### 3.1 Data Ingestion & Caching (SF-1)
**Description:** The system shall subscribe to and ingest multiple streams of raw transportation data, caching it for low-latency access by processing services.

**Requirements:**
*   **SF-1.1:** The system **shall** subscribe to the *VII Proof of Concept Probe Data Service* via the X-031 interface to receive a continuous stream of SAE J2735 probe data.
*   **SF-1.2:** The system **shall** connect to the *MITS Center ATMS* to receive traffic data (speed, volume, occupancy).
*   **SF-1.3:** The system **shall** connect to the *Clarus System* (or equivalent) to receive weather data elements.
*   **SF-1.4:** The system **shall** cache all ingested raw data in a Dynamic Data service for a minimum period of one (1) week.
*   **SF-1.5:** Cached data **shall** be made accessible to internal Computational Services as soon as it is stored.

#### 3.2 Data Processing & Derivation (SF-2)
**Description:** The system shall apply algorithms to raw and cached data to derive higher-value information such as traffic metrics, incidents, and road surface conditions.

**Requirements:**
*   **SF-2.1:** The system **shall** provide Computational Services to calculate link-based traffic metrics (e.g., average speed, queue length) from probe and sensor data.
*   **SF-2.2:** The system **shall** provide an Incident Detection Computational Service that analyzes probe data patterns (e.g., sudden deceleration, stopped clusters) to automatically generate incident records.
*   **SF-2.3:** The system **shall** provide Computational Services to derive road condition assessments (e.g., wet, icy, pothole detection) from probe sensor data and weather data.
*   **SF-2.4:** The system **shall** provide Data Quality Checking Computational Services to flag data with potential latency, accuracy, or calibration issues.

#### 3.3 Data Publication & Output (SF-3)
**Description:** The system shall format and publish processed data and alerts for external systems and internal presentation services.

**Requirements:**
*   **SF-3.1:** The system **shall** format processed traveler, event, and link traffic data into SAE J2354 compliant XML messages.
*   **SF-3.2:** The system **shall** publish processed traffic and incident data to the *Transportation Management System (TMS)* in its required interface format.
*   **SF-3.3:** When a Computational Service detects a condition exceeding a defined threshold, the system **shall** automatically generate and publish an alert to all subscribed external systems and presentation layers.

#### 3.4 Data Presentation & Visualization (SF-4)
**Description:** The system shall provide web-based interfaces for authorized human users to query and visualize processed data.

**Requirements:**
*   **SF-4.1:** The system **shall** provide a web-based traffic information browser that displays traffic flow data (e.g., speed, congestion) on a map interface using standard icons.
*   **SF-4.2:** The system **shall** provide a web-based incident information browser that displays incident and alert data (including weather alerts) on a map and in tabular lists.
*   **SF-4.3:** Users **shall** be able to query and filter displayed data by geographic area, time range, and event type.

#### 3.5 Data Archival & Persistence (SF-5)
**Description:** The system shall persistently store all raw and derived data for long-term access and analysis.

**Requirements:**
*   **SF-5.1:** The system **shall** archive all ingested raw data records to a Persistent Data store (Oracle database).
*   **SF-5.2:** The system **shall** archive all derived data records (incidents, conditions, metrics) to the Persistent Data store.
*   **SF-5.3:** Archived data **shall** be queryable via structured interfaces for research and analysis purposes.

#### 3.6 System Administration & Security (SF-6)
**Description:** The system shall provide capabilities for managing services, users, and configuration in a secure manner.

**Requirements:**
*   **SF-6.1:** Authorized System Administrators **shall** be able to add, modify, and remove system services (Input, Computational, Output, Presentation) via an Administrative Client.
*   **SF-6.2:** The system **shall** restrict access to all functions and data views based on user roles and access rights.
*   **SF-6.3:** The system **shall** maintain an audit log of all user authentication and access attempts.
*   **SF-6.4:** System Administrators **shall** be able to view system configuration and transaction logs.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   The Dynamic Data cache **shall** retain data for a minimum of one (1) week.
*   Data **shall** be available for processing by Computational Services as soon as it is written to the cache.
*   The system shall be designed to handle variable data volumes contingent on VII vehicle penetration rates during the prototype phase.

#### 5.2 Safety and Security Requirements
*   The system **shall** authenticate all user access attempts.
*   The system **shall** implement role-based access control (RBAC) to restrict data and functions.
*   All user transactions and system administrative actions **shall** be logged for audit purposes.
*   System design and operation **shall** consider privacy policies for handling anonymized probe data.

#### 5.3 Software Quality Attributes
*   **Reliability:** All critical service transactions (input, processing, output) **shall** be logged to facilitate debugging and ensure data lineage.
*   **Maintainability:** The service-oriented architecture **shall** allow for new Computational Services to be added with minimal impact on existing services.
*   **Observability:** The system **shall** generate logs for data transactions across all core service types (Input, Dynamic Data, Computational, Output, Persistent Data).
*   **Compliance:** The system **shall** conform to all applicable MDIT IT standards for software and database deployment.

### 6. Other Requirements

#### 6.1 Acceptance Criteria
**For Incident Detection:**
*   *Given* probe vehicle data indicating sudden deceleration and stopped vehicles on a freeway segment, *when* the incident detection service processes the data, *then* an incident record with type and location shall be generated and cached.
*   *Given* no anomalous patterns in the probe vehicle data stream, *when* the incident detection service processes the data, *then* no new incident records shall be generated.

**For Data Presentation:**
*   *Given* a system operator with valid credentials, *when* they access the traffic information browser and select a geographic area, *then* a map displaying traffic icons for that area shall be rendered.
*   *Given* a published weather alert for a specific roadway, *when* a user queries incident information for that area, *then* the alert shall be visible in the incident information browser display.

#### 6.2 Data Model (Key Entities)
*   **ProbeDataRecord:** `ID` (PK), `Timestamp`, `Location`, `Speed`, `Heading`, `VehicleSensorData`
*   **TrafficDataRecord:** `ID` (PK), `LinkID` (FK), `Timestamp`, `Speed`, `Volume`, `Occupancy`
*   **IncidentDerivation:** `ID` (PK), `DetectionTime`, `Location`, `Type`, `Severity`, `Status`
*   **RoadConditionDerivation:** `ID` (PK), `Location`, `Timestamp`, `ConditionType`, `Severity`
*   **SystemUser:** `UserID` (PK), `Role`, `AccessRights`
*   **DataTransactionLog:** `LogID` (PK), `ServiceType`, `Timestamp`, `TransactionDetails`
