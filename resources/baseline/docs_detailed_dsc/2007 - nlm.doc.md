# Software Requirements Specification (SRS)
## NLM Digital Repository

**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the National Library of Medicine (NLM) Digital Repository. The purpose of this system is to provide a robust, standards-based infrastructure for the long-term preservation and access of NLM's digital biomedical collections, in alignment with its mission and the OAIS (Open Archival Information System) reference model.

#### 1.2 Scope
The NLM Digital Repository will encompass the core digital preservation and access functions for collection materials managed under NLM Library Operations.

**In-Scope:**
*   Acquisition, ingest, validation, and quality assurance of digital materials.
*   Secure, redundant archival storage of digital objects.
*   Comprehensive metadata management (descriptive, administrative, structural, technical).
*   Long-term preservation planning and action execution (e.g., format migration).
*   Public and staff access interfaces for discovery and retrieval.
*   Management of existing digital collections (e.g., PubMed Central content as a collection).
*   Integration with specified internal and external systems.

**Out-of-Scope:**
*   Non-collection resources such as UMLS (Unified Medical Language System) or the Visible Human Project.
*   Web harvesting functionality (to be handled by separate, dedicated software).
*   Creation of original digital surrogates (digitization).

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **AIP:** Archival Information Package. The package containing the preserved digital object and its associated metadata, stored within the repository.
*   **DIP:** Dissemination Information Package. The package derived from one or more AIPs, delivered to a user in response to an access request.
*   **OAIS:** Open Archival Information System. An ISO standard reference model (ISO 14721) for a digital archive.
*   **SIP:** Submission Information Package. The package of data and metadata submitted by a Producer to the repository.
*   **PREMIS:** Preservation Metadata: Implementation Strategies. A standard for metadata supporting the long-term preservation of digital objects.
*   **METS:** Metadata Encoding and Transmission Standard. A standard for encoding descriptive, administrative, and structural metadata for digital objects.
*   **ILS:** Integrated Library System.
*   **NCCS:** NIH Consolidated Collocation Site.
*   **OAI-PMH:** Open Archives Initiative Protocol for Metadata Harvesting.

#### 1.4 References
*   ISO 14721:2012, Space data and information transfer systems – Open archival information system (OAIS) – Reference model.
*   NLM Collection Development Guidelines.
*   HHS and NIH Information Security and Privacy Policies.

#### 1.5 Document Overview
This document is structured to present an overview of the system, followed by detailed functional and non-functional requirements, interface specifications, and supporting project information.

### 2. Overall Description

#### 2.1 Product Perspective
The NLM Digital Repository is a major component within NLM's digital infrastructure. It will interact with external producers and users, as well as internal NLM systems. It is conceived as an independent system adhering to the OAIS model, ensuring clear boundaries and standardized interfaces.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **General Public** | Diverse, international, varying technical expertise. Unauthenticated or minimally authenticated. | Discover, view, and download publicly accessible materials via an intuitive web interface. |
| **NIH/NLM Staff (Research)** | Authenticated internal users. May have enhanced access rights. | Access materials for research and reference, potentially including items with internal-only access. |
| **NLM Staff (Metadata)** | Catalogers, metadata specialists. Authenticated with specific role. | Create, review, edit, and enhance descriptive and administrative metadata for objects. |
| **NLM Staff (Object Maintenance)** | Digital archivists, technicians. Authenticated with specific role. | Perform QA, technical investigations, file manipulation, and format conversions on digital objects. |
| **System Administrators** | IT and developer staff. Highest level of system access. | Configure system, manage user roles/access, monitor health, perform backups, and implement updates. |
| **Content Producers/Donors** | External entities (publishers, donors). Authenticated via submission agreement. | Submit digital materials via defined protocols and receive status notifications. |

#### 2.3 Operating Environment
*   **Software:** Must be compatible with existing NLM enterprise operating systems (Linux/Windows), databases, and middleware.
*   **Hardware:** Must be deployable within NLM/NIH data centers, with scalability to support petabyte-scale storage growth.
*   **Network:** Must operate within NIH secure network zones, supporting both internal and controlled external access.

#### 2.4 Design and Implementation Constraints
1.  The system **must** implement the core functional entities of the OAIS reference model.
2.  The system **must** comply with HHS/NIH security policies and FISMA standards.
3.  The system **must** support key metadata standards: METS, PREMIS, MODS, and MARC.
4.  The system **should** be built upon or integrate with existing, supported open-source or commercial repository platforms where feasible.

#### 2.5 Assumptions and Dependencies
*   Adequate funding and staffing will be secured for implementation and long-term maintenance.
*   Submission agreements with producers will define technical requirements for SIPs.
*   Existing NLM systems (e.g., ILS) will provide necessary data via standards-based interfaces.

### 3. System Features and Requirements

#### 3.1 OAIS Functional Entity: Ingest
**3.1.1 Description:** Receive Submission Information Packages (SIPs) from Producers, prepare them for storage, and ensure the creation of compliant Archival Information Packages (AIPs).

**3.1.2 Functional Requirements:**
*   **FR-INGEST-01:** The system shall accept SIPs via multiple transfer mechanisms (e.g., FTP/SFTP, API, physical media load).
*   **FR-INGEST-02:** The system shall perform virus/malware scanning on all incoming files.
*   **FR-INGEST-03:** The system shall verify the integrity of transferred data using checksum comparison (e.g., MD5, SHA-256).
*   **FR-INGEST-04:** The system shall validate the file formats within a SIP against a configurable list of approved/preferred formats.
*   **FR-INGEST-05:** The system shall support both automated and manual Quality Assurance (QA) workflows, allowing staff to review content and approve/reject submissions.
*   **FR-INGEST-06:** The system shall generate a unique, persistent identifier for each accepted Digital Object and its corresponding AIP.
*   **FR-INGEST-07:** The system shall transform the SIP into an AIP, which may include format normalization to archival standards based on configurable rules.
*   **FR-INGEST-08:** The system shall extract technical metadata from digital files (e.g., using tools like JHOVE, FITS) and incorporate it into the preservation metadata.
*   **FR-INGEST-09:** The system shall coordinate the successful storage of the AIP in Archival Storage and its associated metadata in Data Management.
*   **FR-INGEST-10:** The system shall notify the Producer of the submission's status (received, accepted, rejected).

#### 3.2 OAIS Functional Entity: Archival Storage
**3.2.1 Description:** Provide secure, redundant, and managed storage for AIPs, including disaster recovery functions.

**3.2.2 Functional Requirements:**
*   **FR-STORAGE-01:** The system shall store AIPs in a secure, managed storage environment with redundancy to prevent data loss.
*   **FR-STORAGE-02:** The system shall regularly verify the integrity of stored AIPs using checksums and report discrepancies.
*   **FR-STORAGE-03:** The system shall manage the replication of AIPs to a geographically separate disaster recovery site (e.g., NCCS).
*   **FR-STORAGE-04:** The system shall provide a mechanism for retrieving a specific AIP or components thereof for access, preservation, or recovery purposes.
*   **FR-STORAGE-05:** The system shall support storage migration strategies (e.g., from one filesystem to another) without loss of data or integrity.

#### 3.3 OAIS Functional Entity: Data Management
**3.3.1 Description:** Maintain and provide access to descriptive, administrative, and preservation metadata to support discovery, access, and preservation.

**3.3.2 Functional Requirements:**
*   **FR-DATAMGMT-01:** The system shall store and manage descriptive metadata (e.g., MODS, MARC) linked to Digital Objects.
*   **FR-DATAMGMT-02:** The system shall store and manage preservation metadata (PREMIS) documenting provenance, fixity, and preservation actions.
*   **FR-DATAMGMT-03:** The system shall support the creation, reading, updating, and deletion of metadata records by authorized staff (with audit logging).
*   **FR-DATAMGMT-04:** The system shall support complex searches across metadata fields and full-text content (where applicable).
*   **FR-DATAMGMT-05:** The system shall maintain a configurable hierarchy of collections for organizing objects.

#### 3.4 OAIS Functional Entity: Administration
**3.4.1 Description:** Manage the daily operation, configuration, and policy enforcement of the repository system.

**3.4.2 Functional Requirements:**
*   **FR-ADMIN-01:** The system shall implement granular, role-based access control (RBAC) for all functions and data.
*   **FR-ADMIN-02:** The system shall maintain a comprehensive audit log of all significant system events and user actions (who, what, when, where).
*   **FR-ADMIN-03:** The system shall manage agreements with Producers (Submission Agreements), linking them to submitted content.
*   **FR-ADMIN-04:** The system shall generate operational reports (ingest statistics, storage metrics, user activity).
*   **FR-ADMIN-05:** The system shall allow administrators to configure system policies (e.g., format validation rules, normalization paths).

#### 3.5 OAIS Functional Entity: Preservation Planning
**3.5.1 Description:** Monitor the digital preservation environment and recommend/trigger actions to ensure long-term usability of content.

**3.5.2 Functional Requirements:**
*   **FR-PRES-01:** The system shall generate reports on the formats stored in the repository, highlighting obsolete or at-risk formats.
*   **FR-PRES-02:** The system shall support the definition and execution of preservation action plans (e.g., format migration campaigns) on sets of AIPs.
*   **FR-PRES-03:** The system shall document all preservation actions taken on an AIP within its preservation metadata.

#### 3.6 OAIS Functional Entity: Access
**3.6.1 Description:** Provide a user interface for discovering, requesting, and receiving repository content as Dissemination Information Packages (DIPs).

**3.6.2 Functional Requirements:**
*   **FR-ACCESS-01:** The system shall provide a public, web-based interface for searching and browsing repository holdings.
*   **FR-ACCESS-02:** The system shall enforce access control rules based on user identity, role, object metadata (e.g., embargo date), and IP location.
*   **FR-ACCESS-03:** The system shall deliver DIPs in appropriate formats (e.g., PDF for viewing, TIFF for download by authorized staff).
*   **FR-ACCESS-04:** The system shall expose metadata for harvesting via the OAI-PMH protocol in standard formats (Dublin Core, MODS).
*   **FR-ACCESS-05:** The system shall be compliant with Section 508 accessibility standards.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Public Web Interface:** A responsive, accessible website for search, discovery, and access to public materials.
*   **Staff Management Interface:** A secure web application for staff to manage ingest workflows, edit metadata, administer the system, and perform preservation tasks.

#### 4.2 Hardware Interfaces
*   Must interface with high-capacity, redundant storage arrays (SAN/NAS).
*   Must support deployment in a virtualized or containerized environment within NIH data centers.

#### 4.3 Software Interfaces
| Interface Name | Direction | Purpose | Protocol/Standard | Key Requirement |
| :--- | :--- | :--- | :--- | :--- |
| **Integrated Library System (ILS)** | Inbound | Receive bibliographic metadata | Z39.50, SRU, MARC XML | Must support standard bibliographic exchange. |
| **NIH Consolidated Collocation Site (NCCS)** | Bi-directional | Disaster recovery backup & restore | Secure transfer (e.g., Rsync over SSH) | Must conform to NIH security policies for data at rest and in transit. |
| **OAI-PMH Provider** | Outbound | Expose metadata for harvesting | OAI-PMH 2.0 | Must support Dublin Core and MODS as metadata formats. |
| **Authentication Service** | Inbound | Validate user credentials | LDAP, SAML 2.0 | Must integrate with NIH central authentication where possible. |

#### 4.4 Communications Interfaces
*   Must support HTTPS for all web-based interfaces.
*   Must support SFTP for secure batch file transfers from producers.
*   Must support API calls (REST/SOAP) for system-to-system integration.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   The public search interface shall return results for typical queries within **3 seconds**.
*   The system shall support the bulk ingest of collections containing **millions of objects**.
*   The system shall be able to deliver files to users with throughput suitable for large image or video files.

#### 5.2 Safety and Security Requirements
*   The system shall comply with all **HHS and NIH mandatory security controls**.
*   All PII (Personally Identifiable Information) in metadata or logs shall be protected in accordance with NLM policy.
*   All data transfers, both internal and external, shall use encryption (TLS 1.2+).
*   A complete audit trail shall be maintained for a minimum of **10 years**.

#### 5.3 Software Quality Attributes
*   **Availability:** 99.9% uptime for the access interface.
*   **Reliability:** Statistically valid error checking (checksums) on all internal data movements.
*   **Maintainability:** System components shall be modular with well-documented APIs to facilitate updates and integration.
*   **Scalability:** The architecture shall scale horizontally to accommodate growth in storage and user load.
*   **Usability:** The staff interface shall be intuitive, reducing training time for new users. The public interface shall meet WCAG 2.1 AA guidelines.

### 6. Other Requirements

#### 6.1 Acceptance Criteria
*   **AC-INGEST-01:** Given a valid SIP is submitted via FTP, the system shall perform virus checking, checksum validation, and place it in a staging area for QA, generating a receipt confirmation.
*   **AC-ACCESS-01:** Given a public user searches for an embargoed article, the system shall omit the article from search results or clearly mark it as restricted.
*   **AC-PRES-01:** Given a scheduled job is run, the system shall generate a report listing all AIPs in a specified at-risk format (e.g., Adobe Flash).

#### 6.2 Business Rules
*   The "Permanence Level" of a Digital Object (e.g., Permanent, Temporary) shall be assigned during ingest and govern preservation priorities.
*   Access to an object is determined by the most restrictive rule applying to the user's role, the object's metadata, and the Submission Agreement.

#### 6.3 Data Migration Requirements
The repository system must provide tools or APIs to facilitate the ingestion of existing NLM digital collections (e.g., from PubMed Central, legacy systems) while preserving existing identifiers and metadata where required.

### Appendix A: Risk List and Mitigation
1.  **Risk:** Evolving digital formats outpace preservation strategies.
    *   **Mitigation:** Establish an active preservation planning function with dedicated staff.
2.  **Risk:** Complex copyright/licensing complicates access management.
    *   **Mitigation:** Develop a flexible rights metadata schema (e.g., based on PREMIS Rights) and a rules-based access control engine.
3.  **Risk:** Integration challenges with existing systems (ILS, PMC).
    *   **Mitigation:** Prioritize the use of standards-based interfaces (OAI-PMH, APIs) and conduct integration testing early in the development cycle.
4.  **Risk:** Ensuring long-term data integrity and disaster recovery.
    *   **Mitigation:** Implement fixity checking at multiple levels and maintain a tested, automated replication process to NCCS.
