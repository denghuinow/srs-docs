### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for an Automated Diagnostic Tool designed to detect faults in Heating, Ventilation, and Air Conditioning (HVAC) subsystems. It serves as a formal agreement between stakeholders and the development team, providing a comprehensive blueprint for system design, implementation, and validation.

#### 1.2 Scope
The software will automate the detection of faults in HVAC subsystems—initially focusing on chillers and cooling towers—by applying expert-derived algorithms to sensed (real-time or batch) and fixed (specifications, setpoints) data. It will present fault identifications, root causes, and corrective actions to various user roles via a hierarchical Windows-based interface.

**In-Scope:**
*   Automated fault detection for chillers and cooling towers.
*   Support for real-time data acquisition and batch file processing.
*   User authentication and role-based access control (General User, Administrator).
*   Configuration management for fixed data and diagnostic sensitivity.
*   Display and browsing of current and historical diagnostic results.
*   Architectural extensibility for future subsystems (e.g., boilers).

**Out-of-Scope (Non-Goals):**
*   Implementation of field-level control logic or actuator commands.
*   User-defined or custom diagnostic algorithm creation.
*   Support for non-Windows operating systems.
*   Detailed development of boiler diagnostic algorithms (planned for future version).

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **HVAC:** Heating, Ventilation, and Air Conditioning.
*   **Sensed Data:** Time-series measurements from physical sensors (e.g., temperature, current, power).
*   **Fixed Data:** Static configuration data (e.g., equipment specifications, operational setpoints, schedules).
*   **Fault:** A detected deviation from normal or optimal subsystem operation.
*   **SLA:** Service Level Agreement.
*   **IEEE Std 610.12-1990:** IEEE Standard Glossary of Software Engineering Terminology.

### 2. Overall Description

#### 2.1 Product Perspective
The tool is a standalone, desktop diagnostic application. It interfaces with external data sources (sensors, batch files) and persists data to permanent storage. The system architecture is modular to allow for the future integration of additional HVAC subsystems.

**System Interfaces:**
```
[Data Acquisition Devices] --> [Automated Diagnostic Tool] --> [User Interface]
         ^                              |                            |
         |                              v                            v
[Batch Data Files] ---------------> [Permanent Storage] <------ [Printer]
```

#### 2.2 Product Functions (High-Level)
1.  **Data Acquisition & Ingestion:** Accept real-time sensor streams and batch ASCII files.
2.  **Data Preprocessing:** Validate, convert units, filter, and average incoming data.
3.  **Diagnostic Processing:** Execute algorithms to detect faults in target subsystems.
4.  **Result Management:** Generate, display, and store fault descriptions with causes and fixes.
5.  **User & Configuration Management:** Authenticate users and manage system configuration data.
6.  **Historical Analysis:** Provide tools for browsing and visualizing past diagnostic results.

#### 2.3 User Characteristics and Stakeholders
| Stakeholder Role | Primary Goal | Key System Interaction |
| :--- | :--- | :--- |
| **General User** | Browse diagnostic results for situational awareness. | View current/historical fault displays. |
| **Administrator** | Configure and control the diagnostic system. | Start/stop diagnostics, modify fixed data, manage units. |
| **Building Operator** | Monitor HVAC health from a central control room. | Continuously observe diagnostic outputs for multiple units. |
| **Service Technician** | Diagnose issues during repair or off-site monitoring. | Use detailed fault causes and corrective actions. |
| **Energy Service Provider** | Identify inefficiencies across a portfolio of buildings. | Remotely analyze trends and fault frequencies. |
| **Building Operator Supervisor** | Prioritize maintenance work and assign tasks. | Use diagnostic results to guide operator assignments. |

#### 2.4 Operating Environment
*   **Software:** Microsoft Windows 10/11 (64-bit).
*   **Hardware:** Standard desktop or laptop meeting minimum requirements for running .NET/WPF applications (to be defined during design).
*   **External Systems:** Data acquisition hardware drivers, database system (e.g., SQLite, SQL Server).

#### 2.5 Design and Implementation Constraints
1.  **Platform:** Must be developed for the Microsoft Windows platform.
2.  **Compliance:** Data storage and terminology must adhere to IEEE Std 610.12-1990.
3.  **Precision:** All stored numerical data must retain at least three significant figures.
4.  **Architecture:** Must be designed with modularity to allow integration of boiler diagnostics in a future release.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** Sensor data providers will maintain basic format and protocol consistency.
*   **Assumption:** Users possess basic computer literacy and fundamental understanding of HVAC systems.
*   **Dependency:** Availability of validated diagnostic algorithms for chillers and cooling towers.
*   **Dependency:** Successful integration with specified data acquisition device APIs.

### 3. System Features and Requirements

#### 3.1 Feature: Diagnostic Processing & Fault Detection
**Description:** The system shall process sensed and fixed data through automated algorithms to detect faults in chiller and cooling tower subsystems.

**Functional Requirements:**
*   **FR-1:** The system shall accept real-time sensed data streams from configured data acquisition devices.
*   **FR-2:** The system shall accept sensed data from ASCII batch files with tab or comma delimiters and defined column headers.
*   **FR-3:** The system shall validate all incoming sensed data for format, range, and completeness.
*   **FR-4:** The system shall convert sensed data to consistent internal units as defined by the administrator.
*   **FR-5:** The system shall apply filtering and averaging logic during data preprocessing as defined per diagnostic algorithm.
*   **FR-6:** The system shall execute diagnostic algorithms for chillers and cooling towers using the preprocessed data and current fixed data.
*   **FR-7:** Upon detecting a fault, the system shall generate a diagnostic result containing: Fault ID, Timestamp, Subsystem/Building reference, Description, Probable Causes, and Recommended Corrective Actions.
*   **FR-8:** The system shall save all diagnostic results and the associated sensed data to permanent storage.

#### 3.2 Feature: User Interface & Result Browsing
**Description:** The system shall provide a hierarchical, window-based interface for all users to browse current and historical diagnostic results.

**Functional Requirements:**
*   **FR-9:** The system shall present a hierarchical navigation model (e.g., Building -> Subsystem -> Diagnostic View).
*   **FR-10:** The system shall display current diagnostic results in a clear, color-coded format (e.g., map, list, dashboard).
*   **FR-11:** The system shall provide a "History View" allowing users to select a date/time range.
*   **FR-12:** For historical data, the system shall display a color-coded map or timeline with at least hourly resolution.
*   **FR-13:** The system shall allow any user to print the current view of any diagnostic results window.

#### 3.3 Feature: System Configuration & Administration
**Description:** Administrators shall be able to configure system parameters, manage fixed data, and control diagnostic execution.

**Functional Requirements:**
*   **FR-14:** The system shall allow administrators to start and stop the diagnostic processing engine.
*   **FR-15:** The system shall provide interfaces for administrators to create, read, update, and delete (CRUD) fixed data (setpoints, schedules, equipment specs).
*   **FR-16:** The system shall allow administrators to adjust sensitivity settings for diagnostic algorithms.
*   **FR-17:** Configuration changes made while diagnostics are active shall be relayed to the processing engine after user confirmation.
*   **FR-18:** All configuration changes shall be logged with the user ID, timestamp, original value, and new value.

#### 3.4 Feature: User Authentication & Authorization
**Description:** The system shall control access to functions based on user roles.

**Functional Requirements:**
*   **FR-19:** The system shall require username and password authentication upon launch and for privileged functions.
*   **FR-20:** The system shall enforce a limit of three consecutive failed authentication attempts.
*   **FR-21:** The system shall automatically revert an authenticated session to "General User" privileges after 15 minutes of inactivity.
*   **FR-22:** The system shall restrict "Start/Stop Diagnostics" and "Configure System" functions to users with the Administrator role.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **UI-1:** The interface shall be a Windows Presentation Foundation (WPF) or equivalent desktop application.
*   **UI-2:** Navigation shall be modal and hierarchical, preventing user confusion.
*   **UI-3:** Diagnostic results shall use color-coding (e.g., red for fault, green for normal) for rapid interpretation.
*   **UI-4:** Animated indicators shall show the status of data acquisition and diagnostic processing.

#### 4.2 Hardware Interfaces
*   **HW-1:** The system shall interface with industry-standard data acquisition devices (e.g., BACnet, Modbus) to read sensed data.
*   **HW-2:** The system must tolerate less than three successive failures per sensor type before raising a major alert.

#### 4.3 Software Interfaces
*   **SI-1:** **Batch File Interface:** Accept ASCII files with tab/comma-delimited columns, defined headers, and timestamps.
*   **SI-2:** **Storage Interface:** Connect to a relational database (e.g., SQL Server) or file-based store (e.g., SQLite) for persistent data.
*   **SI-3:** **Printing Service:** Interface with the Windows OS printing subsystem to generate hard copies of diagnostic views.

#### 4.4 Communications Interfaces
*   **CI-1:** Support protocols necessary for real-time data acquisition (e.g., TCP/IP, Serial) as defined by the supported hardware.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   **PER-1:** The system shall process real-time data and generate a diagnostic result with a latency of less than 1 second from data receipt.
*   **PER-2:** The system shall support simultaneous monitoring and display of diagnostics for up to 10 buildings without significant UI degradation.

#### 5.2 Safety & Security Requirements
*   **SEC-1:** All user passwords shall be stored in a hashed, non-reversible format.
*   **SEC-2:** All access attempts to administrative functions shall be logged.
*   **SEC-3:** The system shall validate all input data to prevent injection attacks.

#### 5.3 Software Quality Attributes
*   **REL-1:** The system shall be designed for continuous, 24/7 operation. All errors shall be logged with module and function details.
*   **OBS-1:** All sensor validation failures and data gaps shall be logged for maintenance purposes.
*   **MAI-1:** The system architecture shall be modular, allowing new HVAC subsystem diagnostic modules (e.g., boiler) to be added with minimal impact to existing code.

### 6. Acceptance Criteria
*Scenario-based criteria derived from the provided information.*

**AC-1: Fault Detection - High Temperature**
*   **Given:** Sensed data indicates a chilled water supply temperature consistently above its configured setpoint.
*   **When:** The diagnostic processing cycle executes.
*   **Then:** The tool shall generate a fault result identified as "Chilled Water Supply Temperature Too High," including potential causes (e.g., low refrigerant, dirty condenser) and corrective actions.

**AC-2: Historical Browsing**
*   **Given:** Diagnostic results have been stored for the past week.
*   **When:** A user selects the "History View" and inputs a start and end time for the previous day.
*   **Then:** The system shall display a color-coded timeline for the selected day with hourly resolution, showing periods of fault and normal operation.

**AC-3: Administrator Configuration**
*   **Given:** A user with Administrator privileges is logged in and diagnostic processing is active.
*   **When:** The administrator modifies the sensitivity threshold for the "Compressor Cycling" diagnostic and confirms the change.
*   **Then:** The change is saved to permanent storage, logged, and the active diagnostic processing engine begins using the new threshold for subsequent cycles.

#### 7.2 Risk Mitigation Summary
| Risk | Mitigation Strategy |
| :--- | :--- |
| Missing Sensor Data | Halt affected diagnostics, notify user, use default thresholds where safe. |
| Algorithm Inaccuracy | Include administrator-adjustable sensitivity settings; validate with domain experts. |
| UI Complexity | Implement clear hierarchical navigation with tooltips and consistent layouts. |
| Data Volume Overload | Employ data averaging in preprocessing; limit historical display to a 2-year maximum. |
| Platform Dependence | Enforce strict modularity in code to isolate platform-specific components for future porting. |
