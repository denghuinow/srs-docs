## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the ZNIX Framework, an object-based, application-independent information management system. It is intended for use by the project's stakeholders, including system architects, developers, testers, and the open-source community, to establish a common understanding of the system's capabilities and constraints.

### 1.2 Scope
The ZNIX Framework is a research and development effort designed to shift the paradigm of personal information management from application-centric to information-centric. It provides a unified model for storing, relating, and browsing user data (Entities and Associates) regardless of the originating application.

**In-Scope:**
*   Design and implementation of the core framework services and centralized data store.
*   Development of a public API for ZNIX-aware application development.
*   Creation of a proxy mechanism to integrate with common, ZNIX-unaware applications (email, web, documents).
*   Implementation of a user-facing GUI browser for hierarchical information navigation and management.
*   Functionality for archiving information subsets to removable media.
*   Single-user operation on the Microsoft Windows 2000/XP operating systems.

**Out-of-Scope (Non-Goals for v1.0):**
*   Multi-user support or networked access.
*   Compatibility with operating systems other than Windows 2000/XP.
*   Real-time collaboration features.
*   Native mobile application clients.

### 1.3 Definitions, Acronyms, and Abbreviations
*   **Entity:** A first-class information object with an independent identity (e.g., a Person, a Project).
*   **Associate:** A unit of data (e.g., an email body, a document reference) whose context is defined by its relationship to one or more Entities.
*   **Relationship:** A directed link associating an Associate with an Entity.
*   **Category:** A user-definable classification for Entities (e.g., "People", "Email").
*   **Proxy Mechanism:** A system component that intercepts or captures data from third-party applications.
*   **API:** Application Programming Interface.
*   **GUI:** Graphical User Interface.
*   **POP3:** Post Office Protocol version 3.
*   **SLA:** Service Level Agreement (used here to denote required interface characteristics).
*   **MTBF:** Mean Time Between Failures.

## 2. Overall Description

### 2.1 Product Perspective
The ZNIX Framework is a middleware layer that sits between the Windows operating system/user applications and a unified, semantically rich information store. It mediates between data-producing applications (via proxies or direct API calls) and the end-user (via a dedicated browser).

### 2.2 Stakeholders and User Characteristics
| Stakeholder | Description | Key Goals/Needs |
| :--- | :--- | :--- |
| **End User** (Home User, Manager, Researcher) | Primary consumer of the framework's GUI. Manages personal/professional information. | Intuitive, Explorer-like interface. Minimal training required. Reliable archiving. |
| **ZNIX-Aware Application Developer** | Builds new applications that leverage the ZNIX data model. | Clean, well-documented public API. Powerful query capabilities. Stable data model. |
| **ZNIX Framework System Architect** | Designs the core system components and integration strategy. | Coherent, extensible architecture. Efficient data store. Robust proxy interfaces. |
| **Open Source Community Contributor** | Reviews, uses, modifies, or extends the open-source project. | Accessible source code. Clear contribution guidelines. Transparent roadmap. |

### 2.3 Operating Environment
*   **Software:** Microsoft Windows 2000 Professional or Windows XP Professional.
*   **Target Applications (for Proxy Integration):**
    *   Email Client: Outlook Express 6.x
    *   Web Browser: Internet Explorer 6.x
    *   Document Editor: Microsoft Word 2003
*   **Runtime:** .NET Framework (specific version TBD) or equivalent native Windows APIs.

### 2.4 Design and Implementation Constraints
1.  The system shall be designed for a single user per installation.
2.  The core framework shell process shall not exceed 40 MB of RAM utilization.
3.  The system must be operational on hardware with a Pentium III 1-GHz processor and 256 MB of RAM.
4.  All text data must be stored using Unicode (UTF-8 or UTF-16) encoding.
5.  The user interface must comply with the Windows 2000 Logo Requirements for consistency.

### 2.5 Assumptions and Dependencies
*   The user possesses basic familiarity with the Windows Explorer interface.
*   Third-party applications (Outlook Express, IE, Word) will remain stable within the versions specified for integration.
*   The project will be hosted and distributed via a public open-source platform (e.g., SourceForge).

## 3. System Requirements

### 3.1 Functional Requirements

#### 3.1.1 Core Data Management (FR-01)
*   **FR-01.1:** The system shall provide the capability to create, read, update, and delete (CRUD) **Entity** objects.
*   **FR-01.2:** The system shall provide the capability to create, read, update, and delete (CRUD) **Associate** objects.
*   **FR-01.3:** The system shall provide the capability to create and delete **Relationship** objects linking an Associate to an Entity.
*   **FR-01.4:** The system shall persist all Entity, Associate, and Relationship data in a centralized, reliable data store.

#### 3.1.2 Information Capture & Proxy Integration (FR-02)
*   **FR-02.1:** The system shall intercept outbound email messages from Outlook Express 6.x prior to sending.
    *   **FR-02.1.1:** For each intercepted email, the system shall create an Associate containing the message body and metadata.
    *   **FR-02.1.2:** The system shall create or retrieve a "Person" Entity for each recipient (To, CC) and link the new email Associate to them.
*   **FR-02.2:** The system shall fetch inbound email from a user-configured POP3 server.
    *   **FR-02.2.1:** For each fetched email, the system shall create an Associate.
    *   **FR-02.2.2:** The system shall create or retrieve a "Person" Entity for the sender and link the email Associate to it.
*   **FR-02.3:** The system shall provide a mechanism to capture references to documents saved from Microsoft Word 2003.
*   **FR-02.4:** The system shall provide a mechanism to capture URLs and page content from Internet Explorer 6.x navigation.

#### 3.1.3 User Interface & Browsing (FR-03)
*   **FR-03.1:** The system shall provide a graphical user interface (the "ZNIX Browser") for navigating managed information.
*   **FR-03.2:** The browser shall present a hierarchical, folder-like view that organizes Associates under their related Entities.
*   **FR-03.3:** The browser shall allow users to select and view the properties of any Entity or Associate.
*   **FR-03.4:** The browser shall provide visual feedback (e.g., a distinct icon or label) for any Entity or Associate that has been archived to removable media.

#### 3.1.4 Relationship Management (FR-04)
*   **FR-04.1:** The system shall provide a dedicated GUI for manually defining relationships between a data item (e.g., an open document) and existing Entities.
*   **FR-04.2:** This GUI shall allow the user to visually select one or more target Entities and create a Relationship to the active data item.

#### 3.1.5 Archiving (FR-05)
*   **FR-05.1:** The user shall be able to select a set of related information (an Entity and its associated Associates) for archiving.
*   **FR-05.2:** The system shall copy the selected data set to a user-specified removable storage medium (e.g., CD-ROM, USB drive).
*   **FR-05.3:** Upon successful copy, the system shall replace the original data in the central store with a lightweight **Archive Record** placeholder containing the media ID and path.
*   **FR-05.4:** When a user attempts to access an archived item, the system shall notify the user of its archived status and the required media.

#### 3.1.6 Developer API (FR-06)
*   **FR-06.1:** The system shall expose a public API for programmatic CRUD operations on Entities and Associates.
*   **FR-06.2:** The API shall provide methods for creating and managing Relationships.
*   **FR-06.3:** The API shall provide a query function to search for Entities and Associates based on user-defined criteria (e.g., name, type, date).

#### 3.1.7 Security (FR-07)
*   **FR-07.1:** The system shall include a security layer to prevent unauthorized data access by scripts executing in remote contexts (e.g., web pages).
*   **FR-07.2:** The system shall implement safeguards to prevent unintended logical corruption of the relationship graph by user actions.

### 3.2 External Interface Requirements

#### 3.2.1 User Interfaces
*   **UI-01 ZNIX Browser:** Must be intuitive for Windows users, with interaction patterns and visual design resembling Windows Explorer. Must support hierarchical navigation, context menus, and drag-and-drop where appropriate.
*   **UI-02 Relationship GUI:** A modeless or dialog window that allows visual linking of a focal data item to Entity symbols.

#### 3.2.2 Hardware Interfaces
*   **HW-01:** Must support reading from and writing to standard removable media interfaces (USB, CD-ROM).

#### 3.2.3 Software Interfaces
*   **SI-01 ZNIX Public API:** A programmatic interface (e.g., a .NET assembly) exposing classes and methods for Entity, Associate, and Relationship management. Its design should offer familiarity comparable to the `System.IO` namespace for listing and manipulation.
*   **SI-02 Windows OS Integration:** The framework shall integrate with the Windows shell, potentially as a namespace extension, and comply with relevant OS event and service models.

#### 3.2.4 Communications Interfaces
*   **CI-01:** Must be capable of connecting to POP3 servers on standard port 110 to retrieve email.

### 3.3 Non-Functional Requirements

#### 3.3.1 Performance Requirements
*   **PER-01:** The memory footprint of the core framework shell process shall not exceed **40 MB** under normal browsing and idle conditions.
*   **PER-02:** The system shall be usable on a computer with a **Pentium III 1-GHz** CPU and **256 MB** of system RAM.
*   **PER-03:** Query operations via the public API for common searches shall return results in less than **3 seconds** for a store containing 10,000 objects.

#### 3.3.2 Reliability & Availability
*   **REL-01:** The Mean Time Between Failures (MTBF) for the core framework services shall be greater than **3 months**.
*   **REL-02:** Data corruption due to framework failure shall be recoverable via standard backup mechanisms (user responsibility) or archive records.

#### 3.3.3 Security Requirements
*   **SEC-01:** The framework shall not expose data access points to web-based scripts or remote processes.
*   **SEC-02:** User confirmation shall be required for operations that permanently delete or archive large sets of primary data.

#### 3.3.4 Compliance
*   **COM-01:** The product shall conform to the **Windows 2000 Logo Requirements** for application compatibility and user interface.
*   **COM-02:** All textual data shall be stored and processed using **ISO 10646 (Unicode UTF-8/16)** character encoding.

#### 3.3.5 Observability & Support
*   **OBS-01:** The project's distribution website shall include a mechanism for users to submit feedback and bug reports.
*   **OBS-02:** The project's distribution website shall include a public feature wish-list or roadmap to manage community input.

### 3.4 Acceptance Criteria
The following high-level tests define the minimum criteria for acceptance of the v1.0 release.

**AC-01: Email Capture**
*   *Given* a user sends an email using Outlook Express 6,
    *When* the send button is pressed,
    *Then* a new Associate for the email appears in the ZNIX Browser linked to Person Entities for each recipient.

**AC-02: Hierarchical Browsing**
*   *Given* the data store contains multiple Entities and Associates,
    *When* the user opens the ZNIX Browser,
    *Then* they can expand Entity nodes to see a list of related Associates in a tree-view pane.

**AC-03: Archiving Notification**
*   *Given* an Entity "Project Alpha" has been archived to a USB drive,
    *When* the user searches for "Project Alpha" in the browser,
    *Then* the result is visibly marked as "Archived" and details the required media.

**AC-04: API Relationship Creation**
*   *Given* a developer has a valid Entity ID and Associate ID,
    *When* they call `CreateRelationship(entityId, associateId)` via the public API,
    *Then* the relationship is immediately persisted and is reflected in the next refresh of the ZNIX Browser view.
