### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the NPOESS Data Exploitation (NDE) system. It serves as the authoritative source for developers, testers, project managers, and stakeholders to understand what the system must accomplish. The intended audience includes the NDE development team, NOAA operational and climate users, system operators, and integration partners.

#### 1.2 Scope
The NDE system is a ground-based data processing, archiving, and distribution system designed to support the NPOESS Preparatory Project (NPP) and subsequent NPOESS satellite missions. Its core mission is to:
*   Receive Sensor Data Records (SDRs), Environmental Data Records (EDRs), and associated metadata (collectively, xDRs) from the Interface Data Processing Segment (IDPS).
*   Generate NOAA-unique and user-tailored environmental data products.
*   Distribute products to NOAA operational centers (e.g., NWS, NCEP), the climate community, and authorized external civilian customers.
*   Archive NOAA-unique products and system elements to the Comprehensive Large Array-data Stewardship System (CLASS) for long-term preservation.
*   Provide system monitoring, management, and customer support capabilities.

The system will be deployed in three distinct environments: Operational (OPS), System Test (TEST), and Development (DEV).

**Out of Scope:**
*   Primary satellite data acquisition and Level 0-2 processing (performed by IDPS).
*   Internal development of core scientific algorithms (supplied by NOAA, e.g., from STAR).
*   Direct management of satellite spacecraft or instruments.

### 2. Overall Description

#### 2.1 Product Perspective
The NDE system is a major component within the NOAA ESPC/PSGS program. It acts as a downstream processor and distributor, dependent on upstream data from the IDPS and ancillary sources. It interacts with external archival (CLASS), mission management (MMC), and customer systems.

**System Interfaces Diagram (Context):**
```
[IDPS] --(xDRs)--> [NDE CORE] --(Products)--> [Customers]
                        |                              |
                        |--(Archive)--> [CLASS]        |
                        |                              |
                        |--(Status)--> [MMC]           |
                        |                              |
                        |--(Alerts)--> [ESPC/NPOESS Trouble Tickets]
```

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **System Operators** | Technical staff, 24/7 shift work. | Real-time monitoring, alerting, job control, failure recovery tools, reporting. |
| **NOAA Operational Users (NWS/NCEP)** | Meteorologists, forecasters. Low latency tolerance. | Reliable, timely delivery of specific products in standard formats (GRIB, BUFR) for ingestion into forecast models. |
| **NOAA Climate Community** | Researchers, scientists. High data quality/consistency needs. | Complete, well-documented, archived data products with robust metadata for long-term studies. |
| **External Civilian Customers** | Diverse organizations (academia, private sector). Varied technical expertise. | Flexible subscription management, multiple data formats and delivery methods (push/pull). |
| **Algorithm Developers (STAR)** | Scientists, software engineers. | Well-defined integration standards (DAP), robust test environment (SADIE), and version management. |
| **Administrators/Managers** | Government and project management. | System health dashboards, performance metrics, user management, audit logs. |

#### 2.3 Operating Environment
*   **Hardware:** To be deployed on ESPC/IPD infrastructure. Expected to include high-performance computing clusters, large-scale storage arrays, and network appliances.
*   **Software:** Will utilize a combination of COTS, GOTS, and custom-developed software. Must integrate with existing NOAA enterprise services.
*   **Environments:** Three parallel environments: DEVELOPMENT (DEV), SYSTEM TEST (TEST), and OPERATIONAL (OPS).

#### 2.4 Design and Implementation Constraints
1.  Must comply with all applicable NOAA IT security policies and controls.
2.  Must conform to Federal Enterprise Architecture (FEA) guidelines.
3.  Must implement interfaces as specified in governing ICDs (IDPS, CLASS, MMC).
4.  Scientific algorithms are "black boxes" supplied by NOAA; NDE provides execution framework only.
5.  Must support continuity of operations (COOP) and disaster recovery requirements.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** IDPS will deliver xDR data per agreed-upon SLAs and ICDs.
*   **Assumption:** CLASS will be available and provide stable archive/retrieval interfaces.
*   **Assumption:** Necessary ancillary data (e.g., from NCEP) will be available via defined services.
*   **Dependency:** Timely delivery and quality of NOAA-supplied scientific algorithms.
*   **Dependency:** Availability of underlying ESPC/IPD infrastructure and network capacity.

### 3. System Features and Requirements

#### 3.1 Feature: Data Ingestion and Validation
**Description:** The system shall acquire xDR data from IDPS and ancillary data from external sources, validating integrity and completeness before making it available for processing.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **ING-01** | The system shall subscribe to and receive real-time notifications of xDR data availability from IDPS. | High |
| **ING-02** | Upon notification, the system shall retrieve the xDR data from IDPS with an access latency of <10 seconds for 99% of requests. | High |
| **ING-03** | The system shall validate the checksum and metadata of all ingested xDR files against IDPS Data Delivery Reports (DDRs). | High |
| **ING-04** | The system shall retrieve required ancillary data (e.g., model data from NCEP) based on product generation schedules. | Medium |
| **ING-05** | The system shall log all ingestion activities, including successes, failures, and validation errors, to the system log. | Medium |

#### 3.2 Feature: Product Generation and Processing
**Description:** The system shall execute NOAA-supplied algorithms to generate NOAA-unique products and apply tailoring operations to create customer-specific products.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **GEN-01** | The system shall schedule and execute product generation jobs triggered by the arrival of all required input data (xDRs and ancillary). | High |
| **GEN-02** | The system shall generate NOAA-unique products in HDF5 format, incorporating FGDC-compliant metadata with remote sensing extensions. | High |
| **GEN-03** | The system shall tailor products according to customer subscription profiles, including operations such as format conversion (to GRIB, BUFR, netCDF), re-projection, aggregation, and compression. | High |
| **GEN-04** | For 98% of products, the total generation latency (time from receipt of final input to product ready for distribution) shall be less than 5 minutes. | High |
| **GEN-05** | The system shall manage the lifecycle of processing jobs, tracking status (Queued, Running, Complete, Failed), priority, and resource utilization. | Medium |

#### 3.3 Feature: Product Distribution and Delivery
**Description:** The system shall manage customer subscriptions and deliver finished products via push or pull mechanisms, meeting defined latency targets.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **DST-01** | The system shall maintain a database of customer subscriptions, including product type, delivery format, method (push/pull), and endpoint. | High |
| **DST-02** | The system shall automatically push products to customer-specified endpoints (e.g., FTP, HTTP) for subscriptions configured for push delivery. | High |
| **DST-03** | The system shall provide a secure pull interface (e.g., HTTPS API) for customers to retrieve their subscribed products. | High |
| **DST-04** | The system shall meet the latency requirement specified in each active subscription (e.g., <5 min for operational users). | High |
| **DST-05** | The system shall relay SARSAT and A-DCS telemetry/data to the USMCC & US Global Processing Center within 1 minute of receipt from IDPS. | High |

#### 3.4 Feature: Archival to CLASS
**Description:** The system shall package and deliver NOAA-unique products, associated metadata, and baselined system elements to the CLASS long-term archive.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **ARC-01** | The system shall automatically package each NOAA-unique product with its FGDC-compliant metadata and deliver it to CLASS. | High |
| **ARC-02** | The system shall generate and transmit a delivery manifest to CLASS for each archival transaction and record CLASS's receipt acknowledgement. | High |
| **ARC-03** | Upon government approval, the system shall deliver baselined system elements (e.g., algorithm source code, documentation) to CLASS for permanent preservation. | Medium |
| **ARC-04** | The system shall be capable of retrieving archived xDRs and products from CLASS for reprocessing scenarios. | Medium |

#### 3.5 Feature: System Management and Monitoring
**Description:** The system shall provide capabilities for operators to monitor health, control operations, manage configurations, and respond to failures.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **MGT-01** | The system shall provide a graphical dashboard displaying real-time system health, performance metrics (latency, volume), and job status. | High |
| **MGT-02** | The system shall generate alerts (via email, dashboard, SNMP) for predefined fault conditions (e.g., job failure, interface disruption, performance threshold breach). | High |
| **MGT-03** | The system shall support manual operator initiation of reprocessing jobs using historical data from CLASS. | Medium |
| **MGT-04** | The system shall implement automated failover procedures to a redundant OPS or TEST environment upon detection of a critical failure in the primary OPS environment. | High |
| **MGT-05** | The system shall retain detailed performance and event logs for a minimum of 90 days. | Medium |

#### 3.6 Feature: User and Subscription Management
**Description:** The system shall support the lifecycle management of users and their product subscriptions through a governed workflow.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **USR-01** | The system shall provide a web-based portal for user registration and subscription requests. | Medium |
| **USR-02** | The system shall route new subscription requests to a designated government authority for approval/denial. | Medium |
| **USR-03** | Upon approval, the system shall automatically update user access controls and subscription profiles without requiring a system restart. | Medium |
| **USR-04** | The system shall enforce data access restrictions as defined in the Data Denial Plan when in Restricted Access Mode. | High |

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Operator Console:** Web-based GUI for monitoring, alerting, and job control.
*   **Customer Portal:** Web-based interface for subscription management and product pull access.
*   **Administration Interface:** Secure UI for user management and system configuration.

#### 4.2 Hardware Interfaces
Interfaces with ESPC/IPD-provided hardware (servers, storage, network) are defined by underlying infrastructure contracts and are outside the direct scope of this SRS.

#### 4.3 Software Interfaces
| Interface System | Direction | Protocol/Format | Key Data | SLA/Constraint |
| :--- | :--- | :--- | :--- | :--- |
| **IDPS** | Inbound | As per ICD (e.g., CFDP, FTP) | xDRs (HDF5), DDRs (XML), Telemetry | Access latency <10 sec. Real-time notification. |
| **CLASS** | Bi-directional | As per ICD (e.g., HTTPS, SFTP) | Products (HDF5, etc.), Metadata, Manifests | Conform to CLASS ICD. Delivery acknowledgement. |
| **NPOESS MMC** | Bi-directional | As per ICD (e.g., Messaging) | Status, Notifications, Service Requests | 100% message delivery within ICD time. |
| **Ancillary Data Sources (NCEP)** | Inbound | Various (e.g., NFS, LDM) | Model Data (GRIB, etc.) | Availability as per source schedule. |
| **Customer Endpoints** | Outbound | FTP, SFTP, HTTPS | Tailored Products (GRIB, BUFR, netCDF) | Meet subscription latency (e.g., <5 min). |

#### 4.4 Communications Interfaces
System components shall communicate over secure, high-bandwidth networks within the ESPC/NOAA infrastructure, utilizing protocols such as HTTPS, SFTP, and enterprise messaging services as required by specific interfaces.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   **Product Generation Latency:** <5 minutes from final input receipt for 98% of products.
*   **IDPS Data Access Latency:** <10 seconds from notification for 99% of retrievals.
*   **Data Relay Latency:** SARSAT/A-DCS data relay within 1 minute of IDPS receipt.
*   **Throughput:** Must support peak data volumes from NPP and scale to future NPOESS C1/C2 volumes.

#### 5.2 Reliability and Availability
*   **System Availability:** The operational (OPS) environment shall achieve >98% availability over any 12-month period.
*   **Capability Uptime:** Individual critical capabilities (Ingest, Generation, Distribution) shall not be interrupted for more than 2 hours in a 24-hour period, or 4 hours in a 30-day period.
*   **Mean Time To Repair (MTTR):** Automated failover shall be initiated within 5 minutes of critical failure detection.

#### 5.3 Security Requirements
*   The system shall comply with all controls specified in the current NOAA IT Security Manual.
*   The system shall protect data integrity against human error, transmission error, software bugs, hardware failure, and natural disasters.
*   All external interfaces shall employ authentication and encryption (e.g., TLS 1.2+).
*   The system shall implement role-based access control (RBAC) for all user functions.

#### 5.4 Compliance Requirements
*   The system architecture shall conform to the Federal Enterprise Architecture (FEA) reference models.
*   All metadata shall comply with the FGDC Content Standard for Digital Geospatial Metadata (CSDGM) and its remote sensing extensions.
*   All deliverables shall adhere to relevant NOAA and Department of Commerce policies.

#### 5.5 Observability Requirements
*   The system shall retain all performance, event, and audit logs for a minimum of 90 days.
*   The system shall provide tools to generate custom reports on system performance, product throughput, and user activity.

### 6. Acceptance Criteria
The following acceptance tests shall be passed to verify core capabilities.

#### 6.1 Generate NOAA-Unique Product
*   **Test AC-GEN-01 (Nominal):**
    *   **Given** all required xDRs and ancillary data are successfully ingested and validated,
    *   **When** the scheduled product generation job executes,
    *   **Then** a NOAA-unique product in HDF5 format with FGDC-compliant metadata is created and placed in the distribution queue.
*   **Test AC-GEN-02 (Failure):**
    *   **Given** a product generation job is initiated with corrupt input data,
    *   **When** the failure is detected by the system,
    *   **Then** the job status is logged as "Failed," a high-priority alert is sent to operators, and automated recovery procedures are initiated.

#### 6.2 Distribute Product to Customer
*   **Test AC-DST-01 (Push Delivery):**
    *   **Given** a customer with an active "push" subscription for Product X in GRIB2 format,
    *   **When** Product X is generated and ready for distribution,
    *   **Then** the system formats the product as GRIB2 and successfully transmits it to the customer's pre-configured FTP endpoint.
*   **Test AC-DST-02 (Latency):**
    *   **Given** a subscription with a 5-minute latency requirement,
    *   **When** the final required input xDR is received by NDE,
    *   **Then** the finished, tailored product is available for customer pull (or pushed) within 5 minutes.

#### 6.3 Archive to CLASS
*   **Test AC-ARC-01 (Product Archive):**
    *   **Given** a NOAA-unique product has been generated,
    *   **When** the daily archiving process runs,
    *   **Then** the product and its metadata are packaged, transmitted to CLASS, and a corresponding delivery manifest is recorded in the NDE database upon CLASS acknowledgement.
*   **Test AC-ARC-02 (Element Archive):**
    *   **Given** a system algorithm version is approved for baselining,
    *   **When** an operator initiates the "Archive System Element" procedure,
    *   **Then** the algorithm's source code, documentation, and dependency manifest are delivered to CLASS for permanent archive.
