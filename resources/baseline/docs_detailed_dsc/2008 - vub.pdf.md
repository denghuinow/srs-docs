### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Publications Management System (PMS). It serves as a contract between the customer (VUB) and the development team (SE1), providing a comprehensive description of the system's intended capabilities, constraints, and external interfaces. The primary audiences are stakeholders, project managers, developers, and testers.

#### 1.2 Scope
The PMS is a web-based platform for managing a database of academic publications. Its core functions include:
*   Storing bibliographical metadata and full-text documents (PDF/PostScript).
*   Automatically extracting metadata from uploaded documents.
*   Providing manual correction interfaces for extracted data.
*   Offering sophisticated search and retrieval capabilities.
*   Enforcing access control based on user roles and physical network location (VUB-network).
*   Providing both web browser (W3C XHTML compliant) and command-line interfaces.

**In-Scope (Core Release):**
*   User role management (Guest, VUB-Network User, Member, Publisher, Moderator, Administrator).
*   Publication upload, metadata extraction, editing, search, view, and download.
*   Reference export in BIB and RIS formats.
*   User registration, validation, and account management.
*   System administration via web and CLI.
*   Deployment on the Linux server "Wilma" using Ruby (without frameworks) and MySQL.

**Out-of-Scope (Non-Goals):**
*   Support for non-academic media formats (audio, video).
*   Automatic disambiguation of author or institute names/aliases.
*   Compatibility with non-free (proprietary) software tools for core functionality.
*   Support for additional document formats (e.g., MS Word, ODT) in the core release.
*   Integration with external bibliographic databases.
*   Automated fetching of full texts from URLs.

### 2. Overall Description

#### 2.1 Product Perspective
The PMS is a new, self-contained web application. It will interact with the following external systems:
*   **MySQL Database:** For persistent storage of all system data.
*   **Email Server (SMTP):** For sending account validation and notification emails.
*   **Client Web Browsers:** For user interaction, requiring W3C XHTML 1.0 compliance.
*   **Wilma Server OS (Linux):** The deployment and runtime environment.

#### 2.2 User Classes and Characteristics
| User Class | Key Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Guest** | Anonymous, outside VUB-network. | To register for an account or log in if already a member. |
| **VUB-Network User** | Connected via VUB IP, not logged in. | To search, browse, view details, and download publications without an account. |
| **Member** | Authenticated user with a personal account. | To manage personal profile, and perform all VUB-Network User actions. |
| **Publisher** | Authenticated Member with elevated privileges. | To upload new publications (single/bulk) and edit metadata for publications they own. |
| **Moderator** | Authenticated user, typically per department/group. | To manage user levels within their group and edit publications within their purview. |
| **Administrator** | Authenticated user with full system control. | To manage all users, groups, publications, and system configuration. |
| **Customer/Supplier** | VUB academic institution. | To define requirements, receive the system, and ensure it meets academic needs. |
| **Developer/Tester** | SE1 team. | A clear, unambiguous specification to design, implement, and verify the system. |

#### 2.3 Operating Environment
*   **Server:** Application must run on the Linux server named "Wilma."
*   **Software Stack:** Core application logic must be implemented in Ruby without using frameworks (e.g., Rails, Sinatra). Data persistence must use MySQL.
*   **Client Interface:** The web interface must generate W3C XHTML 1.0 Transitional compliant output.
*   **Network:** The system must distinguish between requests originating from the VUB-network and those from outside it.

#### 2.4 Design and Implementation Constraints
1.  **Technology:** Ruby (no frameworks), MySQL, XHTML 1.0.
2.  **Access:** Must provide both web and command-line (for administration) interfaces.
3.  **Security:** CLI administrative access must be restricted to the local VUB-network.
4.  **Compliance:** Must adhere to W3C standards and SE1 coding conventions.
5.  **Free Software:** Core system must not depend on non-free software tools.

#### 2.5 User Documentation
*   Online help text integrated into the web interface.
*   Administrator manual covering CLI commands and system configuration.
*   Installation and deployment guide for the Wilma server.

#### 2.6 Assumptions and Dependencies
*   The Wilma server is stable, maintained, and has necessary resources (disk, memory).
*   A functional MySQL server and SMTP server are available and accessible.
*   Users have a modern, XHTML-compliant web browser or command-line access (for admins).

### 3. System Requirements

#### 3.1 Functional Requirements

##### 3.1.1 User Management (AUTH)
*   **AUTH-1: User Registration**
    *   **Description:** A Guest shall be able to register for a new account by providing a unique username, password, and valid email address.
    *   **Priority:** Critical
*   **AUTH-2: Email Validation**
    *   **Description:** The system shall send an email with a validation link upon successful registration. The account shall remain inactive until the link is clicked.
    *   **Priority:** Critical
*   **AUTH-3: User Authentication (Login/Logout)**
    *   **Description:** A Guest or Member shall be able to authenticate using their username and password. Authenticated users shall be able to log out.
    *   **Priority:** Critical
*   **AUTH-4: Password Recovery**
    *   **Description:** A user who has forgotten their password shall be able to request a reset link via their registered email address.
    *   **Priority:** Sufficient
*   **AUTH-5: IP-Based Access Grant**
    *   **Description:** The system shall automatically grant "VUB-Network User" privileges to any user accessing the system from a recognized VUB-network IP address, without requiring login.
    *   **Priority:** Critical
*   **AUTH-6: Role-Based Access Control (RBAC)**
    *   **Description:** The system shall enforce permissions based on the user classes defined in Section 2.2. A user shall only be able to perform actions allowed for their role.
    *   **Priority:** Critical

##### 3.1.2 Publication Management (PUB)
*   **PUB-1: Publication Upload**
    *   **Description:** A Publisher, Moderator, or Administrator shall be able to upload a PDF or PostScript file to create a new publication record.
    *   **Priority:** Sufficient
*   **PUB-2: Metadata Auto-Extraction**
    *   **Description:** Upon upload, the system shall attempt to automatically extract bibliographical metadata (e.g., title, authors, abstract, publication date) from the document.
    *   **Priority:** Sufficient
*   **PUB-3: Metadata Manual Editing**
    *   **Description:** The user who uploaded a publication shall be presented with the auto-extracted metadata for review and manual correction before final submission. Moderators and Admins shall be able to edit publications within their scope.
    *   **Priority:** Sufficient
*   **PUB-4: Publication Storage**
    *   **Description:** The system shall store the full-text document and its associated metadata permanently in the database.
    *   **Priority:** Critical
*   **PUB-5: Publication Deletion**
    *   **Description:** Administrators shall be able to delete publication records and their associated files.
    *   **Priority:** Sufficient

##### 3.1.3 Search and Retrieval (SRCH)
*   **SRCH-1: Basic Search**
    *   **Description:** A VUB-Network User or Member shall be able to search publications using keywords, author names, and date ranges.
    *   **Priority:** Critical
*   **SRCH-2: Search Results Display**
    *   **Description:** The system shall display a list of matching publications, showing at minimum the title and primary author for each.
    *   **Priority:** Critical
*   **SRCH-3: Publication Detail View**
    *   **Description:** A user shall be able to select a publication from the results list to view its full metadata.
    *   **Priority:** Critical
*   **SRCH-4: Full-Text Download**
    *   **Description:** A VUB-Network User or Member shall be able to download the full-text (PDF/PS) file of a publication.
    *   **Priority:** Critical
*   **SRCH-5: Reference Export**
    *   **Description:** A user shall be able to export the bibliographical reference of a publication (or a set of publications) in standard BIB and RIS formats.
    *   **Priority:** Sufficient

##### 3.1.4 Administration (ADMIN)
*   **ADMIN-1: User Account Management**
    *   **Description:** An Administrator shall be able to create, delete, enable/disable, and modify the role/group membership of any user account via a web interface.
    *   **Priority:** Sufficient
*   **ADMIN-2: Group Management**
    *   **Description:** An Administrator shall be able to create, delete, and modify user groups (e.g., departments, research units).
    *   **Priority:** Sufficient
*   **ADMIN-3: System Configuration**
    *   **Description:** An Administrator shall be able to modify system-wide parameters (e.g., email settings, upload limits) via a configuration panel.
    *   **Priority:** Sufficient
*   **ADMIN-4: Command-Line Interface (CLI)**
    *   **Description:** An Administrator shall be able to perform all user and publication management functions via a command-line interface, accessible only from the VUB-network.
    *   **Priority:** Sufficient
*   **ADMIN-5: Audit Logging**
    *   **Description:** The system shall log all download events (timestamp, user ID, publication ID) for audit purposes.
    *   **Priority:** Sufficient

#### 3.2 Non-Functional Requirements

##### 3.2.1 Performance
*   **PERF-1:** The system shall return search results to the user within 3 seconds for typical queries under expected load.
*   **PERF-2:** The system shall support a concurrent user load to be determined during detailed design (TBD).

##### 3.2.2 Reliability
*   **RELY-1:** The system shall target a defined Mean Time Between Failures (MTBF) per development spiral iteration.
*   **RELY-2:** The system shall support automated backup of the database and document store, with a restore capability.

##### 3.2.3 Security
*   **SEC-1:** User passwords shall be stored encrypted (hashed and salted) in the database.
*   **SEC-2:** All user input (forms, CLI) shall be validated to prevent common injection attacks.
*   **SEC-3:** Role-based access control (RBAC) shall be enforced on all application functions.
*   **SEC-4:** Credentials (login, registration) shall be transmitted over a secure channel (HTTPS recommended, implied by "secure HTTP").

##### 3.2.4 Usability & Compliance
*   **USAB-1:** The web interface shall comply with the W3C XHTML 1.0 Transitional standard.
*   **USAB-2:** All error messages shall be informative and guide the user toward corrective action.
*   **USAB-3:** The source code shall adhere to the SE1 team's coding conventions.

##### 3.2.5 Observability
*   **OBS-1:** All system errors and exceptions shall be logged with sufficient detail for administrator review.
*   **OBS-2:** The system shall provide a status page indicating overall availability and health.

#### 3.3 External Interface Requirements

##### 3.3.1 User Interfaces
*   **Web UI:** Shall be rendered in XHTML 1.0, containing forms for login, search, upload, and administration. Must be functional in text-based browsers (e.g., Links2).
*   **CLI:** Shall provide a suite of administrative commands (e.g., `pms-cli --create-user --username jdoe`).

##### 3.3.2 Hardware Interfaces
*   The system shall interface with the local filesystem of the Wilma server for storage of uploaded document files.

##### 3.3.3 Software Interfaces
*   **MySQL Database:** Interface via a Ruby database driver (e.g., `mysql2` gem). Requires ACID compliance and concurrent connection support.
*   **SMTP Server:** Interface via Ruby's `net/smtp` or similar library for sending notification emails.

##### 3.3.4 Communications Interfaces
*   **HTTP/HTTPS:** Over TCP port 80 (and optionally 443) for web browser communication.
*   **SSH:** For secure CLI access to the Wilma server (implied by "direct server shell access").

#### 3.4 Acceptance Criteria (Examples)
*   **AC-1 Publication Search:** Given a user is connected from the VUB-network, when they enter an author's last name and a keyword in the search form and submit, then a page is displayed listing all matching publications, each showing its title and the main author's name.
*   **AC-2 User Registration:** Given a guest user is outside the VUB-network, when they fill the registration form with a unique username, valid password, and valid email and submit, then a confirmation email is sent to that address and the user's account status is set to "pending validation."
*   **AC-3 Publication Upload:** Given a user with the 'Publisher' role is logged in, when they upload a valid PDF file via the upload form, then a page is displayed showing the auto-extracted metadata in editable fields, allowing them to correct data before final submission.
*   **AC-4 Access Control:** Given a user with the 'Member' role is logged in, when they attempt to access the URL to edit a publication they did not upload, then the system responds with an HTTP 403 error (or equivalent) and displays an "authorization denied" message.

#### 4.3 Risk Management
| Risk | Probability | Impact | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| Inaccurate Auto-Extraction | High | Medium | Mandate manual review/correction step; provide bulk edit tools. |
| Database Scalability | Medium | High | Design for concurrency; implement database indexing; optimize queries. |
| Security Breaches | Medium | High | Encrypt passwords; validate/sanitize all inputs; restrict CLI access. |
| Wilma Server Downtime | Low | High | Communicate dependency clearly; implement system status page. |
| Complex Role Management | High | Medium | Use clear, hierarchical role model; conduct thorough permission testing. |

#### 4.4 Release Strategy & Milestones
1.  **Iteration 1 (Alpha):** Implements **Critical** requirements: AUTH-1, AUTH-3, AUTH-5, AUTH-6, PUB-4, SRCH-1, SRCH-2, SRCH-3, SRCH-4.
2.  **Iteration 2 (Beta):** Implements **Sufficient** requirements: AUTH-2, AUTH-4, PUB-1, PUB-2, PUB-3, PUB-5, SRCH-5, ADMIN-1 through ADMIN-5.
3.  **Iteration 3 (Optional):** Implements **Optional** features: Support for additional document formats (e.g., .doc, .odt), enhanced reference linking.
4.  **Final Release:** Deployment on Wilma with complete documentation and handover to the customer.
