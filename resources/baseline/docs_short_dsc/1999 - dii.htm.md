### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the XML Services (XS) component within the Defense Information Infrastructure (DII) Common Operating Environment (COE). The primary purpose is to provide a clear, complete, and unambiguous description of the XS capabilities to serve as a basis for design, implementation, qualification, and configuration management.

#### 1.2 Scope
The XS component provides core infrastructure services to enable mission applications to leverage XML technology for data interchange and management. It aims to abstract vendor-specific implementations and furnish data management functions for accessing distributed databases, thereby achieving system interoperability across the COE.

**In-Scope Elements:**
*   XML artifact lifecycle management via a central registry (producer, consumer, manager services).
*   XML schema design, creation, and validation tools.
*   Generation of conformant XML documents and schemas.
*   Parsing and validation of XML documents.
*   Operation in specified environmental modes (real-time, fixed, dynamic, degraded communications).

**Out-of-Scope Elements:**
*   Detailed internal API and data structure design.
*   Specifications for external Commercial Off-The-Shelf (COTS) RDBMS interfaces.
*   Personnel, training, and detailed administrative process definitions.
*   Detailed packaging procedures (deferred to COE guidelines).

### 2. Overall Description

#### 2.1 Product Perspective
XS is a middleware service component within the DII COE architecture. It interfaces transparently with existing data access services (DBIF, DAC) and underlying COTS RDBMSs. It provides a standardized layer for XML-based data definition, discovery, and interchange, insulating applications from proprietary database and XML parser implementations.

#### 2.2 Product Functions (Summary)
1.  **Registry Services:** Submit, discover, review, approve, and manage XML artifacts (tags, DTDs, schemas).
2.  **Design Services:** Create and validate XML schema structures using registered components.
3.  **Generation Services:** Produce XML instance documents and schema documents, ensuring conformance to registered structures.
4.  **Consumption Services:** Parse, validate, and process incoming XML documents.
5.  **Environmental Adaptation:** Adjust operational behavior (e.g., timeouts, caching) based on communication status and specified mode.

#### 2.3 User Characteristics
| Role | Expertise | Primary Interaction |
| :--- | :--- | :--- |
| **Producer** | Subject Matter Expert, Data Modeler | Submits new XML artifacts and metadata to the registry. |
| **Consumer** | Application Developer, System Integrator | Discovers and retrieves registered XML artifacts for reuse. |
| **Data/Database Manager** | Data Administrator, COI POC | Reviews, approves, and governs registry content. |
| **Application Developer** | Software Engineer | Uses XS design and generation services to build compliant applications. |
| **End-User (Deployed)** | Military Personnel | Uses applications reliant on XS; affected by environmental adaptations. |
| **Maintainer** | System Administrator | Manages data segments, user permissions, and system configuration. |

#### 2.4 Constraints
1.  **Architectural:** Must comply with COE segmentation and compliance levels as defined in the I&RTS.
2.  **Standards:** Must adhere to DOD data standards and COE-prescribed naming conventions.
3.  **Integration:** Must interface transparently with existing DBIF, DAC, and COTS RDBMS components.
4.  **Portability:** Registry and service software must be portable across all COE-compliant platforms.
5.  **Process:** Development shall follow government standards (e.g., MIL-STD-498).

#### 2.5 Assumptions and Dependencies
*   A COTS XML parser and validation engine will be available on the target platform.
*   Underlying COE data services (DBIF, DAC) are present and functional.
*   Network connectivity, albeit potentially degraded, will be available.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 XML Registry Services
*   **REQ-F-1.1:** The system shall provide a mechanism for a **Producer** to submit an Information Resource Submittal Package (IRSP) containing metadata and XML artifacts (tags, DTDs, DCDs).
*   **REQ-F-1.2:** The system shall allow a **Consumer** to search, browse, and discover registered XML artifacts based on metadata attributes (e.g., name, COI, date, keyword).
*   **REQ-F-1.3:** The system shall allow a **Consumer** to view the details of a registered artifact and download its technical specification.
*   **REQ-F-1.4:** The system shall provide a workflow for a **Data Manager** to review a submitted IRSP, approve it, reject it (with comments), or return it for modification.
*   **REQ-F-1.5:** The system shall maintain the status (e.g., Draft, Under Review, Approved, Deprecated) of each registered artifact throughout its lifecycle.
*   **REQ-F-1.6:** The system shall enforce access controls based on user roles (Producer, Consumer, Manager) and COI affiliation.

##### 3.1.2 XML Design Services
*   **REQ-F-2.1:** The system shall provide tools for an **Application Developer** to create new XML schema structures by assembling and extending registered tags and complex types.
*   **REQ-F-2.2:** The system shall validate that a newly designed schema references only approved/registered components or new components pending submission.

##### 3.1.3 XML Generation Services
*   **REQ-F-3.1:** The system shall generate well-formed XML instance documents that conform to a specified registered schema or DTD.
*   **REQ-F-3.2:** The system shall generate schema documents (e.g., DTD, XML Schema) from registered structures.
*   **REQ-F-3.3:** The system shall perform conformance checking between an XML instance document and its declared schema/DTD during generation.

##### 3.1.4 XML Consumption Services
*   **REQ-F-4.1:** The system shall parse incoming XML documents using a configured COTS parser.
*   **REQ-F-4.2:** The system shall validate an incoming XML document against its referenced schema or DTD registered within the system.
*   **REQ-F-4.3:** The system shall provide an API for applications to access the parsed and validated document object model (DOM) or event stream (SAX).

##### 3.1.5 Operational Mode Services
*   **REQ-F-5.1:** The system shall operate in predefined environmental modes: Real-Time, Fixed, Dynamic, and Degraded Communications.
*   **REQ-F-5.2:** In **Degraded Communications** mode, the system shall dynamically adjust local session timeouts and employ cached registry data where possible to maintain application functionality.

#### 3.2 External Interface Requirements

##### 3.2.1 User Interfaces
*   **REQ-UI-1:** A web-based interface shall be provided for all registry interactions (submission, search, review, management).
*   **REQ-UI-2:** Command-line tools shall be provided for schema design, generation, and validation to support scripting and integration into development pipelines.

##### 3.2.2 Software Interfaces
*   **REQ-SI-1:** XS shall interface with the COE **DBIF** and **DAC** components for persistent storage and retrieval of registry metadata and artifacts.
*   **REQ-SI-2:** XS shall be configurable to work with COE-approved **COTS RDBMS** (e.g., Oracle, Sybase) via the DAC.
*   **REQ-SI-3:** XS shall integrate with a COE-approved **COTS XML Parser**.

##### 3.2.3 Communications Interfaces
*   **REQ-CI-1:** Submission of IRSPs shall be possible via a defined electronic method (e.g., secure email, FTP upload). *[Note: Specific addressee TBD].*
*   **REQ-CI-2:** XS components shall communicate using COE-specified secure protocols.

#### 3.3 Performance Requirements
*   **REQ-P-1:** Registry search operations shall return results for simple queries within 3 seconds under normal load.
*   **REQ-P-2:** XML document validation (parsing + schema check) shall complete within time constraints appropriate for the operational mode (e.g., sub-second for Real-Time mode).
*   **REQ-P-3:** The system shall support concurrent access by a minimum of 100 registered users.

#### 3.4 Design Constraints
*   **REQ-DC-1:** The software shall be developed in a language compliant with the COE I&RTS (e.g., Java, C++).
*   **REQ-DC-2:** The database schema for the registry shall comply with FIPS PUB 127-2 (SQL).
*   **REQ-DC-3:** All configuration parameters shall be modifiable without source code recompilation.

#### 3.5 System Attributes

##### 3.5.1 Reliability
*   **REQ-R-1:** The core registry service shall have an availability of 99.5% during standard operating hours.

##### 3.5.2 Security
*   **REQ-S-1:** All access to XS management functions shall require PKI-based authentication.
*   **REQ-S-2:** All data in transit shall be encrypted using COE-mandated algorithms.

##### 3.5.3 Portability
*   **REQ-PT-1:** The XS component suite shall be portable across all UNIX and Windows variants specified as COE-compliant platforms.

#### 3.6 Other Requirements
*   **REQ-O-1:** The system shall produce audit logs for all submissions, approvals, and configuration changes.
*   **REQ-O-2:** The system shall support the concept of federated registries. *[Note: Rules of engagement TBD].*

### Appendix A: Metadata Schema Outline (Proposed)

The Information Resource Submittal Package (IRSP) shall include, but not be limited to, the following metadata:
1.  **Resource Identifier:** Unique ID (URN)
2.  **Administrative Metadata:**
    *   Submitter Name/Contact
    *   Submitting COI
    *   Date of Submission
    *   Intended Status (New, Revision, Deprecation)
3.  **Descriptive Metadata:**
    *   Resource Name
    *   Definition/Description
    *   Keywords
    *   Classification
4.  **Technical Metadata:**
    *   Artifact Type (Element, Attribute, ComplexType, DTD, Schema, etc.)
    *   Technical Specification (the actual XML/DTD file)
    *   Dependencies on other registered resources
    *   Version
5.  **Lifecycle Metadata:**
    *   Effective Date
    *   Expiration Date (if applicable)
    *   Manager Notes/Approval Record
