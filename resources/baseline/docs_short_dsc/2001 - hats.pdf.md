### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the HATS-GUI (High Assurance Transformation System Graphical User Interface). The purpose of this SRS is to provide a complete description of the system to be developed, serving as a basis for agreement between the customer (Dr. Victor Winter) and the development teams. It will guide the design, implementation, and testing phases of the project.

#### 1.2 Document Conventions
This document uses standard SRS formatting conventions. Requirements are uniquely identified with labels (e.g., `FR-001`, `NFR-001`). Markdown is used for structure, with headers, lists, and code blocks for clarity.

#### 1.3 Intended Audience and Reading Suggestions
*   **Stakeholders & Customers (Dr. Victor Winter, Guidance Team):** Should focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (Success Metrics & Constraints).
*   **Project Managers & Architects:** Should read the entire document, with emphasis on Sections 2, 3, and 4 to understand scope, interfaces, and system features.
*   **Software Developers & Testers:** Should use Sections 3 (Specific Requirements) and 4 (External Interface Requirements) as the primary reference for implementation and verification.

#### 1.4 Project Scope
The HATS-GUI is a platform-independent graphical front-end for the HATS-SML transformation engine. Its core mission is to simplify user interaction with transformation-based software development by providing intuitive tools for managing applications, executing transformations, and visualizing results via Syntax Derivation Trees (SDTs) and pretty-printed text. The GUI acts as a controller and visualizer; it does not perform core transformation logic, which remains the responsibility of the underlying HATS-SML system.

**In-Scope Items:**
*   Management of HATS applications (create, delete, modify, associate files).
*   Parsing of transformation language programs and target files to generate SDTs.
*   Orchestration of transformation execution via HATS-SML.
*   Display, navigation, and manipulation of SDT and pretty-printed text outputs.
*   Configuration of application-specific settings and editor associations.

**Out-of-Scope Items:**
*   Direct application of program transformations (handled by HATS-SML).
*   Multi-user or collaborative features.
*   Comprehensive tutorials or help systems (targets expert users).
*   Modification of HATS-SML's core algorithms or functionality.
*   Support for operating systems other than Sun Solaris, Windows 2000, and Linux.

### 2. Overall Description

#### 2.1 Product Perspective
The HATS-GUI is a new, self-contained component that integrates with the existing HATS ecosystem. It is a dependent subsystem that requires the HATS-SML 2.0 engine to function. The relationship is that of a master (GUI) and servant (HATS-SML), where the GUI invokes SML processes and interprets their outputs.

#### 2.2 Product Functions (Summary)
1.  **Application Management:** CRUD operations for HATS application projects.
2.  **File Parsing & SDT Generation:** Interface with HATS-SML parsers to produce SDTs from source files.
3.  **Transformation Execution:** Manage the lifecycle of a transformation run, handling input to and output from HATS-SML.
4.  **Visualization:** Render SDTs as interactive graphs and display pretty-printed text outputs.
5.  **Configuration Management:** Allow users to customize editor associations and visual display properties.

#### 2.3 User Classes and Characteristics
*   **End User:** An expert in transformation-based software development. Proficient in the HATS transformation language. Expects efficiency, precision, and robust handling of complex transformation artifacts. Has no need for basic tutorials.
*   **System Administrator:** Responsible for installing the GUI, ensuring JVM and ML interpreter are present, and configuring base system paths. Technical proficiency is assumed.

#### 2.4 Operating Environment
*   **Software:** Must run on Java 1.3 Platform. Requires a pre-installed Java Virtual Machine (JVM) and an ML interpreter for HATS-SML.
*   **Hardware:** Must operate on systems running the following OSes:
    *   Sun Solaris
    *   Microsoft Windows 2000
    *   Linux (Kernel 2.2.x or compatible)
*   **Dependencies:** HATS-SML version 2.0 must be installed and accessible.

#### 2.5 Design and Implementation Constraints
1.  **Language & Portability:** The system shall be implemented in Java 1.3 to ensure platform independence across the three target operating systems.
2.  **Performance:** Algorithms for SDT display must avoid excessive memory consumption (e.g., "virtual window zooming" techniques are prohibited).
3.  **Architecture:** The system shall be designed to isolate HATS-SML process interactions to facilitate error handling and prevent GUI halts.
4.  **Schedule:** The final deliverable must be completed and delivered by December 2001.

#### 2.6 User Documentation
A concise user manual detailing installation, application management, and feature operation will be provided. It will assume user expertise in the HATS transformation methodology.

#### 2.7 Assumptions and Dependencies
The project assumes that HATS-SML 2.0 is stable and provides consistent, documented interfaces for parsing and transformation. The project is dependent on this stability. Failure of HATS-SML may cause the GUI to fail, though the GUI should handle such failures gracefully where possible.

### 3. System Features

This section details the functional requirements derived from the user stories.

#### 3.1 Application Management
**Description:** Users shall be able to create, modify, and delete logical "applications," which are project containers for transformation language programs and target files.

**Requirements:**
*   `FR-001`: The system shall provide a dialog or view to create a new application, requiring at minimum a unique application name.
*   `FR-002`: The system shall allow a user to associate existing transformation language (`.tl`) files and target source files with an application.
*   `FR-003`: The system shall allow a user to modify an application's properties, including its name and file associations.
*   `FR-004`: The system shall allow a user to delete an application, with a confirmation prompt.
*   `FR-005`: The system shall persist application configurations between sessions.

#### 3.2 File Parsing and SDT Generation
**Description:** Users shall be able to parse relevant files to generate internal Syntax Derivation Tree (SDT) representations required for execution.

**Requirements:**
*   `FR-010`: The system shall provide a user action (e.g., menu item, button) to parse a selected transformation language program file.
*   `FR-011`: The system shall provide a user action to parse a selected target source file.
*   `FR-012`: Upon successful parsing, the system shall store the generated SDT in memory for the active application.
*   `FR-013`: The system shall display a clear error message if the HATS-SML parser fails, showing the relevant error output from the SML process.

#### 3.3 Transformation Execution
**Description:** Users shall be able to execute a parsed transformation language program against a parsed target file to apply transformations.

**Requirements:**
*   `FR-020`: The system shall provide an "Execute" action that is enabled when both a transformation program SDT and a target file SDT are loaded.
*   `FR-021`: Upon execution, the system shall invoke the HATS-SML engine with the correct parameters and inputs.
*   `FR-022`: The system shall capture the standard output and error streams from the HATS-SML process.
*   `FR-023`: Upon successful execution, the system shall capture and store the resulting output SDT and any pretty-printed text generated by HATS-SML.
*   `FR-024`: The system shall display HATS-SML error messages to the user in a dedicated console or log panel without the main GUI becoming unresponsive.

#### 3.4 SDT Visualization and Navigation
**Description:** Users shall be able to view, explore, and manipulate SDTs graphically.

**Requirements:**
*   `FR-030`: The system shall display an SDT as a graphical tree structure, with clear differentiation between node types (e.g., non-terminals, terminals).
*   `FR-031`: The system shall allow the user to expand/collapse sub-trees within the SDT view.
*   `FR-032`: The system shall allow basic navigation: panning and zooming of the overall tree view.
*   `FR-033`: The system shall highlight the corresponding node in the SDT when a user selects text in the associated pretty-printed output view (where correspondence is well-defined).
*   `NFR-001 (Performance):` The system shall render and display an SDT containing 10,000 nodes within 5 seconds of receiving the data from HATS-SML.

#### 3.5 Pretty-Printed Text Display and Search
**Description:** Users shall be able to view and search through the textual output of transformations.

**Requirements:**
*   `FR-040`: The system shall display pretty-printed text output in a scrollable, read-only text panel.
*   `FR-041`: The system shall provide a text search function (find) within the pretty-printed output panel.
*   `FR-042`: Search results shall be highlighted within the text panel.

#### 3.6 Configuration Management
**Description:** Users shall be able to configure system and application-level settings.

**Requirements:**
*   `FR-050`: The system shall provide a configuration dialog for associating specific file extensions (e.g., `.tl`, `.c`) with external editor executables.
*   `FR-051`: The system shall provide a "Launch Editor" context menu action for associated files that opens the file in the configured external editor.
*   `FR-052`: The system shall allow configuration of SDT visual properties (e.g., default colors for node types, font size) on a per-user basis.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The primary UI shall be a single-window, multi-panel desktop application using standard Java Swing (or AWT) components.
*   It shall include a menu bar (`File`, `Application`, `Parse`, `Execute`, `View`, `Configuration`), a toolbar for common actions, a main workspace for SDT and text views, and a status/console panel.

#### 4.2 Hardware Interfaces
None specified beyond standard OS-supported input/output devices.

#### 4.3 Software Interfaces
*   **HATS-SML 2.0:** The GUI shall interact with HATS-SML via system process invocation (`java.lang.Process`). It shall pass command-line arguments as defined by the HATS-SML API and communicate via standard input/output/error streams.
*   **External Editors:** The GUI shall launch external editor applications using the host OS's process execution mechanism, passing the target file path as an argument.

#### 4.4 Communications Interfaces
None required. All communication is local inter-process communication (IPC).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   `NFR-001`: As stated in FR-033, display of a 10,000-node SDT within 5 seconds.
*   `NFR-002`: User interface actions (button clicks, menu selections) shall provide visual feedback (e.g., cursor change, button press) within 200 milliseconds.
*   `NFR-003`: The GUI shall remain responsive (not block the UI thread) during long-running HATS-SML operations.

#### 5.2 Safety Requirements
Not applicable for this software system.

#### 5.3 Security Requirements
*   `NFR-010`: The system shall not require elevated privileges to install or run.
*   `NFR-011`: Application configuration files shall be stored in the user's home directory or application data directory.

#### 5.4 Software Quality Attributes
*   **Portability (`NFR-020`):** The system shall operate correctly on Sun Solaris, Windows 2000, and Linux without modification to the source code or bytecode.
*   **Robustness (`NFR-021`):** The GUI shall not crash due to errors or unexpected termination of the HATS-SML process. Errors shall be contained and reported.
*   **Usability (`NFR-022`):** The interface shall be intuitive for an expert user familiar with HATS concepts. Common tasks (Parse, Execute) shall be accessible within two clicks or keystrokes from the main view.

### 6. Success Metrics
The project will be deemed successful if the following acceptance criteria are met:
1.  The GUI successfully displays an SDT of 10,000 nodes within five seconds on reference hardware for all three target OS platforms.
2.  The complete system (HATS-GUI + HATS-SML) operates correctly end-to-end (create app, parse files, execute transformation, view outputs) on Sun Solaris, Windows 2000, and Linux without source code modification.
3.  Users can execute transformations and view outputs; the GUI does not halt or become unusable due to errors originating from the HATS-SML subsystem.

### 7. Undecided and TBD Issues
The following issues require resolution during the design phase:
1.  **Algorithm Strategy:** Optimization approach for SDT search algorithms to improve upon baseline O(n²) complexity.
2.  **Error Handling:** Specific recovery mechanisms for different classes of HATS-SML process failures (e.g., parse error vs. segmentation fault).
3.  **Data Consistency:** Handling strategy for edge cases where the pretty-printed text output does not have a clear, one-to-one correspondence with terminal nodes in the output SDT.
4.  **UI Layout:** Detailed wireframes and specifications for configuration menus and dialogs.
5.  **Maintenance Plan:** Long-term plan for bug fixes, compatibility updates, and feature enhancements post the December 2001 delivery.
