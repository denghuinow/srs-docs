### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the National Library of Medicine (NLM) Digital Repository System (DRS). The purpose of this system is to provide a robust, standards-based infrastructure for the long-term preservation and access of biomedical digital collections managed by NLM Library Operations. This SRS serves as a contract between the project stakeholders and the development team, establishing a definitive guide for system design, implementation, and validation.

#### 1.2 Document Conventions
- **Requirements IDs:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
- **Priority:** (H)igh, (M)edium, (L)ow.
- **Keywords:** `MUST`, `SHALL`, `SHOULD`, `MAY`, `WILL` are used as defined in IETF RFC 2119.
- Formatting: User roles are in *italics*. System components are in `monospace`.

#### 1.3 Intended Audience and Reading Suggestions
- **Project Sponsors & Management:** For scope validation and approval.
- **System Architects & Developers:** For design and implementation guidance. Focus on Sections 2, 3, and 4.
- **Quality Assurance Team:** For test plan and case development. Focus on Section 3.
- **NLM Stakeholders (Catalogers, Preservation Specialists, etc.):** For understanding system capabilities and providing feedback. Focus on Section 2 (Stakeholders) and relevant functional requirements.

#### 1.4 Project Scope
The NLM DRS is an Open Archival Information System (OAIS)-compliant digital repository. Its core mission is to **acquire, organize, preserve, and provide access** to designated biomedical digital materials for which NLM Library Operations has curatorial responsibility.

**Included Collections:**
- PubMed Central
- NLM Bookshelf
- History of Medicine Division digital projects
- Other born-digital and digitized materials under Library Operations purview.

**Explicitly Out of Scope:**
- Digital assets from other NLM divisions (e.g., UMLS, Visible Human).
- Web harvesting or crawling functionality.
- Maintenance of special client software for accessing complex objects (e.g., proprietary audiovisual players).
- Offline delivery services (e.g., physical media shipment).
- Materials with a "Permanence Not Guaranteed" rating, which may be subject to removal.

### 2. Overall Description

#### 2.1 Product Perspective
The DRS is a new, mission-critical system that will integrate with the existing NLM technology ecosystem. It will serve as the system of record for preserved digital objects, while other systems (e.g., PubMed Central public interface) may serve as primary access points.

**System Interfaces:**
- **PubMed Central / Bookshelf:** For ingesting content and potentially serving as an access channel.
- **Integrated Library System (ILS):** For potential metadata synchronization and authority control.
- **Authentication Services:** NIH Login (for NIH/NLM staff) and public access mechanisms.
- **Off-site Backup Facility:** For disaster recovery storage.

#### 2.2 Product Functions (High-Level)
1. **Ingest:** Accept Submission Information Packages (SIPs) from producers, validate them, and transform them into Archival Information Packages (AIPs).
2. **Archival Storage:** Securely store and manage AIPs, ensuring bit-level preservation and integrity.
3. **Data Management:** Maintain and provide access to descriptive, administrative, and structural metadata for all AIPs.
4. **Administration:** Manage system configuration, policies, user accounts, and audit logs.
5. **Preservation Planning:** Monitor technology landscape and support planning for format migration and other preservation actions.
6. **Access:** Provide a user interface for searching, browsing, and retrieving Dissemination Information Packages (DIPs) to authorized users.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| *General Public* | Anonymous or registered external users. Varied technical skill. | Discover and view publicly accessible materials. Simple, intuitive search. |
| *NIH Staff Researcher* | Authenticated internal user. Subject-matter expert. | Access to licensed/restricted materials. Reliable, performant access for research. |
| *NLM Cataloger* | Authenticated internal user. Metadata expert. | Intuitive interface for creating, editing, and linking descriptive metadata. No ability to modify preserved object bits. |
| *NLM Preservation Specialist* | Authenticated internal user. Digital preservation expert. | Tools to monitor file formats, run fixity checks, and execute preservation plans (e.g., format migration). |
| *NLM System Administrator* | Authenticated internal user. IT/Systems expert. | Full system control: user/role management, system configuration, audit log review, backup/restore operations. |
| *Content Producer/Donor* | External entity (organization or individual). | Clear submission guidelines and protocols (FTP, API, physical media). Receipt confirmation. |

#### 2.4 Operating Environment
- **Software:** Must run on enterprise-grade operating systems (e.g., Linux). Must support Java/.NET/Python-based application stacks and relational databases (e.g., PostgreSQL, Oracle).
- **Hardware:** Must be deployable on NLM's virtualized or bare-metal data center infrastructure.
- **Network:** Must operate within the NIH secure network enclave, supporting standard web protocols (HTTPS, SFTP).

#### 2.5 Design and Implementation Constraints
1. **Integration Constraints:** MUST integrate with existing PubMed Central and ILS systems.
2. **Security Constraints:** SHALL comply with all HHS/NIH security standards, including data-at-rest and data-in-transit encryption.
3. **Internationalization Constraint:** MUST support ingest, storage, and display of metadata and content in multiple languages and non-Roman scripts (e.g., Cyrillic, Arabic, CJK).
4. **Preservation Constraint:** MUST accept and preserve historically important materials in non-standard or obsolete formats.
5. **Project Constraint:** Implementation MUST be phased due to budget and staffing limitations.

#### 2.6 Assumptions and Dependencies
- **Assumption:** NLM will provide clear, evolving policies for ingest embargoes and format migration to guide system configuration.
- **Assumption:** Adequate storage growth will be budgeted for long-term preservation.
- **Dependency:** The selected off-site backup facility will provide compatible APIs or protocols for data transfer.
- **Dependency:** Final metadata schema decisions will be made prior to the completion of the Data Management module.

### 3. System Features and Requirements

#### 3.1 Ingest Module
**Description:** This module handles the receipt and validation of digital materials from producers and their preparation for archival storage.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-101** | The system SHALL accept Submission Information Packages (SIPs) via secure FTP (SFTP) and from designated network-mounted physical media drives. | H |
| **FR-102** | The system SHALL generate and communicate a machine-readable receipt to the producer upon SIP acceptance. | M |
| **FR-103** | The system SHALL validate SIPs against pre-defined rules, including checks for virus/malware, file format compliance, and completeness of required metadata. | H |
| **FR-104** | The system SHALL quarantine SIPs that fail validation and notify administrators with a detailed error report. | H |
| **FR-105** | The system SHALL transform a validated SIP into an Archival Information Package (AIP), assigning a persistent unique identifier (e.g., ARK, Handle). | H |
| **FR-106** | The system SHALL support the application of configurable embargo periods to AIPs, restricting access until a specified date. | M |
| **NFR-101** | The ingest process SHALL be scalable to handle batch submissions containing >10,000 files. | M |

#### 3.2 Archival Storage & Preservation Module
**Description:** This module is responsible for the secure, integrity-checked storage of AIPs and the execution of preservation actions.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-201** | The system SHALL store at least three copies of each AIP: one primary and two geographically separate backups. | H |
| **FR-202** | The system SHALL perform regular fixity checks (e.g., checksum verification) on all stored AIPs and alert administrators of any corruption. | H |
| **FR-203** | The system SHALL maintain a complete audit trail (who, what, when) of all preservation actions performed on an AIP. | H |
| **FR-204** | The system SHALL provide a manual and scheduled process for migrating AIPs from at-risk formats to current preservation formats, creating a new versioned AIP while preserving the original. | H |
| **FR-205** | The system SHALL allow *preservation specialists* to define and schedule preservation plans (e.g., "Check TIFF 6.0 files every 6 months"). | M |
| **NFR-201** | The storage system SHALL provide 99.95% availability for retrieval operations. | H |
| **NFR-202** | Data integrity (bit-level preservation) SHALL be guaranteed with a target of zero undetected corruption over a 10-year period. | H |

#### 3.3 Data Management (Metadata) Module
**Description:** This module manages the metadata necessary to describe, administer, and provide access to the archived objects.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-301** | The system SHALL store and manage descriptive (e.g., Dublin Core, MODS), administrative (PREMIS), and structural (METS) metadata for each AIP. | H |
| **FR-302** | The system SHALL provide a web-based interface for *NLM catalogers* to create, read, update, and delete descriptive metadata records. | H |
| **FR-303** | The system SHALL prevent *catalogers* and other non-administrative roles from modifying the actual bitstream of archived objects. | H |
| **FR-304** | The system SHALL support metadata harvesting protocols (e.g., OAI-PMH) to expose metadata to external aggregators. | M |
| **FR-305** | The system SHALL allow metadata to be exported in standard schemas (XML, JSON-LD) for external use. | M |
| **NFR-301** | Metadata search and retrieval operations SHALL return results in under 2 seconds for 95% of queries. | M |

#### 3.4 Access Module
**Description:** This module provides the public and restricted interfaces for discovering and retrieving repository content.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-401** | The system SHALL provide a public web interface for searching and browsing metadata and full-text (where available) of publicly accessible objects. | H |
| **FR-402** | The system SHALL enforce access controls based on user role (*public*, *NIH staff*, *NLM staff*) and object-level permissions (e.g., embargo, license restriction). | H |
| **FR-403** | The system SHALL allow *NIH researchers* to access restricted materials when logged in from an authorized NIH network location. | H |
| **FR-404** | The system SHALL generate Dissemination Information Packages (DIPs) on-demand, which may be derivatives (e.g., PDF-A for viewing) of the preserved AIP. | H |
| **FR-405** | The system SHALL provide stable, persistent URLs (leveraging the AIP's persistent identifier) for all accessible objects. | H |
| **NFR-401** | The public access interface SHALL be usable on modern desktop and mobile browsers. | H |

#### 3.5 Administration Module
**Description:** This module provides the tools for overall system management, configuration, and monitoring.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-501** | The system SHALL provide an interface for *system administrators* to create, modify, and deactivate user accounts and assign roles. | H |
| **FR-502** | The system SHALL maintain a comprehensive, immutable audit log of all significant system events (ingest, access, modification, deletion). | H |
| **FR-503** | The system SHALL provide a dashboard displaying key system health metrics (storage capacity, ingest queue, failed fixity checks). | M |
| **FR-504** | The system SHALL allow administrators to configure ingest workflows, validation rules, and format registries. | M |
| **NFR-501** | All administrative functions SHALL be accessible only via authenticated connections over HTTPS. | H |

### 4. External Interface Requirements

#### 4.1 User Interfaces
- **Public Access UI:** A clean, responsive web interface with search bar, faceted browse, and item detail views.
- **Staff Admin UI:** A secure, role-based web application providing all management, cataloging, and preservation functions.

#### 4.2 Hardware Interfaces
- Must interface with SAN/NAS storage systems via standard protocols (NFS, SMB, or API).
- Must support drivers for reading from common physical media (e.g., external HDDs, DVDs) when connected to designated ingestion workstations.

#### 4.3 Software Interfaces
1. **Authentication Interface:** MUST integrate with NIH Central Authentication Service (e.g., NIH Login) for staff access.
2. **ILS Interface:** SHOULD provide an API for querying and synchronizing bibliographic authority data.
3. **Backup System Interface:** MUST have a secure method (e.g., Rsync over SSH, API) to transfer AIPs to the off-site backup facility.

#### 4.4 Communications Interfaces
- MUST use HTTPS (TLS 1.2 or higher) for all web-based communications.
- MUST use SFTP for producer submissions.
- MUST support SMTP for sending system notifications and alerts.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
- **Search Response Time:** 95% of search queries shall return results within 3 seconds.
- **Object Retrieval Time:** 95% of requested objects (or DIPs) shall be available for download within 5 seconds of request.
- **Concurrent Users:** The system shall support at least 500 concurrent users on the access interface.
- **Ingest Throughput:** The system shall sustain an ingest rate of at least 100 GB per hour.

#### 5.2 Safety and Security Requirements
- The system SHALL comply with all applicable NIST and HHS security controls.
- All PII (if any) in metadata SHALL be encrypted at rest.
- The system SHALL undergo annual security penetration testing.
- Access to administrative functions SHALL require multi-factor authentication (MFA).

#### 5.3 Software Quality Attributes
- **Reliability:** System uptime shall be 99.9% excluding scheduled maintenance.
- **Availability:** The access interface shall be available 24/7 with minimal planned downtime (<4 hours/month).
- **Maintainability:** The system shall be designed with modular components allowing for independent updates.
- **Preservability:** The system's own data (AIPs, metadata) shall be stored in open, well-documented formats to ensure the repository's own long-term sustainability.

### 6. Appendices

#### Appendix A: Glossary
- **AIP (Archival Information Package):** The version of an information package that is preserved within the repository.
- **DIP (Dissemination Information Package):** The version of an information package delivered to a user in response to an access request.
- **Fixity:** The property of a digital file being fixed, or unchanged. Typically verified with checksums.
- **OAIS (Open Archival Information System):** A reference model (ISO 14721) for a system dedicated to preserving and providing access to digital information over the long term.
- **SIP (Submission Information Package):** The version of an information package sent by a producer to the repository for ingest.
