### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the I-15 Reversible Lane Control System (RLCS) Application Software. It serves as a formal agreement between the stakeholders and the development team, providing a comprehensive description of the system to be developed. The intended audience includes project managers, software developers, testers, system integrators, and all stakeholders identified in Section 3.

#### 1.2 Scope
The RLCS Application Software is a new system designed to replace an aging control system. Its primary purpose is to safely and reliably monitor and control field devices (gates, pop-up barriers, Changeable Message Signs (CMS), and lane control lights) to manage reversible lanes on the I-15 corridor during peak traffic periods and special events.

**In-Scope Elements:**
*   Development of the core RLCS application software.
*   Design and implementation of a Graphical User Interface (GUI) for operators and administrators.
*   Integration with new field controllers and their associated I/O cards via provided driver software.
*   Provision of real-time system status data to external traffic management systems via a dedicated external server interface.
*   Implementation of scheduled operations (automatic opening/closing sequences).
*   Configuration management for system parameters, users, and devices.

**Out-of-Scope Elements:**
*   Procurement, installation, and hardware configuration of field devices, controllers, and network infrastructure.
*   Development of underlying Operating Systems (OS), Database Management Systems (DBMS), or commercial reporting engines (COTS solutions will be used).
*   Design or implementation of the physical communications network.
*   Manual field operations that do not require software intervention.
*   Long-term data archival beyond the operational retention periods defined in this document.

### 2. Overall Description

#### 2.1 Product Perspective
The RLCS Application Software is a new, self-contained component within the larger I-15 Reversible Lane infrastructure. It will interface with several external systems:
*   **Field Device Controllers:** To send control commands and receive status/health data.
*   **External Data Server:** To publish lane status and system health data for consumption by ATMS, ValuePricing, and ATIS.
*   **COTS Database:** For storing configuration, event logs, and historical data.
*   **Operator Workstations:** Where the GUI will be hosted.

It is intended to replace the legacy system, offering improved reliability, configurability, and integration capabilities.

#### 2.2 Product Functions (Summary)
The core functions of the RLCS software include:
1.  **Device Monitoring:** Continuously poll and display the real-time status of all field devices.
2.  **Lane Control:** Execute safe, sequenced commands to open or close reversible lanes, either manually (operator-initiated) or automatically (scheduled).
3.  **Alarm Management:** Detect device faults, communication failures, and safety rule violations, and present them to the operator with appropriate priority.
4.  **User Management:** Provide role-based access control for all system functions.
5.  **Configuration Management:** Allow authorized users to configure devices, schedules, user accounts, and system parameters.
6.  **Reporting:** Generate standard and ad-hoc reports on system operations, alarms, and events.
7.  **Data Provisioning:** Securely transmit system state information to designated external systems.

#### 2.4 Constraints
1.  **Operational:** The system must operate 24/7/365 with a maximum recovery time objective (RTO) of 10 minutes following any failure.
2.  **Technical:** The database and reporting layer must be implemented using approved COTS products.
3.  **Safety:** The software must enforce strict safety interlocks to prevent the simultaneous opening of entrances for opposing traffic flows.
4.  **Maintainability:** The system must be designed to accommodate future roadway changes (e.g., adding new gates) through configuration table updates, without requiring source code modifications.
5.  **Security:** All communications between the central system and field controllers must use wired, secure connections; wireless communication is prohibited.

#### 2.5 Assumptions and Dependencies
*   It is assumed that the field hardware (controllers, I/O cards, devices) and their driver software will be provided and will conform to specified interface protocols.
*   The system depends on the stability and availability of the underlying OS, network, and COTS database/reporting software.
*   Final requirements for polling intervals and communication rates are dependent on the selected field controller model's capabilities.

### 3. Stakeholder and User Requirements

#### 3.2 Core Use Cases
1.  **UC-01: Execute Manual Lane Reversal**
    *   **Actor:** Operator
    *   **Description:** Operator initiates a safe, sequenced opening or closing of the reversible lanes outside of scheduled times.
2.  **UC-02: Configure System Security**
    *   **Actor:** System Administrator
    *   **Description:** Admin creates/modifies/deletes user accounts and assigns roles/permissions to control system access.
3.  **UC-03: Perform Remote Maintenance Operation**
    *   **Actor:** Field Maintenance Staff
    *   **Description:** Staff places the system or a device subset into maintenance mode and executes test or repair sequences from a field terminal.
4.  **UC-04: Generate Historical Performance Report**
    *   **Actor:** Management
    *   **Description:** User selects a date range and generates a report detailing system availability, operation success/failure rates, and alarm history.
5.  **UC-05: Monitor Real-Time System Status**
    *   **Actor:** Operator
    *   **Description:** The GUI continuously updates to show device states (e.g., gate position, light color) and triggers visual/audible alarms for any faults.
6.  **UC-06: Provide Lane Status to External System**
    *   **Actor:** External System (e.g., ATMS)
    *   **Description:** The RLCS external server makes current lane status (OPEN/CLOSED/TRANSITION) available via a defined API for polling by authorized external systems.

### 4. System Requirements

#### 4.1 Functional Requirements

##### 4.1.1 User Interface (GUI) Requirements
*   **FR-GUI-01:** The GUI shall provide a schematic map view of the reversible lane corridor, displaying the real-time status of all monitored devices.
*   **FR-GUI-02:** The GUI shall provide a dedicated control panel for operators to initiate **Open Sequence**, **Close Sequence**, **Halt**, and **Override** commands.
*   **FR-GUI-03:** The GUI shall include an alarm banner/panel that lists active alarms, sorted by priority (Critical, Major, Minor), and updates within **2 seconds** of detection.
*   **FR-GUI-04:** The GUI shall require user authentication via login and enforce role-based permissions for all control and configuration functions.

##### 4.1.2 Control and Monitoring Requirements
*   **FR-CONTROL-01:** The system shall execute a pre-defined, sequential set of commands to field devices to transition lanes from "Closed" to "Open" (and vice-versa).
*   **FR-CONTROL-02:** The system shall poll the status of all field devices at a configurable interval (to be determined based on hardware).
*   **FR-CONTROL-03:** The system shall compare device command feedback with expected states and generate an alarm on any mismatch.
*   **FR-SAFETY-01:** The system shall implement a configurable safety interlock rule to physically prevent the "Open" command from being sent to entrances for opposing directions simultaneously.

##### 4.1.3 Scheduling Requirements
*   **FR-SCHED-01:** The system shall allow an administrator to create and store weekly schedules for standard opening and closing operations.
*   **FR-SCHED-02:** The system shall automatically initiate scheduled opening and closing sequences without operator intervention.
*   **FR-SCHED-03:** The system shall support configuration of special event schedules that override the standard weekly schedule.

##### 4.1.4 Reporting Requirements
*   **FR-REP-01:** The system shall log all operator commands, system actions, device state changes, and alarms with a timestamp and user ID.
*   **FR-REP-02:** The system shall generate a standard "Daily Operations Log" report.
*   **FR-REP-03:** The system shall allow users to generate ad-hoc reports based on filterable criteria (date, device, alarm type, etc.) using the COTS reporting tool.

##### 4.1.5 Configuration Management Requirements
*   **FR-CONFIG-01:** The system shall provide forms/tables for administrators to configure: User accounts and roles, Field device parameters, Safety interlock rules, and Communication settings.
*   **FR-CONFIG-02:** All configuration changes shall be logged and require administrator-level authentication.

##### 4.1.6 External Interface Requirements
*   **FR-EXT-01:** The system shall provide lane status (OPEN, CLOSED, IN TRANSITION, FAULT) to an external server module.
*   **FR-EXT-02:** The external server shall make this data available via a secure, documented API (e.g., RESTful web service or message queue).

#### 4.2 Non-Functional Requirements

##### 4.2.1 Performance Requirements
*   **NFR-PERF-01:** The system shall achieve **99.99%** operational availability annually.
*   **NFR-PERF-02:** The GUI shall reflect device status updates and alarm conditions within **2 seconds** of the system detecting the change.
*   **NFR-PERF-03:** The system shall be capable of successfully executing a minimum of **four** scheduled opening/closing sequences per day.

##### 4.2.2 Reliability & Availability Requirements
*   **NFR-REL-01:** The system shall be designed for 24/7 operation.
*   **NFR-REL-02:** In the event of a software failure, the system shall be capable of restarting and resuming normal operations within a **10-minute** recovery time objective.

##### 4.2.3 Security Requirements
*   **NFR-SEC-01:** All user access shall be controlled by username/password authentication.
*   **NFR-SEC-02:** Communications between the central system and field controllers shall be via secure, wired protocols only.
*   **NFR-SEC-03:** User permissions shall follow a role-based access control (RBAC) model.

##### 4.2.4 Maintainability Requirements
*   **NFR-MAIN-01:** The system shall be designed so that changes to roadway geometry or device additions can be managed through configuration updates, without modifying application source code.

#### 4.3 Interface Requirements
*   **IR-01:** **Field Controller Interface:** The software shall communicate via a protocol defined by the selected controller's driver software (e.g., Modbus TCP, DNP3, proprietary API). *[Specific model TBD]*.
*   **IR-02:** **Database Interface:** The application shall connect to a relational database (e.g., Oracle, SQL Server, PostgreSQL) using standard ODBC/JDBC connectors.
*   **IR-03:** **External System API:** The external server shall provide data in a standard format (e.g., JSON, XML) over HTTPS or a dedicated message bus.
