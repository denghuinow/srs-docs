### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Indigent Defense Services Management System (IDSMS). The IDSMS is a component of the broader Integrated Justice Information System (IJIS) initiative. Its purpose is to automate and streamline the process of appointing, managing, and compensating defense counsel for indigent defendants in Tarrant County, ensuring compliance with Texas statutes and improving administrative efficiency.

#### 1.2 Document Conventions
This SRS follows the IEEE 830-1998 standard structure. Requirements are uniquely identified with tags (e.g., `FR-001`, `NFR-010`). "Shall" indicates a mandatory requirement, "should" indicates a desirable but not mandatory feature, and "may" indicates an optional capability.

#### 1.3 Project Scope
The system is scoped to support the end-to-end workflow for indigent defense services from the initial request for counsel through final compensation, as detailed in the "In Scope" and "Out of Scope" sections of the project summary.

#### 1.4 References
*   Texas Code of Criminal Procedure (CCP), Articles 1.051, 15.17, 26.04, 26.05, and related articles.
*   Texas Government Code, Section 71.0351 (Reporting Requirements).
*   Texas Fair Defense Act (FDA).
*   Texas Department of Information Resources (DIR) Standards and Guidelines.
*   Tarrant County IJIS Initiative Charter.

### 2. Overall Description

#### 2.1 Product Perspective
The IDSMS is a new software module that must integrate seamlessly with two existing primary systems:
1.  **Court Case Management System (CCMS):** For defendant, case, and hearing data.
2.  **District Attorney Electronic Case Filing (DA-ECF) System:** For charge and filing information.
The system will serve as a standalone application for workflow management while acting as a data hub between these external systems.

#### 2.2 Product Functions (Summary)
*   Electronically capture and process Requests for Appointed Counsel.
*   Maintain qualified attorney lists with rotation logic for fair appointment.
*   Track key milestones (appointment date, first contact, subsequent activities).
*   Manage the submission, review, and approval workflow for attorney compensation claims.
*   Generate statutory compliance reports for the Texas Fair Defense Act and internal management.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **Magistrate** | Judicial officer; works in detention facility or court. | Inform defendant of rights, determine indigency, submit request for counsel. |
| **Office of Attorney Appointments (OAA) Staff** | County administrative staff. | Process requests, manage attorney lists, make appointments, generate reports. |
| **Defense Attorney** | External contract attorney. | Accept appointments, log contacts/activities, submit compensation claims. |
| **Judge (County/District)** | Judicial officer presiding over cases. | Approve attorney appointments and compensation vouchers. |
| **Court Coordinator** | Court administrative staff. | Schedule hearings; view appointment status. |
| **Auditor** | County financial officer. | Review approved compensation for payment processing. |
| **System Administrator** | IT staff. | Manage user accounts, system configuration, and technical health. |

#### 2.4 Operating Environment
*   **Software:** Must operate in a standard county government IT environment, likely utilizing Windows Server, standard RDBMS (e.g., SQL Server, Oracle), and web-based client access.
*   **Integration:** Must support secure, standards-based (e.g., web services, API) integration with CCMS and DA-ECF systems.

#### 2.5 Design and Implementation Constraints
1.  **Legal Compliance:** The system shall comply with all mandates in the Texas CCP and Government Code related to indigent defense.
2.  **Integration:** The system shall be designed to integrate with the specified external justice systems (CCMS, DA-ECF).
3.  **State Standards:** All electronic transactions and records shall adhere to Texas DIR guidelines.
4.  **Capital Cases:** The system shall support distinct workflows and approval chains for capital felony cases where the death penalty is sought, involving the Local Selection Committee.

#### 2.6 Assumptions and Dependencies
*   Assumes necessary network connectivity and security infrastructure exists at all user locations (courthouses, detention facilities, attorney offices).
*   Dependent on the external CCMS and DA-ECF systems providing stable interfaces for data exchange.
*   Assumes stakeholders will provide definitive requirements for undecided issues prior to the design phase.

### 3. System Features and Requirements

#### 3.1 Feature: Request for Appointed Counsel Management
**Description:** This feature supports the initiation of the indigent defense process, from defendant interaction through the electronic submission of a formal request.

**3.1.1 Functional Requirements**
*   `FR-001` The system shall allow a Magistrate to create a new "Request for Appointed Counsel" record linked to a specific defendant and case (via integration with CCMS/DA-ECF).
*   `FR-002` The system shall capture the Magistrate's determination of indigency (Yes/No) and the reason/waiver if the defendant declines counsel.
*   `FR-003` The system shall electronically route the submitted request to the Office of Attorney Appointments queue immediately upon submission.
*   `FR-004` The system shall timestamp all request submissions and route actions for audit trail purposes.

#### 3.2 Feature: Attorney Appointment Management
**Description:** This feature manages lists of qualified attorneys and the automated, fair selection process for appointing counsel to indigent defendants.

**3.2.1 Functional Requirements**
*   `FR-010` The system shall maintain separate, configurable appointment lists (e.g., felony, misdemeanor, juvenile, capital).
*   `FR-011` For each list, the system shall implement a rotating appointment mechanism that selects the next eligible attorney based on a defined algorithm (e.g., next in line, considering conflicts, availability).
*   `FR-012` The system shall allow OAA staff to manually override the automatic selection with documented reason (e.g., conflict of interest, special expertise).
*   `FR-013` Upon appointment, the system shall automatically generate a formal notice of appointment to the selected Defense Attorney (via email/system notification).
*   `FR-014` The system shall record the date/time of appointment and calculate statutory deadlines for first contact.

#### 3.3 Feature: Defense Activity Tracking
**Description:** This feature allows Defense Attorneys to log mandatory and discretionary activities related to their representation, providing oversight and proof of compliance.

**3.3.1 Functional Requirements**
*   `FR-020` The system shall provide a secure portal for Defense Attorneys to view their appointed cases.
*   `FR-021` The system shall allow a Defense Attorney to log the date, time, and method (e.g., in-person, phone) of first contact with a defendant.
*   `FR-022` The system shall compare the logged first contact date against the statutory deadline and flag any late contacts for reporting.
*   `FR-023` The system shall allow Defense Attorneys to log subsequent case activities (e.g., investigation, motions filed, hearings attended) on a per-case basis.

#### 3.4 Feature: Compensation Claim Processing
**Description:** This feature manages the lifecycle of a defense attorney's request for payment, from submission through judicial approval to financial processing.

**3.4.1 Functional Requirements**
*   `FR-030` The system shall allow a Defense Attorney to submit a compensation claim (voucher) for a closed or ongoing case, detailing hours worked and expenses incurred.
*   `FR-031` The system shall route the submitted claim to the presiding Judge for review and approval based on configurable business rules.
*   `FR-032` The system shall support an approval workflow where the Judge may: Approve, Deny, or Modify the claim amount, with required comments for any denial or modification.
*   `FR-033` Approved claims shall be electronically routed to the County Auditor's office for payment processing.
*   `FR-034` The system shall support an appeals process routed to the Presiding Administrative Judge for claims disputed by the attorney.

#### 3.5 Feature: Compliance and Management Reporting
**Description:** This feature enables the generation of standard and ad-hoc reports to demonstrate compliance with state law and support operational management.

**3.5.1 Functional Requirements**
*   `FR-040` The system shall generate a "Texas Fair Defense Act Compliance Report" as specified in Gov't Code Sec. 71.0351, including metrics on time to appointment and time to first contact.
*   `FR-041` The system shall provide pre-configured operational reports (e.g., appointments by attorney, pending requests, claim status summary).
*   `FR-042` The system shall allow OAA staff to filter and export report data in standard formats (PDF, Excel).

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The system shall provide role-based web interfaces optimized for the tasks of each user class (Magistrate, OAA, Attorney, Judge, etc.).
*   UI design shall follow county accessibility and usability standards (detailed design out of scope for this SRS).

#### 4.2 Hardware Interfaces
*   The system shall support access from standard county-issued desktop computers, laptops, and tablets.

#### 4.3 Software Interfaces
1.  **Court Case Management System (CCMS):** The system shall bi-directionally synchronize defendant demographic data, case numbers, and hearing dates/times.
2.  **District Attorney ECF System:** The system shall receive initial charge information, filing dates, and case dispositions.
3.  **County Financial System:** The system shall export approved compensation claim data for payment issuance.

#### 4.4 Communications Interfaces
*   The system shall use HTTPS/TLS 1.2+ for all web-based communications.
*   System-to-system integration shall use secure, county-approved methods (e.g., RESTful APIs with OAuth, secure file transfer).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   `NFR-001` The system shall support concurrent access by a minimum of 200 users.
*   `NFR-002` All common user transactions (e.g., submitting a request, logging contact) shall complete in less than 3 seconds under normal load.
*   `NFR-003` The system shall be available 99.5% during core business hours (6:00 AM to 8:00 PM CT, Monday-Friday), excluding scheduled maintenance.

#### 5.2 Security Requirements
*   `NFR-010` The system shall implement role-based access control (RBAC) where permissions are strictly aligned with user classes and duties.
*   `NFR-011` All access shall require authentication via county Active Directory or a compatible single sign-on (SSO) solution.
*   `NFR-012` The system shall maintain a complete audit log of all user actions, especially creation, modification, approval, and deletion of records.
*   `NFR-013` Data at rest and in transit shall be encrypted in compliance with county IT security policy.

#### 5.3 Data Quality Requirements
*   `NFR-020` Data imported from external systems (CCMS, DA-ECF) shall be validated for critical field completeness upon receipt.
*   `NFR-021` The system shall enforce referential integrity (e.g., an appointment must link to a valid request, a claim must link to a valid appointment).

### 6. Appendices

#### Appendix A: Glossary
*   **Indigent:** A defendant who is not financially able to employ counsel.
*   **Magistration:** The initial appearance before a magistrate following arrest.
*   **Rotation List:** A list of qualified attorneys maintained for the purpose of sequential appointment.
*   **Capital Case:** A felony case for which the death penalty may be imposed.
