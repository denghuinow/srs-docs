### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional requirements for the Public Health Information Network (PHIN) Outbreak Management System (OMS). The primary purpose is to provide a comprehensive description of the system's capabilities to support public health professionals in investigating, monitoring, managing, analyzing, and reporting on health events, including outbreaks and acts of bioterrorism. This document serves as a foundation for system design, development, testing, and stakeholder agreement.

#### 1.2 Document Conventions
*   **Requirements:** Functional requirements are uniquely identified with the prefix `FR` (e.g., `FR-1.1`).
*   **Keywords:** The terms "MUST," "MUST NOT," "SHALL," "SHALL NOT," "SHOULD," and "MAY" are used as defined in IETF RFC 2119.
*   **References:** References to other documents or system components are denoted in *italics*.

#### 1.3 Intended Audience and Reading Suggestions
*   **Project Sponsors & Public Health Administrators:** Should focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (Success Metrics).
*   **System Architects & Developers:** Should review the entire document, with emphasis on Sections 3 (System Features) and 4 (External Interface Requirements).
*   **Quality Assurance & Testers:** Should use Section 3 (System Features) as the primary basis for test case development.
*   **Project Managers & Business Analysts:** Should use this document to track scope, constraints, and undecided issues.

#### 1.4 Project Scope
The OMS is a configurable software platform designed to collect, link, analyze, visualize, and exchange data related to public health events. Its core mission is to enable the identification, containment, and mitigation of outbreaks through structured data management and analytical tools.

**In-Scope Elements:**
*   A configurable data architecture supporting dynamic definition of entities, fields, and relationships.
*   Core workflows for case investigation, contact tracing, and laboratory data integration.
*   Analytical tools for visualization (maps, charts, epi-curves) and aggregate reporting.
*   Secure, standards-based data exchange with external public health systems.

**Out-of-Scope Elements:**
*   Detailed technical specifications for network transport protocols and message construction.
*   Comprehensive IT operational procedures (backup, disaster recovery, user training).
*   Low-level implementation details for security, privacy, and system deployment.
*   Functional processes for countermeasure administration (e.g., vaccination campaigns) and adverse event tracking.

### 2. Overall Description

#### 2.1 Product Perspective
The OMS is a component within the larger PHIN ecosystem. It must interoperate seamlessly with existing systems such as Laboratory Information Management Systems (LIMS), Surveillance Systems, and Immunization Information Systems (IIS). The system acts as a central hub for outbreak-specific data aggregation and analysis.

#### 2.2 Product Functions (Summary)
1.  **Configurable Data Management:** Adapt data models for specific pathogens or events.
2.  **Case Investigation:** Facilitate data collection via electronic, dynamic questionnaires.
3.  **Contact Tracing:** Identify, manage, and monitor contacts of cases.
4.  **Laboratory Integration:** Manage test requests and results electronically.
5.  **Data Linkage:** Dynamically associate cases, contacts, specimens, lab results, and locations.
6.  **Analysis & Visualization:** Generate maps, timelines, charts, and statistical reports.
7.  **Interoperability:** Securely exchange data with partner systems using standard protocols.
8.  **Multi-Mode Deployment:** Operate in connected, disconnected (field), and web-based modes with synchronization.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Investigator/Epidemiologist** | Public health expert, non-technical, works in field and office. | Efficient data entry, intuitive linking of data, access to analysis tools. |
| **Laboratory Personnel** | Lab technician or manager, uses LIMS. | Clear electronic test requests, simple result reporting interface. |
| **Public Health Administrator** | Managerial role, makes strategic decisions. | High-level dashboards, aggregate reports, export functionality. |
| **System Configurator/IT Support** | Technical staff, understands data modeling. | Tools to modify data dictionaries, create questionnaires, manage deployments. |
| **Response Partner Organization** | External user from another jurisdiction or agency. | Secure, standards-based data exchange portal or interface. |

#### 2.4 Operating Environment
*   **Software:** Must operate on standard web browsers, mobile field devices (e.g., tablets), and in client-server configurations.
*   **Network:** Must function in both high-availability networked environments and intermittently connected/disconnected field scenarios.
*   **Integration:** Must support web services (e.g., RESTful APIs, SOAP) and message-based (e.g., HL7 v2.x, FHIR) integration.

#### 2.5 Design and Implementation Constraints
1.  **Configurability Constraint:** `FR-CONF-1`: The system MUST be configurable for new health events without custom software development or source code changes.
2.  **Standards Constraint:** `FR-STD-1`: All external data exchanges MUST adhere to published vocabulary standards (LOINC, SNOMED CT) and message implementation guides.
3.  **Deployment Constraint:** `FR-DEP-1`: The system MUST support client-server, disconnected (field), and web-based deployment models with robust data synchronization.
4.  **Privacy Constraint:** `FR-PRIV-1`: The system MUST enforce role-based access controls and data encryption to comply with relevant privacy laws (e.g., HIPAA).
5.  **Availability Constraint:** `FR-AVAIL-1`: The system MUST maintain high availability (target 99.5% uptime) to support emergency response operations.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** Trained public health personnel will be the primary users.
*   **Assumption:** Partner organizations will have compatible systems capable of sending/receiving standard data messages.
*   **Dependency:** Successful operation depends on stable network connectivity for core exchange functions (though offline operation is supported for data collection).
*   **Dependency:** System configuration requires personnel with foundational knowledge of public health data concepts.

### 3. System Features

#### 3.1 Feature: Configurable Data Architecture
**Description:** The system shall provide administrative tools to dynamically define and modify the data model to suit specific outbreak investigations.

**Requirements:**
*   `FR-1.1`: The system SHALL allow a Configurator to define new entity types (e.g., "Food Item," "Water Source").
*   `FR-1.2`: The system SHALL allow a Configurator to add, modify, and deactivate data fields within any entity.
*   `FR-1.3`: The system SHALL allow a Configurator to define relationships between entities (e.g., "Person *attended* Event," "Animal *is owned by* Person").
*   `FR-1.4`: The system SHALL allow a Configurator to build electronic questionnaires by selecting from defined data fields, specifying question text, response types (text, date, coded value, etc.), and validation rules.

#### 3.2 Feature: Case Investigation & Management
**Description:** The system shall support the complete workflow of identifying, interviewing, and classifying cases associated with a health event.

**Requirements:**
*   `FR-2.1`: The system SHALL provide an interface for an Investigator to create a new case record.
*   `FR-2.2`: The system SHALL present the Investigator with the appropriate electronic questionnaire based on the health event being investigated.
*   `FR-2.3`: The system SHALL allow an Investigator to classify a case status (e.g., Suspect, Probable, Confirmed, Not a Case, Ruled Out).
*   `FR-2.4`: The system SHALL allow an Investigator to link a case record to other relevant records, including Contacts (`FR-3.1`), Laboratory Specimens/Results (`FR-4.2`), and Locations.

#### 3.3 Feature: Contact Tracing & Exposure Management
**Description:** The system shall facilitate the identification, enrollment, and monitoring of individuals exposed to a case.

**Requirements:**
*   `FR-3.1`: The system SHALL allow an Investigator to create a contact record from a case interview and dynamically link it to the source case(s).
*   `FR-3.2`: The system SHALL support the assignment of contact monitoring protocols (e.g., daily symptom checks for 14 days).
*   `FR-3.3`: The system SHALL provide a dashboard or list view for tracking the status of all contacts (e.g., under monitoring, completed monitoring, lost to follow-up, became case).

#### 3.4 Feature: Laboratory Data Integration
**Description:** The system shall manage the bidirectional electronic flow of laboratory test requests and results.

**Requirements:**
*   `FR-4.1`: The system SHALL allow an Investigator to generate an electronic laboratory test request from within a case record, populating relevant patient and specimen data.
*   `FR-4.2`: The system SHALL automatically receive electronic laboratory results and link them to the originating case and specimen record.
*   `FR-4.3`: The system SHALL display laboratory results to the Investigator with clear indicators of positivity, negativity, reference ranges, and test method.

#### 3.5 Feature: Data Analysis, Visualization, and Reporting
**Description:** The system shall provide tools to analyze aggregated data and create visual and textual reports.

**Requirements:**
*   `FR-5.1`: The system SHALL generate epidemiological curves (epi-curves) based on case onset dates.
*   `FR-5.2`: The system SHALL generate geographical maps plotting case and contact locations (using provided address data, geocoded).
*   `FR-5.3`: The system SHALL allow an Administrator to create and save standard aggregate reports (e.g., daily case counts by jurisdiction, totals of administered countermeasures).
*   `FR-5.4`: The system SHALL allow users to export reports and visualizations in standard formats (e.g., PDF, PNG, CSV).

#### 3.6 Feature: Secure Data Exchange
**Description:** The system shall enable secure, standards-based exchange of outbreak data with external partner systems.

**Requirements:**
*   `FR-6.1`: The system SHALL be able to send and receive HL7 v2.x (or FHIR) messages for case reports, laboratory results, and contact notifications.
*   `FR-6.2`: The system SHALL authenticate and authorize all external system connections.
*   `FR-6.3`: The system SHALL encrypt all data in transit during exchange with external partners.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The web-based interface shall be compatible with the latest two versions of major browsers (Chrome, Firefox, Edge).
*   The field (disconnected) interface shall be designed for use on tablets with touch-screen capabilities.
*   All interfaces shall follow accessibility guidelines (WCAG 2.1 Level AA).

#### 4.2 Hardware Interfaces
*   The system shall support printing reports to network and locally connected printers.
*   The field deployment package shall support synchronization via USB or secure network connection.

#### 4.3 Software Interfaces
1.  **Laboratory System (LIMS):** Interface via HL7 v2.x ORU (Observation Result) and OML (Laboratory Order) messages.
2.  **Surveillance System:** Interface via HL7 v2.x case notification messages.
3.  **Countermeasure Administration System:** Interface via HL7 v2.x messages for administered vaccine/drug data (detailed in separate functional requirements).

#### 4.4 Communications Interfaces
*   HTTP/S for web-based access and API communication.
*   TLS 1.2 or higher for all encrypted communications.
*   Support for asynchronous message queuing (e.g., via an Enterprise Service Bus) for system-to-system exchanges.

### 5. Success Metrics
The following quantitative and qualitative measures will indicate successful implementation:

1.  **Laboratory Integration Efficiency:** >95% of laboratory test requests are sent electronically; >90% of electronic results are automatically linked to the correct case record within 1 hour of receipt.
2.  **Interoperability:** The system successfully sends and receives standard PHIN messages for cases, contacts, and countermeasures with at least two external partner systems in a testing environment.
3.  **Operational Impact:** User satisfaction surveys indicate that Investigators and Administrators agree the system improves the speed and accuracy of outbreak data analysis and reporting, contributing to effective containment efforts.

### 6. Undecided Issues & Open Requirements
The following items require further stakeholder analysis and decision-making before final design:

1.  The specific business rules governing the handoff from contact tracing monitoring to a countermeasure administration workflow.
2.  The definitive data standards and required fields for unique animal identification within the system.
3.  The complete set of operational policies that will be automated or supported by the system for external communication (e.g., automated public alerts, media report generation).
4.  The final technical methodology for grouping observations within exchange messages.
5.  The approved list of file formats for bulk data import (e.g., `.xlsx`, `.csv`, `.geojson`) and export.
