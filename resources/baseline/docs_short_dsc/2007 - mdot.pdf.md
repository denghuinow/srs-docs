## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the VII Data Use Analysis and Processing (DUAP) System. The DUAP system is a research prototype designed to evaluate the utility of Vehicle Infrastructure Integration (VII) data for enhancing transportation safety, mobility, and asset management. This SRS serves as a reference for developers, testers, project managers, and stakeholders, and will be used to guide the design, implementation, and verification of the system.

### 1.2 Document Conventions
*   **Requirements:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Priority:** (H) High, (M) Medium, (L) Low.
*   **Keywords:** `MUST`, `SHALL`, `SHOULD`, `WILL`, `MAY` are used as defined in IETF RFC 2119.

### 1.3 Project Scope
The DUAP system is a functional prototype, not a production operational system. Its core purpose is to collect, consolidate, convert, and communicate VII and complementary transportation data to support operational decision-making demonstrations and application assessments.

**In-Scope:**
*   Collection of probe vehicle, traffic, weather, and road condition data from multiple sources, including the VII Proof of Concept network.
*   Processing of raw data via computational services to derive traffic metrics, detect incidents, and assess road conditions.
*   Dynamic (cached) storage for one week and persistent (archived) long-term storage of all data with geo-references and timestamps.
*   Publication of processed data and alerts in standard formats (e.g., SAE J2354) for consumption by external systems and internal presentation services.
*   Provision of role-based, web-based user interfaces for browsing traffic, incident, weather, and asset condition information.

**Out-of-Scope:**
*   Operational deployment as a 24/7 production system.
*   Collection of probe data from deferred sources (e.g., The Rapid, Ann Arbor Transit, DDOT, car rental fleets).
*   Direct publishing interfaces to specific traffic analysis tools (VISSIM, Synchro, Paramics, SimTraffic).
*   Guarantee of real-time data with zero latency.
*   Resolution of data privacy, ownership, and policy issues (these are external institutional requirements).

## 2. Overall Description

### 2.1 Product Perspective
The DUAP system is a middleware and application layer component that sits between various transportation data sources and end-user applications. It ingests data, processes it, stores it, and makes it available for visualization and integration.

### 2.2 Product Functions (Summary)
1.  **Data Ingestion:** Acquire data from VII probe vehicles, traffic sensors, weather feeds, and road condition reports.
2.  **Data Processing:** Transform and analyze raw data to compute travel times, speeds, detect incidents, and identify road surface issues.
3.  **Data Storage:** Manage a short-term cache for operational data and a long-term archive for historical analysis.
4.  **Data Publication:** Expose processed data, alerts, and metrics via standard APIs and data feeds.
5.  **Data Visualization:** Provide web-based map and reporting interfaces for different stakeholder roles.

### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Transportation Operator** | MDOT staff in TOC; needs timely, accurate situational awareness. | View real-time incidents, traffic flow, and alerts on a map. |
| **System Administrator** | IT staff responsible for system upkeep. | Configure data sources, monitor system health, manage users. |
| **Maintainer / Field Crew** | Roadway maintenance staff; often mobile. | Receive and view prioritized alerts (e.g., potholes) on a map or simple list. |
| **Asset Manager** | Planning staff; uses historical and condition data. | Access reports and summaries on road condition trends for planning. |
| **Researcher** | UMTRI or academic analyst; requires detailed data. | Query and export large sets of archived, geo-referenced raw and processed data. |
| **Traveler (Public)** | General public accessing a public website. | View current travel times, incidents, and construction for trip planning. |
| **Emergency Services** | Police, Fire, EMS dispatch. | Access incident data and traffic impact assessments. |

### 2.4 Operating Environment
*   **Software:** Java-based application server (e.g., Tomcat, JBoss), Oracle 11g/12c database, ESRI or open-source geospatial libraries compatible with MGF.
*   **Hardware:** Must run on MDIT-approved server infrastructure.
*   **Network:** Must operate within secured MDOT network zones, with controlled access to external data sources (VII network, weather APIs).

### 2.5 Design and Implementation Constraints
1.  `NFR-CON-001` (H): The system SHALL be developed using a Java foundation, in compliance with MDIT standards.
2.  `NFR-CON-002` (H): The system SHALL use an Oracle database for persistent storage.
3.  `NFR-CON-003` (H): All spatial data and geo-references SHALL use the Michigan Geographic Framework (MGF).
4.  `NFR-CON-004` (M): The system architecture SHALL be extensible to allow for the addition of new data source adapters and processing algorithms with minimal code changes.

### 2.6 Assumptions and Dependencies
*   **Assumption:** The VII Proof of Concept network and other defined data sources will be available and provide data in a consistent, albeit potentially changing, format.
*   **Assumption:** Data provided will be "near real-time"; applications consuming DUAP data are responsible for checking timestamps for suitability.
*   **Dependency:** Data quality flags from source systems (e.g., vehicle sensor calibration state) will be propagated and must be handled by downstream applications.
*   **Dependency:** System performance and data volume are dependent on external factors (e.g., penetration rate of VII-equipped vehicles).

## 3. System Features and Requirements

### 3.1 Data Ingestion Service
**Description:** This component is responsible for connecting to external data sources, receiving or fetching data, performing initial validation, and placing it into the processing pipeline.

**Requirements:**
*   `FR-ING-001` (H): The system SHALL accept VII probe data messages (BSM, TIM) from the VII Proof of Concept network interface.
*   `FR-ING-002` (H): The system SHALL ingest traffic data (e.g., volume, speed) from specified MDOT sensor sources (e.g., TOC feeds).
*   `FR-ING-003` (H): The system SHALL ingest weather data (e.g., precipitation, temperature) from designated weather service APIs.
*   `FR-ING-004` (M): The system SHALL provide a configuration interface (e.g., admin UI) to add, modify, or disable data source connections. *(Supports User Story #2)*
*   `FR-ING-005` (M): The system SHALL tag all ingested data with a source identifier, receipt timestamp, and original quality flags.

### 3.2 Data Processing & Computation Service
**Description:** This component transforms raw data into derived metrics and detects events of interest.

**Requirements:**
*   `FR-PRC-001` (H): The system SHALL compute link-based traffic metrics (e.g., average speed, travel time) from probe vehicle data.
*   `FR-PRC-002` (H): The system SHALL implement algorithms to automatically detect traffic incidents (e.g., sudden speed drops, congestion patterns) and generate incident alerts.
*   `FR-PRC-003` (H): The system SHALL process probe and other data to assess road surface conditions (e.g., detect potential potholes from vertical acceleration data) and generate condition alerts. *(Supports User Story #3)*
*   `FR-PRC-004` (M): The system SHALL fuse data from multiple sources (e.g., probe + fixed sensors) to improve metric accuracy where possible.
*   `FR-PRC-005` (L): The system MAY compute and store Origin/Destination (O/D) data, pending definition of specific O/D type.

### 3.3 Data Storage Service
**Description:** This component manages both short-term operational cache and long-term historical archive.

**Requirements:**
*   `FR-STR-001` (H): The system SHALL maintain a dynamic cache of processed data (metrics, alerts) for a minimum of seven (7) days for operational access.
*   `FR-STR-002` (H): The system SHALL persist all raw and processed data, with timestamps and MGF geo-references, to an archival database for long-term retention. *(Supports User Story #5)*
*   `FR-STR-003` (M): The archival storage SHALL support efficient time-range and spatial queries by the Researcher user class.

### 3.4 Data Publication & API Service
**Description:** This component provides standardized interfaces for internal and external systems to access DUAP data.

**Requirements:**
*   `FR-PUB-001` (H): The system SHALL publish processed traffic metrics, incident alerts, and road condition alerts in a standards-based format (e.g., compliant with SAE J2354 profiles).
*   `FR-PUB-002` (H): The system SHALL provide a RESTful API or web service for authenticated programmatic access to cached and archived data.
*   `FR-PUB-003` (M): Published data feeds SHALL include clear metadata indicating data latency, timestamp, and quality indicators.

### 3.5 Presentation & User Interface Service
**Description:** This component provides web-based visualizations and tools for different user roles.

**Requirements:**
*   `FR-UI-001` (H): The system SHALL provide a secure, map-based operational view for Transportation Operators to display real-time incidents, traffic speeds, and weather overlays. *(Supports User Story #1)*
*   `FR-UI-002` (H): The system SHALL provide a public, map-based traveler information website displaying current travel times, major incidents, and construction zones. *(Supports User Story #4)*
*   `FR-UI-003` (H): The system SHALL provide an interface for Maintainers to view and prioritize a list or map of generated road condition alerts (e.g., potholes). *(Supports User Story #3)*
*   `FR-UI-004` (M): The system SHALL provide a reporting interface for Asset Managers to generate and browse summaries of road condition trends over user-defined periods. *(Supports User Story #6)*
*   `FR-UI-005` (M): The system SHALL provide a tool for Researchers to query, filter, and export archived raw and processed data in common formats (CSV, Shapefile). *(Supports User Story #5)*
*   `FR-UI-006` (L): The interface MAY allow users to select units of measurement and manage map data layers.

## 4. Non-Functional Requirements

### 4.1 Performance Requirements
*   `NFR-PER-001`: The system SHALL process and make available ingested VII probe data with a latency of no more than 2 minutes from time of receipt 95% of the time ("near real-time").
*   `NFR-PER-002`: The public traveler website SHALL load the initial map view and data within 5 seconds under normal load conditions.
*   `NFR-PER-003`: The operational view SHALL update incident and traffic data on the map at intervals configurable by the user (e.g., every 30-120 seconds).

### 4.2 Safety & Security Requirements
*   `NFR-SEC-001`: The system SHALL implement role-based access control (RBAC) to restrict data and functions based on user classes (Operator, Admin, Researcher, Public).
*   `NFR-SEC-002`: All administrative functions and access to raw/archived data SHALL require authentication.
*   `NFR-SEC-003`: The system SHALL not store personally identifiable information (PII). Data linking probes to specific vehicle IDs SHALL be anonymized or excluded per policy.

### 4.3 Data Quality Requirements
*   `NFR-QUA-001`: The system SHALL propagate data quality flags from source systems through to published outputs and user interfaces.
*   `NFR-QUA-002`: The system SHALL log all data ingestion errors and processing failures for administrative review.

### 4.4 Usability Requirements
*   `NFR-USA-001`: The operational and maintenance interfaces SHALL be designed for use in a Transportation Operations Center (TOC) environment, with clear visual cues for alerts.
*   `NFR-USA-002`: The public traveler interface SHALL be designed for clarity and ease of use by the general public on standard web browsers.

## 5. Appendices

### 5.1 Glossary
*   **VII:** Vehicle Infrastructure Integration.
*   **Probe Data:** Data generated by vehicles, such as position, speed, heading, and vehicle state.
*   **BSM:** Basic Safety Message (SAE J2735).
*   **TIM:** Traveler Information Message (SAE J2735).
*   **MGF:** Michigan Geographic Framework.
*   **TOC:** Transportation Operations Center.
*   **O/D:** Origin/Destination.

### 5.2 Undecided and Deferred Issues
1.  The specific interface formats (protocol, schema) for many external data sources and output consumers are TBD during prototype design.
2.  Privacy policies for handling vehicle probe anonymity are externally governed and may impact certain research functionalities.
3.  Data ownership and use limitations from third-party sources (e.g., weather data) may impose constraints on DUAP's data redistribution.
4.  Implementation details for advanced UI features (unit selection, complex layer management) are deferred as low priority.
