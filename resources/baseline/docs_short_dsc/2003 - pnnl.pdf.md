### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Automated Diagnostics Tool. This tool is designed to automate the detection of faults in Heating, Ventilation, and Air Conditioning (HVAC) subsystems—specifically chillers and cooling towers in its initial version—using pattern-recognition algorithms. The purpose is to provide building operators and service technicians with real-time fault detection and corrective guidance, thereby replacing manual visual analysis and improving operational efficiency.

#### 1.2 Document Conventions
- Requirements are uniquely identified with labels (e.g., `FR-001`, `NFR-010`).
- **Shall** indicates a mandatory requirement.
- **Should** indicates a desirable but not mandatory feature.
- *Italicized text* provides explanatory notes.
- Markdown formatting is used for structure (headers, lists, code blocks).

- **Software Architects & Developers:** To guide system design and implementation.
- **QA Engineers & Testers:** To develop verification plans and test cases.

#### 1.4 Project Scope
The scope of this project is the development of a Windows-based software application that:
- Automates fault detection for chiller and cooling tower subsystems.
- Acquires data in both real-time (from sensors) and batch-mode (from files).
- Presents diagnostic results, configuration, and historical data via a user interface.
- Stores diagnostic results with associated metadata.
- Supports distinct user roles (General User and Administrator).

**Out-of-Scope Items:**
- Manual data visualization or graphical analysis tools for human experts.
- Diagnostic algorithms for boilers or other HVAC subsystems in the initial release.
- Capabilities for users to define custom analytical procedures.
- Deployment on non-Windows operating systems (e.g., Linux, macOS).
- Generation of formal printed reports (only on-screen "print" functionality is included).

### 2. Overall Description

#### 2.1 Product Perspective
This tool is a standalone, installable software application for the Microsoft Windows ecosystem. It interfaces with external data sources (sensor networks via protocols like BACnet, Modbus, or CSV data files) but does not require integration with other enterprise management systems in its initial version. The architecture must be modular to allow for the future addition of diagnostic algorithms for other HVAC subsystems (e.g., boilers, air handlers).

#### 2.2 Product Functions (Summary)
1.  **Data Acquisition:** Interface with live sensor data streams and import historical data from standard file formats.
2.  **Fault Detection Engine:** Execute pattern-recognition algorithms on incoming data to identify predefined faults in chillers and cooling towers.
3.  **Result Management:** Generate, timestamp, annotate with metadata, and persistently store diagnostic findings.
4.  **User Interface:** Provide views for real-time monitoring, historical review, and system configuration.
5.  **User & System Administration:** Manage user authentication, authorization, and application settings.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Building Operator** | Monitors from control room; may have basic computer skills. | Quick, clear status overview; real-time alerts. |
| **Service Technician** | On-site or remote; uses software intermittently for diagnostics. | Ability to start/stop analysis on demand; detailed fault cause and fix guidance. |
| **Energy Service Provider** | Manages multiple client facilities; technically proficient. | Consolidated historical view across assets; trend identification. |
| **Operation Supervisor** | Oversees maintenance workflow; needs documentation. | Ability to generate hard copies of findings for work orders. |
| **Administrator** | IT or lead technician; sets up and maintains the system. | Configure system parameters, user accounts, and data sources. |

#### 2.4 Operating Environment
- **Software:** Microsoft Windows 10/11 (64-bit). .NET Framework or equivalent runtime as determined by architecture.
- **Hardware:** Standard PC with minimum specifications to be determined during design phase. Must support continuous 24/7 operation.
- **External Systems:** Must communicate with building management system (BMS) sensors for real-time data and read from common file formats (e.g., CSV, Excel) for batch processing.

#### 2.5 Design and Implementation Constraints
1.  **C1:** The user interface shall be intuitive and support users with computer expertise ranging from rudimentary to sophisticated.
2.  **C2:** The application shall be compatible only with Microsoft Windows-compatible operating systems.
3.  **C3:** The system shall support both real-time and batch-mode data acquisition, but not process both modes simultaneously for the same equipment instance.
4.  **C4:** The software architecture shall be modular to allow for the future addition of diagnostic algorithms for other HVAC subsystems without major refactoring.
5.  **C5:** The system, when configured for monitoring, shall be capable of operating continuously for indefinite periods without memory leaks or performance degradation.

#### 2.6 User Documentation
The system shall include:
- Integrated, context-sensitive help within the application.
- A comprehensive user manual in PDF format covering installation, configuration, and all user workflows.

#### 2.7 Assumptions and Dependencies
- **Assumption:** Reliable and correctly formatted sensor data or data files will be available to the system.
- **Assumption:** Users will have appropriate Windows operating system permissions to install and run the application.
- **Dependency:** Availability of specific communication protocol libraries (e.g., for BACnet/IP) for real-time data acquisition.

### 3. System Features and Requirements

#### 3.1 Data Acquisition and Management
**Description:** This feature handles the ingestion of data from both real-time sensor streams and historical data files.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-001** | The system shall acquire real-time data from configured sensor points via supported industrial protocols (e.g., BACnet, Modbus). | High |
| **FR-002** | The system shall import historical time-series data from user-selected files in CSV format. | High |
| **FR-003** | The system shall allow the user to select either real-time monitoring **or** batch file processing mode for a given equipment instance. | High |
| **FR-004** | The system shall validate the format and completeness of incoming data and log errors for invalid or missing data points. | Medium |
| **FR-005** | The system shall buffer incoming real-time data to handle temporary communication interruptions. | Medium |

#### 3.2 Fault Detection Engine
**Description:** The core analytical component that processes data to identify faults using pattern-recognition algorithms.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-010** | The system shall execute diagnostic algorithms to detect a specified list of faults for chiller subsystems (e.g., refrigerant undercharge, condenser fouling). | High |
| **FR-011** | The system shall execute diagnostic algorithms to detect a specified list of faults for cooling tower subsystems (e.g., fan malfunction, approach temperature deviation). | High |
| **FR-012** | For each detected fault, the system shall generate a result containing: a unique fault ID, timestamp, equipment identifier, fault description, probable cause, and recommended corrective action. | High |
| **FR-013** | The diagnostic engine shall allow an administrator to adjust algorithm sensitivity thresholds (e.g., tolerance bands) via the configuration interface, without code modification. | High |

#### 3.3 Diagnostic Results Storage and Retrieval
**Description:** Manages the persistence and querying of diagnostic results.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-020** | The system shall store every diagnostic result in a persistent database with all associated metadata (see FR-012). | High |
| **FR-021** | The system shall allow users to browse and retrieve historical diagnostic results filtered by: date/time range, equipment ID, and fault type. | High |
| **FR-022** | The system shall automatically archive or purge old results based on configurable retention policies. | Low |

#### 3.4 User Interface
**Description:** Provides all interactive functions to the various user classes.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-030** | The system shall provide a "Dashboard" view for building operators showing current status (OK, Fault) and a list of active faults for monitored equipment. | High |
| **FR-031** | The system shall provide a "Diagnostic Browser" view for service technicians and energy providers to review historical faults, with filtering capabilities as per FR-021. | High |
| **FR-032** | The system shall provide controls for a service technician to manually start, pause, and stop the diagnostic processing for selected equipment. | High |
| **FR-033** | The system shall provide a "Configuration" interface, accessible only to administrators, for setting data source connections, equipment parameters, and algorithm sensitivity. | High |
| **FR-034** | The system shall allow any user to print the current screen view of diagnostic results or historical data lists to a locally connected printer. | Medium |

#### 3.5 User Management and Security
**Description:** Handles authentication and role-based access control.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-040** | The system shall require user authentication via username and password upon startup. | High |
| **FR-041** | The system shall support at least two distinct roles: "General User" (can view data and results) and "Administrator" (has all General User privileges plus configuration access). | High |
| **FR-042** | The system shall enforce role-based permissions, preventing users from accessing functions outside their privilege level. | High |

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-001** | The system shall process incoming real-time data and execute diagnostics with a latency of less than 60 seconds from data receipt to fault display for 95% of occurrences. |
| **NFR-002** | The user interface shall respond to any user action (click, filter) with a perceptible delay of no more than 2 seconds. |

#### 4.2 Safety Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-010** | The software shall be a monitoring/diagnostic tool only and shall not send direct control commands to HVAC equipment. |
| **NFR-011** | All diagnostic guidance related to safety-critical systems (e.g., boiler shutoffs, pump operations) shall include prominent disclaimers advising consultation of operational manuals and safety procedures. |

#### 4.3 Software Quality Attributes
| ID | Requirement Description |
| :--- | :--- |
| **NFR-020** | **Reliability:** The system shall achieve 99.5% uptime during scheduled monitoring periods, excluding planned maintenance. |
| **NFR-021** | **Usability:** A first-time building operator shall be able to log in and understand the current equipment status on the dashboard without training. |
| **NFR-022** | **Maintainability:** The codebase shall be structured such that adding a new diagnostic algorithm for a new subsystem (e.g., boiler) requires no changes to the core data acquisition or UI modules. |
| **NFR-023** | **Scalability:** The system shall be capable of monitoring at least 50 distinct pieces of HVAC equipment concurrently without performance degradation below specified thresholds. |

### 5. Appendices

#### 5.1 Glossary
- **HVAC:** Heating, Ventilation, and Air Conditioning.
- **BMS:** Building Management System.
- **Approach Temperature:** In a cooling tower, the difference between the cold water temperature leaving the tower and the ambient wet-bulb temperature.
- **Fault:** A detected deviation from normal operating conditions that indicates degraded performance or impending failure.

#### 5.2 Undecided Issues and TBDs
The following items are explicitly noted as unresolved and require further analysis, design, or stakeholder decision:
1.  The specific procedure for deriving cooling tower approach temperature benchmarks from historical performance data.
2.  The detailed development of chiller performance diagnostics (scheduled for "Round 2").
3.  Diagnostic logic for determining boiler shutoffs based on ambient temperature.
4.  Methods for safely handling and diagnosing scenarios involving hot-water pump operation when the boiler is off.
5.  The most computationally efficient algorithm for updating cycle-counting variables within the (future) boiler diagnostic module.
