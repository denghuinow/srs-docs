### **1. Introduction**

#### **1.1 Purpose**
This document defines the functional and non-functional requirements for the Automated ISIN Issuance System for Money Market Instruments (MMIs). The system will enable the JSE, in its capacity as the National Numbering Agent (NNA), to automatically issue, cancel, and manage International Securities Identification Numbers (ISINs) for MMIs in response to electronic requests from STRATE, the Central Securities Depository (CSD). This SRS serves as the primary reference for stakeholders, developers, testers, and project managers throughout the system's lifecycle.

#### **1.2 Document Conventions**
*   **Requirements:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a recommendation. "Will" indicates a statement of fact.
*   **Acronyms:**
    *   **ANNA:** Association of National Numbering Agencies
    *   **BCP:** Business Continuity Plan
    *   **BIC:** Bank Identifier Code
    *   **C&S:** Clearing & Settlement (JSE Division)
    *   **CSD:** Central Securities Depository
    *   **ISIN:** International Securities Identification Number
    *   **JSE:** Johannesburg Stock Exchange
    *   **MMF:** Money Market Forum
    *   **MMI:** Money Market Instrument
    *   **NMPG:** National Market Practice Group
    *   **NNA:** National Numbering Agent
    *   **SLA:** Service Level Agreement
    *   **SWIFT:** Society for Worldwide Interbank Financial Telecommunication

#### **1.3 Project Scope**
This project involves the development of an automated system to process SWIFT MT598 messages from STRATE for the issuance, cancellation, and deregistration of ISINs specifically for Money Market Instruments. The system will feature a front-end administrative interface for monitoring and manual overrides, and will operate under a defined SLA and BCP. It is designed to support the MMF's initiative for electronic dematerialisation and same-day settlement.

**In Scope:**
*   Automated processing of ISIN lifecycle events (Issuance, Cancellation, Deregistration) via SWIFT MT598.
*   Support for four generic MMI categories with defined data fields.
*   A secure web-based front-end for JSE C&S operational monitoring, manual input (BCP), and reporting.
*   Implementation of operational agreements (SLA, BCP) with STRATE.
*   Use of the dedicated ISIN prefix "ZAM" for all MMI ISINs.

**Out of Scope:**
*   Manual ISIN issuance processes for equities or bonds (existing systems remain).
*   Functionality for top-up or reduction of issued amounts.
*   Direct system interaction with MMF participants (all communication is JSE<->STRATE).
*   Modifications to ANNA/ISO ISIN issuance rules.
*   Development of STRATE's internal MMI Engine or settlement systems.

### **2. Overall Description**

#### **2.1 Product Perspective**
The system is a new, standalone application within the JSE's technology ecosystem. It will interface externally with STRATE via the SWIFT network and internally with JSE's operational teams via a web interface. It must coexist with, but remain distinct from, the JSE's existing ISIN issuance systems for equities and bonds.

#### **2.2 Product Functions (Summary)**
1.  **SWIFT Message Processing:** Receive, parse, validate, and process incoming SWIFT MT598 messages from STRATE.
2.  **ISIN Generation & Management:** Automatically generate valid ISINs with the "ZAM" prefix, store instrument details, and manage their status (Active, Cancelled).
3.  **SWIFT Response Generation:** Automatically generate and send appropriate SWIFT MT598 confirmation or rejection messages back to STRATE.
4.  **Administrative Interface:** Provide a secure web portal for JSE C&S staff to monitor requests, perform manual entries (BCP), view reports, and manage reference data.
5.  **Reporting & Logging:** Maintain a complete audit trail of all transactions and generate daily activity reports.

#### **2.3 User Classes and Characteristics**
| User Class | Description | Key Characteristics |
| :--- | :--- | :--- |
| **STRATE (System Actor)** | The external CSD initiating requests. | Interacts solely via SWIFT MT598. Requires real-time, automated responses. |
| **JSE C&S Operator** | Primary internal user. | Monitors system health, performs manual overrides during BCP, generates reports. Requires clear, actionable alerts. |
| **JSE C&S Supervisor** | Internal user for oversight. | Reviews reports, audits logs, manages reference data (e.g., issuer codes). |
| **JSE ASD (System Admin)** | Technical support and maintenance. | Deploys updates, manages system configuration, database administration. |

#### **2.4 Operating Environment**
*   **Software:** Enterprise-grade Java/.NET/Python application server; RDBMS (e.g., Oracle, SQL Server); SWIFT Alliance Access/Alliance Gateway (or equivalent).
*   **Hardware:** High-availability servers located in a secure, resilient data center.
*   **Network:** Secure connection to the SWIFT network (SNL).

#### **2.5 Design and Implementation Constraints**
1.  `CON-001`: The system **shall** comply fully with ANNA and ISO 6166 rules for ISIN issuance.
2.  `CON-002`: All SWIFT message formats and content **shall** be approved by the National Market Practice Group (NMPG) prior to implementation.
3.  `CON-003`: All generated MMI ISINs **shall** use the prefix "ZAM".
4.  `CON-004`: The system **shall** support the four MMI categories and data fields as defined by the MMF.
5.  `CON-005`: A new SWIFT BIC branch code (e.g., `JSEZAJJISN`) **shall** be established for routing messages to this system.
6.  `CON-006`: The system's development and operational cost model **shall** be defined in an SLA with STRATE for cost recovery.

#### **2.6 Assumptions and Dependencies**
*   **Assumption:** STRATE will have the capability to send and receive correctly formatted SWIFT MT598 messages.
*   **Assumption:** The NMPG will approve the proposed SWIFT message structures in a timely manner.
*   **Dependency:** Successful procurement and configuration of the dedicated SWIFT BIC branch code (`ISN`).
*   **Dependency:** Finalization of the SLA and BCP agreements with STRATE before operational go-live.

### **3. System Features and Requirements**

#### **3.1 Feature 1: SWIFT Message Processing**
**Description:** The system shall receive, validate, and act upon SWIFT MT598 messages from STRATE.

**3.1.1 Functional Requirements:**
*   `FR-101`: The system **shall** listen for incoming SWIFT MT598 messages on the designated BIC (`JSEZAJJISN`).
*   `FR-102`: The system **shall** parse the MT598 message, extracting all relevant fields from the structured narrative (Field 79).
*   `FR-103`: The system **shall** validate the message format against the NMPG-approved specification.
*   `FR-104`: The system **shall** validate all business data (e.g., valid issuer code, logical dates, valid MMI type).
*   `FR-105`: For **ISIN Issuance Requests**, the system **shall** trigger the ISIN Generation process (See Feature 2).
*   `FR-106`: For **ISIN Cancellation/Deregistration Requests**, the system **shall** update the status of the specified ISIN to "Cancelled" and log the action.
*   `FR-107`: Upon successful processing, the system **shall** automatically generate and send a positive acknowledgment MT598 message back to STRATE.
*   `FR-108`: Upon failed validation (`FR-103`, `FR-104`), the system **shall** immediately generate and send a rejection MT598 message (MT598-901/902) to STRATE, including a relevant error code and description.
*   `FR-109`: The system **shall** log every incoming and outgoing message with a unique transaction ID, timestamp, and status.

#### **3.2 Feature 2: ISIN Generation & Management**
**Description:** The system shall generate a valid, unique ISIN for a validated MMI issuance request.

**3.2.1 Functional Requirements:**
*   `FR-201`: The system **shall** generate an ISIN using the prefix "ZAM", followed by the 9-character alphanumeric National Security Identifier (NSIN), and a calculated ISO 6166 check digit.
*   `FR-202`: The NSIN **shall** be constructed based on the MMI type and issuer code as defined by MMF rules (e.g., padding with 'X' for "NOTX").
*   `FR-203`: The system **shall** store the full ISIN along with all instrument details (issue date, maturity date, coupon rate, issuer, currency, etc.) in a persistent database.
*   `FR-204`: The system **shall** assign an "Active" status to a newly issued ISIN.
*   `FR-205`: The system **shall** prevent the issuance of a duplicate ISIN for the same instrument key data.

#### **3.3 Feature 3: Administrative Web Interface**
**Description:** The system shall provide a secure web-based interface for JSE C&S operational staff.

**3.3.1 Functional Requirements:**
*   `FR-301`: Authorized users **shall** be able to log in via secure authentication (e.g., LDAP/AD integration).
*   `FR-302`: The interface **shall** provide a real-time dashboard showing system status, recent SWIFT messages, and any pending alerts.
*   `FR-303`: Users **shall** be able to perform a manual ISIN issuance or cancellation by entering all mandatory data fields, as per the BCP procedure (`FR-304`).
*   `FR-304`: All manual entries **shall** be clearly flagged as "Manual (BCP)" in the database and audit logs.
*   `FR-305`: Users **shall** be able to search for ISINs by ISIN code, issuer, date range, or status.
*   `FR-306`: Users **shall** be able to view and print a daily report of all issued and cancelled ISINs.
*   `FR-307`: Supervisors **shall** be able to view and manage a list of valid issuer codes via the interface.

#### **3.4 Feature 4: Reporting & Audit**
**Description:** The system shall maintain a complete audit trail and generate standard reports.

**3.4.1 Functional Requirements:**
*   `FR-401`: The system **shall** maintain an immutable audit log of all system events (SWIFT in/out, manual actions, configuration changes).
*   `FR-402`: The system **shall** generate a daily transaction summary report (PDF/CSV) available via the web interface by 07:00 the following business day.
*   `FR-403`: All reports **shall** include key data: ISIN, Instrument Description, Action (Issue/Cancel), Date/Time, Initiator (STRATE/Manual), and Status.

### **4. External Interface Requirements**

#### **4.1 SWIFT Interface**
*   **Message Format:** SWIFT MT598.
*   **Content:** Structured narrative in Field 79, as per NMPG specification.
*   **BIC:** Incoming messages addressed to `JSEZAJJISN`. Outgoing messages sent from `JSEZAJJISN`.
*   `NFR-401`: The interface **shall** support a minimum volume of 500 messages per day with 99.9% availability during market hours.

#### **4.2 User Interfaces**
*   **Web Interface:** Responsive, intuitive web application compatible with current versions of Chrome, Firefox, and Edge.
*   **Login Screen:** Username/Password with optional 2FA.
*   **Dashboard:** Graphical summary of daily activity, system health indicators, and alert panel.
*   **Manual Entry Forms:** Clear, validated forms replicating SWIFT message data fields.

### **5. Non-Functional Requirements**

#### **5.1 Performance Requirements**
*   `NFR-501`: The system **shall** process a valid ISIN issuance request and return a confirmation SWIFT message within **3 minutes** under normal load, 95% of the time.
*   `NFR-502`: The system **shall** be designed to handle a peak load of **500 ISIN issuance requests** within a one-hour window.
*   `NFR-503`: The web interface **shall** render dashboard data within **5 seconds** of page load.

#### **5.2 Security Requirements**
*   `NFR-504`: All user access to the web interface **shall** be controlled via role-based access control (RBAC).
*   `NFR-505`: All sensitive data at rest (e.g., instrument details) **shall** be encrypted.
*   `NFR-506`: All communication with the web interface **shall** use TLS 1.2 or higher.
*   `NFR-507`: The system **shall** log all authentication attempts (success and failure).

#### **5.3 Reliability, Availability, and Maintainability**
*   `NFR-508`: The core SWIFT processing engine **shall** have an availability of 99.5% during agreed SLA business hours (e.g., 07:00-19:00 SAST).
*   `NFR-509`: The system **shall** support a BCP failover mode, allowing manual operations to continue if the SWIFT link is unavailable.
*   `NFR-510`: The system **shall** be designed to allow for software updates with a maximum of 2 hours of scheduled downtime per quarter.

#### **5.4 Operational Requirements**
*   `NFR-511`: The system **shall** integrate with JSE's central logging/monitoring platform (e.g., Splunk, ELK) for alerts.
*   `NFR-512`: Comprehensive system documentation and runbooks **shall** be provided for JSE C&S and ASD teams.

### **6. Appendices**

#### **6.1 Undecided Issues & Open Items**
The following items require resolution prior to final design or implementation:
1.  **Error Code Standardization:** Final list of error codes and descriptions for SWIFT rejection messages (MT598-901/902) to be agreed between JSE and STRATE.
2.  **Billing Methodology:** Detailed billing logic (per transaction, flat fee, tiered) to be defined within the SLA.
3.  **Issuer Code Management:** Clarification needed on the process and authorization for updating issuer codes via the front-end interface.
4.  **Issued Amount Field:** Specification for the handling of the "issued amount" field if not populated in initial requests (default behavior and future requirements).
5.  **NSIN Padding Rules:** Final standardisation of padding rules for MMI type codes (e.g., "NOTX" -> "NOTXXXXXX") to be confirmed.

#### **6.2 Success Metrics**
*   **Throughput:** System successfully processes 200-500 ISIN requests per day without manual intervention.
*   **Latency:** ISINs are issued and confirmed within the `NFR-501` specification of 3 minutes for valid requests.
*   **Compliance:** 100% of SWIFT message exchanges comply with the NMPG-approved MT598 formats.
*   **Operational Readiness:** Successful execution of BCP drills, demonstrating manual ISIN issuance capability.
