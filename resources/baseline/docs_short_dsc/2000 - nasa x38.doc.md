## **1. Introduction**

### **1.1 Purpose**
This document defines the functional and non-functional requirements for the X-38 Fault Tolerant System Services (FTSS) software. The FTSS provides a foundational software layer that enables reliable, fault-tolerant operation of the quad-redundant Flight Critical Computer (FCC) on NASA's X-38 Crew Return Vehicle. This SRS serves as the authoritative source for developers, testers, and stakeholders.

### **1.2 Document Conventions**
- Requirements are uniquely identified as `FTSS-REQ-XXX`.
- **Shall** indicates a mandatory requirement.
- **Should** indicates a recommendation.
- *Italicized text* provides explanatory notes.
- `Monospaced text` denotes code, APIs, or specific technical terms.

### **1.3 Project Scope**
The FTSS software acts as an abstraction layer between flight application software and the underlying hardware (Radstone PowerPC) and operating system (VxWorks 5.4). Its primary purpose is to manage redundancy, ensure deterministic scheduling, facilitate robust inter-processor communication, and provide fault management to achieve the required level of system reliability.

**In-Scope Elements:**
*   System initialization and synchronization across redundant channels.
*   Deterministic, rate-based task scheduling.
*   Fault detection, isolation, and recovery (FDIR) mechanisms.
*   Synchronous and low-latency immediate communication services.
*   Mission and separation elapsed time management.

**Out-of-Scope Elements:**
*   Initialization of non-Radstone VME slave boards.
*   Application-specific fault response logic.
*   Low-level hardware network diagnostics.
*   Year 2000 compliance considerations.
*   Training, documentation, and logistics support.

## **2. Overall Description**

### **2.1 Product Perspective**
The FTSS is a middleware component within the X-38 FCC architecture. It resides below the flight application software and above the VxWorks Real-Time Operating System (RTOS) and hardware abstraction layer. The FCC consists of multiple, identical Flight Control Processors (FCPs). The FTSS enables these redundant channels to operate as a synchronized, fault-tolerant unit.

### **2.2 Product Functions (Summary)**
1.  **Initialization & Synchronization:** Coordinate cold/warm start of all FCPs to a known, synchronized state.
2.  **Deterministic Scheduling:** Execute application tasks within defined 50Hz, 10Hz, and 1Hz rate groups.
3.  **Fault Tolerance:** Continuously monitor system health, detect faults, isolate faulty components, and manage redundancy to maintain functionality.
4.  **Inter-Processor Communication:** Provide reliable message-passing services between tasks on the same or different FCPs.
5.  **Time Management:** Maintain and distribute synchronized Mission Elapsed Time (MET) and Separation Elapsed Time (SET).
6.  **Mode Management:** Support vehicle operational mode changes (e.g., pre-flight, ascent, re-entry).
7.  **Health & Status Reporting:** Provide telemetry data on system state and fault events.

### **2.3 User Characteristics**
*   **Flight Application Developers:** Skilled in C/C++, understand real-time concepts, and use the FTSS API to build tasks.
*   **System Integrators:** Understand the FCC hardware and software stack for integration and testing.
*   **Flight Operations Personnel:** Use system telemetry for monitoring; not direct software users.

### **2.4 Major Constraints**
1.  **FTSS-REQ-CON-001:** The software **shall** execute on the Radstone PowerPC 604R processor.
2.  **FTSS-REQ-CON-002:** The software **shall** use the VxWorks 5.4 operating system.
3.  **FTSS-REQ-CON-003:** The FTSS image **shall** not exceed 3 MB of ROM space.
4.  **FTSS-REQ-CON-004:** The FTSS runtime memory usage **shall** not exceed 9 MB of DRAM.
5.  **FTSS-REQ-CON-005:** All FCP software modules (FTSS + applications) **shall** be bit-for-bit identical.
6.  **FTSS-REQ-CON-006:** The system **shall** maintain full functionality with any 3 of the 5 Flight Control Receivers (FCRs) active.

### **2.5 Assumptions and Dependencies**
*   The underlying VxWorks 5.4 and board support package (BSP) function correctly.
*   The hardware meets its specified reliability and performance characteristics.
*   Application developers adhere to the prescribed FTSS API and design patterns.

## **3. System Features and Requirements**

### **3.1 Initialization and Synchronization Services**
**FTSS-REQ-INIT-010:** The FTSS **shall** perform a coordinated initialization sequence across all operational FCPs upon power-on or reset.
**FTSS-REQ-INIT-011:** The FTSS **shall** achieve full system synchronization within 90 seconds (1.5 minutes) from power-on.
**FTSS-REQ-INIT-012:** The FTSS **shall** provide an API for applications to register initialization functions that are called in a defined order during system start-up.
**FTSS-REQ-INIT-013:** The FTSS **shall** support a "warm start" capability, re-integrating a previously failed channel without a full system reboot.

### **3.2 Scheduling Services**
**FTSS-REQ-SCHED-020:** The FTSS **shall** provide a deterministic, time-triggered scheduler.
**FTSS-REQ-SCHED-021:** The scheduler **shall** support three primary rate groups: 50Hz (20ms period), 10Hz (100ms period), and 1Hz (1000ms period).
**FTSS-REQ-SCHED-022:** The FTSS **shall** provide an API (`ftssTaskCreate`) for applications to create tasks assigned to a specific rate group.
**FTSS-REQ-SCHED-023:** The scheduler **shall** guarantee that tasks within a rate group complete execution before the next period begins.
**FTSS-REQ-SCHED-024:** The FTSS **shall** manage task prioritization within and between rate groups.

### **3.3 Fault Detection, Isolation, and Recovery (FDIR)**
**FTSS-REQ-FDIR-030:** The FTSS **shall** continuously perform Built-In Tests (BIT) on hardware and software components.
**FTSS-REQ-FDIR-031:** The FTSS **shall** detect and isolate a faulty FCP or FCR within 60 milliseconds of fault detection.
**FTSS-REQ-FDIR-032:** The system **shall** be designed to tolerate any two concurrent faults throughout all mission phases.
**FTSS-REQ-FDIR-033:** The FTSS **shall** implement redundancy management to mask faults, allowing the system to operate correctly with failed components.
**FTSS-REQ-FDIR-034:** The FTSS **shall** provide memory alignment services to synchronize the state of a recovered channel before its reintegration.
**FTSS-REQ-FDIR-035:** The FTSS **shall** log all fault events and make them available via telemetry.

### **3.4 Communication Services**
**FTSS-REQ-COMM-040:** The FTSS **shall** provide synchronous, guaranteed message-passing services between tasks on any FCP.
**FTSS-REQ-COMM-041:** The FTSS **shall** provide immediate (asynchronous, low-latency) message-passing services, specifically optimized for sensor data flow from ICPs to FCPs.
**FTSS-REQ-COMM-042:** Communication services **shall** handle message routing, buffering, and acknowledgment transparently to the application.
**FTSS-REQ-COMM-043:** The FTSS **shall** ensure message consistency across redundant channels.

### **3.5 Time Services**
**FTSS-REQ-TIME-050:** The FTSS **shall** maintain a synchronized Mission Elapsed Time (MET) across all FCPs.
**FTSS-REQ-TIME-051:** The FTSS **shall** maintain a Separation Elapsed Time (SET), which may be reset independently of MET.
**FTSS-REQ-TIME-052:** The FTSS **shall** provide APIs (`ftssGetMET`, `ftssGetSET`) for applications to retrieve the current time.
**FTSS-REQ-TIME-053:** Time synchronization **shall** be resilient to single faults.

### **3.6 Mode Management**
**FTSS-REQ-MODE-060:** The FTSS **shall** support discrete vehicle operational modes (e.g., Standby, Ascent, Guided, Parachute).
**FTSS-REQ-MODE-061:** The FTSS **shall** provide an API for the commanding of mode changes.
**FTSS-REQ-MODE-062:** The FTSS **shall** manage the enabling/disabling of specific rate groups or tasks based on the active vehicle mode.

### **3.7 Telemetry and Health Reporting**
**FTSS-REQ-TLM-070:** The FTSS **shall** generate a health and status packet containing fault logs, synchronization status, and processor utilization.
**FTSS-REQ-TLM-071:** The format and transmission rate of the telemetry packet **shall** be configurable.

## **4. External Interface Requirements**

### **4.1 Application Programming Interface (API)**
The FTSS shall expose a well-defined C-language API for use by flight applications. Key API families include:
*   `ftssTaskCreate()`, `ftssRateGroupEnter()`
*   `ftssMsgSend()`, `ftssMsgReceive()`, `ftssMsgSendImmediate()`
*   `ftssGetMET()`, `ftssGetSET()`
*   `ftssSetMode()`, `ftssGetMode()`
*   `ftssRegisterInitFunction()`
*   `ftssGetFaultStatus()`

### **4.2 Hardware Interfaces**
*   VME Bus for inter-processor communication.
*   Discrete I/O lines for synchronization and fault signaling.
*   Timers and clocks for scheduling and timekeeping.

## **5. Non-Functional Requirements**

### **5.1 Performance Requirements**
*   **FTSS-REQ-PERF-101:** System initialization time ≤ 90 seconds.
*   **FTSS-REQ-PERF-102:** Fault isolation latency ≤ 60 ms.
*   **FTSS-REQ-PERF-103:** Inter-processor message latency for immediate messages ≤ 2 ms.
*   **FTSS-REQ-PERF-104:** Scheduler jitter within a rate group ≤ 100 microseconds.

### **5.2 Safety and Reliability Requirements**
*   **FTSS-REQ-REL-110:** The system shall demonstrate a probability of loss of function < 1x10⁻⁹ per mission (derived from two-fault tolerance requirement).
*   **FTSS-REQ-REL-111:** The FTSS shall not contain a single point of failure.

### **5.3 Software Quality Attributes**
*   **Determinism:** All services must have bounded and predictable execution times.
*   **Verifiability:** The design shall support rigorous testing and analysis, including resilience to Byzantine faults.
*   **Maintainability:** The code shall be modular, well-commented, and traceable to these requirements.

## **6. Other Requirements**

### **6.1 Success Metrics**
*   Achieve full two-fault tolerance as validated through fault injection testing.
*   Meet all performance deadlines (initialization, fault isolation) in integrated system testing.
*   Operate successfully with any combination of 3 active FCRs.

### **6.2 Undecided and TBD Issues**
1.  The specific methodology for memory protection (hardware MMU vs. software partitioning).
2.  The final, approved list of VxWorks API calls that application tasks are permitted to use.
3.  The detailed structure and downlink format of the telemetry data packet.
4.  The detailed requirements for power sequencing of the FCC.
5.  The final validation test plan for proving Byzantine fault resilience.
