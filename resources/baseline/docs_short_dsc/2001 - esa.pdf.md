### 1. Introduction

#### 1.1 Purpose
This document defines the software requirements for the APAF (ASPERA-3 Processing and Archiving Facility) Ground Data System. The APAF system is responsible for processing telemetry from the ASPERA-3 instrument and Mars Express spacecraft into scientifically usable datasets, supporting the science team during operations, and ensuring timely delivery of validated data to NASA's Planetary Data System (PDS). This SRS serves as a contract between the project stakeholders and the development team, providing a complete description of the system's functionality, constraints, and interfaces.

#### 1.2 Document Conventions
- Requirements are uniquely identified with labels (e.g., `FR-001`, `NFR-010`).
- **Shall** indicates a mandatory requirement.
- **Should** indicates a desirable but not mandatory feature.
- *Italicized text* provides explanatory notes or clarifications.
- Markdown formatting is used for structure and readability.

#### 1.3 Project Scope
The APAF system is a ground-based data processing and archiving system for the ASPERA-3 instrument aboard the Mars Express orbiter.

**In-Scope:**
- Automated acquisition of ASPERA-3 telemetry and Mars Express orbit/attitude data from ESOC.
- Processing of raw telemetry into calibrated IDFS (Instrument Data File System) datasets.
- Long-term archival of raw telemetry and processed IDFS data on local SwRI storage.
- Provision of web-based interfaces for data display, including public views and password-protected science analysis tools.
- Distribution of IDFS data and necessary processing software to designated ASPERA-3 Co-Investigators.
- Generation and submission of PDS-compliant data bundles to NASA PDS.

**Out-of-Scope:**
- System operation in multiple distinct states or modes.
- Requirements dependent on specific hardware installations.
- Safety-critical requirements (the system poses no physical hazard).
- Explicit software quality factor metrics (e.g., specific reliability percentages).
- Formal training programs for developers or end-users.

### 2. Overall Description

#### 2.1 Product Perspective
The APAF system is a standalone component within the broader ASPERA-3 ground segment. It interfaces externally with ESA's ESOC (for telemetry) and NASA PDS (for data delivery). Internally, it consists of processing pipelines, a database, archive storage, and web servers.

#### 2.2 Product Functions
1.  **Data Acquisition:** Automatically pull telemetry data from ESOC via the NISN.
2.  **Data Processing:** Convert raw telemetry and ancillary orbit/attitude data into calibrated IDFS science datasets.
3.  **Data Archiving:** Securely store all input telemetry and output IDFS data in a managed local archive.
4.  **Data Distribution:** Deliver IDFS datasets and software to Co-Investigators via agreed-upon mechanisms.
5.  **Data Display & Analysis:** Provide web-based tools for visualizing instrument performance and scientific data.
6.  **Data Archival:** Prepare and submit validated, calibrated data to NASA PDS.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **System Operator** | Technical staff at SwRI. Manages daily system health. | Automated, reliable data flow with clear error logging and notification. |
| **Scientist / Co-I** | ASPERA-3 team member. Expert in data analysis. | Rapid access to calibrated IDFS data via web and downloadable formats. |
| **Data Manager / Archivist** | Responsible for data integrity and PDS delivery. | Robust archival, data validation tools, and PDS packaging workflows. |
| **Public Outreach Coordinator** | Manages public engagement. | Reliable, automatically updated public web displays of instrument status. |
| **Project Management (SwRI/IRF)** | Oversees project execution and science return. | System meets schedule milestones (24-hour delivery, 6-month PDS delivery). |

#### 2.4 Operating Environment
- **Software:** UNIX-based operating system (e.g., Linux). Specific distributions to be determined.
- **Hardware:** Standard production servers and storage arrays located at SwRI.
- **Networks:** Must connect to the NASA Integrated Services Network (NISN) for telemetry acquisition and to the public internet for web services and PDS delivery.

#### 2.5 Design and Implementation Constraints
1.  `CON-001`: The system **shall** interface with the ESOC Data Disposition System exclusively via the NISN for telemetry acquisition.
2.  `CON-002`: Core data processing algorithms **shall** be deliverable to IRF to support Mars Express launch and independent operations.
3.  `CON-003`: The system **shall** be designed to operate on UNIX-based development and production computers.
4.  `CON-004`: The software distribution mechanism for Co-Investigators **shall** be finalized and documented six months prior to the Mars Express launch.
5.  `CON-005`: All software and data products **shall** comply with NASA Discovery Program requirements.

#### 2.6 Assumptions and Dependencies
- Assumes daily availability of telemetry data streams from ESOC.
- Assumes stable definitions of the IDFS format and PDS standards for the mission lifetime.
- Dependent on timely delivery of Mars Express orbit and attitude data (SPICE kernels) for processing.
- Success is dependent on finalizing Co-I distribution details six months before launch (`Undecided Issue`).

### 3. System Features and Requirements

#### 3.1 Feature: Automated Data Acquisition
**Description:** The system shall automatically acquire daily telemetry dumps from ESOC.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-001` | The system **shall** automatically initiate a connection to the ESOC Data Disposition System via NISN on a scheduled daily basis. | High |
| `FR-002` | The system **shall** retrieve all new ASPERA-3 instrument telemetry packets available since the last successful acquisition. | High |
| `FR-003` | The system **shall** retrieve all new Mars Express orbit and attitude (SPICE kernel) data available since the last acquisition. | High |
| `FR-004` | The system **shall** verify the integrity (e.g., via checksum) of all retrieved data files. | High |
| `FR-005` | The system **shall** log the outcome (success, partial failure, complete failure) of each acquisition attempt and generate an alert for operator intervention upon failure. | Medium |

#### 3.2 Feature: Telemetry Processing Pipeline
**Description:** The system shall process raw telemetry into calibrated IDFS datasets.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-010` | The system **shall** process acquired raw ASPERA-3 telemetry packets using mission-provided algorithms to generate Level 1 IDFS datasets (time-ordered, unpacked data). | High |
| `FR-011` | The system **shall** apply calibration algorithms using the latest calibration files to convert Level 1 data into Level 2 IDFS datasets (calibrated physical units). | High |
| `FR-012` | The system **shall** merge processed ASPERA-3 data with corresponding Mars Express orbit and attitude data to create Level 3 IDFS datasets (geo-located science data). | High |
| `FR-013` | The system **shall** be capable of reprocessing data for any specified time range upon operator command, using contemporary or user-specified calibration files. | Medium |

#### 3.3 Feature: Data Archival and Management
**Description:** The system shall provide secure, organized storage for all data.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-020` | The system **shall** store all acquired raw telemetry files in a permanent, organized archive with a searchable database of contents. | High |
| `FR-021` | The system **shall** store all generated IDFS datasets (Levels 1, 2, 3) in a permanent, organized archive with a searchable database of contents. | High |
| `FR-022` | The database **shall** allow querying of data by time range, data level, and processing version. | Medium |

#### 3.4 Feature: Web-Based Data Display and Analysis
**Description:** The system shall provide both public and secure web interfaces for data access.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-030` | The system **shall** provide a public website displaying near-real-time ASPERA-3 instrument health, status, and summary science plots. | High |
| `FR-031` | The system **shall** provide a password-protected science portal for Co-Investigators. | High |
| `FR-032` | The science portal **shall** provide interactive tools to search, browse, plot, and subset all archived IDFS data. | High |
| `FR-033` | The science portal **shall** allow authorized users to download IDFS data files for local analysis. | High |

#### 3.5 Feature: Data Distribution to Co-Investigators
**Description:** The system shall distribute data and software to the science team.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-040` | The system **shall** distribute the latest version of the IDFS processing software to Co-Investigators via a mechanism to be finalized (e.g., secure FTP, physical media). | High |
| `FR-041` | The system **shall** distribute new IDFS datasets to Co-Investigators within **24 hours** of successful acquisition and processing of error-free telemetry. | High |
| *Note* | The specific datasets per Co-I and the exact distribution mechanism are `Undecided Issues` to be resolved pre-launch. | |

#### 3.6 Feature: PDS Archival Preparation and Delivery
**Description:** The system shall prepare and deliver validated data to NASA PDS.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| `FR-050` | The system **shall** provide tools to generate PDS-compliant labels for calibrated (Level 2/3) ASPERA-3 data bundles. | High |
| `FR-051` | The system **shall** validate the completeness and format of PDS bundles before submission. | High |
| `FR-052` | The system **shall** submit the validated, calibrated ASPERA-3 data to NASA PDS **no later than six (6) months** after data acquisition on Mars Express. | High |

### 4. External Interface Requirements

#### 4.1 User Interfaces
- **Primary UI:** Web browser (Chrome, Firefox, Safari) for all data display and analysis functions (`FR-030`, `FR-032`).
- **Operator UI:** Command-line interface and/or scriptable API for system control, monitoring, and reprocessing (`FR-013`).

#### 4.2 Hardware Interfaces
- Must communicate with ESOC servers via the NISN network interface (`CON-001`).
- Must interface with local RAID or SAN storage systems for the data archive (`FR-020`, `FR-021`).

#### 4.3 Software Interfaces
- **ESOC DDS:** Interface via standard protocols (e.g., SFTP) over NISN to acquire telemetry files.
- **PDS:** Interface via standard upload protocols (e.g., HTTPS) to deliver data bundles.
- **SPICE Toolkit:** Must incorporate NASA NAIF SPICE toolkit for reading orbit/attitude kernels.

#### 4.4 Communications Interfaces
- All external communications (NISN, PDS, Web) **shall** use secure, encrypted protocols (e.g., SSH, TLS/SSL).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
| ID | Requirement Description |
| :--- | :--- |
| `NFR-001` | The system **shall** complete processing of one day's worth of ASPERA-3 telemetry into Level 3 IDFS datasets within 4 hours of data acquisition, under nominal load. |
| `NFR-002` | Web page loads for data displays **shall** render in under 3 seconds for 95% of requests. |
| `NFR-003` | The system **shall** support concurrent access by at least 20 Co-Investigator users on the science portal. |

#### 5.2 Safety Requirements
*No safety requirements are applicable as the system poses no hazard to personnel or equipment.*

#### 5.3 Security Requirements
| ID | Requirement Description |
| :--- | :--- |
| `NFR-010` | Access to the science analysis portal and data download functions **shall** require individual user authentication (username/password). |
| `NFR-011` | User roles **shall** be defined (e.g., Public, Co-Investigator, Operator) with appropriate access controls. |
| `NFR-012` | All system logs **shall** be protected from unauthorized modification or deletion. |

#### 5.4 Software Quality Attributes
- **Reliability:** The system shall be available for processing >95% of scheduled acquisition windows.
- **Maintainability:** The code shall be modular, well-documented, and under version control to facilitate updates.
- **Portability:** The core processing software shall be portable across common UNIX environments (`CON-003`).

### 6. Other Requirements

#### 6.1 Success Metrics
1.  **Operational Success:** ASPERA-3 IDFS data is delivered to Co-Investigators within 24 hours of error-free telemetry acquisition.
2.  **Programmatic Success:** Calibrated ASPERA-3 data is submitted to NASA PDS no later than six months after acquisition.
3.  **User Success:** Web-based displays are continuously operational for both public viewing and science team analysis.

#### 6.2 Undecided Issues and TBDs
1.  The specific distribution mechanisms (e.g., automated FTP push, pull-based web service) and the exact dataset subscriptions for each Co-Investigator will be finalized and documented six months prior to the Mars Express launch.
2.  Any requirements that emerge as installation-dependent will be captured in the Operations Procedures Document, not in this SRS.
3.  The precedence and criticality of requirements in this document may be reviewed and adjusted during the design phase.
