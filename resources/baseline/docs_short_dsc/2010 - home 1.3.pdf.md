### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the DigitalHome (DH) prototype system. It serves as a comprehensive agreement between stakeholders—including HomeOwner Inc. management, the development team, and end-users—and provides the foundation for system design, implementation, and testing. The primary audience includes the development team, project managers, and quality assurance personnel.

#### 1.2 Document Conventions
This document follows standard SRS conventions. Requirements are uniquely identified with tags (e.g., `FR-001`, `NFR-010`). Key terms are **bolded** upon first use. All requirements are written in a clear, testable, and unambiguous manner.

#### 1.3 Project Scope
The DH project is a prototype "Smart House" system designed to demonstrate core capabilities for remote home management via a web interface. The system will operate in a **simulated environment** to validate concepts for future commercial development.

**In-Scope Features:**
*   Environmental Control: Remote monitoring and control of temperature and humidity via simulated thermostats and humidistats.
*   Security Management: Monitoring of contact sensors and activation of alarm systems.
*   Appliance Management: Remote control of power switches for lights and small appliances.
*   Planning & Reporting: Monthly scheduling and generation of reports for environmental and security data.

**Explicitly Out-of-Scope:**
*   Physical hardware deployment in a real home.
*   Integration of entertainment systems, irrigation, pool controls, or video surveillance.
*   Non-web-based user interfaces (e.g., hardware control panels).
*   Advanced biometric security features.

### 2. Overall Description

#### 2.1 Product Perspective
The DH system is a standalone, web-based application that simulates a network of smart home devices. It will interface with a simulated environment engine that models real-world physical properties (e.g., temperature decay, device state changes). The system architecture is envisioned as a three-tier application: a web-based user interface, a central application server with business logic, and a simulation/data persistence layer.

#### 2.2 Product Functions (Summary)
1.  Provide a secure web portal for user authentication and role-based access.
2.  Display real-time status of all simulated devices (thermostats, humidistats, contact sensors, power switches).
3.  Allow remote manual control of individual or grouped devices.
4.  Enable creation and management of schedules for environmental parameters.
5.  Detect security breaches based on contact sensor states and activate simulated alarms (light/sound).
6.  Generate and export monthly reports detailing historical data and event logs.
7.  Provide configuration interfaces for system parameters and user management (for privileged roles).

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **General User** | Home resident; basic technical proficiency; primary consumer of monitoring/control features. | Monitor home status, adjust temperature/humidity, control appliances, view reports. |
| **Master User** | Trusted resident (e.g., head of household); elevated privileges. | All General User functions, plus adding/managing General User accounts. |
| **DH Technician** | Trained professional; expert knowledge of DH system. | Initial system configuration, setting system-wide parameters, performing maintenance tasks. |
| **HomeOwner Inc. Management** | Executive/managerial role; non-technical evaluator. | Review system reports and prototype demonstrations to assess commercial viability. |
| **System Administrator** | (Implied) IT support role. | Maintain server infrastructure, application deployment, and database backups. |

#### 2.4 Operating Environment
*   **Software:** Modern web browsers (Chrome, Firefox, Safari, Edge latest stable versions). Backend server to run on a mainstream OS (e.g., Linux, Windows Server).
*   **Hardware:** Standard server hardware for hosting the application and database. Client access via desktop, tablet, or smartphone.
*   **Simulation:** A dedicated simulation environment must be developed to model device behaviors and physical constraints without requiring actual hardware.

#### 2.5 Design and Implementation Constraints
1.  **Resource Constraint:** Development team size is fixed at five engineers.
2.  **Schedule Constraint:** A fully functional prototype must be delivered within twelve months.
3.  **Technical Constraint:** Must use cost-minimized, widely available technologies and standards (e.g., HTTP/HTTPS, RESTful APIs, relational databases).
4.  **Process Constraint:** Mandatory adherence to HomeOwner Inc. SDLC and documentation standards.
5.  **Methodology Constraint:** Object-oriented analysis and design using UML 2.0 is preferred.
6.  **Change Control Constraint:** All requirement changes require formal approval from the DigitalHomeOwner Division Director.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** Users will have reliable internet access to use the web interface.
*   **Assumption:** The simulated environment will accurately reflect the latency and failure modes of real wireless devices.
*   **Dependency:** Project success is dependent on the timely provision of HomeOwner Inc. development standards and review cycles.
*   **Dependency:** Final selection of specific wireless protocols for simulation may impact the simulation layer design.

### 3. System Features and Requirements

#### 3.1 Web-Based User Interface
**Description:** A responsive, secure web portal accessible from major browsers.
*   `FR-001`: The system shall present a login screen requiring username and password.
*   `FR-002`: The system shall display a main dashboard showing summary status (e.g., current temperature, security status, active alerts).
*   `FR-003`: The system shall provide distinct navigation sections for Environment, Security, Appliances, Schedules, and Reports.
*   `FR-004`: The interface shall adapt its layout for optimal viewing on screens from 320px to 1920px wide.

#### 3.2 Environmental Control (HVAC Simulation)
**Description:** Manage simulated heating/cooling and humidity systems.
*   `FR-010`: The system shall support the simulation of up to **eight (8) thermostats**.
*   `FR-011`: The system shall allow a user to view the current temperature reading (in °F) for each thermostat.
*   `FR-012`: The system shall allow a user to set a target temperature for any thermostat within the range of **60°F to 80°F**.
*   `FR-013`: The system shall support the simulation of up to **eight (8) humidistats**.
*   `FR-014`: The system shall allow a user to view the current humidity reading (in %RH) for each humidistat.
*   `FR-015`: The system shall allow a user to set a target humidity level for any humidistat within the range of **30% to 60%**.
*   `FR-016`: The system shall provide a scheduling interface to program different temperature/humidity setpoints for specific days and times.

#### 3.3 Security System Management
**Description:** Monitor security sensors and manage alarm states.
*   `FR-020`: The system shall support the simulation of up to **fifty (50) contact sensors** (e.g., for doors/windows).
*   `FR-021`: The system shall display the real-time state (Open/Closed) of each contact sensor.
*   `FR-022`: The system shall allow a Master User or DH Technician to arm and disarm the security system.
*   `FR-023`: When armed, if a contact sensor transitions to "Open," the system shall trigger a security breach event.
*   `FR-024`: Upon a security breach, the system shall activate a simulated alarm (light and sound indicator in the UI) and log the event.
*   `FR-025`: The system shall send an alert notification (e.g., on-screen alert, email - TBD) to authenticated users upon a security breach.

#### 3.4 Appliance Management
**Description:** Control simulated power switches for lights and appliances.
*   `FR-030`: The system shall support the simulation of up to **one hundred (100) power switches**.
*   `FR-031`: The system shall display the current state (On/Off) for each power switch.
*   `FR-032`: The system shall allow a user to toggle the state (On/Off) of any individual power switch.
*   `FR-033`: The system shall allow a user to create and control groups of power switches (e.g., "All Downstairs Lights").

#### 3.5 User and System Configuration
**Description:** Administrative functions for account and system settings.
*   `FR-040`: The system shall support role-based access control (General User, Master User, DH Technician).
*   `FR-041`: A Master User shall be able to create, modify, enable, and disable accounts for General Users.
*   `FR-042`: A DH Technician shall be able to configure system-wide parameters (e.g., system name, default temperature units, alert notification settings).
*   `FR-043`: A DH Technician shall be able to perform simulated "device discovery" to add new thermostats, humidistats, sensors, or switches to the system.

#### 3.6 Reporting and Planning
**Description:** Generate historical data reports and manage monthly schedules.
*   `FR-050`: The system shall allow a user to generate a monthly report for environmental data (temperature/humidity over time, setpoint changes).
*   `FR-051`: The system shall allow a user to generate a monthly security report (breach events, system arm/disarm logs).
*   `FR-052`: Reports shall be exportable in a standard format (e.g., PDF, CSV).
*   `FR-053`: The system shall provide a calendar view for planning and reviewing monthly schedules for environmental controls.

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements
*   `NFR-001` (Reliability): The system shall achieve a mean time between failures (MTBF) of **at least 10,000 hours** in the simulated production environment.
*   `NFR-002` (Responsiveness): 95% of user interface interactions (e.g., button clicks, page navigation) shall result in a visual update within **2 seconds** under simulated normal load.
*   `NFR-003` (Capacity): The system shall support concurrent sessions for at least **10 users** without significant performance degradation.

#### 4.2 Safety & Security Requirements
*   `NFR-010`: All communication between the client browser and the application server shall be encrypted using **Transport Layer Security (TLS) 1.2 or higher**.
*   `NFR-011`: User passwords shall be stored using a strong, salted, one-way hashing algorithm.
*   `NFR-012`: The system shall implement session management to prevent unauthorized access.
*   `NFR-013`: The system shall log all authentication attempts (success and failure).

#### 4.3 Software Quality Attributes
*   `NFR-020` (Usability): A new General User shall be able to perform basic tasks (log in, adjust temperature, turn on a light) without training, based on intuitive UI design.
*   `NFR-021` (Maintainability): The codebase shall be developed with object-oriented principles, documented per internal standards, and have a cyclomatic complexity of less than 15 for all critical methods.
*   `NFR-022` (Simulation Fidelity): The simulation environment shall model real-world constraints, such as the time required for a room to change temperature after a thermostat adjustment.
