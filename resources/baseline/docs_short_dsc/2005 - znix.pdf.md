# Software Requirements Specification (SRS)
## Project ZNIX Framework
**Version:** 1.0  
**Date:** October 26, 2023  
**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for Project ZNIX, an object-based, application-independent information management framework. It is intended for use by the project's stakeholders, including developers, system administrators, and testers, to ensure a common understanding of the system to be delivered.

#### 1.2 Document Conventions
- Requirements are uniquely identified with tags (e.g., `FR-001`, `NFR-010`).
- **Bold** text is used for key terms and emphasis.
- `Code blocks` are used for API examples and technical notes.

#### 1.3 Project Scope
Project ZNIX aims to shift the paradigm of information management from application-centric to semantics-centric. It provides a unified framework for storing, retrieving, and manipulating user information from disparate sources (e.g., email, documents, contacts) based on its meaning and user-defined relationships, rather than its originating application.

**In-Scope Items:**
*   Centralized, object-based data store for user information.
*   Hierarchical, customizable browser interface for information navigation.
*   Archiving functionality to removable media with persistent indicators.
*   Public API for third-party application integration.
*   Single-user operation on Windows 2000/XP.

**Out-of-Scope Items:**
*   Multi-user, networked, or client-server operation.
*   Support for non-standard hardware interfaces.
*   Implementation of network communication protocols.
*   Creation of comprehensive user manuals.
*   Proprietary licensing; components will use LGPL/GPL.

### 2. Overall Description

#### 2.1 Product Perspective
ZNIX is a new, standalone desktop application for Windows. It interfaces with specified third-party applications (e.g., Microsoft Outlook, web browsers) to import data but operates independently as the central management hub for the user's information ecosystem.

#### 2.2 Product Functions (Summary)
1.  **Data Aggregation:** Automatically capture and centralize information from configured email clients and web documents.
2.  **Semantic Storage:** Store information as Entities with rich metadata and user-definable attributes.
3.  **Relationship Management:** Allow users to create and manage logical relationships between Entities (e.g., linking a document to a person).
4.  **Hierarchical Navigation:** Provide an Explorer-like browser for users to create and navigate custom hierarchical views of their information.
5.  **Archival:** Enable offloading of Entities to removable media while maintaining "stub" records within the primary store.
6.  **Programmatic Access:** Expose a public, .NET-like API for developers to build ZNIX-aware client applications.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Goals |
| :--- | :--- | :--- |
| **End User** | Home users, managers, executives, researchers. Basic IT proficiency. Familiar with Windows Explorer. | Organize and retrieve information intuitively without learning new software paradigms. |
| **Developer** | Third-party software developer. Proficient in .NET (C#/VB.NET). | Integrate application data with ZNIX using a clean, well-documented API. |
| **System Administrator** | IT staff responsible for deployment. Manages older corporate hardware. | Deploy and run the Framework reliably on low-resource Windows systems. |
| **Open Source Contributor** | Technical user interested in modifying or extending the Framework. | Understand the codebase and licensing to contribute effectively. |

#### 2.4 Operating Environment
*   **Hardware:** Intel Pentium III or compatible 1 GHz CPU, 256 MB RAM, 2 GB free disk space minimum.
*   **Software:** Microsoft Windows 2000 Professional or Windows XP. .NET Framework 1.1 or later.
*   **Operation Mode:** Single-user, non-networked.

#### 2.5 Design and Implementation Constraints
1.  **Performance:** The Framework Shell must not exceed 40 MB of RAM during standard operation.
2.  **Reliability:** The system shall achieve an MTBF greater than 3 months.
3.  **Security:** The Framework must include safeguards against corruption of information by user error and execution of malicious scripts via the API or imported data.
4.  **Compatibility:** The design assumes stable interfaces from third-party applications (e.g., MAPI for email). Changes to these external interfaces are a compatibility risk.

#### 2.6 Assumptions and Dependencies
*   The user has administrative rights to install software on the target Windows system.
*   Required third-party applications (for data capture) are installed and functional.
*   The .NET Framework runtime is present on the target system.

### 3. System Features and Requirements

#### 3.1 Feature: Hierarchical Information Browser
**Description:** Provides a Windows Explorer-like interface for users to view, navigate, and manage their information in a customizable hierarchy.

| ID | Requirement | Priority |
| :--- | :--- | :--- |
| **FR-001** | The system shall present a tree-view pane allowing the user to create, rename, reorder, and delete logical folders/categories. | High |
| **FR-002** | The system shall present a details-view pane showing the Entities contained within the selected tree node. | High |
| **FR-003** | The details view shall display Entity properties (name, type, modified date, user-defined attributes). | High |
| **FR-004** | The user shall be able to drag and drop Entities between nodes in the tree view to reorganize the hierarchy. | Medium |
| **FR-005** | The browser's state (window position, expanded tree nodes) shall be persisted between sessions. | Low |

#### 3.2 Feature: Entity and Relationship Management
**Description:** Core functionality for creating, manipulating, and linking data objects (Entities).

| ID | Requirement | Priority |
| :--- | :--- | :--- |
| **FR-010** | The system shall allow the user to create a new Entity of a defined type (e.g., Note, Document Reference, Person). | High |
| **FR-011** | The user shall be able to edit the properties and metadata of any Entity. | High |
| **FR-012** | The system shall allow a user to create a bidirectional relationship between any two Entities (e.g., "Document X is *authored by* Person Y"). | High |
| **FR-013** | The browser shall provide a means to view all relationships associated with a selected Entity. | Medium |
| **FR-014** | The user shall be able to search/filter Entities based on properties, metadata, and relationship types. | Medium |

#### 3.3 Feature: Data Capture and Import
**Description:** Automatically acquires information from external sources to populate the ZNIX data store.

| ID | Requirement | Priority |
| :--- | :--- | :--- |
| **FR-020** | The system shall be configurable to monitor a specified MAPI email profile and import emails (header, body, attachments) as Entities. | High |
| **FR-021** | The system shall provide a browser plugin or system hook to allow a user to manually capture the current web page as an Entity. | High |
| **FR-022** | The import process shall preserve the original source metadata (e.g., sender, received date, URL). | High |

#### 3.4 Feature: Archival to Removable Media
**Description:** Manages the offloading of less-frequently accessed Entities to external storage.

| ID | Requirement | Priority |
| :--- | :--- | :--- |
| **FR-030** | The user shall be able to select one or more Entities and initiate an "Archive" command. | High |
| **FR-031** | The system shall copy the selected Entities' data to a user-specified removable drive (CD-ROM, USB). | High |
| **FR-032** | Upon successful archival, the system shall replace the original Entity in the store with a residual "stub" Entity clearly indicating its archived status and location. | High |
| **FR-033** | The user shall be able to "Restore" an archived Entity by selecting its stub, provided the corresponding media is accessible. | Medium |

#### 3.5 Feature: Public Developer API
**Description:** A .NET-style API for programmatic interaction with the ZNIX Framework.

| ID | Requirement | Priority |
| :--- | :--- | :--- |
| **FR-040** | The API shall provide classes for core operations: `ZNIX.Entity.Create()`, `.Modify()`, `.Delete()`, `.Query()`. | High |
| **FR-041** | The API shall provide classes for managing relationships: `ZNIX.Relationship.Create()`, `.Enumerate()`. | High |
| **FR-042** | The API design shall be semantically and structurally analogous to the `System.IO` namespace for developer familiarity. | High |
| **FR-043** | Comprehensive API documentation in XML (IntelliSense) and CHM format shall be provided. | Medium |

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Framework Shell:** Primary GUI. Must adhere to Windows UI guidelines (Win32/.NET Forms). The decision on integration with Windows Explorer vs. standalone application is pending (see Undecided Issues).
*   **Context Menus:** Right-click menus in the browser shall provide relevant actions for folders and Entities.
*   **Setup Wizard:** A simple, linear installation wizard.

#### 4.2 Hardware Interfaces
*   Must support reading/writing to standard USB mass storage devices and CD/DVD-R drives via Windows OS services.

#### 4.3 Software Interfaces
*   **Microsoft MAPI:** For importing email from clients like Microsoft Outlook.
*   **Windows File System:** For accessing local documents and managing archival media.
*   **.NET Framework 1.1 Runtime:** The ZNIX API and core components will be built upon this.

#### 4.4 Communications Interfaces
*   None required for this version. (Explicitly out of scope).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
| ID | Requirement |
| :--- | :--- |
| **NFR-001** | The Framework Shell process shall maintain a memory footprint ≤ 40 MB under typical load. |
| **NFR-002** | The browser shall populate the tree view and display the contents of a selected node within 2 seconds on the minimum hardware specification. |
| **NFR-003** | API calls for simple Entity queries shall return results in < 1 second. |

#### 5.2 Safety & Security Requirements
| ID | Requirement |
| :--- | :--- |
| **NFR-010** | The system shall validate and sanitize all input from the public API to prevent script injection or buffer overflow attacks. |
| **NFR-011** | Critical operations (e.g., bulk delete, schema modification) shall require user confirmation. |
| **NFR-012** | The data store shall maintain integrity through transactions; a failed operation shall not leave the store in a corrupted state. |

#### 5.3 Software Quality Attributes
| ID | Requirement |
| :--- | :--- |
| **NFR-020** | **Reliability:** The system shall have an MTBF > 3 months. |
| **NFR-021** | **Usability:** A user familiar with Windows Explorer shall be able to perform basic navigation, creation, and archival tasks without reference to documentation. |
| **NFR-022** | **Maintainability:** The codebase shall be modular, with clear separation between the data layer, API layer, and UI layer. |
| **NFR-023** | **Portability:** The system is constrained to Windows 2000/XP. No portability to other OSs is required. |

### 6. Other Requirements

#### 6.1 Licensing and Legal
*   All ZNIX Framework components shall be released under the GNU Lesser General Public License (LGPL) version 2.1 or later, to allow linking by proprietary third-party applications.
*   Associated tools, plugins, or standalone utilities may be released under the GNU General Public License (GPL).
*   All license texts must be included in the distribution.

#### 6.2 Documentation
*   **API Documentation:** Comprehensive .chm help file with examples.
*   **Installation Guide:** Brief document covering setup and configuration.
*   **"Getting Started" Guide:** A short (≤10 page) primer introducing the core concepts of Entities and Relationships.

### 7. Appendices

#### Appendix A: Undecided Issues / Open Questions
1.  **Browser Integration:** Will the ZNIX browser be a standalone application or a namespace extension integrated into Windows Explorer? *Decision required before UI design finalization.*
2.  **Automation Level:** What heuristics, if any, will be used to automatically categorize imported data (e.g., placing all emails from "Client A" into a specific folder)? *Decision impacts FR-020/021.*
3.  **Coding Conventions:** Specific .NET coding standards (naming, structure, commenting) must be formally documented for the development team.
4.  **Client Process Standards:** Should ZNIX-aware applications adhere to specific behavioral standards (e.g., for error handling, Entity locking)? *Decision impacts FR-040.*
5.  **Help Documentation:** The precise scope and depth of end-user help content needs to be defined to balance intuitiveness with support.
