## 1. Introduction

### 1.1 Purpose
This document defines the software requirements for the Gaia Object Generator (GOG). GOG is a high-level simulator designed to generate statistically representative catalog, main database, and final mission data products for the Gaia astrometry mission. It serves as a critical tool for algorithm development, pipeline testing, and mission analysis within the Data Processing and Analysis Consortium (DPAC), enabling rapid generation of large datasets without the computational overhead of detailed instrument simulation.

### 1.2 Document Conventions
*   **Requirements:** Functional requirements are labeled `FR-[Feature#].[Requirement#]`. Non-functional requirements are labeled `NFR-[Section#].[Requirement#]`.
*   **Priority:** (H) High, (M) Medium, (L) Low.
*   **Keywords:** `MUST`, `SHALL`, `SHOULD`, `MAY` as per IETF RFC 2119.
*   **Acronyms:** Defined upon first use and listed in the glossary.

### 1.3 Intended Audience and Reading Suggestions
*   **CU2 Developers & System Architects:** Should focus on Sections 2, 3, 4.3, and 5 for design and implementation guidance.
*   **DPAC End Users (Researchers, Calibration Teams):** Should focus on Sections 2.2, 2.3, 3, and 4.1 to understand capabilities and usage.
*   **Quality Assurance & Validation Teams:** Should focus on Sections 3, 5.1, and 5.4 for test planning and validation criteria.
*   **Project Management:** Should focus on Sections 1.4, 2.5, 2.7, and 5 for scope, constraints, and success metrics.

### 1.4 Project Scope
GOG is a software component of the broader Gaia Simulator project. It generates simulated observational data (astrometry, photometry, radial velocity) for celestial sources by applying spacecraft and error models to an input source list.

**In-Scope:**
*   Generation of source data from a statistical Universe Model or a user-provided object catalog.
*   Simulation of per-transit (epoch) observations.
*   Aggregation of epoch data into end-of-mission combined data.
*   Application of user-selectable instrumental and data reduction noise/error effects.
*   Production of output files compliant with the Universe Model and Main Database Interface Control Documents (ICDs).

**Out-of-Scope:**
*   Simulation of raw pixel data or detailed instrumental point-spread functions (PSFs). This is the domain of GIBIS.
*   Modeling of source confusion, crowding, or overlapping effects in the current release (processes sources independently).
*   Real-time processing or direct integration with operational mission databases.
*   Development of fundamental error models (GOG consumes models provided by other DPAC units).
*   Native support for Microsoft Windows operating systems.

## 2. Overall Description

### 2.1 Product Perspective
GOG is a standalone application within the Gaia Simulator ecosystem. It relies on the `GaiaSimu` and `Gaia Tools` libraries for core astronomical and spacecraft modeling functions. GOG sits at a higher level of abstraction than GIBIS, focusing on catalog-level data rather than raw detector signals. Its primary outputs feed into downstream DPAC data processing pipelines for testing and validation.

### 2.2 Product Functions
1.  **Configuration Parsing:** Read simulation parameters from a structured input file.
2.  **Source Ingestion:** Read source lists from the Universe Model or a user-defined catalog.
3.  **Observation Simulation:** For each source, generate a timeline of observations (transits) based on the Gaia scanning law.
4.  **Noise/Error Application:** Apply configurable noise and systematic error models to simulated ideal observations.
5.  **Data Aggregation:** Combine all epoch observations for a source to generate final astrometric, photometric, and radial velocity parameters.
6.  **Format-Compliant Output:** Write results to files adhering to defined ICD structures for the Main Database and final catalog.

### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **CU2 Developer** | Expert in Java, Gaia simulation architecture. Maintains and extends GOG. | Clean APIs, modular design, integration with Gaia libraries. |
| **Researcher / Scientist** | Domain expert in astronomy/astrophysics. Uses GOG for analysis testing. | Flexible configuration, region-specific generation, interpretable output. |
| **Calibration Team Member** | Expert in instrument performance and error budgets. Validates calibration algorithms. | Selective application of specific error models, reproducible results. |
| **Data Processor / System Operator** | Manages batch processing and data pipelines. | Command-line operation, batch scripting support, logging, predictable resource use. |
| **QA / Validation Engineer** | Ensures software correctness and output fidelity. | Deterministic execution, validation datasets, detailed error reporting. |

### 2.4 Operating Environment
*   **Software:** Java Runtime Environment (JRE) 8 or later. Dependent on GaiaSimu and Gaia Tools libraries.
*   **Operating Systems:** Linux, Unix variants (e.g., Solaris), macOS. Windows is explicitly **not** supported.
*   **Execution Modes:** Standalone (single JVM), batch job on a single server, or as an array job within an HPC/grid environment (e.g., Sun Grid Engine, SLURM).

### 2.5 Design and Implementation Constraints
1.  **Integration Constraint:** MUST be implemented in Java and utilize the designated `GaiaSimu` and `Gaia Tools` libraries.
2.  **Output Format Constraint:** Output data structures and file formats SHALL strictly comply with the Universe Model and Main Database ICDs.
3.  **Platform Constraint:** MUST be developed and tested for Linux/Unix/macOS. The same input configuration MUST produce bitwise-identical output across all supported platforms.
4.  **Deployment Constraint:** SHALL be packaged as a standalone, executable JAR file.
5.  **Architectural Constraint:** SHALL support both single-threaded execution and parallel execution via independent processes (e.g., for cluster environments).

### 2.6 User Documentation
A user manual SHALL be provided covering:
*   Installation of the GOG JAR and its dependencies.
*   Syntax and schema of the XML configuration file.
*   Description of available error model flags and parameters.
*   Command-line options and examples.
*   Interpretation of output file formats.

### 2.7 Assumptions and Dependencies
*   **Assumption:** Error models will be provided as stable libraries or data files by other DPAC Coordination Units.
*   **Assumption:** The final Main Database ICD will be stable prior to the final release of GOG v1.0.
*   **Dependency:** GOG is dependent on the continued development and maintenance of the `GaiaSimu` and `Gaia Tools` libraries.
*   **Dependency:** Access to the Universe Model data is required for default source generation.

## 3. System Features and Requirements

### 3.1 Feature 1: Configuration Management
**Description:** GOG shall be configured via an external XML file, allowing users to define all simulation parameters without code modification.

**Requirements:**
*   `FR-1.1 (H):` The system SHALL read its complete configuration from a user-specified XML file at startup.
*   `FR-1.2 (H):` The configuration file SHALL define parameters including: input source type (Universe Model or custom catalog), sky region filters, error model selections, output file paths, and verbosity of logging.
*   `FR-1.3 (M):` The system SHALL validate the configuration file against a defined XML Schema (XSD) and provide clear, actionable error messages for invalid entries.

### 3.2 Feature 2: Source Data Generation
**Description:** GOG shall ingest a list of celestial sources, either generated on-the-fly from the statistical Universe Model or read from a user-provided catalog file.

**Requirements:**
*   `FR-2.1 (H):` The system SHALL be able to generate a list of sources with basic parameters (position, magnitude, color, radial velocity) from the integrated Universe Model for a user-defined region of the sky.
*   `FR-2.2 (H):` The system SHALL be able to read source lists from an ASCII or FITS catalog file conforming to a specified format documented in the user manual.
*   `FR-2.3 (M):` The system SHALL allow filtering of sources based on celestial coordinates (e.g., rectangular or conical regions) and magnitude limits.

### 3.3 Feature 3: Epoch Data Simulation
**Description:** For each source, GOG shall simulate individual transit observations (epochs) over the nominal Gaia mission lifetime, applying the spacecraft scanning law.

**Requirements:**
*   `FR-3.1 (H):` For each source, the system SHALL calculate the times of all Gaia transits based on the nominal scanning law.
*   `FR-3.2 (H):` For each transit epoch, the system SHALL generate ideal (noiseless) observables: astrometry (AL and AC field angles), photometry (in Gaia bandpasses), and radial velocity.
*   `FR-3.3 (H):` The system SHALL output per-epoch data to an intermediate structured file format.

### 3.4 Feature 4: Combined Data Simulation
**Description:** GOG shall aggregate all epoch data for a source to produce final, mission-averaged parameters—simulating the result of the Gaia data processing pipeline.

**Requirements:**
*   `FR-4.1 (H):` The system SHALL combine all simulated epoch astrometry to compute the five standard astrometric parameters (position, parallax, proper motion) and their covariance matrix.
*   `FR-4.2 (H):` The system SHALL combine epoch photometry to produce mean magnitudes and variability indicators.
*   `FR-4.3 (H):` The system SHALL combine epoch radial velocity measurements to produce a mean radial velocity and associated error.

### 3.5 Feature 5: Noise Effect Application
**Description:** Users shall be able to select which instrumental and calibration error models are applied to the ideal simulated data.

**Requirements:**
*   `FR-5.1 (H):` The system SHALL apply a configurable, additive Gaussian noise model to astrometric, photometric, and radial velocity measurements based on source magnitude and color.
*   `FR-5.2 (H):` The system SHALL provide configuration flags to enable or disable specific systematic error models (e.g., basic angle variations, attitude errors, calibration errors).
*   `FR-5.3 (M):` When an error model is enabled, the system SHALL apply its effects at the appropriate stage of the simulation (e.g., attitude error per epoch, calibration error per CCD).
*   `FR-5.4 (H):` The random number generators used for noise addition SHALL be seedable via the configuration file to ensure reproducibility.

### 3.6 Feature 6: Data Output and Formatting
**Description:** GOG shall produce final output files that are compliant with DPAC interface standards and ready for ingestion by downstream systems.

**Requirements:**
*   `FR-6.1 (H):` The system SHALL output the combined source data (final catalog) in a format compliant with the Main Database (MDB) ICD.
*   `FR-6.2 (M):` The system SHALL output the epoch data in a format compliant with the Universe Model ICD or a specified interim format.
*   `FR-6.3 (M):` Output files SHALL be in FITS format, as mandated by the referenced ICDs.
*   `FR-6.4 (L):` The system MAY provide an option for human-readable ASCII output for debugging purposes.

### 3.7 Feature 7: Execution and Control
**Description:** GOG shall be controllable via the command line, suitable for interactive use and batch processing.

**Requirements:**
*   `FR-7.1 (H):` The system SHALL be invoked from the command line, accepting the path to the configuration XML file as its primary argument.
*   `FR-7.2 (H):` The system SHALL support a command-line flag to specify an output directory, overriding the configuration file.
*   `FR-7.3 (M):` The system SHALL log progress, warnings, and errors to both the console and a timestamped log file.
*   `FR-7.4 (H):` Given identical configuration and random seed, the system MUST produce bitwise-identical output files across multiple runs on the same hardware/OS.

## 4. External Interface Requirements

### 4.1 User Interfaces
*   **Primary Interface:** Command-line terminal.
*   **Input:** XML configuration file path (required argument). Optional command-line flags for output directory and verbosity.
*   **Output:** Status and error messages to `stdout`/`stderr`. Primary data output to FITS files.

### 4.2 Hardware Interfaces
None specified. Performance is subject to the constraints in Section 5.1.

### 4.3 Software Interfaces
*   **GaiaSimu Library:** Used for core spacecraft modeling, scanning law, and astronomical calculations. Interface via Java API.
*   **Gaia Tools Library:** Used for common utilities, file I/O, and geometry functions. Interface via Java API.
*   **Error Model Libraries/Data:** Provided as Java classes or parameter files. GOG will call defined interfaces or read specified file formats.
*   **Universe Model Data:** Accessed via a defined database or file system interface (TBD based on GaiaSimu).

### 4.4 Communications Interfaces
None required for standalone operation. In a grid environment, communication is managed by the batch scheduling system (e.g., environment variables, shared file system).

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   `NFR-5.1.1:` The software SHALL process a single source (from input to final combined data) in an average of ≤ 2 CPU seconds on a reference 2.5 GHz Intel Xeon processor.
*   `NFR-5.1.2:` The software SHALL be capable of generating simulated data for a volume equivalent to **20% of the expected final Gaia catalog** (approx. 200 million sources) within a reasonable batch processing timeframe, assuming proportional scaling of compute resources.
*   `NFR-5.1.3:` Memory usage per process SHALL be predictable and shall not exceed 2 GB for processing catalogs of up to 1 million sources at a time.

### 5.2 Safety Requirements
Not applicable (scientific software with no physical safety implications).

### 5.3 Security Requirements
*   `NFR-5.3.1:` The software SHALL not require elevated system privileges to run.
*   `NFR-5.3.2:` The software SHALL only read from and write to user-specified directories.

### 5.4 Software Quality Attributes
*   **Reliability:** The application shall not crash due to malformed input data; it shall log an error and skip the problematic source or terminate gracefully.
*   **Maintainability:** The code shall be modular, with clear separation between the simulation engine, error model interface, and I/O components. Code shall adhere to Java standard conventions.
*   **Portability:** The Java source code and build process shall ensure the executable JAR runs identically on all supported platforms (Linux, Unix, macOS).
*   **Verifiability:** All functional requirements shall be verifiable through automated unit and integration tests. A test suite covering core functions shall be delivered with the code.

### 5.5 Business Rules
*   The software is developed for and owned by the Gaia DPAC. Its primary use is for internal mission preparation and analysis.
*   Output data shall be labeled as "Simulated Data - Not for Science Publication" in file headers.

## 6. Other Requirements
*   **Licensing:** The software shall be released under the GNU General Public License v3 (GPLv3) or a similar open-source license approved by the DPAC.
*   **Code Management:** Source code shall be maintained in a designated DPAC version control system (e.g., Git).

## 7. Appendix A: Glossary
*   **AC:** Across-Scan direction.
*   **AL:** Along-Scan direction.
*   **CU:** Coordination Unit (of DPAC).
*   **DPAC:** Data Processing and Analysis Consortium.
*   **Epoch:** A single transit observation of a source.
*   **FITS:** Flexible Image Transport System (standard data format).
*   **GIBIS:** Gaia Instrument and Basic Image Simulator.
*   **ICD:** Interface Control Document.
*   **MDB:** Main Database.
*   **Transit:** The passage of a source across the Gaia focal plane.
