# Software Requirements Specification (SRS)
## VII Data Research Prototype System
**Document Version:** 1.0
**Date:** 2023-10-27
**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This document defines the requirements for a prototype research system designed to evaluate the utility of Vehicle Infrastructure Integration (VII) data for enhancing transportation safety, mobility, and asset management within the state of Michigan. The intended audience includes project stakeholders, researchers, system architects, software developers, and quality assurance personnel. This SRS serves as the authoritative specification for the system's functionality, constraints, and interfaces.

#### 1.2 Scope
The system, herein referred to as the **VII Research Prototype**, is a non-operational, proof-of-concept platform. Its core mission is to ingest, process, analyze, and disseminate multi-source transportation data—with a primary focus on VII probe vehicle data—to assess its potential value for real-world transportation applications.

**In-Scope:**
*   Development of data collection interfaces for VII, traffic, and weather data feeds.
*   Implementation of data processing algorithms to derive traffic conditions, detect incidents, and infer road surface status.
*   Creation of data publication mechanisms for both machine-to-machine (M2M) and human consumption.
*   Research-focused evaluation of data quality, latency, and derived information utility.
*   Compliance with applicable Michigan Department of Information Technology (MDIT) standards for prototyping.

**Out-of-Scope:**
*   Deployment as a production, mission-critical Transportation Management System (TMS).
*   Direct control of field devices (e.g., traffic signals, Dynamic Message Signs).
*   Long-term archival of raw data beyond the needs of the prototype evaluation period.
*   Development of end-user applications for the traveling public (e.g., mobile apps).

### 2. Overall Description

#### 2.1 Product Perspective
The VII Research Prototype is a new, standalone system. It will act as a data fusion and analytics hub, positioned between upstream data providers and downstream research consumers. It does not replace any existing system but may interface with them (e.g., existing traffic data warehouses, visualization dashboards).

#### 2.2 Product Functions
The high-level functions of the system are:
1.  **Data Collection:** Acquire data streams from VII probes, legacy traffic sensors (e.g., loop detectors), and weather information services.
2.  **Data Processing & Analysis:** Clean, filter, and fuse incoming data. Apply algorithms to compute:
    *   Traffic speed, volume, and congestion levels.
    *   Probable incident detection (e.g., stopped vehicles, sudden slowdowns).
    *   Road surface condition inferences (e.g., wet, icy) based on probe data (wiper status, ABS activation, temperature).
3.  **Data Publication:** Distribute processed data products and generated alerts via standardized APIs and to a human-readable operator dashboard.

#### 2.3 User Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Research Analyst** | Transportation domain expert; not necessarily a software expert. | Access to processed data for validation and analysis; ability to configure algorithm parameters for testing. |
| **System Administrator** | IT staff familiar with MDIT standards and system maintenance. | Tools for monitoring system health, logging, and managing data source connections. |
| **External System (M2M)** | Automated downstream applications (e.g., a research visualization tool). | Reliable, well-documented API for subscribing to specific data feeds (traffic conditions, alerts). |

#### 2.4 Constraints
1.  **Prototype Nature:** The system shall be designed with the understanding that it is a research tool. Maintainability and scalability for production use are secondary to demonstrating core functional concepts.
2.  **VII Data Handling:** The system must be designed to accommodate the **near real-time** and **variable quality** characteristics of VII data (e.g., message loss, inaccuracies, irregular update intervals).
3.  **MDIT Compliance:** The system's development, hosting, and security practices shall conform to prevailing **Michigan Department of Information Technology (MDIT)** standards for prototyping efforts.
4.  **Budget & Timeline:** Development is bound by the allocated research grant funding and project timeline.

#### 2.5 Assumptions and Dependencies
*   Assumes the availability of stable, albeit prototype-quality, VII data feeds for the duration of the research project.
*   Dependent on external data sources (traffic, weather) maintaining their existing API interfaces.
*   Assumes that research algorithms for incident detection and surface condition inference will be provided by the research team.

### 3. Specific Requirements

#### 3.1 Functional Requirements

**3.1.1 Data Collection Module**
*   **FR-1.1:** The system shall connect to and ingest VII probe data from a designated provider's API/feed.
*   **FR-1.2:** The system shall connect to and ingest traffic sensor data from at least one (1) legacy source (e.g., MDOT traffic feed).
*   **FR-1.3:** The system shall connect to and ingest road weather information from a designated service (e.g., RWIS).
*   **FR-1.4:** The system shall log all ingestion failures and source connectivity status.

**3.1.2 Data Processing & Analysis Module**
*   **FR-2.1:** The system shall filter incoming VII data for gross errors (e.g., implausible speeds, invalid coordinates).
*   **FR-2.2:** The system shall fuse VII probe data with fixed-sensor data to calculate link-based traffic speed and congestion estimates.
*   **FR-2.3:** The system shall execute a configurable incident detection algorithm on the processed data stream to identify potential incidents.
*   **FR-2.4:** The system shall execute a configurable road surface condition algorithm using VII data (e.g., wiper status, external temp) and weather data.
*   **FR-2.5:** All derived data (traffic conditions, incidents, surface status) shall be timestamped and associated with a geographic location (link/segment).

**3.1.3 Data Publication Module**
*   **FR-3.1:** The system shall provide a RESTful API for external systems to query current traffic conditions for specified road segments.
    ```json
    // Example API Response
    {
      "segment_id": "I-94_EB_12345",
      "timestamp": "2023-10-27T14:30:00Z",
      "avg_speed_mph": 42.5,
      "congestion_level": "MODERATE",
      "confidence": 0.85
    }
    ```
*   **FR-3.2:** The system shall publish incident and road surface alerts via a publish-subscribe (Pub/Sub) mechanism (e.g., WebSocket, MQTT).
*   **FR-3.3:** The system shall display key processed data, system status, and active alerts on a web-based operator dashboard.

**3.1.4 System Administration**
*   **FR-4.1:** The system shall allow an administrator to enable/disable specific data sources.
*   **FR-4.2:** The system shall provide a configuration interface for adjusting key parameters of the analysis algorithms (e.g., incident detection sensitivity).

#### 3.2 Non-Functional Requirements

**3.2.1 Performance Requirements**
*   **PR-1:** The end-to-end latency from VII data ingestion to the availability of a derived data product (e.g., updated speed for a segment) shall be less than 2 minutes under normal load (**near real-time**).
*   **PR-2:** The system shall be able to process a sustained input of up to 1,000 VII messages per second during peak testing scenarios.

**3.2.2 Design Constraints**
*   **DC-1:** The software shall be developed in a language and framework compliant with MDIT's approved technologies list for prototypes.
*   **DC-2:** The system architecture shall be modular to allow for the independent replacement of data source adapters or analysis algorithms.

**3.2.3 Software Quality Attributes**
*   **Reliability:** The system shall maintain an uptime of 95% during scheduled research evaluation periods.
*   **Maintainability:** The code shall be well-documented to allow research staff to understand and modify analysis algorithms.
*   **Usability:** The operator dashboard shall require no more than 30 minutes of training for a research analyst to use effectively.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **UI-1:** A secure, web-based dashboard for monitoring and configuration (see FR-3.3, FR-4.2).

#### 4.2 Hardware Interfaces
*   **HI-1:** The system will be hosted on virtual servers provided by the state or research institution; no specific hardware interfaces are required.

#### 4.3 Software Interfaces
*   **SI-1:** VII Data Provider API (Format: Likely SAE J2735 over IP or a proprietary JSON/XML wrapper).
*   **SI-2:** Legacy Traffic Data Feed (e.g., XML-based DATEX II or proprietary JSON).
*   **SI-3:** Weather Data Service API (e.g., RESTful JSON).

#### 4.4 Communications Interfaces
*   **CI-1:** All external communications shall use secure protocols (HTTPS, WSS).
*   **CI-2:** The publication API (FR-3.1) shall support JSON as the primary data exchange format.

### 5. Other Requirements

#### 5.1 Standards Compliance
*   The system shall adhere to applicable **MDIT Security and Privacy Standards** for prototyping.
*   Data exchange formats shall follow industry best practices (REST, JSON Schema) where specific standards are not mandated.

#### 5.2 Documentation Requirements
*   A System Design Specification (SDS) shall be created.
*   API documentation (e.g., OpenAPI Specification) for all external interfaces shall be provided.
*   A user guide for the research analyst and administrator shall be created.
