# Software Requirements Specification (SRS)
## Prototype Home Management System (PHMS)

**Document Version:** 1.0
**Date:** 2023-10-27
**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the Prototype Home Management System (PHMS). This document is intended to serve as a comprehensive guide for the development team, testers, project managers, and stakeholders. It defines the system's capabilities, interfaces, and constraints to ensure a common understanding of the project scope.

#### 1.2 Document Conventions
*   **Requirements IDs:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a desirable but not mandatory feature.
*   **Priority:** (H)igh, (M)edium, (L)ow.

#### 1.3 Intended Audience and Reading Suggestions
*   **Project Managers & Stakeholders:** Focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (Non-Functional Requirements).
*   **Developers & Architects:** Focus on Sections 3 (System Features), 4 (External Interface Requirements), and 5.
*   **QA & Test Engineers:** Focus on all sections, with particular emphasis on Section 3 for test case derivation.

#### 1.4 Project Scope
The PHMS is a software prototype for monitoring and controlling simulated home environmental, security, and appliance devices via a central web interface. The system will operate entirely within a simulated software environment, with no connection to physical hardware. Its primary purpose is to validate system architecture, communication protocols, and user interaction models for a future physical implementation. The project must be completed within a twelve-month timeframe.

*   Project Charter: PHMS-CHARTER-1.0

### 2. Overall Description

#### 2.1 Product Perspective
The PHMS is a standalone, self-contained simulation. It will consist of three main components:
1.  **Device Simulator:** A software module that emulates the behavior and communication of various home devices (thermostats, sensors, appliances).
2.  **Wireless Gateway Simulator:** A software module that emulates a central hub with a simulated 1000-foot indoor range, managing communication between devices and the web server.
3.  **Web Application:** A browser-based interface for users to monitor and control the simulated home environment.

#### 2.2 Product Functions (Summary)
*   Simulate and manage environmental conditions (temperature, humidity).
*   Simulate and manage security devices (contact sensors, alarm states).
*   Simulate and control appliance and lighting units (on/off state).
*   Provide a unified web dashboard for system status and control.
*   Log all system events and user actions for review.

#### 2.3 User Classes and Characteristics
*   **Homeowner/End-User:** Primary user. Assumed to have basic computer literacy. Uses the system for monitoring and manual control.
*   **System Administrator:** Secondary user. Responsible for initial system setup in the simulation, adding/removing simulated devices, and viewing system logs.
*   **Developer/Tester:** Uses the system to validate functionality and integration within the simulated environment.

#### 2.4 Operating Environment
*   **Software:** The entire system will run on standard development workstations (Windows/Linux/macOS).
*   **Simulation:** All "devices" and the "wireless network" will be software simulations. No physical hardware dependencies.
*   **Web Server:** Application will be hosted on a local or virtualized web server (e.g., Node.js, Python Django, .NET Core).
*   **Database:** A relational (e.g., PostgreSQL, MySQL) or lightweight (SQLite) database for storing device states, logs, and user data.

#### 2.5 Design and Implementation Constraints
1.  `NFR-CON-001` (H): The system **shall** be developed and tested exclusively in a simulated environment. No physical home or devices will be used.
2.  `NFR-CON-002` (H): The project **shall** be completed within a twelve-month development cycle.
3.  `NFR-CON-003` (H): The system architecture **shall** simulate a wireless gateway with a communication range model of up to 1000 feet indoors. Device connectivity must be simulated based on this constraint.
4.  `NFR-CON-004` (M): The prototype **shall** use a modular design to allow for easy replacement of the simulation layer with a physical device layer in future iterations.

#### 2.6 Assumptions and Dependencies
*   It is assumed that the simulation environment can accurately model device communication delays and potential packet loss.
*   The project's success is dependent on the availability of development and testing resources for the full twelve-month period.
*   The system does not depend on any external, third-party live services (e.g., weather APIs) unless specifically added as a future enhancement.

### 3. System Features

#### 3.1 Environmental Management
**Description:** This feature allows monitoring and control of simulated temperature and humidity via programmable thermostats and humidistats.

**Requirements:**
*   `FR-ENV-001` (H): The system **shall** display the current temperature and humidity readings from all simulated environmental sensors on the web dashboard.
*   `FR-ENV-002` (H): The user **shall** be able to set a desired target temperature for any simulated thermostat.
*   `FR-ENV-003` (M): The user **shall** be able to set a desired target humidity level for any simulated humidistat.
*   `FR-ENV-004` (M): The user **shall** be able to create and manage time-based programs (schedules) for thermostats (e.g., "Weekday: 68°F at 8 AM, 62°F at 10 PM").
*   `FR-ENV-005` (L): The system **shall** simulate a heating/cooling system response when the target temperature deviates from the current simulated temperature by more than 1 degree.

#### 3.2 Security Management
**Description:** This feature manages the state of simulated security contact sensors (e.g., for doors/windows) and a central alarm.

**Requirements:**
*   `FR-SEC-001` (H): The system **shall** display the real-time status (Open/Closed) of all simulated contact sensors on the web dashboard.
*   `FR-SEC-002` (H): The user **shall** be able to arm (activate) and disarm (deactivate) the simulated security system from the web interface.
*   `FR-SEC-003` (H): When armed, if a contact sensor changes state to "Open," the system **shall** trigger a simulated alarm state.
*   `FR-SEC-004` (M): The triggered alarm state **shall** be visually and audibly indicated on the web dashboard (e.g., flashing red banner, simulated alarm sound option).
*   `FR-SEC-005` (M): The system **shall** log all security events (arming, disarming, sensor trigger) with a timestamp.

#### 3.3 Appliance & Lighting Control
**Description:** This feature allows control of the on/off state of simulated small appliances and lighting units.

**Requirements:**
*   `FR-ALC-001` (H): The system **shall** display the current state (On/Off) of all simulated appliances and lights on the web dashboard.
*   `FR-ALC-002` (H): The user **shall** be able to turn any simulated appliance or light on or off from the web dashboard.
*   `FR-ALC-003` (M): The user **shall** be able to group lights/appliances into named "scenes" (e.g., "Evening Mode") and activate the entire scene with one action.
*   `FR-ALC-004` (L): The user **shall** be able to set simple timers to turn a device on or off after a specified delay.

#### 3.4 Device & System Management
**Description:** This feature allows administrative control over the simulated ecosystem.

**Requirements:**
*   `FR-DSM-001` (H): The System Administrator **shall** be able to add, configure, and remove simulated devices (specifying type, simulated location, and initial state) via a dedicated admin interface.
*   `FR-DSM-002` (H): The system **shall** simulate the wireless gateway's range constraint. Devices added beyond 1000 simulated feet from the gateway **shall** be indicated as "Out of Range" and be unresponsive.
*   `FR-DSM-003` (M): The system **shall** provide an event log viewable in the web interface, showing device state changes, user commands, and system errors.
*   `FR-DSM-004` (L): The system **shall** allow the administrator to simulate a device communication failure and observe the system's response.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Primary UI:** A responsive web application accessible via modern browsers (Chrome, Firefox, Safari, Edge).
*   **Dashboard:** A single, unified view displaying categorized tiles or panels for Environmental, Security, and Appliance status.
*   **Control Elements:** Buttons, sliders, and switches for controlling device states. Forms for setting schedules and scenes.
*   **Visual Feedback:** Clear visual indicators for device status (e.g., green for on/closed/normal, red for off/open/alarm).

#### 4.2 Simulation Interfaces
*   **Device-Gateway Interface:** A simulated wireless protocol (e.g., modeled after Zigbee or Z-Wave) using internal messaging (e.g., message queues, event buses, or direct function calls within the simulation).
*   **Gateway-Webserver Interface:** A defined internal API (e.g., RESTful or WebSocket) for the gateway simulator to communicate device states to the web server and receive commands from it.

#### 4.3 Communications Interfaces
*   The web application **shall** use HTTPS (simulated with local SSL for professionalism) for all client-server communication.
*   Real-time updates on the dashboard (e.g., a temperature change) **shall** be implemented using WebSockets or Server-Sent Events (SSE).

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   `NFR-PER-001`: The web dashboard **shall** load within 3 seconds under simulated normal load (<100 devices).
*   `NFR-PER-002`: A user command (e.g., turn on light) **shall** be reflected in the UI within 1 second, including simulated network delay.
*   `NFR-PER-003`: The simulator **shall** be capable of modeling at least 150 concurrent devices without degradation of core functions.

#### 5.2 Safety & Security Requirements
*   `NFR-SEC-001`: User access to the admin functions (device management) **shall** require authentication separate from the basic user role.
*   `NFR-SEC-002`: All user passwords **shall** be stored using industry-standard hashing algorithms (e.g., bcrypt).
*   `NFR-SEC-003`: The system **shall** be designed to prevent simulation-level denial-of-service from a single misbehaving simulated device.

#### 5.3 Software Quality Attributes
*   **Maintainability:** Code **shall** be modular with clear separation between simulation logic, business logic, and presentation logic. `NFR-QLT-001`
*   **Usability:** The web interface **shall** be intuitive and require minimal training for the Homeowner user. Common tasks (on/off) **shall** be achievable in 2 clicks or less. `NFR-QLT-002`
*   **Reliability:** The core web service **shall** have an uptime of 99.9% within the simulated test environment. `NFR-QLT-003`
*   **Portability:** The system **shall** be deployable on Windows, Linux, and macOS development platforms. `NFR-QLT-004`
