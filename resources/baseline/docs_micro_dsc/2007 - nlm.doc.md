## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the National Library of Medicine's (NLM) Digital Preservation Repository (DPR). The primary purpose of the DPR is to establish a robust, secure, and standards-compliant system for the long-term preservation of and controlled access to NLM's digitized and born-digital biomedical collection materials. This document serves as a contractual agreement between stakeholders and the development team and will guide the design, development, testing, and deployment phases of the project.

### 1.2 Document Conventions
*   Requirements are uniquely identified using the format `FR-XXX` for Functional Requirements and `NFR-XXX` for Non-Functional Requirements.
*   **Bold** text is used for key terms and emphasis.
*   All system names, such as DPR, are capitalized.
*   Priority levels are indicated as: **High (H)**, **Medium (M)**, **Low (L)**.

### 1.3 Intended Audience and Reading Suggestions
*   **Project Sponsors & NLM Management:** Focus on Sections 1 (Introduction) and 2 (Overall Description).
*   **System Architects & Developers:** Focus on Sections 3 (External Interfaces), 4 (System Features), and 5 (Non-Functional Requirements).
*   **Quality Assurance & Test Engineers:** Focus on Sections 4 (System Features) and 5 (Non-Functional Requirements) to derive test cases.
*   **Project Managers:** Use the entire document for planning, tracking, and scope management.

### 1.4 Project Scope
The DPR will be a core component of NLM's digital infrastructure, designed to:
*   **Ingest** diverse digital materials (e.g., scanned pages, PDFs, datasets, audiovisual files) from NLM's digitization pipelines and born-digital acquisition workflows.
*   **Preserve** these materials by generating, storing, and managing standards-compliant Archival Information Packages (AIPs) based on the OAIS Reference Model (ISO 14721).
*   **Provide Access** to preserved materials for designated user classes (public, researchers, staff) through controlled discovery and delivery interfaces.
*   **Ensure Long-term Viability** through automated preservation planning, monitoring, and actions (e.g., format migration, integrity checking).
*   **Integrate** seamlessly with existing NLM enterprise systems, including the Integrated Library System (ILS), authentication services, and storage infrastructure.

**Out-of-Scope:**
*   Initial digitization or creation of source digital objects.
*   Development of a public-facing, general-purpose search portal (the DPR will provide APIs and limited interfaces for access, but not a full-featured public website).
*   Physical preservation of non-digital assets.

*   HHS and NIH Information Security and Privacy Policies.

## 2. Overall Description

### 2.1 Product Perspective
The DPR is a new, self-contained system that will operate within the larger NLM IT ecosystem. It will function as the system of record for preserved digital assets, interacting with upstream content suppliers and downstream access systems.

```
[Content Creators] --> (Submission API) --> [DPR CORE]
                                                          |--> (Storage Layer)
[ILS / Catalog] <--> (Metadata Sync) <--> [DPR CORE] <-->|--> (Preservation Engine)
                                                          |--> (Access API)
[Public/Researchers] <-- (Access Interface) <-----------[DPR CORE] <--> (Admin Console) <--> [NLM Staff]
```

### 2.2 Product Functions (Summary)
1.  **Ingest & Packaging:** Accept submissions, validate content, and create OAIS-compliant AIPs (Submission Information Packages -> Archival Information Packages).
2.  **Storage & Data Management:** Securely store AIPs, manage file integrity (checksums), and replicate content for disaster recovery.
3.  **Preservation Planning:** Monitor technology obsolescence, assess risks, and execute preservation strategies (normalization, migration, emulation).
4.  **Access & Discovery:** Provide search/browse functionality and deliver Dissemination Information Packages (DIPs) based on user permissions.
5.  **Administration:** Manage users, policies, system configuration, and generate audit reports.

### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Repository Manager** | NLM staff; expert in digital preservation; administrative privileges. | Configure preservation policies, run audits, manage preservation actions, oversee system health. |
| **Ingest Specialist** | NLM staff; knowledgeable in metadata and formats. | Initiate and monitor ingest workflows, troubleshoot submission errors, manage queues. |
| **Reference Staff** | NLM staff; provides user support. | Search for preserved items, generate access copies for users, verify rights. |
| **Authenticated Researcher** | External user with granted credentials. | Discover and request access to restricted materials, download approved files. |
| **Public User** | General internet user. | Discover and access publicly available materials, view access copies online. |
| **System Integrator** | External or internal developer. | Integrate DPR services with other systems via well-documented APIs. |

### 2.4 Operating Environment
*   **Software:** Enterprise Linux distribution (e.g., RHEL). Java/Python runtime environments. Relational (PostgreSQL) and/or triplestore database. Apache/Tomcat or similar application server.
*   **Hardware:** High-availability servers, significant network-attached storage (SAN/NAS) with planned growth capacity, load balancers.
*   **Cloud:** Potential for hybrid deployment (on-premise core with cloud storage/processing components).

### 2.5 Design and Implementation Constraints
1.  **NFR-CON-01:** The system **must** conform to all applicable HHS and NIH security policies, data handling standards, and software development lifecycle requirements.
2.  **NFR-CON-02:** The system **must** integrate with the existing NLM Integrated Library System (ILS) for bi-directional metadata synchronization and item status updates.
3.  **NFR-CON-03:** The system **must** support Unicode (UTF-8) fully to handle metadata and content in multiple languages and non-Roman scripts (e.g., Arabic, Chinese, Cyrillic).
4.  **FR-CON-04:** The system **must** implement the OAIS Reference Model as its foundational architectural framework.
5.  **NFR-CON-05:** The system **must** use open, community-supported standards for packaging (e.g., BagIt), metadata (e.g., PREMIS, MODS), and identifiers (e.g., ARK, DOI).

### 2.6 Assumptions and Dependencies
*   **AS-01:** Adequate and sustained funding will be available for development, deployment, and ongoing maintenance.
*   **AS-02:** NLM will provide subject matter experts for metadata schemas, digital preservation policies, and collection specifics.
*   **DE-01:** The project depends on the stability and availability of existing NLM enterprise services (e.g., LDAP/Active Directory for authentication, network infrastructure).
*   **DE-02:** Successful integration requires cooperation from the teams managing external systems (e.g., ILS team).

## 3. External Interface Requirements

### 3.1 User Interfaces
*   **Web-based Admin Console:** Responsive, accessible (WCAG 2.1 AA), dashboard-driven interface for repository management tasks.
*   **Staff Ingest Client:** Web interface or desktop utility for preparing and submitting large/ complex digital collections.
*   **Public Access Portal:** A clean, simple web interface for searching, browsing, and viewing public domain materials.
*   **RESTful APIs:** JSON/XML-based APIs for all core functions (ingest, search, retrieve, manage).

### 3.2 Hardware Interfaces
The DPR must interface with:
*   High-performance, redundant storage arrays (SAN/NAS) via standard protocols (NFS, SMB, S3).
*   Tape library or other cold storage system for disaster recovery copies.

### 3.3 Software Interfaces
1.  **ILS (Integrated Library System):** `FR-INT-01` The DPR shall provide a real-time or batch API for synchronizing descriptive metadata and access status (e.g., "available in repository") with the NLM catalog.
2.  **Authentication/Authorization Service:** `FR-INT-02` The DPR shall integrate with the NLM enterprise identity provider (e.g., NIH Login) for user authentication and role assignment.
3.  **Format Registry:** `FR-INT-03` The DPR shall be able to query an external format registry (e.g., PRONOM) to validate file formats and determine preservation risks.

### 3.4 Communications Interfaces
*   All external communications shall use encrypted channels (TLS 1.2+).
*   Internal service-to-service communication within the trusted zone may use secure messaging protocols (e.g., AMQP over TLS).

## 4. System Features

### 4.1 Feature 1: Ingest and AIP Generation
**Description:** This feature encompasses the process of accepting digital materials, validating them, enriching them with preservation metadata, and packaging them into Archival Information Packages for secure storage.

**Requirements:**
*   `FR-ING-01 (H):` The system shall accept digital content via a secure web upload, SFTP, or API submission.
*   `FR-ING-02 (H):` The system shall validate the integrity of submitted files using checksums (SHA-256).
*   `FR-ING-03 (H):` The system shall generate a unique, persistent identifier (e.g., ARK) for each AIP.
*   `FR-ING-04 (H):` The system shall create a complete AIP conforming to the BagIt specification and including PREMIS preservation metadata.
*   `FR-ING-05 (M):` The system shall support configurable, multi-step ingest workflows (e.g., virus scan -> format identification -> metadata extraction -> package).

### 4.2 Feature 2: Controlled Access and Discovery
**Description:** This feature provides the mechanisms for users to find and access preserved materials based on their authorization level.

**Requirements:**
*   `FR-ACC-01 (H):` The system shall provide a web-based search interface supporting keyword search and faceted browsing (by date, format, collection).
*   `FR-ACC-02 (H):` The system shall enforce access control rules, differentiating between public, on-site, and restricted materials.
*   `FR-ACC-03 (H):` The system shall generate and deliver Dissemination Information Packages (DIPs), which may be access copies (e.g., derived JPEGs, watermarked PDFs) rather than preservation masters.
*   `FR-ACC-04 (M):` The system shall provide a REST API for programmatic search and retrieval of metadata and access copies.

### 4.3 Feature 3: Preservation Planning and Action
**Description:** This feature monitors the repository's content and technological environment to proactively ensure long-term accessibility.

**Requirements:**
*   `FR-PRE-01 (H):` The system shall regularly verify the integrity of all stored AIPs by re-calculating and comparing checksums.
*   `FR-PRE-02 (H):` The system shall generate alerts when files are in formats identified as being at high preservation risk.
*   `FR-PRE-03 (M):` The system shall support configurable preservation action workflows, such as format migration (e.g., TIFF -> JPEG2000) upon manager approval.
*   `FR-PRE-04 (M):` The system shall maintain a complete audit trail (provenance) of all preservation actions performed on an AIP.

### 4.4 Feature 4: System Administration and Reporting
**Description:** This feature allows administrators to configure, monitor, and report on the repository's operations.

**Requirements:**
*   `FR-ADM-01 (H):` The system shall provide a dashboard showing system health, ingest statistics, storage usage, and preservation alerts.
*   `FR-ADM-02 (H):` The system shall allow administrators to manage user accounts and assign roles/permissions.
*   `FR-ADM-03 (M):` The system shall generate standard preservation audit reports (e.g., ISO 16363 checklist support) and custom operational reports.

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   `NFR-PER-01:` The system shall support the concurrent ingest of at least 10,000 medium-sized (100MB) objects per day.
*   `NFR-PER-02:` Search results for simple queries shall be returned in under 2 seconds for 95% of queries.
*   `NFR-PER-03:` The system shall be designed for 99.9% uptime during core business hours.

### 5.2 Security Requirements
*   `NFR-SEC-01:` The system shall comply with all NIST 800-53 controls as mandated by HHS/NIH policy for a Moderate-impact system.
*   `NFR-SEC-02:` All data at rest containing sensitive information shall be encrypted using FIPS 140-2 validated cryptographic modules.
*   `NFR-SEC-03:` The system shall maintain detailed, tamper-evident logs of all user actions and system events for auditing.
*   `NFR-SEC-04:` Access to administrative functions shall require multi-factor authentication (MFA).

### 5.3 Software Quality Attributes
*   **Reliability:** The system must have automated failover capabilities for critical components.
*   **Maintainability:** Code shall be modular, documented, and accompanied by a full test suite. Deployment shall be automated.
*   **Scalability:** The architecture shall allow for horizontal scaling of stateless services (e.g., web servers, ingest workers) and storage capacity without major redesign.
*   **Usability:** Administrative interfaces shall follow NLM UX guidelines. Task success rate for core ingest and search tasks shall exceed 90% in user acceptance testing.

### 5.4 Internationalization and Localization
*   `NFR-I18N-01:` The system shall use UTF-8 encoding for all text processing, storage, and display.
*   `NFR-I18N-02:` The user interface shall be designed to accommodate right-to-left (RTL) scripts and variable text lengths.
*   `NFR-I18N-03:` All metadata schemas supported shall be capable of storing multilingual values.
