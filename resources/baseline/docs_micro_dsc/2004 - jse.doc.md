### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the **ISIN Management System (IMS)**. The system is to be developed for the Johannesburg Stock Exchange (JSE) in its capacity as the National Numbering Agent (NNA). The primary purpose of the IMS is to provide a fully automated, electronic system for the issuance, cancellation, and de-registration of International Securities Identification Numbers (ISINs) for dematerialized Money Market Instruments, based on validated requests received from STRATE via the SWIFT network.

This document is intended for use by the project stakeholders, including JSE management, STRATE representatives, system architects, software developers, testers, and project managers.

#### 1.2 Scope
The in-scope functionality of the ISIN Management System includes:
*   Automated processing of incoming SWIFT MT598 messages from STRATE.
*   Validation of message structure and business content.
*   Automatic generation of a new ISIN with the prefix 'ZAM' in compliance with ANNA/ISO rules.
*   Cancellation or de-registration of an existing ISIN.
*   Generation and transmission of appropriate SWIFT MT598 response or rejection messages back to STRATE.
*   Maintenance of an audit log of all requests and system actions.

Out of Scope:
*   User interface for manual ISIN management.
*   Management of ISINs for instrument types other than dematerialized Money Market Instruments.
*   Direct interaction with other JSE or STRATE internal systems beyond the defined SWIFT interface.
*   Payment or billing functionalities associated with ISIN issuance.

### 2. Overall Description

#### 2.1 Product Perspective
The IMS is a new, standalone backend processing system. It will interface with the existing JSE SWIFT Alliance Gateway to send and receive financial messages. It does not replace any existing system but automates a currently manual or semi-automated process.

#### 2.2 Product Functions
The core high-level functions are:
1.  **SWIFT Message Reception:** Listen for incoming MT598 messages from the SWIFT gateway.
2.  **Validation:** Validate the syntax, structure, and business logic of the incoming request.
3.  **ISIN Issuance:** For valid issuance requests, generate a new, unique ISIN.
4.  **ISIN Lifecycle Management:** Process valid requests for cancellation or de-registration.
5.  **Response Generation:** Create and send an appropriate MT598 response (acknowledgement or rejection) back to STRATE.
6.  **Audit Logging:** Record every transaction for compliance and troubleshooting.

#### 2.3 User Characteristics
The primary "user" is an **external system**: STRATE's automated systems. No direct human users are envisioned for core processing. Administrative personnel from JSE may require access to the audit logs and reporting functions (handled by a separate support interface, out of scope).

#### 2.4 Constraints
1.  **Regulatory Compliance:** The system **must** comply with ISO 6166 and ANNA guidelines for ISIN construction and issuance.
2.  **Message Format:** All communication **must** use the project-specific SWIFT MT598 format as detailed in the appendices.
3.  **ISIN Prefix:** All generated ISINs **must** have the country code prefix 'ZAM' (for South Africa).
4.  **Automation:** The process **must** be fully automatic upon receipt of a valid SWIFT message. No manual intervention is required for standard processing.
5.  **Interface:** The system **must** integrate with the existing JSE SWIFT infrastructure.

#### 2.5 Assumptions and Dependencies
*   STRATE will send correctly formatted MT598 messages.
*   The JSE SWIFT Gateway is available and configured correctly.
*   The system will have access to a persistent database to store issued ISINs and prevent duplication.
*   ANNA rules for ISIN issuance for Money Market Instruments are stable during development.

### 3. Specific Requirements

#### 3.1 External Interface Requirements
##### 3.1.1 SWIFT Interface
*   **Protocol:** The system shall connect to the existing SWIFT Alliance Gateway (SAG) using SWIFTNet.
*   **Message Type:** Inbound and outbound messages shall be of type **MT598**.
*   **Format:** The detailed structure of fields within the MT598 (e.g., :16R:GENL, :20C::SEME, :12A::CLAS/ISIN/) shall conform to the templates in **Appendix A**.

#### 3.2 Functional Requirements

##### 3.2.1 FR1: SWIFT Message Reception & Parsing
*   **FR1.1:** The system shall continuously monitor the designated SWIFT input queue for incoming MT598 messages from STRATE.
*   **FR1.2:** The system shall parse the incoming MT598 message into its constituent blocks and fields as per SWIFT standards.

##### 3.2.2 FR2: Message Validation
*   **FR2.1 (Syntax Validation):** The system shall validate that the incoming message is a well-formed MT598.
*   **FR2.2 (Field Validation):** The system shall validate the presence and format of mandatory fields as defined in Appendix A (e.g., Sender's Reference (:20C::SEME), Function of the Message (:22F::CAIS), Instrument Description (:35B:)).
*   **FR2.3 (Business Logic Validation):**
    *   For an **ISSUE** request, the system shall validate that the instrument description does not already exist for an active ISIN.
    *   For a **CANCEL** or **DE-REGISTER** request, the system shall validate that the provided ISIN (:35B: ISIN ZAMXXXXXXXXX) exists and is in an active state.
*   **FR2.4:** If any validation check (FR2.1-FR2.3) fails, the system shall **not** process the request and shall proceed to **FR4**.

##### 3.2.3 FR3: ISIN Processing
###### 3.2.3.1 FR3.1: ISIN Issuance
*   **FR3.1.1:** Upon a validated ISSUE request, the system shall generate a new ISIN.
*   **FR3.1.2:** The generated ISIN shall have the prefix **'ZAM'**.
*   **FR3.1.3:** The 9-character alphanumeric National Security Identifier (NSIN) portion shall be generated according to an algorithm that guarantees uniqueness and complies with ANNA rules for MMIs.
*   **FR3.1.4:** The system shall calculate the final ISIN check digit as per ISO 6166.
*   **FR3.1.5:** The system shall persist the new ISIN, its associated instrument details from the SWIFT message, status ('ACTIVE'), and timestamp in the system database.

###### 3.2.3.2 FR3.2: ISIN Cancellation/De-registration
*   **FR3.2.1:** Upon a validated CANCEL request, the system shall update the status of the specified ISIN to 'CANCELLED'.
*   **FR3.2.2:** Upon a validated DE-REGISTER request, the system shall update the status of the specified ISIN to 'DE-REGISTERED'.
*   **FR3.2.3:** The system shall persist the action, timestamp, and original request reference in the database audit log.

##### 3.2.4 FR4: Response Generation & Transmission
*   **FR4.1 (Positive Acknowledgement):** For a successfully processed ISSUE request, the system shall generate an MT598 response message containing the newly assigned ISIN in field :35B:.
*   **FR4.2 (Action Confirmation):** For a successfully processed CANCEL or DE-REGISTER request, the system shall generate an MT598 response message confirming the action and the affected ISIN.
*   **FR4.3 (Rejection):** For a request that failed validation (FR2), the system shall generate an MT598 rejection message. The rejection message shall include the original sender's reference (:20C::SEME) and a reason code in field :24B: indicating the nature of the failure (e.g., //FORM/ for format error, //DUPL/ for duplicate, //INVD/ for invalid data).
*   **FR4.4:** All response/rejection messages shall be placed on the designated SWIFT output queue for transmission back to STRATE.

##### 3.2.5 FR5: Audit & Logging
*   **FR5.1:** The system shall create an immutable log entry for every incoming MT598 message, regardless of processing outcome.
*   **FR5.2:** Each log entry shall include: message raw content, sender, timestamp, validation result, processing action taken, response sent, and system-generated reference ID.

#### 3.3 Non-Functional Requirements

##### 3.3.1 Performance Requirements
*   **PR1:** The system shall process 95% of incoming requests and generate a response within **5 seconds** under normal load.
*   **PR2:** The system shall be designed to handle a peak load of **50 ISIN requests per minute**.

##### 3.3.2 Reliability & Availability
*   **RA1:** The system shall have an availability of **99.5%** during JSE business hours (06:00 - 20:00 SAST).
*   **RA2:** No single point of failure shall cause the complete loss of system functionality.

##### 3.3.3 Security Requirements
*   **SR1:** All communication via SWIFT shall inherit the security (encryption, authentication) provided by the SWIFTNet PKI.
*   **SR2:** Access to system logs and the ISIN database shall be restricted to authorized JSE personnel only.
*   **SR3:** The system shall not store full SWIFT messages longer than required by regulatory compliance (7 years).

##### 3.3.4 Maintainability
*   **MR1:** The system shall be designed modularly to allow for updates to the ISIN generation algorithm or SWIFT format definitions with minimal impact on other components.

### Appendix A: SWIFT MT598 Format Specifications

*(This appendix would contain the detailed, project-specific mappings. The following is a template structure.)*

#### A.1 Incoming Message from STRATE (Request)

**Message Type:** MT598
**Function:** Request for ISIN Action

**Mandatory Fields:**
```
:20C::SEME//[STRATE's unique reference for this request]
:22F::CAIS//[ISSU, CANC, or DREG]
:12A::CLAS/ISIN/
:35B:[ISIN ZAMXXXXXXXXX] or [Instrument Description]
//For ISSUE: /IN/[Full instrument description text]
//For CANC/DREG: ISIN ZAMXXXXXXXXX
```

#### A.2 Outgoing Message to STRATE (Response)

**Message Type:** MT598
**Function:** Response to ISIN Action Request

**Mandatory Fields for Positive Response:**
```
:20C::SEME//[Original Sender's Reference from request]
:22F::CAIS//[CONF]
:35B:ISIN ZAMXXXXXXXXXX //The newly issued or affected ISIN
```

**Mandatory Fields for Rejection:**
```
:20C::SEME//[Original Sender's Reference from request]
:22F::CAIS//[REJT]
:24B::REAS//[Reason Code, e.g., //FORM/, //DUPL/, //INVD/]
:70E::SPRO//[Textual description of the error]
```
