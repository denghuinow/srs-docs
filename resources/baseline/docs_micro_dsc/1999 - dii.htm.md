### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the requirements for the XML Infrastructure Services system. The primary purpose of this system is to provide a standardized, portable XML service layer for applications within the Defense Information Infrastructure (DII) Common Operating Environment (COE). This layer will enable application interoperability and abstract vendor-specific data access implementations, ensuring consistency and reducing integration complexity across the COE.

#### 1.2 Scope
The scope of this project encompasses the design, development, and delivery of a suite of software services that facilitate XML-based data interchange for DII COE applications. The system will provide core functions for managing XML metadata, designing schemas, and handling XML document generation and consumption. It will act as an intermediary between COE applications and existing data access components (DBIF, DAC, COTS RDBMS), isolating applications from the underlying data persistence specifics.

**In-Scope:**
*   A centralized registry for XML metadata (terms, tags, structures).
*   Tools and services for designing and validating XML document schemas (XSD).
*   Services to generate XML documents from underlying data sources.
*   Services to parse, validate, and consume incoming XML documents.
*   Adapters for interfacing with DBIF, DAC, and standard RDBMS interfaces.
*   Compliance packaging and documentation per DII COE guidelines.

**Out-of-Scope:**
*   Modification of existing COE core services (DBIF, DAC).
*   Development of end-user applications that will consume these services.
*   Long-term archival and retrieval of XML documents (beyond transactional processing).
*   Graphical user interface (GUI) for administrative functions (initial release will be API/service-driven).

### 2. Overall Description

#### 2.1 Product Perspective
The XML Infrastructure Services system is a new component within the DII COE middleware layer. It is not a standalone application but a set of services that other COE-compliant applications will invoke.

**System Interfaces:**
*   **Upstream (Consumer):** DII COE Applications via defined service APIs.
*   **Downstream (Provider):** DBIF, DAC, and direct JDBC/ODBC connections to COTS RDBMS.
*   **Adjacent:** COE System Management and Registry services for deployment and discovery.

#### 2.2 Product Functions
The high-level functions of the system are:
1.  **Metadata Registration:** Maintain a secure, searchable registry of approved XML elements, data types, and complex structures.
2.  **Schema Design & Management:** Provide capabilities to create, version, validate, and store XML Schemas (XSD) based on registered metadata and relational data models.
3.  **Document Generation:** Dynamically generate well-formed and valid XML documents by querying data from specified sources (via DBIF/DAC/RDBMS) and applying transformation rules defined in a schema.
4.  **Document Consumption:** Parse incoming XML documents, validate them against a specified schema, and map the data to operations on the underlying data sources (insert, update, query).

#### 2.3 User Characteristics
The intended users of the system are:
*   **System Integrators/Developers:** Technical personnel who will configure the services, register metadata, design schemas, and integrate the APIs into COE applications. They possess strong understanding of XML, DII COE, and data modeling.
*   **Application Software:** Automated clients that will call the service APIs programmatically.

#### 2.4 Constraints
1.  **Portability Constraint:** The software must be portable and execute without modification on any hardware/software platform certified as compliant with the DII COE.
2.  **Integration Constraint:** Must interface with existing DBIF and DAC components, adhering strictly to their published interfaces. Must also support standard interfaces for major COTS RDBMS (e.g., Oracle, SQL Server via JDBC/ODBC).
3.  **Compliance Constraint:** All software, including documentation and build scripts, must be delivered in accordance with DII COE integration and packaging guidelines.
4.  **Language Constraint:** Core service logic must be implemented in a language mandated by the DII COE (e.g., Java EE).

#### 2.5 Assumptions and Dependencies
*   It is assumed that the existing DBIF and DAC services are stable, available, and conform to their documented specifications.
*   The system depends on the presence of a JRE/JDK and application server environment as stipulated by the DII COE.
*   Successful operation depends on correctly configured data source connections (e.g., JDBC URLs, credentials).

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Metadata Registration Services
*   **FUN-REG-001:** The system shall provide an API to register a new atomic XML data type (term), including its name, data type (string, integer, dateTime, etc.), and optional constraints.
*   **FUN-REG-002:** The system shall provide an API to register an XML element (tag), associating it with a registered data type or a complex structure.
*   **FUN-REG-003:** The system shall provide an API to define and register a complex XML structure (e.g., `xs:complexType`), composed of sequences or choices of registered elements or other structures.
*   **FUN-REG-004:** The system shall maintain version history for all registered metadata items.
*   **FUN-REG-005:** The system shall provide query APIs to search and retrieve metadata items by name, type, or date.

##### 3.1.2 Schema Design & Management Services
*   **FUN-SCH-010:** The system shall provide an API to create a new XML Schema (XSD) by assembling registered metadata items (structures, elements).
*   **FUN-SCH-011:** The system shall generate a standard XSD 1.0 document from the internally assembled schema definition.
*   **FUN-SCH-012:** The system shall validate a generated or user-provided XSD document for syntactic and semantic correctness against W3C standards.
*   **FUN-SCH-013:** The system shall store and manage schema documents, associating them with a unique identifier and version.
*   **FUN-SCH-014:** The system shall provide an API to map schema elements to physical data sources (e.g., Table.Column for RDBMS, DAC object attributes).

##### 3.1.3 XML Document Generation Services
*   **FUN-GEN-020:** The system shall provide an API to generate an XML document by specifying a target schema ID and a set of data retrieval parameters (e.g., key values for a query).
*   **FUN-GEN-021:** The system shall, upon request, execute the data source mappings associated with the schema to retrieve data from DBIF, DAC, or RDBMS.
*   **FUN-GEN-022:** The system shall transform the retrieved relational/object data into a well-formed XML document that validates against the specified schema.
*   **FUN-GEN-023:** The generated XML document shall be returned to the calling application as a stream (e.g., byte stream, DOM/SAX representation).

##### 3.1.4 XML Document Consumption Services
*   **FUN-CON-030:** The system shall provide an API to submit an XML document for processing, along with a specified target schema ID for validation.
*   **FUN-CON-031:** The system shall validate the submitted XML document against the specified schema. If invalid, the system shall return a detailed validation error report.
*   **FUN-CON-032:** Upon successful validation, the system shall parse the XML document and, based on schema mappings, transform the data into commands or operations for the underlying data source (e.g., SQL `INSERT/UPDATE`, DAC method calls).
*   **FUN-CON-033:** The system shall execute the derived operations against the configured data source (DBIF/DAC/RDBMS) within a transactional context, if applicable.

##### 3.1.5 System Interface Services
*   **FUN-INT-040:** The system shall implement the standard client interfaces for DBIF as defined in the DBIF ICD.
*   **FUN-INT-041:** The system shall implement the standard client APIs for the DAC.
*   **FUN-INT-042:** The system shall support connectivity to COTS RDBMS via JDBC 4.0 (or later) compliant drivers.

#### 3.2 Non-Functional Requirements

##### 3.2.1 Performance
*   **PER-001:** The metadata registration and query APIs shall respond to 95% of requests within 2 seconds under a nominal load of 50 concurrent users.
*   **PER-002:** The XML document generation and consumption services shall process documents of up to 10MB in size within 30 seconds for 95% of transactions under test load.

##### 3.2.2 Portability (Key Constraint)
*   **PORT-001:** The entire software system, including all dependencies, shall be packaged and certified to run on any platform listed in the current DII COE Master Configuration List.

##### 3.2.3 Reliability & Availability
*   **REL-001:** The system shall have an operational availability of 99.5% during standard operating hours.
*   **REL-002:** The metadata registry shall maintain data integrity, preventing corruption of registered items and their relationships.

##### 3.2.4 Security
*   **SEC-001:** All service APIs shall require authentication via the DII COE standard security mechanism (e.g., PKI, Kerberos).
*   **SEC-002:** Access to register, modify, or delete metadata and schemas shall be restricted to authorized administrator roles.
*   **SEC-003:** The system shall not log sensitive data contained within XML documents at the `INFO` or `DEBUG` levels.

##### 3.2.5 Compliance
*   **COMP-001:** The delivered software package shall conform to the structure and content requirements specified in the *DII COE Software Development and Integration Guide*.
*   **COMP-002:** All XML schemas generated or accepted by the system shall conform to the W3C XML Schema 1.0 specification.
