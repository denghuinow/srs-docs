### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Publications Management System (PMS). The PMS is a web-accessible system designed to manage a database of bibliographic information and full-text publications. It includes access control, automated metadata extraction, and administrative functions. This SRS serves as a contract between the development team and stakeholders, providing a complete description of the system's behavior.

#### 1.2 Scope
The PMS will be a self-contained web application that allows authorized users to:
*   Search, browse, view, and download publication records and associated full-text files.
*   Upload new publications, with automated extraction of bibliographic metadata from uploaded files.
*   Manage and curate bibliographic metadata for all publications in the system.
*   Administer system users, define access groups, and configure system parameters.

The system will **not** include:
*   Integration with external publication databases (e.g., Crossref, PubMed).
*   Advanced publication analytics or citation tracking.
*   Social features such as commenting or rating.

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **PMS:** Publications Management System.
*   **Bibliographic Metadata:** Structured data describing a publication (e.g., title, authors, journal, year, DOI, abstract).
*   **Full-text:** The complete digital document of the publication (e.g., PDF, DOC).
*   **W3C:** World Wide Web Consortium.
*   **XHTML 1.0 Transitional:** A web standard for markup language.
*   **Admin/Superuser:** A user with full system privileges.
*   **Contributor:** A user with privileges to upload and manage their own publications.
*   **Viewer:** A user with read-only access.

### 2. Overall Description

#### 2.1 Product Perspective
The PMS is a new, standalone web application. It will interact with:
*   **Users:** Via a web browser over HTTP/HTTPS.
*   **Server OS:** The Linux server named "Wilma."
*   **Persistent Storage:** A database (to be selected, e.g., SQLite/PostgreSQL) for metadata and a filesystem directory for full-text files.

#### 2.2 Product Functions (High-Level)
1.  **Publication Repository:** Secure storage and retrieval of publication files and metadata.
2.  **Discovery Interface:** Public and authenticated search/browse functionality.
3.  **Submission Workflow:** Process for uploading files and associated metadata.
4.  **Metadata Enrichment:** Automated extraction of metadata from uploaded documents.
5.  **User & Access Management:** Creation, authentication, and authorization of users and groups.
6.  **System Administration:** Configuration and maintenance interfaces.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Anonymous User** | Public web visitor. No authentication. | Browse and search public publications. View metadata. Download public files. |
| **Viewer** | Authenticated basic user (e.g., lab member). | All anonymous functions. Access to restricted publications. |
| **Contributor** | Authenticated power user (e.g., researcher). | All Viewer functions. Upload new publications. Edit metadata for their own publications. |
| **Administrator** | Authenticated system manager. | All Contributor functions. Manage all publications (edit/delete). Full user and group administration. System configuration. |

#### 2.4 Operating Environment
*   **Software Environment:**
    *   Server: Linux (specifically, the server named "Wilma").
    *   Runtime: Ruby (MRI) – **No external web frameworks (e.g., Rails, Sinatra) are permitted.**
    *   Web Server: To be determined (e.g., Puma, Unicorn, or a custom Ruby HTTP server).
    *   Database: To be determined (e.g., SQLite for simplicity or PostgreSQL).
    *   Markup: All generated web interfaces **must comply with W3C XHTML 1.0 Transitional** standard.
*   **Hardware Environment:** The Linux server "Wilma" and its associated storage.

#### 2.5 Design and Implementation Constraints
1.  **Implementation Language:** The application core must be implemented in Ruby.
2.  **Framework Prohibition:** The use of full-stack web frameworks (Ruby on Rails, Sinatra, Hanami, etc.) is explicitly forbidden. Lightweight libraries for specific tasks (e.g., `Rack` for interface, a database ORM/connector, a template engine) may be allowable pending review, but the architecture must be custom-built.
3.  **Web Standard Compliance:** All user-facing HTML must validate as XHTML 1.0 Transitional.
4.  **Deployment Target:** The system must be deployable and operational on the specified Linux server ("Wilma").

#### 2.6 Assumptions and Dependencies
*   The server "Wilma" has a compatible version of Ruby installed.
*   Necessary system permissions are available on "Wilma" to install Ruby gems, run a web server, and access persistent storage.
*   A suitable database system is available or can be installed on "Wilma."

### 3. System Features & Functional Requirements

#### 3.1 Feature: User Authentication & Authorization
*   **FR1.1:** The system shall provide a login page for user authentication.
*   **FR1.2:** The system shall allow Administrators to create, modify, enable, disable, and delete user accounts.
*   **FR1.3:** The system shall support user roles (Viewer, Contributor, Admin) with predefined permissions.
*   **FR1.4:** The system shall provide logout functionality that securely terminates the user session.

#### 3.2 Feature: Publication Search & Browse
*   **FR2.1:** The system shall provide a public search interface accessible without login.
*   **FR2.2:** The system shall allow searching by metadata fields (title, author, year, keyword, etc.).
*   **FR2.3:** The system shall display search results in a list with key metadata (title, authors, year).
*   **FR2.4:** The system shall provide a detailed view for a single publication, displaying all stored metadata.
*   **FR2.5:** The system shall provide a link/button to download the full-text file if the user has appropriate permissions.

#### 3.3 Feature: Publication Upload & Management
*   **FR3.1:** Contributor and Admin users shall have access to an "Upload Publication" interface.
*   **FR3.2:** The upload interface shall allow selection of a full-text file from the local filesystem.
*   **FR3.3:** Upon file selection, the system shall attempt to **automatically extract metadata** (e.g., title, authors, abstract from PDF/DOC) and pre-populate a submission form.
*   **FR3.4:** The user shall be able to review, modify, and supplement all metadata before final submission.
*   **FR3.5:** The system shall save the file to a secure storage location and the metadata to the database.
*   **FR3.6:** Contributor users shall be able to edit or delete publications they own.
*   **FR3.7:** Admin users shall be able to edit or delete any publication.

#### 3.4 Feature: Administrative Functions
*   **FR4.1:** The system shall provide an admin panel accessible only to Admin users.
*   **FR4.2:** Admins shall be able to view, filter, and manage all user accounts (FR1.2).
*   **FR4.3:** Admins shall be able to define access groups and assign users to groups.
*   **FR4.4:** Admins shall be able to set publication visibility (public, group-restricted, private) and manage permissions based on groups.
*   **FR4.5:** Admins shall be able to view system logs and statistics.

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements
*   The system should load search results and publication detail pages within 3 seconds under typical load (≤20 concurrent users).
*   File uploads should be handled efficiently for files up to 100MB.

#### 4.2 Safety & Security Requirements
*   User passwords must be hashed and salted before storage.
*   User sessions must be managed securely to prevent hijacking.
*   Direct file system access to uploaded documents must be controlled; downloads must be served through the application after checking authorization.
*   The system shall prevent SQL injection and cross-site scripting (XSS) attacks.

#### 4.3 Software Quality Attributes
*   **Maintainability:** The Ruby code shall be modular, well-commented, and follow community style guides.
*   **Reliability:** The system shall have an uptime goal of 99.5% during business hours.
*   **Usability:** The web interface shall be intuitive and consistent. Error messages shall be clear and guide the user toward resolution.

#### 4.4 Technical Constraints (Reiterated)
*   The application must be developed in **Ruby**.
*   The application **must not use a full-stack web framework** (e.g., Rails).
*   All generated web pages must be valid **W3C XHTML 1.0 Transitional**.
*   The application must be deployable on the Linux server **"Wilma."**
