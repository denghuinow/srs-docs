### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the NOAA Data Exploitation (NDE) System. It serves as a comprehensive description of the system's intended capabilities, constraints, and interfaces for stakeholders, developers, testers, and project managers. The primary audience includes the development team, NOAA operational staff, and system architects.

#### 1.2 Scope
The NDE System is a mission-critical data processing and distribution platform designed to receive, process, archive, and distribute environmental satellite data from the **NPOESS Preparatory Project (NPP)** and the **National Polar-orbiting Operational Environmental Satellite System (NPOESS)** missions. The system serves NOAA's operational weather forecasting and long-term climate monitoring communities by generating tailored data products, ensuring their long-term preservation, and facilitating secure distribution to authorized users.

**In-Scope:**
*   Ingest of raw and intermediate satellite data feeds from NPP/NPOESS missions.
*   Processing algorithms to generate NOAA-unique environmental data records (EDRs) and tailored products.
*   Automated archiving of final products to the Comprehensive Large Array-data Stewardship System (CLASS).
*   Secure distribution of products to NOAA operational centers (e.g., NCEP, NWS) and other authorized users via defined interfaces.
*   System monitoring, management, and reporting.

**Out-of-Scope:**
*   Development of satellite sensors or ground segment uplink capabilities.
*   Operation of the CLASS archive system (NDE is a contributor/client).
*   Development of end-user scientific analysis tools.
*   Direct public distribution of data (handled by downstream systems).

### 2. Overall Description

#### 2.1 Product Perspective
The NDE System is a major component within NOAA's satellite data processing infrastructure. It acts as a **middleware processing and distribution hub**, situated between upstream satellite data providers (e.g., the Integrated Program Office/IPO ground segment) and downstream consumers (operational users, CLASS archive).

**System Interfaces:**
*   **Upstream:** Receives data feeds via high-rate data links from the NPP/NPOESS ground stations.
*   **Downstream (Archive):** Pushes finalized products to the CLASS archive via a standardized ingest protocol (e.g., FTP over dedicated line).
*   **Downstream (Users):** Distributes products to users via push (e.g., NOAAPort, SBN) and pull (e.g., authenticated web portal, FTP) mechanisms.
*   **Management:** Provides a web-based administrative interface for monitoring and control.

#### 2.2 Product Functions
The core high-level functions of the NDE System are:
1.  **Data Ingest:** Reliably receive and perform initial quality checks on incoming satellite data streams.
2.  **Product Generation:** Execute processing algorithms to transform raw/level-0 data into NOAA-unique Level-1, Level-2, and tailored products.
3.  **Product Archiving:** Format, catalog, and transmit final products to the CLASS long-term archive for permanent preservation.
4.  **Product Distribution:** Disseminate products to authorized operational and climate users with appropriate latency and reliability.
5.  **System Management:** Provide tools for monitoring system health, job scheduling, error handling, and reporting.

#### 2.3 User Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Operational Forecaster** | Meteorologist at NCEP or NWS; requires low-latency data for numerical weather prediction. | Timely, reliable delivery of specific atmospheric profiles (temperature, moisture, ozone). |
| **Climate Researcher** | Scientist studying long-term trends; uses reprocessed data sets. | Access to consistent, well-documented, and complete historical data archives from CLASS. |
| **System Administrator** | IT staff responsible for NDE operations. | Robust monitoring, alerting, and control capabilities to maintain system availability. |
| **Data Product Manager** | NOAA staff who manages product algorithms and specifications. | Ability to update processing algorithms and validate new product versions. |

#### 2.4 Constraints
1.  **Regulatory:** The system must comply with all applicable **Federal Enterprise Architecture (FEA)** guidelines and **ESPC security procedures** for data handling, access control, and auditing.
2.  **Operational:** System availability for the core functions of ingest, generation, and distribution shall not be interrupted for more than **2 consecutive hours in any 24-hour period** (99.2% availability for these functions).
3.  **Performance:** The system architecture must be designed to support peak data volumes of **up to 8 Terabytes per day of input data and 16 Terabytes per day of output products** during the operational phase of NPOESS missions.
4.  **Architectural:** Must integrate with the existing CLASS archive system using its published APIs and protocols.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** Upstream data providers will deliver data in agreed-upon formats and schedules.
*   **Assumption:** CLASS archive will be available and have sufficient capacity to accept NDE products.
*   **Dependency:** Existence of secure, high-bandwidth network connections between NDE, data sources, CLASS, and user communities.
*   **Dependency:** Availability of validated scientific algorithms for product generation from NOAA algorithm teams.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Data Ingest (ING)
*   **ING-001:** The system shall ingest satellite data streams from designated NPP/NPOESS sources via high-speed data links (e.g., RDS, LDM).
*   **ING-002:** The system shall perform a checksum validation on all ingested data files to ensure data integrity.
*   **ING-003:** The system shall generate an acknowledgment receipt for successfully ingested data files and log all ingest transactions.

##### 3.1.2 Product Processing (PRO)
*   **PRO-001:** The system shall execute configured processing algorithms to generate NOAA-unique EDRs (e.g., atmospheric vertical temperature profiles, sea surface temperature) from raw or Level-0 data.
*   **PRO-002:** The system shall support the generation of "tailored" products, which are subsets or aggregated versions of standard EDRs for specific user groups.
*   **PRO-003:** The system shall tag all generated products with complete metadata, including product type, version, spatial/temporal coverage, processing timestamp, and data quality flags.
*   **PRO-004:** The system shall manage processing job queues, handle job failures with automatic retry logic (up to a configurable limit), and notify operators of critical failures.

##### 3.1.3 Product Archiving (ARC)
*   **ARC-001:** The system shall transmit all NOAA-unique final products to the CLASS archive.
*   **ARC-002:** The system shall format products and metadata according to the CLASS ingest specification before transmission.
*   **ARC-003:** The system shall verify successful transmission and ingestion into CLASS and maintain a local manifest of archived products.

##### 3.1.4 Product Distribution (DST)
*   **DST-001:** The system shall distribute products to pre-authorized users and systems based on subscription profiles.
*   **DST-002:** The system shall support multiple distribution methods, including:
    *   **DST-002.1:** Multicast/broadcast (e.g., NOAAPort) for low-latency operational data.
    *   **DST-002.2:** Secure pull-based access (e.g., HTTPS, SFTP) for on-demand retrieval.
*   **DST-003:** The system shall enforce access control, ensuring only users with proper credentials and authorization can receive specific products.

##### 3.1.5 System Management (MGT)
*   **MGT-001:** The system shall provide a web-based dashboard displaying real-time system health, ingest rates, processing backlog, and distribution status.
*   **MGT-002:** The system shall generate daily and monthly operational reports detailing data volumes, product counts, success/failure rates, and SLA compliance.
*   **MGT-003:** The system shall allow administrators to start, stop, pause, and reconfigure processing workflows.

#### 3.2 Non-Functional Requirements

##### 3.2.1 Performance Requirements
*   **PER-001:** The system shall sustain a peak **ingest rate** of 8 TB/day and a peak **output/distribution rate** of 16 TB/day.
*   **PER-002:** Latency from data receipt to availability for distribution for priority operational products shall be less than 30 minutes, 95% of the time.
*   **PER-003:** The system shall be able to concurrently process a minimum of 50 distinct product generation jobs.

##### 3.2.2 Availability & Reliability Requirements
*   **AVL-001:** The combined availability of the ingest, processing, and distribution functions shall be **≥ 99.2% in any 24-hour rolling period**, equating to no more than 2 hours of unscheduled downtime.
*   **REL-001:** The system shall achieve a Mean Time Between Critical Failures (MTBCF) of 1,000 hours.
*   **REL-002:** Data loss due to system failure shall not exceed 0.001% of total data volume processed annually.

##### 3.2.3 Security Requirements
*   **SEC-001:** The system shall comply with all **ESPC Moderate** confidentiality, integrity, and availability security controls.
*   **SEC-002:** All system access (administrative, user data pull) shall require authentication via PIV cards or equivalent strong credentials.
*   **SEC-003:** All data in transit to external systems (except public broadcast) shall be encrypted using FIPS 140-2 validated cryptographic modules.
*   **SEC-004:** The system shall maintain detailed audit logs of all user actions, data accesses, and configuration changes, retaining them for a minimum of 90 days.

##### 3.2.4 Scalability & Capacity Requirements
*   **SCA-001:** The system's storage architecture shall be scalable to hold a minimum of 45 days of raw input and generated product data online (based on peak volumes: ~360 TB input, ~720 TB output).
*   **SCA-002:** The processing architecture shall be designed to scale horizontally (adding nodes) to accommodate future mission growth without major architectural redesign.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Administrative Web Interface:** A secure (HTTPS), role-based web portal for system monitoring, reporting, and control.
*   **User Data Access Portal:** A secure (HTTPS) web interface for authorized users to browse, search, and download available data products.

#### 4.2 Hardware Interfaces
*   High-performance NAS or SAN storage subsystems for high-throughput data access.
*   Dedicated network interface cards (NICs) for segregated data ingest, processing, and distribution networks.

#### 4.3 Software Interfaces
*   **CLASS Ingest API:** SOAP/RESTful web service or protocol (e.g., FTPES with manifest) for product and metadata submission.
*   **Upstream Data Feed:** Interface defined by the NPP/NPOESS IPO (e.g., specific LDM configuration).
*   **Enterprise Authentication Service:** LDAP or Active Directory for user credential validation.

#### 4.4 Communication Interfaces
*   **Internal:** Gigabit Ethernet or higher for intra-system communication.
*   **External:** Dedicated high-bandwidth WAN connections (e.g., NOAA WAN) for data feeds, CLASS archive, and user distribution (NOAAPort, etc.). All external communications shall use TLS 1.2 or higher where applicable.

### 5. System Attributes

#### 5.1 Maintainability
*   The system shall be modular, with clear separation between ingest, processing, archive, and distribution components.
*   All custom software shall include comprehensive logging and shall be developed with accompanying design and API documentation.

#### 5.2 Portability
*   While initially deployed on a specific Linux operating system, core application software shall avoid OS-specific dependencies where possible to facilitate future migration.

#### 5.3 Fault Tolerance
*   Critical components (e.g., ingest servers, database) shall be deployed in an active-active or active-passive high-availability configuration to meet the 2-hour interruption constraint.
*   The system shall implement automated failover procedures for these critical components.
