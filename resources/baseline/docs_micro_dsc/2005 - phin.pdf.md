### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Public Health Investigation & Outbreak Management System (PHIOMS). The intended audience includes project stakeholders, software developers, testers, project managers, and system administrators. This SRS serves as the primary reference for system design, implementation, verification, and project scope management.

#### 1.2 Scope
PHIOMS is a comprehensive software application designed to support public health agencies in the end-to-end management of disease outbreaks and other significant health events. The system will enable the collection, linkage, analysis, and secure exchange of investigation data. It is scoped to be a configurable platform adaptable to various event types (e.g., infectious disease, foodborne illness, environmental hazard) without requiring core code changes.

**In-Scope:**
*   Configuration-driven data model management for cases, contacts, exposures, specimens, and treatments.
*   Relationship mapping and visualization for contact tracing and exposure networks.
*   Secure, standards-based data import/export with external public health systems.
*   Role-based access control and comprehensive audit logging.
*   Reporting and dashboarding for epidemiological analysis.
*   System administration interfaces for configuration management.

**Out-of-Scope:**
*   Direct patient-facing portals or public health education websites.
*   Laboratory Information Management System (LIMS) functionality.
*   Billing or financial management modules.
*   Real-time geospatial mapping services (though it must support location data for integration with such services).

### 2. Overall Description

#### 2.1 Product Perspective
PHIOMS is envisioned as a new, standalone system that will integrate into the existing public health IT ecosystem. It must interoperate with legacy surveillance systems, electronic lab reporting (ELR) systems, and immunization information systems (IIS) via standard interfaces.

#### 2.2 Product Functions (Summary)
1.  **Configurable Data Management:** Create and modify data collection forms and entities for different health events.
2.  **Core Investigation Workflow:** Record and link data for cases, contacts, exposures, specimens, and treatments throughout an investigation lifecycle.
3.  **Relationship & Network Analysis:** Define and visualize relationships between investigation entities to trace transmission chains.
4.  **Interoperability:** Securely send and receive investigation data using HL7 FHIR and other public health standards.
5.  **Reporting & Analytics:** Generate standard and ad-hoc reports, statistics, and dashboards.
6.  **Security & Administration:** Manage users, roles, permissions, and system configurations.

#### 2.3 User Characteristics
| User Class | Expertise | Key Responsibilities |
| :--- | :--- | :--- |
| **Field Investigator** | Moderate computer skill, high domain expertise. | Enter case/contact interviews, link exposures, initiate follow-ups. |
| **Epidemiologist** | High analytical skill, moderate computer skill. | Analyze data, define event configurations, generate reports, interpret trends. |
| **System Administrator** | High technical skill. | Manage user accounts, system configuration, backups, and integrations. |
| **Public Health Official** | Varied computer skill, management focus. | View dashboards, high-level reports, and outbreak status summaries. |
| **External System** | Machine interface. | Automated data exchange via API. |

#### 2.4 Constraints
1.  **Regulatory:** Must comply with HIPAA, 42 CFR Part 2, and relevant state public health data privacy laws.
2.  **Technical:** Data exchange must support HL7 FHIR and/or CDC PHIN standards.
3.  **Business:** The system must be operational with 99.5% availability during business hours and support on-call access for emergencies.
4.  **Implementation:** The data model and UI must be configurable by authorized epidemiologists without developer intervention for new event types.

#### 2.5 Assumptions and Dependencies
*   Users will have appropriate training for their role.
*   Partner health systems will have the capability to send/receive data via supported standards.
*   The system will be hosted in a secure, compliant cloud or government data center environment.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Configuration Management (CONF)
*   **CONF-1:** The system shall provide an administrative interface for authorized users to define new **Event Types** (e.g., "COVID-19", "Salmonella").
*   **CONF-2:** For each Event Type, authorized users shall be able to dynamically define **Entities** (e.g., add "Employer" as a new entity related to a Case).
*   **CONF-3:** For each Entity, authorized users shall be able to define custom **Data Fields** (type, validation rules, optional/mandatory status).
*   **CONF-4:** The system shall allow the configuration of **Workflow States** (e.g., Suspect, Probable, Confirmed, Closed) and rules for transitioning between them.

##### 3.1.2 Core Data Management (DATA)
*   **DATA-1:** The system shall allow users to create, read, update, and deactivate (with audit trail) records for the core entities: **Case, Contact, Exposure, Specimen, Treatment**.
*   **DATA-2:** The system shall enforce referential integrity and allow users to **create explicit linkages** between records (e.g., link a Contact record to a source Case record).
*   **DATA-3:** The system shall provide a **unified timeline or narrative view** for any person (Case/Contact), showing all related events, interviews, lab results, and status changes.

##### 3.1.3 Relationship Tracing (TRACE)
*   **TRACE-1:** The system shall allow users to define **relationship types** between entities (e.g., "Household Contact of", "Attended Same Event as", "Healthcare Provider for").
*   **TRACE-2:** The system shall provide a **visual network graph** to display relationships between Cases, Contacts, and Exposures.
*   **TRACE-3:** The graph view shall allow interactive exploration (zoom, pan, click for details).

##### 3.1.4 Interoperability (INTEROP)
*   **INTEROP-1:** The system shall provide a secure, standards-based **API** for data exchange.
*   **INTEROP-2:** The system shall be capable of **importing data** in HL7 FHIR format to create or update investigation records.
*   **INTEROP-3:** The system shall be capable of **exporting data** in HL7 FHIR format for consumption by partner systems (e.g., state health department repositories).
*   **INTEROP-4:** All data exchanges shall be logged with source, destination, timestamp, and record count.

##### 3.1.5 Reporting & Analysis (REPORT)
*   **REPORT-1:** The system shall provide a library of **standard epidemiological reports** (e.g., line lists, incidence over time, attack rates).
*   **REPORT-2:** The system shall provide a **dashboard** with key metrics (total cases, active investigations, contacts monitored).
*   **REPORT-3:** Authorized users shall be able to create and save **ad-hoc queries** based on configurable data fields.

##### 3.1.6 Security & Administration (SEC)
*   **SEC-1:** The system shall implement **RBAC**. Access to functions and data shall be determined by the user's role(s).
*   **SEC-2:** All user interactions with PHI (Create, Read, Update, Delete, Export) shall be recorded in an **immutable audit log**.
*   **SEC-3:** The system shall support **multi-factor authentication** (MFA) for all user accounts.
*   **SEC-4:** Data shall be **encrypted at rest** and **in transit** using industry-standard protocols (AES-256, TLS 1.2+).

#### 3.2 Non-Functional Requirements

##### 3.2.1 Security
*   The system shall undergo annual third-party penetration testing.
*   The system shall support segregation of duties (e.g., a configurer cannot also be an auditor).
*   Session timeout shall not exceed 15 minutes of inactivity.

##### 3.2.2 Performance
*   The system shall support **200 concurrent users** without significant degradation in response time.
*   **95% of all UI interactions** shall complete in less than 2 seconds.
*   **Bulk data exports** of up to 10,000 records shall be generated within 5 minutes.

##### 3.2.3 Availability
*   The system shall be available for use **99.5% of the time during core business hours (8 AM - 8 PM local time)**.
*   Scheduled maintenance shall be communicated at least 72 hours in advance.

##### 3.2.4 Usability
*   The system shall comply with **WCAG 2.1 AA** guidelines for accessibility.
*   Critical public health workflows (e.g., entering a new case) shall be completable with minimal training (<30 minutes).

##### 3.2.5 Data Integrity
*   The system shall maintain a complete version history for all records, enabling "view as of date" functionality.
*   Data validation rules defined in configuration (CONF-3) shall be enforced at the application and database levels.
