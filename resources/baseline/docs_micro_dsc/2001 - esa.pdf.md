### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the ASPERA-3 Data Processing and Archiving System (ADPAS). The primary purpose of this system is to process, archive, and disseminate telemetry data from the ASPERA-3 instrument and ancillary data from the Mars Express spacecraft for the science team and the public archive. This document serves as a comprehensive guide for developers, testers, project managers, and stakeholders.

#### 1.2 Scope
The ADPAS will:
*   Acquire raw telemetry data from the European Space Operations Centre (ESOC).
*   Process science, engineering, and ancillary (orbit/attitude) data into standardized Interplanetary Data Format System (IDFS) data sets.
*   Manage access to processed data, providing secure access for the science team and preparing data for public release.
*   Ensure the validated ASPERA-3 IDFS data sets are submitted to the NASA Planetary Data System (PDS) within a strict six-month deadline from data acquisition.
*   Operate exclusively within a UNIX-based environment.

**Out of Scope:**
*   Development of the IDFS standard itself.
*   Operation of the ESOC data distribution servers.
*   Long-term archival storage at PDS (only submission interface).
*   Data analysis tools for end-users.

### 2. Overall Description

#### 2.1 Product Perspective
ADPAS is a standalone data processing system. It interfaces externally with:
*   **ESOC Data Servers:** As the source of raw telemetry.
*   **Science Team Users:** Via a password-protected web interface for data access.
*   **NASA PDS:** As the final archive for validated public data sets.
*   **Potential Local Storage Systems:** For interim data holding.

The system acts as the central data pipeline between raw mission data and the scientific community.

#### 2.2 Product Functions
The core high-level functions of ADPAS are:
1.  **Data Acquisition:** Automated, scheduled retrieval of ASPERA-3 and MEX ancillary telemetry packets from ESOC servers.
2.  **Data Processing:** Conversion of raw telemetry into calibrated, time-ordered IDFS data sets. This includes science data processing, engineering data extraction, and merging with ancillary orbit/attitude data.
3.  **Data Validation & Quality Control:** Automated checks and manual review tools to ensure data meets IDFS and PDS standards before archiving.
4.  **Data Management & Archiving:** Organized storage of raw, intermediate, and final IDFS data sets with associated metadata.
5.  **Data Access & Delivery:** Provision of a secure web portal for Co-Is to access data and implementation of defined mechanisms to deliver final data sets to Co-Is.
6.  **PDS Submission:** Packaging and transmission of validated IDFS data sets to the NASA PDS archive.

#### 2.3 User Characteristics
| User Class | Expertise | Key Tasks |
| :--- | :--- | :--- |
| **System Administrator** | Expert in UNIX system administration, networking, and security. | Install, maintain, backup, and secure the ADPAS server and software. |
| **Data Operations Engineer** | Trained on ADPAS procedures, understands IDFS/PDS formats. | Monitor automated processing, perform manual quality control, manage data flow, execute PDS submission. |
| **Science Team Co-Investigator** | Scientist, non-expert in system operations. | Browse, search, and download processed IDFS data sets via the web interface. |
| **External User (Public)** | General public or researcher. | Access and download publicly released data sets (post PDS submission). |

#### 2.4 Constraints
1.  **Operating System:** The entire system must be developed and deployed on a **UNIX-based** operating system (e.g., Linux, Solaris).
2.  **Security Constraint:** Access to non-public data (e.g., pre-PDS release) via the web server **must be password-protected** using a secure authentication mechanism.
3.  **Project Milestone:** The final data delivery mechanisms (e.g., FTP, physical media, dedicated server) from ADPAS to individual Co-Investigators **must be formally defined and agreed upon six months prior to the Mars Express launch**.
4.  **Regulatory Constraint:** Submission of validated ASPERA-3 IDFS data sets to the NASA PDS is mandatory and must occur **within six months of data acquisition**.

#### 2.5 Assumptions and Dependencies
*   ESOC will provide stable, documented interfaces for telemetry data acquisition.
*   The IDFS and PDS format specifications will be stable during the development and operational lifecycle of ADPAS.
*   Necessary computational resources (server, storage) will be available and funded.
*   The six-month PDS delivery deadline is driven by project policy and is assumed to be fixed.

### 3. Specific Requirements

#### 3.1 Functional Requirements

**FR1: Data Acquisition**
*   **FR1.1:** The system shall connect to specified ESOC servers using the protocol defined in the ESOC ICD.
*   **FR1.2:** The system shall automatically acquire new ASPERA-3 science and engineering telemetry files as they become available at ESOC.
*   **FR1.3:** The system shall automatically acquire Mars Express orbit and attitude (ancillary) data files as they become available.
*   **FR1.4:** The system shall verify data integrity (e.g., via checksum) upon acquisition and log any transfer failures.

**FR2: Data Processing**
*   **FR2.1:** The system shall process raw ASPERA-3 telemetry into calibrated science data products in IDFS format.
*   **FR2.2:** The system shall extract engineering/housekeeping data from telemetry and store it in IDFS format.
*   **FR2.3:** The system shall merge processed science data with corresponding MEX orbit and attitude ancillary data to create time-synchronized IDFS data sets.
*   **FR2.4:** The system shall generate all mandatory IDFS metadata and labels for each data set.

**FR3: Data Validation & Quality Control (QC)**
*   **FR3.1:** The system shall perform automated validation checks on processed IDFS data sets for format compliance (IDFS and PDS).
*   **FR3.2:** The system shall provide a tool/interface for the Data Operations Engineer to manually review data quality, view plots/summaries, and flag data sets.
*   **FR3.3:** The system shall maintain a processing log and QC status for each data set (e.g., "raw", "processed", "validated", "rejected").

**FR4: Data Management & Archiving**
*   **FR4.1:** The system shall maintain a structured directory hierarchy for raw, processing, and final IDFS data sets.
*   **FR4.2:** The system shall implement a database or catalog to track all data sets, their metadata, processing history, and location.
*   **FR4.3:** The system shall protect against unauthorized deletion or modification of validated and archived data sets.

**FR5: Data Access & Delivery**
*   **FR5.1:** The system shall provide a web server interface for data access.
*   **FR5.2:** The web interface shall require username/password authentication for accessing any data not yet publicly released via PDS. **(Links to Key Constraint)**
*   **FR5.3:** Authenticated users shall be able to search/browse data sets by time range, data type, and quality flag.
*   **FR5.4:** Authenticated users shall be able to download selected IDFS data sets.
*   **FR5.5:** The system shall implement the final data delivery mechanism (e.g., automated batch transfers) to Co-Investigators as defined per project milestone. **(Links to Key Constraint)**

**FR6: PDS Submission**
*   **FR6.1:** The system shall package validated IDFS data sets into the specific format required by the NASA PDS.
*   **FR6.2:** The system shall submit the packaged data to the PDS via the designated interface (e.g., FTP, API).
*   **FR6.3:** The system shall initiate the submission process for a data set **no later than six months after its acquisition timestamp**. **(Links to Key Constraint)**
*   **FR6.4:** The system shall confirm successful receipt by PDS and log the submission status.

#### 3.2 External Interface Requirements

**3.2.1 User Interfaces**
*   **Web Interface (UI-1):** A clean, professional web portal for data search, browse, and download. Must include a secure login page.

**3.2.2 Hardware Interfaces**
*   **HI-1:** The system must run on standard UNIX server hardware with sufficient CPU, RAM, and significant redundant storage for raw and processed data.

**3.2.3 Software Interfaces**
*   **SI-1 (ESOC):** Protocol: [e.g., SFTP, CCSDS File Delivery Protocol]. Data Format: [e.g., raw packet files, SPICE kernels].
*   **SI-2 (PDS):** Protocol: [e.g., FTP/S, PDS Submission API]. Data Format: PDS-compliant bundles with labels.
*   **SI-3 (Internal):** The processing pipeline will use the official IDFS software libraries (version [X.Y]) for all IDFS read/write operations.

**3.2.4 Communication Interfaces**
*   **CI-1:** Secure shell (SSH) for system administration.
*   **CI-2:** HTTPS (TLS 1.2+) for all web server communications.

#### 3.3 Performance Requirements
*   **PR1:** The system shall be capable of processing one day's worth of nominal ASPERA-3 and MEX data within 4 hours of acquiring all necessary inputs.
*   **PR2:** The web interface shall return search results to an authenticated user within 5 seconds for 95% of queries.
*   **PR3:** The data acquisition module shall retry failed transfers from ESOC at least 3 times before raising a critical alert.

#### 3.4 Design Constraints
*   **DC1:** The system shall be developed in a language and framework compatible with standard UNIX environments (e.g., C, Python, Java).
*   **DC2:** All system components (acquisition, processing, web server) shall be capable of running on a single server or be easily distributable across multiple servers.
*   **DC3:** The system shall not require a graphical desktop environment for its core processing operations (must be operable via command line/scripts).

#### 3.5 Security Requirements
*   **SR1:** User passwords shall be stored using a strong, salted hashing algorithm (e.g., bcrypt, Argon2).
*   **SR2:** All access to non-public data shall be controlled by role-based authentication (e.g., Co-I, Data Operator, Admin).
*   **SR3:** System administrative access (SSH) shall be restricted to a defined set of IP addresses or require key-based authentication.

#### 3.6 Data Management Requirements
*   **DMR1:** The system shall retain raw telemetry files for a minimum of 2 years after successful PDS submission of the corresponding processed data.
*   **DMR2:** All processing steps and parameter versions used to create a final IDFS data set shall be recorded in its metadata.
