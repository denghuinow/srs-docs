## **1. Introduction**

### **1.1 Purpose**
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the software component of the I-15 Reversible Lane Control System (RLCS) Replacement project. It serves as a formal agreement between the stakeholders (State DOT) and the development team, providing a comprehensive description of the system's intended capabilities, constraints, and interfaces. This document will be used as the foundation for system design, implementation, testing, and project management.

### **1.2 Document Conventions**
*   **Requirements IDs:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a desirable but not mandatory feature.
*   **Formatting:** User interface elements are denoted in *italics*. System messages or code are in `monospace`.

### **1.3 Project Scope**
The scope of this project is to design, develop, test, and deploy a new software system to replace the aging I-15 Reversible Lane Control System. The software will enable traffic management operators to safely and efficiently open and close reversible lanes for peak traffic flows and special events. The system includes a central control application, communication protocols with field devices, and a robust database for operations and reporting.

**In-Scope:**
*   Central Control Server Software with a Graphical User Interface (GUI).
*   Communication middleware for interfacing with field controllers (gates, signs, pop-up barriers).
*   Logic to execute pre-defined and ad-hoc lane control sequences.
*   System health monitoring, alerting, and reporting.
*   Data persistence for configuration, logs, and event history.

**Out-of-Scope:**
*   Physical fabrication and installation of field hardware (gates, signs, controllers).
*   Design of underlying network infrastructure.
*   Development of firmware for field controllers (software will interface with existing controller APIs).

## **2. Overall Description**

### **2.1 Product Perspective**
The new RLCS software is a component within the larger State DOT Traffic Management Center (TMC) ecosystem. It will replace a legacy standalone system. The new system must integrate with existing TMC networks and may share data with other systems (e.g., traffic camera feeds, incident management software) via defined interfaces.

### **2.2 Product Functions**
The core functions of the RLCS software are:
1.  **Real-Time Monitoring:** Provide a continuous, accurate status of all connected field devices.
2.  **Device Control:** Send commands to individual or grouped field devices to change their state (e.g., lower gate, change sign message).
3.  **Sequence Execution:** Automatically execute stored sequences of commands to transition the reversible lane facility between operational states (e.g., "Open Northbound," "Close All," "Open Southbound").
4.  **Safety Interlocking:** Enforce operational rules to prevent conflicting lane configurations.
5.  **User Interface:** Offer an intuitive, graphical interface for operators to monitor, command, and report on the system.
6.  **Data Management:** Securely store configuration, event logs, and operator actions for audit and analysis.

### **2.3 User Classes and Characteristics**
*   **TMC Operator:** Primary user. Trained in traffic management procedures. Uses the system for daily operations and during incidents. Requires a clear, reliable, and fast interface.
*   **System Administrator:** Configures system parameters, manages user accounts, performs backups, and reviews system health logs. Has advanced technical knowledge.
*   **Supervisor/Engineer:** Accesses historical reports and data analytics to assess system performance and plan operations. Needs robust reporting tools.

### **2.4 Operating Environment**
*   **Hardware:** The software shall run on standard TMC server hardware (rack-mounted servers) and operator workstations (PCs with dual monitors).
*   **Software:** The central application shall be compatible with the TMC's standard operating system (e.g., Windows Server 20XX, Red Hat Enterprise Linux). It shall support standard web browsers for client access if using a web-based GUI.
*   **Field Controllers:** The software shall communicate with field programmable logic controllers (PLCs) or similar devices via a standard industrial protocol (e.g., Modbus TCP/IP, DNP3) over a wired fiber-optic network.

### **2.5 Design and Implementation Constraints**
1.  **NFR-CONST-001:** The system shall be available 24 hours per day, 7 days per week, with a target uptime of 99.9%.
2.  **FR-CONST-002:** The software shall implement a safety interlock that physically prevents the system from opening an entrance for one direction of travel if any entrance for the opposite direction is already open.
3.  **NFR-CONST-003:** The application software and all critical operational data (e.g., current device states, active sequence) residing in field controllers must be stored in non-volatile memory to survive a power cycle.
4.  The system must comply with State DOT cybersecurity policies for critical infrastructure.

### **2.6 Assumptions and Dependencies**
*   It is assumed that field devices and their local controllers are functional and provide a stable communication interface.
*   The project depends on the timely provision of network access and API documentation from field controller vendors.
*   System availability is dependent on the underlying power and network infrastructure maintained by the DOT.

## **3. System Features and Requirements**

### **3.1 Field Device Monitoring and Control**
#### **3.1.1 Description**
The system shall provide continuous monitoring and discrete control of all field devices from the central control station.

#### **3.1.2 Requirements**
*   **FR-010:** The system shall poll or receive updates from all configured field controllers at an interval not to exceed 5 seconds to determine device status (e.g., `Gate_1_Status: OPEN/CLOSED/FAULT`, `Sign_5_Message: "USE LEFT LANE"`).
*   **FR-011:** The GUI shall display the real-time status of all devices on a schematic map of the reversible lane facility.
*   **FR-012:** An operator shall be able to select any individual device or a predefined group of devices from the GUI and issue a direct control command (e.g., "Open Gate," "Set Sign to Blank").
*   **FR-013:** The system shall provide immediate visual and auditory confirmation in the GUI upon successful execution or failure of a direct control command.

### **3.2 Operational Sequence Execution**
#### **3.2.1 Description**
The system shall store and execute predefined sequences of commands to automate the opening and closing of the facility.

#### **3.2.2 Requirements**
*   **FR-020:** The system shall allow an authorized user to create, modify, and delete operational sequences (e.g., "Morning Northbound Opening," "Event Closure").
*   **FR-021:** A sequence shall consist of an ordered list of steps, each containing a command (or set of commands) and a configurable delay before the next step.
*   **FR-022:** The GUI shall provide a dedicated control panel with buttons to initiate any stored sequence.
*   **FR-023:** During sequence execution, the GUI shall display a progress indicator, the current step, and the next step.
*   **FR-024:** An operator shall have the authority to pause, resume, or abort any sequence in progress.

### **3.3 Safety Interlock System**
#### **3.3.1 Description**
A critical software-based interlock shall prevent unsafe lane configurations.

#### **3.3.2 Requirements**
*   **FR-030:** The system shall maintain a definitive state variable for the facility's operational direction (`NORTHBOUND`, `SOUTHBOUND`, `CLOSED`).
*   **FR-031:** Before executing any command or sequence step that would open an entrance, the system shall check the current facility direction state.
*   **FR-032:** If the facility direction is `CLOSED`, the system shall allow the opening command and update the direction state accordingly.
*   **FR-033:** **FR-CONST-002:** If the facility direction is `NORTHBOUND`, the system shall reject any command to open a southbound entrance. The GUI shall display a clear error: "**Safety Interlock Engaged: Cannot open Southbound entrance while facility is set for Northbound traffic.**"
*   **FR-034:** The interlock logic shall be evaluated at both the central software level and, where possible, within the field controller logic as a redundant safeguard.

### **3.4 User Interface**
#### **3.4.1 Description**
The system shall provide a graphical user interface for all monitoring and control activities.

#### **3.4.2 Requirements**
*   **FR-040:** The main interface shall be a color-coded, schematic map of the reversible lane facility, showing gates, signs, and pop-up barriers in their real-time state.
*   **FR-041:** The system shall provide a dedicated *Alarms and Events* panel that lists all system faults, interlock violations, and operator actions in chronological order.
*   **FR-042:** The GUI shall include a *Reporting Module* that allows users to generate pre-formatted reports (e.g., "Daily Operations Log," "System Fault Summary for Month") and export them to PDF or CSV format.

### **3.5 Data Persistence and Reliability**
#### **3.5.1 Description**
The system shall ensure data integrity and availability as per key constraints.

#### **3.5.2 Requirements**
*   **FR-050:** All system events, operator actions, and device state changes shall be timestamped and logged to a central, redundant database.
*   **FR-051:** **NFR-CONST-003:** The software shall be designed such that the operational logic and critical state variables sent to field controllers are stored by the controllers in non-volatile memory. The central system shall have a procedure to verify and, if necessary, restore this configuration upon controller reboot.
*   **FR-052:** The central database shall be automatically backed up daily, with backups retained for a minimum of one year.

## **4. Non-Functional Requirements**

### **4.1 Performance Requirements**
*   **NFR-PERF-001:** The system GUI shall update the status of all field devices within 2 seconds of the data being received at the server.
*   **NFR-PERF-002:** The system shall be capable of sending a control command and receiving a status confirmation from any field device within 5 seconds under normal network conditions.

### **4.2 Safety Requirements**
*   **FR-CONST-002** (reiterated) is the primary safety requirement. All other requirements support this goal.
*   **NFR-SAFE-001:** The system shall implement role-based access control (RBAC). Only users with the "Operator" or higher role shall be permitted to issue control commands.

### **4.3 Availability & Reliability**
*   **NFR-CONST-001** (reiterated): 24/7/365 availability.
*   **NFR-REL-001:** The mean time between failures (MTBF) for the software system shall be greater than 10,000 hours.
*   **NFR-REL-002:** The system shall support a failover configuration for the central server, allowing a standby server to assume control within 5 minutes of a primary server failure.

### **4.4 Security Requirements**
*   **NFR-SEC-001:** All user access shall require authentication via username and password, compliant with DOT password policy.
*   **NFR-SEC-002:** All communication between the central server and field controllers shall be encrypted.

### **4.5 Maintainability**
*   **NFR-MAIN-001:** The system shall allow for the addition, removal, or reconfiguration of field devices without requiring a full software recompilation, using configuration files or a management GUI.
