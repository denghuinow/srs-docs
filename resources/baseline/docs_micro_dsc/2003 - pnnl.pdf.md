### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the HVAC Fault Detection and Diagnostics (FDD) System. The primary purpose of this software is to automatically detect, identify, and report operational and performance faults within chiller and cooling tower subsystems. This document is intended for use by stakeholders, project managers, developers, testers, and end-users to ensure a common understanding of the system to be developed.

#### 1.2 Document Conventions
*   **Requirements:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** The terms "MUST," "MUST NOT," "REQUIRED," "SHALL," "SHALL NOT," "SHOULD," "SHOULD NOT," "RECOMMENDED," "MAY," and "OPTIONAL" are to be interpreted as described in IETF RFC 2119.
*   **Formatting:** Code, file names, and user interface elements are presented in `inline code` blocks.

#### 1.3 Intended Audience and Reading Suggestions
*   **Project Sponsors & Managers:** Focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (External Interface Requirements).
*   **Developers & Architects:** Focus on Sections 3 (System Features), 4 (Data Requirements), and 6 (Non-Functional Requirements).
*   **QA Testers:** Focus on all sections, particularly Section 3 to derive test cases.
*   **End-Users (Operators/Technicians):** Focus on Sections 2.2 (User Classes) and 3.1, 3.3 (specific features).

#### 1.4 Project Scope
The scope of this project is the development of a desktop software application that:
1.  Ingests sensed (real-time or historical) and fixed (equipment model, design parameters) data related to HVAC chiller and cooling tower subsystems.
2.  Executes proprietary diagnostic algorithms to detect predefined operational faults.
3.  Presents clear diagnostic results to the user via a graphical interface.
4.  Logs all results, including fault details and timestamps, to a persistent local database.
5.  Is designed to be extensible for future diagnostic modules for other HVAC subsystems (e.g., air handlers, pumps).
6.  Is initially targeted for deployment on Microsoft Windows operating systems.

**Out of Scope:**
*   Development or manufacturing of physical sensor hardware.
*   Direct, low-level control of HVAC equipment (e.g., closing valves, shutting down compressors).
*   Network-based data acquisition from Building Management Systems (BMS) in Version 1.0 (data input is via local files or defined acquisition device APIs).
*   Mobile or web-based client applications.
*   Diagnostic algorithms for HVAC subsystems other than chillers and cooling towers.

### 2. Overall Description

#### 2.1 Product Perspective
The HVAC FDD System is a standalone desktop application. It acts as an intermediary analysis engine between data sources (sensors, data loggers, BMS exports) and the end-user. The system architecture is modular, with a clear separation between the data ingestion layer, the diagnostic engine, and the user interface/persistence layer to facilitate future expansion.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Building Operator** | Monitors daily building system performance. Has general HVAC knowledge but is not a specialist. | High-level fault alerts, clear descriptions, recommended actions, simple data import. |
| **Service Technician** | Diagnoses and repairs specific HVAC equipment. Has deep mechanical/electrical knowledge. | Detailed fault data (cause, location), historical logs, ability to input manual test readings. |
| **System Administrator** | Installs, configures, and maintains the software on a workstation. IT-literate. | Straightforward installation, configuration of data source paths, system resource management. |

#### 2.3 Operating Environment
*   **Software:** Microsoft Windows 10 (64-bit) or Windows 11.
*   **Hardware:** Standard workstation or laptop meeting minimum specifications for .NET Framework 4.8 or .NET 6/8 runtime.
*   **Dependencies:** Required runtime libraries (to be specified by development team). Local file system read/write permissions.

#### 2.4 Design and Implementation Constraints
1.  `C-001`: The software **MUST** be compatible with and run on Microsoft Windows-compatible operating systems for the initial release.
2.  `C-002`: The diagnostic engine **MUST NOT** execute if any required input data point for the selected algorithm is null, missing, or invalid. The system shall halt processing and notify the user.
3.  `C-003`: The software architecture **SHALL** be modular to allow for the future integration of additional diagnostic algorithms for other HVAC subsystems (e.g., boilers, VAV boxes) without major refactoring of the core application.
4.  `C-004`: All diagnostic results **MUST** be stored permanently in a local, structured database (e.g., SQLite, Microsoft SQL Server Express).

#### 2.5 Assumptions and Dependencies
*   **Assumption:** Input data files (batch) will be provided in a pre-agreed, structured format (e.g., CSV, JSON).
*   **Assumption:** Real-time data acquisition devices will provide a compatible software interface (API/DLL) for data polling.
*   **Dependency:** Availability and correctness of the underlying fault detection algorithms and their mathematical models.
*   **Dependency:** End-user workstations will have sufficient processing power to run diagnostic calculations in a timely manner.

### 3. System Features

#### 3.1 Fault Detection and Identification
**Description:** This is the core feature where the system applies diagnostic logic to input data to identify specific faults.

**Requirements:**
*   `FR-101`: The system **SHALL** execute diagnostic algorithms for a predefined list of chiller faults (e.g., refrigerant undercharge, condenser fouling, reduced water flow).
*   `FR-102`: The system **SHALL** execute diagnostic algorithms for a predefined list of cooling tower faults (e.g., fan belt slippage, fouled fill, low water level).
*   `FR-103`: For each detected fault, the system **MUST** generate a result containing, at minimum:
    *   A unique fault identifier.
    *   A plain-language fault description.
    *   The most probable root cause.
    *   The specific subsystem and component location (e.g., "Chiller #1 - Condenser Tube Bundle").
    *   A severity or confidence indicator.
    *   The date and time of the analysis.

#### 3.2 Data Input and Validation
**Description:** The system must accept data from configured sources and ensure it is valid and complete before processing.

**Requirements:**
*   `FR-201`: The system **SHALL** provide a mechanism to configure and connect to real-time data acquisition devices (e.g., via a provided driver or API).
*   `FR-202`: The system **SHALL** provide a mechanism to import and read data from batch files (e.g., CSV, JSON) stored on the local filesystem.
*   `FR-203`: The system **MUST** validate all input data points against defined data types, ranges, and units before passing them to the diagnostic engine.
*   `FR-204`: The system **MUST** check for the completeness of the required dataset as defined by the selected diagnostic algorithm. If data is missing, `FR-205` is triggered.
*   `FR-205`: If validation fails (`FR-203`) or data is incomplete (`FR-204`), the system **SHALL** immediately halt the diagnostic process and display a clear error message to the user listing the problematic data points.

#### 3.3 Results Display and Storage
**Description:** Diagnostic results must be presented to the user and archived for historical review.

**Requirements:**
*   `FR-301`: The system **SHALL** display the results of the most recent diagnostic run in a clear, tabular, or dashboard-style view within the main application window.
*   `FR-302`: The user **SHALL** be able to filter and sort the displayed results by criteria such as date, severity, subsystem, and fault type.
*   `FR-303`: The system **MUST** permanently store every diagnostic result, including all details specified in `FR-103`, in a local database.
*   `FR-304`: The system **SHALL** provide a dedicated interface or view to query, browse, and export historical diagnostic results from the database.
*   `FR-305`: The system **SHOULD** allow the user to generate a printable or exportable (e.g., PDF, CSV) report for a selected fault or time period.

### 4. Data Requirements

#### 4.1 Input Data Schema
The system will require two primary categories of input data:
1.  **Sensed Data:** Time-series values from sensors (e.g., temperatures, pressures, flows, power draws).
2.  **Fixed Data:** Static equipment properties and design parameters (e.g., rated capacity, design temperatures, pump curves, refrigerant type).

A detailed data point list (DP-ID, Description, Units, Valid Range) will be provided as a separate appendix.

#### 4.2 Output Data Schema
The primary output is the **Fault Record**, which shall be stored in the `FaultLog` table with the following structure:
```sql
FaultLog {
    FaultID          INTEGER PRIMARY KEY,
    Timestamp        DATETIME,
    Subsystem        TEXT,       -- e.g., "Chiller", "CoolingTower"
    EquipmentID      TEXT,       -- e.g., "CH-1", "CT-2"
    FaultCode        TEXT,       -- Internal algorithm code
    Description      TEXT,
    ProbableCause    TEXT,
    Location         TEXT,
    Severity         INTEGER,    -- e.g., 1 (Low) to 3 (Critical)
    Confidence       FLOAT,      -- Algorithm confidence score (0.0-1.0)
    InputDataSnapshot TEXT       -- JSON or reference to raw input data used
}
```

### 5. External Interface Requirements

#### 5.1 User Interfaces
*   **UI-01:** A main graphical user interface (GUI) with:
    *   A menu bar and toolbar for core functions.
    *   A configuration panel for data source settings.
    *   A central dashboard/results display area.
    *   A status bar showing system status (e.g., "Ready", "Processing", "Error").
*   **UI-02:** Modal dialog windows for:
    *   Configuring new data sources (file paths, device connections).
    *   Initiating a diagnostic run and selecting algorithms.
    *   Viewing detailed historical logs.

#### 5.2 Hardware Interfaces
*   **HI-01:** The software must interface with supported real-time data acquisition devices via their provided Windows-compatible communication protocols (e.g., Modbus TCP/IP, BACnet IP, proprietary USB/Serial APIs).

#### 5.3 Software Interfaces
*   **SI-01:** The application will require a local database library (e.g., Entity Framework Core with SQLite provider).
*   **SI-02:** For file import, the application will use standard .NET file I/O and parsing libraries (e.g., for CSV, JSON).

#### 5.4 Communications Interfaces
*   **CI-01:** Version 1.0 does not require network communication for core functionality. Future versions may include HTTP/REST APIs for cloud data syncing.

### 6. Non-Functional Requirements

#### 6.1 Performance Requirements
*   `NFR-101`: For a standard dataset (up to 1000 data points), the diagnostic algorithm execution **SHALL** complete within 10 seconds on reference hardware.
*   `NFR-102`: The user interface **SHALL** remain responsive during data processing (non-blocking UI).

#### 6.2 Safety Requirements
*   `NFR-201`: The software **MUST NOT** send any control signals to HVAC equipment. It is for monitoring and diagnosis only.

#### 6.3 Security Requirements
*   `NFR-301`: Access to the historical fault log and configuration settings **MAY** be protected by a local username/password mechanism (TBD).
*   `NFR-302`: The local database file **SHOULD** not store data in plaintext if it contains sensitive building information.

#### 6.4 Software Quality Attributes
*   **Maintainability:** Code shall be well-documented and follow a modular design to satisfy constraint `C-003`.
*   **Reliability:** The application shall be able to recover gracefully from unexpected disconnections of real-time data sources.
*   **Usability:** A trained building operator shall be able to perform a standard diagnostic run with less than 5 minutes of instruction.
