## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the requirements for the Fault-Tolerant System Services (FTSS) software component of the X-38 Crew Return Vehicle's Flight Critical Computer (FCC). The FTSS provides a robust, fault-tolerant interface between flight application software and the underlying quad-redundant hardware and operating system, ensuring continuous system operation in the presence of hardware faults.

### 1.2 Scope
The FTSS software shall operate on a quad-redundant (four-channel) Flight Critical Computer architecture. It provides core system services including deterministic task scheduling, fault-tolerant inter-processor communication, and comprehensive fault detection, isolation, and recovery (FDIR). The FTSS abstracts hardware and OS complexities, presenting a reliable execution environment for mission-critical application tasks. This SRS covers the functional, performance, and design constraints of the FTSS.

### 1.3 Definitions, Acronyms, and Abbreviations

## 2. Overall Description

### 2.1 Product Perspective
The FTSS is a middleware layer that sits between the mission-specific application software (e.g., guidance, navigation, and control) and the quad-redundant FCC hardware running the VxWorks 5.4 RTOS. It manages redundancy, synchronization, and fault management transparently to the application.

**System Context Diagram:**
```
+-------------------------------+
|     Application Software      |
|  (50Hz, 10Hz, 1Hz Tasks)      |
+-------------------------------+
            | (API Calls)
+-------------------------------+
|   Fault-Tolerant System       |
|   Services (FTSS)             |
|  - Scheduler                  |
|  - Communication Manager      |
|  - Fault Manager              |
+-------------------------------+
            | (OS & HW Abstraction)
+-------------------------------+
| VxWorks 5.4 RTOS | FCC Hardware|
| (x4 Channels)    | (Quad-Redundant)|
+-------------------------------+
```

### 2.2 Product Functions
The primary functions of the FTSS are:
1.  **Deterministic Task Scheduling:** Execute application tasks at precisely defined cyclic rates (50 Hz, 10 Hz, 1 Hz) across all synchronized channels.
2.  **Fault-Tolerant Communication:** Provide reliable, voteable message-passing services between processors (inter-channel and intra-channel).
3.  **Fault Management:** Continuously monitor hardware health, detect faults, isolate faulty channels, and reconfigure the system to maintain operation with the remaining healthy channels.

### 2.3 User Characteristics
The end-user is the **flight application software**. The application developer is an indirect user who utilizes the FTSS API. Both require no knowledge of redundancy management or fault handling.

### 2.4 Constraints
1.  **Implementation Language:** The system shall be implemented in the C programming language.
2.  **Operating System:** The system shall be built upon the VxWorks 5.4 real-time operating system.
3.  **Fault Tolerance:** The system shall be **two-fault tolerant** for any two non-simultaneous hardware faults within the FCC.
4.  **Startup Time:** The system, from power application to being fully operational and ready to execute application tasks, shall take no more than **1.5 minutes (90 seconds)**.
5.  **Hardware Platform:** The software shall be designed for the specific quad-redundant FCC hardware architecture.

### 2.5 Assumptions and Dependencies
*   Hardware faults are non-malicious and non-simultaneous for the two-fault tolerance requirement.
*   VxWorks 5.4 and the underlying Board Support Package (BSP) function correctly on non-faulty hardware.
*   The system has access to reliable, synchronized time across all channels.

## 3. Specific Requirements

### 3.1 External Interface Requirements

#### 3.1.1 Application Programming Interface (API)
The FTSS shall provide a well-defined C-language API for the application layer.
*   **Task Registration:** `FTSS_register_task(rate_hz, task_function_ptr)`
*   **Message Send:** `FTSS_send_message(message_id, *data, size)`
*   **Message Receive:** `FTSS_receive_message(message_id, *buffer, timeout)`
*   **System Status:** `FTSS_get_system_status(*status_struct)`

#### 3.1.2 Hardware Interfaces
The FTSS shall interface with:
*   Quad-redundant processors (e.g., PowerPC).
*   Cross-channel data buses (e.g., SpaceWire, MIL-STD-1553) for synchronization and communication.
*   Hardware watchdogs and Built-In-Test (BIT) facilities.

### 3.2 Functional Requirements

#### 3.2.1 Cyclic Task Scheduling (FTSS-SCHED)
*   **FR-SCHED-001:** The FTSS shall schedule and invoke registered application tasks at a **50 Hz** rate (±1 ms jitter).
*   **FR-SCHED-002:** The FTSS shall schedule and invoke registered application tasks at a **10 Hz** rate (±5 ms jitter).
*   **FR-SCHED-003:** The FTSS shall schedule and invoke registered application tasks at a **1 Hz** rate (±50 ms jitter).
*   **FR-SCHED-004:** The scheduler shall ensure task execution is synchronized across all operational channels to a defined synchronization point within each major cycle (50 Hz frame).
*   **FR-SCHED-005:** The scheduler shall provide a deterministic execution order for tasks of the same rate.

#### 3.2.2 Fault-Tolerant Communication (FTSS-COMM)
*   **FR-COMM-001:** The FTSS shall provide a message-passing service where a message sent from any channel is reliably received by all other healthy channels.
*   **FR-COMM-002:** The communication service shall implement a voting mechanism (e.g., Mid-value Select, Majority Vote) on received redundant messages from other channels to produce a single, correct value for the application.
*   **FR-COMM-003:** The service shall detect and discard messages originating from a channel that has been identified as faulty.
*   **FR-COMM-004:** Inter-channel communication latency shall be bounded and deterministic.

#### 3.2.3 Fault Detection, Isolation, and Recovery (FTSS-FDIR)
*   **FR-FDIR-001:** The FTSS shall continuously perform Built-In-Test (BIT) on local channel hardware (CPU, memory, I/O).
*   **FR-FDIR-002:** The FTSS shall employ cross-channel comparison (voting on intermediate results or messages) to detect processing faults.
*   **FR-FDIR-003:** Upon detecting a fault in a channel, the FTSS shall unambiguously **isolate** that channel, removing it from the active voting set and preventing it from affecting system outputs.
*   **FR-FDIR-004:** The system shall maintain full functionality with three operational channels after one fault.
*   **FR-FDIR-005:** The system shall maintain full functionality with two operational channels after a second, non-simultaneous fault, satisfying the two-fault tolerance requirement.
*   **FR-FDIR-006:** The FTSS shall log all fault events with relevant data (timestamp, channel ID, fault type) to non-volatile memory.
*   **FR-FDIR-007:** The FTSS shall provide a health status of all channels to the application.

### 3.3 Performance Requirements
*   **PR-PERF-001:** System startup time from power-on to "operational" state shall be ≤ **90 seconds**.
*   **PR-PERF-002:** The overhead imposed by the FTSS (scheduling, communication, voting) shall not exceed 40% of the 50 Hz frame time (i.e., ≤ 8 ms per 20 ms frame).
*   **PR-PERF-003:** Inter-channel message latency shall be ≤ 2 ms.
*   **PR-PERF-004:** Fault detection, isolation, and reconfiguration shall be completed within **3 major cycles (60 ms)** of fault occurrence.

### 3.4 Design Constraints
*   **DC-CONST-001:** The software shall be written in ANSI C (C89/C90 standard).
*   **DC-CONST-002:** The software shall be compatible with and run on top of the **VxWorks 5.4** RTOS.
*   **DC-CONST-003:** The design shall follow the two-fault tolerant architecture patterns (quad-redundant, vote-based).
*   **DC-CONST-004:** The software shall avoid dynamic memory allocation (`malloc/free`) during operational mode to ensure determinism and prevent fragmentation.

### 3.5 Software System Attributes

#### 3.5.1 Reliability & Availability
*   The system shall have a probability of loss of function of less than 1x10⁻⁹ per mission hour in the presence of up to two non-simultaneous hardware faults.
*   The system shall be available for mission execution within 90 seconds of power application.

#### 3.5.2 Safety
*   The FTSS shall prevent any single or dual hardware fault from causing a hazardous or catastrophic event.
*   All safety-critical data paths shall be protected by voting or comparison.

#### 3.5.3 Maintainability
*   The software shall be modular, with clear separation between scheduling, communication, and FDIR components.
*   All code shall adhere to a documented coding standard (e.g., NASA JPL or MISRA C guidelines).

### 3.6 Verification Requirements
*   Each requirement (FR-XX, PR-XX, DC-XX) shall have a corresponding test case defined in the Software Verification and Validation Plan.
*   Fault tolerance shall be verified through fault injection testing, simulating processor, memory, and bus failures.
