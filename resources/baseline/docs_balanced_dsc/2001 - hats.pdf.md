### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the High Assurance Transformation System Graphical User Interface (HATS-GUI). It serves as a formal agreement between the customer (Dr. Victor Winter), the guidance team, the development teams, and all other stakeholders. The primary audience includes software developers, testers, project managers, and the guidance team.

#### 1.2 Scope
The HATS-GUI is a platform-independent desktop application that provides an intuitive interface for interacting with the High Assurance Transformation System (HATS) backend (HATS-SML). It enables users to manage transformation "applications," parse transformation and target programs, execute formal transformations, and visualize the results via Syntax Derivation Trees (SDTs) and pretty-printed text. The GUI abstracts the complexities of direct command-line interaction with HATS-SML, aiming to increase the adoption and usability of the HATS framework.

**In-Scope:**
*   Management of HATS application directories and configurations.
*   Invocation of HATS-SML for parser generation, file parsing, and transformation execution.
*   Graphical display and navigation of SDT structures.
*   Display and navigation of pretty-printed text output.
*   User configuration of visual properties (colors, shapes) and file associations.
*   Search functionality across SDT and text views.

**Out-of-Scope:**
*   The underlying transformation logic and algorithms (provided by HATS-SML).
*   The creation or editing of transformation language programs (.tlp) or target files (.tgt) via built-in editors (external editors are launched).
*   Version control of application files.
*   Network or multi-user functionality.

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **HATS:** High Assurance Transformation System.
*   **HATS-SML:** The core transformation engine, implemented in Standard ML.
*   **SDT:** Syntax Derivation Tree. The internal tree representation of a parsed program.
*   **TLP:** Transformation Language Program.
*   **TGT:** Target File.
*   **GUI:** Graphical User Interface.
*   **JVM:** Java Virtual Machine.
*   **SRS:** Software Requirements Specification.

### 2. Overall Description

#### 2.1 Product Perspective
The HATS-GUI is a standalone, mediator-tier application. It operates as a front-end client to the HATS-SML backend process. The relationship is master-slave: the GUI initiates all interactions by spawning HATS-SML processes, passing commands and files, and interpreting the results. The system architecture is depicted below:

```
[User] <-> [HATS-GUI (Java)] <-> [HATS-SML Process (SML)] <-> [File System]
```

#### 2.2 User Classes and Characteristics
*   **Transformation Expert (Primary User):** A domain expert (e.g., in compiler design, software refactoring) with strong computer skills. They understand formal grammars and transformation concepts but seek a more efficient workflow than a command-line interface. They are the direct beneficiary of all GUI features.
*   **System Administrator:** Responsible for installing the HATS-GUI, HATS-SML, Java, and ML on the target platforms. They are technically proficient but not a daily user of the transformation features.

#### 2.3 Operating Environment
*   **Software:**
    *   Must execute on any operating system with a compliant Java 1.3 Runtime Environment (JRE).
    *   Requires HATS-SML version 2.0 (or compatible) and its ML interpreter (e.g., SML/NJ) to be installed and accessible on the system PATH.
*   **Hardware:** Must run on hardware capable of supporting the JVM and the display of complex graphical trees (minimum 1024x768 resolution recommended).

#### 2.4 Design and Implementation Constraints
1.  **Language:** The application shall be implemented in Java 1.3.
2.  **Portability:** The code shall not use native calls or OS-specific libraries. All file and process operations must use standard Java APIs.
3.  **External Process Communication:** Interaction with HATS-SML shall be via standard input/output streams and file system operations as defined in the communication protocol (Appendix D).
4.  **Graphics:** The SDT display component must be implemented without using a "virtual window" technique (i.e., rendering an enormous canvas and displaying a viewport). Incremental, on-demand layout and rendering are required.

#### 2.5 Assumptions and Dependencies
*   The successful operation of the HATS-GUI is entirely dependent on the availability and correct functioning of HATS-SML version 2.0.
*   It is assumed the user has a basic understanding of HATS concepts, file types (.tlp, .tgt, .grm), and their own transformation domain.
*   The project completion is dependent on the timely delivery of the approved SRS and the stable interface of HATS-SML 2.0.

### 3. System Features (Functional Requirements)

#### 3.1 Application Management
**3.1.1 Select and Open Application**
*   **FR-1:** The system shall provide a "File > Open Application..." menu option.
*   **FR-2:** Upon selection, the system shall display a directory chooser dialog.
*   **FR-3:** The system shall validate the selected directory as a HATS application by checking for the existence of a valid `config.xml` (or equivalent) file.
*   **FR-4:** Upon successful validation, the GUI shall load the application configuration, scan the directory for associated `.tlp`, `.tgt`, `.parsed`, `.sdt`, and `.txt` files, and update the main workspace view to reflect the application context.

**3.1.2 Prepare/Create Application**
*   **FR-5:** The system shall provide a "File > New Application..." menu option to create a new application directory structure with default core file templates (`lexical.spec`, `grammar.grm`, `library.sml`, `config.xml`).
*   **FR-6:** The system shall allow users to edit core application files (`lexical.spec`, `grammar.grm`, `library.sml`, `config.xml`) by launching the user-configured external text editor for the respective file type.

#### 3.2 Parser Generation
*   **FR-7:** The system shall automatically determine when a parser needs to be (re)generated (e.g., when a `.grm` or `.spec` file is newer than the current parser data files).
*   **FR-8:** The system shall provide a manual "Tools > Generate Parser" menu option.
*   **FR-9:** Upon trigger, the system shall invoke HATS-SML with the appropriate command to generate a parser from the current application's `lexical.spec` and `grammar.grm` files.
*   **FR-10:** The system shall capture and display any error messages from HATS-SML during parser generation in a dedicated log/console pane.

#### 3.3 File Parsing
*   **FR-11:** Within the workspace, the user shall be able to right-click on any `.tlp` or `.tgt` file and select "Parse".
*   **FR-12:** Before parsing, the system shall check if the current parser is up-to-date relative to the grammar files. If not, it shall prompt the user to regenerate the parser.
*   **FR-13:** The system shall invoke HATS-SML to parse the selected file, producing a corresponding `.parsed` (SDT) file.
*   **FR-14:** The system shall display the progress of the parsing operation and report success/failure.

#### 3.4 Transformation Execution
*   **FR-15:** The user shall be able to select a parsed `.tlp` file (program) and a parsed `.tgt` file (target) from the workspace.
*   **FR-16:** The system shall provide an "Execute" action (e.g., button or menu item) that is enabled when valid source and target files are selected.
*   **FR-17:** Upon execution, the system shall verify all dependencies (parser currency, file existence).
*   **FR-18:** The system shall invoke HATS-SML's transformation engine, passing the selected program and target SDTs.
*   **FR-19:** The system shall capture the standard output and error streams from HATS-SML, displaying them in a console pane. The GUI must remain responsive during this potentially long-running operation.
*   **FR-20:** Upon successful completion, the system shall save the resulting output SDT (e.g., as a `.sdt` file) and any pretty-printed text output (e.g., as a `.txt` file) in the application directory.

#### 3.5 Output Visualization and Navigation
**3.5.1 SDT Display**
*   **FR-21:** The user shall be able to double-click any `.parsed` or `.sdt` file to open it in an SDT View window.
*   **FR-22:** The SDT View shall render the tree structure graphically, using shapes and colors to denote different node types (non-terminals, terminals, etc.).
*   **FR-23:** The user shall be able to pan and zoom within the SDT view.
*   **FR-24:** The user shall be able to expand/collapse subtrees by clicking on parent nodes.
*   **FR-25:** Clicking on a node shall highlight it and display its properties (type, value, production rule) in a separate pane.

**3.5.2 Pretty-Printed Text Display**
*   **FR-26:** The user shall be able to double-click any `.txt` output file to open it in a Text View window.
*   **FR-27:** The Text View shall display formatted, syntax-highlighted text with selectable lines and symbols.

**3.5.3 View Synchronization**
*   **FR-28:** When both an SDT View and its corresponding Text View are open, selecting a node in the SDT shall attempt to highlight the corresponding text region in the Text View, and vice-versa. The system shall log a warning when the mapping is ambiguous (see Undecided Issues).

#### 3.6 Configuration
**3.6.1 Application Configuration**
*   **FR-29:** The system shall provide an "Edit > Configure Application..." menu option to modify the current application's `config.xml`, including file associations and default settings.

**3.6.2 Global Display Settings**
*   **FR-30:** The system shall provide a "View > Settings..." or "Tools > Preferences..." dialog.
*   **FR-31:** This dialog shall allow the user to define a color and shape scheme for each node type (e.g., `Statement = Blue Rectangle`, `Expression = Green Oval`).
*   **FR-32:** The dialog shall allow configuration of default expansion depth for new SDT views.

**3.6.3 External Tool Settings**
*   **FR-33:** The user shall be able to configure the path to the preferred external text editor for different file extensions (`.tlp`, `.tgt`, `.grm`, `.sml`, `.txt`).

#### 3.7 Search Functionality
*   **FR-34:** The system shall provide a search dialog (Ctrl+F) accessible from both SDT View and Text View windows.
*   **FR-35:** The user shall be able to search for nodes in an SDT based on criteria defined in Appendices E & F (e.g., node type, node value, subtree pattern).
*   **FR-36:** The user shall be able to search for text patterns in the Text View using regular expressions.
*   **FR-37:** Search results shall be highlighted in the view, and the user shall be able to navigate through them (Next/Previous).

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements
*   **NFR-1 (Display Performance):** The system shall render and display the initial view of an SDT containing 10,000 nodes within 5 seconds on standard hardware (Pentium III ~500MHz, 256MB RAM).
*   **NFR-2 (Scalability):** The SDT visualization architecture shall be designed to handle navigation and basic operations (pan, zoom, expand/collapse) on trees containing up to 1,000,000 nodes without catastrophic performance degradation or memory exhaustion.
*   **NFR-3 (Responsiveness):** The user interface shall not block (freeze) during long-running HATS-SML operations (parsing, execution). A progress indicator shall be shown, and the user shall be able to cancel the operation or interact with other parts of the GUI.

#### 4.2 Portability Requirement
*   **NFR-4:** The delivered software shall run identically, without modification or recompilation, on the following operating systems: Microsoft Windows 2000, Sun Solaris 8, and a standard Linux distribution (e.g., Red Hat 7.x).

#### 4.3 Usability Requirements
*   **NFR-5:** The interface shall be primarily menu-driven, following common desktop application conventions for the target platforms.
*   **NFR-6:** The learning curve shall be minimized for users already familiar with HATS concepts; therefore, extensive wizards, tutorials, or help systems are not required. Tooltips and clear error messages are sufficient.

#### 4.4 Implementation Requirements
*   **NFR-7:** The system shall be implemented in Java, utilizing the Java 1.3 SDK and its standard libraries (Swing/AWT for GUI, `java.io`, `java.lang.Process`).

### 5. Appendices

#### Appendix A: Undecided Issues
1.  The final, detailed specification of the HATS-GUI to HATS-SML communication protocol (Appendix D) is contingent upon the finalized HATS-SML 2.0 API.
2.  The algorithm for "mirroring" navigation between SDT and text views when the node-to-text mapping is not one-to-one requires further analysis and stakeholder input.
3.  Default color and shape schemes for common grammar constructs need to be established.
4.  Error recovery strategy for scenarios where a HATS-SML process crashes or hangs must be defined (e.g., timeout mechanisms, process termination).
5.  Detailed mockups for all dialog boxes and the main workspace layout are pending.
6.  Policy for managing memory when multiple large SDTs are open concurrently (e.g., lazy loading, caching, purge on close).
