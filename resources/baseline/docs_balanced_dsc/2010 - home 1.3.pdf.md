### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the DigitalHome (DH) prototype smart home management system. It serves as the authoritative specification for the development team, a basis for agreement between stakeholders, and a reference for validation and verification activities. The intended audience includes the Development Team, DH Technicians, HomeOwner Inc. Management, and project stakeholders.

#### 1.2 Document Conventions
*   **Bold text** is used for key terms and entity names.
*   *Italic text* is used for emphasis.
*   `Monospaced text` is used for technical references, code, or data elements.
*   Requirements are uniquely identified as `FR-XXX` (Functional) or `NFR-XXX` (Non-Functional).

#### 1.3 Project Scope
The DigitalHome (DH) system is a prototype smart home management system designed to allow residents to monitor and control environmental, security, and appliance functions via a web interface. Its scope is limited to managing temperature, humidity, security, and appliance power in a **simulated home environment**. The primary goal is to create a functional prototype to support future business decisions for HomeOwner Inc. regarding the feasibility and design of a commercial product.

**In-Scope:**
*   Web-based user interface for monitoring and control.
*   Simulation of sensor data (temperature, humidity, contact sensors) and device controllers (thermostats, power switches).
*   User role management (General, Master, Technician).
*   Scheduling of environmental and appliance settings.
*   Security breach detection and alarm simulation.
*   Data logging, backup, and report generation.

**Out-of-Scope:**
*   Production-grade hardware integration.
*   Mobile application development.
*   Billing or subscription management features.
*   Integration with third-party services (e.g., weather, voice assistants).
*   Advanced AI or learning algorithms for automation.

### 2. Overall Description

#### 2.1 Product Perspective
The DH system is a self-contained, simulated prototype. It will consist of a web server application, a simulation engine for home devices, and a database. The system is independent but designed with modularity to allow future integration with real hardware components.

#### 2.2 Product Functions (Summary)
1.  Provide secure user authentication and role-based access control.
2.  Simulate real-time monitoring of temperature and humidity in multiple rooms.
3.  Allow remote manual control of simulated lights and appliances.
4.  Enable creation and execution of weekly schedules for thermostat settings.
5.  Detect simulated security breaches and trigger alarms.
6.  Generate monthly summary reports of environmental extremes and security events.
7.  Perform automated daily backups of system data.
8.  Allow Master Users and Technicians to configure system parameters and user accounts.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **General User** | Home resident; basic technical proficiency; primary consumer of monitoring/control features. | Intuitive interface to view status and control devices easily and reliably. |
| **Master User** | Designated resident; higher trust level; manages household access. | Ability to manage user accounts and oversee general system settings. |
| **DH Technician** | Trained professional; high technical skill; performs installation and maintenance. | Tools for initial system configuration, backup setup, and troubleshooting. |
| **HomeOwner Inc. Management** | Business decision-makers; non-technical from a systems perspective. | A demonstrable, stable prototype that validates product concepts and feasibility. |
| **Development Team** | System architects and engineers; expert technical skill. | Clear, unambiguous requirements to guide design and implementation. |

#### 2.4 Operating Environment
*   **Software:** The web interface shall be accessible via standard web browsers (Chrome, Firefox, Safari) version N-1. The server shall run on a mainstream operating system (e.g., Linux, Windows Server).
*   **Hardware (Simulated):** The system shall simulate a network of wireless devices (sensors, controllers) communicating with a central gateway. The simulation must model realistic constraints (e.g., 1000-foot wireless range, device state latency).
*   **Network:** The system depends on standard ISP services (e.g., cable modem, DSL) for remote web access. Local communication is simulated as a wireless network.

#### 2.5 Design and Implementation Constraints
1.  The system must be developed as a prototype within a **12-month timeline**.
2.  Development costs must be minimized while meeting core requirements.
3.  The architecture must use **abstraction and modularity** to facilitate future transition to a commercial product with real hardware.
4.  All sensitive data (passwords, communication) must be protected using recognized encryption standards.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** Users have a reliable internet connection for remote access.
*   **Assumption:** The simulated environment provides a sufficiently accurate model for stakeholder evaluation.
*   **Dependency:** The project schedule is dependent on meeting the defined milestone dates.
*   **Dependency:** Final technology selections (e.g., specific security library) may impact detailed design.

### 3. System Features and Requirements

#### 3.1 Feature: User Authentication and Authorization
**Description:** The system shall control access based on user credentials and assigned roles.
*   **FR-010:** The system shall provide a login page for users to enter a `Username` and `Password`.
*   **FR-011:** The system shall authenticate credentials against the stored `User Account` data.
*   **FR-012:** The system shall enforce role-based permissions (`General`, `Master`, `Technician`) upon successful login, presenting only authorized functions.
*   **FR-013:** A `Master User` shall be able to create, modify, and disable `General User` accounts via a dedicated interface.
*   **Related NFR:** `NFR-030` (Security).

#### 3.2 Feature: Real-Time Environmental Monitoring
**Description:** The system shall display current temperature and humidity readings from simulated sensors.
*   **FR-020:** The system shall poll simulated temperature and humidity sensors **at least every 2 seconds**.
*   **FR-021:** The web interface shall update the displayed sensor values for each room/location in real-time (within 2 seconds of the poll).
*   **FR-022:** The system shall log all sensor readings (`Sensor Reading` entity) with a `Timestamp` and `DeviceID` for historical review.
*   **Related NFR:** `NFR-010` (Performance), `NFR-050` (Operational Range - simulated).

#### 3.3 Feature: Device Control
**Description:** Users shall be able to remotely control simulated devices.
*   **FR-030:** A `General User` shall be able to view the current state (`on`/`off`, set-point) of all controllable devices (lights, appliances, thermostats).
*   **FR-031:** A `General User` shall be able to send a command to turn a simulated light or appliance switch `on` or `off`. The interface shall reflect the state change within 3 seconds.
*   **FR-032:** A `General User` shall be able to adjust the temperature set-point for a simulated thermostat. The command shall be sent to the simulation controller.
*   **Related NFR:** `NFR-050` (Operational Range - simulated).

#### 3.4 Feature: Environmental and Appliance Scheduling
**Description:** Users shall be able to create weekly plans for automatic device control.
*   **FR-040:** A `General User` shall be able to create, view, edit, and delete an `Environmental Plan`.
*   **FR-041:** A plan shall allow setting different temperature and humidity set-points for defined time periods (e.g., "Weekday Morning", "Weekend Night") across a month.
*   **FR-042:** A plan shall include schedules for turning specified appliances `on` or `off` at defined times.
*   **FR-043:** The system shall automatically execute the active plan for the current day and time, sending appropriate set-point and on/off commands to the simulation.
*   **Undecided Issue:** Conflict resolution between a scheduled plan action and a simultaneous manual user override.

#### 3.5 Feature: Security Breach Detection and Alarm
**Description:** The system shall monitor contact sensors and activate alarms upon a breach.
*   **FR-050:** The system shall monitor the state of simulated door/window contact sensors.
*   **FR-051:** Upon detecting a change from `closed` to `open` during armed state, the system shall create a `Security Event` record of type `Breach`.
*   **FR-052:** Upon a breach, the system shall activate simulated alarms (e.g., a visual alert on the web interface and an audible sound from the server/console).
*   **FR-053:** The system shall provide an interface for an authorized user (`Master` or `General`) to reset the alarm, logging a `Security Event` of type `Reset`.

#### 3.6 Feature: Reporting
**Description:** The system shall generate a monthly summary report.
*   **FR-060:** A `General User` shall be able to request a monthly report for any previous month.
*   **FR-061:** The report shall include, for each day of the month:
    *   Maximum and minimum recorded temperature per sensor.
    *   Maximum and minimum recorded humidity per sensor.
    *   A list of all `Security Event` breaches.
*   **Undecided Issue:** The exact algorithm for calculating daily averages/extremes.

#### 3.7 Feature: System Configuration and Backup
**Description:** Technicians and Master Users shall configure system settings and backups.
*   **FR-070:** A `DH Technician` shall have a dedicated interface to configure initial system parameters (e.g., simulated device network setup, timezone).
*   **FR-071:** A `DH Technician` shall be able to set the daily time for automatic system backup.
*   **FR-072:** The system shall perform an automated backup daily at the configured time, creating a `System Backup` record.
*   **FR-073:** The backup shall include all system configuration data, user `Environmental Plans`, `Sensor Readings`, and `Security Events`.
*   **FR-074:** In the event of a system failure, the system shall provide a mechanism to restore all data from the most recent backup.
*   **Related NFR:** `NFR-060` (Recoverability).
*   **Undecided Issue:** The detailed format and storage mechanism for backups.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The primary interface shall be a web-based portal accessible from a browser.
*   The layout shall be clean, intuitive, and role-specific.
*   **Undecided Issue:** Detailed user interface design and layout.

#### 4.2 Hardware Interfaces (Simulated)
*   The system shall include a simulation module that mimics the behavior of wireless sensors (temperature, humidity, contact) and controllers (thermostat, switch) communicating via a simulated gateway.
*   The simulation API shall be abstracted to allow future replacement with real hardware drivers.

#### 4.3 Software Interfaces
*   **Database:** The system shall persist data in a relational database (e.g., PostgreSQL, MySQL). Entities and primary keys are defined in Section 1.5 of the provided summary.
*   **Web Server:** The application shall be served via a standard HTTP/S web server (e.g., Apache, Nginx).

#### 4.4 Communications Interfaces
*   Client-to-Server: HTTP/S with TLS 1.2 or higher (`NFR-030`).
*   Simulated Device Network: Internal simulation of a wireless protocol (e.g., Zigbee, Z-Wave) with a modeled 1000-foot range constraint.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   **`NFR-010`:** The web interface shall update all displayed sensor readings at least every **2 seconds** to reflect the latest simulated data.
*   **`NFR-011`:** User-initiated control commands (on/off, set-point) shall be acknowledged and reflected in the simulation within **3 seconds** under normal load.

#### 5.2 Reliability & Availability
*   **`NFR-020`:** The system shall have a Mean Time Between Failures (MTBF) of not less than **10,000 hours** during the prototype evaluation period. (A "failure" is defined as any event requiring a full system restart to restore core functionality).

#### 5.3 Security Requirements
*   **`NFR-030`:** All user authentication shall require a valid account name and password. Passwords shall be stored using a strong, salted cryptographic hash.
*   **`NFR-031`:** All communication between the client browser and the web server shall be encrypted using **Transport Layer Security (TLS)** version 1.2 or higher.
*   **Undecided Issue:** Specification of additional security technologies.

#### 5.4 Maintainability & Supportability
*   **`NFR-040`:** The software design shall adhere to principles of high cohesion and loose coupling. The hardware simulation layer shall be abstracted behind a well-defined interface to allow for future replacement with physical hardware modules.

#### 5.5 Operational Constraints
*   **`NFR-050`:** The simulated wireless device network shall model a maximum effective indoor communication range of **1000 feet**. Devices simulated beyond this range shall be reported as "unavailable."

#### 5.6 Recoverability Requirements
*   **`NFR-060`:** Following a system failure, it must be possible to restore the system state (configuration, plans, and historical data) from the most recent daily backup. Data loss shall be limited to transactions occurring after the last backup.
