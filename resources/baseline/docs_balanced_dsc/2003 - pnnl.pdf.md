### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Automated Diagnostics Software. The purpose of this software is to automate the detection and diagnosis of faults in HVAC subsystems (chillers, cooling towers, and boilers) using pattern-recognition algorithms, thereby replacing manual analysis and improving operational efficiency, maintenance response, and energy performance.

#### 1.2 Document Conventions
*   **Bold text** is used for key terms and interface elements.
*   *Italic text* is used for emphasis.
*   `Monospaced text` is used for code, file names, and specific parameter values.
*   Requirements are uniquely identified as **FR** (Functional Requirement) or **NFR** (Non-Functional Requirement) with a numeric suffix.

*   **Project Sponsors & Managers:** Focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (External Interface Requirements) for scope and high-level functionality.

*   **System Administrators:** Focus on Sections 3.6 (System Configuration) and 6 (Non-Functional Requirements) for deployment and maintenance details.

#### 1.4 Project Scope
The software will automate fault detection and diagnostics for HVAC subsystems, initially focusing on chillers and cooling towers. The system will process both real-time data streams and batch files containing sensed data (e.g., temperatures, currents) alongside fixed equipment data (e.g., specifications, setpoints). It will provide identified faults, their likely causes, and recommended corrective actions via a graphical user interface. The architecture will be designed for future expansion to include boilers and other subsystems. The software is a desktop application intended for use on Microsoft Windows operating systems.

### 2. Overall Description

#### 2.1 Product Perspective
The Automated Diagnostics Software is a standalone desktop application. It interfaces externally with:
1.  **Data Acquisition Systems:** To receive real-time sensed data streams (e.g., from a building automation system or AEC Micrologger).
2.  **Data Files:** To import batch data from loggers in a standard ASCII format.
3.  **Users:** Via a graphical user interface (GUI).
4.  **Local Database/Storage:** For persistent storage of configuration, historical data, and diagnostic results.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Building Operator** | Monitors from control room. Good HVAC knowledge, moderate computer skills. | Quick, at-a-glance system status. Alerting for active faults. |
| **Service Technician** | Works on-site or remotely. Deep HVAC knowledge, variable computer skills. | Detailed fault analysis. Ability to import and diagnose logged data. |
| **Energy Service Provider** | Manages multiple buildings remotely. Analytical focus. | Historical trend analysis across portfolios. Efficiency reporting. |
| **Building Operator Supervisor** | Oversees team and work orders. | Prioritization dashboard. Summary of fault severity and location. |
| **Administrator** | IT/System savvy. Responsible for setup and health of the software. | Full system configuration, user management, and parameter tuning. |
| **General User** | Read-only access (e.g., trainees, managers). | View and print reports. Cannot alter system state or configuration. |

#### 2.3 Operating Environment
*   **Software:** Microsoft Windows 10/11 (64-bit).
*   **Hardware:** Standard business desktop/laptop with minimum 8GB RAM and 500MB free disk space.
*   **Dependencies:** .NET Framework 4.8 or later (or equivalent runtime as per technology stack).

#### 2.4 Design and Implementation Constraints
1.  The user interface must be a single-window, hierarchical navigation application.
2.  The system must support adding new diagnostic algorithms without modifying the core processing engine.
3.  All administrative functions must be protected by role-based authentication.
4.  Data must be stored with precision to three significant figures.

#### 2.5 Assumptions and Dependencies
*   **D1:** Accurate fixed data (equipment specs, setpoints) will be provided by the customer during configuration.
*   **D2:** Sensed data will be provided in a predefined, documented ASCII format for file-based import.
*   **D3:** A real-time data stream interface specification will be provided by the hardware/software vendor.
*   **Assumption:** Users possess a fundamental understanding of HVAC system components and principles.

### 3. System Features

#### 3.1 Data Acquisition and Preprocessing
**FR-1:** The system shall acquire sensed data from either a real-time data stream or a user-selected ASCII file.
**FR-2:** The system shall validate incoming sensed data against configurable minimum and maximum range limits.
**FR-3:** The system shall flag data points that are missing, out of range, or otherwise erroneous.
**FR-4:** The system shall convert all sensed data to consistent, predefined internal units (e.g., °C, Amps, kW).
**FR-5:** The system shall merge validated sensed data with pre-configured fixed data for the relevant subsystem.

#### 3.2 Equipment Status Determination
**FR-6:** The system shall calculate an "On"/"Off" status for key components (compressor, pumps, fans) by comparing measured electrical current or power values against administrator-configurable thresholds.
**FR-7:** The calculated equipment status shall be associated with the corresponding sensed data points.

#### 3.3 Diagnostic Algorithm Execution
**FR-8:** The system shall execute diagnostic algorithms when new, validated data and equipment status are available.
**FR-9:** For Version 1.0, the system shall include algorithms for at least the following conditions:
    *   **FR-9.1:** Chiller Schedule Compliance
    *   **FR-9.2:** Chilled Water Supply Temperature Control
    *   **FR-9.3:** Cooling Tower Approach Temperature
**FR-10:** Algorithms shall produce a diagnostic result including: Fault Category, Severity (OK, Caution, Not OK), Description, and Timestamp.

#### 3.4 Fault Logging, Storage, and Historical Review
**FR-11:** The system shall permanently store all diagnostic results in a local database.
**FR-12:** The system shall allow users to query and view historical diagnostic results for any subsystem over a user-configurable time period (e.g., last 24 hours, last week, custom date range).
**FR-13:** The system shall provide filtering options for historical results by severity and fault category.

#### 3.5 User Interface and Reporting
**FR-14:** The system shall present a main dashboard with a simple, graphical summary (e.g., health icons, color-coded list) of current faults across all monitored buildings and subsystems.
**FR-15:** The system shall provide a hierarchical navigation interface following the structure: Building -> HVAC Subsystem -> Diagnostic Condition -> Detailed Result View.
**FR-16:** The system shall generate a printable, detailed report for any specific fault, including its description, probable cause, recommended corrective action, and relevant data points.

#### 3.6 System Configuration and Control
**FR-17:** An Administrator user shall be able to define and modify the list of monitored buildings and their associated HVAC subsystems.
**FR-18:** An Administrator user shall be able to view, add, modify, and delete fixed data parameters (specifications, setpoints) for any subsystem.
**FR-19:** An Administrator user shall be able to adjust configurable sensitivity thresholds (e.g., `CHWST Alarm Evaluation Interval`, current thresholds for status) for diagnostic algorithms.
**FR-20:** An Administrator user shall be able to start and stop the continuous real-time diagnostic processing engine.
**FR-21:** An Administrator user shall be able to create, modify, and delete user accounts and assign roles (General User or Administrator).

### 4. Data Requirements

#### 4.1 Logical Data Model
The system shall manage the following core entities:
*   **Building:** `Building_ID` (PK), `Name`, `Location`, `Contact_Info`
*   **HVAC_Subsystem:** `Subsystem_ID` (PK), `Building_ID` (FK), `Type` (Chiller, CoolingTower, Boiler), `Model`, `Specifications` (JSON/Text), `Schedule`
*   **Sensed_Data_Point:** `Timestamp`, `Sensor_ID` (Composite PK), `Subsystem_ID` (FK), `Value`, `Unit`, `Validation_Status`, `Equipment_Status` (On/Off)
*   **Fixed_Data_Parameter:** `Parameter_ID`, `Subsystem_ID` (Composite PK), `Name`, `Value`, `Unit`, `Date_Entered`
*   **Diagnostic_Result:** `Result_ID` (PK), `Timestamp`, `Subsystem_ID` (FK), `Fault_Category`, `Severity`, `Description`, `Detailed_Data_Snapshot`
*   **User:** `User_ID` (PK), `Name`, `Role`, `Hashed_Password`, `Last_Login`

#### 4.2 Data Import/Export Format
For batch file processing, the system shall accept ASCII files with the following characteristics:
*   Comma-separated values (CSV).
*   A header row defining `Timestamp`, `Sensor_ID`, and `Value`.
*   Timestamp format: `YYYY-MM-DD HH:MM:SS`.

### 5. External Interface Requirements

#### 5.1 User Interfaces
*   **UI-1:** A login screen for user authentication.
*   **UI-2:** A main dashboard showing a summary of system health.
*   **UI-3:** A hierarchical tree-view panel for navigating buildings and subsystems.
*   **UI-4:** A detailed view panel showing data trends, current status, and diagnostic results for the selected item.
*   **UI-5:** Modal dialog windows for configuration tasks (adding buildings, editing fixed data, adjusting parameters).
*   **UI-6:** A reporting window with print preview functionality.

#### 5.2 Hardware Interfaces
*   **HI-1:** The software shall communicate with data acquisition hardware (e.g., AEC Micrologger) via a vendor-provided API or communication protocol (e.g., Modbus TCP) for real-time data streaming.

#### 5.3 Software Interfaces
*   **SI-1:** The software shall read from and write to a local SQLite (or equivalent) database for data persistence.
*   **SI-2:** The software shall include necessary drivers or libraries to support the real-time data stream protocol specified in HI-1.

#### 5.4 Communications Interfaces
*   **CI-1:** For real-time data acquisition, the software will use standard TCP/IP socket communication on a configurable port.

### 6. Non-Functional Requirements

#### 6.1 Usability
**NFR-1:** A user with good HVAC knowledge but only moderate computer expertise shall be able to perform core monitoring and historical review tasks with less than 30 minutes of training.

#### 6.2 Supportability
**NFR-2:** All significant application errors (unhandled exceptions) shall be logged to a local file with timestamp, module name, function name, and a descriptive message.

#### 6.3 Extensibility
**NFR-3:** The software shall be designed with a plug-in or modular architecture so that new diagnostic algorithm modules for additional HVAC subsystems (e.g., boilers) can be added without changes to the core data acquisition, status determination, or UI navigation code.

#### 6.4 Data Integrity
**NFR-4:** All stored sensed data values shall maintain a precision of three significant figures.
**NFR-5:** The user interface shall clearly indicate when displayed data is calculated from incomplete or flagged source data.

#### 6.5 Platform Constraint
**NFR-6:** The software shall be developed, tested, and certified to run on Microsoft Windows 10 and 11 operating systems.

#### 6.6 Security
**NFR-7:** User privileges shall be enforced at the application level. Administrative functions (all requirements in Section 3.6) shall be accessible only after authentication as a user with the "Administrator" role.

### 7. Appendices

#### Appendix A: Glossary
*   **Fixed Data:** Static or semi-static parameters describing the equipment (e.g., rated capacity, setpoints, schedule).
*   **Sensed Data:** Dynamic measurements collected from sensors in the field (e.g., temperature, current, flow).
*   **Subsystem:** A major HVAC component unit, such as a specific chiller, cooling tower cell, or boiler.
*   **Approach Temperature:** The difference between the cooling tower water outlet temperature and the ambient wet-bulb temperature.
