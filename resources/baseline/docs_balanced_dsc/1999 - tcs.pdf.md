### 1. Introduction

#### 1.1 Purpose
This document defines the software requirements for the Tactical Control System (TCS) Block 0. It serves as the definitive specification for developers, testers, and project managers, and provides a basis for agreement between the stakeholders on the system's capabilities. The intended audience includes Integrated Product Teams (IPTs), the Warfighters Planning Group, and system validation personnel.

#### 1.2 Scope
The TCS is a joint-service, scalable command and control system for operating present and future tactical Unmanned Aerial Vehicles (UAVs), including the Predator (MAE) and Outrider (TUAV). This SRS covers the software required to perform mission planning, UAV control, payload data management, and interoperability with external C4I systems. The system emphasizes an open, DII/COE-compliant software architecture and the use of COTS/GOTS hardware. This specification pertains to the initial development block (Block 0).

### 2. Overall Description

#### 2.1 Product Perspective
The TCS is a standalone system that interfaces with external UAVs via data links and with tactical networks via C4I systems. It is a major component within the joint tactical UAV ecosystem, acting as the primary ground control and data exploitation node.

**System Interfaces:**
*   **UAV Data Links:** Line-of-sight and satellite communication links for command/control and data downlink.
*   **C4I Systems:** Interfaces with systems such as AFATDS, ASAS, and JSTARS for receiving tasking and disseminating products.
*   **NIMA Data Servers:** For accessing digital map and terrain data (DTED, DFAD, ADRG).
*   **Security Infrastructure:** For user authentication and secure communications.

#### 2.2 Product Functions (High-Level)
1.  **System Management:** Startup, shutdown, health monitoring, and configuration.
2.  **Mission Planning:** Graphical creation, validation, and management of flight and payload plans.
3.  **UAV Control:** Uploading plans, monitoring telemetry, and providing manual override controls.
4.  **Payload Data Handling:** Reception, processing, display, annotation, storage, and dissemination of sensor data.
5.  **C4I Interoperability:** Sending and receiving standardized tactical messages and imagery products.
6.  **System Maintenance:** Diagnostics, software updates, and log management.
7.  **Training:** Embedded interactive training modules.

#### 2.3 User Characteristics
*   **UAV Operators & Mission Planners:** Military personnel trained in aviation operations and tactical planning. They are proficient with computer-based graphical tools.
*   **Imagery Analysts:** Intelligence personnel skilled in imagery exploitation and analysis.
*   **System Maintainers:** Technical personnel with training in computer system maintenance and diagnostics.
*   **All Users:** Operate in mission-oriented protective posture (MOPP) gear. The user population spans from 5th percentile female to 95th percentile male.

#### 2.4 Constraints
1.  **Architectural:** Software must be DII/COE and JTA compliant.
2.  **Hardware:** Must utilize designated COTS/GOTS hardware platforms.
3.  **Security:** Must be accreditable for processing up to [Classified Level] information.
4.  **Environmental:** Software must operate on hardware qualified for rugged land-based shelter and shipboard environments.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** UAV OEMs will provide necessary data link protocols and AV-specific software modules.
*   **Dependency:** Timely availability of digital map data from NIMA.
*   **Dependency:** Finalized Interface Design Descriptions (IDDs) for each C4I system.
*   **Dependency:** The precedence of requirements is: TCS ORD > TCS SSS > other referenced documents.

### 3. Specific Requirements

#### 3.1 Functional Requirements

**3.1.1 System Startup & Initialization (SYS-001)**
*   **Requirement:** Upon application of power, the TCS software shall initialize all hardware components, load the operating system and application software, perform a Built-In Test (BIT), and present a status summary to the operator.
*   **Input:** Power On signal.
*   **Processing:** Sequence through hardware POST, software load, fault detection checks.
*   **Output:** Operational status display, indication of achievable UAV interaction level.

**3.1.2 Mission Planning (MP-001)**
*   **Requirement:** The system shall provide a graphical user interface allowing an operator to create, modify, save, and validate mission plans consisting of flight routes (waypoints), payload tasking schedules, and communication settings.
*   **Input:** User input via pointing device, keyboard; imported map data (NIMA); tasking orders (via C4I or manual entry).
*   **Processing:** Overlay graphics on map, perform terrain avoidance and airspace deconfliction validation (as per rulesets).
*   **Output:** Stored Mission Plan data object with a unique Plan ID and validity status.

**3.1.3 UAV Control & Monitoring (CTL-001)**
*   **Requirement:** The system shall allow an operator to select a validated mission plan and upload it to a designated UAV via the established data link.
*   **Requirement:** The system shall display real-time telemetry data (location, altitude, heading, fuel state, system status) for all controlled UAVs on a situational awareness display.
*   **Input:** Operator command; Mission Plan; downlinked telemetry stream.
*   **Processing:** Encode and transmit plan via data link; parse and update telemetry database.
*   **Output:** Command uplink; updated AV status display.

**3.1.4 Payload Data Management (PDM-001)**
*   **Requirement:** The system shall receive, decode, and display near-real-time EO/IR/SAR imagery and video streams from UAV payloads.
*   **Requirement:** The system shall allow an imagery analyst to annotate imagery products with symbols, text, and geometric shapes, and store the annotated product in NITF 2.0 (or later) format.
*   **Input:** Downlinked sensor data stream.
*   **Processing:** Decode video/imagery, apply georeferencing, provide annotation tools, format to NITF.
*   **Output:** Displayed imagery/video; stored, annotated Payload Product file.

**3.1.5 C4I Interface & Dissemination (C4I-001)**
*   **Requirement:** The system shall send and receive standardized tactical messages (e.g., USMTF, VMF) with external C4I systems as defined in the JROC-validated interface schedule.
*   **Requirement:** The system shall disseminate annotated imagery products and target reports to pre-configured external systems.
*   **Input:** Internal target/product data; incoming C4I messages.
*   **Processing:** Format translation, protocol handling, routing.
*   **Output:** Outgoing C4I messages; disseminated product files.

**3.1.6 System Maintenance (MNT-001)**
*   **Requirement:** The system shall provide role-based access to diagnostic functions and software update procedures.
*   **Input:** Maintainer credentials; software update packages.
*   **Processing:** Authenticate user, execute diagnostics, apply updates with rollback capability.
*   **Output:** Diagnostic logs; system status; update success/failure confirmation.

#### 3.2 Data Requirements (Logical Data Model)
The system shall manage the following core data entities:

| Entity          | Primary Key       | Key Attributes/Fields                                                                                             |
|-----------------|-------------------|-------------------------------------------------------------------------------------------------------------------|
| **Mission Plan**    | `Plan_ID`         | `Plan_Name`, `UAV_Type`, `Flight_Route` (list of waypoints), `Payload_Tasking`, `Comms_Settings`, `Validity_Status` |
| **Air Vehicle (AV)** | `AV_Tail_Number`  | `Current_Location`, `Altitude`, `Heading`, `Telemetry_Data` (struct), `Fuel_State`, `Active_Plan_ID`               |
| **Payload Product** | `Product_ID`      | `Sensor_Type`, `Collection_Timestamp`, `Geospatial_Coordinates`, `Annotations`, `Format` (e.g., NITF 2.0), `File_Path` |
| **Target**          | `Target_Designation` | `Coordinates_Lat`, `Coordinates_Lon`, `Location_Error`, `Target_Type`, `Associated_Product_IDs` (list)            |
| **C4I Message**     | `Message_ID`      | `Message_Format`, `Source_System`, `Destination_System`, `Content`, `Timestamp_Sent`, `Timestamp_Received`        |
| **System Config**   | `Config_Profile_Name` | `Available_UAV_Types`, `Enabled_C4I_Interfaces`, `User_Roles_Permissions`, `Active_Map_Datasets`                 |

#### 3.3 Non-Functional Requirements

**3.3.1 Performance**
*   **P.1:** The system shall be designed such that its throughput does not exceed 50% of its total processing or communication capability over any rolling 10-second period under maximum specified load. (Objective: 25%).
*   **P.2:** Critical operator commands (e.g., emergency abort) shall have a maximum latency of [TBD] seconds from initiation to transmission.

**3.3.2 Reliability, Availability, and Maintainability**
*   **RAM.1:** The system shall meet or exceed the MTBF, MTTR, and Operational Availability (Ao) thresholds specified in the Predator and Outrider ORDs.
*   **RAM.2:** The software shall support automatic logging of all system errors and operator actions for diagnostic purposes.

**3.3.3 Security**
*   **SEC.1:** The system shall comply with DoDD 5200.28 and be accreditable for processing classified information.
*   **SEC.2:** All user access shall be controlled via role-based authentication (username/password minimum).
*   **SEC.3:** All external communications links (UAV, C4I) shall be secured using approved cryptographic methods.

**3.3.4 Usability**
*   **US.1:** The HCI shall be a graphical, windowed interface (X-windows/Motif compliant) as detailed in TCS 108.
*   **US.2:** The interface shall be operable by personnel wearing mission-oriented protective posture (MOPP) gear.
*   **US.3:** All menu structures and dialogs shall comply with MIL-STD-1472.

**3.3.5 Portability & Flexibility**
*   **PF.1:** The application software shall be hostable on multiple Service-specific hardware configurations without modification to source code.
*   **PF.2:** The system architecture shall be modular to allow for the integration of future UAV types and sensor payloads with minimal software changes.

**3.3.6 Environmental**
*   **ENV.1:** The software shall operate on hardware qualified to withstand specified levels of shock, vibration, temperature, and humidity for land and shipboard environments.
