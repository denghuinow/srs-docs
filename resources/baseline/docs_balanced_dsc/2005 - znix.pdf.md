# Software Requirements Specification (SRS)
## Project ZNIX Framework
**Version:** 1.0
**Date:** October 26, 2023
**Status:** Draft for Review

---

### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for Project ZNIX, an object-based, application-independent framework for personal information management. It is intended for use by the project's developers, testers, project managers, and stakeholders to guide the design, implementation, and verification of the system.

#### 1.2 Scope
The ZNIX Framework will centralize and hierarchically organize user information (e.g., emails, contacts, documents) from disparate sources into a unified semantic model. Its core capabilities include automated information capture, relationship inference, hierarchical browsing, archiving, and a public API for third-party integration. The scope is limited to the high-level design and core components of the framework, targeting deployment on modest Windows-based hardware.

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **Entity:** A primary, independent information object within the ZNIX model (e.g., a Person, a Project).
*   **Associate:** A dependent information object linked to an Entity (e.g., an Email, a Document).
*   **Proxy Mechanism:** A component that intercepts data from ZNIX-unaware applications to integrate it into the framework.
*   **API (Application Programming Interface):** The public interface allowing developers to interact programmatically with the ZNIX Framework.
*   **MTBF (Mean Time Between Failures):** A reliability metric indicating the expected operational time between system failures.
*   **UTF (Unicode Transformation Format):** Standard for encoding Unicode characters.

### 2. Overall Description

#### 2.1 Product Perspective
ZNIX is a new, standalone framework that operates as a middleware layer between the user's applications and their data. It will integrate with existing software (e.g., Microsoft Outlook, Internet Explorer, Microsoft Word) via a proxy layer and provide its own user interface for browsing and management.

#### 2.2 Product Functions
The major functions of the ZNIX Framework are:
1.  **Information Capture & Integration:** Automatically ingest data from supported third-party applications.
2.  **Semantic Data Modeling:** Store data as interconnected Entities and Associates.
3.  **Relationship Management:** Automatically infer and allow manual creation of relationships between objects.
4.  **Unified Hierarchical Browsing:** Present all user information in a single, customizable, Explorer-like view.
5.  **Data Archiving:** Move data subsets to removable media while maintaining referential integrity within the system.
6.  **Developer API:** Expose a filesystem-like API for creating ZNIX-aware applications.
7.  **Proxy Mediation:** Enable transparent use of managed data by legacy applications.

#### 2.3 User Characteristics
| Stakeholder | Characteristics & Skills |
| :--- | :--- |
| **End User** | Home users, managers, executives, or researchers. Possesses basic IT skills (file management, email, web browsing). Familiar with Windows 2000/XP GUI paradigms. |
| **Developer** | Third-party application developer. Proficient in a programming language compatible with the ZNIX public API. |
| **System Administrator** | Responsible for deployment. Has experience installing software on Windows systems and managing hardware resources. |

#### 2.4 Constraints
1.  **Hardware:** Must operate on an Intel Pentium III (or compatible) 1GHz processor with 256MB of RAM.
2.  **Software:** Primary target operating systems are Windows 2000 Professional and Windows XP.
3.  **License:** The software will be released under an open-source license (LGPL/GPL).
4.  **Performance:** The framework shell process is constrained to a maximum of 40MB RAM usage.

#### 2.5 Assumptions and Dependencies
*   The specified versions of third-party applications (see Table 3.10.3-A) will remain stable and accessible for integration.
*   Users will have write access to their local file system for data storage.
*   The project's open-source distribution website will be available for launch.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Information Capture (FR-01)
*   **FR-01.1:** The system shall capture data (e.g., sent/received email, saved documents, browsed URLs) upon user-triggered events (Save, Send, Close) in supported proxy-enabled applications.
*   **FR-01.2:** The source application identifier and timestamp shall be recorded with all captured data.

##### 3.1.2 Data Storage & Classification (FR-02)
*   **FR-02.1:** The system shall store captured information as either an **Entity** (standalone object) or an **Associate** (object dependent on an Entity).
*   **FR-02.2:** The system shall allow every object to be assigned one or more user-defined or system **Categories**.
*   **FR-02.3:** The system shall provide, at a minimum, the default Categories "People" and "Email".

##### 3.1.3 Relationship Management (FR-03)
*   **FR-03.1:** The system shall automatically create relationships based on content analysis (e.g., link an email *Associate* to a person *Entity* based on the sender's address).
*   **FR-03.2:** The system shall provide a graphical user interface for users to manually create, view, and delete relationships between any two objects.
*   **FR-03.3:** All relationships shall be typed (e.g., "authored by", "pertains to") and may have a user-assigned strength/weight.

##### 3.1.4 Browsing & Navigation (FR-04)
*   **FR-04.1:** The system shall provide a hierarchical, Explorer-like interface (the "ZNIX Browser") for users to navigate all managed information.
*   **FR-04.2:** The hierarchy shall be customizable, allowing users to create virtual folders and organize objects based on Categories, Relationships, and other metadata.
*   **FR-04.3:** Selecting an object shall display its properties, content (preview), and all associated relationships.

##### 3.1.5 Archiving (FR-05)
*   **FR-05.1:** The user shall be able to select any set of Entities and/or Associates for archiving to removable media (e.g., CD-R, USB drive).
*   **FR-05.2:** Upon archiving, the original object in the central store shall be replaced with a non-removable **Archive Record** placeholder that indicates its archived status and location.
*   **FR-05.3:** The placeholder shall allow the user to view the object's metadata and provide an option to restore it from the archive media when available.

##### 3.1.6 Public API (FR-06)
*   **FR-06.1:** The system shall expose a public, filesystem-like API with operations such as `znix_create()`, `znix_query()`, `znix_modify()`, and `znix_delete()` for Entities, Associates, and Relationships.
*   **FR-06.2:** The API shall be documented in a separate Developer's Guide.

##### 3.1.7 Proxy Mechanism (FR-07)
*   **FR-07.1:** The system shall include a proxy component for Microsoft Outlook to capture email and contact data.
*   **FR-07.2:** The system shall include a proxy component for Microsoft Internet Explorer to capture browsing history and downloaded files.
*   **FR-07.3:** The system shall include a proxy component for Microsoft Word to capture document saves.

#### 3.2 External Interface Requirements

##### 3.2.1 User Interfaces
*   **UI-01:** The ZNIX Browser shall follow the graphical conventions of Windows 2000/XP (e.g., tree-view, list-view, standard menu bars).
*   **UI-02:** All graphical user interfaces shall be designed for intuitiveness, requiring less than 2 hours of training for a proficient Windows user.

##### 3.2.2 Hardware Interfaces
*   **HW-01:** The system shall support standard removable media interfaces (USB, CD/DVD) for archiving operations.

##### 3.2.3 Software Interfaces
*   **SI-01:** The public API shall be callable from C and C++ applications.
*   **SI-02:** The proxy mechanism shall interface with:
    *   Microsoft Outlook 2000/2003
    *   Microsoft Internet Explorer 6
    *   Microsoft Word 2000/2003

##### 3.2.4 Communications Interfaces
*   **CI-01:** The framework components will use local inter-process communication (IPC). No network communication is required for core functionality.

#### 3.3 Data Requirements
The system's persistent data model shall consist of the following core elements:

**Entity**
*   `Entity_ID` (PK, Unique Identifier)
*   `Name` (String)
*   `Type` (String, linked to Category)
*   `Creation_Date` (DateTime)
*   `Metadata` (Key-Value Pairs)

**Associate**
*   `Associate_ID` (PK, Unique Identifier)
*   `Entity_ID` (FK, References Entity)
*   `Content` (Binary Data or Pointer)
*   `Source_Application` (String)
*   `Creation_Date` (DateTime)

**Relationship**
*   `Relationship_ID` (PK, Unique Identifier)
*   `Source_ID` (FK)
*   `Target_ID` (FK)
*   `Type` (String)
*   `Strength` (Float, Optional)

**Archive_Record**
*   `Archive_ID` (PK, Unique Identifier)
*   `Archived_Object_ID` (FK)
*   `Storage_Media_ID` (String)
*   `Archive_Date` (DateTime)
*   `Location_Pointer` (String, e.g., file path)

#### 3.4 Non-Functional Requirements

##### 3.4.1 Performance Requirements
*   **PER-01:** The main ZNIX framework shell process shall not exceed 40MB of RAM during normal operation.
*   **PER-02:** The hierarchical view shall populate and respond to navigation actions (expand, select) with a latency of less than 2 seconds for an information store containing 10,000 objects.

##### 3.4.2 Reliability Requirements
*   **REL-01:** The system shall have a Mean Time Between Failures (MTBF) of greater than 3 months under typical daily use.
*   **REL-02:** Data corruption due to framework errors shall not occur. All data transactions shall be atomic.

##### 3.4.3 Usability Requirements
*   **USA-01:** A user familiar with Windows Explorer shall be able to perform basic navigation and search operations in the ZNIX Browser without consulting documentation.

##### 3.4.4 Supportability Requirements
*   **SUP-01:** The source code shall be released under an LGPL or GPL open-source license.
*   **SUP-02:** A public project website shall be established to host documentation, source code, and a feedback/wish-list system.

##### 3.4.5 Compatibility Requirements
*   **COM-01:** The system shall install and run correctly on Windows 2000 Professional (SP4) and Windows XP (SP2).
*   **COM-02:** The system shall be compatible with the hardware specification listed in Section 2.4.

##### 3.4.6 Security Requirements
*   **SEC-01:** The framework shall validate and sanitize all data received via the proxy mechanism from external applications to prevent injection of malicious scripts.
*   **SEC-02:** User-level permissions shall prevent the accidental corruption of relationship graphs (e.g., confirmation prompts for bulk deletions).

#### 3.5 Design Constraints
*   The core data store shall be isolated from the proxy layers to limit the impact of vulnerabilities in third-party application integrations.
