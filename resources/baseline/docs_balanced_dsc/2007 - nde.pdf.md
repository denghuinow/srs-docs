### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the NPOESS Data Exploitation (NDE) system. It serves as a comprehensive guide for developers, testers, project managers, and stakeholders to understand the system's capabilities, constraints, and external interfaces. The intended audience includes the NDE development team, NOAA management, and operational personnel.

#### 1.2 Scope
The NDE system is a mission-critical environmental data processing and distribution system. It will ingest, process, archive, and distribute satellite data from the NPP (NPOESS Preparatory Project) and subsequent NPOESS (National Polar-orbiting Operational Environmental Satellite System) missions.

**In-Scope:**
*   Ingest of Sensor Data Records (SDRs), Environmental Data Records (EDRs/xDRs), telemetry, and ancillary data from the Interface Data Processing Segment (IDPS) and other external sources (e.g., NCEP).
*   Generation of NOAA-unique and customer-tailored data products in specified formats and projections.
*   Quality monitoring of input data and output products.
*   Distribution of products via push/pull mechanisms to authorized users and systems.
*   Archival of NOAA-unique products and associated metadata to the Comprehensive Large Array-data Stewardship System (CLASS).
*   System management, scheduling, monitoring, and customer support services (help desk, subscriptions, notifications).
*   Operation across three distinct environments: Operational (OPS), System Test (TEST), and Development (DEV).

**Out-of-Scope:**
*   The development of core scientific algorithms (provided by NOAA science teams).
*   The CLASS archive system itself (an external dependency).
*   The IDPS system (an external interface).

### 2. Overall Description

#### 2.1 Product Perspective
The NDE system is a major component within the NOAA satellite data processing chain. It is a successor/complement to existing systems and interfaces directly with the IDPS for primary data ingest and with CLASS for long-term archival. It serves as the primary source for NOAA-unique products for operational and climate users.

**System Interfaces:**
1.  **IDPS Interface:** Primary source for satellite xDRs, telemetry, and status messages. (Input)
2.  **External Ancillary Data Interfaces:** Sources such as NCEP for model data. (Input)
3.  **CLASS Archive Interface:** For long-term preservation of NOAA-unique products. (Output)
4.  **Customer Delivery Interfaces:** Various protocols (e.g., FTP, SCP, HTTP/S) for pushing data to authorized user systems. (Output)
5.  **Customer Access Portal:** Web-based interface for subscription management, product browsing, and manual retrieval. (I/O)

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **System Operator** | Technical staff, 24/7 shift work. | Monitor system health, execute operational procedures, manage job queues, respond to alerts. |
| **Data Product Developer** | Scientific/technical staff. | Integrate, configure, and test new/updated processing algorithms in the DEV/TEST environments. |
| **Customer (End-User)** | NOAA operational forecasters, climate researchers, other agencies. | Subscribe to and receive data products for use in analysis, models, and decision-making. |
| **Archive Manager** | Data stewardship staff. | Ensure complete and accurate flow of data to CLASS, verify archive manifests. |

#### 2.3 Operating Environments
The system shall be deployed and function identically in three logical environments:
1.  **Development (DEV):** For integration and unit testing of new algorithms and software components.
2.  **System Test (TEST):** For integrated system testing, performance validation, and operational readiness exercises. Must be capable of acting as a failover for OPS.
3.  **Operational (OPS):** The live, 24/7 production system delivering mission-critical data products.

#### 2.4 Design and Implementation Constraints
*   Must comply with all DOC/NOAA/NESDIS and ESPC security policies and accreditation processes.
*   Must use the specified external interfaces (IDPS, CLASS) as defined in their respective ICDs.
*   Must support data formats including, but not limited to, BUFR, GRIB2, netCDF, and HDF5.
*   Infrastructure must be scalable to handle increased data volumes from NPP to NPOESS missions.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** IDPS will deliver data according to agreed-upon schedules, formats, and quality standards.
*   **Assumption:** Ancillary data feeds from external sources (NCEP, NAVOCEANO) will be stable and available.
*   **Dependency:** Successful security accreditation is a prerequisite for operational deployment.
*   **Dependency:** The system's operational timeline is dependent on the NPP/NPOESS launch schedule.

### 3. System Features and Requirements

#### 3.1 Data Ingest (DI)
**3.1.1 Description:** The system shall automatically ingest data products and messages from the IDPS and other configured external sources.
**3.1.2 Requirements:**
*   **DI-1:** The system shall poll for or receive notifications from IDPS for the availability of new xDR, telemetry, and ancillary data files.
*   **DI-2:** Upon receipt, the system shall validate the basic integrity (e.g., checksum, file size) of the ingested data.
*   **DI-3:** The system shall record all ingest events, including source, timestamp, filename, and integrity check status, in the System Event Log.
*   **DI-4:** The system shall stage successfully ingested data for subsequent processing and notify the Product Generation subsystem.

#### 3.2 Product Generation (PG)
**3.2.1 Description:** The system shall execute configured scientific algorithms to generate NOAA-unique and tailored data products.
**3.2.2 Requirements:**
*   **PG-1:** The system shall initiate product generation tasks automatically upon the availability of all required input data, as defined by the Processing Algorithm metadata.
*   **PG-2:** The system shall support the execution of algorithms configured for specific Product_Types (NOAA-Unique, Tailored).
*   **PG-3:** The system shall generate products in customer-specified formats (e.g., BUFR, GRIB2, netCDF) and map projections.
*   **PG-4:** The system shall create a complete Data Product record, including Product_ID, Generation_Timestamp, and format, for each generated product.

#### 3.3 Quality Monitoring (QM)
**3.3.1 Description:** The system shall monitor the quality of incoming data and outgoing products.
**3.3.2 Requirements:**
*   **QM-1:** The system shall perform configurable quality checks on ingested data, comparing values against defined thresholds (e.g., range, spatial consistency).
*   **QM-2:** The system shall perform configurable quality checks on generated products before distribution.
*   **QM-3:** If a quality check fails, the system shall generate an alert in the System Event Log with appropriate Severity and prevent the distribution of the affected product.
*   **QM-4:** Quality thresholds shall be configurable by authorized personnel without code deployment.

#### 3.4 Product Distribution (PD)
**3.4.1 Description:** The system shall distribute generated products to customers and external systems.
**3.4.2 Requirements:**
*   **PD-1:** The system shall make products available for customer retrieval via a secure access portal.
*   **PD-2:** The system shall automatically "push" products to external user systems based on active Data Subscriptions.
*   **PD-3:** The system shall support multiple delivery methods (e.g., FTP, SCP) as specified in the Subscription record.
*   **PD-4:** The system shall update the status of a Subscription upon successful or failed delivery attempts.

#### 3.5 Archival (AR)
**3.5.1 Description:** The system shall deliver NOAA-unique products and required metadata to the CLASS archive.
**3.5.2 Requirements:**
*   **AR-1:** Upon generation of any product with Product_Type = "NOAA-Unique", the system shall automatically package the product and its associated metadata for archival.
*   **AR-2:** The system shall transmit the archival package to the CLASS system via the defined interface.
*   **AR-3:** The system shall record an Archive Record upon receiving confirmation of successful receipt from CLASS, including the Archive_ID and Archive_Location.

#### 3.6 System Management (SM)
**3.6.1 Description:** The system shall provide capabilities for scheduling, monitoring, and maintaining operational health.
**3.6.2 Requirements:**
*   **SM-1:** The system shall provide a dashboard for real-time monitoring of system health, job status, data latency, and disk usage.
*   **SM-2:** The system shall allow authorized operators to schedule, pause, resume, and prioritize processing tasks.
*   **SM-3:** The system shall execute automated backup procedures for critical system databases and configuration files.
*   **SM-4:** The system shall implement documented restart and recovery procedures to meet Recovery Time Objectives (RTO - TBD).

#### 3.7 Customer & Help Desk Services (CH)
**3.7.1 Description:** The system shall support customer account management, product subscriptions, and trouble ticketing.
**3.7.2 Requirements:**
*   **CH-1:** The system shall provide a web portal for users to register, manage profiles, and browse available products.
*   **CH-2:** The system shall allow users to create and manage Data Subscriptions for specific products.
*   **CH-3:** The system shall send automated notifications to customers for subscription approval, product availability, and system status changes.
*   **CH-4:** The system shall provide a ticketing system for customers to report issues, which can be tracked and managed by support staff.

### 4. Non-Functional Requirements

#### 4.1 Availability
*   **NFR-AV-1:** The critical operational capabilities (Data Ingest, Product Generation, Product Distribution, Operations Monitoring) shall have a combined availability of 99.9%, meaning unplanned interruptions shall not exceed 2 hours in any 24-hour period.

#### 4.2 Performance
*   **NFR-PF-1:** **Latency:** The system shall make a generated data product available for distribution within 5 minutes of receiving the last necessary input data element from IDPS.
*   **NFR-PF-2:** **Throughput:** The system must sustain a continuous ingest and processing rate commensurate with input data volumes of 4 TB/day (NPP) and 8 TB/day (NPOESS).

#### 4.3 Reliability
*   **NFR-REL-1:** The system shall successfully execute 99% of all scheduled and event-driven processing tasks in any consecutive 30-day period.

#### 4.4 Security
*   **NFR-SEC-1:** The system shall comply with all DOC/NOAA/NESDIS and ESPC security policies, procedures, and accreditation requirements.
*   **NFR-SEC-2:** The system shall implement Role-Based Access Control (RBAC) to restrict system functions and data access based on User Authorization_Level.
*   **NFR-SEC-3:** The system shall support a Restricted Access Mode, governed by a Data Denial Plan (procedures TBD), to limit data distribution under specific security conditions.
*   **NFR-SEC-4:** All system access, data transactions, and security-relevant events shall be logged to an immutable audit trail.

#### 4.5 Scalability & Maintainability
*   **NFR-SCA-1:** The system architecture shall allow for the addition of processing, storage, and network capacity without major redesign or significant operational downtime.
*   **NFR-SCA-2:** The system shall be designed to accept technology refreshes (e.g., operating system, libraries) and updates to scientific algorithms with minimal impact on operations.

#### 4.6 Data Integrity
*   **NFR-DI-1:** The system shall protect the integrity of all data products against loss or corruption due to system errors, malfunctions, or disasters, utilizing mechanisms such as checksums, redundant storage, and the CLASS archive.
