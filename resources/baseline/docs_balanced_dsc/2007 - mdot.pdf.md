### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the VII Data Use Analysis and Processing (DUAP) System. It serves as a comprehensive guide for stakeholders, developers, testers, and project managers throughout the system's design, implementation, and validation phases. The intended audience includes all project stakeholders as identified in Section 2.

#### 1.2 Project Scope
The DUAP system is a research prototype designed to evaluate the utility of Vehicle Infrastructure Integration (VII) data for enhancing transportation safety, mobility, and asset management within the state of Michigan. The system will collect, consolidate, process, and disseminate VII probe vehicle data integrated with complementary traffic, weather, and roadway information sources.

The primary scope is to demonstrate robust data transformation and management capabilities that support operational decision-making by transportation agencies. The system is not intended for initial statewide production deployment but as a scalable proof-of-concept.

**In-Scope:**
*   Development of a service-oriented architecture for data ingestion, processing, storage, and dissemination.
*   Integration of VII probe data with defined third-party data sources.
*   Provision of web-based interfaces for defined user roles.
*   Implementation of core computational algorithms for traffic and road condition analysis.
*   System administration and configuration tools.

**Out-of-Scope:**
*   Development of in-vehicle VII hardware or roadside equipment (RSE).
*   Operation of the VII network infrastructure.
*   Long-term, high-availability production hosting and support beyond the prototype phase.
*   Development of native mobile applications.

### 2. Overall Description

#### 2.1 Product Perspective
The DUAP system is a new, self-contained software application. It will interface with multiple external systems to receive data and provide processed information to end-users and other systems. It acts as a central data fusion and analytics engine within a broader VII and transportation management ecosystem.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **TA Operator** | Monitors traffic systems; requires timely, accurate incident data. | Real-time alerts, situational awareness dashboards. |
| **TA Maintainer** | Performs physical road maintenance; works in the field. | Location-based alerts (potholes, ice), task prioritization lists. |
| **TA Asset Manager** | Performs strategic planning and analysis. | Access to historical and aggregated data, reporting tools. |
| **System Administrator** | IT professional; manages system health and configuration. | Service management, user/role administration, log viewing. |
| **Traveler** | General public; uses web browsers. | Simple, clear display of traffic, travel times, and incidents. |
| **Emergency Services** | First responders; require precise, reliable data under time pressure. | Accurate incident location and severity, potential integration with CAD. |
| **Researcher/Analyst** | Conducts data analysis; may use specialized tools. | Bulk data access, archival data querying, export capabilities. |
| **OEM / VII Entity** | Provides or manages core VII data streams. | System status, data quality feedback, interface monitoring. |

#### 2.3 Operating Environment
*   **Software:** The system shall be deployable on a standard J2EE or .NET application server. The database shall be a relational DBMS (e.g., Oracle, SQL Server, PostgreSQL). Web interfaces shall be compatible with browsers supporting HTML 4.01, JavaScript, and XML.
*   **Hardware:** The system shall be deployable on standard enterprise-grade servers meeting MDIT specifications.
*   **Networks:** The system must operate over secure government data networks and communicate with external data providers via defined protocols (e.g., HTTPS, Web Services).

#### 2.4 Design and Implementation Constraints
1.  The system architecture **shall** be service-oriented to allow for modular addition of new data sources and computational services.
2.  The system **shall** comply with all applicable MDIT security, privacy, and infrastructure standards.
3.  Data exchange with external VII components **shall** adhere to the SAE J2354 standard where specified.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** The VII POC Probe Data Service and its X-031 interface will be available for integration.
*   **Assumption:** Data sharing agreements with key third-party providers (Traffic.com, etc.) will be established.
*   **Dependency:** System functionality is dependent on the completion of the MDOT RWIS.
*   **Dependency:** Final interface specifications from certain data providers (Chrysler, SEMSIM) are pending.

### 3. System Features and Requirements

#### 3.1 Functional Requirements

##### 3.1.1 Data Ingestion & Integration (FR-DI)
*   **FR-DI-01:** The system shall collect VII probe data via the designated POC Probe Data Service interface (X-031).
*   **FR-DI-02:** The system shall integrate traffic condition data from third-party providers (e.g., Traffic.com).
*   **FR-DI-03:** The system shall integrate weather and pavement data from the MDOT RWIS.
*   **FR-DI-04:** The system shall be configurable to accept data from additional sources (transit agencies, TMCs) as formats are defined.
*   **FR-DI-05:** All ingested data shall be tagged with source, receipt timestamp, and a quality/confidence indicator.

##### 3.1.2 Data Processing & Computation (FR-DP)
*   **FR-DP-01:** The system shall derive real-time traffic speed and travel time estimates from probe vehicle data.
*   **FR-DP-02:** The system shall detect potential traffic incidents (e.g., sudden deceleration clusters) from probe data patterns.
*   **FR-DP-03:** The system shall identify and locate potholes or significant road surface anomalies based on vehicle sensor (e.g., suspension) data.
*   **FR-DP-04:** The system shall fuse data from multiple sources (VII, RWIS, third-party) to create a unified view of road conditions.
*   **FR-DP-05:** Computational algorithms shall be modular and configurable via the Administrative Services.

##### 3.1.3 Data Storage & Management (FR-DS)
*   **FR-DS-01:** The system shall cache all raw and derived data in a dynamic data store for a minimum period of one (1) week to support processing.
*   **FR-DS-02:** The system shall archive historical data (raw and processed) in a persistent data store for long-term access by researchers and asset managers.
*   **FR-DS-03:** The system shall store geographic reference data (road network, RSE locations).
*   **FR-DS-04:** The system shall store all configuration parameters, user accounts, and access rights securely.

##### 3.1.4 Information Presentation & Dissemination (FR-IP)
*   **FR-IP-01:** The system shall provide a web-based map interface for TA Operators to view real-time traffic conditions, incidents, and weather.
*   **FR-IP-02:** The system shall provide a public traveler information website displaying current travel times, congestion, and major incidents.
*   **FR-IP-03:** The system shall provide a web interface for Researchers to query, filter, and export archived geo-referenced data.
*   **FR-IP-04:** The system shall generate and disseminate automated alerts (e.g., for incidents, potholes) to subscribed users (TA Operators, Maintainers, Emergency Services) via configurable methods (e.g., dashboard, email).
*   **FR-IP-05:** The system shall package data for external systems in specified formats (e.g., SAE J2354 XML).

##### 3.1.5 System Administration (FR-SA)
*   **FR-SA-01:** The system shall provide an interface for administrators to add, modify, and remove data source configurations.
*   **FR-SA-02:** The system shall provide role-based user access control (RBAC) for all interfaces.
*   **FR-SA-03:** The system shall maintain comprehensive transaction logs for all major service activities (data ingress, processing, user access).
*   **FR-SA-04:** The system shall allow administrators to monitor system health and service status.

#### 3.2 Non-Functional Requirements

##### 3.2.1 Usability
*   **NF-UR-01:** The web interfaces for TA Operators and Travelers shall be designed for ease of use, with critical information visible within 3 clicks or 15 seconds of login/public access.
*   **NF-UR-02:** System status and error messages shall be clear and guide the user toward resolution.

##### 3.2.2 Reliability & Performance
*   **NF-PR-01:** Data presented to end-users shall be "near real-time," with a maximum latency of 2 minutes from source generation to presentation for high-priority data (incidents, major congestion).
*   **NF-PR-02:** The system shall be available for 99% of scheduled uptime during core business hours (6:00 AM - 10:00 PM EST).
*   **NF-PR-03:** The system architecture shall be designed to handle increasing data volumes as VII penetration grows.

##### 3.2.3 Supportability & Maintainability
*   **NF-SR-01:** The system shall be designed to allow new data sources, computational algorithms, and output formats to be added with minimal impact on existing services.
*   **NF-SR-02:** All system configuration shall be managed through the administrative interface or configuration files, not requiring code changes.

##### 3.2.4 Security & Privacy
*   **NF-SEC-01:** The system shall conform to all IT security standards established by MDIT.
*   **NF-SEC-02:** The system shall authenticate all users and enforce role-based access controls.
*   **NF-SEC-03:** The system shall anonymize all VII probe data to remove any direct vehicle identifier before processing and storage, in accordance with operational privacy policies.
*   **NF-SEC-04:** The system shall log all user authentication attempts and data access transactions for audit purposes.

##### 3.2.5 Implementation Constraints
*   **NF-IC-01:** Presentation services shall support standard web browsers (Internet Explorer 6.0+, Firefox 2.0+, or equivalent) capable of rendering HTML 4.01, JavaScript, and XML.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Administrative UI:** A secure, web-based interface for system configuration and user management.
*   **Operator/Maintainer UI:** A secure, role-based web portal with map views, alert panels, and data query tools.
*   **Traveler UI:** A public-facing website with traffic maps, travel time information, and incident lists.
*   **Researcher UI:** A secure web interface with advanced query builders, data visualization, and export functions.

#### 4.2 Hardware Interfaces
*   The system will interface with standard server hardware. No direct sensor or roadside hardware interfaces are within DUAP's scope.

#### 4.3 Software Interfaces
*   **VII POC Probe Service:** Interface X-031 for ingesting VII probe data.
*   **MDOT RWIS:** Web service or API for weather and pavement data.
*   **Third-Party Traffic Data (e.g., Traffic.com):** Defined XML/JSON over HTTPS feed.
*   **External Agency Systems (Deferred):** Interfaces for SEMSIM, transit agencies, etc., as formats are finalized.

#### 4.4 Communication Interfaces
*   All external communications shall use secure protocols (HTTPS, SFTP, Web Services over TLS) as required by data sharing agreements and MDIT policy.

### 5. Other Non-Functional Requirements

#### 5.1 Data Quality
Applications within the system shall evaluate the suitability of data for use based on its source, timestamp, and embedded quality flags.

#### 5.2 Legal & Compliance
The system's design and operation shall consider data use and redistribution restrictions outlined in third-party provider service agreements.

#### 6.2 Risk Analysis Summary
| Risk | Probability | Impact | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| Data Latency & Quality | Medium | High | Design applications to be tolerant of "near real-time" data with quality flags. |
| Low VII Penetration Rate | High | High | Treat as a controlled variable during prototype evaluation; plan for strategic RSE deployment. |
| Data Privacy Concerns | Medium | High | Implement and enforce strict data anonymization policies before any processing. |
| Third-Party Data Restrictions | Medium | Medium | Formalize data use constraints in service agreements and design system accordingly. |
| Unanticipated Research Needs | High | Medium | Implement a flexible, service-oriented architecture to allow easy addition of new modules. |
