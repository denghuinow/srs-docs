### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the National Library of Medicine (NLM) Digital Repository System (DRS). The purpose of this system is to provide a robust, standards-based infrastructure for the long-term preservation and access of NLM's digital biomedical collections. This document serves as a contractual agreement between the stakeholders and the development team and will be the basis for system design, implementation, and verification.

#### 1.2 Document Conventions
*   **Requirements IDs:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a desirable but not mandatory feature. "May" indicates a permissible action.
*   **Acronyms:**
    *   **AIP:** Archival Information Package
    *   **SIP:** Submission Information Package
    *   **DIP:** Dissemination Information Package
    *   **OAIS:** Open Archival Information System (ISO 14721)
    *   **PDI:** Preservation Description Information
    *   **ILS:** Integrated Library System
    *   **NIH:** National Institutes of Health
    *   **HHS:** Department of Health and Human Services

#### 1.3 Project Scope
The NLM Digital Repository System is an OAIS-conformant digital preservation repository. Its core mission is to **acquire, organize, preserve, and provide long-term access** to NLM's digital biomedical collections, encompassing both digitized legacy materials and born-digital assets.

**In-Scope:**
*   Digital collection materials under the curatorial responsibility of NLM Library Operations.
*   Full lifecycle management of digital objects as defined by the OAIS reference model (Ingest, Archival Storage, Data Management, Access, Administration, Preservation Planning).
*   Management of associated descriptive, administrative, and technical metadata.
*   Access for designated user communities (General Public, NIH Staff, NLM Staff) with appropriate rights enforcement.

**Out-of-Scope:**
*   Non-collection resources such as transactional research databases (e.g., PubMed, GenBank).
*   The initial creation of digital surrogates via digitization (the system ingests digitized files).
*   The creation of original published content.

### 2. Overall Description

#### 2.1 Product Perspective
The DRS is a major new system within the NLM IT ecosystem. It will interface with several external systems:
*   **NLM ILS:** For potential import/export of bibliographic metadata.
*   **NIH Authentication Infrastructure:** For user identity management (e.g., NIH Login).
*   **NIH National Center for Computational Sciences (NCCS):** As a geographically separate disaster recovery backup location.
*   **External Content Producers:** Via secure transfer protocols (e.g., SFTP) for SIP submission.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **General Public** | Anonymous or registered external users. Varied technical expertise. | Discover and view publicly accessible materials. Simple search/browse interface. |
| **NIH Staff** | Authenticated internal users (NIH Login). Research-oriented. | Access to materials with internal-use licenses or embargoes. Trusted IP range or authentication. |
| **NLM Staff (Metadata)** | Authenticated internal staff with specialized roles. Subject matter experts. | Interfaces for creating, editing, and validating complex descriptive metadata. |
| **NLM Staff (Object Maintenance)** | Authenticated internal staff with technical roles. | Tools for QA, virus checking, format validation, and initiating preservation actions (migrations). |
| **System Administrators** | NLM IT staff with highest privileges. | Full system configuration, user/role management, performance monitoring, and audit log review. |
| **Content Producers/Donors** | External organizations or individuals. | Clear guidelines and secure, reliable methods for transferring digital materials to NLM. |

#### 2.3 Operating Environment
*   **Software:** To be determined based on evaluation (see Undecided Issues 1). Must run on NIH-approved enterprise operating systems (Linux/Windows Server).
*   **Hardware:** Must scale to support petabytes of storage, with a hierarchical storage management (HSM) capability.
*   **Network:** Must operate within the secured NIH network enclave, accessible via the public internet for designated access functions.

#### 2.4 Design and Implementation Constraints
1.  **NFR-001:** The system **shall** conform to all applicable HHS and NIH security, privacy, and records management standards.
2.  **NFR-002:** The system **shall** implement the conceptual model and functional entities of the OAIS reference model.
3.  **Constraint:** The system must integrate with existing NIH central authentication services where possible.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** Dedicated funding and staff resources will be provided for implementation and sustained operation.
*   **Dependency:** Successful negotiation of submission agreements with content producers will define SIP structure and transfer schedules.
*   **Dependency:** Finalized preservation policies (format support, migration triggers) will inform system configuration.
*   **Dependency:** The NIH NCCS facility will be available and compatible for off-site backup.

### 3. System Features and Requirements

#### 3.1 OAIS Functional Entity: Ingest
**Description:** This feature encompasses the receipt of Submission Information Packages (SIPs) from Producers, validation of content and metadata, and the creation of Archival Information Packages (AIPs) for deposit into archival storage.

**3.1.1 Functional Requirements**
*   `FR-101:` The system shall accept SIPs via multiple transfer methods (e.g., SFTP, SCP, physical media load).
*   `FR-102:` The system shall validate that a received SIP is associated with a valid and active Submission Agreement.
*   `FR-103:` The system shall perform automated quality assurance checks on submitted files, including virus scanning, fixity verification (checksums), and format validation against policy.
*   `FR-104:` The system shall extract technical metadata from submitted files automatically where possible.
*   `FR-105:` The system shall generate a unique, persistent NLM identifier for each new AIP.
*   `FR-106:` The system shall package the validated content data and its associated metadata (descriptive, technical, administrative) into a standardized AIP format.
*   `FR-107:` The system shall provide a dashboard for NLM Staff (Object Maintenance) to monitor ingest queues, review QA results, and manually intervene in case of ingest failures.

#### 3.2 OAIS Functional Entity: Archival Storage
**Description:** This feature provides the services and functions for the secure storage, maintenance, and retrieval of AIPs.

**3.2.1 Functional Requirements**
*   `FR-201:` The system shall store AIPs on primary managed storage with redundancy (e.g., RAID, erasure coding).
*   `FR-202:` The system shall maintain at least one complete copy of all AIPs at a geographically separate location (NIH NCCS).
*   `FR-203:` The system shall regularly verify the integrity of stored AIPs using checksums and report discrepancies.
*   `FR-204:` The system shall manage a storage hierarchy, potentially moving less-accessed AIPs to lower-cost storage tiers while maintaining immediate access to metadata.
*   `FR-205:` The system shall provide a mechanism for the secure and integrity-checked retrieval of an AIP by its unique identifier for preservation or access purposes.

#### 3.3 OAIS Functional Entity: Data Management
**Description:** This feature manages the descriptive and administrative metadata database, enabling search, reporting, and administration.

**3.3.1 Functional Requirements**
*   `FR-301:` The system shall maintain a database of descriptive metadata records linked to AIP identifiers.
*   `FR-302:` The system shall provide a web-based interface for NLM Staff (Metadata) to create, read, update, and delete descriptive metadata records based on their role permissions.
*   `FR-303:` The system shall support the use of controlled vocabularies (e.g., MeSH) within metadata fields.
*   `FR-304:` The system shall store and manage administrative metadata (preservation events, access rights, source information) linked to each AIP.
*   `FR-305:` The system shall generate standard and ad-hoc reports on repository holdings, ingest statistics, and preservation actions.

#### 3.4 OAIS Functional Entity: Access
**Description:** This feature handles user requests, retrieves content and metadata, and delivers Dissemination Information Packages (DIPs) according to access controls.

**3.4.1 Functional Requirements**
*   `FR-401:` The system shall provide a public-facing web interface for searching and browsing descriptive metadata.
*   `FR-402:` The system shall enforce access controls at the object level, restricting download/viewing of content based on user class (Public, NIH, NLM) and specific rights statements.
*   `FR-403:` The system shall generate DIPs on-demand, which may consist of access derivatives (e.g., PDF, JPEG) rather than preservation master files.
*   `FR-404:` The system shall display relevant rights and licensing information to the user alongside accessible content.
*   `FR-405:` The system shall allow authenticated NIH and NLM users to discover and request access to restricted materials, where workflow permits.

#### 3.5 OAIS Functional Entity: Administration & Preservation Planning
**Description:** These cross-cutting features manage system configuration, policies, and long-term preservation strategy.

**3.5.1 Functional Requirements**
*   `FR-501:` The system shall provide an interface for System Administrators to manage user accounts and assign granular roles/permissions.
*   `FR-502:` The system shall maintain a registry of Submission Agreements and link them to ingested content.
*   `FR-503:` The system shall allow administrators to configure preservation action plans (e.g., "migrate all TIFF 6.0 files to TIFF 8.0 by 2028").
*   `FR-504:` The system shall provide alerts and reports to support preservation planning (e.g., format obsolescence warnings).
*   `FR-505:` The system shall support the governed update or removal of an AIP (Archival Information Update), with a comprehensive audit trail documenting the action and authority.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Public Access Interface:** A responsive, accessible web application supporting search, browse, and display of objects and metadata.
*   **Staff Management Interface:** A secure web portal providing role-based dashboards for metadata management, ingest review, preservation actions, and system administration.
*   **Producer Submission Interface:** Clear documentation and automated receipt endpoints (SFTP server) for content producers.

#### 4.2 Hardware Interfaces
The system must interface with large-scale, managed storage systems (SAN/NAS) and support tape or object storage libraries for backup/HSM.

#### 4.3 Software Interfaces
*   **ILS Interface:** Potential API or batch import/export for synchronizing bibliographic metadata.
*   **Authentication Interface:** LDAP or SAML 2.0 interface to NIH central authentication service.
*   **Virus Scanning Interface:** Integration with NIH-standard antivirus software APIs.

#### 4.4 Communications Interfaces
Secure, encrypted protocols (HTTPS, SFTP) shall be used for all external communications.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   `NFR-101:` The public search interface shall return initial search results for simple queries within 2 seconds under normal load.
*   `NFR-102:` The system shall support the concurrent ingest of multiple SIPs from authorized producers.

#### 5.2 Security Requirements
*   `NFR-201:` The system shall maintain an immutable audit trail for all significant actions (ingest, metadata edit, deletion, access to restricted item). `[Linked to User Story 6]`
*   `NFR-202:` All data at rest and in transit shall be encrypted using NIH-approved standards.
*   `NFR-203:` The system shall support granular, role-based access control (RBAC) for all functions.

#### 5.3 Software Quality Attributes
*   `NFR-301:` **Accessibility:** The public interface shall conform to WCAG 2.1 AA standards. `[Expands on NFR Summary 2]`
*   `NFR-302:` **Usability:** The staff interfaces shall be designed to minimize duplicate metadata entry. `[Linked to NFR Summary 6]`
*   `NFR-303:` **Interoperability:** The system shall support import/export of metadata in standard schemas (e.g., MODS, Dublin Core, PREMIS).
*   `NFR-304:` **Supportability:** The system shall provide comprehensive logging and monitoring hooks for operational support.

#### 5.4 Preservation & Compliance Requirements
*   `NFR-401:` The system shall support metadata and content in multiple languages and non-Roman scripts (Unicode UTF-8). `[Linked to NFR Summary 3]`
*   `NFR-402:` The system shall be designed to maximize automation for metadata extraction and QA processes. `[Linked to NFR Summary 5]`
*   `NFR-403:` The repository shall not be a "dark archive"; all preserved objects shall have at least their metadata publicly discoverable. `[Linked to NFR Summary 2]`

### 6. Data Definitions and Domain Model

**Core Data Entities:**
```yaml
Archival_Information_Package (AIP):
  primary_key: nlm_unique_id (String, Persistent)
  attributes:
    content_data (Binary/Reference)
    preservation_description_info (PDI)
    packaging_info (Format)
    descriptive_info (Link to Descriptive_Metadata_Record)

Descriptive_Metadata_Record:
  primary_key: record_id (UUID)
  foreign_key: links_to AIP.nlm_unique_id
  attributes:
    title (String, Multilingual)
    author (String)
    subject (Array: MeSH_Descriptors, Keywords)
    date (ISO 8601)
    resource_type (Controlled Vocabulary)

User_Account:
  primary_key: user_id (String, e.g., NIH Login)
  attributes:
    affiliation: ['Public', 'NIH', 'NLM_Staff_Metadata', 'NLM_Staff_Tech', 'Admin']
    access_level (Derived from affiliation/roles)
    authentication_credentials (Managed externally)
```

### 7. Appendices

#### 7.1 Risk Management
| Risk | Probability | Impact | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| Format Obsolescence | Medium | High | Implement active Preservation Planning (FR-503, FR-504) and define migration policies. |
| Insufficient Resources | Medium | High | Secure dedicated funding and staffing as a prerequisite for project initiation. |
| Complex Rights Management | High | Medium | Develop granular rights system (FR-402, FR-404) and clear submission agreements (FR-502). |
| Ingest of Problematic Formats | High | Low | Define acceptance policies and manual handling workflows (FR-107). |
| Data Corruption/Loss | Low | Critical | Implement integrity checking (FR-203) and geographic replication (FR-202). |

#### 7.2 Undecided Issues (To Be Resolved)
1.  **Software Platform:** Final selection of repository software (Fedora, Samvera, DSpace, commercial solution).
2.  **Technical Metadata:** Specification of required technical metadata profiles for each supported file format (e.g., based on FITS, ExifTool).
3.  **Detailed Workflows:** Specification of step-by-step ingest and QA workflows for each major content type (text, image, video, datasets).
4.  **Metadata Schema:** Finalization of the primary metadata schema(s) (e.g., MODS, VRA, TEI) and their crosswalks.
5.  **Deaccession Policy:** Technical implementation of policy for removing "Permanent" objects, if ever required.
6.  **Federated Search:** Scope and architecture for searching across this repository and other NLM digital collections.
