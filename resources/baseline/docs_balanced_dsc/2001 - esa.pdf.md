## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the ASPERA-3 Processing and Archiving Facility (APAF) ground data system. The APAF system is responsible for processing raw instrument telemetry and spacecraft ancillary data into calibrated, validated, and archived scientific data products for the ASPERA-3 instrument aboard the Mars Express (MEX) spacecraft. This SRS serves as the primary reference for developers, testers, project managers, and stakeholders throughout the software development lifecycle.

### 1.2 Scope
The APAF system will:
*   Automatically acquire daily ASPERA-3 telemetry and MEX Orbit/Attitude (OA) data from the European Space Operations Centre (ESOC) via the NASA Integrated Services Network (NISN).
*   Process raw and cleaned-up telemetry into standardized IDFS (Instrument Data File System) datasets.
*   Maintain a comprehensive local archive of all source data and generated products.
*   Provide web-based data displays for both public outreach and password-protected science team analysis.
*   Distribute processed data to ASPERA-3 Co-Investigators (Co-I's) in a timely manner.
*   Prepare and deliver validated, PDS-compliant datasets to the NASA Planetary Data System (PDS) within six months of data receipt.

The system supports the mission operations and data analysis phase of the Mars Express mission. It does not include the development of the flight instrument software or the deep-space communication network.

## 2. Overall Description

### 2.1 Product Perspective
The APAF is a standalone ground data system that interfaces with external entities (ESOC/NISN, PDS) and serves internal users (science team, public). It is part of the larger ASPERA-3 ground segment ecosystem.

**System Interfaces:**
*   **ESOC/NISN:** Primary source of input data (telemetry, OA). Interface is defined by ESOC's DDID/SGICD.
*   **PDS:** Output destination for validated archival data. Interface is defined by NASA PDS standards.
*   **Co-I's:** Recipients of distributed data products (mechanism TBD).
*   **Web Clients:** Browsers used by the public and science team to view data displays.

### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **System Operator** | SwRI technical staff. Manages daily system execution. | Automated, reliable data acquisition and processing. Clear error reporting. |
| **Scientist (Co-I)** | ASPERA-3 science team member. Expert in data analysis. | Timely access to high-quality, calibrated IDFS data. Tools for preliminary analysis. |
| **Data Archivist** | Responsible for long-term data preservation. | Robust archiving, PDS compliance, and submission capabilities. |
| **Public Outreach Officer** | Manages public engagement. | Simple, visually appealing displays of current mission status. |
| **Science Team Member** | Co-I with proprietary data access rights. | Secure, detailed, and configurable data displays for collaborative analysis. |
| **System Maintainer** | SwRI software/systems engineer. | Maintainable code, comprehensive logging, and easy re-processing capabilities. |
| **Project Management** | IRF & SwRI leads (PI, PM). | System meets scientific and schedule requirements. High-level status visibility. |

### 2.3 Operating Environment
*   **Hardware:** Designated UNIX-based production and development computers at SwRI.
*   **Software:** Operating system and necessary libraries for a UNIX environment (specifics to be defined in SDD).
*   **Network:** Persistent connection between SwRI and NISN for data transfer. Internal network for web server access.

### 2.4 Design and Implementation Constraints
1.  The system **shall** be developed to operate in a UNIX environment.
2.  The system **shall** conform to the input data formats specified by ESOC (DDID/SGICD).
3.  The system **shall** produce output data compliant with the IDFS standard and NASA PDS standards.
4.  Data processing pipelines **shall** be automated to meet the 24-hour Co-I delivery and 6-month PDS delivery timelines.

### 2.5 Assumptions and Dependencies
*   **Assumption:** ESOC will deliver telemetry and OA data daily via NISN as specified.
*   **Assumption:** The definitions of Virtual Instruments and IDFS schemas will be finalized in the Software Design Documents (SDDs).
*   **Dependency:** The project is dependent on ESOC for continuous data supply and interface stability.
*   **Dependency:** Final data distribution mechanisms to Co-I's will be defined in the APAF Operations Procedures Document six months prior to launch.

## 3. System Features and Requirements

### 3.1 Data Acquisition (FUN-1)
**Description:** The system shall automatically acquire raw telemetry data from ESOC.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-1.1** | The system shall connect to the ESOC data feed via NISN daily to check for and acquire new ASPERA-3 telemetry packets. | High |
| **FUN-1.2** | The system shall acquire Mars Express Orbit and Attitude (OA) data corresponding to the telemetry time ranges. | High |
| **FUN-1.3** | The system shall log all acquisition activities, including timestamps, data volume, and success/failure status. | Medium |
| **FUN-1.4** | The system shall implement retry logic and handle network interruptions during data transfer. | High |

### 3.2 Telemetry Processing (FUN-2)
**Description:** The system shall process raw telemetry into cleaned-up and intermediate data products.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-2.1** | The system shall accept raw telemetry packets as defined by the ESOC DDID. | High |
| **FUN-2.2** | If cleaned-up telemetry is not provided by ESOC, the system shall generate cleaned-up intermediate files from the raw packets. | High |
| **FUN-2.3** | The system shall separate telemetry by source instrument component (DPU, ELS, IMA, etc.). | High |

### 3.3 IDFS Dataset Generation (FUN-3)
**Description:** The system shall process science, engineering, and ancillary data into standardized IDFS datasets.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-3.1** | The system shall combine cleaned-up telemetry with OA data to create time-synchronized IDFS datasets. | High |
| **FUN-3.2** | The system shall apply calibration coefficients and algorithms to generate science-ready data products. | High |
| **FUN-3.3** | The system shall create IDFS datasets according to Virtual Instrument definitions and schemas. | High |
| **FUN-3.4** | Each IDFS dataset shall include all required metadata and be flagged for PDS compliance readiness. | High |

### 3.4 Data Archiving (FUN-4)
**Description:** The system shall maintain a local archive of all data.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-4.1** | The system shall store all received raw telemetry files in a designated, organized archive. | High |
| **FUN-4.2** | The system shall store all generated IDFS datasets in a designated, organized archive. | High |
| **FUN-4.3** | The archive shall be structured to allow for efficient retrieval and re-processing of data. | Medium |

### 3.5 Web-Based Displays (FUN-5)
**Description:** The system shall provide web-based interfaces for data visualization.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-5.1** | The system shall generate public web displays showing the most current mission data (e.g., latest spectra, time series). | High |
| **FUN-5.2** | The system shall provide password-protected web displays for authorized science team members, offering more detailed and configurable data analysis views. | High |
| **FUN-5.3** | Web displays shall be updated automatically upon the successful generation of new IDFS datasets. | Medium |
| **FUN-5.4** | The configuration of plot types (time series, spectra), data sources, and refresh rates shall be manageable. | Low |

### 3.6 Data Distribution (FUN-6)
**Description:** The system shall facilitate the distribution of data to Co-Investigators and the PDS.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-6.1** | The system shall distribute IDFS datasets and relevant intermediate files to all ASPERA-3 Co-Is within 24 hours of error-free acquisition and processing. | High |
| **FUN-6.2** | The system shall provide functionality to prepare a complete, validated set of IDFS data for a given time period. | High |
| **FUN-6.3** | The system shall support the submission of PDS-compliant data bundles to the NASA Planetary Data System. | High |

### 3.7 System Management & Logging (FUN-7)
**Description:** The system shall provide tools for operation and maintenance.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FUN-7.1** | The system shall maintain a comprehensive log of all system processes, including errors, warnings, and informational messages. | High |
| **FUN-7.2** | The system shall provide mechanisms for an operator to manually trigger or re-run specific processing steps. | Medium |
| **FUN-7.3** | The system shall implement error handling that prevents data corruption and allows processes to fail gracefully with alerts. | High |

## 4. Data Requirements

### 4.1 Data Entities and Attributes
*   **Telemetry Data:** `{Packet_ID, Packet_Time, Source_Instrument, Raw_Data, Receipt_Timestamp, Quality_Flag}`
*   **IDFS Dataset:** `{Virtual_Instrument_ID, Processing_Start_Time, Processing_End_Time, Instrument_Parameters[], Science_Measurements[], Calibration_Coefficients[], Metadata{}, PDS_Compliance_Flag}`
*   **Orbit/Attitude Data:** `{SC_Time, Position_X, Position_Y, Position_Z, Attitude_Q1, Attitude_Q2, Attitude_Q3, Attitude_Q4, Velocity_X, Velocity_Y, Velocity_Z, Reference_Frame}`
*   **System Log Entry:** `{Log_Timestamp, Process_Name, Event_Type, Message, Severity, Operator_ID}`

### 4.2 Data Volumes and Retention
*   Volume estimates for daily telemetry and derived products are to be defined in the SDD based on instrument modes.
*   All source and processed data shall be retained locally for the duration of the project (until at least September 30, 2007).

## 5. Non-Functional Requirements

| Category | Requirement ID | Requirement Description |
| :--- | :--- | :--- |
| **Performance** | NFR-1 | Process and deliver IDFS data to Co-I's within 24 hours of error-free telemetry receipt. |
| **Reliability** | NFR-2 | Implement automated retry logic for data transfer failures. System uptime shall be >99% during scheduled operations. |
| **Security** | NFR-3 | Web server components for science analysis shall be password-protected, restricting access to authorized ASPERA-3 team members only. |
| **Maintainability**| NFR-4 | The system shall be designed with modularity and documentation to allow for ongoing maintenance by SwRI staff. |
