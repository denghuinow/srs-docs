## **1. Introduction**

### **1.1 Purpose**
This document defines the functional and non-functional requirements for the Publications Management System (PMS). It serves as a formal agreement between the stakeholders and the development team, providing a comprehensive description of the system's intended capabilities, constraints, and behavior. The primary audience includes project managers, developers, testers, and system administrators.

### **1.2 Scope**
The PMS is a web- and command-line-accessible system designed to manage a centralized database of academic publications, including their full-text documents (PDF/PostScript). The system's core functionalities include:
*   **Automated Metadata Extraction:** Parsing bibliographic data from uploaded documents.
*   **Data Management:** Manual correction of metadata and management of author/institute aliases for name normalization.
*   **Accessible Discovery:** Robust search and download capabilities for users.
*   **Hierarchical Access Control:** A role-based permissions model, further refined by network location (VUB network vs. external).
*   **Administrative Control:** Comprehensive tools for user, group, and publication management by privileged users.

**Out of Scope:**
*   Real-time collaborative editing of publications.
*   Advanced bibliometric analysis or reporting tools.
*   Integration with external publisher APIs for automatic metadata fetching (beyond basic URL retrieval from BibTeX, which is TBD).
*   Native mobile applications.

## **2. Overall Description**

### **2.1 Product Perspective**
The PMS is a new, self-contained web application. It will interact with:
*   **Users:** Via a web browser or command-line interface.
*   **Database:** A relational database (e.g., MySQL, PostgreSQL) for persistent storage.
*   **Server:** The Linux-based "Wilma" server, which hosts the application and its dependencies (Ruby, web server).
*   **File System:** For storage of uploaded full-text publication files (PDF/PostScript).

### **2.2 User Classes and Characteristics**
| User Class            | Characteristics                                                                                                                                                               |
| :-------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guest**             | Anonymous user from outside the VUB network. Access is restricted to viewing the login/registration page only.                                                                |
| **VUB-Network User**  | User identified by an IP address within the university network. Can search and download publications **without authentication**. Cannot upload or edit.                       |
| **Member**            | Authenticated user with a basic account. Can search, view details, and download all publications. May have additional personalization features.                               |
| **Publisher**         | Authenticated user with publishing rights. Can upload publications, edit metadata for publications they uploaded, and perform bulk imports. Belongs to at least one group.    |
| **Moderator**         | Privileged user assigned to a specific department/group. Can manage (edit, approve, hide) all publications within their assigned scope and manage user levels for their group. |
| **Administrator**     | Super-user with system-wide access. Can manage all users, all groups, all publications, and system-wide configuration settings.                                                |

### **2.3 Operating Environment**
*   **Software:**
    *   Server: Ruby 1.8 or higher runtime environment.
    *   Web Server: Apache, Nginx, or equivalent (compatible with Ruby application server).
    *   Database: A supported RDBMS (e.g., SQLite for development, MySQL/PostgreSQL for production).
    *   Client: Any W3C XHTML 1.0 Transitional compliant web browser.
*   **Hardware:** The system is primarily targeted for the existing "Wilma" Linux server. Specifications must meet the performance requirements outlined in Section 4.

### **2.4 Design and Implementation Constraints**
1.  **Development Model:** The system shall be developed using a Spiral Model with two planned iterations.
2.  **Programming Language:** The core application shall be developed in Ruby.
3.  **Documentation:** Source code shall be documented using RDoc.
4.  **Architecture:** The code shall be modular and object-oriented to ensure maintainability.
5.  **Web Standards:** The user interface must generate XHTML 1.0 Transitional compliant markup.
6.  **Security:** All passwords must be encrypted using a strong, modern hashing algorithm (e.g., bcrypt) both in transit (HTTPS) and at rest in the database.

### **2.5 User Documentation**
The following user documentation shall be provided:
*   Online help system integrated into the web interface.
*   A system administrator's manual covering installation, configuration, and backup procedures.
*   A command-line interface (CLI) reference guide.

### **2.6 Assumptions and Dependencies**
*   **Assumption:** The Wilma server will maintain a stable network connection and high uptime.
*   **Assumption:** Users will have modern, standards-compliant web browsers.
*   **Dependency:** The system requires Ruby 1.8+ and a compatible database server to be installed and configured on the host machine.
*   **Dependency:** The system's availability is contingent on the Wilma server's availability.

## **3. System Features and Requirements**

### **3.1 Functional Requirements**

#### **3.1.1 User Authentication & Authorization (FR1)**
*   **FR1.1:** The system shall allow a Guest to register for a new account by providing a username, email address, and password.
*   **FR1.2:** The system shall authenticate users via username/ password.
*   **FR1.3:** The system shall automatically recognize and grant "VUB-Network User" privileges to any user accessing the system from a predefined IP range, without requiring login.
*   **FR1.4:** The system shall enforce role-based access control (RBAC) as defined in Section 2.2 for all actions.
*   **FR1.5:** The system shall provide a logout function that terminates the user's session.

#### **3.1.2 Publication Search & Browsing (FR2)**
*   **FR2.1:** The system shall provide a search interface accessible to VUB-Network Users, Members, Publishers, Moderators, and Administrators.
*   **FR2.2:** The system shall allow searching by: author name (full or partial), keyword(s) in title/abstract, and publication date range.
*   **FR2.3:** The system shall display search results in a list, showing at minimum: Title, Author(s), Publication Date, and a link to details.
*   **FR2.4:** The system shall provide a paginated view for large result sets.
*   **FR2.5:** Selecting a publication from the results shall display a detailed view containing all bibliographic metadata and an option to download the full text.

#### **3.1.3 Publication Upload & Management (FR3)**
*   **FR3.1:** The system shall allow Publishers, Moderators, and Administrators to upload new publication files (PDF, PostScript).
*   **FR3.2:** The system shall allow uploads via a BibTeX file, from which it shall automatically extract and populate bibliographic fields (Title, Authors, Abstract, Date, etc.).
*   **FR3.3:** Upon document (PDF/PS) upload, the system shall attempt to automatically extract bibliographic metadata.
*   **FR3.4:** The system shall provide an interface for the uploader (and authorized Moderators/Administrators) to manually view and correct all extracted metadata.
*   **FR3.5:** Publishers may edit or delete only the publications they have uploaded.
*   **FR3.6:** Moderators may edit or delete publications within their assigned department/group.
*   **FR3.7:** Administrators may edit or delete any publication.
*   **FR3.8:** The system shall support bulk import of publications via a structured data file (e.g., CSV, BibTeX).

#### **3.1.4 Data Management (FR4)**
*   **FR4.1:** The system shall maintain a normalized database of Authors and Institutes.
*   **FR4.2:** The system shall allow Administrators and Moderators (for their scope) to define and manage aliases for Author and Institute names to normalize variations (e.g., "VUB" -> "Vrije Universiteit Brussel").
*   **FR4.3:** The system shall store and display citation relationships between publications (References).

#### **3.1.5 Administration (FR5)**
*   **FR5.1:** The system shall provide an administrative control panel accessible only to Administrators.
*   **FR5.2:** Administrators shall be able to create, read, update, and delete User Groups.
*   **FR5.3:** Administrators shall be able to assign users to groups, modify user roles (Member, Publisher, Moderator), and assign Moderators to specific groups.
*   **FR5.4:** Administrators shall be able to configure system-wide settings via a configuration panel.

#### **3.1.6 Command-Line Interface (FR6)**
*   **FR6.1:** The system shall provide a CLI for performing key administrative and batch operations (e.g., bulk import, user management, database maintenance).

### **3.2 External Interface Requirements**

#### **3.2.1 User Interfaces**
*   The web interface shall be clean, intuitive, and adhere to W3C XHTML 1.0 Transitional standards.
*   Key pages include: Login/Registration, Search, Results, Publication Detail, Upload/Edit Publication, User/Group Management (Admin), and System Configuration (Admin).

#### **3.2.2 Hardware Interfaces**
*   The system interfaces with the server's file system for storing and retrieving uploaded document files.

#### **3.2.3 Software Interfaces**
*   **Database:** The application shall interface with a relational database via SQL queries (using an ORM like ActiveRecord).
*   **Metadata Extraction:** The system shall interface with external libraries or tools (TBD, e.g., `bibtex-ruby`, `pdftotext`) for parsing uploaded files.

#### **3.2.4 Communications Interfaces**
*   The primary communication interface is HTTP/HTTPS over TCP/IP for web access.
*   The CLI will communicate directly with the application's business logic layer.

### **3.3 Non-Functional Requirements**

#### **3.3.1 Performance Requirements**
*   **Search Response Time:** A simple search query shall return results within 3 seconds under normal load (TBD: define "normal load").
*   **Page Load Time:** Any web page shall load completely within 4 seconds under normal load.
*   **Concurrency:** The database and application shall be designed to handle [TBD: e.g., 50] concurrent users without significant degradation in performance.
*   **Upload Limit:** The maximum size for an uploaded publication file is [TBD: e.g., 100MB].

#### **3.3.2 Safety Requirements**
*   Not applicable for this software system.

#### **3.3.3 Security Requirements**
*   **SEC1:** All user passwords shall be encrypted in the database using a strong, salted one-way hash.
*   **SEC2:** All authentication sessions shall be conducted over an encrypted connection (HTTPS).
*   **SEC3:** The system shall be protected against common web vulnerabilities (e.g., SQL Injection, Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF)).
*   **SEC4:** The access control model defined in Section 2.2 shall be strictly enforced at every access point in the application logic.

#### **3.3.4 Software Quality Attributes**
*   **Reliability:** Developed using an iterative spiral model to identify and mitigate faults early. Mean Time Between Failures (MTBF) should target [TBD] hours.
*   **Availability:** System uptime shall be 99.5%, excluding scheduled maintenance and dependent on Wilma server uptime.
*   **Maintainability:** Code shall be modular, object-oriented, and documented with RDoc. The system shall be designed to allow for easy updates and feature additions.
*   **Portability:** While targeted for a Linux/Ruby environment, the design shall avoid hard-coded dependencies to facilitate potential future migration.
*   **Scalability:** The database schema and application architecture shall be designed to accommodate a growing number of publications and users.
