### 1. Introduction

#### 1.1 Purpose
This document defines the software requirements for the Gaia Object Generator (GOG). It is intended for use by the Coordination Unit 2 (CU2) development team, DPAC members, quality assurance engineers, and other stakeholders involved in the design, implementation, verification, and maintenance of the GOG software. The purpose is to provide a complete description of the system's functionality, constraints, and interfaces to guide the development process.

#### 1.2 Document Conventions
*   **Requirements:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a recommendation. "May" indicates a permissible action.
*   **Acronyms:**
    *   **CU:** Coordination Unit
    *   **DPAC:** Data Processing and Analysis Consortium
    *   **GASS:** Gaia Attitude and Sensor Simulator
    *   **GIBIS:** Gaia Instrument and Basic Image Simulator
    *   **ICD:** Interface Control Document
    *   **MDB:** Main Database
    *   **QA:** Quality Assurance
    *   **SRS:** Software Requirements Specification

#### 1.3 Project Scope
GOG is a rapid, modular software simulator designed to generate statistically equivalent catalog data, auxiliary data, and intermediate main database data for all Gaia instruments. It operates independently of GASS telemetry, GIBIS, and the main ESAC database. Its core function is to apply configurable error models to source data—either from the GaiaSimu Universe Model or a user-provided catalog—to produce simulated epoch data, combined astrometric/photometric solutions, and spectra. The realism of the simulation is directly dependent on the availability and sophistication of the integrated error models. The software shall be configurable via an input file and executable as a standalone command-line application.

### 2. Overall Description

#### 2.1 Product Perspective
GOG is a component of the broader Gaia simulation ecosystem. It interfaces with the **GaiaSimu** library for Universe Model data and source physics, and the **Gaia Tools** library for common utilities. It is a successor/companion to more detailed simulators like GIBIS, focusing on rapid, large-scale statistical simulation rather than per-CCD physics. The primary output interfaces are files formatted according to the Universe Model and MDB ICDs.

#### 2.2 Product Functions (High-Level)
1.  Parse a user-defined XML configuration file to control simulation parameters.
2.  Ingest source data from either a Universe Model snapshot or a user-provided catalog.
3.  For each source, calculate observation times and field angles for all transits.
4.  Apply user-selected instrumental and reduction noise models to generate noisy epoch measurements (astrometry, photometry, radial velocity).
5.  Statistically combine epoch data to generate a combined astrometric/photometric solution per source.
6.  Simulate BP/RP and RVS spectra with applicable noise.
7.  Write output data in formats compliant with external ICDs.
8.  Execute deterministically and be deployable on high-performance computing clusters.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **DPAC Scientist/Algorithm Developer** | Expert in Gaia data processing. Needs realistic data for testing. | Generate specific data products (catalog, MDB) for algorithm development without real telemetry. |
| **GOG User (Researcher)** | Scientist or engineer familiar with Gaia concepts. May provide custom source lists. | Configure simulations (region, noise models) to match specific study cases. |
| **GOG Developer (CU2)** | Software engineer/astronomer. Maintains and extends GOG. | Modular architecture for easy integration of new models; clear codebase. |

| **QA Engineer** | Responsible for verification and validation. | Deterministic output for testing; adherence to requirements and standards. |

#### 2.4 Operating Environment
*   **Software:** Java Runtime Environment (JRE) version 8 or later. Dependent on GaiaSimu and Gaia Tools libraries.
*   **Hardware:** Must be capable of running on standard Linux, UNIX, and macOS workstations and compute nodes.
*   **Network:** For cluster deployment, standard network file systems for input/output.

#### 2.5 Design and Implementation Constraints
1.  **Implementation Language:** Java.
2.  **Packaging:** Must be deployable as a standalone JAR (Java ARchive) file.
3.  **Interface:** Primary user interface shall be the command line and an XML configuration file.
4.  **Architecture:** Must be modular to allow for the independent development and integration of error models.
5.  **Dependencies:** Must integrate with the existing GaiaSimu and Gaia Tools libraries.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** The Gaia Universe Model and its ICD will provide a stable interface for generating source populations.
*   **Assumption:** The final MDB data model and ICD will be defined and stable prior to GOG's final release.
*   **Dependency:** The realism and completeness of GOG are directly dependent on the availability of detailed instrumental and reduction error models from other CU teams.
*   **Dependency:** Validation activities require comparison data from other simulators like GIBIS.

### 3. System Features and Requirements

#### 3.1 Feature: Configuration Management
**Description:** GOG shall be controlled by a single, well-defined XML configuration file.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-010** | The system shall load all runtime parameters from a user-specified XML configuration file. | High |
| **FR-011** | The configuration file shall specify the source input mode: "UNIVERSE_MODEL" or "USER_CATALOG". | High |
| **FR-012** | The configuration file shall allow the user to specify a sky region (e.g., RA, Dec, radius) for filtering sources from the Universe Model. | High |
| **FR-013** | The configuration file shall specify the path to a user-provided source catalog if `USER_CATALOG` mode is selected. | High |
| **FR-014** | The configuration file shall allow the user to selectively enable or disable individual instrumental and reduction noise models. | High |
| **FR-015** | The configuration file shall define the output parameters, including which data products (epoch, combined, spectra) to generate and their file formats/paths. | High |

#### 3.2 Feature: Source Data Input
**Description:** GOG shall ingest initial source data from either a built-in model or an external file.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-020** | In `UNIVERSE_MODEL` mode, the system shall query the GaiaSimu library to generate or retrieve a list of sources within the configured sky region. | High |
| **FR-021** | In `USER_CATALOG` mode, the system shall read source data (minimally `source_id`, celestial coordinates, and basic astrophysical parameters) from a user-specified file in a defined format. | High |
| **FR-022** | The system shall propagate all intrinsic source properties (coordinates, proper motion, parallax, magnitudes, spectrum, radial velocity) through the simulation chain. | High |

#### 3.3 Feature: Epoch Data Simulation
**Description:** For each source transit, GOG shall compute observed parameters with applied noise.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-030** | For each source, the system shall calculate the times and field angles (AL, AC) for all transits across all Gaia instruments based on the nominal scanning law. | High |
| **FR-031** | For each transit, the system shall compute the apparent photometric magnitude in the Gaia G, BP, and RP bands. | High |
| **FR-032** | The system shall apply enabled instrumental noise models (e.g., photon noise, CCD charge transfer inefficiency, basic calibration errors) to the ideal astrometric field angles and photometric magnitudes. | High |
| **FR-033** | The system shall apply enabled reduction noise models (e.g., attitude error, calibration model residuals) to the epoch data where applicable. | High |
| **FR-034** | The system shall generate epoch-level flags indicating the quality and processing status of each measurement. | Medium |

#### 3.4 Feature: Combined Data Calculation
**Description:** GOG shall statistically combine all epoch data for a source to produce a final astrometric and photometric solution.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-040** | For each source, the system shall combine noisy epoch astrometry (field angles, times) to solve for the five-parameter astrometric solution (position, parallax, proper motion). | High |
| **FR-041** | The system shall calculate the covariance matrix for the solved astrometric parameters. | High |
| **FR-042** | The system shall compute mean photometric magnitudes (G, BP, RP) and mean radial velocity from the epoch data. | High |
| **FR-043** | The system shall derive final astrophysical parameters (where applicable) and generate combined data flags. | Medium |

#### 3.5 Feature: Spectrum Simulation
**Description:** GOG shall generate simulated BP/RP and RVS spectra.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-050** | The system shall generate a simulated BP/RP spectrum for each source based on its intrinsic spectral energy distribution. | High |
| **FR-051** | The system shall generate a simulated RVS spectrum for each source where applicable (e.g., based on magnitude limit). | High |
| **FR-052** | The system shall apply relevant noise models (e.g., flux noise, CCD combination effects, wavelength calibration error) to the simulated spectra. | Medium |
| **FR-053** | The system shall output spectra with associated wavelength, flux, and flux error arrays. | High |

#### 3.6 Feature: Output Generation
**Description:** GOG shall write all simulated data to files in specified formats.

| Requirement ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-060** | The system shall write catalog data (combined source parameters) in a format compliant with the Universe Model ICD. | High |
| **FR-061** | The system shall write epoch data, combined data, and auxiliary data in formats compliant with the Main Database (MDB) data model ICD. | High |
| **FR-062** | The system shall write spectral data to files in a defined format specified in the configuration. | High |
| **FR-063** | The system shall generate log files documenting the simulation run, including configuration summary and any warnings/errors. | Medium |

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Command Line:** The application shall be invoked as: `java -jar gog.jar -config <path_to_config.xml>`
*   **Configuration File:** The primary user interface is an XML file. A schema (XSD) shall be provided to validate user configuration files.

#### 4.2 Software Interfaces
1.  **GaiaSimu Library:** GOG shall call functions from this library to generate sources from the Universe Model and to access astrophysical models.
2.  **Gaia Tools Library:** GOG shall use common utilities (e.g., geometry, time conversion, file I/O) from this library.
3.  **Error Model Plugins:** The architecture shall allow for error model implementations to be loaded as modular plugins conforming to a defined Java interface.

#### 4.3 Communication Interfaces
Not applicable for this standalone batch-processing application.

### 5. Non-Functional Requirements

| Requirement ID | Category | Requirement Description |
| :--- | :--- | :--- |
| **NFR-001** | Performance | The system shall process one complete source (including all transits, epoch/combined data, and spectra calculation) in an average time of ≤ 2 CPU seconds on a reference hardware specification. |
| **NFR-002** | Portability | The system shall execute identically on Linux, UNIX, and macOS platforms. Simulation results must be bitwise identical across these platforms for the same input and random seed. |
| **NFR-003** | Deployability | The system shall be distributed as a single, executable JAR file with all dependencies (excluding the JRE). |
| **NFR-004** | Scalability | The system shall be capable of running in single-threaded mode on a workstation and be amenable to parallel execution on cluster or grid environments (e.g., via job arrays where each job processes a distinct subset of sources). |
| **NFR-005** | Determinism | Given an identical configuration file and random seed, the system shall produce identical output files in subsequent runs. |
| **NFR-006** | Interoperability | Output data formats and structures shall strictly comply with the relevant external ICDs (Universe Model and MDB). |
| **NFR-007** | Reliability | The system shall handle malformed input files gracefully, providing informative error messages and exiting with a non-zero error code, without data corruption. |
| **NFR-008** | Maintainability | The software shall be designed with modularity, separating core processing, error models, I/O, and configuration. Code shall be well-documented. |

### 6. Other Requirements

#### 6.1 Data Model
Key persistent data entities include:
*   **Source:** The fundamental object. Attributes: `source_id` (Long), coordinates, astrophysical parameters.
*   **Transit:** An observation of a source. Attributes: `transit_id`, `source_id` (FK), time, field angles, photometry, flags.
*   **CombinedSolution:** The final solution for a source. Attributes: `source_id` (FK), astrometric parameters, covariance matrix, mean photometry, flags.
*   **Spectrum:** A 1D spectrum. Attributes: `spectrum_id`, `source_id` (FK), band, wavelength array, flux array.
