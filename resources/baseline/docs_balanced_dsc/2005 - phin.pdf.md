## PHIN Outbreak Management System (POMS)
**Document Version:** 1.0
**Date:** 2023-10-27
**Status:** Draft for Review

### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the PHIN Outbreak Management System (POMS). It is intended for use by project managers, developers, testers, system administrators, and stakeholders to guide the design, implementation, verification, and deployment of the system.

#### 1.2 Scope
The POMS is a configurable software platform designed to support public health agencies in the investigation, monitoring, management, analysis, and reporting of disease outbreaks and bioterrorism events. Its core scope includes:
*   The collection and management of data related to cases, contacts, exposures, specimens, and treatments.
*   The facilitation of contact tracing and exposure linking across jurisdictional boundaries.
*   The integration of laboratory results to confirm diagnoses and update case status.
*   The generation of analytical reports and visualizations for situational awareness.
*   Configurable adaptation to different event types (e.g., infectious, environmental, bioterrorism).
*   Standards-based data exchange with external public health information systems (e.g., laboratories, surveillance systems).

**Out of Scope:**
*   Direct clinical care delivery or electronic health record (EHR) functionality.
*   Management of non-health-related emergency responses (e.g., natural disasters).
*   Primary early event detection algorithms (though it will receive data from such systems).
*   Public-facing communication portals or media management.

### 2. Overall Description

#### 2.1 Product Perspective
POMS is a component within the larger PHIN architecture. It will interface with external systems as both a consumer and provider of data.

**System Interfaces:**
*   **Upstream:** Early Event Detection (EED) Systems, Syndromic Surveillance Systems.
*   **Downstream:** Laboratory Information Systems (LIS), Countermeasure/Response Administration Systems, Jurisdictional Reporting Systems.
*   **Lateral:** Other POMS instances in neighboring jurisdictions for cross-jurisdiction contact tracing.

#### 2.2 Product Functions (High-Level)
1.  **Event Management:** Register and configure new public health events.
2.  **Case Investigation:** Collect and manage case data via electronic questionnaires.
3.  **Contact Tracing & Exposure Management:** Identify, document, and monitor contacts of cases.
4.  **Specimen & Lab Integration:** Manage specimen lifecycle and integrate laboratory orders/results.
5.  **Monitoring & Follow-up:** Track the status and outcomes of cases and contacts.
6.  **Analysis & Visualization:** Generate reports, maps, epi-curves, and dashboards.
7.  **Data Exchange:** Send and receive standardized messages with partner systems.
8.  **System Configuration:** Dynamically adapt data models, forms, and workflows.

#### 2.3 User Characteristics
| Role | Expertise | Key Tasks |
| :--- | :--- | :--- |
| **Public Health Investigator** | Field epidemiology, interview skills. | Conduct investigations, administer questionnaires, trace contacts. |
| **Laboratory Technician** | Laboratory procedures, information systems. | Access lab orders, input results, ensure specimen-result linkage. |
| **Epidemiologist** | Data analysis, biostatistics, public health. | Analyze aggregated data, create visualizations, interpret trends. |
| **System Administrator** | IT administration, system configuration. | Configure events, manage users/roles, oversee data synchronization. |
| **Public Health Official** | Public health management, decision-making. | Review reports, monitor response metrics, make resource decisions. |
| **Case/Contact Subject** | Varied. | Subject of data collection (data provided *about* them, not *by* them). |

#### 2.4 Constraints
*   Must comply with all applicable federal and state health information privacy and security regulations.
*   Must adhere to PHIN technical standards and vocabulary standards (LOINC, SNOMED CT) for data exchange.
*   Must support deployment in varied IT infrastructure environments (from state-level servers to local health departments).

#### 2.5 Assumptions and Dependencies
*   **Dependencies:** Successful implementation depends on the finalization of external standards (see Milestones 1 & 2 in provided summary).
*   **Assumption:** Jurisdictions will have defined policies for data sharing and case reporting.
*   **Assumption:** Adequate training will be provided to end-users on configurable components.

### 3. Specific Functional Requirements

#### 3.1 Event Management
*   **FR-EM-01:** The system shall allow an authorized user (e.g., System Administrator, Epidemiologist) to create a new Health Event record.
*   **FR-EM-02:** During event creation, the user shall define core attributes: Event Name, Category, Start Date, Suspected Agent, and initial Case Definition.
*   **FR-EM-03:** The system shall allow the configuration of event-specific data fields and entity types to be used in investigations for this event.

#### 3.2 Case Investigation
*   **FR-CI-01:** The system shall provide functionality for a Public Health Investigator to initiate a new Case Investigation linked to a specific Health Event and Entity.
*   **FR-CI-02:** The system shall present the investigator with a dynamic, electronic questionnaire form. The fields in this form shall be configurable based on the associated Health Event's configuration (FR-EM-03).
*   **FR-CI-03:** The system shall enforce structured data entry with validation rules (e.g., date formats, required fields, value ranges) as defined in the questionnaire configuration.
*   **FR-CI-04:** The system shall allow the investigator to assign a Case Status (e.g., Suspect, Probable, Confirmed) based on collected data and the event's Case Definition.
*   **FR-CI-05:** The system shall record all investigation activity with timestamps and investigator identity.

#### 3.3 Contact Tracing & Exposure Management
*   **FR-CT-01:** From within a Case record, the system shall allow an investigator to create a new Exposure Contact record, linking a Source Entity (the case) to an Exposed Entity.
*   **FR-CT-02:** The system shall capture exposure details: Exposure Type, Dates/Times, Place of Exposure, and Health Status of the exposed entity.
*   **FR-CT-03:** The system shall provide search and visualization tools to display a network graph of exposure links between entities.
*   **FR-CT-04:** The system shall support identifying and querying exposure contacts where the linked entities are managed by a different jurisdictional instance of POMS (cross-jurisdiction tracing).

#### 3.4 Specimen Management & Laboratory Integration
*   **FR-SM-01:** The system shall allow the recording of a Specimen collected from an Entity, including Collection Date/Time, Type, Location, and Chain of Custody information.
*   **FR-SM-02:** The system shall generate a standardized electronic lab order (e.g., HL7 message) for a specimen and transmit it to a designated Laboratory Information System.
*   **FR-SM-03:** The system shall receive, parse, and store standardized laboratory result messages (e.g., HL7).
*   **FR-SM-04:** Upon receiving a result, the system shall automatically link the result to the correct Specimen record and its associated Case/Entity, based on a unique specimen identifier.

#### 3.5 Monitoring, Follow-up, and Reporting
*   **FR-MF-01:** The system shall allow users to record follow-up status updates for Cases and Contacts (e.g., "in isolation," "symptom resolution," "lost to follow-up").
*   **FR-MF-02:** The system shall provide dashboard views showing aggregate counts (e.g., total cases by status, contacts under monitoring).
*   **FR-MF-03:** The system shall generate standard epidemiological visualizations, including epi-curves (histograms of case onset dates) and thematic maps showing case/contact geography.
*   **FR-MF-04:** The system shall generate pre-defined and ad-hoc reports for Public Health Officials, including summaries of case counts, laboratory results, and countermeasure administration.

#### 3.6 System Administration & Configuration
*   **FR-SA-01:** The system shall provide a configuration interface for a System Administrator to define new Entity Types (beyond core Person, Animal, Location).
*   **FR-SA-02:** The system shall allow the administrator to add new data fields (with type, validation rules) to existing or new Entity Types and Questionnaires.
*   **FR-SA-03:** The system shall implement Role-Based Access Control (RBAC), allowing the administrator to assign users to roles with specific permissions.

#### 3.7 Data Exchange
*   **FR-DE-01:** The system shall import and export data using PHIN/HL7 implementation guides for case reporting and laboratory messaging.
*   **FR-DE-02:** For configurable/custom data fields, the system shall provide a mapping interface to translate these fields to/from standard exchange formats.
*   **FR-DE-03:** The system shall support a reliable data synchronization mechanism for clients operating in a disconnected mode.

### 4. Non-Functional Requirements

#### 4.1 Usability
*   **NF-UR-01:** Core investigative tasks (creating a case, adding a contact) shall be achievable with no more than 4 clicks/navigations from the main dashboard.
*   **NF-UR-02:** The system shall provide context-sensitive help and tooltips for all configurable fields.

#### 4.2 Reliability, Availability, and Continuity
*   **NF-RA-01:** The system shall maintain an operational uptime of 99.5% during declared public health emergencies.
*   **NF-RA-02:** The system shall support a disconnected operation mode, allowing investigators to collect data offline with robust conflict resolution upon re-synchronization.
*   **NF-RA-03:** A documented Continuity of Operations (COOP) plan shall be established for system recovery within 4 hours of a major failure.

#### 4.3 Performance
*   **NF-PR-01:** The system shall support concurrent use by at least 500 investigators during a large-scale event.
*   **NF-PR-02:** Search queries for an entity across all linked records (cases, contacts, specimens) shall return results in less than 3 seconds under normal load.
*   **NF-PR-03:** The system shall be capable of managing data for outbreak events involving up to 100,000 cases and their associated contacts.

#### 4.4 Security & Privacy
*   **NF-SP-01:** All access to the system shall require authentication.
*   **NF-SP-02:** Access to investigation data shall be strictly controlled by RBAC, ensuring users can only see data relevant to their role and jurisdiction.
*   **NF-SP-03:** All accesses and changes to case, contact, and specimen records shall be recorded in an immutable audit log.
*   **NF-SP-04:** All data in transit between system components and external partners shall be encrypted using TLS 1.2 or higher.

#### 4.5 Supportability & Configurability
*   **NF-SC-01:** The system shall allow configuration changes (new fields, entity types) to be made without requiring vendor-led code deployment or system downtime.
*   **NF-SC-02:** The system shall support the creation and deployment of pre-configured "syndromic packages" for known outbreak types (e.g., influenza, foodborne illness) to enable rapid setup.

### 5. Appendices

#### 5.1 Data Model (Simplified ER Diagram)
```yaml
HealthEvent (EventID PK)
├── has (1:M)
└── Case (CaseID PK, EventID FK, EntityID FK)
    ├── is_source_for (1:M)
    └── ExposureContact (ContactID PK, SourceEntityID FK, ExposedEntityID FK)
        └── references
Entity (EntityID PK) ──┬── is_subject_of (1:M)
                       │   Specimen (SpecimenID PK, EntityID FK)
                       │       └── yields (1:1)
                       │           LaboratoryResult (ResultID PK, SpecimenID FK)
                       └── (Person, Animal, Location subtypes)
```

#### 5.2 Undecided Issues & Open Questions
1.  The technical specification for the disconnected client synchronization protocol requires further architectural design.
2.  Operational criteria for transitioning from contact tracing to mass countermeasure administration need to be defined by public health policy stakeholders.
3.  Detailed import/export specifications for SAS, SPSS, and Excel formats will be finalized during the design phase.
4.  The extended demographic and descriptive attributes for Person entities will be defined based on a review of existing national standards (e.g., PHIN VADS).
5.  A working group will be convened to propose a standard for unique animal subject identification.
6.  External communication workflows and interfaces are considered out of scope for Version 1.0 but are noted for future consideration.
