### 1. Introduction

#### 1.1 Purpose
This document defines the functional and non-functional requirements for the Grid 3D Application. It is intended to serve as a comprehensive guide for the design, development, testing, and maintenance of the software. The primary audience includes the development team, project stakeholders, and client representatives.

#### 1.2 Scope
The Grid 3D Application is a desktop software tool designed to visualize and investigate multi-dimensional biological data within an interactive three-dimensional environment. Its core functionality includes:
*   Loading and parsing user-supplied, tab-delimited data files.
*   Rendering up to 2000 data points as a 3D scatter plot (grid).
*   Providing intuitive user controls (mouse/keyboard) for manipulating the 3D view (rotate, zoom, pan).
*   Enabling selection of individual data points to retrieve detailed attribute information.
*   Color-coding data points based on a defined cluster attribute for visual differentiation.

The application is explicitly scoped for research and presentation use within scientific domains such as parasitology and protein analysis. It is **out of scope** to perform complex statistical analysis, generate the source data, or function as a web-based or multi-user collaborative platform.

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **3D Grid:** The visual representation of data points within the three-dimensional Cartesian coordinate system rendered by the application.
*   **Data Point:** A single entity plotted in the 3D grid, representing one row from the input data file.
*   **Cluster:** A categorical attribute of a data point used to group and color-code points visually.
*   **NIMR:** National Institute for Medical Research.
*   **UCL:** University College London.
*   **SRS:** Software Requirements Specification.

### 2. Overall Description

#### 2.1 Product Perspective
The Grid 3D Application is a new, standalone desktop product. It may rely on external components for deployment (e.g., Java Runtime Environment). Its primary input is a user-generated data file, and its output is an interactive visual representation and textual data display. It does not integrate with other software systems for its core functionality.

#### 2.2 Product Functions (High-Level)
1.  **File Management:** Load and validate tab-delimited text data files.
2.  **3D Visualization:** Generate a scientifically accurate 3D scatter plot from loaded data.
3.  **View Manipulation:** Allow real-time rotation, zooming, and panning of the 3D viewport.
4.  **Data Interaction:** Support selection of individual data points via mouse interaction.
5.  **Information Display:** Show details of selected data points in a dedicated panel.
6.  **Visual Encoding:** Automatically color-code data points based on a specified cluster column.

#### 2.3 User Characteristics
| User Class | Description | Key Skills/Assumptions |
| :--- | :--- | :--- |
| **Research Scientist / Investigator** | Primary user. Analyzes biological data to identify patterns and outliers. | Deep domain knowledge. Variable computer literacy. Expects precision and clarity. |
| **Student / Trainee** | Uses application for learning and preliminary research. | May have less domain or technical experience. Requires an intuitive interface. |
| **Demonstrator / Presenter** | Uses application to illustrate findings to an audience. | Needs smooth, reliable manipulation to control the narrative during presentations. |
| **Identifier** | A role focused on the initial data loading and overview to spot points of interest. | Capable of preparing data in the required tab-delimited format. |

#### 2.4 Constraints
1.  **Platform:** Must be deployable and fully functional on Windows and Linux operating systems.
2.  **Hardware:** Must run on a mid-range personal computer (specifications TBD - see Undecided Issues).
3.  **Interface:** Must be operable using only a standard mouse and keyboard.
4.  **Deadline:** Core feature set must be complete for inclusion in a scientific paper by **March 2005**.
5.  **Data Format:** Dependent on users providing correctly formatted tab-delimited files.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** Users have the ability to generate data in the required tab-delimited format using tools like Matlab or spreadsheets.
*   **Dependency:** Final deployment packaging may depend on tools like Apache Ant.
*   **Assumption:** No user authentication or concurrent session management is required for Version 1.0.

### 3. Specific Requirements

#### 3.1 External Interface Requirements
**3.1.1 User Interfaces**
*   **UI-01: Main Application Window:** Shall contain a large 3D viewport, a menu bar (File, View, Help), a toolbar for common actions, and a side panel for data point details.
*   **UI-02: File Open Dialog:** Shall allow navigation of the filesystem to select a `.txt` or `.tsv` data file.
*   **UI-03: Information Panel:** Shall display the `Point_Name` on single-click and all `Key Fields` (see 3.5) on double-click of a data point. Text shall be selectable for copying.
*   **UI-04: Status Bar:** Shall display application status (e.g., "File loaded: 1500 points", "Ready").

**3.1.2 Hardware Interfaces**
*   The application shall accept standard mouse (with scroll wheel) and keyboard input.

**3.1.3 Software Interfaces**
*   Requires a compatible Java Runtime Environment (JRE) version [TBD] or equivalent runtime for the chosen implementation language.

**3.1.4 Communications Interfaces**
*   None required for Version 1.0.

#### 3.2 Functional Requirements
**3.2.1 Data Management**
*   **FR-01: Load Data File**
    > The system shall allow the user to load a data file via a `File > Open` menu action or toolbar button.
    *   **Fit Criterion:** User can successfully initiate a file open dialog from the UI.
*   **FR-02: Validate Data Format**
    > The system shall validate that the selected file is a plain text, tab-delimited file with a header row containing at least the following columns: `Name`, `X_Title`, `Y_Title`, `Z_Title`, `Cluster_Title`, `Description`.
    *   **Fit Criterion:** If the file format is invalid, a clear, non-technical error message is displayed, and no data is plotted.
*   **FR-03: Parse and Store Data**
    > The system shall parse the validated file, storing in memory up to 2000 data rows, each mapped to a `Data Point` entity (see 3.5).
    *   **Fit Criterion:** Application correctly reads and internally represents all data from a valid 1500-row test file.

**3.2.2 3D Visualization & Rendering**
*   **FR-04: Generate 3D Grid**
    > Upon successful data load, the system shall automatically render a 3D scatter plot within the viewport.
    *   **Fit Criterion:** A 3D graph with points plotted at coordinates (`X_Value`, `Y_Value`, `Z_Value`) is visible within 30 seconds for a 2000-point dataset.
*   **FR-05: Apply Cluster Coloring**
    > The system shall color each data point based on its integer `Cluster_Number` value, using a distinct, pre-defined color palette.
    *   **Fit Criterion:** Visual inspection confirms all points with `Cluster_Number=1` are one color, `Cluster_Number=2` another, etc.
*   **FR-06: Label Axes**
    > The system shall label the X, Y, and Z axes using the text from the `X_Title`, `Y_Title`, and `Z_Title` header columns, respectively.
    *   **Fit Criterion:** Axis labels in the viewport match the headers from the loaded file.

**3.2.3 User Interaction**
*   **FR-07: Rotate View**
    > The user shall be able to rotate the 3D grid in any direction by clicking and dragging with the left mouse button.
    *   **Fit Criterion:** Dragging the mouse results in smooth, continuous rotation of the 3D scene.
*   **FR-08: Zoom View**
    > The user shall be able to zoom the view in and out using the mouse scroll wheel or predefined keyboard shortcuts (e.g., `+`/`-`).
    *   **Fit Criterion:** Scrolling forward zooms in, making objects appear larger; scrolling backward zooms out.
*   **FR-09: Pan View**
    > The user shall be able to pan (move) the view laterally by clicking and dragging with the right mouse button (or middle button).
    *   **Fit Criterion:** Dragging with the specified button moves the entire scene without rotating it.
*   **FR-10: Select Data Point (Single-Click)**
    > The user shall be able to select a single data point by left-clicking on it. The selected point shall be visually highlighted (e.g., with a halo or increased size).
    *   **Fit Criterion:** Clicking on a point highlights it and displays its `Point_Name` in the information panel within 2 seconds.
*   **FR-11: Display Point Details (Double-Click)**
    > The user shall be able to display all stored details of a data point by double-left-clicking on it.
    *   **Fit Criterion:** Double-clicking a point populates the information panel with `Name`, `X_Value`, `Y_Value`, `Z_Value`, `Cluster_Number`, and `Description`.

#### 3.3 Performance Requirements
*   **PR-01: Startup Time:** The application shall present its main window and be ready to load a file within 30 seconds of launch on the target mid-range PC.
*   **PR-02: Interaction Responsiveness:** All user interactions (rotation, zoom, point selection) shall have a perceived delay of no more than **2 seconds** with a full load of 2000 data points.
*   **PR-03: Render Performance:** The 3D view shall maintain a minimum frame rate of 15 frames per second during continuous manipulation (e.g., mouse-drag rotation) with 2000 points.

#### 3.4 Design Constraints
*   **DC-01: Cross-Platform:** The design and implementation shall use platform-agnostic libraries (e.g., OpenGL via JOGL, JavaFX) to ensure identical behavior on Windows and Linux.
*   **DC-02: Accessibility for Print:** The default color scheme shall use high-contrast colors (e.g., dark points on a light background) to ensure legibility in printed screenshots or grayscale prints.

#### 3.5 Software System Attributes
*   **SSA-01: Usability:** The interface shall be intuitive enough for a scientist familiar with basic desktop applications to perform core functions (load data, rotate view, select point) without reference to a manual. Success will be validated via user testing with 3 representative stakeholders.
*   **SSA-02: Reliability:** The application shall not crash due to malformed data files. Errors shall be caught and presented as informative messages to the user.
*   **SSA-03: Portability:** The deliverable shall be a single executable JAR file or a similarly portable package that runs on any target machine with the correct JRE installed.

#### 3.6 Business Rules
*   **BR-01: Data Limit:** A maximum of 2000 data points may be loaded and visualized in a single session. Files with more rows shall be truncated with a warning message, or rejected.
*   **BR-02: Change Authority:** All changes to the requirements specified in this document after the baseline date must be approved in writing by **Dr Delmiro Fernandez-Reyes**.

### 4. Data Requirements
#### 4.1 Input Data Format Specification
The application requires a plain text file with **tab characters (`\t`)** as delimiters.

**Required Header Row (First Line):**
```
Name<TAB>X_Title<TAB>Y_Title<TAB>Z_Title<TAB>Cluster_Title<TAB>Description
```
**Example Data Row:**
```
Pax-6<TAB>0.75<TAB>-0.22<TAB>1.04<TAB>3<TAB>Transcription factor involved in eye development.
```

#### 4.2 Logical Data Model
*   **Entity: Data Point**
    *   **Primary Key:** `Point_Name` (String, from `Name` column)
    *   **Attributes:**
        *   `X_Value` (Float)
        *   `Y_Value` (Float)
        *   `Z_Value` (Float)
        *   `Cluster_Number` (Integer)
        *   `Description` (String)
