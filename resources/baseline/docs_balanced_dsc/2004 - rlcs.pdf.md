### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the I-15 Reversible Lane Control System (I-15 RLCS) Application Software. This document is intended for use by the project stakeholders, including Caltrans management, system developers, testers, and implementation teams, to ensure a common understanding of the system to be delivered.

#### 1.2 Scope
The I-15 RLCS Application Software will replace an aging legacy system to safely and efficiently manage the opening and closing of reversible lanes on the I-15 corridor in Southern California. The software will provide centralized monitoring, control, sequencing, data processing, and reporting functions. It will interface with new intelligent field hardware (controllers, sensors, signs, gates) via a new fiber optic network. The core purpose is to enhance traffic management during peak periods and special events while ensuring the highest levels of safety and system integrity.

**In-Scope:**
*   Centralized application software running at the Traffic Management Center (TMC).
*   Interfaces to new field controllers and devices.
*   Operator, Administrator, Maintenance, and Management user interfaces.
*   Data logging, reporting, and external system data export.
*   Safety interlocking and command validation logic.

**Out-of-Scope:**
*   Physical field hardware design and manufacturing.
*   Fiber optic network infrastructure deployment.
*   External systems (e.g., ATMS) beyond the defined data export interface.

### 2. Overall Description

#### 2.1 Product Perspective
The I-15 RLCS is a subsystem within the larger Caltrans District 11 traffic management infrastructure. It is a replacement system that must operate in parallel with the existing system during transition. The new software will interface with new field hardware and provide data to external systems like the ATMS.

**System Interfaces:**
*   **Hardware Interface (HI):** Communication with intelligent field controllers (e.g., 2070 ATC) over a fiber optic network.
*   **Software Interface (SI-1):** Export of lane status and log data to an external database/server for consumption by the ATMS.
*   **User Interfaces:** Detailed in Section 2.2.

#### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Responsibilities |
| :--- | :--- | :--- |
| **Operator** | TMC staff; trained on RLCS procedures; works in shifts. | Primary system control during Normal mode; monitors alarms; confirms scheduled sequences. |
| **System Administrator** | District 11 technical staff; high-level system access. | Configures users, devices, schedules, and system parameters; can change system mode. |
| **Field Maintenance Staff** | Field technicians; may access system remotely. | Controls system in Maintenance mode from authorized workstations/terminals for repairs. |
| **Management** | Supervisors and planners; read-only access. | Generates historical and performance reports for analysis. |
| **Electrical/Software Staff** | Support personnel; read-only access. | Performs status checks and generates reports for troubleshooting. |
| **External System (ATMS)** | Automated system; machine-to-machine interface. | Retrieves lane status data for traveler information dissemination. |

#### 2.3 Operating Environment
*   **Hardware:** Servers and workstations located at the TMC; remote dial-in terminals for maintenance; intelligent field controllers along I-15 corridor.
*   **Software:** Microsoft Windows-based operating systems for servers and workstations; commercial RDBMS (e.g., Microsoft SQL Server, Oracle); field controller firmware.
*   **Networks:** Secure LAN at TMC; dedicated fiber optic WAN to field devices.

#### 2.4 Design and Implementation Constraints
1.  Must use MD5 algorithm for password encryption and integrity verification as specified.
2.  Must support communication protocols compatible with selected field controllers (e.g., 2070 ATC).
3.  Must be designed for 24/7 operation with high availability requirements.
4.  Architectural design must be finalized by the contractor before high-level design proceeds.

#### 2.5 Assumptions and Dependencies
*   **D-1:** The new fiber optic network will be deployed and operational prior to full system integration.
*   **D-2:** New intelligent field controllers will be selected, procured, and installed.
*   **D-3:** A suitable COTS database and reporting software will be selected.
*   **Assumption:** Field hardware will provide reliable status data via the defined communication interface.

### 3. System Features and Requirements

#### 3.1 Feature: System Monitoring and Alarm Management
**Description:** The system shall continuously monitor the status of all field devices and provide real-time alerts for failures or abnormal conditions.

**3.1.1 Requirement:** The system shall poll all field device sensors and update the central status display at an interval not to exceed **2 seconds**.
**Priority:** High

**3.1.2 Requirement:** Upon detection of a status change that meets predefined alarm criteria (Critical or Warning), the system shall generate an audible and visual alarm at the operator workstation within **2 seconds**.
**Priority:** High

**3.1.3 Requirement:** The system shall maintain a real-time alarm log showing alarm type, device, location, time, and acknowledgment status.
**Priority:** Medium

#### 3.2 Feature: Lane Control and Command Processing
**Description:** The system shall allow authorized users to initiate commands to open or close reversible lanes, subject to rigorous multi-layered safety screening.

**3.2.1 Requirement:** An Operator shall be able to issue an "Open Lanes" or "Close Lanes" command via the GUI.
**Priority:** High

**3.2.2 Requirement:** Before executing any lane control command, the system shall validate the command against a set of safety rules stored in non-volatile memory at both the central and field controller levels.
**Priority:** High (Safety-Critical)

**3.2.3 Requirement:** The system shall prevent the simultaneous opening of entrances in opposite directions. This check is mandatory and non-overridable.
**Priority:** High (Safety-Critical)

**3.2.4 Requirement:** During a control sequence, if a device failure or illegal status change is detected, the sequence shall halt immediately, and the operator shall be presented with recovery options (e.g., abort, override with verification, retry).
**Priority:** High

#### 3.3 Feature: Scheduled Operations
**Description:** The system shall support time-based automatic initiation of opening and closing sequences.

**3.3.1 Requirement:** The System Administrator shall be able to create, modify, and delete schedules for lane openings and closings.
**Priority:** Medium

**3.3.2 Requirement:** The system shall check for pending scheduled operations every **60 seconds**.
**Priority:** Medium

**3.3.3 Requirement:** When a scheduled operation time is reached, the system shall present a confirmation request to the Operator for manual approval before proceeding.
**Priority:** Medium

#### 3.4 Feature: System Administration and Security
**Description:** The system shall provide tools for managing users, devices, and system configuration securely.

**3.4.1 Requirement:** A System Administrator shall be able to create, modify, and disable user accounts, assigning Personnel Classification IDs that define security levels and command permissions.
**Priority:** High

**3.4.2 Requirement:** All user passwords shall be stored in the database using **MD5 encryption**.
**Priority:** High

**3.4.3 Requirement:** The Administrator shall be able to add, modify, or decommission field devices in the system configuration without requiring programming changes or system downtime.
**Priority:** Medium

**3.4.4 Requirement:** The system shall operate in distinct modes (Normal, Maintenance, Degraded, Emergency), with control privileges automatically adjusted based on the active mode.
**Priority:** High

#### 3.5 Feature: Data Logging, Reporting, and Export
**Description:** The system shall record all activities, generate reports, and provide data to external systems.

**3.5.1 Requirement:** The system shall log all operator commands, system events, alarm events, and device status changes to a permanent database record, including timestamp and user ID.
**Priority:** High

**3.5.2 Requirement:** The system shall update an external data store (e.g., a database table or file) with current lane status and system health information at an interval not to exceed **30 seconds** for access by external systems like the ATMS.
**Priority:** Medium

**3.5.3 Requirement:** Authorized users (Management, Staff) shall be able to generate standard and ad-hoc historical reports based on logged data (e.g., operation summaries, alarm frequency reports, device performance).
**Priority:** Medium

#### 3.6 Feature: System Integrity and Reliability
**Description:** The system shall include mechanisms to ensure continuous, correct operation.

**3.6.1 Requirement:** The system shall be designed for an uptime of **≥99.99%** with a mean time to recover from a software failure of **≤10 minutes**.
**Priority:** High

**3.6.2 Requirement:** The system shall operate continuously without requiring a restart due to an RLCS software error for a minimum of **30 consecutive days**.
**Priority:** High

**3.6.3 Requirement:** A one-way hash function (**MD5**) shall be used to verify the integrity of software and configuration data in field controllers. This verification shall run automatically once every 24 hours and shall be available on-demand.
**Priority:** High

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   **Operator GUI:** Graphical map-based display of the I-15 corridor showing real-time device status (color-coded), lane status, alarms, and control buttons. Must be intuitive for rapid decision-making.
*   **Administration GUI:** Forms-based interfaces for user management, device configuration, schedule management, and system parameter settings.
*   **Reporting Interface:** A web-based or client-based portal for generating and viewing pre-defined and custom reports.
*   **Maintenance Interface:** A simplified, secure interface accessible from remote terminals for maintenance mode control.

#### 4.2 Hardware Interfaces
*   The software shall communicate with field controllers using a standard protocol (e.g., NTCP over TCP/IP) via the provided fiber optic network interface card in the central server.

#### 4.3 Software Interfaces
*   **SI-1: External Data Export:** The system shall write lane status (`OPEN`, `CLOSED`, `TRANSITION`, `FAULT`) and timestamp to a designated table in a separate SQL database via a secure connection (e.g., ODBC/JDBC).

#### 4.4 Communications Interfaces
*   Communication with field devices shall be over a dedicated, secure fiber optic network. The software shall support reconnection logic in case of temporary network outages.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   GUI status updates: ≤ 2 seconds from field event.
*   Alarm notification: ≤ 2 seconds from detection.
*   Command validation and initiation: ≤ 5 seconds from operator confirmation.
*   External data export update cycle: ≤ 30 seconds.

#### 5.2 Safety Requirements
*   The system shall implement redundant, multi-level safety screening (central and field) for all lane control commands.
*   Safety rules shall be stored in non-volatile memory at the field controller level to ensure enforcement even if central communication is lost.
*   Design shall include degraded modes of operation (e.g., local control at FCU/DCU) to maintain basic safety during partial system failures.

#### 5.3 Security Requirements
*   Authentication via login initials and MD5-encrypted passwords.
*   Role-based access control (RBAC) tied to Personnel Classification ID.
*   Command-level security to ensure users can only execute commands permitted by their role and the current system mode.
*   External data export shall be a one-way, read-only interface for external systems.

#### 5.4 Software Quality Attributes
*   **Availability:** 99.99% uptime (≤52.6 minutes downtime/year).
*   **Reliability:** Mean Time Between Software Failures (MTBSF) > 30 days.
*   **Maintainability:** System configuration (devices, users, schedules) shall be modifiable through admin GUI without code changes. Remote administration shall be supported.
*   **Scalability:** The architecture shall support a minimum 20% increase in the number of field devices without significant performance degradation. (Specific limits TBD per Undecided Issue #5).
