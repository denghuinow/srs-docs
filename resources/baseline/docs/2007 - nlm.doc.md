## 1. Introduction

### 1.1 Purpose
This document provides a detailed description of the Software Requirements Specification (SRS) for the National Library of Medicine (NLM) Digital Repository. It specifies the functional and non-functional requirements for a system designed to preserve and provide access to the NLM's biomedical digital content. This SRS is intended for use by the project managers, developers, testers, and stakeholders involved in the system's implementation and validation.

### 1.2 Scope
The NLM Digital Repository is a preservation and access system for both digitized and born-digital materials within the NLM's collections. The system will manage the entire digital asset lifecycle, including **ingest, archival storage, data management, administration, preservation planning, and access**.

**Out-of-Scope:**
*   Management of projects outside the responsibility of Library Operations (e.g., UMLS, Visible Human Project).
*   Web harvesting or crawling functionality.
*   Provision of special software or viewers for accessing materials; standard formats will be used.

## 2. Overall Description

### 2.1 Product Perspective
The NLM Digital Repository is conceived as a trusted digital repository built upon the **OAIS reference model**. It is not a standalone system but a core component of the NLM's digital infrastructure. It will integrate with existing systems such as PubMed Central and Bookshelf for content ingestion and dissemination. It replaces legacy preservation methods like microfilming, addressing the unique challenges of digital preservation, including format obsolescence and media decay.

### 2.2 Product Functions
The system's core functions are organized around the OAIS functional model:
1.  **Ingest:** Accept Submission Information Packages (SIPs), perform quality assurance, and generate Archival Information Packages (AIPs).
2.  **Archival Storage:** Manage storage media, perform error checking, and provide for disaster recovery.
3.  **Data Management:** Administer the descriptive, technical, and preservation metadata; handle queries and reporting.
4.  **Administration:** Manage system policies, negotiate submission agreements, and audit system operations.
5.  **Preservation Planning:** Monitor the technology environment and develop migration and preservation strategies.
6.  **Access:** Handle user requests for Dissemination Information Packages (DIPs) with appropriate access controls.

### 2.3 User Characteristics
| User Role | Key Characteristics & Access Level |
| :--- | :--- |
| **General Public** | Read-only access to publicly available materials. Access may be restricted by licensing agreements or embargo periods. |
| **NIH Staff** | Read-only access to a broader set of materials than the public, potentially based on network location (IP range) and embargo status. |
| **NLM Staff (Metadata Editor)** | Read and write access to descriptive and administrative metadata for assigned collections. |
| **NLM Staff (Object Maintainer)** | Access to perform preservation actions on digital objects (e.g., run fixity checks, initiate migrations). |
| **NLM System Administrator** | Full administrative control over the system, including user management, policy configuration, and system monitoring. |

### 2.4 Constraints
*   The system must prioritize the preservation of **intellectual content** over the original "look and feel" of the object.
*   Original physical collections must be maintained after digitization.
*   The repository must not be a "dark archive"; all preserved objects must be available for access and use.
*   The system must support multiple, simultaneous ingest streams from various sources.

### 2.5 Assumptions and Dependencies
*   **Assumption:** The NIH Consolidated Collocation Site (NCCS) will provide a reliable, geographically separate location for disaster recovery backups.
*   **Assumption:** The Integrated Library System (ILS) will serve as the authoritative source for core bibliographic metadata.
*   **Dependency:** Compliance with HHS and NIH information security standards is mandatory.
*   **Dependency:** The system's acceptance is dependent on its compliance with the OAIS reference model and NLM's established collection policies and permanence rating system.

## 3. System Features

This section details the functional requirements for each OAIS functional area.

### 3.1 Ingest Functional Area
**3.1.1** The system shall accept Submission Information Packages (SIPs) from designated sources (e.g., PubMed Central, internal digitization projects).
**3.1.2** The system shall validate the structural and syntactic integrity of the SIP upon receipt.
**3.1.3** The system shall perform quality assurance (QA) checks on the content of the SIP, including virus scanning and file format validation.
**3.1.4** The system shall generate an Archival Information Package (AIP) from the validated SIP, including the addition of preservation metadata (PREMIS).
**3.1.5** The system shall assign a unique, persistent identifier to each AIP.
**3.1.6** The system shall send a confirmation or failure report to the submitting entity.

### 3.2 Archival Storage Functional Area
**3.2.1** The system shall store AIPs on managed, secure storage media.
**3.2.2** The system shall generate a checksum (e.g., SHA-256) for each file in an AIP upon ingest.
**3.2.3** The system shall perform scheduled fixity checks on all stored AIPs by recalculating and comparing checksums, and report any discrepancies.
**3.2.4** The system shall provide a mechanism for repairing or replacing corrupted files from a known-good copy (e.g., from the disaster recovery site).
**3.2.5** The system shall automatically replicate all AIPs and essential metadata to the off-site NCCS backup facility to support disaster recovery.

### 3.3 Data Management Functional Area
**3.3.1** The system shall store and manage descriptive (e.g., Dublin Core), administrative, and technical (PREMIS) metadata for all AIPs.
**3.3.2** The system shall support querying the metadata database via a standard API (e.g., SQL, REST).
**3.3.3** The system shall generate standard and ad-hoc reports on repository holdings, ingest statistics, and preservation activities.
**3.3.4** The system shall provide an OAI-PMH endpoint to allow external systems to harvest public metadata.

### 3.4 Administration Functional Area
**3.4.1** The system shall provide a secure interface for administrators to manage user accounts and role-based permissions.
**3.4.2** The system shall allow administrators to configure and manage submission agreements with content providers.
**3.4.3** The system shall maintain audit trails for all significant system events (e.g., ingest, deletion, user access).

### 3.5 Preservation Planning Functional Area
**3.5.1** The system shall monitor and report on the file formats in the repository.
**3.5.2** The system shall alert administrators when file formats are at risk of obsolescence.
**3.5.3** The system shall provide tools for administrators to plan and execute preservation actions, such as format migration.

### 3.6 Access Functional Area
**3.6.1** The system shall provide a public-facing interface for discovering and accessing repository content.
**3.6.2** The system shall enforce access restrictions based on user role, IP address, and embargo dates as defined by object-level metadata.
**3.6.3** For authorized users, the system shall generate and deliver a Dissemination Information Package (DIP), which may be a derivative of the AIP (e.g., a PDF instead of a TIFF master).
**3.6.4** The system must support the display and processing of multiple languages and non-Roman scripts (e.g., Cyrillic, CJK).

## 4. External Interface Requirements

### 4.1 User Interfaces
*   **Administrative UI:** A web-based interface for repository management, with role-based views for metadata editors, object maintainers, and system administrators.
*   **Public Access UI:** A public website for searching, browsing, and viewing/downloading available content. The interface must be fully accessible per Section 508 guidelines.

### 4.2 Hardware Interfaces
The system must interface with high-capacity, redundant storage systems (e.g., SAN/NAS) for primary storage and the infrastructure at the NCCS for backup.

### 4.3 Software Interfaces
| Interface | Purpose & Requirements |
| :--- | :--- |
| **Integrated Library System (ILS)** | To retrieve and synchronize authoritative bibliographic metadata. Interaction via a standard API (e.g., REST, Z39.50). |
| **PubMed Central / Bookshelf** | To serve as a source of SIPs for born-digital content. |
| **NIH Consolidated Collocation Site (NCCS)** | To transfer backup data for disaster recovery purposes. |
| **OAI-PMH Harvesters** | To expose public metadata for harvesting by external aggregators. |

### 4.4 Communications Interfaces
All external communications, especially those involving transfer of AIPs or sensitive metadata, must use secure protocols (e.g., HTTPS, SFTP).

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   **Ingest:** The system must be able to process concurrent ingest streams from multiple sources without significant degradation in performance.
*   **Access:** Search results for simple queries shall be returned in under 3 seconds. Delivery of standard DIPs (e.g., PDFs) shall be initiated within 5 seconds of user request.
*   **Fixity Checking:** The system must be capable of performing a full fixity audit of the entire repository within a predefined maintenance window (e.g., 30 days).

### 5.2 Security Requirements
*   The system shall comply with all HHS and NIH security and privacy policies.
*   All user authentication shall be performed via the central NIH authentication system.
*   All data at rest and in transit must be encrypted using FIPS 140-2 validated cryptographic modules.
*   The system shall implement role-based access control (RBAC) to enforce the principle of least privilege.

### 5.3 Software Quality Attributes
*   **Reliability:** The system must achieve 99.9% uptime for access functions. Preservation functions (storage, fixity) must be highly resilient.
*   **Integrity:** Data integrity is paramount. The use of CRCs and other checksums must provide a statistically acceptable level of error detection.
*   **Maintainability:** The system shall be designed with modular components to facilitate updates and maintenance.
*   **Usability:** Administrative interfaces shall be intuitive and require minimal training for users familiar with digital library concepts.

### 5.4 Business Rules
*   The **highest priority** is the preservation of intellectual content.
*   Acceptance of content into the repository is governed by NLM's existing collection policies and selection criteria for digitization.
*   All objects will be assigned a permanence rating of either "Permanent" or "Permanence Not Guaranteed" based on predefined criteria.
*   The system's design and operation must be verifiable against the OAIS reference model.
