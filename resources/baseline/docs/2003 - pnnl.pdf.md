## 1. Introduction

### 1.1 Purpose
This document specifies the requirements for an Automated Fault Detection and Diagnostics (AFDD) system for HVAC chiller and cooling tower subsystems. It serves as a comprehensive guide for developers, testers, and stakeholders to ensure the system meets intended functionality and performance standards.

### 1.2 Scope
The system automates fault detection and diagnostics for chiller and cooling tower subsystems, replacing manual visual analysis by human experts. The tool detects operational faults, provides visual indicators with detailed information, and stores results for historical review.

**In-Scope:**
- Chiller subsystem fault detection and diagnostics
- Cooling tower subsystem fault detection and diagnostics
- Real-time and batch data processing
- Historical data storage and retrieval
- Role-based user access

**Out-of-Scope:**
- Boiler diagnostics (excluded from initial version)
- User-defined analysis beyond predefined fault categories
- Printed reports (screen printing only)
- Non-Windows operating systems

## 2. Overall Description

### 2.1 Product Perspective
The system replaces a manual diagnostic process where data acquisition devices feed into graphical display software for human review. The tool preserves the logical construction of the current process (preprocessing, diagnostic, output components) but automates the diagnostic phase.

### 2.2 Product Functions

#### Core Functional Capabilities:
1. **Fault Detection & Identification**
   - Detect faults in chiller and cooling tower subsystems
   - Identify specific operational faults from predefined categories
   - Provide visual indicators (OK, Caution, Not OK)

2. **Diagnostic Information Management**
   - Display fault descriptions, causes, and recommended fixes
   - Store diagnostic results with metadata
   - Support historical data review

3. **Data Processing**
   - Handle real-time data from acquisition devices
   - Process batch data from files
   - Validate input data against defined ranges

4. **System Configuration**
   - Adjust diagnostic parameters and sensitivity
   - Manage fixed data configuration
   - Support role-based access control

5. **User Authentication**
   - Authenticate users with three-attempt limit
   - Provide role-based permissions (general user vs. administrator)

### 2.3 User Characteristics

#### 2.3.1 General Users (Building Operators)
- **Primary Role:** View current and historical diagnostics
- **Usage Frequency:** Periodic (seconds to minutes)
- **Technical Knowledge:** HVAC system expertise with varying computer skills
- **Responsibilities:** Monitor system status, identify fault conditions

#### 2.3.2 Administrators
- **Service Technicians:**
  - Usage: Daily (up to hours)
  - Responsibilities: Configure diagnostics, adjust sensitivity, modify fixed data

- **Energy Providers:**
  - Usage: Continuous remote monitoring
  - Responsibilities: System configuration, performance monitoring

- **Building Operator Supervisors:**
  - Usage: Decision support for work assignments
  - Responsibilities: Review diagnostics, allocate resources

### 2.4 Constraints
- **Platform:** Windows-compatible operating systems only
- **Scope:** Initial version excludes boiler diagnostics
- **Reporting:** No printed reports (screen printing only)
- **Data Processing:** No diagnostic processing when input data is missing
- **Analysis:** Limited to predefined fault categories

### 2.5 Assumptions and Dependencies
- Users possess HVAC system knowledge
- Data acquisition devices provide reliable input data
- System operates continuously for indefinite duration
- Configuration management of fixed data is required
- Missing data is handled with defined indicators

## 3. Specific Requirements

### 3.1 External Interface Requirements

#### 3.1.1 User Interfaces
The system shall provide six primary windows with hierarchical navigation:

1. **Main Window**
   - System overview and navigation hub
   - Access to all major functions

2. **Configuration Window**
   - Diagnostic parameter settings
   - Sensitivity adjustments
   - Fixed data management (administrators only)

3. **Subsystems Window**
   - Chiller and cooling tower subsystem status
   - Visual fault indicators
   - Navigation to detailed views

4. **Condition Window**
   - Detailed operational conditions
   - Real-time data display
   - Historical trend visualization

5. **Diagnostic Information Window**
   - Fault descriptions, causes, and recommended fixes
   - Contextual help information
   - Actionable guidance

6. **Diagnostic History Window**
   - Historical fault records
   - Filtering and search capabilities
   - Time-based analysis

#### 3.1.2 Hardware Interfaces
- **Data Acquisition Devices:** Real-time sensed data input
- **File Systems:** Batch data processing from files
- **Windows-compatible platforms only**

#### 3.1.3 Software Interfaces
- **Operating System:** Windows-compatible platforms
- **Data Formats:** Standardized input formats for sensed data
- **Authentication:** Role-based access control system

#### 3.1.4 Communication Interfaces
- Real-time data acquisition protocols
- File-based batch processing
- User authentication services

### 3.2 Functional Requirements

#### 3.2.1 Fault Detection and Diagnostics

**FR-001: Fault Detection**
```
The system shall detect operational faults in chiller and cooling tower subsystems
based on sensed and fixed data inputs.
Priority: High
```

**FR-002: Fault Identification**
```
The system shall identify specific faults from predefined categories as specified
in Table 7 of project requirements.
Priority: High
```

**FR-003: Visual Indicators**
```
The system shall provide clear visual fault indicators:
- OK (Green): Normal operation
- Caution (Yellow): Warning condition
- Not OK (Red): Fault condition
Priority: High
```

**FR-004: Diagnostic Information**
```
The system shall display comprehensive fault information including:
- Fault description
- Root causes
- Recommended corrective actions
Priority: High
```

#### 3.2.2 Data Management

**FR-005: Data Storage**
```
The system shall store diagnostic results with:
- Absolute timestamp
- Unit identity
- Diagnostic identity
- Three significant figures precision for sensed data
Priority: High
```

**FR-006: Data Validation**
```
The system shall validate sensed data against defined ranges:
- Temperature: -40°F to 130°F
- Other parameters as specified in technical specifications
Priority: High
```

**FR-007: Missing Data Handling**
```
The system shall handle missing data using defined indicators:
- Null values for missing data points
- No diagnostic processing when required data is missing
Priority: Medium
```

#### 3.2.3 User Management

**FR-008: User Authentication**
```
The system shall authenticate users with:
- Username/password verification
- Three attempt limit before dismissal
- Session management
Priority: Medium
```

**FR-009: Role-Based Access**
```
The system shall provide two user roles:
- General Users: View current/historical diagnostics
- Administrators: Configuration and system management
Priority: Medium
```

#### 3.2.4 System Configuration

**FR-010: Parameter Configuration**
```
The system shall allow administrators to:
- Configure diagnostic parameters
- Adjust sensitivity settings
- Modify fixed data (set points, specifications)
Priority: Medium
```

**FR-011: Processing Duration**
```
The system shall support indefinite duration diagnostic processing
for continuous operation.
Priority: Medium
```

### 3.3 Performance Requirements

**PR-001: Data Precision**
```
Sensed data shall be stored with three significant figures precision.
```

**PR-002: Response Time**
```
The system shall provide diagnostic results within:
- Real-time mode: < 5 seconds from data receipt
- Batch mode: Processing time proportional to data volume
```

**PR-003: Availability**
```
The system shall maintain 99.5% operational availability during normal
business hours.
```

**PR-004: Concurrent Users**
```
The system shall support up to 50 concurrent users without performance
degradation.
```

### 3.4 Design Constraints

**DC-001: Platform Compatibility**
```
The system shall operate exclusively on Windows-compatible operating systems.
```

**DC-002: Scope Limitation**
```
The initial version shall focus exclusively on chiller and cooling tower
subsystems, excluding boiler diagnostics.
```

**DC-003: Reporting Limitations**
```
The system shall operate without printed reports, supporting only
screen printing functionality.
```

### 3.5 Software System Attributes

#### 3.5.1 Reliability
- Mean Time Between Failures (MTBF): > 720 hours
- Automatic recovery from non-fatal errors
- Data integrity validation

#### 3.5.2 Availability
- 24/7 operational capability
- Scheduled maintenance windows with advance notification
- Graceful degradation during partial system failures

#### 3.5.3 Security
- Three-attempt authentication limit
- Role-based access control
- Session timeout after 30 minutes of inactivity
- Secure data transmission for remote access

#### 3.5.4 Maintainability
- Modular architecture for easy updates
- Comprehensive logging and debugging support
- Configuration management for fixed data

#### 3.5.5 Portability
- Windows OS compatibility requirement
- Standardized data formats for easy integration
- Hardware-agnostic data acquisition interfaces

### 3.6 Business Rules

**BR-001: Fault Processing**
```
Diagnostics shall not be processed when required input data is missing.
```

**BR-002: User Access**
```
Configuration changes shall be restricted to administrator role only.
```

**BR-003: Data Retention**
```
Historical diagnostic data shall be maintained for minimum 2 years.
```

## 4. Verification and Acceptance

### 4.1 Acceptance Criteria

#### 4.1.1 Primary Acceptance Requirements
- Detection of all faults listed in Table 7 with associated descriptions, causes, and fixes
- Accurate fault identification for specified subsystems and fault categories
- Storage of diagnostic results with absolute time, unit identity, and diagnostic identity

#### 4.1.2 Secondary Acceptance Requirements
- Clear user interface with role-based access
- Proper handling of missing data scenarios
- Accurate data validation against defined ranges

### 4.2 Testing Priorities

#### Priority 1 (Critical):
- Fault detection accuracy
- Data storage integrity
- Basic user authentication

#### Priority 2 (High):
- User interface functionality
- Role-based access control
- Configuration management

#### Priority 3 (Medium):
- Performance under load
- Long-duration operation
- Error handling and recovery

### 4.3 Validation Methods

| Requirement Type | Validation Method |
|-----------------|-------------------|
| Fault Detection | Test against known fault scenarios |
| Data Storage | Verify data integrity and precision |
| User Interface | Usability testing with target users |
| Performance | Load testing and stress testing |
| Security | Penetration testing and access control verification |
