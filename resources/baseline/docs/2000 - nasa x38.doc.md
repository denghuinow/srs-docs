## 1. Introduction

### 1.1 Purpose
This document provides a detailed description of the Software Requirements Specification (SRS) for the Fault Tolerant System Services (FTSS). The FTSS is the core software layer for NASA's X-38 Flight Critical Computer (FCC), providing critical services for quad-redundant operation. This SRS is intended for developers, testers, project managers, and other stakeholders involved in the implementation and verification of the FTSS.

### 1.2 Scope
The FTSS provides the foundational software services that enable the reliable, fault-tolerant operation of the X-38 Crew Return Vehicle's flight computer. Its scope encompasses:

*   **In-Scope:**
    *   Scheduling Services for task execution across vehicle modes.
    *   Inter-processor Communication Services.
    *   Fault Detection, Isolation, and Recovery (FDIR).
    *   Redundancy Management for processors and network elements.
    *   Memory Management, including scrubbing and alignment.
    *   Time Services for mission and separation elapsed time.
    *   The Application Programming Interface (API) for flight software.

*   **Out-of-Scope:**
    *   The design of underlying hardware components.
    *   The development of specific vehicle application code (e.g., guidance, navigation, and control algorithms).
    *   User interface development for ground personnel.

## 2. Overall Description

### 2.1 Product Perspective
The FTSS is a core component of the X-38 avionics software suite. It is positioned as a middleware layer between the VxWorks 5.4 operating system and the vehicle's flight application software. The system operates on a quad-redundant set of Flight Critical Processors (FCPs), interfacing with five Instrument Control Processors (ICPs) and managing communication across five Network Elements (NEs) to form a robust, fault-tolerant computing platform based on Draper's FTPP architecture.

### 2.2 Product Functions
The high-level functions of the FTSS are:
1.  **Scheduling:** Manage and schedule task execution in predefined rate groups.
2.  **Communication:** Facilitate reliable, synchronous data exchange between processors.
3.  **Fault Tolerance:** Detect, isolate, and recover from hardware faults.
4.  **Redundancy Management:** Manage the set of active processors and network elements.
5.  **Memory Management:** Ensure data integrity through scrubbing and maintain consistency during recovery.
6.  **Time Services:** Provide and maintain a synchronized, high-accuracy time reference across the system.

### 2.3 User Characteristics
The primary users of the FTSS are indirectly involved:
*   **NASA Flight Operations Personnel:** Rely on the system's correct and fault-tolerant operation during flight. No direct interaction is required.
*   **System Maintainers:** Interact with the system during ground operations for initialization, testing, and diagnostics.

### 2.4 Constraints
*   **Hardware:** Must execute on the Radstone Power PC 604R processor.
*   **Operating System:** Must be compatible with VxWorks 5.4.
*   **Memory:** Must not exceed 3 MB of ROM and 9 MB of DRAM.
*   **Fault Tolerance:** Must support continuous operation with any 3 of 5 active Fault Containment Regions (FCRs).
*   **Architecture:** Must be compatible with the existing X-38 avionics architecture and flight software.

### 2.5 Assumptions and Dependencies
*   It is assumed that the underlying VxWorks 5.4 OS and Radstone hardware function as specified.
*   The system's fault tolerance is dependent on the integrity of the hardware Fault Containment Regions (FCRs).
*   The system depends on the correct implementation of the communication interfaces with the ICPs and NEs.

## 3. Specific Requirements

### 3.1 External Interface Requirements

#### 3.1.1 Software Interfaces
*   **SI-1: VxWorks 5.4:** The FTSS shall interface with and utilize the services of the VxWorks 5.4 real-time operating system.
*   **SI-2: Flight Application Software:** The FTSS shall provide a defined API for all flight software applications to access scheduling, communication, and time services.

#### 3.1.2 Hardware Interfaces
*   **HI-1: Radstone PPC 604R:** The software shall be compiled and executed on the Radstone Power PC 604R hardware platform.
*   **HI-2: Network Elements (NEs):** The software shall manage communication through five independent Network Elements.
*   **HI-3: Multi-Protocol Communications Controller (MPCC):** The software shall utilize the MPCC for inter-processor data transfer.

#### 3.1.3 Communication Interfaces
*   **CI-1: FCP-ICP Communication:** The FTSS shall manage the communication link between the four Flight Critical Processors (FCPs) and the five Instrument Control Processors (ICPs).
*   **CI-2: Inter-FCP Communication:** The FTSS shall provide transparent communication between processors within the virtual group.

### 3.2 Functional Requirements

#### 3.2.1 Scheduling Services
*   **FUNC-SCHED-001:** The system shall manage task execution in three distinct rate groups: 50Hz, 10Hz, and 1Hz.
*   **FUNC-SCHED-002:** The system shall support multiple vehicle modes of operation.
*   **FUNC-SCHED-003:** The system shall complete a transition between any two vehicle modes within 1.02 seconds.

#### 3.2.2 Communication Services
*   **FUNC-COMM-001:** The system shall provide synchronous message queues for inter-processor communication.
*   **FUNC-COMM-002:** The system shall provide immediate pipes for low-latency, inter-processor data transfer.
*   **FUNC-COMM-003:** Communication between virtual groups shall be transparent to the application software.

#### 3.2.3 Fault Detection and Isolation
*   **FUNC-FDI-001:** The system shall perform an Initial Built-In Test (IBIT) upon system startup.
*   **FUNC-FDI-002:** The system shall perform a Continuous Built-In Test (CBIT) during normal operation.
*   **FUNC-FDI-003:** The system shall be capable of isolating a faulty processor or network element.

#### 3.2.4 Redundancy Management
*   **FUNC-RM-001:** The system shall manage a set of four FCPs as a single, quad-redundant virtual group.
*   **FUNC-RM-002:** Upon detection of a fault, the system shall initiate recovery procedures for the affected component.
*   **FUNC-RM-003:** The system shall support the reintegration of a recovered processor back into the active set.
*   **FUNC-RM-004:** The system shall mask failures from the application layer, allowing continuous operation.

#### 3.2.5 Memory Management
*   **FUNC-MEM-001:** The system shall perform memory scrubbing at a rate of 10 Megabytes every 8 minutes.
*   **FUNC-MEM-002:** During processor recovery, the system shall ensure memory alignment between the recovering processor and the active set.

#### 3.2.6 Time Services
*   **FUNC-TIME-001:** The system shall maintain Mission Elapsed Time (MET).
*   **FUNC-TIME-002:** The system shall maintain Separation Elapsed Time (SEP).
*   **FUNC-TIME-003:** The MET and SEP shall be congruent across all active FCPs.

### 3.3 Performance Requirements

*   **PERF-001:** The system shall tolerate up to two non-simultaneous hardware faults during a single mission.
*   **PERF-002:** The system shall maintain synchronization across all processors with a maximum skew of 330 microseconds.
*   **PERF-003:** The MET and SEP time services shall have an accuracy of 50 Parts Per Million (PPM).
*   **PERF-004:** The system shall complete a full recovery and reintegration of a faulty component within 1.5 minutes.

### 3.4 Design Constraints

*   **DC-001:** The software image shall fit within 3 Megabytes of ROM.
*   **DC-002:** The software runtime memory footprint shall not exceed 9 Megabytes of DRAM.
*   **DC-003:** The system shall be designed to operate with any combination of 3 active FCRs out of a total of 5.

### 3.5 Software System Attributes

#### 3.5.1 Reliability
*   **REL-001:** The system shall ensure continuous operation without loss of critical functionality in the presence of any two non-simultaneous faults.

#### 3.5.2 Availability
*   **AVAIL-001:** The system shall be designed for high availability, with redundancy management ensuring service continuity through component failures.

#### 3.5.3 Maintainability
*   **MAINT-001:** The system shall provide diagnostic interfaces (IBIT/CBIT) for ground maintenance and troubleshooting.

## 4. Verification and Acceptance

### 4.1 Acceptance Criteria
Formal acceptance of the FTSS shall require successful demonstration of the following:
*   All fault tolerance requirements, including handling two non-simultaneous faults.
*   All timing constraints, including mode change duration (1.02 sec) and processor synchronization (≤330 µs skew).
*   Successful recovery and reintegration of a faulty component within 1.5 minutes.
*   Compliance with all memory and performance budgets.

### 4.2 Verification Methods
Verification shall be achieved through a combination of the following methods:
*   **Testing:** Unit, integration, and system-level testing to demonstrate functional and performance requirements.
*   **Analysis:** Timing analysis, fault tree analysis, and memory usage analysis.
*   **Inspection:** Code and design reviews against this SRS and other governing documents.

## Appendix A: Usage Scenarios

**Scenario 1: System Initialization**
1.  Power is applied to the Flight Critical Computer.
2.  FTSS boots on each FCP and executes Initial Built-In Test (IBIT).
3.  Successful FCPs form a quad-redundant virtual group.
4.  Time services synchronize MET across the group.
5.  The system enters the standby vehicle mode, ready for mission commands.

**Scenario 2: Fault Recovery During Flight**
1.  During ascent, a Single Event Upset (SEU) causes an FCP to fail its CBIT.
2.  FTSS fault detection logic identifies and isolates the faulty FCP.
3.  The system continues operation seamlessly with the three remaining FCPs.
4.  Redundancy management initiates recovery procedures on the faulty FCP.
5.  Once recovered and realigned, the FCP is reintegrated into the active set, restoring quad-redundancy.
