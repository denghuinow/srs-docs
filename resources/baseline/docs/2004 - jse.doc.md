## 1. Introduction

### 1.1 Purpose
This document describes the functional and non-functional requirements for the JSE Money Market Instrument (MMI) ISIN Management System. The purpose of this system is to automate the electronic issuance, cancellation, and de-registration of International Securities Identification Numbers (ISINs) for MMIs, enabling same-day trading and settlement. This SRS is intended for use by the project stakeholders, development team, and quality assurance team.

### 1.2 Project Scope
The system will exclusively handle ISIN lifecycle management for Money Market Instruments, which are identified by the `ZAM` prefix.

**In-Scope:**
*   Electronic processing of new ISIN requests for MMIs.
*   Electronic cancellation and de-issuance of active MMI ISINs.
*   Automated cancellation of ISINs upon their maturity date.
*   Real-time validation and rejection of invalid requests.
*   Communication with STRATE via SWIFT MT598 messages.
*   A front-end interface for JSE Operations to monitor ISIN statuses.

**Out-of-Scope:**
*   Handling of equities (`ZAE` prefix) or bonds (`ZAG` prefix).
*   Any processes related to physical ISIN certificates.
*   Primary market issuance for non-MMI instruments.

### 1.3 Definitions, Acronyms, and Abbreviations
*   **ANNA:** Association of National Numbering Agencies
*   **BCP:** Business Continuity Plan
*   **CSDP:** Central Securities Depository Participant
*   **ISIN:** International Securities Identification Number (ISO 6166)
*   **JSE:** Johannesburg Stock Exchange
*   **MMI:** Money Market Instrument
*   **NNA:** National Numbering Agent
*   **NMPG:** National Market Practice Group
*   **SLA:** Service Level Agreement
*   **STRATE:** The Central Securities Depository for South Africa

### 1.4 References
*   ISO 6166:2021, *Financial services — International securities identification number (ISIN)*
*   ANNA Derivatives Service Bureau (DSB) and NNA Guidelines
*   Service Level Agreement (SLA) between JSE and STRATE

## 2. Overall Description

### 2.1 Product Perspective
The JSE MMI ISIN Management System is a new, standalone component that replaces manual ISIN processing. It positions the JSE in its role as the NNA for South Africa. The system's sole external interface is with STRATE's SAFIRES settlement platform, acting as the central hub through which all MMI participants (e.g., banks) must operate. The integration is achieved via a SWIFT MT598 message channel.

### 2.2 Product Functions
The core functions of the system are:
1.  **ISIN Issuance:** Receive, validate, and process requests for new MMI ISINs.
2.  **ISIN Cancellation:** Process requests to cancel active ISINs before maturity.
3.  **Maturity Processing:** Automatically cancel ISINs on their predefined maturity date.
4.  **Validation & Rejection:** Perform real-time validation and reject invalid requests with specific error codes.
5.  **Notification:** Send confirmations for successful issuances, cancellations, and rejections.
6.  **Status Reporting:** Provide a front-end view for JSE Operations to see all issued, cancelled, and de-registered ISINs.

### 2.3 User Characteristics
| User Class | Description | Key Interactions |
| :--- | :--- | :--- |
| **STRATE (CSDP)** | The sole external entity initiating ISIN lifecycle events. | Initiates all ISIN requests (NEWM), cancellations (DISS), and maturity events (MATU) via SWIFT. Receives confirmations and rejections. |
| **Issuers (Banks)** | Financial institutions creating MMIs. | Submit MMI application details **via STRATE**; receive final confirmations through their STRATE interface. |
| **JSE Operations** | Internal JSE staff responsible for system monitoring. | Monitors the system for rejections, views the status dashboard, and manages data via the system's front-end. |

### 2.4 Constraints
*   The system **must** adhere to the ISO 6166 standard and ANNA guidelines for ISIN generation.
*   The system **must** use the `ZAM` prefix for all generated MMI ISINs.
*   STRATE is the **sole external interface**; the system must not provide direct access to MMF participants.
*   The content of all SWIFT MT598 messages **must** be pre-approved by the NMPG before implementation.

### 2.5 Assumptions and Dependencies
*   **Assumption:** STRATE will provide correctly formatted and sequenced SWIFT messages.
*   **Assumption:** The system will have a stable and reliable connection to the SWIFT network.
*   **Dependency:** Successful development is dependent on STRATE's funding and final NMPG approval of message specifications.
*   **Dependency:** The system's Business Continuity Plan is dependent on the overarching SLA between JSE and STRATE.

## 3. System Features

### 3.1 ISIN Issuance (NEWM)
**Description:** This feature allows the system to process requests for new MMI ISINs.
**Stimulus/Response:**
*   **Stimulus:** STRATE sends a SWIFT MT598-150 message with a `NEWM` (New ISIN) request.
*   **Response:** The system validates the request, generates a valid `ZAM` ISIN, records it in the database, and sends an MT598-151 confirmation message back to STRATE.

**Functional Requirements:**
*   **FR1.1:** The system shall parse incoming MT598-150 `NEWM` messages.
*   **FR1.2:** The system shall validate that the instrument type is an MMI and the request is for a `ZAM` prefix ISIN.
*   **FR1.3:** The system shall generate a valid ISIN compliant with ISO 6166 and ANNA rules.
*   **FR1.4:** The system shall store the new ISIN record with status "Issued".
*   **FR1.5:** The system shall send an MT598-151 message to STRATE containing the newly generated ISIN.

### 3.2 ISIN Cancellation (DISS)
**Description:** This feature allows for the manual cancellation of an active ISIN before its maturity date.
**Stimulus/Response:**
*   **Stimulus:** STRATE sends a SWIFT MT598-150 message with a `DISS` (De-issue/Cancel) request for a specific ISIN.
*   **Response:** The system validates the request and the ISIN's status, updates the record to "Cancelled", and sends an MT598-151 confirmation.

**Functional Requirements:**
*   **FR2.1:** The system shall parse incoming MT598-150 `DISS` messages.
*   **FR2.2:** The system shall validate that the target ISIN exists and is in an "Issued" state.
*   **FR2.3:** The system shall update the ISIN status to "Cancelled".
*   **FR2.4:** The system shall send an MT598-151 confirmation message to STRATE.

### 3.3 Automated Maturity Cancellation (MATU)
**Description:** The system will automatically cancel an ISIN on its scheduled maturity date without requiring a manual request.
**Stimulus/Response:**
*   **Stimulus:** The system's internal scheduler triggers a maturity check based on the system date.
*   **Response:** For all ISINs with a maturity date matching the current date, the system updates their status to "Matured" and sends an MT598-151 notification to STRATE.

**Functional Requirements:**
*   **FR3.1:** The system shall automatically process all active ISINs with a maturity date equal to the current system date.
*   **FR3.2:** The system shall update the status of these ISINs to "Matured".
*   **FR3.3:** The system shall send an unsolicited MT598-151 message to STRATE for each matured ISIN.

### 3.4 Rejection Handling
**Description:** This feature manages the real-time rejection of invalid requests with appropriate error codes.
**Stimulus/Response:**
*   **Stimulus:** An incoming MT598-150 message fails validation (e.g., duplicate ISIN request, invalid data).
*   **Response:** The system immediately sends an MT598-151 rejection message to STRATE with a specific error code and description.

**Functional Requirements:**
*   **FR4.1:** The system shall validate all incoming requests in real-time.
*   **FR4.2:** The system shall reject requests for non-MMI instrument types.
*   **FR4.3:** The system shall reject duplicate ISIN requests.
*   **FR4.4:** The system shall send an MT598-151 rejection message containing error codes (e.g., 901 for invalid data, 902 for duplicate request).

### 3.5 ISIN Status Dashboard
**Description:** A front-end interface for JSE Operations to view and monitor ISIN data.
**Functional Requirements:**
*   **FR5.1:** The system shall provide a web-based dashboard.
*   **FR5.2:** The dashboard shall display a searchable and filterable list of all ISINs.
*   **FR5.3:** The dashboard shall allow filtering by ISIN status: "Issued", "Cancelled", "Matured".
*   **FR5.4:** The dashboard shall display details of rejected requests for monitoring purposes.

## 4. External Interface Requirements

### 4.1 SWIFT MT598 Interface
The system's primary external interface is via SWIFT MT598 messages.

**Message Flow:**
| Direction | Message Type | Purpose | Key Fields |
| :--- | :--- | :--- | :--- |
| **STRATE → JSE** | MT598-150 | Request for a new ISIN. | `:20C::SEME//[Unique Ref]`<br>`:22F::ISSU//NEWM`<br>`:35B:[Instrument Details]` |
| **JSE → STRATE** | MT598-151 | Confirmation of a successful action. | `:20C::SEME//[Original Ref]`<br>`:22F::ISSU//[NEWM/DISS/MATU]`<br>`:35B:[ISIN]` |
| **JSE → STRATE** | MT598-151 | Rejection of a request. | `:20C::SEME//[Original Ref]`<br>`:22F::ISSU//REJT`<br>`:24B::REAS/[Rejection Code e.g., 901]` |

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   **Throughput:** The system shall be capable of processing between **200 and 500 ISIN requests** per day during peak operational hours.
*   **Response Time:** 95% of all SWIFT MT598-151 confirmation/rejection messages shall be generated and sent within **5 seconds** of receiving the corresponding MT598-150 request.

### 5.2 Availability Requirements
*   The system shall maintain an availability of **99.9%** in accordance with the SLA, supporting 24/7 operations to facilitate same-day trading and settlement.

### 5.3 Business Rules & Compliance
*   The system **must** enforce all business rules defined by the ISO 6166 standard and ANNA guidelines for ISIN generation and management.
*   All generated ISINs for MMIs **must** use the `ZAM` prefix.

### 5.4 Reliability & Business Continuity
*   The system shall implement a robust Business Continuity Plan (BCP) as stipulated in the SLA to ensure continuous operation and rapid recovery in the event of a failure.
*   All ISIN data and transaction records must be persisted and backed up to prevent data loss.
