## 1. Introduction

### 1.1 Purpose
This document defines the functional and non-functional requirements for the High Assurance Transformation System Graphical User Interface (HATS-GUI). The purpose of this SRS is to provide a detailed description of the software to be developed, serving as a basis for agreement between customers (domain experts, researchers) and developers. It will guide the design, implementation, and testing phases of the project.

### 1.2 Scope
The HATS-GUI is a platform-independent desktop application that provides a graphical front-end to the High Assurance Transformation System (HATS). It simplifies user interaction with HATS by allowing users to visually manage transformation projects, construct transformation language programs, apply them to target files, and inspect the results. The core of the transformation logic (parsing, execution) remains within the HATS-SML subsystem, which this interface orchestrates.

**In-Scope:**
*   Graphical management of "applications" (projects containing files and associations).
*   Invocation of HATS-SML for parsing and execution.
*   Visualization and navigation of Syntax Derivation Trees (SDTs).
*   Display of pretty-printed transformation outputs.
*   Cross-platform operation (Solaris, Windows 2000, Linux).

**Out-of-Scope:**
*   Modification of the underlying HATS-SML transformation engine logic.
*   Direct editing of transformation language syntax within the GUI (initial files are created/modified as text).
*   Network or multi-user functionality.

## 2. Overall Description

### 2.1 Product Perspective
The HATS-GUI is a new, self-contained component that acts as a mediator between the user and the existing HATS-SML backend. It is part of the larger HATS ecosystem.

**System Interfaces:**
*   **HATS-SML:** The GUI will execute HATS-SML as a separate process, passing command-line arguments and file paths, and capturing its standard output/error streams for display.
*   **File System:** The system will read from and write to the user's local file system for storing application data, source files, and outputs.

### 2.2 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Domain Expert / Researcher** | Deep knowledge of formal methods and program transformations. Computer-savvy. | Efficiently test and iterate on complex transformations. Accurately visualize SDT changes. Precise control over the transformation process. |
| **Advanced User** | Strong understanding of hierarchical file systems and software tools. May have basic transformation knowledge. | Manage multiple transformation projects. Apply pre-defined transformations reliably. Understand transformation outputs. |

### 2.3 Operating Environment
*   **Software:**
    *   Must operate identically on Sun Solaris, Microsoft Windows 2000, and Linux operating systems.
    *   Requires a JVM (version 1.3 or later recommended) to be installed on the host machine.
    *   Requires a functional installation of the HATS-SML interpreter (ML interpreter) accessible via system PATH or a configurable location.
*   **Hardware:** Hardware requirements are dictated by the JVM and the size of the SDTs being visualized. Minimum 128 MB RAM and 50 MB disk space is recommended.

### 2.4 Design and Implementation Constraints
1.  **Implementation Language:** The application must be implemented in Java (JDK 1.2 or later) to ensure platform independence.
2.  **Delivery Date:** The system must be feature-complete and tested by **December 2001**.
3.  **Libraries:** Use of standard Java libraries (Swing/AWT for GUI) is mandated. Third-party libraries require project lead approval.
4.  **Backend Dependency:** The GUI cannot function without a correctly installed and configured HATS-SML backend.

### 2.5 Assumptions and Dependencies
*   It is assumed the user has a valid HATS-SML installation.
*   It is assumed the user is familiar with the transformation language's syntax, as the GUI does not provide syntactic validation beyond what HATS-SML provides.
*   Project completion is dependent on the stability of the HATS-SML command-line interface.

## 3. System Features & Requirements

### 3.1 Application Management
**Description:** The system shall provide a workspace ("Application") to organize all files and meta-data for a transformation task.

**Requirements:**
*   **3.1.1** The system shall allow a user to create a new, empty Application.
*   **3.1.2** The system shall allow a user to save an Application to a user-specified directory, persisting file references and associations.
*   **3.1.3** The system shall allow a user to open a previously saved Application.
*   **3.1.4** Within an Application, the user shall be able to add existing transformation program files (.tl) and target source files.
*   **3.1.5** Within an Application, the user shall be able to create new, empty transformation program or target files.
*   **3.1.6** The system shall provide a visual tree or list component to navigate files within the open Application.
*   **3.1.7** The user shall be able to associate a specific transformation program with one or more target files within the Application.

### 3.2 Parsing and Execution Orchestration
**Description:** The system shall act as a controller, invoking the HATS-SML backend to perform parsing and execution.

**Requirements:**
*   **3.2.1** The system shall provide a user action (e.g., button, menu item) to parse a selected transformation program file. It shall invoke HATS-SML with the correct parse command.
*   **3.2.2** The system shall provide a user action to parse a selected target source file. It shall invoke HATS-SML with the correct parse command.
*   **3.2.3** The system shall provide a user action to execute a selected transformation program on an associated, parsed target file. It shall invoke HATS-SML with the correct execute command.
*   **3.2.4** For all invocations (3.2.1-3.2.3), the system shall capture and display the standard output and standard error streams from the HATS-SML process in a dedicated console panel.
*   **3.2.5** The system shall visually indicate the parse/execution status (e.g., "Parsed", "Ready", "Error") for each file in the Application.

### 3.3 Output Examination and Navigation
**Description:** The system shall visually present the results of parsing and transformation.

**Requirements:**
*   **3.3.1** Upon successful parsing of a file, the system shall load and be ready to display the generated SDT.
*   **3.3.2** The system shall provide a dedicated viewer to display an SDT as a collapsible/expandable tree graph. Nodes shall display syntax node types and key tokens.
*   **3.3.3** The user shall be able to navigate the SDT viewer by expanding/collapsing nodes and using scrollbars.
*   **3.3.4** Upon successful execution of a transformation, the system shall load and be ready to display the output SDT (the transformed program).
*   **3.3.5** The system shall allow the user to switch views between the original SDT and the output SDT for a given target file.
*   **3.3.6** The system shall provide a "pretty-print" view that displays the textual representation of any loaded SDT (original or transformed) in a readable, formatted text pane.
*   **3.3.7** The user shall be able to save the pretty-printed text of an output SDT to a new source file.

### 3.4 Non-Functional Requirements

**3.4.1 Usability:**
*   The GUI shall follow common platform-specific UI conventions where possible within the constraints of Java Swing.
*   Common operations (Open, Save, Parse, Execute) shall have both menu and toolbar shortcuts.
*   Error messages from HATS-SML shall be presented clearly in the console panel.

**3.4.2 Performance:**
*   The GUI shall remain responsive (no full UI locks) during HATS-SML execution. A "busy" cursor or progress indicator shall be used.
*   Loading and rendering of large SDTs (>10,000 nodes) shall be optimized to avoid excessive memory consumption and UI lag.

**3.4.3 Reliability:**
*   The GUI shall not crash due to malformed user input. Errors from the backend shall be handled gracefully.
*   The application state should be recoverable if a saved Application file is manually corrupted.

**3.4.4 Portability:**
*   The application shall be deliverable as a single Java Archive (JAR) file executable on any supported platform with a compatible JVM.
*   File path handling shall be cross-platform.
