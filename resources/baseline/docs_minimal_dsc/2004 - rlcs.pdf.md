# Software Requirements Specification (SRS)
## Reversible Lane Control System (RLCS)
**Document Version:** 1.0
**Date:** 2023-10-27
**Status:** Draft for Review

---

### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional and non-functional requirements for the Reversible Lane Control System (RLCS). The RLCS is designed to replace an aging system for managing the I-15 reversible lanes. This document is intended for use by the project stakeholders, including developers, testers, project managers, and system maintainers, to ensure a common understanding of the system to be developed.

#### 1.2 Document Conventions
*   Requirements are uniquely identified with tags (e.g., `FR-001`, `NFR-010`).
*   **Shall** indicates a mandatory requirement.
*   *Should* indicates a desirable but not mandatory feature.
*   Keywords are **highlighted in bold** for emphasis.
*   All system states (e.g., OPEN, CLOSED, FAULT) are denoted in UPPERCASE.

#### 1.3 Scope
The RLCS is a software application that provides centralized monitoring and control of field hardware (gates, barriers, dynamic message signs, etc.) to safely open and close the I-15 reversible lanes for peak traffic hours and special events. The system executes pre-defined, safe sequences for these operations and provides a real-time graphical interface for operators.

**In-Scope:**
*   Software for the central control server.
*   Operator Graphical User Interface (GUI).
*   Communication protocols to interface with new field hardware controllers.
*   Management and reporting interfaces.
*   System administration and configuration tools.

**Out-of-Scope:**
*   Design and manufacture of field hardware.
*   Physical installation of field hardware.
*   Network infrastructure (though compatibility is required).
*   Third-party operating systems and database software.

### 2. Overall Description

#### 2.1 Product Perspective
The RLCS is a new, self-contained software system that replaces the legacy control system. It interfaces with a new generation of field hardware controllers via a standardized communication network. The system is mission-critical and forms the primary control point for reversible lane operations.

#### 2.2 Product Functions
The core functions of the RLCS are:
1.  **Real-Time Monitoring:** Continuously poll and display the status of all connected field devices.
2.  **Sequential Control:** Execute stored, step-by-step sequences to transition lanes from a `CLOSED` state to a `NORTHBOUND_OPEN` or `SOUTHBOUND_OPEN` state, and vice-versa.
3.  **Manual Override:** Allow authorized operators to manually control individual devices with appropriate safety interlocks.
4.  **Status Visualization:** Provide an intuitive, graphical map-based interface showing the state of the entire corridor.
5.  **Alerting & Logging:** Generate alarms for faults and maintain an immutable audit log of all commands and system events.
6.  **Reporting:** Generate operational and maintenance reports for management and field staff.

#### 2.3 User Classes and Characteristics
| User Class | Characteristics | Key Needs |
| :--- | :--- | :--- |
| **Operator** | Primary user, works in traffic management center. Trained on safety procedures. | Clear system status, intuitive control, unambiguous alarms, execution of pre-set sequences. |
| **Management** | Reviews operations, plans for events. Not a daily user. | High-level status dashboards, historical reports, trend analysis. |
| **Field Maintenance Staff** | Technicians who service field devices. | Remote diagnostic views, device-specific status and fault history, ability to place devices in maintenance mode. |
| **System Administrator** | IT staff responsible for system health. | User account management, system configuration, log access, backup/restore functions. |

#### 2.4 Operating Environment
*   **Hardware:** Commercial off-the-shelf (COTS) server hardware meeting specified performance benchmarks.
*   **Operating System:** The software shall be compatible with the latest stable Long-Term Support (LTS) versions of specified commercial and/or open-source server operating systems (e.g., Windows Server 20XX, Red Hat Enterprise Linux X).
*   **Network:** Must operate over a dedicated, secure network connecting the central server to field controllers.

#### 2.5 Design and Implementation Constraints
1.  The system **shall** interface with the new field hardware controllers using the protocol defined in the *Field Controller Hardware Interface Specification, v2.1*.
2.  The GUI **shall** be developed using a technology that supports high-resolution, real-time graphical displays.
3.  All configuration data (sequences, device parameters) **shall** be stored in a relational database.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** Field hardware controllers will be available, installed, and network-connected prior to RLCS software deployment.
*   **Assumption:** A stable, low-latency communication network will be provided.
*   **Dependency:** The system relies on the continuous availability of the underlying database and operating system services.

### 3. System Features and Requirements

#### 3.1 Feature: System Monitoring & Status Display
**Description:** The system shall provide a real-time, graphical view of all monitored field devices and system health.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-001** | The system shall continuously poll all field devices for status (e.g., position, health, communication state) at an interval not to exceed 5 seconds. | High |
| **FR-002** | The GUI shall display a schematic map of the I-15 corridor with icons representing each field device (gate, barrier, sign). | High |
| **FR-003** | The color and symbol of each device icon shall change dynamically to represent its current state (e.g., green for OPEN/ON, red for CLOSED/OFF, flashing yellow for FAULT, gray for COMMUNICATION_LOST). | High |
| **FR-004** | The system shall display a dedicated status panel showing the overall lane configuration (e.g., `CLOSED`, `NORTHBOUND_OPEN`, `TRANSITION_IN_PROGRESS`). | High |

#### 3.2 Feature: Sequence Execution
**Description:** The system shall execute pre-defined, safe sequences to open or close the reversible lanes.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-010** | The system shall store multiple named sequences (e.g., "Morning Northbound Open", "Evening Southbound Close"). | High |
| **FR-011** | An operator shall be able to select and initiate a stored sequence from the GUI. | High |
| **FR-012** | Before executing any sequence, the system **shall** perform a pre-condition check to verify a safe starting state (e.g., all entrances for the opposite direction are confirmed CLOSED). | Critical |
| **FR-013** | The system shall execute the sequence steps in a defined order, waiting for positive confirmation from a field device before proceeding to the next step. | High |
| **FR-014** | The GUI shall provide a visual progress indicator during sequence execution and log each step's success or failure. | Medium |

#### 3.3 Feature: Safety Interlocks & Manual Control
**Description:** The system shall enforce critical safety rules and allow for supervised manual operation.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-020** | **Safety Constraint:** The system shall implement a hardware and software interlock that physically prevents any command from opening an entrance for one direction if any entrance for the opposite direction is in an OPEN state. This is a **catastrophic safety failure** condition that must be avoided. | Critical |
| **FR-021** | An operator with appropriate authorization shall be able to take manual control of an individual field device. | High |
| **FR-022** | When in manual control mode, any command issued by the operator **shall** still be validated against the core safety interlock (`FR-020`) and other relevant safety rules before being sent to the field device. | Critical |

#### 3.4 Feature: Alarm and Event Management
**Description:** The system shall alert operators to faults and log all significant events.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-030** | The system shall generate audible and visual alarms for critical faults (e.g., device failure, communication loss, safety interlock violation). | High |
| **FR-031** | All operator commands, system actions, sequence steps, and device state changes shall be recorded in a tamper-evident audit log with a timestamp and user ID. | High |
| **FR-032** | The system shall provide a filterable alarm and event history viewer. | Medium |

#### 3.5 Feature: User Management and Reporting
**Description:** The system shall support multiple user roles and generate reports.

| ID | Requirement Description | Priority |
| :--- | :--- | :--- |
| **FR-040** | The system shall support user authentication and role-based access control (RBAC) with distinct permissions for Operators, Managers, and System Administrators. | High |
| **FR-041** | The system shall generate daily/weekly/monthly operational reports (e.g., sequence execution times, fault summaries) for management. | Medium |
| **FR-042** | The system shall provide field maintenance staff with a view of device-specific diagnostic data and fault history. | Medium |

### 4. Non-Functional Requirements

#### 4.1 Performance Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-001** | The system shall update the status of all field devices on the GUI within 2 seconds of receiving data from the field controller. |
| **NFR-002** | Command acknowledgment from the central system to the field device shall occur within 1 second under normal network conditions. |

#### 4.2 Safety Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-010** | The system shall be designed to fail into a safe state (defaulting to `CLOSED` or maintaining last valid state) upon detection of a critical internal error or loss of communication with the central control. |
| **NFR-011** | The safety interlock logic (`FR-020`) shall be implemented in a separate, verifiable module with the highest priority in the control logic. |

#### 4.3 Availability & Reliability
| ID | Requirement Description |
| :--- | :--- |
| **NFR-020** | The system shall be available 24 hours a day, 7 days a week, with a target uptime of 99.9% excluding scheduled maintenance. |
| **NFR-021** | The mean time between failures (MTBF) for the software system shall be greater than 10,000 hours. |
| **NFR-022** | Scheduled maintenance windows shall not exceed 2 hours per month and require advance approval from operations management. |

#### 4.4 Security Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-030** | All communication between the central server and field controllers shall be encrypted. |
| **NFR-031** | User passwords shall be stored using strong, salted cryptographic hashing. |
| **NFR-032** | The system shall maintain an audit trail of all user authentication attempts (successful and failed). |

#### 4.5 Usability Requirements
| ID | Requirement Description |
| :--- | :--- |
| **NFR-040** | A trained operator shall be able to execute a standard opening or closing sequence with no more than 3 user actions. |
| **NFR-041** | The system status (overall lane direction) shall be discernible at a glance from a distance of 10 feet from the operator console. |
