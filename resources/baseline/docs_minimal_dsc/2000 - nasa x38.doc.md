### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document defines the functional, performance, and interface requirements for the Fault-Tolerant Software Services (FTSS) of the NASA X-38 Crew Return Vehicle's Flight Critical Computer (FCC). This software acts as a critical middleware layer, providing deterministic, fault-tolerant execution and communication services between the vehicle's application software and the underlying quad-redundant hardware and operating system. The primary audience for this document includes system architects, software developers, test engineers, and verification & validation personnel.

#### 1.2 Scope
The FTSS encompasses all software necessary to manage the redundancy, scheduling, communication, fault management, and recovery of the quad-redundant Flight Critical Processors (FCPs) and simplex Instrument Control Processors (ICPs). It excludes:
*   The development of the vehicle's mission-specific application software.
*   The design of the Radstone Power PC 604R hardware or VxWorks 5.4 operating system.
*   Ground support equipment or telemetry processing systems external to the FCC.

#### 1.3 Definitions, Acronyms, and Abbreviations
| Term | Definition |
| :--- | :--- |
| **FCC** | Flight Critical Computer |
| **FCP** | Flight Critical Processor (one node in the redundant set) |
| **ICP** | Instrument Control Processor (simplex unit) |
| **FTSS** | Fault-Tolerant Software Services |
| **BIST** | Built-In Self Test |
| **2-Fault Tolerant** | The system can withstand and recover from two non-simultaneous hardware faults without loss of critical function. |
| **Rate Group** | A set of tasks scheduled to execute at a specific, deterministic frequency (e.g., 50 Hz). |
| **Congruent Memory** | Identical memory state across redundant processors to enable seamless failover. |

### 2. Overall Description

#### 2.1 Product Perspective
The FTSS is a core component of the X-38 FCC software architecture. It resides between the VxWorks Real-Time Operating System (RTOS) and the application software layer.

```
+---------------------------------------+
|     Vehicle Application Software      |
+---------------------------------------+
| Fault-Tolerant Software Services (FTSS)|
| - Redundancy Management               |
| - Deterministic Scheduler             |
| - Fault-Tolerant Communication        |
| - Fault Detection & Isolation         |
| - Recovery & Memory Alignment         |
+---------------------------------------+
|      VxWorks 5.4 RTOS (Kernel)        |
+---------------------------------------+
|   Radstone Power PC 604R Hardware     |
|     (Quad-Redundant FCPs + ICPs)      |
+---------------------------------------+
```

**System Interfaces:**
*   **Hardware:** Radstone Power PC 604R processors, network interfaces, memory, I/O.
*   **Operating System:** VxWorks 5.4 kernel, including its tasking and IPC primitives.
*   **Application Software:** Provides API for task creation, communication, and health status.

#### 2.2 Product Functions
The high-level functions of the FTSS are:
1.  **Redundancy Management:** Coordinate the operation of four FCPs as a fault-tolerant set, managing operational modes (e.g., active, standby, spare, failed).
2.  **Deterministic Scheduling:** Execute application tasks within precise 50 Hz, 10 Hz, and 1 Hz rate groups with minimal and bounded jitter.
3.  **Fault-Tolerant Communication:** Provide reliable, synchronous, and immediate message-passing services between tasks, both within a single processor and across the redundant network.
4.  **Fault Detection, Isolation, and Reporting:** Continuously monitor hardware health via BIST, identify faulty components, isolate them from the system, and report faults for telemetry.
5.  **Recovery and Memory Management:** Facilitate the reintegration of repaired or spare processors by aligning their application memory state (congruent memory) with the active set.

#### 2.3 User Characteristics
The primary "users" of the FTSS are system-level software components:
*   **Flight Critical Processors (FCPs):** Operate as a coordinated, redundant set. The FTSS must manage state synchronization, voting, and failover between these units transparently.
*   **Instrument Control Processors (ICPs):** Operate as simplex (non-redundant) units. The FTSS must provide communication and health monitoring services to/from these units.

#### 2.4 Constraints
*   **Fault Tolerance:** The system must be two-fault tolerant for non-simultaneous hardware faults.
*   **Real-Time Performance:** All critical operations have strict temporal deadlines.
    *   Fault isolation must complete within **3 milliseconds** of detection.
    *   Scheduler overhead per major cycle must not exceed **1 millisecond**.
*   **Software Environment:** Must be developed in the **C programming language** for the **VxWorks 5.4** operating system.
*   **Hardware Platform:** Must execute on the **Radstone Power PC 604R** processor.
*   **Memory Limits:** The combined footprint of the FTSS and the VxWorks OS must not exceed:
    *   **3 Megabytes** of ROM (for code and constant data).
    *   **9 Megabytes** of DRAM (for runtime data and stack).

#### 2.5 Assumptions and Dependencies
*   The VxWorks 5.4 operating system provides a stable and deterministic kernel foundation.
*   Hardware faults are non-malicious and non-simultaneous for the purpose of achieving two-fault tolerance.
*   The underlying hardware provides necessary support for BIST and redundancy cross-channel data links.

### 3. Specific Requirements

#### 3.1 External Interface Requirements
**3.1.1 Application Programming Interface (API)**
The FTSS shall provide a well-defined C-language API for the application layer, including but not limited to:
*   `FTSS_task_create(rate_group, entry_point)`
*   `FTSS_msg_send(destination, message, timeout)`
*   `FTSS_msg_receive(source, buffer, timeout)`
*   `FTSS_get_system_status()`

**3.1.2 Hardware Abstraction Layer (HAL)**
The FTSS shall interface with a Hardware Abstraction Layer that provides uniform access to:
*   Redundant network channels (e.g., SpaceWire, 1553).
*   Processor-specific BIST functions.
*   Watchdog timers and interrupt controllers.

#### 3.2 Functional Requirements
**3.2.1 Redundancy Management (FTSS-RM)**
*   **FTSS-RM-001:** The system shall maintain exactly one FCP as the "Active" controller at any time.
*   **FTSS-RM-002:** The system shall maintain at least one FCP in a "Hot Standby" state, with synchronized memory and execution context.
*   **FTSS-RM-003:** Upon detection of a fault in the Active FCP, the system shall perform a failover to a Standby FCP within one major scheduler cycle (20 ms).
*   **FTSS-RM-004:** The system shall support the manual or automatic reintegration of a repaired or spare FCP into the redundant set.

**3.2.2 Deterministic Scheduling (FTSS-DS)**
*   **FTSS-DS-001:** The scheduler shall execute tasks in three predefined rate groups: 50 Hz (20 ms period), 10 Hz (100 ms period), and 1 Hz (1000 ms period).
*   **FTSS-DS-002:** The order of task execution within each rate group shall be deterministic and configurable.
*   **FTSS-DS-003:** The scheduler shall guarantee that all tasks in the 50 Hz rate group complete execution before the next 20 ms period begins.
*   **FTSS-DS-004:** Scheduler overhead (context switching, timing logic) shall not exceed **1 ms** per major (20 ms) cycle.

**3.2.3 Fault-Tolerant Communication (FTSS-FTC)**
*   **FTSS-FTC-001:** The system shall provide a synchronous message-passing service where the sender blocks until receipt is acknowledged.
*   **FTSS-FTC-002:** The system shall provide an immediate (asynchronous) message-passing service with bounded queue depths.
*   **FTSS-FTC-003:** Inter-processor messages shall be automatically sent across multiple redundant network channels.
*   **FTSS-FTC-004:** The communication layer shall perform message voting (e.g., mid-value select, Byzantine agreement) on received redundant messages to mask communication link faults.

**3.2.4 Fault Detection, Isolation, and Reporting (FTSS-FDI)**
*   **FTSS-FDI-001:** The system shall execute continuous BIST on processors, memory, and network interfaces.
*   **FTSS-FDI-002:** Upon detecting a fault, the system shall identify and isolate the faulty component (CPU, network link, etc.) from the operational set within **3 ms**.
*   **FTSS-FDI-003:** All detected faults shall be logged in a non-volatile fault log with a timestamp and severity.
*   **FTSS-FDI-004:** A summary health status of all FCPs and ICPs shall be available via the API and downlinked via telemetry.

**3.2.5 Recovery and Memory Alignment (FTSS-RMA)**
*   **FTSS-RMA-001:** During the reintegration of a spare FCP, the system shall transfer the congruent application memory image from the Active FCP to the spare.
*   **FTSS-RMA-002:** The memory alignment process shall ensure data consistency and shall not disrupt the execution of the Active FCP's critical 50 Hz tasks.
*   **FTSS-RMA-003:** The system shall validate the integrity of the aligned memory on the spare FCP before declaring it operational.

#### 3.3 Performance Requirements
*   **PERF-001:** End-to-end latency for a synchronous inter-processor message (sender task to receiver task) shall be ≤ 5 ms under nominal, fault-free conditions.
*   **PERF-002:** Deterministic jitter for 50 Hz tasks shall be ≤ 100 microseconds.
*   **PERF-003:** Fault detection latency (from fault occurrence to internal detection) shall be ≤ 10 ms for processor BIST failures.

#### 3.4 Design Constraints
*   **CONST-001:** The software shall be implemented in ANSI C, with no use of dynamic memory allocation (`malloc/free`) after system initialization.
*   **CONST-002:** All time-critical code paths shall be analyzable for Worst-Case Execution Time (WCET).
*   **CONST-003:** The software shall be structured to facilitate modular verification and testing of redundancy management and fault handling paths independently.

#### 3.5 Software System Attributes
*   **RELIABILITY-001:** The FTSS shall have a probability of failure of less than 1x10⁻⁹ per hour of operation.
*   **AVAILABILITY-001:** The system shall maintain availability of critical services (scheduling, communication) at 99.999% during a mission, accounting for specified fault scenarios.
*   **MAINTAINABILITY-001:** All configuration parameters (e.g., rate group tables, fault thresholds) shall be stored in a separate, easily modifiable data module.

#### 3.6 Safety and Fault Tolerance Requirements
*   **SAFT-001:** The system shall implement a hardware watchdog timer that must be serviced by the FTSS health monitor task. Failure to service shall trigger a processor reset.
*   **SAFT-002:** The design shall ensure that no single point of software failure can cause the loss of more than one FCP.
*   **SAFT-003:** The fault isolation mechanism shall be designed to fail-operational, then fail-safe. A second fault during recovery from a first fault shall not result in a hazardous condition.
