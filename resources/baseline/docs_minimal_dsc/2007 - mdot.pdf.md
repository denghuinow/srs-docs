### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for a research prototype system designed to investigate and evaluate the utility of Vehicle Infrastructure Integration (VII) probe data. The system integrates VII data with other transportation data sources to enhance safety, mobility, and asset management insights. This document is intended for use by the project stakeholders, developers, testers, and project managers involved in the system's design, implementation, and validation.

#### 1.2 Scope
The scope of the VII Research Prototype System encompasses the end-to-end data pipeline for transportation data, specifically:
*   **In-Scope:** The acquisition, processing, storage, and dissemination of VII probe data, traffic data, weather data, and road condition data for the purposes of demonstration, assessment, and research.
*   **Out-of-Scope:** The development of in-vehicle probe data collection hardware, the creation of source data provider systems (e.g., weather stations, traffic cameras), and the deployment of production-grade, 24/7 operational systems for public use.

#### 1.3 Definitions, Acronyms, and Abbreviations
| Term | Definition |
| :--- | :--- |
| **VII** | Vehicle Infrastructure Integration. A communication framework enabling data exchange between vehicles and roadside infrastructure. |
| **Probe Data** | Data generated by vehicles (e.g., location, speed, heading, wiper status, ABS activation) that provides insights into traffic and road conditions. |
| **Near Real-Time (NRT)** | Data processing with minimal latency, typically ranging from seconds to a few minutes from the time of data generation to availability. |
| **SaaS** | Software as a Service. |
| **API** | Application Programming Interface. |
| **MDIT** | Michigan Department of Information Technology. |

#### 1.5 Overview
The remainder of this document is structured as follows: Section 2 provides a high-level description of the product and its operating environment. Section 3 details specific system requirements, including external interfaces, functional requirements, and non-functional requirements.

### 2. Overall Description

#### 2.1 Product Perspective
This system is a standalone research prototype. It will interface with multiple external data sources and provide data to external consumer systems and internal presentation services. It operates within the broader context of Intelligent Transportation Systems (ITS) research.

#### 2.2 Product Functions
The core high-level functions of the system are:
1.  **Data Acquisition:** Collect heterogeneous data streams from multiple external sources.
2.  **Data Processing:** Apply computational algorithms to raw and fused data to derive higher-value information.
3.  **Data Management:** Store raw and processed data in a persistent repository with appropriate metadata.
4.  **Data Dissemination:** Publish processed data, alerts, and metrics via standardized APIs and feeds.
5.  **System Administration:** Provide interfaces for configuration, monitoring, and management of the data pipeline.

#### 2.3 User Characteristics
| User Class | Description | Key Skills/Needs |
| :--- | :--- | :--- |
| **Transportation Operator** | Agency staff monitoring traffic and incidents. | Needs clear, real-time visualizations of traffic speed, incidents, and alerts. |
| **Maintainer/Asset Manager** | Agency staff responsible for road maintenance. | Needs data on road surface conditions (e.g., icy, wet) and asset performance metrics. |
| **System Administrator** | Technical staff managing the prototype. | Needs tools to configure data sources, monitor system health, and manage users. |
| **Researcher** | Internal or external user analyzing data. | Needs access to historical and real-time data feeds in analyzable formats. |
| **Traveler** (Indirect) | End-user of public traveler information systems. | Consumes information (e.g., travel times, alerts) via third-party applications. |
| **Emergency Services** (Indirect) | Police, fire, EMS. | May consume incident and congestion data to inform response. |

#### 2.4 Constraints
1.  **Regulatory/Policy:** The system must operate under formal policies governing data privacy, ownership, and retention, particularly for personally identifiable information (PII) potentially embedded in probe data.
2.  **Technical:** The system must conform to all applicable IT standards (e.g., security, hosting, software stack) established by the Michigan Department of Information Technology (MDIT).
3.  **Operational:** The system is designed for "near real-time" processing; absolute real-time guarantees are not required, but latency must be quantified and managed.
4.  **Implementation:** The system is a research prototype, prioritizing flexibility and evaluative capability over ultimate scalability and fault tolerance.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** External data sources (VII, traffic, weather) will provide data in documented, parsable formats via reliable connectivity.
*   **Assumption:** Sufficient computational and storage resources will be available to handle the anticipated data volumes for the prototype's duration.
*   **Dependency:** The system's ability to assess data suitability is dependent on source systems providing accurate timestamps and metadata.

### 3. Specific Requirements

#### 3.1 External Interface Requirements

##### 3.1.1 User Interfaces
*   **FR-UI-01:** The system shall provide a web-based administrative console for system configuration and health monitoring.
*   **FR-UI-02:** The system shall provide a web-based dashboard for transportation operators, displaying processed data (maps, charts, alerts).
*   **FR-UI-03:** All user interfaces shall be accessible via standard web browsers (Chrome, Firefox, Edge) without requiring browser plugins.

##### 3.1.2 Hardware Interfaces
*   **NFR-HW-01:** The system shall be deployable on standard x86-64 server hardware or virtual machines as specified by MDIT.

##### 3.1.3 Software Interfaces
*   **FR-SI-01:** The system shall ingest VII probe data from a designated source API or message queue (e.g., Kafka, RESTful endpoint).
*   **FR-SI-02:** The system shall ingest traffic data (e.g., from ATMS) via a standardized protocol (e.g., NTCIP, DATEX II, or REST).
*   **FR-SI-03:** The system shall ingest weather and road condition data from designated sources (e.g., RWIS, NOAA APIs).
*   **FR-SI-04:** The system shall publish processed data via a RESTful API adhering to OpenAPI specification.
*   **FR-SI-05:** The system shall publish real-time alerts via a standards-based feed (e.g., RSS, CAP, or WebSocket).

##### 3.1.4 Communications Interfaces
*   **NFR-COM-01:** All external communications shall use secure protocols (HTTPS, WSS, TLS for message queues).

#### 3.2 Functional Requirements

##### 3.2.1 Data Acquisition Module
*   **FR-DA-01:** The system shall connect to and authenticate with each configured external data source.
*   **FR-DA-02:** The system shall poll or subscribe to data streams from each source according to configurable schedules.
*   **FR-DA-03:** The system shall parse incoming data from each source format into a common internal canonical model.
*   **FR-DA-04:** The system shall tag each data record with a system receipt timestamp and source metadata.

##### 3.2.2 Data Processing Module
*   **FR-DP-01:** The system shall assess the suitability of incoming data based on configurable rules for timeliness (source vs. receipt timestamp) and source reliability.
*   **FR-DP-02:** The system shall fuse correlated data from different sources (e.g., vehicle speed probes with weather conditions).
*   **FR-DP-03:** The system shall execute algorithms to derive the following from probe and fused data:
    *   **FR-DP-03.1:** Segment-based traffic speed and volume.
    *   **FR-DP-03.2:** Link-based travel time estimates.
    *   **FR-DP-03.3:** Probabilistic detection of traffic incidents.
    *   **FR-DP-03.4:** Inference of road surface conditions (e.g., dry, wet, icy).
*   **FR-DP-04:** The system shall generate alerts when derived metrics exceed configurable thresholds (e.g., speed < 20 mph, incident detected, icy road inferred).

##### 3.2.3 Data Storage Module
*   **FR-DS-01:** The system shall persist all raw ingested data for a configurable retention period.
*   **FR-DS-02:** The system shall persist all processed/derived data and alerts.
*   **FR-DS-03:** The system shall support time-series-based queries for historical data analysis.

##### 3.2.4 Data Dissemination Module
*   **FR-DD-01:** The system shall expose processed data (speeds, travel times, conditions) via a read-only REST API.
*   **FR-DD-02:** The system shall push alerts to a designated alert feed upon generation.
*   **FR-DD-03:** Published data shall be formatted using industry-standard structures (e.g., JSON-LD for linked data, GPX for geographic traces).

##### 3.2.5 System Administration Module
*   **FR-SA-01:** The system shall allow administrators to configure data source endpoints, credentials, and polling intervals.
*   **FR-SA-02:** The system shall allow administrators to configure processing algorithm parameters and alert thresholds.
*   **FR-SA-03:** The system shall provide a dashboard showing system health metrics (data flow rates, processing latency, error logs).

#### 3.3 Non-Functional Requirements

##### 3.3.1 Performance Requirements
*   **NFR-PER-01:** The system shall process 95% of incoming data records from receipt to availability in the published API within **2 minutes** under expected load ("near real-time").
*   **NFR-PER-02:** The system's data ingestion interfaces shall support a sustained data rate of [TBD] messages per second.
*   **NFR-PER-03:** API response times for queries of current conditions shall be less than **3 seconds** (p95).

##### 3.3.2 Safety & Security Requirements
*   **NFR-SEC-01:** The system shall comply with all MDIT security standards for application hosting and data management.
*   **NFR-SEC-02:** All data at rest containing PII or sensitive infrastructure details shall be encrypted.
*   **NFR-SEC-03:** The system shall implement role-based access control (RBAC) for administrative functions.
*   **NFR-SEC-04:** The system shall anonymize or aggregate probe data prior to storage and dissemination to protect vehicle privacy, as per operational policy.

##### 3.3.3 Software Quality Attributes
*   **Maintainability:** The system shall be modular, with clear separation between data acquisition, processing, and dissemination components. Code shall be well-documented.
*   **Reliability:** As a research prototype, the system should maintain an uptime of 95% during core research evaluation periods. Data loss from internal failure should be minimized.
*   **Usability:** The operator dashboard shall present critical alert information within the top portion of the screen without requiring scrolling.
