### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the Tarrant County Attorney Appointment & Compensation System (TCAACS). The primary purpose of this document is to provide a detailed description of the system's capabilities, interfaces, and performance characteristics to serve as a basis for design, development, testing, and stakeholder agreement.

#### 1.2 Document Conventions
*   **Requirements IDs:** Functional requirements are labeled `FR-XXX`. Non-functional requirements are labeled `NFR-XXX`.
*   **Keywords:** "Shall" indicates a mandatory requirement. "Should" indicates a desirable but not mandatory feature.
*   **Formatting:** System entities (e.g., `Case`, `Attorney`) are in `code font`. User roles are **bolded**.

#### 1.3 Project Scope
The TCAACS is a web-based enterprise application designed to automate and manage the end-to-end workflow for appointing, tracking, and compensating court-appointed defense attorneys for indigent defendants in Tarrant County's criminal courts. The system shall streamline administrative processes, ensure strict compliance with Texas statutes, and provide robust reporting capabilities.

**In-Scope:**
*   Electronic submission and processing of indigency and appointment requests.
*   Management of attorney qualification rosters and automated appointment rotation.
*   Tracking of attorney activity (contacts, hearings, filings).
*   Processing, review, and approval of attorney fee vouchers and expenses.
*   Generation of statutory reports for the Texas Fair Defense Act (FDA).
*   Secure user authentication and role-based access control.
*   System-to-system integration with the external Court Case Management System (CCMS).

**Out-of-Scope:**
*   The external Court Case Management System (CCMS) itself.
*   Attorney timekeeping/billing software used by individual attorneys.
*   Electronic filing (e-filing) with the court clerk.
*   Financial systems for generating and issuing payments (system will approve claims for export).

#### 1.4 References
*   Texas Code of Criminal Procedure, Articles 1.051, 15.17, 26.04, 26.05.
*   Texas Government Code, Chapter 71.
*   Texas Fair Defense Act (FDA) Standards and Forms.
*   Tarrant County Local Rules of Administration.

### 2. Overall Description

#### 2.1 Product Perspective
The TCAACS is a new, self-contained system that will replace manual and semi-automated processes. It must integrate as a "subsystem" with the existing county Court Case Management System (CCMS) via a defined API. The relationship is shown below:

```
[External CCMS] <-- (API: Case Data Sync) --> [TCAACS Core] --> [Users via Web Browser]
                                         \
                                          -> [Reporting Engine] --> [FDA/Compliance Reports]
```

#### 2.2 Product Functions
The core high-level functions of TCAACS are:
1.  **Appointment Intake & Processing:** Capture defendant indigency information and magistrate requests for counsel.
2.  **Attorney Management:** Maintain lists of eligible attorneys by case type and court, and manage a fair, automated appointment rotation.
3.  **Case & Activity Tracking:** Record key case events, attorney-defendant contacts, and document milestones.
4.  **Compensation Management:** Facilitate the submission, review, audit, and approval of attorney fee claims.
5.  **Compliance & Reporting:** Generate required FDA reports and ad-hoc operational analytics.

#### 2.3 User Classes and Characteristics
| User Class | Description | Key Characteristics |
| :--- | :--- | :--- |
| **Defendant** | An individual claiming indigency and requesting court-appointed counsel. | Limited, one-time access. Minimal technical proficiency. May use a kiosk or provided device. |
| **Magistrate** | Judicial officer (Judge, Hearing Officer) who determines probable cause and indigency. | Authoritative user. Needs rapid, auditable workflow during initial hearings. |
| **Defense Attorney** | Attorney appointed to represent an indigent defendant. | Primary external user. Needs to log activities, submit claims, and view case data. |
| **OAA Staff** | Staff of the Office of Attorney Appointments. | Primary internal user. Manages rosters, processes appointments, reviews claims, generates reports. |
| **OAA Administrator** | Supervisory/management staff within OAA. | Configures system rules, manages users, oversees compliance reporting. |
| **System Administrator** | IT personnel responsible for system health. | Technical user. Manages servers, integrations, backups, and core user accounts. |

#### 2.4 Operating Environment
*   **Software:** Web application accessible via modern browsers (Chrome, Edge, Firefox). Backend built on .NET/Java stack with SQL database.
*   **Hardware:** Hosted on county-approved servers or cloud infrastructure (compliant with CJIS standards if applicable).
*   **Networks:** Accessible via the county's secure intranet and through a secure portal for external users (attorneys).
*   **Integrations:** RESTful API integration with the external CCMS.

#### 2.5 Design and Implementation Constraints
1.  **Legal Compliance:** The system's logic and data model **shall** directly reflect requirements in Texas Code of Criminal Procedure Articles 1.051, 26.04, and 26.05.
2.  **Integration Constraint:** The system **shall not** duplicate core case data stored in the CCMS. It **shall** consume a real-time or daily feed of case `(Cause Number, Defendant, Charges, Court)` and hearing data.
3.  **Security Constraint:** The system **shall** comply with all Tarrant County IT security policies and data classification standards for criminal justice information.

#### 2.6 Assumptions and Dependencies
*   **Assumption:** The external CCMS will provide a stable, documented API for data exchange.
*   **Assumption:** Attorneys will have internet access and a basic ability to use a web browser.
*   **Dependency:** Final FDA reporting requirements will be confirmed by the OAA prior to UAT.
*   **Dependency:** County IT will provide necessary hosting infrastructure and network security.

### 3. System Features and Requirements

#### 3.1 Appointment Intake & Processing
**3.1.1 Description:** This feature allows for the electronic submission of a request for appointed counsel, the collection of indigency information, and the judicial determination and order for appointment.

**3.1.2 Requirements:**
*   `FR-101` The system shall allow a **Magistrate** or **OAA Staff** to initiate a new `Appointment Request` linked to a `Case` imported from the CCMS.
*   `FR-102` The system shall present an electronic version of the state-mandated indigency questionnaire to the **Defendant** (via kiosk or staff-assisted entry).
*   `FR-103` The system shall allow the **Magistrate** to electronically sign an `Order Appointing Counsel` upon a finding of indigency, which shall be stored as a PDF and its data recorded in the system.
*   `FR-104` The system shall immediately notify the **OAA Staff** of a new, approved appointment request requiring attorney assignment.

#### 3.2 Attorney Management & Rotation
**3.2.1 Description:** This feature maintains rosters of qualified attorneys and automates the fair, rotational assignment of attorneys to cases based on predefined rules.

**3.2.2 Requirements:**
*   `FR-201` The system shall allow **OAA Administrators** to create and maintain `Attorney Rosters` categorized by case type (e.g., Felony, Misdemeanor, Juvenile, Appellate) and specific court.
*   `FR-202` The system shall track each attorney's `Appointment History` (date, case type, complexity).
*   `FR-203` Upon assignment trigger, the system shall automatically select the next eligible attorney from the appropriate roster using a "next-in-line" rotation algorithm, considering attorney availability and maximum caseloads.
*   `FR-204` The system shall allow **OAA Staff** to manually override the automatic selection with a reason for override logged.

#### 3.3 Case & Activity Tracking
**3.3.1 Description:** This feature provides a dashboard for tracking key events, attorney-defendant contacts, and important deadlines for each appointed case.

**3.3.2 Requirements:**
*   `FR-301` The system shall provide a `Case Dashboard` for **Defense Attorneys** and **OAA Staff** displaying all cases, their status, and next key dates.
*   `FR-302` The system shall allow **Defense Attorneys** to log `Contacts` with their client (date, time, type: in-person, phone, email, duration) and `Case Events` (motions filed, hearings attended).
*   `FR-303` The system shall automatically create timeline entries from data integrated from the CCMS (e.g., hearing dates, dispositions).
*   `FR-304` The system shall generate automated reminders for required initial client contact (per Article 26.04(j)(1)) and other configurable deadlines.

#### 3.4 Compensation Claim Processing
**3.4.1 Description:** This feature enables attorneys to submit fee vouchers and expenses electronically, and allows OAA staff to review, adjust, and approve them for payment.

**3.4.2 Requirements:**
*   `FR-401` The system shall provide a structured, electronic `Fee Voucher` form for **Defense Attorneys** to claim hours and expenses, pre-populated with case and attorney data.
*   `FR-402` The system shall apply statutory and local rate tables (e.g., hourly caps, travel rates) automatically during voucher submission.
*   `FR-403` The system shall enforce a review workflow where an **OAA Staff** reviewer must approve, modify (with notes), or reject a submitted voucher.
*   `FR-404` The system shall export all approved voucher data in a format suitable for import into the county's financial/payroll system.

#### 3.5 Reporting & Compliance
**3.5.1 Description:** This feature generates standardized reports required by law and ad-hoc reports for operational management.

**3.5.2 Requirements:**
*   `FR-501` The system shall generate the official `Texas Fair Defense Act Report` in the exact format specified by the State, covering all required metrics (time to appointment, contact, etc.).
*   `FR-502` The system shall provide standard operational reports (e.g., `Attorney Assignment Summary`, `Voucher Approval Status`, `Case Aging Report`).
*   `FR-503` The system shall allow **OAA Administrators** to create and save ad-hoc report criteria based on all system data fields.

### 4. External Interface Requirements

#### 4.1 User Interfaces
*   The system shall employ a responsive, accessible web interface compatible with WCAG 2.1 AA standards.
*   A clean, role-specific dashboard shall be the primary UI for all logged-in users.
*   Key judicial actions (e.g., signing an order) shall have a clear, unambiguous UI.

#### 4.2 Hardware Interfaces
*   Support for barcode scanners or document scanners in OAA offices for linking paper documents to electronic records (if needed).

#### 4.3 Software Interfaces
*   `SI-001` **CCMS Integration Interface:** The system shall consume a daily XML/JSON feed from the CCMS via a secure REST API to synchronize `Case` and `Hearing` data. The system shall also be capable of pushing back `Appointment` and `Attorney of Record` data.
*   `SI-002` **Payment System Interface:** The system shall produce a nightly CSV flat file of approved vouchers for pickup by the county's financial system.

#### 4.4 Communications Interfaces
*   The system shall send email notifications for assigned appointments, pending reviews, and system alerts using the county's SMTP server.
*   External communications (to attorneys) shall be encrypted.

### 5. Non-Functional Requirements

#### 5.1 Performance Requirements
*   `NFR-P1` **Response Time:** 95% of all database transactions and page loads shall complete in under 3 seconds under normal load.
*   `NFR-P2` **Concurrent Users:** The system shall support up to 200 concurrent users without significant degradation.
*   `NFR-P3` **Data Volume:** The system shall be designed to efficiently handle a database growing by approximately 15,000 new cases and 50,000 vouchers per year.

#### 5.2 Safety Requirements
*   Not applicable (no physical safety implications).

#### 5.3 Security Requirements
*   `NFR-S1` The system shall implement role-based access control (RBAC) as defined in Section 2.3.
*   `NFR-S2` All user authentication shall integrate with the county's Active Directory/LDAP system.
*   `NFR-S3` All Personally Identifiable Information (PII) and case data shall be encrypted at rest and in transit (TLS 1.2+).
*   `NFR-S4` The system shall maintain a complete audit log of all user logins, data changes, and key actions (appointments, approvals).

#### 5.4 Software Quality Attributes
*   **Availability:** 99.5% uptime during core business hours (7 AM - 7 PM, CST).
*   **Reliability:** System shall have a mean time between failures (MTBF) of greater than 720 hours.
*   **Maintainability:** The system shall be modular with comprehensive technical documentation to allow county IT staff to perform routine maintenance.
*   **Usability:** New users shall be able to complete core tasks (e.g., log a contact, submit a voucher) with less than 15 minutes of training, as measured by user acceptance testing.
