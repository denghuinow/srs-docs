## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the HVAC Automated Fault Detection and Diagnosis (AFDD) System. The primary purpose of this document is to provide a detailed description of the system's capabilities, interfaces, and performance characteristics. It is intended for use by the project stakeholders, developers, testers, and project managers to guide the design, implementation, and verification of the system.

### 1.2 Document Conventions
This document follows standard SRS conventions. Requirements are uniquely identified with tags (e.g., `FR-001`, `NFR-001`). Markdown formatting is used for structure, with headers, lists, and code blocks to enhance readability.

### 1.3 Intended Audience and Reading Suggestions
*   **Project Sponsors & Managers:** Should focus on Sections 1 (Introduction), 2 (Overall Description), and 5 (Non-Functional Requirements) to understand project scope and constraints.
*   **Developers & System Architects:** Should read the entire document, with particular emphasis on Sections 3 (System Features) and 4 (External Interface Requirements) for detailed functional specifications.
*   **QA Engineers & Testers:** Should use Sections 3 and 5 to derive test cases and validation criteria.
*   **End-Users & Subject Matter Experts:** Should review Sections 2.3 (User Characteristics) and 3 (System Features) to confirm the system meets operational needs.

### 1.4 Project Scope
The HVAC AFDD System is a desktop software application designed to automate the detection and diagnosis of performance and operational faults within Heating, Ventilation, and Air Conditioning (HVAC) subsystems, specifically chillers and cooling towers. The system utilizes pattern-recognition algorithms on a combination of real-time sensed data and fixed system parameters to identify faults, thereby replacing manual expert analysis. The core value proposition is increased operational efficiency, reduced energy waste, and proactive maintenance for building systems.

## 2. Overall Description

### 2.1 Product Perspective
The AFDD System is a new, standalone software product. It will interact with external data sources (sensors, data historians, batch files) and present information to users via a graphical user interface. Its architecture must be modular to allow for future expansion to other HVAC subsystems (e.g., air handling units, pumps).

### 2.2 Product Functions
The high-level functions of the system are:
1.  **Fault Detection & Diagnosis:** Automatically identify predefined faults in chiller and cooling tower subsystems.
2.  **Data Acquisition & Validation:** Ingest and validate data from both real-time streams and static batch files.
3.  **Continuous Monitoring & Logging:** Run ongoing diagnostics on connected units and persistently store all results.
4.  **Results Presentation & Browsing:** Provide an intuitive interface for users to navigate current and historical diagnostic information.

### 2.3 User Characteristics
| User Role | Primary Goal | Technical Expertise |
| :--- | :--- | :--- |
| **Building Operator** | Daily system health monitoring, responding to active fault alerts. | Moderate. Comfortable with building management systems and basic software UIs. |
| **HVAC Service Technician** | Diagnose root cause of identified faults, perform recommended fixes. | High. Deep understanding of HVAC mechanics; may have limited software training. |
| **Energy Service Provider** | Analyze historical fault trends to advise on energy efficiency improvements. | High. Data-literate, uses analytics software regularly. |
| **Building Operator Supervisor** | Oversee overall system health, generate reports on fault frequency and resolution. | Moderate to High. Managerial focus, requires summary views and reporting. |

### 2.4 Constraints
1.  **Platform Constraint:** The application must be compatible with and run on Microsoft Windows-compatible operating systems (e.g., Windows 10, Windows 11, Windows Server 2019+).
2.  **Design for Extensibility:** The software's core architecture and data model must be designed to facilitate the future incorporation of diagnostic algorithms for additional HVAC subsystems without requiring a major redesign.
3.  **Algorithm Dependency:** System accuracy is inherently constrained by the logic and thresholds defined within the implemented pattern-recognition algorithms.

### 2.5 Assumptions and Dependencies
*   **Assumption:** Reliable and correctly calibrated sensor data will be available from the connected HVAC systems or provided in batch files.
*   **Assumption:** Users possess basic training on the operation of the software.
*   **Dependency:** The system depends on the provision and validation of specific pattern-recognition algorithms for chillers and cooling towers by the domain experts (algorithm developers).

## 3. System Features

### 3.1 Fault Detection and Diagnosis
**Description:** This feature is the core analytical engine of the system. It applies configured pattern-recognition algorithms to input data to detect operational anomalies and diagnose specific faults.

**Requirements:**
*   `FR-001`: The system shall execute pre-defined diagnostic algorithms for chiller subsystems (e.g., refrigerant undercharge, condenser fouling, reduced water flow).
*   `FR-002`: The system shall execute pre-defined diagnostic algorithms for cooling tower subsystems (e.g., fan motor failure, low water level, fouled fill).
*   `FR-003`: For each detected fault, the system shall generate a diagnostic record containing:
    *   A unique fault identifier and name.
    *   Timestamp of detection.
    *   Identifier of the source HVAC unit.
    *   Severity level (e.g., Warning, Critical).
    *   A descriptive text of the fault.
    *   The probable root cause(s).
    *   Recommended corrective action(s).

### 3.2 Data Input and Validation
**Description:** This feature handles the acquisition of data from external sources and ensures its validity before processing.

**Requirements:**
*   `FR-004`: The system shall accept real-time data input from connected sensing devices or building automation system (BAS) gateways via a configurable communication protocol (e.g., Modbus TCP, BACnet IP).
*   `FR-005`: The system shall accept historical or test data via user-uploaded batch files in a specified format (e.g., CSV, JSON).
*   `FR-006`: The system shall validate all incoming data for:
    *   **Format Compliance:** Adherence to expected data types and structures.
    *   **Range Checks:** Values within physically plausible limits (e.g., temperature > -50°C and < 200°C).
    *   `FR-007`: The system shall log all data validation errors and alert the user without processing the invalid data set.

### 3.3 Monitoring and Logging
**Description:** This feature manages the ongoing surveillance of configured HVAC units and the persistent storage of all system activities and results.

**Requirements:**
*   `FR-008`: The system shall provide a configuration interface for users to select which HVAC units to monitor and at what sampling interval.
*   `FR-009`: The system shall continuously monitor data from selected units and automatically execute diagnostic algorithms at the configured frequency.
*   `FR-010`: The system shall log all diagnostic results (`FR-003`) to a persistent, searchable database.
*   `FR-011`: The system shall maintain an audit log of significant system events (e.g., user logins, configuration changes, data source connectivity loss).

### 3.4 User Interface and Results Browsing
**Description:** This feature provides the visual interface for all user interactions, focusing on the hierarchical navigation of fault data.

**Requirements:**
*   `FR-012`: The system shall provide a hierarchical browsing interface, allowing users to navigate from a site/building level down to individual HVAC units.
*   `FR-013`: For a selected unit, the interface shall display a **Current Status Dashboard** showing:
    *   Overall health indicator.
    *   List of active faults with severity highlighted.
    *   Key real-time sensor readings.
*   `FR-014`: The system shall provide a **Historical Results Viewer** with filtering capabilities by:
    *   Date/Time range.
    *   HVAC unit.
    *   Fault type.
    *   Severity level.
*   `FR-015`: From any list of faults (current or historical), the user shall be able to select a fault to view its full diagnostic record (details from `FR-003`).

## 4. External Interface Requirements

### 4.1 User Interfaces
*   **UI-001:** A graphical desktop application with a main navigation pane (hierarchy tree), a content display area (dashboard/details), and a menu/toolbar for system functions (configuration, data import, reporting).
*   **UI-002:** All fault displays shall use a consistent color scheme (e.g., Red for Critical, Amber for Warning, Green for Normal).

### 4.2 Hardware Interfaces
*   **HI-001:** The system shall communicate with sensing devices and BAS networks via standard PC network interfaces (Ethernet, Wi-Fi) using industry-standard protocols.

### 4.3 Software Interfaces
*   **SI-001:** The system shall include drivers or libraries to support communication protocols for data acquisition (e.g., Modbus, BACnet).
*   **SI-002:** The system shall interface with a relational database (e.g., SQLite, Microsoft SQL Server Express) for persistent data storage.

### 4.4 Communications Interfaces
*   **CI-001:** Communication with real-time data sources shall support configurable IP addresses, port numbers, and polling intervals.

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
*   `NFR-001`: The system shall process incoming data and execute diagnostics for a single unit within 5 seconds of data receipt under normal load.
*   `NFR-002`: The user interface shall respond to any user action (click, filter) with a latency of less than 2 seconds.

### 5.2 Safety Requirements
*   `NFR-003`: The software shall not send control signals or commands that could alter the physical state of the connected HVAC equipment. It is a monitoring and diagnostic tool only.

### 5.3 Security Requirements
*   `NFR-004`: The system shall implement user authentication (username/password) with role-based access control (e.g., Operator: view only; Technician: view & acknowledge faults; Supervisor: full configuration access).
*   `NFR-005`: All stored data, including credentials, shall be encrypted at rest.

### 5.4 Software Quality Attributes
*   **Reliability:** `NFR-006`: The system shall achieve 99.5% operational uptime during scheduled building operating hours.
*   **Availability:** `NFR-007`: In case of a loss of connection to a real-time data source, the system shall continue running and log the connectivity issue, resuming monitoring automatically upon restored connection.
*   **Maintainability:** `NFR-008`: The system's algorithm module shall be designed as a plug-in architecture, allowing new diagnostic libraries (e.g., for Air Handling Units) to be added via configuration without modifying the core application code.
*   **Portability:** `NFR-009`: The software shall be compatible with the 64-bit versions of Microsoft Windows 10 and Windows 11.
