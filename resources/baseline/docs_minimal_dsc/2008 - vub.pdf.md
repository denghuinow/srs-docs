### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the Publication Repository System (PRS). The PRS is a bibliographic and full-text publication management system designed to store, organize, and provide controlled access to academic and research publications. This document is intended for use by the project stakeholders, developers, testers, and project managers to guide the design, implementation, and verification of the system.

#### 1.2 Scope
The PRS will provide a centralized repository for publications, accessible via both a web interface and a command-line interface (CLI). The system's core capabilities include automated metadata extraction from uploaded documents, sophisticated search and retrieval functions, and comprehensive user and access control management. The system will operate within a specific technical environment (the Wilma server) and adhere to strict development constraints regarding programming language, framework usage, and web standards.

**In-Scope:**
*   User registration, authentication, and role-based authorization.
*   Publication upload with automatic metadata parsing.
*   Advanced search across bibliographic data and full text.
*   Publication download with access control.
*   Management of user accounts, groups, and system-wide configuration.
*   Web interface compliant with specified standards.
*   CLI for administrative and batch operations.

**Out-of-Scope:**
*   Integration with external authentication systems (beyond VUB-network IP recognition).
*   Mobile-specific application development.
*   Advanced text mining or data analytics beyond basic search.
*   Long-term archival preservation features (format migration, checksum auditing).

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **PRS:** Publication Repository System.
*   **VUB:** Vrije Universiteit Brussel (contextual user role).
*   **W3C:** World Wide Web Consortium.
*   **XHTML:** Extensible HyperText Markup Language.
*   **CLI:** Command Line Interface.
*   **Metadata:** Structured data describing a publication (e.g., title, author, abstract, keywords).
*   **Wilma Server:** The designated Linux-based production server for the system.

### 2. Overall Description

#### 2.1 Product Perspective
The PRS is a new, self-contained system. It will interact with the underlying Linux operating system on the Wilma server, a file system for storing publication files, and a database (to be selected) for storing metadata and system data. Users will access it via standard web browsers or system shell access for the CLI.

#### 2.2 Product Functions
The high-level functions of the PRS are:
1.  **Publication Management:** Ingest, store, index, retrieve, and distribute publication files and their associated metadata.
2.  **User & Access Management:** Control system access through user accounts, roles, and permissions at individual and group levels.
3.  **Search & Discovery:** Provide efficient and effective search mechanisms for locating publications.
4.  **System Administration:** Configure system parameters, manage back-end processes, and oversee all content and users.

#### 2.3 User Characteristics
| User Role | Description | Key Activities |
| :--- | :--- | :--- |
| **Guest** | Unauthenticated public user. | Browse public metadata; search; download publicly accessible publications. |
| **VUB-Network User** | User accessing from a recognized VUB IP address. | All Guest functions. |
| **Member** | Registered, authenticated user. | All VUB-Network User functions; upload personal publications; manage personal profile. |
| **Publisher** | Privileged member (e.g., research group). | All Member functions; upload publications on behalf of a group; manage group-specific metadata. |
| **Moderator** | Content administrator. | All Member functions; approve/reject uploaded publications; edit metadata for publications within assigned scope; manage comments or flags. |
| **Administrator** | System super-user. | All functions; manage all user accounts and roles; configure system settings (e.g., metadata schemas, group structures); access system logs; perform CLI operations. |

#### 2.4 Constraints
1.  **Technical Environment:** The system must be deployed and run on the Linux-based "Wilma" server.
2.  **Implementation Language:** The application must be implemented in the Ruby programming language.
3.  **Framework Restriction:** The use of full-stack web application frameworks (e.g., Ruby on Rails, Sinatra) is prohibited. Low-level libraries for specific tasks (e.g., database connectivity, PDF parsing) are permitted.
4.  **Web Standard:** All dynamically generated web pages must comply with the W3C XHTML 1.0 Transitional standard.
5.  **Software Engineering Practices:** The design and code must follow specified object-oriented design principles and coding conventions (to be provided in a separate coding standards document).

#### 2.5 Assumptions and Dependencies
*   The Wilma server will have a stable installation of a compatible Ruby interpreter.
*   Necessary system libraries for desired metadata extraction (e.g., from PDF, DOC) will be available or installable.
*   A suitable SQL database (e.g., PostgreSQL, MySQL) is available on the Wilma server.

### 3. Specific Requirements

#### 3.1 Functional Requirements

##### 3.1.1 User Management (UM)
*   **UM-1: User Registration**
    *   The system shall allow a Guest to register as a Member by providing a valid email address, a chosen password, and basic profile information.
*   **UM-2: User Authentication**
    *   The system shall authenticate users via email/password credentials.
    *   The system shall automatically recognize users from the VUB network via IP address and grant them the "VUB-Network User" role for the session.
*   **UM-3: Role-Based Access Control (RBAC)**
    *   The system shall enforce permissions based on the user roles defined in Section 2.3.
*   **UM-4: Profile Management**
    *   An authenticated Member shall be able to view and edit their own profile information (e.g., name, contact details).
*   **UM-5: Administrative User Control**
    *   An Administrator shall be able to create, view, modify, disable, and delete any user account.
    *   An Administrator shall be able to assign and revoke roles (Publisher, Moderator, Administrator) to any Member.

##### 3.1.2 Publication Upload and Metadata Extraction (PU)
*   **PU-1: File Upload**
    *   An authorized user (Member, Publisher, Moderator, Admin) shall be able to upload one or more publication files (e.g., PDF, DOC) via the web interface.
*   **PU-2: Automatic Metadata Extraction**
    *   Upon upload, the system shall automatically extract bibliographic metadata (e.g., title, author, abstract, publication date, keywords) from the uploaded document's content and/or headers.
*   **PU-3: Metadata Validation and Editing**
    *   The uploader shall be presented with the extracted metadata in an editable form for validation and completion before final submission.
*   **PU-4: Submission Workflow**
    *   Publications uploaded by a Member may be subject to moderation (configurable by an Administrator).
    *   The system shall place such publications in a "pending" state, visible only to the uploader and Moderators/Administrators.
*   **PU-5: Batch Upload (CLI)**
    *   An Administrator shall be able to ingest batches of publications and associated metadata via a command-line interface tool.

##### 3.1.3 Search and Retrieval (SR)
*   **SR-1: Basic and Advanced Search**
    *   The system shall provide a simple search box for full-text and metadata search.
    *   The system shall provide an advanced search interface allowing field-specific queries (title, author, year, etc.) and Boolean operators.
*   **SR-2: Search Results**
    *   The system shall display search results in a list, showing key metadata (title, authors, year, abstract snippet).
    *   Results shall be paginated.
*   **SR-3: Publication Detail View**
    *   Selecting a result shall display a detailed view with all stored metadata for that publication.
*   **SR-4: File Download**
    *   From the detail view, a user shall be able to download the full-text file, subject to the publication's access permissions.

##### 3.1.4 Access Control and Permissions (AC)
*   **AC-1: Publication Visibility Levels**
    *   The uploader/administrator shall be able to set a publication's visibility to: Public, VUB-Network only, or Group-specific.
*   **AC-2: Group Management**
    *   An Administrator shall be able to create and manage groups (e.g., "Department of Computer Science").
    *   An Administrator shall be able to assign users (Members, Publishers, Moderators) to groups.
*   **AC-3: Group-Based Permissions**
    *   A Publisher assigned to a group shall be able to upload publications visible to that group.
    *   A Moderator assigned to a group shall have moderation rights over publications within that group.

##### 3.1.5 System Administration (SA)
*   **SA-1: Configuration Management**
    *   An Administrator shall be able to modify system configuration via a web interface or CLI (e.g., enable/disable moderation, define metadata fields, set default visibility).
*   **SA-2: System Monitoring (CLI)**
    *   The CLI shall provide utilities for system health checks, log inspection, and re-indexing of search data.

#### 3.2 Non-Functional Requirements

##### 3.2.1 Performance
*   **PER-1:** The system shall support concurrent access by at least 50 users without significant degradation in response time.
*   **PER-2:** A simple search query shall return results within 3 seconds under normal load.
*   **PER-3:** The metadata extraction process for a standard PDF shall complete within 30 seconds of upload.

##### 3.2.2 Security
*   **SEC-1:** All passwords shall be stored using a strong, salted cryptographic hash.
*   **SEC-2:** All web sessions shall be managed securely to prevent hijacking.
*   **SEC-3:** Direct file system access to publication files shall be prevented; downloads must be served through the application layer enforcing ACLs.
*   **SEC-4:** The CLI shall be accessible only to users with system shell accounts on Wilma and shall require additional authentication/authorization within the tool.

##### 3.2.3 Software Quality Attributes
*   **RELI-1:** The system shall maintain an uptime of 99.5% during core business hours.
*   **MAIN-1:** The codebase shall adhere to the provided Ruby coding conventions, ensuring readability and maintainability.
*   **COMP-1:** The web interface shall render correctly in all major browsers that support XHTML 1.0 Transitional (e.g., Firefox, Chrome, Safari, Edge).

##### 3.2.4 Design Constraints
*   **DC-1:** The application shall be structured using Object-Oriented Design principles.
*   **DC-2:** The front-end HTML must be generated by the Ruby application and validate as W3C XHTML 1.0 Transitional.
