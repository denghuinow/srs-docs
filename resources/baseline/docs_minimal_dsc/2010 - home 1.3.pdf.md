### 1. Introduction

#### 1.1 Purpose
This Software Requirements Specification (SRS) document describes the functional and non-functional requirements for the Smart Home Management System (SHMS) Prototype. The intended audience includes the project stakeholders, development team, quality assurance engineers, and technical management. This document will serve as the primary reference for system design, implementation, and verification.

#### 1.2 Scope
The SHMS Prototype is a web-based application designed to simulate the management of a home's environment, security, and appliances. The system operates entirely within a simulated software environment, with no physical hardware components. The core capabilities are bounded to the management of:
*   **Environmental Controls:** Up to eight (8) simulated thermostats and eight (8) simulated humidistats.
*   **Security System:** Up to fifty (50) simulated contact sensors (e.g., door/window sensors) with alarm functionality.
*   **Appliance/Light Controls:** Up to one hundred (100) simulated appliances or lights with binary (on/off) power states.

The system will provide a centralized web interface for monitoring status and issuing control commands to all simulated devices.

#### 1.3 Definitions, Acronyms, and Abbreviations
*   **SHMS:** Smart Home Management System.
*   **DH Technician:** Designated Home Technician. A privileged user responsible for system setup and maintenance.
*   **SRS:** Software Requirements Specification.
*   **UI:** User Interface.
*   **API:** Application Programming Interface.
*   **Simulated Environment:** A software-based model that mimics the behavior of physical devices without actual hardware.

### 2. Overall Description

#### 2.1 Product Perspective
The SHMS Prototype is a standalone, self-contained web application. It will simulate device states and behaviors internally. The primary interface is a modern web browser. The architecture will follow a client-server model, with a backend server managing the simulation logic and a frontend providing the user interface.

#### 2.2 Product Functions
The high-level functions of the system are:
1.  **Environmental Monitoring & Control:** Display real-time readings and allow setpoint adjustments for temperature and humidity zones.
2.  **Security System Management:** Display the status (open/closed) of contact sensors, arm/disarm the security system, and visualize/acknowledge alarm states.
3.  **Appliance & Light Control:** Display the power state of simulated appliances/lights and allow users to toggle them on or off.
4.  **System Configuration:** Allow a DH Technician to configure simulated devices (name, location, type, parameters).
5.  **User Management:** Provide authentication and role-based access (General User vs. DH Technician).

#### 2.3 User Characteristics
| User Class | Description | Key Responsibilities | Technical Skill Level |
| :--- | :--- | :--- | :--- |
| **General Home User** | Primary end-user of the home system. | Monitor home status, adjust environment settings, control appliances/lights, arm/disarm security. | Basic; familiar with web applications. |
| **DH Technician** | Responsible for initial setup and ongoing maintenance of the SHMS. | Configure simulated devices, assign devices to zones, perform system diagnostics, manage user accounts. | Advanced; understands system concepts and configuration. |

#### 2.4 Constraints
1.  **Development Constraints:**
    *   The project must be completed within **twelve (12) months**.
    *   The development team consists of **five (5) engineers**.
    *   The system must be developed for a **simulated environment only**. No physical I/O or device drivers are required.
2.  **Economic Constraints:** Design and implementation must prioritize minimal component costs, favoring open-source technologies and frameworks.
3.  **Technical Constraints:** The system shall be accessible via standard web browsers (Chrome, Firefox, Safari, Edge) from desktop and tablet devices.

#### 2.5 Assumptions and Dependencies
*   **Assumption:** Users have a reliable network connection to access the web interface.
*   **Assumption:** The simulated device behaviors (e.g., temperature change rate) will be defined by simple, deterministic algorithms.
*   **Dependency:** The project relies on the availability of selected open-source web development frameworks and libraries.

### 3. Specific Requirements

#### 3.1 External Interface Requirements

##### 3.1.1 User Interfaces
*   **UI-1:** A responsive web-based dashboard providing a consolidated view of system status.
*   **UI-2:** Dedicated panels/views for:
    *   Environmental controls (thermostats/humidistats with gauges and setpoint sliders).
    *   Security system status (sensor map/list, arm/disarm button, alarm indicator).
    *   Appliance/light control (grid/list of devices with toggle switches).
*   **UI-3:** A login screen for user authentication.
*   **UI-4:** A configuration interface (accessible only to DH Technicians) for adding, modifying, and removing simulated devices.

##### 3.1.2 Software Interfaces
*   **SI-1:** The frontend and backend shall communicate via a RESTful API using JSON data format.
*   **SI-2:** The backend simulation engine shall maintain the state of all devices in a structured data model.

#### 3.2 Functional Requirements

##### 3.2.1 Authentication & Authorization
*   **FR1:** The system shall require user login to access the control dashboard.
*   **FR2:** The system shall distinguish between "General User" and "DH Technician" roles.
*   **FR3:** Only users with the "DH Technician" role shall access the system configuration interface.

##### 3.2.2 Environmental Control (Thermostats & Humidistats)
*   **FR4:** The system shall simulate and display the current temperature for up to 8 thermostats.
*   **FR5:** The system shall allow an authenticated user to set a target temperature (setpoint) for any individual thermostat.
*   **FR6:** The system shall simulate and display the current relative humidity for up to 8 humidistats.
*   **FR7:** The system shall allow an authenticated user to set a target humidity (setpoint) for any individual humidistat.
*   **FR8:** The system shall visually indicate when a thermostat or humidistat is actively working to reach its setpoint (e.g., "Heating", "Cooling", "Humidifying").

##### 3.2.3 Security System Management
*   **FR9:** The system shall simulate and display the status (Open/Closed) of up to 50 contact sensors.
*   **FR10:** The system shall allow an authenticated user to arm or disarm the entire security system.
*   **FR11:** When armed, if the system detects a simulated "Open" signal from any contact sensor, it shall trigger a security alarm.
*   **FR12:** The system shall provide a clear, persistent visual and auditory indicator in the UI when an alarm is active.
*   **FR13:** The system shall require a DH Technician to acknowledge and reset an alarm state.

##### 3.2.4 Appliance & Light Control
*   **FR14:** The system shall simulate and display the power state (On/Off) for up to 100 appliances/lights.
*   **FR15:** The system shall allow an authenticated user to toggle the power state of any individual appliance or light.

##### 3.2.5 System Configuration (DH Technician Only)
*   **FR16:** The system shall allow a DH Technician to add, name, assign a location/zone to, and remove simulated devices (thermostats, humidistats, contact sensors, appliances).
*   **FR17:** The system shall allow a DH Technician to configure basic simulation parameters for devices (e.g., initial temperature for a zone, sensor normal state).

#### 3.3 Non-Functional Requirements

##### 3.3.1 Performance Requirements
*   **PERF-1:** The web dashboard shall update the status of all simulated devices at a minimum interval of **5 seconds**.
*   **PERF-2:** User control actions (e.g., toggling a light, setting a temperature) shall result in a UI update confirmation within **2 seconds**.

##### 3.3.2 Safety & Security Requirements
*   **SEC-1:** User passwords shall be stored using industry-standard hashing algorithms (e.g., bcrypt).
*   **SEC-2:** All API communications shall be secured using HTTPS/SSL.

##### 3.3.3 Software Quality Attributes
*   **QUAL-1: Usability:** The UI shall be intuitive enough for a General User to perform primary functions with less than 15 minutes of familiarization.
*   **QUAL-2: Reliability:** The core simulation and control backend shall have an uptime of 99.9% during development and testing phases.
*   **QUAL-3: Maintainability:** The codebase shall be modular with clear separation between simulation logic, API layer, and UI components. Documentation for the simulation API shall be provided.

##### 3.3.4 Design Constraints
*   **DC-1:** The application shall be built using a technology stack that minimizes licensing costs (e.g., Node.js/Python backend, React/Vue.js frontend, PostgreSQL/MySQL database).
*   **DC-2:** The simulation shall be deterministic and repeatable to facilitate testing.
